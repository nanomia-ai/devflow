# 개인 워크플로우 설정

사용자가 반복해서 원하는 실행 방법을 매번 설명하지 않도록 현재 팀원의 Work·Verify 개인 설정을
관리한다. 이번 실행에만 쓸 지시는 저장하지 않는다. 지속 설정의 생성·수정·초기화를 요청했을 때만
파일을 바꾸며, 작업 계약·단계·관리권·검증 의무는 개인 설정으로 변경하지 않는다.

이 스킬을 수행하기 전에 `references/communication.md`를 열고 설명·질문·보고에 적용한다. 이어서
`references/project-gate.md`를 열고 모든 target이 진입할 수 있는 상태일 때만 편집한다. Work 계약이나
활성 관리권은 요구하지 않으며, 이 스킬을 `next_route`로 기록하거나 프로젝트를 초기화·복구하지 않는다.
현재 팀원은 gate의 기존 team identity를 사용한다.

유효한 편집에서는 `references/member-preferences.md`를 열고 권위·충돌·검증 경계를 적용한다.

## 지원하는 설정만 다룬다

작성 범위는 현재 팀원의 `.devflow/team/<current-member>/preferences/work.md`와 `verify.md`다. Work에는
구현 접근, 결함 재현·원인 판단과 자체 점검 방법을, Verify에는 기존 검증 항목의 관찰 순서·반례·경계
입력과 증거 확인 방법을 둔다. 사용자가 범위를 물으면 요청과 관련된 선택지만 설명하고 파일을 만들지
않는다. 지속 설정인지 실제로 불명확할 때만 질문한다. `direct.md`나 다른 스킬 설정은 만들지 않는다.

요청한 파일만 읽는다. 두 역할을 함께 조정하거나 양쪽 관계를 실제로 판단해야 할 때만 같은 팀원의
상대 파일을 읽는다. 다른 팀원 파일, 프로젝트 정본과 활성 작업 artifact는 편집하지 않는다. 개인화를
위한 추가 문서·상태·등록부·보조 스크립트를 만들거나 그 생성을 개인 파일에 지시하지 않는다.

## 기존 의미를 보존해 편집한다

사용자가 원하는 이유·행동·적용 조건을 이해하고 관련 없는 기존 선호를 보존한다. 허용된 방법으로
같은 목적을 표현할 수 있으면 그 표현으로 작성한다. 목적이나 효과가 달라지는 대안은 저장하기 전에
차이를 설명하고 선택을 받는다. 공유 계약과 충돌하는 요구 및 그에 의존하는 내용은 제외하며, 거부한
요구를 다른 말의 새 선호로 바꾸지 않는다. 유효한 내용이 없으면 파일을 만들지 않는다.

개인 파일은 프로젝트의 표준 `summary`와 `read_when` header를 가진 Markdown으로 쓰고,
`read_when`에는 이 선호를 적용할 작업 조건을 적는다. 본문에는 이유와 원하는 방법을 자기완결적으로
설명하되 Work·Verify의 공통 규칙이나 작업 이력을 복제하지 않는다.

첫 설정은 요청한 파일과 필요한 부모 폴더만 만든다. 일부 해제는 요청한 선호만 제거하고, 전체 초기화는
명시한 개인 파일 하나만 삭제한다. 기존 내용이 이미 요청을 충족하면 다시 쓰지 않는다. 기존 파일을
읽을 수 없거나 병합 충돌이 있으면 추측해 교체하지 않는다. 쓰기 직전 현재 내용을 다시 대조하고,
예기치 않은 변경이 있으면 멈춰 보존할 내용을 확인한다.

## 실제 결과를 확인한다

완료 뒤 생성·수정·삭제 결과를 다시 확인한다. commit하지 않으며, 변경·삭제한 개인 파일 경로와 아직
commit되지 않았다는 사실, 달라질 실행 방법과 제외한 요구를 보고한다. 설정의 실제 효과는 다음
Work·Verify 진입에서 판단되므로 편집만으로 행동이 입증됐다고 보고하지 않는다.
