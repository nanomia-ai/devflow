## 0. 이 문서의 위치와 판정 기준

`docs/v0.13.0-plan_ko.md`는 현재 구현을 설명하는 리포트가 아니다. v0.12.0 구현과 그 독립
검증 뒤에 다시 세운 **차기 구현 플랜**이다. 따라서 이 검증은 플랜의 문장을 현재 동작으로
간주하지 않았다.

판정에 사용한 권위 순서는 다음과 같다.

1. `docs/design.md` — 이미 채택하거나 기각한 결정의 이유
2. 현재 v0.12.0 스킬·판정 정본·역할 계약 — 플랜이 바꾸려는 실제 출발점
3. `docs/v0.13.0-plan_ko.md` — 이번 검증의 설계 대상
4. `docs/v0.12.0-usage-flow-validation-report_ko.md` — 앞선 결함과 재현 기준선

플랜과 현재 구현이 다른 것은 결함이 아니다. 다음 중 하나가 재현될 때만 결함으로 판정했다.

- 플랜 안의 두 결정을 함께 지킬 수 없다.
- 지원한다고 선언한 정상 사용 동선에서 상태 소실·중복 실행·유령 점유가 생긴다.
- 생산자·소비자·종료점·중단 복구 중 하나가 빠져 AI가 다음 행동을 결정할 수 없다.
- 실제 Git이나 플랫폼 동작이 플랜이 전제한 동작과 다르다.
- 앞선 기각 이유를 반증하지 않고 같은 구조를 다른 이름으로 다시 도입한다.

단어를 다른 단어로 바꾸면 끝나는 취향 차이는 소견으로 세지 않았다. 모든 확정 소견에는
시작 상태, 문자 실행, 잘못된 결과가 있다. 반대로 실패 경로가 없는 설명 추가도 권하지 않는다.

이 리포트는 증거 수준을 섞지 않는다. §5~§7의 각 소견에서 `발견 사실`은 현재 플랜을
문자 실행하거나 Git으로 재현한 결과만 담고, `해결 방식 및 방향 판단`은 그 뒤의 설계
제안으로 분리한다. §8은 개별 수리를 하나의 상위 모델로 합친 권고안이다. 해결책이 기술적으로
가능하다는 판정은 발견 사실을 약화하지 않으며, 권고안을 선택하지 않았다고 재현 결과가
사라지지도 않는다.

## 1. 결론

### 1.1 최종 판정

**v0.13.0 플랜은 방향이 크게 좋아졌지만, 현재 형태 그대로 구현을 시작할 단계는 아니다.**

좋아진 핵심은 분명하다. 통합 브랜치를 어느 작업 폴더도 checkout하지 않는 배치, 실제 Git
실험을 먼저 한 태도, 요청 소실을 막는 다중 도메인 인식, Codex 중복 전달 채널 제거, 닫힌
역사의 읽기 비용 축소는 모두 문제를 정확히 겨냥한다. v0.12.0의 카드·진행 로그·능력 문서·
검증 폐쇄 골격도 폐기할 이유가 없다.

그러나 동시 작업의 중심 모델에는 아직 서로 양립하지 않는 네 결정이 있다.

```
공유 진실은 통합 브랜치 하나다
+ 통합에 못 써도 새 공유 상태를 각 브랜치에서 계속 만든다
+ 뒤처진 브랜치의 점유는 읽지 않는다
+ 같은 물리 작업 폴더의 여러 자율 writer를 공식 지원한다
```

첫 문장을 지키려면 나머지 세 문장에 경계가 필요하다. 지금 경계로는 살아 있는 형제
워크트리의 점유가 사라지고, 완료했지만 아직 통합되지 않은 카드는 다시 점유되며, 같은 작업
폴더의 HANDOFF·journal·Git index 갱신은 조용히 서로를 덮을 수 있다.

구현 전에 다시 결정해야 할 차단 항목은 다음 네 개다.

1. 카드 상태를 통합 하나에 둘지, 워크트리별 전이를 합성할지
2. 통합을 쓸 수 없을 때 허용할 동작의 범위
3. 같은 물리 작업 폴더의 동시 writer를 지원 범위에서 뺄지, 직렬화 장치를 만들지
4. 카드 번호와 검증 출처 id를 통합 밖에서 발급할지

이 네 가지를 닫지 않고 문구부터 구현하면 기존 규칙 위에 예외가 더 생긴다. 반대로 아래의
권장 모델로 정리하면 새 상태 기계 대부분이 필요 없다. §8의 재검토에서는 이 목적을
integration CAS, claim-generation fencing, 카드별 workspace 격리로 기술적으로 닫을 수 있음을
확인했다.

### 1.3 기술적으로 불가능한 경계

다음 넷은 문구를 정교하게 고쳐도 해결되지 않는다.

- **공유 쓰기 지점이 전혀 없는 서로 다른 clone에서 새 카드 번호와 점유를 전역 중복 없이
  발급하는 것.** 두 clone이 서로를 볼 수 없으면 둘 다 같은 대기 카드를 정당하게 점유할 수
  있다. 공유 ref, 중앙 coordinator, 또는 사전 배정 중 하나가 반드시 필요하다.
- **같은 물리 작업 폴더의 여러 자율 세션이 임의 파일을 동시에 고쳐도 소실되지 않는다고
  보장하는 것.** 협력하는 helper가 devflow 쓰기를 직렬화할 수는 있지만, 편집기·사람·다른
  도구가 같은 파일에 쓰는 것까지 prompt 규칙으로 원자화할 수 없다.
- **`Read first`와 현재 `git status`만 보고 카드가 앞으로 쓸 정확한 경로를 아는 것.**
  `Read first`는 입력 집합이고 새 파일과 구현 중 발견은 미래 정보다. 예측값을 기록하거나
  작업 공간을 격리할 수는 있어도 사실로 계산할 수는 없다.
- **사용자 승인 없이 새 hook을 자동 신뢰시키면서 보안 경계를 유지하는 것.** 자동 승인은
  신뢰 경계를 제거한다. 기존 경로를 잠시 유지하고 사용자가 새 command를 확인하는
  two-stage 전환만 안전하다.

이 한계는 devflow의 실패가 아니라 분산 쓰기와 공유 파일의 성질이다. 플랜이 이를 보장 범위
밖으로 정확히 선을 그으면 문제가 사라진다.

## 2. 잘 설계된 부분

결함만 나열하면 플랜을 잘못 평가하게 된다. 다음 방향은 유지하는 편이 낫다.

### 2.1 측정 뒤 결정하는 순서

Git worktree, checkout된 브랜치 갱신, 병합 충돌을 임시 저장소에서 먼저 실행한 것은 옳다.
특히 “통합 브랜치를 어떤 worktree도 쥐지 않게 둔다”는 6.1은 v0.12.0 대표 동선의 첫 점유
차단을 직접 없앤다. 이 배치는 같은 Git common directory 안의 여러 worktree에서 가장 작은
조정 지점이다.

### 2.2 기존 뼈대를 보존한 판단

플랜은 다음 중심 구조를 불필요하게 뒤집지 않는다.

- 파일 이름의 상태 접미사
- 카드 안의 append-only 진행 로그
- 한 카드의 완료 신호와 작업 커밋
- 능력 폐쇄 때 검증 구역 전면 교체
- 사용자 승인과 구속 결정의 Git 흔적
- 새 요청을 먼저 journal에 보존하고 나중에 계획하는 순서

이 부분은 v0.12.0 독립 검증에서도 단일 흐름과 중단 복구에서 강한 것으로 확인됐다.

### 2.3 비용을 기능과 분리한 판단

L1·L3·L4처럼 의미를 유지한 채 전달량이나 명령 수만 줄이는 방향은 타당하다. 반대로 Layer 0
재읽기와 깨끗한 검토를 줄이려던 L5를 철회한 이유도 맞다. 컨텍스트 압축 뒤 “전에 읽었다”는
기억은 원문 보유와 같지 않다.

### 2.4 플랫폼 의미를 하나로 둔 판단

Claude와 Codex용 규칙을 따로 설계하지 않고 공통 `SKILL.md`와 companion 문서를 쓰는 방향이
맞다. 플랫폼별 차이는 설치·발견·hook 신뢰 같은 전달 계층에서만 다뤄야 한다. 현재 Codex
0.146.0에서 네이티브 `devflow:work`를 명시 호출한 깨끗한 세션이 실제 설치 경로의
`principles/SKILL.md`와 `state-predicates.md`를 찾아 읽는 것도 확인했다.

### 2.5 사용자의 변경과 모호한 목적지를 정상 입력으로 본 판단

6.14와 6.15는 AI가 앞선 계획을 방어하거나 목적지를 지어내는 경로를 막는다. 이미 있는
checkpoint → release → replan 패턴을 재사용하고, 결정할 수 없는 목적지만 묻기 때문에 새
상태 기계도 필요 없다.

### 3.2 실제 Git 재현

| 실험 | 시작 상태 | 결과 | 플랜에 주는 의미 |
|---|---|---|---|
| 형제 worktree 점유 | 통합 `I0`에서 A·B가 서로 다른 카드를 점유 | A만 통합하면 B HEAD는 새 통합 tip을 품지 않음 | 6.5 필터가 살아 있는 B 점유를 숨김 |
| 동시 통합 갱신 | 두 브랜치가 같은 `I0`에서 서로 다른 변경을 push | 첫 push 성공, 둘째는 정상 non-fast-forward | “못 올림”이 아니라 재평가·재시도할 정상 경쟁 |
| 로컬 ref CAS | 두 writer가 같은 예상 OID로 `git update-ref` 실행 | 첫 갱신 성공, stale writer는 128, 새 tip에서 replay는 성공 | 별도 lock service 없이 한 ref를 원자 조정점으로 쓸 수 있음 |
| 원격 ref CAS | 별도 clone 둘이 같은 remote tip에서 일반 fast-forward push | 첫 push 성공, stale push는 1, fetch 뒤 새 parent로 replay 성공 | writable remote ref도 같은 조정 모델을 제공함 |
| journal union | 한쪽은 기존 요청 A 삭제, 다른 쪽은 A 유지+B 추가 | union 결과에 삭제한 A가 부활하고 B도 추가 | W4는 현재 journal 상태 기계와 양립 불가 |
| Codex companion | 네이티브 `$devflow:work`를 read-only 깨끗한 실행으로 호출 | 설치된 principles와 state predicates를 실제로 읽음 | 6.10의 핵심 전제 하나는 현재 CLI에서 통과 |

첫 실험의 핵심 출력은 다음과 같았다.

```text
before: flow-a contains I0 = true; flow-b contains I0 = true
after integrating A: flow-b contains current integration = false
integration still has B as pending
```

journal 실험의 최종 파일은 삭제된 A와 새 B를 모두 가졌다. `merge=union`이 추가끼리는
보존한다는 측정은 맞지만, 현재 journal은 추가 전용 파일이 아니다.

CAS 두 실험의 결과는 다음과 같았다.

```text
local:  first=0, stale-writer=128, replay=0
remote: first=0, stale-push=1, replay=0
replay parent = previous winner tip
```

이 측정은 **ref 갱신의 원자성**을 증명한다. 카드 선택, journal 의미, 검증 판정까지 Git이
대신 판단한다는 뜻은 아니다. 그 의미 규칙은 정본에 남고, helper는 예상 OID와 실제 OID가
같을 때만 이미 결정된 전이를 게시해야 한다.

두 CAS fixture는 임시 저장소에서 실행한 뒤 제거했다. 대상 프로젝트의 branch·ref·worktree는
실험에 사용하지 않았다.

### 3.3 같은 작업 폴더 문자 실행

실제 wall-clock 경합을 만들지 않아도 lost update는 상태 순서만으로 재현된다.

```text
HANDOFF = D0
A가 D0을 읽음
B가 D0을 읽음
A가 D0+D1을 씀
B가 이미 계산한 D0+D2를 씀
최종 = D0+D2, D1 소실
```

“쓰기 직전에 다시 읽는다”는 두 읽기 사이에 쓰기가 없을 때 둘 다 만족한다. 따라서 이 문장은
동시 writer를 직렬화하지 않는다.

### 3.4 검증의 한계

플랜은 아직 구현되지 않았으므로 실제 v0.13.0 end-to-end 사이클은 실행할 수 없다. 이 리포트는
현재 정본에 플랜의 전이를 적용한 Git fixture와 문자 실행 결과다. 구현 뒤에는 §13의 수용
fixture를 실제 저장소 상태 전이 테스트로 다시 실행해야 한다.

리포트 추가 뒤 현재 저장소 불변식은 `node --test "scripts/*.test.js"`에서 **73/73 통과**했고
`git diff --check`도 통과했다. 이는 보고서가 현재 배포물을 바꾸거나 저장소 형식을 깨지
않았다는 확인일 뿐, 아직 없는 v0.13.0 동작의 의미 안전성 증거는 아니다.

## 4. 먼저 분리해야 할 세 위상

플랜의 동시성 문제는 “워크트리를 지원하느냐” 하나가 아니다. 다음 세 위상은 관측 가능성과
안전 조건이 다르다.

| 위상 | 서로 보이는 것 | 안전한 공유 조정점 | 판정 |
|---|---|---|---|
| 한 물리 작업 폴더의 여러 터미널 | 파일·index·HEAD 전부 즉시 공유 | 한 writer 또는 프로세스 lock | 자율 동시 쓰기 보장 불가 |
| 같은 common-dir의 여러 worktree | Git object·ref 공유, 파일·index 분리 | checkout되지 않은 integration ref | 공식 병렬의 가장 좋은 기본형 |
| 서로 다른 clone·기계 | push된 ref만 공유 | writable remote ref 또는 coordinator | ref가 없으면 새 공유 전이 금지 |

`git worktree list`는 두 번째 위상만 열거한다. 다른 clone의 작업은 보지 못한다. 같은 물리
작업 폴더의 터미널도 구분하지 못한다. 따라서 worktree 목록을 “모든 흐름의 전역 등록부”로
부르면 세 위상이 다시 섞인다.

### 4.1 권장 운영 모델

가장 작은 안전 모델은 다음과 같다.

```
사람 신원       owner.md와 Git author identity
실행 위치       현재 worktree 경로·branch — 신원이 아님
공유 상태 권위  integration ref 하나
작업 상태       각 작업 공간의 코드·진행 로그 checkpoint
```

공유 상태 전이는 integration에 성공한 뒤에만 유효하다.

- 번호·출처 id 발급
- 카드 생성·승인·점유·해제·완료
- journal 예약 줄 생성·교체·삭제
- 능력 폐쇄와 verify 상태
- Layer 0·능력 문서의 구속 결정

통합이 일시적으로 막히면 **이미 통합에 점유가 예약된 카드의 task-local 코드와 진행 로그
checkpoint만** 로컬에서 계속할 수 있다. 새 점유, 새 번호, 완료 공개, journal 소비는 기다린다.
오케스트레이터가 병렬 worker를 만들 때는 worker를 띄우기 전에 통합에서 카드를 만들고
점유까지 예약하면 된다.

이 모델에서는 worktree HEAD를 공유 상태로 합성할 필요가 없고, 뒤처진 HEAD가 완료 카드를
되살리는 문제도 없다.

## 5. 차단 소견

### V13-01 · 6.5가 살아 있는 형제 점유를 숨긴다

**등급: 차단**

#### 발견 사실

재현:

1. 통합 `I0`에 대기 카드 A와 B가 있다.
2. worktree A와 B가 각각 `I0`에서 갈라져 서로 다른 카드를 점유한다.
3. 이때 두 HEAD 모두 `I0`를 품으므로 6.5에서 두 점유가 보인다.
4. A의 점유나 경계가 통합되어 새 tip `I1`이 된다.
5. B는 계속 정상 작업 중이지만 B HEAD는 아직 `I1`의 조상이 아니다.
6. 6.5는 B worktree 전체를 “뒤처짐”으로 제외한다.
7. 통합에는 B 카드가 여전히 대기이므로 세 번째 세션이 B를 다시 점유할 수 있다.

“뒤처진 HEAD는 끝난 카드를 되살린다”는 진단은 맞다. 그러나 HEAD 전체를 최신/뒤처짐으로
나누면 **한 카드의 오래된 상태와 다른 카드의 아직 통합되지 않은 새 상태를 함께 버린다.**
Git branch의 신선도는 전역 boolean이 아니라 카드별 delta다.

추가 실패 경로도 있다. B가 통합 불가 상태에서 카드까지 완료하면 B HEAD에는 `.wip.`가 더는
없고 통합에는 대기 카드가 남는다. “점유만 더한다”는 규칙으로는 완료된 미통합 작업이 아무
상태에도 나타나지 않아 같은 카드가 다시 실행된다.

#### 해결 방식 및 방향 판단

**기술 판정: 해결 가능. 권장안은 통합 단일 권위이고, 대안은 더 큰 카드별 전이 투영이다.**

- 공유 카드 상태를 integration tip 하나에서만 읽는다.
- 최초 점유는 반드시 integration에 CAS 방식으로 착지한 뒤 구현한다.
- integration이 막혔을 때는 이미 예약된 점유의 로컬 구현만 계속한다.
- `.done.`과 의존 준비 판정은 경계가 integration에 착지한 뒤에만 참이다.

worktree HEAD 합성을 반드시 유지한다면 다음 전부가 필요하다.

1. 각 HEAD와 integration의 merge-base를 구한다.
2. 카드 번호별로 base→HEAD 전이와 그 전이를 처음 만든 commit을 구한다.
3. integration의 현재 카드 상태가 그 전이의 예상 선행 상태와 같을 때만 미통합 전이를 적용한다.
4. integration이 `.done.`·`.stale.`이면 옛 `.wip.`를 적용하지 않고 뒤처진 작업으로 보고한다.
5. 같은 선행 상태에서 서로 다른 두 전이가 나오면 합성하지 않고 충돌로 보고한다.
6. squash·rebase로 commit ancestry가 바뀌는 경우를 위한 origin token도 정의한다.

이 대안은 기술적으로 가능하지만, 플랜이 피하려는 새 식별자와 상태 기계를 다시 만든다.

### V13-02 · 같은 물리 작업 폴더의 여러 자율 writer는 안전장치 둘로 보호되지 않는다

**등급: 차단**

#### 발견 사실

6.2는 같은 파일 편집만 보장 밖으로 둔다. 하지만 서로 다른 카드도 정상 경계마다 같은 종류의
공유 대상을 쓴다.

- 같은 사람의 `HANDOFF.md`
- `journal.md`
- 같은 Git index와 현재 branch HEAD
- Layer 0와 능력 문서
- 전체 working tree를 보는 completion signal과 formatter

append-only는 데이터 모양이지 원자적 쓰기 연산이 아니다. AI의 patch 도구가 현재 파일을 다시
읽고 적용을 거절할 수도 있고, 오래 읽은 전체 파일을 쓸 수도 있다. Claude와 Codex 모두에서
한 문장만으로 동일한 원자성을 보장할 수 없다.

Git의 `index.lock`도 충분하지 않다. `git add`와 `git commit` 사이에 다른 세션이 다른 경로를
stage하면 첫 세션의 commit이 남의 staged 경로까지 담을 수 있다. 한 명령의 잠금은
읽기→판정→파일 쓰기→stage→commit 전체 트랜잭션을 잠그지 않는다.

#### 해결 방식 및 방향 판단

**기술 판정: 임의 writer를 prompt만으로 안전하게 만드는 것은 불가능하다. 한 writer 제한,
helper 직렬화, 또는 작업 공간 격리는 기술적으로 가능하다.**

- 여러 터미널의 **존재와 순차 전환**은 지원한다.
- 한 물리 작업 폴더에서 동시에 쓰는 devflow writer는 하나라고 명시한다.
- 진짜 병렬 writer는 worktree로 분리한다.
- 같은 작업 폴더에서 다른 세션은 읽기·긴 외부 조회 정도만 허용하고, 결과 적용과 commit은
  현재 writer가 맡는다.

같은 repo root에서 시작하는 사용자 경험만 필수라면 둘째 카드 writer를 카드별 managed
worktree로 이동시키는 §8.5 프로필 B가 더 완전한 우회다. 사용자는 같은 위치에서 시작하지만
실제 파일·index는 공유하지 않는다.

같은 **물리** worktree의 공식 동시 writer가 제품 요구라면 helper가 필요하다.

1. Git common-dir 아래에 원자적으로 획득하는 repository transaction lock을 둔다.
2. lock 안에서 예상 integration OID와 대상 파일 바이트를 다시 읽는다.
3. 정확 경로만 쓰고 stage한 뒤 commit한다.
4. 예상 OID가 바뀌면 쓰지 않고 재평가한다.
5. PID·host를 확인할 수 없는 stale lock은 자동 제거하지 않고 사용자에게 묻는다.
6. 이 보장은 helper를 따르는 devflow 메타데이터 쓰기에만 적용한다고 명시한다.

이 helper도 임의 소스 파일을 동시에 고치는 외부 편집기까지 보호하지 못한다. 따라서 소스
동시 편집 보장은 여전히 worktree 격리가 필요하다.

### V13-03 · 6.3의 무제한 탈출은 “공유 진실은 통합”과 충돌한다

**등급: 차단**

#### 발견 사실

플랜은 통합에 못 올리면 브랜치에 둔 채 계속하고, 나중에 resume으로 정리한다고 한다. 이때
다음 항목까지 각 브랜치에서 독립 생성되면 병합 전에는 전역 답이 없다.

- 누가 어느 카드를 점유했는가
- 다음 카드 번호와 verify 출처 id가 무엇인가
- 어떤 요청이 소비됐는가
- 어떤 카드가 완료되어 의존을 열었는가
- 어느 Layer 0 결정이 하위를 지배하는가

같은 common-dir worktree끼리는 모든 local ref를 볼 수 있지만 별도 clone은 그렇지 않다.
`git worktree list`도 다른 기계의 clone을 열거하지 않는다. 따라서 “나중에 합치면 된다”는
규칙은 한 저장소 안의 병합 실험을 다중 기계에 일반화한다.

같은 저장소 안에서도 worktree 목록은 미통합 상태의 영속 권위가 될 수 없다. 오케스트레이터나
사람이 작업을 합치기 전에 worktree를 제거하고 `git worktree prune`을 실행하면 목록에서 흐름이
사라진다. branch ref가 남으면 사람이 찾아 복구할 수 있지만 projection은 더는 읽지 않고,
detached HEAD까지 정리되면 commit이 도달 불가능해질 수 있다. 점유가 integration에 먼저 있으면
작업 위치가 사라져도 카드는 계속 claimed로 남아 이 사고를 탐지할 수 있다.

#### 해결 방식 및 방향 판단

**기술 판정: 범위를 제한하면 해결 가능하다. 공유 ref·coordinator·사전 배정이 모두 없으면
새 전역 전이는 불가능하다.**

정확한 범위는 다음처럼 나눠야 한다.

| 동작 | integration 불가 중 허용 |
|---|---|
| 이미 전역 점유된 카드의 코드 편집 | 예 |
| 그 카드의 로컬 진행 로그·checkpoint | 예, 아직 공유 완료 아님 |
| 새 카드·번호·출처 id 발급 | 아니오 |
| 새 점유·해제·완료 | 아니오 |
| journal 예약 상태 생성·소비 | 아니오 |
| Layer 0·능력 문서·verify 상태 변경 | 아니오 |

오케스트레이터가 integration을 직접 쥐고 있다면 해결책은 worker가 흩어진 뒤 상태를 추측하는
것이 아니다. 오케스트레이터가 integration의 coordinator가 되거나, 아무 worktree도 checkout하지
않는 별도 `devflow-main`을 먼저 만들고 카드와 점유를 예약한 뒤 worker를 띄워야 한다.

서로 통신할 ref나 coordinator가 없는데도 새 점유를 허용하는 안전한 일반 해법은 없다. 이 경우
멈추는 것이 기술적 한계에 맞는 동작이다.

### V13-04 · `merge=union`은 삭제·교체 상태를 되살린다

**등급: 차단**

#### 발견 사실

현재 journal은 append-only 로그가 아니다. 정상 절차가 다음을 수행한다.

- 계획 완료 뒤 `유지보수 라우팅 대기` 삭제
- 능력 폐쇄 뒤 수확한 `능력 관측` 삭제
- `증거 대기`를 `증거 마감`으로 교체하거나 삭제
- product 검증 실행 상태를 결과 상태로 교체
- 사건 요청과 층 열기 marker 삭제

실제 fixture에서 한쪽 branch가 A를 소비해 삭제하고 다른 branch가 A를 유지한 채 B를 추가했을
때 union 결과는 A+B였다. 소비한 A가 다시 살아난다. 다음 resume은 A를 새 요청으로 다시
계획할 수 있다.

#### 해결 방식 및 방향 판단

**기술 판정: 해결 가능하다. W4 제거와 최신 상태 재생이 최소 수리다.**

수리 선택지는 둘이다.

- 권장: W4를 제거하고 최신 integration 상태에서 정본 전이를 replay한다. 의미가 유지되지
  않으면 일반 Git conflict가 아니라 구조화된 `INVALID_STATE`로 멈춘다.
- 대안: record key와 허용 전이를 아는 semantic merge driver를 만든다. 독립적인 add끼리만
  합치고 delete-vs-retain, replace-vs-replace는 충돌로 남긴다.

journal 전체를 진짜 append-only event log로 바꾸고 tombstone을 fold하는 방법도 가능하지만
v0.13.0 범위를 넘는 전면 상태 모델 교체다.

### V13-05 · 정상적인 non-fast-forward를 구조적 “통합 불가”로 오판할 수 있다

**등급: 높음**

#### 발견 사실

아무도 쥐지 않은 integration에도 두 worker가 같은 tip에서 동시에 push하면 한쪽은 정상적으로
non-fast-forward가 된다. 이는 6.1의 실패가 아니라 동시성 제어가 작동한 것이다. 6.3의 탈출로
보내면 서로 다른 카드의 점유가 불필요하게 흩어진다.

에러 문구는 locale과 Git 버전에 따라 달라질 수 있으므로 문자열로 분류하지 않는다.

#### 해결 방식 및 방향 판단

**기술 판정: 해결 가능하다.**

1. mutation 전에 integration OID `I0`를 저장한다.
2. 갱신 실패 뒤 integration을 다시 읽어 `I1`을 얻는다.
3. `I1 != I0`이면 정상 경쟁이다. 새 상태에서 같은 카드 패자는 물러나고, 다른 카드면
   merge/rebase 뒤 규칙을 다시 판정하고 재시도한다.
4. `I1 == I0`인데 실패했으면 checkout 보유·권한·보호·네트워크 같은 구조적 문제로 보고한다.
5. 구조적 문제일 때만 V13-03의 제한된 로컬 계속 경로를 쓴다.

### V13-06 · 완료 카드까지 재번호화하는 수리는 불변 식별자와 충돌한다

**등급: 높음**

#### 발견 사실

플랜 §7.1 문단 3은 번호가 겹치면 끝난 카드도 중간 삽입 번호로 바꾸고 의존을 갱신한다고 한다.
현재 정본은 파일명 본체와 번호를 불변 식별자로 선언한다. 완료 뒤 번호는 다음 위치에 남을 수
있다.

- 다른 카드의 `Depends`와 `Covered cards`
- HANDOFF·journal·verify locator
- 작업·checkpoint commit 제목
- 외부 CI·이슈·사람의 링크

현재 파일의 의존만 고쳐도 Git 역사와 외부 참조는 바뀌지 않는다. 두 완료 카드가 이미 같은
번호로 각자 외부에 알려졌다면 어느 참조가 어느 카드를 뜻하는지 일반적으로 복원할 수 없다.

#### 해결 방식 및 방향 판단

**기술 판정: 충돌 예방은 가능하다. 이미 외부에 노출된 두 완료 id의 의미를 증거 없이
완전 자동 복구하는 것은 불가능하다.**

수리는 사후 재번호화가 아니라 **통합에서 발급 예약을 먼저 하는 것**이다.

- integration에 번호가 착지하지 않으면 새 카드를 실행하지 않는다.
- 충돌은 대기·미점유 단계에서만 해소한다.
- 이미 점유·완료된 충돌은 자동 renumber하지 않고 integrity incident로 보고한다.
- 꼭 복구해야 하면 origin commit을 붙인 수동 대응표와 live reference 교체가 필요하며, Git
  역사와 외부 참조는 legacy alias로 남는다고 솔직히 기록한다.

verify 출처 id도 같은 원리다. integration 밖에서 독립 발급한 뒤 숫자만 바꾸면 locator가
깨진다.

### V13-07 · 워크트리 이름표가 사람 신원과 실행 위치를 한 개념으로 만든다

**등급: 높음**

#### 발견 사실

6.4의 “흐름 하나 = 이름표 하나 = 방 하나”는 기각된 `users/<person>/flows/<flow>`를 Git
설정으로 다시 표현한 것이다. 아직 기각 이유를 충분히 반증하지 못했다.

- per-worktree `user.name`·`user.email`은 commit 작성자와 감사 흔적을 바꾼다.
- 방 id는 사람 신원인데 worktree 수명으로 만들면 한 사람이 여러 사람처럼 보인다.
- worktree가 삭제돼 Git 관리 항목은 prune되어도 repo에 commit된 `devflow/users/<id>/` 방은
  남는다. “닫는 기점이 Git에 있다”가 방의 종료를 해결하지 않는다.
- 서로 다른 id가 되면 같은 id×단위 정합성 규칙을 우회한다.
- 같은 물리 작업 폴더의 여러 터미널은 per-worktree 설정으로도 구분되지 않는다.

#### 해결 방식 및 방향 판단

**기술 판정: 해결 가능하다. Git author는 사람 신원으로 보존하고 실행 위치는 별도
작업 공간 결합으로 다룬다.**

권장안:

- `user.name`·`user.email`과 room id는 계속 사람을 뜻한다.
- 현재 worktree path·branch는 실행 위치 정보일 뿐 상태 식별자로 만들지 않는다.
- resume은 사용자가 현재 연 worktree에서만 이어가고, 다른 위치가 의심되면
  `git worktree list`의 경로·branch를 보여 주어 사람이 고르게 한다.
- 자동 위치 복원이 필수라면 worktree-local 결합에 card path와 claim commit OID를 저장하고,
  생성·완료·release·takeover·prune 복구를 정의한다. room과 Git author는 바꾸지 않는다.

claim commit OID는 이미 정합성 검사에서 추적하는 값이므로 새 전역 식별자가 아니다. 다만
managed worktree까지 도입하려면 `docs/design.md`의 비관리 결정 이유를 정식으로 반증하고
수명주기 비용을 받아들여야 한다.

### V13-08 · 6.9는 편집 겹침을 사실로 계산하지 못한다

**등급: 높음**

#### 발견 사실

`Read first`는 카드가 읽을 입력이다. 카드가 고치거나 새로 만들 파일 목록이 아니다.
`git status`는 한 작업 폴더의 모든 미커밋 경로를 보여 주지만 어느 터미널·카드가 만든 것인지
말하지 않는다. 따라서 두 집합을 나란히 둬도 “겹침 사실”이 되지 않는다.

또한 현재 정본은 점유 카드의 병렬 승인값을 바꾸지 않고, 묶음을 바꾸려면 release 뒤 같은
계획 commit에서 승인들을 고치라고 한다. 6.9의 “하던 카드를 놓지 않고 두 카드의 parallel만
갱신”은 이 규칙과 승인 신선도를 동시에 뒤집는다.

워크트리도 의미 충돌을 자동으로 시끄럽게 만들지 않는다. 서로 다른 줄을 고친 두 변경이 Git
텍스트 merge에는 성공하면서 하나의 불변식을 함께 깨뜨릴 수 있다.

파일 격리와 실행 환경 격리도 다르다. worktree 둘이 같은 database, port, 개발 서버, 외부 test
account, 저장소 밖 cache를 쓰면 서로 다른 파일을 고쳐도 completion signal이 간섭한다. 현재
split의 “공유 개발 서버를 건드리지 않는다” 조건은 6.9 뒤에도 유지해야 한다.

#### 해결 방식 및 방향 판단

**기술 판정: 병렬 안전성은 격리와 통합 후 검증으로 확보할 수 있다. 미래 write-set의 완전
계산은 불가능하다.**

권장안:

- 계획 시점의 reciprocal parallel 승인을 유지한다.
- 실행 중 새 병렬 묶음이 필요하면 checkpoint → release → 묶음 전체 승인 갱신 → reclaim을
  거친다.
- 진짜 병렬은 worktree로 격리하고, merge 뒤 묶음의 completion signal을 통합 상태에서 다시
  실행한다.
- write-set 필드를 새로 넣는다면 “예측”이라고 부르고 사용자 확인을 받는다. 안전 증명으로
  쓰지 않는다.

### V13-09 · 다중 도메인 요청의 “같은 commit”은 batch 복구 계약이 아니다

**등급: 높음**

#### 발견 사실

6.7이 요청 소실을 발견한 것은 정확하다. 그러나 단위마다 한 줄을 같은 commit에 넣는 것만으로
다음이 결정되지 않는다.

- 각 줄이 원 요청 전체를 복제하는지, 자기 부분만 보존하는지
- 일부 단위만 매핑이 모호하거나 은퇴했을 때 나머지를 계획하는지
- 첫 줄의 층 열기 marker 뒤 세션이 중단되면 같은 batch를 어떻게 다시 찾는지
- 현재 “가장 이른 한 줄” 루프와 “한 번의 실행 제안 승인”을 어떻게 함께 지키는지
- 모든 카드가 착지하기 전에 어느 줄을 삭제할 수 있는지

현재 플랜은 독립 줄의 저장 형태와 원자 batch의 사용자 경험을 동시에 요구한다. 둘 사이의
복구 계약이 없으므로 어느 쪽인지 먼저 골라야 한다.

#### 해결 방식 및 방향 판단

**기술 판정: 해결 가능하다. 새 batch id 없이도 원 요청 locator를 공통 출처로 쓰는 원자
계획 전이가 가장 작은 완전안이다.**

권장안은 원 요청을 journal에 한 번만 보존하고, 영향을 받는 각 parent의 층 열기 marker가
그 **같은 exact source locator**를 가리키게 하는 것이다. 매핑이 전부 확정된 뒤 한 planning
commit이 모든 카드·승인·parent 변경을 만들고, marker 전부와 원 요청을 함께 삭제한다.
resume은 같은 source locator를 가진 활성 marker를 한 묶음으로 복구한다. 일부 단위가
모호하거나 은퇴했다면 begin commit 전에 질문하므로 원 요청은 그대로 남는다.

한 번의 승인과 원자 계획이 요구되지 않는 제품 선택이라면 단위별 독립 요청도 유효하다.
다만 그 경우에는 각 줄이 원문 전체와 자기 단위를 보존하고 자기 planning commit에서만
삭제되며, 승인도 단위별이라는 다른 UX를 명시해야 한다.

### V13-10 · 골조 지식 축적은 작성자와 신뢰 모델이 아직 없다

**등급: 높음**

#### 발견 사실

현재 기준선 정본은 다음을 명시한다.

- 골조에는 능력층 검증 폐쇄가 없다.
- 골조 검증 구역은 초기 `None.`과 `Verified at: none`을 유지한다.
- 검증 구역의 유일한 통상 작성자는 verify다.
- `Entrypoints`는 단순 변경 경로가 아니라 정확 경로·역할·진입 방식의 검증 서술이다.
- `Traps`는 증상·재현 조건·원인·대안 네 칸을 모두 요구한다.

6.6의 “카드가 실제로 건드린 경로를 진입점으로 옮긴다”는 변환은 기계적이지 않다. 변경된
테스트 fixture나 migration 파일은 entrypoint가 아닐 수 있다. carry나 관측 한 줄을 Trap 네
칸으로 바꾸는 것도 진위를 버리지 않는 복사 이상의 판단이다.

구현 전에 다음 여섯 값을 정해야 한다.

1. 발동: foundation 폴더가 처음 닫힐 때인지, 소비 능력이 닫힐 때마다인지
2. 작성자: verify의 새 비판정 경로인지, 다른 skill인지
3. 입력 snapshot: 어느 HEAD의 어느 카드·관측 줄까지인지
4. 출력 허용 절: Entrypoints·Traps·Verify 중 정확히 무엇인지
5. 신뢰: `Verified at:none`인 전체 구역을 독자가 어떻게 해석할지
6. 메타데이터: foundation의 `Covered cards`를 계속 빈 배열로 둘지 실제 카드 집합으로 쓸지

#### 해결 방식 및 방향 판단

**기술 판정: 의도는 해결 가능하지만 현재 6.6의 직접 쓰기 방식은 구현하면 안 된다.**

가장 작은 완전안은 골조 design zone과 fresh 소비 능력 baseline에서 출처·freshness를 보존한
view를 필요할 때 만드는 것이다. 이는 골조 verified zone을 쓰지 않으므로 거짓 검증 상태를
만들지 않는다. 지속 파일 쓰기가 꼭 필요하다면 별도의 “foundation harvest” 전이를 verify가
소유하게 하고, 결과를 검증 사실이 아니라 관측으로 명시하며, 사용자가 구조화 결과를 확인한
뒤 commit한다. 변경 경로를 자동으로 entrypoint라고 부르면 안 된다.

골조를 보통 능력처럼 실제 시나리오 검증하는 대안도 기술적으로 가능하다. 다만 이는 “골조용
검증 사건을 발명하지 않는다”는 기존 이유를 정식으로 뒤집는 더 큰 결정이다.

### V13-11 · L1은 정합성 3·11만 보존해서는 충분하지 않다

**등급: 높음**

#### 발견 사실

닫힌 폴더 본문을 매번 읽지 않는 방향은 맞다. 그러나 플랜이 적은 질의 둘 외에도 다음 판정이
닫힌 역사에 의존한다.

- 전체 트리의 중복 카드 번호
- 활성 카드 `Depends`가 가리키는 정확히 하나의 `.done.` 카드
- HANDOFF·journal locator의 상태 접미사 제거 경로 해석
- baseline `Covered cards`와 현재 완료 집합 비교
- 번호 재사용 금지와 다음 번호 산출
- 닫힌 폴더 안의 잘못된 pending/wip 카드가 발견됐을 때 그 카드 필드 판정

#### 해결 방식 및 방향 판단

**기술 판정: 모델 통독 없이 기계 projection으로 해결 가능하다.**

수리는 전체 본문 통독이 아니다. helper가 전 트리에서 다음 최소 projection을 계산하고, 정상
항목은 모델에 출력하지 않으면 된다.

```text
path, depth-1 unit, card number, filename state, parent state
pending/wip 카드에 한해 Depends·Approval·Review
중복·미해결 locator·닫힌 폴더 이상 목록
```

정합성 15항 각각을 `projection으로 판정 / 이상 때 본문 1개 열기 / 해당 없음`으로 매핑한 표가
있어야 L1을 완료로 볼 수 있다.

### V13-12 · K1·K2는 작은 수리로 닫을 수 있지만 정확한 commit 경계가 필요하다

**등급: 높음**

#### 발견 사실

K1은 begin 뒤 들어온 새 능력 관측까지 정리 대상에 섞일 수 있고, K2는 관측이 남은 능력을
은퇴시키면 그 관측의 소비자가 사라진다. 어느 경우에도 현재 tip만 읽어 “관련 줄”을 판단하면
중단 전 snapshot과 뒤에 추가된 줄을 구별할 수 없다.

#### 해결 방식 및 방향 판단

**기술 판정: 기존 marker head와 exact-note gate로 해결 가능하다.**

K1은 새 marker 필드 없이 해결할 수 있다. 현재 능력 닫기 marker에는 begin 전 `head`가 이미
있다.

1. 기준선 갱신은 marker의 `head`에서 읽은 대상 능력 관측만 입력으로 쓴다.
2. 정리 때도 `git show <marker head>:devflow/journal.md`에 있던 정확한 대상 줄만 제거한다.
3. 같은 줄이 여러 번 있으면 그 snapshot의 발생 횟수만 제거한다.
4. begin 뒤 추가된 줄은 현재 journal에 남긴다.
5. baseline 무연산이면 기존 규칙대로 어느 줄도 제거하지 않는다.
6. snapshot에 있던 줄이 현재 journal에서 이미 사라졌거나 다르게 교체됐으면 추측해 계속하지
   않고 integration을 다시 읽어 전이를 재판정한다.

K2는 은퇴 전에 exact-note gate를 두면 된다.

- 대상 능력의 관측 줄이 0개면 그대로 은퇴한다.
- 하나 이상이면 정확한 줄을 보여 주고 각 줄을 폐기할지, 골조나 정확한 비은퇴 능력 번호로
  다시 지정할지 사용자에게 묻는다.
- 선택한 교체·삭제와 은퇴를 같은 구속 결정 commit에 둔다.
- 사용자가 미루면 은퇴도 미룬다.
- product·arch 내용으로 승격해야 하면 그 문서의 소유 skill을 먼저 실행하고 note가 없어진 뒤
  은퇴한다.

은퇴 commit이 다른 사람의 journal 줄까지 바꾸는 예외는 `product`에만 두면 안 된다. 공유
journal과 commit 규율을 소유한 `principles` 안에 정확한 예외·대상 줄·commit 경계를 선언하고
product는 그것을 참조해야 한다.

이 정도면 별도 6필드 disposition 상태 기계는 필요 없다.

## 7. 중간 중요도와 구현 완성도 소견

### V13-13 · “같은 단위 + 같은 완료 신호”만으로 묶으면 rollback 경계가 너무 넓어진다

**등급: 중간**

#### 발견 사실

`pnpm test`처럼 넓은 명령은 서로 무관한 변경도 공유한다. 같은 능력의 오래된 요청 여러 개를
한 카드로 묶으면 하나의 실패·revert·carry가 모두 결합된다.

#### 해결 방식 및 방향 판단

**기술 판정: exact bundle 승인으로 해결 가능하다.**

묶음은 최소한 다음을 모두 만족할 때 실행 제안에 정확한 item 목록으로 보여 주고 승인받는다.

- 같은 사용자 요청 또는 같은 승인 batch에서 나옴
- 같은 depth-1 단위
- 하나의 Destination으로 결과를 빠짐없이 말할 수 있음
- 하나의 completion signal이 각 item을 실제로 증명함
- 하나의 작업 commit으로 함께 되돌리는 것이 허용됨

“작다”를 AI가 임의 판정하는 지름길은 만들 필요가 없다. 사용자가 보는 묶음 목록과 승인으로
경계를 닫으면 된다.

### V13-14 · “한 번만 경고”와 “거절을 기억”할 저장 위치가 없다

**등급: 중간**

#### 발견 사실

6.3과 6.4는 다음 세션에도 반복하지 않는다고 하지만 producer·storage·consumer·cleanup이
없다. 대화 기억으로 구현하면 새 세션에서 다시 묻는다.

#### 해결 방식 및 방향 판단

**기술 판정: 로컬 범위인지 팀 범위인지 정하면 해결 가능하다.**

6.4 자체를 권장안대로 제거하면 거절 기억도 사라진다. 통합 불가 1회 안내를 유지한다면
worktree-local Git config의 전용 boolean처럼 repo 문서를 오염시키지 않는 위치를 쓰고, clone·
worktree별 값임을 명시한다. 팀 전체에서 한 번이라는 뜻이면 integration의 공유 상태가 필요하다.

### V13-15 · L4의 최적화는 가능하지만 한 실험을 “위험 없음”으로 일반화했다

**등급: 중간**

#### 발견 사실

카드마다 두 diff를 실행하는 대신 트리 전체 dirty path 집합을 한 번 만드는 것은 동치가 될 수
있다. 그러나 현재 한 실험은 rename·삭제·Unicode·index/working-tree 분리를 모두 덮지 않는다.

#### 해결 방식 및 방향 판단

**기술 판정: 경로 상태 행렬과 property test를 통과하면 해결 가능하다.**

구현은 적어도 다음을 지켜야 한다.

- `git diff --name-only -z --no-renames -- devflow/tree`
- `git diff --cached --name-only -z --no-renames <authority> -- devflow/tree`
- authority에 같은 정확 경로가 존재하는지 별도 확인
- 삭제·rename·type change·특수문자·공백·Unicode·case·submodule 경로 fixture
- index와 working tree가 서로 다른 세 단계 fixture

`-z` 없는 줄 parsing이나 rename detection 기본값에 의존하면 경로 하나가 둘로 합쳐지거나 옛
경로가 빠질 수 있다. 상태 행렬 property test가 모두 통과하면 L4는 넣어도 된다.

### V13-16 · L2는 파일을 반으로 나누기 전에 조항×소비자 경계를 증명해야 한다

**등급: 중간**

#### 발견 사실

progressive disclosure 방향은 맞지만 “resume은 읽기 계약만 필요하고 arch·adopt·verify는 쓰기
계약만 필요하다”처럼 둘로 단순 분리되지는 않는다.

- resume은 문서 shape와 freshness뿐 아니라 legacy migration·중단된 writer·경계 손상의 복구
  route도 판정한다.
- verify는 검증 구역 writer이면서 기존 verified state의 freshness와 no-op을 읽는다.
- arch·adopt는 설계 구역 writer이면서 기존 검증 구역 보존·migration 조건을 읽는다.
- work·reviewer·retrospector는 전체 정본이 아니라 서로 다른 bounded projection을 소비한다.

#### 해결 방식 및 방향 판단

**기술 판정: 조항×소비자 행렬에서 실제 절단선이 증명될 때만 가능하다.**

먼저 현재 `baseline-predicates`의 각 H2·규칙 묶음을 행으로, 소비자를 열로 둔 표를 만든다.

```text
조항 × arch | adopt | verify | resume | work projection | reviewer | retrospector
```

각 칸은 `직접 읽음 / companion이 투영 / 해당 없음` 셋 중 하나여야 한다. 한 조항이 두 파일에
복제되면 분할 실패다. 한 소비자가 두 파일을 항상 함께 읽으면 token 절감이 없으므로 역시
분할할 이유가 없다. resume의 recovery 묶음이 읽기/쓰기 경계를 자주 넘으면 이번 릴리스에서는
접는다는 플랜의 조건부 판단이 맞다.

분할할 때는 schema·freshness·reader projection을 한 companion에, writer lifecycle·migration을
다른 companion에 두되 공통 문장을 복제하지 않고 한쪽이 정확 절을 참조한다. Claude와 Codex
양쪽에서 필요한 companion만 실제로 도달하는지 consumer별 smoke test가 필요하다.

### V13-17 · 평면 프롬프트 생성을 지우기만 하면 이전 설치물이 남는다

**등급: 중간**

#### 발견 사실

Codex 네이티브 skill이 companion을 읽는 핵심 전제는 현재 CLI에서 통과했다. 공식 Codex 문서도
custom prompts를 deprecated로 표시하고 skill의 supporting files를 허용한다. 따라서 L3의 방향은
타당하다.

하지만 설치기에서 생성·purge 로직을 전부 삭제하면 이전 버전이 만든

수 있고, 플랜이 없애려던 이중 채널이 upgrade 환경에서 계속된다.

#### 해결 방식 및 방향 판단

**기술 판정: 한 릴리스의 표식 기반 migration cleanup으로 해결 가능하다.**

1. 한 릴리스 이상 migration cleanup을 유지한다.
2. 첫 줄의 devflow generated marker가 있는 정확한 8개 이름만 삭제한다.
3. 사용자가 직접 만든 같은 이름 파일은 자동 삭제하지 않는다.
4. clean install과 v0.12→v0.13 upgrade를 따로 검사한다.
5. `codex/AGENTS-devflow.md`와 README의 `/devflow-*` 안내를 네이티브 skill 호출로 바꾼다.

P-03은 L3이 끝나면 사라지지만, 그 전까지는 “결함 아님”이 아니라 **의도된 호환 tradeoff**다.
공식 `CODEX_HOME`을 프로필로 쓰는 사용자는 plugin과 prompt가 서로 다른 home에 놓인다.

참고: [Codex Skills](https://learn.chatgpt.com/docs/build-skills.md),
[Custom prompts](https://learn.chatgpt.com/docs/custom-prompts.md),
[Hooks](https://learn.chatgpt.com/docs/hooks.md).

### V13-18 · R-06·R-07·R-08은 인정됐지만 구현 계약은 아직 없다

### V13-19 · 여섯 결함 클래스는 분류표이지 상태 공간의 완전성 증명이 아니다

**등급: 중간**

#### 발견 사실

플랜 §9.3은 앞서 발견한 결함을 여섯 부류로 잘 정리했다. 그러나 관측된 표본에서 클래스를 만든 뒤
“클래스가 유한하므로 공간이 소진됐다”고 결론 내릴 수는 없다. 플랜 스스로 일곱 번째 클래스
가능성을 인정하므로 두 문장이 양립하지 않는다.

#### 해결 방식 및 방향 판단

**기술 판정: 문장 반복이 아니라 좌표 sweep 종료 조건으로 해결 가능하다.**

검증 종료 기준은 분류 이름 수가 아니라 다음 독립 좌표를 곱해 필수 칸을 판정하는 것이다.

```
작업 위상        한 tree / 같은 common-dir worktree / 다른 clone
integration      writable / advanced / checked-out / protected·offline
작업자           같은 사람·같은 id / 다른 사람 / bot·unresolved
전이 종류        add / replace / delete / rename / allocate / close
카드 상태        pending / claimed / checkpoint / evidence / done / stale
요청 기수        1단위 / 여러 단위 / 일부 모호 / 일부 은퇴
중단 위치        begin 전 / begin 뒤 / 파일 쓰기 뒤 / commit 뒤 / push 뒤
```

모든 조합을 문장으로 걷지 않아도 된다. 불가능 조합은 `해당 없음`, 기계적으로 같은 조합은
동치 근거를 쓰고 묶는다. 중요한 것은 각 필수 칸에 권위·다음 행동·commit 경계·복구·검사가
하나씩 있는지다.

이 방식이면 끝없는 문장 검토를 멈출 기준도 생긴다. 필수 위상에서 차단 칸이 0이고, 각 변경의
재현 fixture가 통과하며, 남은 칸이 명시적으로 보장 밖이면 기획 검증을 종료한다.

## 8. 상위 해결 모델과 기술 방향

이 장은 §5~§7의 발견을 다시 주장하는 곳이 아니다. 앞에서 확정한 실패 경로를 어떤 설계로
닫을 수 있는지, 그중 무엇을 권장하는지, 무엇은 끝까지 보장할 수 없는지를 분리해 기록한다.

### 8.1 해결 가능성 총괄

**devflow가 의도한 실용적 사용 경험은 기술적으로 구현 가능하다.** 발견된 19개 소견 가운데
15개는 정본·전이·검사 변경으로 닫을 수 있고, 4개는 요구의 문자적 전체를 보장할 수 없지만
격리·사전 예약·통합 후 검증으로 사용 목적을 보존할 수 있다. 스킬 전체를 포기해야 하는
절대 차단은 발견하지 못했다.

| 소견 | 기술 판정 | 권장 폐쇄 방식 | 남는 경계 |
|---|---|---|---|
| V13-01 | 가능 | 공유 카드 상태를 integration 하나에서만 읽음 | 미통합 HEAD는 증거이지 권위가 아님 |
| V13-02 | 목적 보존 가능 | 한 물리 worktree 한 writer 또는 카드별 격리 workspace | 임의 외부 writer의 동시 byte 쓰기는 보장 불가 |
| V13-03 | 가능 | 사전 claim 뒤 task-local 작업만 offline 허용 | 공유 ref가 없으면 새 공유 전이 불가 |
| V13-04 | 가능 | union 제거, 최신 상태에서 의미 전이 replay | 임의 text merge로 상태 의미 보존 불가 |
| V13-05 | 가능 | 예상 OID 비교로 race와 구조 실패 분리 | 경합은 정상적으로 재시도될 수 있음 |
| V13-06 | 예방 가능 | 번호·출처 id를 integration에서 선발급 | 과거 외부 참조의 모호성은 자동 복원 불가 |
| V13-07 | 가능 | 사람 신원과 workspace 결합 분리 | 위치를 사람 id로 쓰지 않음 |
| V13-08 | 목적 보존 가능 | 격리 후 integration에서 결합 검증 | 미래 write-set의 완전 예측 불가 |
| V13-09 | 가능 | 한 source locator를 공유하는 다중 marker 전이 | 독립 승인 UX를 택하면 원자 batch는 포기 |
| V13-10 | 가능 | 검증된 소비 능력에서 골조 view를 필요할 때 투영 | 골조 자체의 verified truth는 별도 검증 수명주기 필요 |
| V13-11 | 가능 | 정합성 projection helper | 이상 항목의 본문은 제한적으로 다시 읽음 |
| V13-12 | 가능 | marker head snapshot과 은퇴 전 exact-note gate | 사용자 처분이 없으면 은퇴가 대기함 |
| V13-13 | 가능 | exact item 묶음과 rollback 경계 승인 | 넓은 test command만으로는 묶지 않음 |
| V13-14 | 가능 | 로컬 안내와 팀 공유 결정을 다른 저장소에 둠 | 대화 기억만으로는 지속 불가 |
| V13-15 | 가능 | NUL path projection과 상태 행렬 property test | 검사 통과 전 최적화 교체 금지 |
| V13-16 | 조건부 가능 | 조항×소비자 행렬이 보이는 절단선만 분리 | 항상 함께 읽으면 분할 이익 없음 |
| V13-17 | 가능 | 한 릴리스의 표식 기반 잔존 prompt cleanup | 사용자 파일은 자동 삭제하지 않음 |
| V13-18 | 가능 | 각 수리에 권위·입력·commit·복구를 명시 | 새 pause 상태는 자동 발명하지 않음 |
| V13-19 | 가능 | 위상×전이×중단 좌표 sweep으로 종료 | 모든 미래 결함의 부재를 증명하는 것은 아님 |

여기서 “목적 보존 가능”은 문자 그대로의 요구를 몰래 낮춘다는 뜻이 아니다. 예를 들어 같은
repo root에서 두 터미널을 시작하는 UX는 유지할 수 있지만, 두 writer가 같은 물리 bytes를
직접 공유하게 두지 않고 두 번째 writer를 격리 worktree로 보내야 한다. 이 구분을 사용자에게
숨기지 않으면 모순이 아니다.

### 8.2 권장 상위 모델 — 조정 면과 실행 면의 분리

문제를 가장 적은 개념으로 닫는 구조는 다음 두 면이다.

```text
공유 조정 면
  integration ref 하나
  번호·출처 id·계획·점유·해제·완료·journal·verify·구속 결정
  예상 integration OID를 선행 조건으로 한 직렬 전이

로컬 실행 면
  카드별 격리 workspace
  코드·진행 로그·task-local checkpoint
  공유 전이를 만들 권위 없음
```

두 면 사이의 규칙은 다섯 개면 충분하다.

1. 공유 전이는 integration에 성공한 뒤에만 존재한다.
2. 구현은 integration에 보이는 claim 뒤에만 시작한다.
3. worker는 자기 claim 세대가 아직 현재일 때만 결과를 게시한다.
4. 경합은 최신 integration에서 같은 의미 전이를 다시 판정한다.
5. 여러 worker 결과의 의미 안전성은 integration에 모은 뒤 completion signal과 검토로
   판정한다.

이 구조는 worktree HEAD union, 완료 카드 재번호화, per-worktree 가짜 사람, journal union을
모두 불필요하게 만든다. 로컬 작업을 버리는 구조도 아니다. integration이 잠시 막혀도 이미
점유된 카드의 코드와 checkpoint는 진행할 수 있고, 새 공유 상태만 기다린다.

### 8.3 integration ref의 원자 전이

Git ref는 별도 lock server 없이 조정점으로 쓸 수 있다. §3.2의 로컬·원격 실험에서 같은 예상
OID를 가진 두 writer 중 하나만 성공했고, 패자는 최신 tip을 parent로 다시 만든 commit만
게시할 수 있었다.

권장 전이는 다음과 같다.

1. integration의 unabbreviated OID를 `expected`로 읽는다.
2. 그 commit의 정본 상태에서 전이의 선행 조건을 다시 판정한다.
3. 정확한 대상 경로만 바꾼 candidate commit을 `expected`의 자식으로 만든다.
4. 같은 common-dir의 local integration이면 expected-old-OID를 가진 `git update-ref`
   비교·교환을 쓴다. 단, integration이 어느 worktree에도 checkout되지 않았음을 먼저 확인한다.
5. remote integration이면 일반 fast-forward push를 쓴다. 거절되면 fetch한 새 tip에서
   candidate를 다시 만든다.
6. 새 tip에서 선행 조건이 사라졌다면 게시하지 않는다.

이는 “merge하고 되면 됨”과 다르다. 최신 상태에서 **의미 전이를 replay**한다.

- 다른 카드의 claim 경쟁이면 최신 상태에 자기 claim을 다시 적용할 수 있다.
- 같은 카드가 이미 다른 사람에게 claimed면 `CLAIM_LOST`다.
- journal A 삭제와 B 추가가 경쟁하면 최신 journal에서 B만 추가한다. A는 부활하지 않는다.
- 이미 done·stale인 카드에 오래된 claim이나 done 전이를 replay하지 않는다.

### 8.4 작은 결정론 helper의 경계

이 전이는 AI가 여러 Git 명령과 파일 쓰기를 매번 재구성하기에는 취약하다. `skill-creator`의
자유도 원칙에 따르면 이 부분은 낮은 자유도의 작은 cross-platform helper가 적합하다.

helper가 맡을 것은 **기계적 게시**뿐이다.

- expected OID와 현재 OID 비교
- 정본 predicate가 허용한 정확 전이의 입력 형식 확인
- 현재 사용자의 index와 분리된 임시 index 또는 격리 coordinator workspace에서 exact path만
  담은 candidate commit 생성
- local CAS 또는 remote fast-forward push
- 최신 tip에서 유한 횟수 replay
- 구조화된 결과 반환

반환값은 최소한 다음처럼 유한해야 한다.

| 결과 | 뜻 | 다음 행동 |
|---|---|---|
| `APPLIED` | 전이가 integration에 착지 | 새 tip에서 계속 |
| `RACE_RELOAD` | 다른 전이가 먼저 착지 | 최신 상태 재판정 |
| `CLAIM_LOST` | 같은 카드의 현재 점유가 다름 | 구현 전 중단 또는 명시 takeover |
| `BLOCKED` | coordination ref를 안전하게 읽거나 쓸 수 없음 | checkout·권한·보호·network blocker 보고 |
| `INVALID_STATE` | 예상 선행 상태와 디스크가 맞지 않음 | 쓰지 않고 integrity route |

첫 시도 뒤 자동 reload·replay는 최대 두 번, 총 세 번으로 제한하는 편이 안전하다. 그 뒤에는
“실패 사다리”를 오염시키지 말고 지속 경합으로 보고한다. 무한 재시도는 결함이다.

helper가 맡지 않을 것도 명시해야 한다.

- 카드 선택, 병렬 승인, journal 의미, verification verdict
- conflict의 의미적 자동 해결
- 사용자 대신 hook 신뢰 승인
- 임의 소스 파일을 쓰는 외부 도구의 직렬화

입력은 argument array나 JSON data로 전달하고 branch·path·사용자 요청을 shell command로
보간하지 않는다. Git path 출력은 NUL 구분을 유지한다. 정책은 정본에 있고 helper는 그 정책의
원자적 실행 장치다.

### 8.5 두 구현 프로필

| 프로필 | 사용자 경험 | 물리 안전성 | 설계 비용 |
|---|---|---|---|
| A · 최소 안전안 | 한 worktree 한 writer, 병렬은 사용자·오케스트레이터가 worktree 생성 | 가장 단순 | 낮음 |
| B · 동일 root 진입 UX | 사용자는 같은 root에서 시작할 수 있으나 둘째 카드 writer를 카드별 managed worktree로 이동 | 실제 쓰기는 격리 | 중간 |

**기본 구현은 A가 안전하다.** 다만 “사용자가 같은 repo root에서 여러 터미널을 열고 각자
작업한다”가 제품의 필수 UX라면 B도 기술적으로 가능하다. 이때 공식 보장은 같은 물리 폴더의
동시 쓰기가 아니라 **같은 진입점에서 시작한 세션을 서로 다른 물리 workspace로 자동
라우팅하는 것**이다.

B의 최소 수명주기는 다음과 같다.

1. 현재 physical worktree에 writer 결합이 없으면 첫 카드가 이를 사용한다.
2. 다른 카드 writer가 같은 worktree를 요구하면 카드 key를 가진 managed worktree를 만든다.
3. claim이 integration에 착지한 뒤 그 worktree에 `card + claim generation`을 결합한다.
4. done·release·retire 뒤 결합을 지운다.
5. worktree 제거는 결과와 경계가 integration에 있고 dirty 상태가 없을 때만 한다.
6. claim 경쟁에서 지면 새 worktree가 clean인지 확인한 뒤 제거하고 구현하지 않는다.
7. crash 뒤에는 claim이 integration에 남으므로 결합을 자동 폐기하지 않고 resume이 복구한다.

같은 카드를 두 터미널이 동시에 고치는 요구는 B로도 안전하지 않다. 이를 지원하려면 별도
broker·session lease와 편집 병합 정책이 필요하다. 그 제품 요구가 없다면 명시적으로 거부하는
편이 맞다.

이 프로필은 `docs/design.md`의 “devflow는 worktree workflow를 만들거나 관리하지 않는다”를
뒤집는다. 따라서 구현 플랜이 B를 선택하려면 기록된 이유를 먼저 반증해야 한다.

- “core edits가 공통이라 조정 비용이 이득보다 크다”는 이유는 공유 전이를 integration CAS로
  직렬화하고 managed worktree를 둘째 code writer에만 만들면 적용 범위가 달라진다.
- “작업 중 화면이 깨져도 된다”는 이유는 preview 격리에는 유효하지만, 서로의 source와 index를
  덮지 않는다는 새 실패 경로에는 답하지 않는다.

이 반증을 받아들이지 않으면 A를 선택해야 한다. B를 `flows/`나 새 사람 방으로 구현해서는
안 된다. 작업 위치의 수명은 Git worktree에, 작업 권위는 claim에 둔다.

### 8.6 사람 신원과 점유 세대

같은 사람이 여러 worktree·clone을 쓰는 모호성은 새 사람 id가 아니라 **점유 세대 fencing
token**으로 닫는 것이 적절하다.

- 사람 id와 Git author는 계속 owner.md의 실제 사람을 뜻한다.
- 최초 claim을 integration에 만든 commit OID를 그 claim의 세대로 쓴다.
- 각 local workspace는 추적되지 않는 결합 `{card path, claim commit OID}`만 가진다.
- resume의 자동 계속은 integration의 현재 claim 세대와 local 결합이 같을 때만 허용한다.
- 같은 사람 id라도 결합이 없는 다른 workspace는 카드를 조용히 이어받지 않는다.
- 명시 takeover는 integration에서 기존 claim을 release한 뒤 CAS로 다시 claim하며, 새 claim
  commit OID가 이전 workspace의 publish를 무효화한다.
- task commit·boundary 게시 직전에 token을 다시 검사한다.

이 방식은 정합성 항목 8이 이미 찾는 “현재 claim을 만든 commit”을 재사용하므로 새 전역
식별자가 아니다. 대신 integration history는 append-only·fast-forward여야 한다. history
rewrite를 허용하면 OID fencing의 의미가 사라진다.

worktree-local Git config가 값 격리를 제공한다는 것은 실험으로 확인했지만, worktree 삭제 뒤
자동 cleanup까지 증명된 것은 아니다. 따라서 config key는 비정본 hint로만 쓸 수 있다.
결합의 정본은 integration claim이고, stale local 결합은 token 불일치로 무해해져야 한다.

HANDOFF는 계속 사람당 하나다. 여러 workspace의 정확한 재개 위치를 HANDOFF에 늘어놓지 않는다.
HANDOFF는 최신 경계의 다음 한 걸음과 열린 결정만 제공하고, exact resume은 local 결합과
claim 세대가 담당한다.

### 8.7 통합 불가·clone·오케스트레이터

통합 불가를 하나의 fallback으로 처리하지 않는다.

| 상태 | 판정 |
|---|---|
| 새 tip 때문에 push 거절 | 정상 race. fetch→재판정→replay |
| OID 불변 + integration branch가 다른 worktree에 checkout | 해당 worktree 또는 coordinator가 공유 전이를 수행 |
| OID를 다시 읽을 수 있고 불변 + checkout·권한·보호 오류 | 구조 blocker. 새 공유 전이 금지 |
| network 오류로 remote tip을 다시 읽을 수 없음 | 상태 불명 blocker. 새 공유 전이 금지 |
| remote 없는 별도 clone | 사전 배정된 카드의 local 구현만 가능 |

오케스트레이터는 worker를 띄운 뒤 점유를 추측하지 않는다.

1. integration에서 카드·승인·claim을 먼저 만든다.
2. 각 worker에 카드와 claim generation을 전달한다.
3. worker는 preclaimed 카드만 고친다.
4. coordinator가 결과를 한 번에 하나씩 최신 integration에 replay한다.
5. 모든 병렬 결과 뒤 결합 검증을 실행한다.

integration branch를 coordinator가 checkout하고 있다면 coordinator가 모든 공유 전이를
수행해야 한다. 더 단순한 배치는 아무 worktree도 checkout하지 않는 전용 integration branch다.

### 8.8 journal·다중 도메인 요청·작은 묶음

journal에는 union merge driver를 두지 않는다. 두 전이가 경쟁하면 최신 state에서 정본 전이를
다시 적용한다. event log+tombstone으로 전면 교체하는 것도 가능하지만, 현재 상태 파일과
소비·교체 규칙을 모두 바꾸므로 v0.13.0의 최소 해법이 아니다.

다중 도메인 요청은 V13-09의 **공통 source locator 방식**을 권장한다.

```text
원 요청 1개를 journal에 기록
→ 영향을 받는 unit의 ordered set을 확정
→ 각 parent marker가 같은 source locator를 참조
→ 실행 제안 1회 승인
→ planning commit 1개가 모든 카드·승인을 만들고
  모든 marker와 원 요청을 함께 소비
```

source locator 자체가 batch identity이므로 새 batch id가 필요 없다. begin 뒤 중단되면 resume은
같은 locator를 가진 marker를 모아 이미 적용된 prefix와 남은 작업을 판정한다. 일부 단위가
모호·은퇴 상태면 begin 전에 묻고 원문을 유지한다.

작은 요청 묶기는 다음 다섯 조건을 모두 만족한 exact item만 허용한다.

1. 같은 source request
2. 같은 depth-1 unit
3. 하나의 coherent Destination
4. 한 completion signal이 모든 item을 증명
5. 한 revert로 함께 되돌려도 되는 rollback boundary

사용자가 실행 제안에서 그 exact bundle을 승인해야 한다. “작다”나 “관련 있다”는 독립 기준이
아니다.

### 8.9 병렬 안전성은 통합 뒤 판정한다

`Read first`와 현재 dirty path는 병렬 안전성의 증명이 아니다. 작업 공간 격리는 file·index
clobber를 막고, reciprocal parallel approval은 계획 의도를 보존한다. 의미 안전성은 다음
순서로 닫는다.

1. 각 worker가 격리 workspace에서 자기 completion signal을 실행한다.
2. 최신 integration에 결과를 하나씩 rebase·merge한다.
3. 매 통합 뒤 해당 카드 signal을 다시 실행한다.
4. parallel group 전부가 들어온 뒤 묶음 전체의 completion signal과 검토를 한 번 더 실행한다.

같은 database·port·server·외부 account·repo 밖 cache를 공유하면 파일 격리만으로 부족하다.
실행 환경까지 격리되지 않으면 parallel 승인을 거부한다.

### 8.10 골조 지식의 상위 우회

골조 파일에 검증되지 않은 내용을 verified state처럼 쓰지 않고도 사용자가 원하는 “공통
인프라가 실제로 어떻게 동작하는가”를 제공할 수 있다. 권장안은 **필요할 때 만드는 출처 보존
view**다.

입력은 다음으로 제한한다.

- 골조 capability document의 design zone
- 현재 freshness가 유효한 소비 능력 baseline의 verified zone
- 그 baseline의 consumed/shared path가 골조 scope에 실제 매핑되는 항목
- 아직 검증되지 않은 관측은 별도 hypothesis 묶음

출력의 각 항목은 원 능력 번호·정확 section/path·freshness를 유지한다. 두 소비 능력의 설명이
충돌하면 하나로 합쳐 “공통 사실”을 만들지 않고 충돌을 나란히 보여 준다. 이 view는 읽기
결과이지 골조 verified zone의 write가 아니다.

골조 파일 자체에 지속적인 verified truth가 반드시 필요하다면 foundation 전용 verify channel,
scope revision, covered evidence, writer, closure와 invalidation을 새로 설계해야 한다. 그것도
기술적으로 가능하지만 “골조용 검증 사건을 만들지 않는다”는 기존 결정을 뒤집는 별도 규모다.

### 8.11 나머지 구현 방향

- **L1:** 정합성 15항 전부를 판정하는 deterministic projector를 만들고 모델에는 활성 항목과
  anomaly만 전달한다.
- **L2:** schema·freshness·reader projection과 writer lifecycle·migration·recovery의 경계를
  조항×소비자 표로 먼저 증명한다. 절단선이 없으면 분할하지 않는다.
- **L4:** NUL-delimited path projector와 삭제·rename·type·Unicode·case·index/working-tree
  property test를 먼저 만든다.
- **Codex prompts:** 새 생성은 제거하되 generated marker가 있는 정확한 옛 파일 cleanup을
  한 릴리스 유지한다.
- **Hook trust:** 새 경로 설치→사용자 확인→옛 경로 삭제의 two-stage만 허용한다.

### 8.12 권장 선택

구현 순서는 **CAS 조정 면 → 점유 세대 → 프로필 A → 동시성 fixture**가 우선이다. 이것만으로
worktree와 별도 clone 병렬은 안전하게 닫힌다. 그 뒤 동일 root 진입 UX가 실제 수용 조건이면
프로필 B의 managed worktree adapter를 추가한다.

즉, 최종 방향은 “같은 폴더 동시 쓰기를 말로 허용”하는 것이 아니라 **사용자는 여러 터미널과
여러 도메인을 자유롭게 시작하되, 시스템은 공유 결정을 직렬화하고 실제 writer를 격리**하는
것이다. 사용 의도를 보존하면서 기술적으로 불가능한 보장은 떠안지 않는 가장 좁은 해법이다.

## 9. 플랫폼과 보안·신뢰 경계

### 9.1 Claude와 Codex 의미 동형성

플랜은 공통 영어 deploy artifact를 유지하므로 의미 분기 위험은 낮다. 구현 뒤 확인할 것은
플랫폼마다 다른 문장이 아니라 다음 전달 결과다.

| 검사 | Claude | Codex |
|---|---|---|
| 명시 호출 | plugin skill 발견 | `$devflow:<name>` 또는 UI skill 선택 |
| 암시 호출 | description으로 skill 선택 | description으로 skill 선택 |
| companion | 상대 경로 문서 원문 전달 | 현재 CLI smoke 통과, 전 skill 회귀 필요 |
| 역할 계약 | 깨끗한 context에 원문 전달 | 깨끗한 context에 원문 전달 |
| SessionStart | plugin hook | plugin hook + 사용자 trust |

L3은 Codex의 deprecated prompt 채널만 없애며 Claude 동작을 바꾸지 않아야 한다.

### 9.2 Hook trust는 자동화할 수 없는 보안 경계다

Codex가 정확한 hook command hash를 사용자가 신뢰하기 전에 실행하지 않는 것은 정상 보안
동작이다. 설치기가 이를 자동 승인하면 안 된다.

권장 two-stage upgrade:

1. 새 plugin과 hook을 설치하되 검증된 legacy hook은 유지한다.
2. 사용자가 새 세션의 trust prompt 또는 `/hooks`에서 정확한 command를 확인한다.
3. 사용자가 확인한 뒤 installer cleanup 단계를 다시 실행해 legacy 등록을 제거한다.

자동 신뢰와 완전 무중단을 동시에 보장하는 안전한 방법은 없다. 사용자 확인이 필요한 항목으로
남기는 것이 정답이다.

### 9.3 Per-worktree Git author 변경은 감사 흔적을 훼손할 수 있다

6.4처럼 흐름을 만들기 위해 `user.name`·`user.email`을 바꾸면 실제 commit 작성자가 가짜 flow
identity로 기록된다. signed commit, blame, 감사 로그, 조직 정책과 충돌할 수 있다. 실행 위치
식별이 필요하면 전용 config key를 쓰고 author identity는 보존해야 한다.

### 9.4 새 helper의 입력 안전성

L1·L4나 transaction helper를 구현하면 branch·path·journal JSON을 shell 문자열로 조립하지
않는다. argument array, `--`, NUL-delimited Git output을 써야 한다. 특히 사용자 요청 JSON과
arch의 integration 값은 실행 문자열이 아니라 데이터다.

## 10. 한국어 설계와 영어 배포에 대한 객관적 판단

현재의 **한국어로 설계하고 영어로 배포하는 순서가 더 적절하다.** 영어로 먼저 쓴 뒤 한국어로
바꾸는 방식이 AI 해석 변수를 본질적으로 줄인다고 보기는 어렵다.

한국어는 주어 생략, 긴 관형절, 문맥 의존이 자연스러워 행위자나 수식 범위를 생략하면 AI가
여러 방식으로 읽을 수 있다. 영어도 대명사 지시 대상, `and/or`, modifier attachment, 단복수
범위에서 같은 문제가 생긴다. 이번에 확인된 차단 결함은 어느 언어에서도 생긴다.

- “뒤처진 worktree를 읽지 않는다”는 한국어 표현 문제가 아니라 branch 단위 판정을 카드 단위
  상태에 적용한 모델 문제다.
- “append-only”는 영어여도 원자성을 만들지 않는다.
- “같은 completion signal”은 어느 언어에서도 rollback 경계를 뜻하지 않는다.

영어 deploy가 유리한 이유는 모델의 기술 문서 학습량과 token 비용, 플랫폼 관례다. 한국어
design original이 유리한 이유는 소유자가 의미를 직접 승인할 수 있기 때문이다. 영어를 먼저
정본으로 만들면 소유자 검토 전에 번역 해석이 한 번 더 들어가 오히려 의미 drift 지점이 늘어난다.

언어 차이를 줄이는 실제 장치는 다음이다.

- 상태 전이표와 권위·writer·commit 경계를 먼저 고정
- 한 문장에 행위자와 대상 ref를 명시
- 실패 경로가 없는 설명 문장 삭제
- 한국어 원본과 영어 배포본의 구조·수치·정본 용어 1:1 검사
- Claude와 Codex의 문자 실행 fixture를 같은 상태에서 비교

모든 해석 편차를 없애는 것은 불가능하다. 그러나 AI가 판단해야 하는 지점을 사용자 승인이나
기계 predicate로 바꾸고, 판단이 남는 지점을 명시하면 사용 가능한 수준으로 유계화할 수 있다.

## 11. 권장 수정 순서

### 단계 A · 플랜의 동시성 모델만 다시 결정

다른 문구를 고치기 전에 다음 여섯 문장을 플랜의 새 불변식으로 확정하는 것을 권한다.

1. 공유 상태의 유일한 권위는 integration ref다.
2. worktree HEAD는 작업 위치와 미통합 증거이지 공유 상태 권위가 아니다.
3. 모든 공유 전이는 예상 integration OID를 가진 CAS로 게시한다.
4. integration 불가 중에는 이미 예약된 카드의 task-local 작업만 허용한다.
5. 사람 신원과 실행 workspace를 분리하고 claim commit OID를 점유 세대로 쓴다.
6. 한 물리 working tree의 동시 writer는 지원하지 않으며 병렬 writer는 격리 worktree를 쓴다.

같은 repo root에서 여러 터미널을 시작하는 UX가 양보할 수 없는 요구라면 6번을 없애지 않는다.
대신 둘째 writer를 카드별 managed worktree로 보내는 프로필 B를 추가한다. 두 writer가 실제로
같은 물리 파일·index를 공유하도록 허용하면 안 된다.

### 단계 B · 파생 결정을 정리

- 6.5와 W4 제거

### 단계 F · 구현 뒤 실전

한 터미널 사이클보다 다음 세 사이클이 먼저 동시성 설계를 증명한다.

1. 같은 common-dir의 worktree 둘이 서로 다른 카드를 동시에 점유·구현·통합한다.
2. 별도 clone 둘이 writable remote integration에서 같은 과정을 수행한다.
3. 같은 사람의 옛 workspace가 takeover 뒤 결과 게시를 시도하고 claim-generation gate에서
   거부된다.

프로필 A에서는 같은 물리 작업 폴더의 두 writer가 정확히 거부되어야 한다. 프로필 B에서는
둘째 writer가 격리 worktree로 이동하고 원래 폴더에 동시 write가 없어야 한다.

## 12. 수정된 사용 동선

### 12.1 한 터미널에서 여러 도메인을 번갈아 수정

```
요청 기록
→ 단위별 매핑
→ 실행 제안 승인
→ 02 카드 점유·checkpoint
→ 03 카드 점유·checkpoint
→ 다시 02를 지목해 이어감
```

한 writer이고 서로 다른 단위이므로 현재 v0.12.0의 능력 축 점유를 유지할 수 있다. 전환할 때
이미 바뀐 코드를 자기 카드 checkpoint로 착지시키고, completion signal은 통합되지 않은 다른
단위 변경의 영향을 받는지 보고한다. 한 요청의 여러 단위 item은 V13-09에서 선택한 계약을
따른다. 한 physical worktree의 local 결합은 한 시점에 한 카드 writer만 가리키며, 다른
단위의 claim은 integration에 계속 남는다.

### 12.2 같은 작업 폴더의 여러 터미널

프로필 A에서는 터미널 수는 제한하지 않되 쓰기는 직렬이다.

```
터미널 A가 active writer
터미널 B는 상태 확인·긴 외부 조회 가능
→ A가 checkpoint/경계 완료
→ B가 integration을 다시 읽고 writer 역할 인계
```

두 터미널이 동시에 코드를 써야 하면 worktree를 만든다. devflow가 worktree를 자동 생성하거나
삭제할 필요는 없다.

프로필 B에서는 사용자가 같은 root에서 시작해도 다음처럼 실행 위치가 갈라진다.

```text
터미널 A → 현재 worktree에 card 02.3 결합
터미널 B → 둘째 writer 감지
           → managed worktree 생성
           → card 03.2 + claim generation 결합
           → B의 실제 쓰기 cwd를 새 worktree로 전환
```

사용자에게 새 실제 경로·branch·card를 보여 주고, 원래 폴더를 계속 쓴다고 오해하게 만들지
않는다. 같은 카드가 이미 다른 workspace에 결합돼 있으면 자동 이동·takeover하지 않고
선택을 묻는다.

### 12.3 같은 저장소의 worktree 둘

```
integration I0
→ A가 카드 02.3 claim을 I0→I1로 CAS
→ B는 I1을 읽고 카드 03.2 claim을 I1→I2로 CAS
→ 각 workspace가 자기 claim commit OID를 결합
→ 각자 코드 구현·checkpoint
→ A 통합 뒤 B는 새 tip에서 재평가·통합
→ 통합 상태에서 결합 completion signal
```

B가 I0에서 동시에 claim을 만들었다면 첫 push 실패 뒤 I1을 받아 다른 카드임을 확인하고
replay한다. 이것은 탈출이 아니라 정상 재시도다.

### 12.4 오케스트레이터가 여러 worktree를 생성

권장 순서:

1. coordinator가 integration에서 카드·승인·점유를 먼저 착지한다.
2. 카드 번호, branch/worktree, claim generation을 worker에 배정한다.
3. worker는 자기 카드의 코드·로그만 만든다.
4. worker는 publish 직전 generation을 다시 확인한다.
5. coordinator가 결과를 integration에 하나씩 받아 현재 상태에서 검증한다.
6. parallel group 전체가 들어오면 결합 검증을 실행한다.
7. worktree 삭제는 merge와 경계 완료 뒤 오케스트레이터가 한다.

오케스트레이터가 worker branch를 만든 뒤 integration까지 checkout해 막아 버리면 coordinator가
그 branch를 직접 갱신해야 한다. 모든 worker가 보이지 않는 로컬 점유를 만들게 해서는 안 된다.

### 12.5 서로 다른 기계의 clone

모든 clone이 같은 writable remote integration을 사용해야 한다. offline 중에는 이미 예약된
카드 구현만 계속하고 새 공유 전이는 만들지 않는다. remote가 돌아오면 integration을 받아
현재 점유 세대가 여전히 유효한지 확인한 뒤 push한다. 그동안 명시 takeover가 있었다면 옛
clone의 결과는 자동 게시하지 않고 patch 후보로만 보고한다.

## 14. 기획 종료 조건

다음이 모두 참이면 같은 의미를 다른 문장으로 반복 검토하지 않고 구현으로 넘어가도 된다.

- §1.3의 불가능 경계가 지원 범위에 정확히 반영됨
- V13-01~04의 설계 결정이 플랜에서 하나씩 교체됨
- 각 공유 전이에 authority·expected OID·writer·commit·유한 retry·recovery가 있음
- local workspace 결합과 claim generation·takeover·옛 writer 거부가 정의됨
- 프로필 A만 지원할지, 동일 root 진입 UX를 위한 프로필 B까지 지원할지 결정됨
- 다중 도메인 요청이 공통 source 원자 계획인지 독립 승인인지 하나로 결정됨
- foundation 지식이 출처 보존 view인지, 별도 검증 수명주기인지, 이번 릴리스 보류인지 결정됨
- §13 fixture의 기대 결과가 플랜과 1:1 대응함
- Claude와 Codex가 같은 영어 deploy artifact와 companion을 소비함
- 남은 위험은 “추가 검토 예정”이 아니라 보장 밖 또는 현장 관찰 항목으로 구분됨

문장 선택은 이 조건 뒤의 번역·편집 문제다. 이 조건을 만족한 뒤에는 동의어를 바꾸는 새
반증 라운드가 설계 품질을 올리지 않는다.

## 15. 최종 제안

v0.13.0의 목표와 주요 개선 방향은 유지할 가치가 있다. 특히 unheld integration, 요청 소실
방지, 읽기 비용 축소, Codex 네이티브 skill 단일화는 다음 플랜에도 남겨야 한다.

기술적으로 권장하는 중심은 **integration CAS + claim-generation fencing + 카드별 격리
workspace**다. 사람 신원, 실행 위치, 공유 상태, 로컬 작업 상태를 서로 다른 것으로 두고
공유 전이는 integration에서만 확정한다. 이 결정을 채택하면 6.5의 HEAD 필터, worktree별
가짜 사람, done 카드 재번호화, journal union이라는 네 보정 장치가 필요 없어지며 정본도
오히려 짧아진다.

구현 위험을 낮추는 순서는 프로필 A를 먼저 완성하고, 동일 repo root에서 여러 writer를 시작하는
UX가 실제 수용 조건일 때만 프로필 B의 managed worktree 라우팅을 더하는 것이다. 프로필 B는
기술적으로 가능하지만 `docs/design.md`의 worktree 비관리 결정을 정식으로 뒤집어야 한다.
그 이유를 반증하지 않거나 자동 관리 비용을 받지 않으면 프로필 A가 맞다.

끝까지 불가능한 것은 “아무 조정자 없이 같은 물리 bytes를 여러 자율 writer가 동시에 고쳐도
안전하다”는 문자적 보장이지, 사용자가 여러 터미널·여러 도메인·여러 worktree·여러 clone에서
작업하는 목적이 아니다. 그 목적은 공유 결정을 직렬화하고 writer를 격리하면 보존된다.

따라서 최종 판정은 **해결 가능한 플랜이지만 현재 플랜 그대로는 구현 보류**다. §8의 상위
모델과 §14의 종료 조건이 플랜에 반영되고 §13의 fixture와 1:1 대응한 뒤에는 문장 표현을
반복 해석하는 대신 구현과 실전 검증으로 넘어가는 것이 적절하다.
