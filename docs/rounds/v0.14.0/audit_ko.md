## 0. 최종 판정

**기획의 큰 방향과 A~E 작업 대부분은 충실하게 구현됐다.** 서로 다른 경로를 맡은 자유
병렬 점유, 순수 경량 요청의 짧은 동선, 같은 브랜치에서의 봉쇄 중 journal 보존, 3-way
journal 병합, 발급/점유 경쟁 분리, Design head 게이트, 은퇴 관측 게이트는 원문과 기계
검사 양쪽에서 성립했다. Claude와 Codex의 현재 0.14.1 설치본도 저장소의 핵심 배포 파일과
동일했다.

그러나 **현재 상태를 “플랜의 목적지가 전부 닫혔고 남은 것은 실전 관찰뿐”이라고 판정할
수는 없다.** 이번 감사에서 다음을 확인했다.

- 조용한 누락 또는 도달 불능 가능성 2건
- 세션 정지·잘못된 행동 가능성 7건
- 기록 정밀도 결함 1건
- v0.14.0 범위 밖에서 발견한 기존 유지보수 정본 표류 1묶음

그중 세 건은 실제 Git fixture로 재현했다. 87개 테스트가 모두 통과한다는 실행 리포트의
수치는 맞지만, 현재 테스트는 서로 다른 경로의 커밋 격리만 고정하고 같은 경로의 두 세션,
통합보다 앞선 브랜치의 보고 수, detached HEAD를 고정하지 않는다.

따라서 판정은 다음과 같다.

| 축 | 판정 |
|---|---|
| 기획 충실도 | **높음, 단 C3와 항목 단위 경량 조합은 부분 구현** |
| 일반 단일 세션 | **조건부 사용 가능** — 이름 있는 브랜치, 최신 통합 포함, 순수 경량 또는 정식 카드 흐름 |
| 한 폴더 다중 터미널 | **서로 다른 경로에서는 사용 가능** — 같은 경로가 겹치면 현재 보장 불충분 |
| 사용자 생성 worktree | **통합을 통한 공유 상태는 작동** — 봉쇄 로컬 기록의 다른 브랜치 재발견은 관찰 상태 |
| 실전 투입 순서 | **1·2계층 수리를 먼저 판정한 뒤 실제 사이클 권장** |

이 판정은 구조를 되돌리자는 결론이 아니다. 자유 병렬과 경량 차선의 목적은 유지할 수 있고,
대부분의 명백 결함은 작은 기계 게이트나 라우팅 순서 교체로 수리 가능하다. 같은 작업 폴더의
동일 파일을 여러 세션이 동시에 바꾸면서도 세션별 커밋을 완전 분리하는 것만은 추가 조정점
없이 절대 보장할 수 없다.

### 0.1 압축 판정을 읽는 방법

위 표는 전체 구현을 단순히 안전/불안전으로 양분한 표가 아니다. 각 행은 특정 전제가 있을 때
어느 범위까지 목적이 성립하는지를 압축한 것이다. 오해를 피하기 위해 판정의 근거와 예상되는
실제 결과를 다음과 같이 풀어 쓴다.

1. **“기획 충실도가 높다”는 말은 주요 구조가 실제 실행문에 들어갔다는 뜻이다.** 자유 점유,
   경량 차선, blockade journal, 3-way 병합, Design head, 은퇴 관측처럼 v0.14.0이 선택한 중심
   메커니즘은 선언만 추가된 것이 아니라 라우팅 절차와 테스트에 연결됐다. 따라서 정상 전제의
   대표 동선을 실행하면 이전 구조로 되돌아가거나 새 개념을 전혀 사용하지 않는 결과가 나오지는
   않을 것으로 예상된다. 다만 “높음”은 “모든 좌표에서 완전함”과 같은 말이 아니다. 항목 단위
   분류와 요청 단위 durable source가 만나는 지점처럼, 각각 구현된 두 규칙의 교차점에서 남은
   결함이 있으므로 무결함 판정으로 읽어서는 안 된다.

2. **“일반 단일 세션에서 조건부 사용 가능”은 조건 밖의 모든 사용이 실패한다는 뜻이 아니다.**
   이름 있는 브랜치에서 현재 통합 결정을 포함한 상태로, 순수 tweak 또는 정식 카드 중 한 동선을
   끝까지 타면 현재 절차와 테스트가 서로 맞는다. 이 조건에서는 작업이 올바른 ref에 남고,
   경량 변경과 카드 작업의 완료 경계도 비교적 명확할 것으로 예상된다. 반대로 detached HEAD,
   낡은 통합 기준, 혼합 요청 같은 조건에서는 실패가 반드시 발생한다는 뜻이 아니라 현재 텍스트가
   실패를 막지 못한다는 뜻이다. 감사 등급은 발생 빈도가 아니라 재현 가능한 손실·오동작 경로의
   존재를 기준으로 매겼다.

3. **“서로 다른 경로에서는 한 폴더 다중 터미널 사용 가능”은 데이터 생존과 세션별 귀속을
   구분한 판정이다.** `git commit --only <path>`는 다른 경로의 변경을 남겨 두므로 두 세션이
   서로 다른 파일 집합을 맡으면 각 커밋 경계를 유지할 수 있다. 그러나 같은 파일에 두 세션의
   hunk가 함께 존재하면 Git은 어느 hunk가 어느 AI 세션의 것인지 알지 못한다. 이 경우 변경
   자체는 사라지지 않더라도 한 세션의 커밋에 다른 세션의 작업이 동승하여 추적·검토·되돌리기
   경계가 틀어질 것으로 예상된다. 따라서 이 판정은 “같은 폴더 병렬 전체가 위험하다”도,
   “충돌 표지만 없으면 완전히 안전하다”도 아니다.

4. **“사용자 생성 worktree에서 공유 상태가 작동한다”는 통합에 게시된 상태에 한정된다.**
   점유·방·게시된 journal처럼 integration tip에 도달한 정보는 다른 worktree에서도 같은 정본을
   읽을 수 있으므로 의도한 자유 병렬의 기반이 된다. 반면 봉쇄 도중 로컬 커밋에만 남긴 journal은
   아직 integration에 없고, 현재 진입 절차는 다른 로컬 ref를 반드시 훑지 않는다. 같은 브랜치로
   돌아오면 복구되지만 다른 브랜치/worktree로 들어오면 기록이 존재하면서도 자동 발견되지 않을
   수 있다. 이는 worktree 지원 전체의 실패가 아니라 “로컬 생존”과 “어디서든 재발견” 사이의
   남은 범위 차이다.

5. **“1·2계층 수리 뒤 실전 사이클 권장”은 대규모 재설계를 먼저 하라는 뜻이 아니다.**
   detached HEAD 확인, integration 조상 확인, 상태 질문 진입 조건, 라우팅 순서처럼 다수의
   소견은 작은 기계 판정으로 닫을 수 있다. 이를 먼저 고정하면 실전 관찰에서 설계 결함과 운영상
   불편을 구분하기 쉬워진다. 혼합 요청의 durable disposition과 동일 파일 동시 편집만은 무엇을
   보장할지 선택해야 하므로 별도 설계 판단이 필요하다. 따라서 예상되는 다음 단계는 구조 폐기나
   전면 재작성보다, 명백 결함을 좁게 수리한 뒤 남은 물리적·운영적 긴장을 실제 사이클에서
   측정하는 순서다.

## 1. 감사 범위와 방법

### 1.1 읽기 순서와 권위

`docs/audit-guideline_ko.md`가 정한 순서를 따랐다.

1. 실행 리포트에서 구현자의 주장과 알려진 이탈을 추출했다.
2. `docs/design.md`에서 결정 이유와 기각 계보를 확인했다.
3. `docs/usecase-matrix_ko.md`에서 변경이 닿는 H×A 좌표를 확인했다.
4. 마지막에 영문 배포 원문을 읽고 주장과 대조했다.

충돌 시 권위는 현재 영문 배포 원문에 두었다. 플랜은 요구사항, 실행 리포트는 구현자의
주장, 테스트는 고정된 좌표의 증거로만 사용했다.

### 1.2 채택 기준과 종료 기준

소견은 다음 둘이 모두 있을 때만 채택했다.

- 현재 파일과 줄을 특정할 수 있는 원문
- 입력/디스크 상태 → AI가 밟는 문장 → 잘못된 결과로 이어지는 구체적 경로

표현 선호, 더 나은 이름, 막연한 재설계 의견은 소견에서 제외했다. 동일한 문장을 동의어로
다시 공격하는 라운드는 열지 않았다. 이번 산출물은 발견을 보고하는 단계이므로 구현 수리와
수리분 재감사는 수행하지 않았다.

### 1.3 실행한 검사

| 검사 | 결과 |
|---|---|
| `node --test` | **87/87 통과** |
| ko↔en 구조 동형성 | 통과 — 위 테스트에 포함 |
| 영문 배포물 한글 검사 | 통과 — 위 테스트에 포함 |

| Git fixture: 통합보다 한 커밋 앞선 브랜치 | 통합 tip은 현재 브랜치의 조상이면서 `integration..work` 커밋 수는 1 — 재현 |

fixture는 운영체제 임시 폴더에서 실행하고 삭제했다. 저장소 작업 트리는 검사 전후 깨끗했다.

### 1.4 감사의 독립성 한계

이번 세션은 플랜과 실행 리포트의 맥락을 함께 가진 단일 감사 컨텍스트다. 렌즈는 반증,
문자 실행, 기록 소실, 좌표 스윕으로 분리했지만 별도 신규 에이전트의 완전한 독립 컨텍스트는
사용하지 않았다. 실행 리포트가 기록한 기존 독립 패스 결과는 증거로 읽었을 뿐, 이번 감사의
독립 결과로 세지 않았다.

### 2.2 실행 리포트 주장 판정

| 실행 리포트의 주장 | 감사 판정 |

| 판정 단위를 항목으로 고쳤다 | **분류 문장에서는 사실, durable source·단위 매핑에서는 부분** |
| 봉쇄 중 요청이 다음 세션에 남는다 | **같은 브랜치/작업 폴더 재진입에서는 사실** |

| 수리분 재감사에서 새 충돌·소실 0 | **그 재감사의 제한된 범위에 대해서는 반박 증거 없음** |
| 다음 검증 수단은 실전뿐 | **현재 전체 구현에 대해서는 성립하지 않음** — 이번 좌표 스윕과 Git fixture에서 새 기계 결함이 재현됨 |

실행 리포트가 거짓 검증을 기록했다고 보지는 않는다. 그 패스는 깨끗한 순수 경량 요청,
비중첩 6터미널, 같은 브랜치 봉쇄 복구, 한 3-way 충돌을 걸었다. 이번 소견은 그 걷기들이
곱하지 않은 요청 모양 × HEAD 관계 × 기존 diff × 상태표 우선순위 좌표에서 나왔다.

### 2.3 실행 리포트 판정의 상세 해설

1. **자유 병렬 점유 주장은 구현됐지만 적용 범위가 있다.** 방 안의 서로 다른 카드를 서로 다른
   세션이 질문 없이 점유하는 규칙과 경쟁 판정은 실제 텍스트와 테스트에 존재한다. 따라서
   비중첩 카드가 비중첩 경로를 바꾸는 대표 장면에서는 실행 리포트가 예측한 병렬성이 나온다.
   다만 점유 분리가 작업 트리의 hunk 소유권까지 만들어 주지는 않는다. 같은 파일을 함께
   변경하는 순간에는 4.3의 Git 한계가 별도로 적용되므로, “점유가 자유롭다”를 “어떤 파일
   중첩도 자동 격리된다”로 확대해 읽을 수 없다.

2. **항목 단위 판정은 분류 단계에서는 사실이나 수명주기 전체에서는 아직 부분적이다.** split은
   한 요청 안의 각 항목을 tweak인지 카드인지 따로 볼 수 있다. 그러나 원 요청을 보존하는 journal
   줄과 그것을 소비하는 시점은 요청 단위이고, 완료한 tweak 항목을 디스크에서 식별하는 표지가
   없다. 중단이 없으면 AI가 대화 문맥을 기억해 모두 처리할 수도 있지만, 경계 사이에서 세션이
   끊기면 이미 완료한 항목과 남은 항목을 기계적으로 재구성할 수 없다. 따라서 “항목 단위”라는
   표현은 현재 분류 범위를 정확히 설명하지만 durable completion까지 보장하는 표현은 아니다.

3. **봉쇄 생존 주장은 저장 위치와 재진입 위치가 같을 때 성립한다.** blockade append를 로컬
   커밋으로 남기는 절차는 작업 트리의 휘발 상태보다 강하고, 같은 브랜치로 돌아오면 다음 세션이
   읽을 수 있다. 예상 결과는 세션 종료 자체로 요청이 사라지지 않는 것이다. 하지만 커밋이 아직
   integration에 게시되지 않았으므로 다른 브랜치/worktree가 그 ref를 탐색하지 않으면 발견하지
   못한다. 실행 리포트의 성공 장면은 유효하되, 그 성공을 모든 재진입 위치로 일반화할 근거는
   아직 없다.

4. **“재감사에서 0건”은 그 패스가 걸어 본 좌표에 대한 결과로 존중해야 한다.** 해당 재감사가
   확인한 수리에서 새 충돌이나 소실이 있었다는 반증은 이번 감사에서도 나오지 않았다. 새 소견은
   같은 문장을 다시 해석해 억지로 만든 것이 아니라, 이전 패스가 곱하지 않은 detached HEAD,
   같은 경로의 기존 diff, 혼합 요청, 상위 상태표 선점 좌표를 추가해 얻었다. 그러므로 두 결과는
   모순되지 않는다. 앞선 수리가 실패했다는 뜻이 아니라 전체 상태 공간이 아직 닫히지 않았다는
   뜻이다.

5. **“남은 검증은 실전뿐”이라는 결론만은 시점상 이르다.** 실제 Git 명령만으로 재현 가능한
   세 좌표와 텍스트 순서만으로 결정되는 라우팅 결함이 남아 있어, 사용자 운영을 시작하지 않고도
   더 닫을 수 있는 기계 검증이 존재한다. 이들을 수리한 뒤에는 빈도, 사용성, 원격 협업처럼
   fixture가 대신하기 어려운 부분이 실전 관찰의 주 대상이 된다. 즉 실전 검증이 불필요하다는
   반박이 아니라, 실전 전에 제거할 수 있는 결정적 변수를 먼저 제거하자는 범위 조정이다.

## 3. 사용 동선·좌표 스윕

아래 표는 인접한 모든 동선이 같은 결함을 가진다고 주장하는 요약표가 아니다. 한 행은 요청
모양, HEAD 관계, 기존 변경, 라우팅 상태가 만나는 한 좌표를 나타낸다. `공백 4.x`는 그 좌표에서
안전한 다음 행동이 정의되지 않았거나 현재 행동이 실패를 막지 못한다는 뜻이고, 정상 전제의
다른 행까지 실패한다는 뜻은 아니다. 발생 원리와 예상 결과는 연결된 소견 본문이 정본이다.

| 요청/상태 좌표 | 권위 | 다음 행동 | 커밋·복구 | 판정 |
|---|---|---|---|---|
| 순수 tweak × 이름 있는 브랜치 × 통합 포함 × 깨끗한 대상 경로 | 현재 문서·코드 | tweak | 단위별 한 커밋 | 정의됨 |
| 순수 tweak × 방 없음 × 게시 가능 | 통합 | 방 생성 후 tweak | 방 커밋 + tweak | 정의됨 |
| 순수 tweak × 방 없음 × 봉쇄 | 통합 | 원인 보고·대기 | 없음 | 정의됨 |
| 순수 tweak × 다른 경로만 dirty | HEAD + 작업 트리 | tweak | 경로 커밋, 다른 경로 잔존 | 정의됨 |
| 순수 tweak × 같은 대상 경로 dirty | 세션 귀속 권위 없음 | tweak 진행 | 다른 세션 변경 동승 | **공백 4.3** |

| 자유 병렬 × 서로 다른 카드/경로 | 통합 tip | 각자 점유·구현 | 경로별 커밋 | 정의됨 |

## 4. 발견한 문제 — 해결안과 분리한 소견

### 4.1 1계층 · 혼합 요청은 항목별 완료 상태가 없어 일부 요청이 조용히 사라질 수 있다

**원문**

- `skills/resume/SKILL.md:59-66` — 모든 항목이 통과할 때만 tweak로 바로 들어가고, 하나가
  실패하면 요청 전체를 일반 경로의 요청 기록 행으로 보낸다.
- `skills/split/SKILL.md:281-284` — 카드·승인 계획 커밋이 요청 **전체**의 journal 줄을
  삭제한다.
- `skills/split/SKILL.md:387-395` — 그 요청 안의 tweak 항목은 카드가 아니라 tweak 차선으로
  보낸다고만 적는다.
- `skills/principles/SKILL.md:566` — 여러 tweak 항목은 단위별 커밋으로 묶는다.

**왜 위험한가**

분류기는 항목 단위가 됐지만 durable source는 여전히 요청 전체 한 줄이고, split에는
“어느 tweak 항목을 이미 커밋했는가”를 디스크에서 복원하는 상태가 없다. tweak 실행과 카드
계획 중 어느 것을 먼저 할지, 중단 뒤 이미 끝난 tweak를 어떻게 제외할지도 정해져 있지 않다.

**구체적 장면**

1. 사용자가 “주문 버튼 테두리 변경”과 “주문 모달의 열림 조건 변경”을 한 번에 요청한다.
2. 둘째 항목 때문에 resume은 전체 요청을 journal에 기록하고 split으로 보낸다.
3. split은 첫째를 tweak, 둘째를 카드로 분류한다.
4. 문자 실행 A는 카드만 만들고 계획 커밋에서 원 요청 줄을 삭제한다. 첫째 항목은 카드도
   journal도 없이 사라진다.
5. 문자 실행 B가 먼저 tweak를 커밋해도, 계획 전에 세션이 죽으면 다음 세션은 원 요청
   전체를 다시 읽고 어느 항목이 끝났는지 판정할 규칙이 없다.

**발생 조건**: 한 요청에 tweak와 비-tweak가 함께 있음 × 세션 중단 또는 split의 두 합법적
읽기 중 카드 우선 읽기.

**자기 반증**: “goes through the tweak lane”을 즉시 실행 명령으로 읽으면 정상 세션에서는
첫째 항목도 처리할 수 있다. 그러나 그 읽기도 중단 뒤의 완료 판정과 요청 줄 삭제 순서를
제공하지 않으므로 소견은 남는다.

### 4.2 1계층 · detached HEAD의 tweak 커밋은 이름 있는 ref 없이 좌초한다

**원문**

- `skills/resume/SKILL.md:62-63` — tweak 진입이 적용하는 Git 게이트는 열린 rebase/merge
  게이트 하나다.
- `skills/principles/SKILL.md:138-149` — 그 게이트는 rebase/merge가 열렸을 때만 detached
  HEAD를 보고한다.
- `skills/principles/SKILL.md:555-560` — tweak는 로컬 커밋 하나로 끝난다.
- `skills/principles/SKILL.md:568-577` — 통합 게시를 하지 않고 봉쇄 중에도 진행한다.

**왜 위험한가**

일반 task commit은 이후 통합 경계가 이름 있는 integration ref로 가져가지만 tweak에는 그
경계가 없다. detached HEAD에서도 열린 Git 작업이 없으면 그대로 커밋한다.

**실측 장면**

1. `git checkout --detach` 뒤 tweak 커밋을 만들었다.
2. `git switch main`을 실행하자 Git은 “브랜치에 연결되지 않은 커밋을 두고 간다”고 경고했다.
3. `git branch --contains <tweak hash>` 결과는 0개였다. 커밋은 reflog에만 남았다.
4. 다음 devflow 세션은 reflog를 읽지 않으므로 완료된 변경을 찾지 못한다. reflog 만료·GC 뒤에는
   실제 객체도 사라질 수 있다.

**발생 조건**: 순수 tweak × detached HEAD × tweak 종료 전에 이름 있는 branch/ref 생성 없음.

### 4.3 2계층 · 경로 단위 커밋은 같은 파일 안의 세션별 변경을 분리하지 못한다

**원문**

- `skills/principles/SKILL.md:581-583` — 커밋은 자기 규칙이 이름 붙인 경로만 담는다고 한다.
- `skills/work/SKILL.md:275-277` — 카드 중 tweak 커밋은 자기 경로만 담으므로 카드 작업과
  섞이지 않는다고 단정한다.
- `README.md:517-527` — 여러 터미널 안전성과 서로 다른 파일 부분의 공존을 설명한다.

**왜 위험한가**

Git 커밋은 세션이 아니라 경로의 최종 blob을 기록한다. 두 세션이 같은 파일의 서로 다른
부분을 바꾸면 데이터는 살아남아도, 먼저 커밋한 세션의 커밋에 두 변경이 함께 들어간다.
“살아남음”과 “올바른 작업 커밋에 귀속됨”은 다른 조건이다.

**실측 장면**

1. `shared.txt`의 첫 줄을 세션 A의 미완성 변경으로 두고 커밋하지 않았다.
2. 둘째 줄에 세션 B의 tweak를 추가했다.
3. B가 `git commit --only shared.txt`를 실행했다.
4. 커밋 blob에는 A와 B의 변경이 모두 들어갔고 작업 트리는 깨끗해졌다.
5. B의 좁은 확인이 A의 미완성 의미를 검증하지 않았어도 A의 코드가 tweak 커밋에 들어간다.
   나중에 B의 tweak를 revert하면 A의 일부도 함께 되돌아간다.

**발생 조건**: 같은 물리 작업 폴더 × 두 세션이 같은 파일 경로를 수정 × 먼저 커밋하는
세션이 그 경로를 커밋.

**자기 반증**: README가 겹치는 카드 할당을 피하라고 하므로 계획된 카드끼리의 발생률은
낮아진다. 그러나 계획 밖에서 들어오는 mid-card tweak는 `parallel:` 계획에 없고, 같은
컴포넌트 파일을 만질 수 있어 방어가 완전하지 않다.

### 4.4 2계층 · tweak가 HEAD 민감 복구 상태를 건너뛰어 준비된 route를 무효화할 수 있다

**원문**

- `skills/resume/SKILL.md:61-63` — tweak는 상태 복원을 전부 생략하며 보호할 것이 없다고
  선언한다.
- `skills/principles/SKILL.md:568-569` — pre-routing integration read와 state restoration이
  적용되지 않는다.
- `skills/principles/SKILL.md:627-635` — uncommitted `routing prepared`는 `HEAD == base`여야
  하고, base와 정규화된 checkout의 차이는 operations의 정확한 prefix여야 한다.

**왜 위험한가**

tweak가 devflow 파일을 바꾸지 않더라도 **HEAD를 바꾼다.** 따라서 HEAD를 복구 키로 쓰는
전환은 보호 대상이다. “공유 상태를 바꾸지 않는다”와 “복구 상태에 영향을 주지 않는다”는
같은 명제가 아니다.

**구체적 장면**

1. 이전 세션이 verify.md에 `routing prepared`를 썼지만 route commit 전에 죽었다.
2. object의 `base`는 그때의 HEAD다.
3. 새 대화가 순수 tweak라서 resume은 prepared route를 읽지 않고 코드 커밋을 만든다.
4. HEAD가 전진했으므로 다음 정상 resume에서 `HEAD == base`가 거짓이다. 코드 diff도 payload
   operations 밖이라 prefix 비교가 실패한다.
5. 원래 재개 가능했던 route가 integrity anomaly로 바뀌어 세션이 멈춘다.

**발생 조건**: 복구 중인 HEAD 민감 transition × 순수 tweak 요청 × tweak가 먼저 진입.

### 4.5 2계층 · tweak는 통합 권위보다 낡은 Layer 0에서 분류·구현될 수 있다

**원문**

- `skills/principles/SKILL.md:75-81` — 공유 상태와 binding decision의 권위는 integration
  tip이다.
- `skills/principles/SKILL.md:557-560` — tweak는 현재 checkout의 기존 문서와 코드로
  분류·수정한다.
- `skills/principles/SKILL.md:568-569` — pre-routing integration read를 명시적으로 생략한다.

**왜 위험한가**

분기된 다른 worktree에서 integration에 새 디자인 토큰이나 ADR이 착지해도, 낡은 브랜치의
tweak 세션은 그 결정을 보지 않는다. 코드 파일과 문서 파일이 달라 merge conflict 없이
합쳐지면 최신 결정에 반하는 코드가 남는다.

**구체적 장면**

1. integration에 “위험 버튼은 `danger` 토큰만 사용” 결정이 착지한다.
2. 그 commit을 포함하지 않은 브랜치에서 사용자가 버튼 테두리 색 변경을 요청한다.
3. tweak는 낡은 design.md를 읽고 질문 2를 “아니오”로 판정한다.
4. 코드 커밋은 최신 문서와 다른 경로라 나중에 충돌 없이 병합된다.
5. digest나 Scope head가 사후에 신선도 저하를 보여 줄 수는 있지만, 잘못된 커밋을 막지는
   않는다.

**발생 조건**: current branch가 integration tip을 포함하지 않음 × 그 사이에 tweak 판정과
관련된 Layer 0 결정 변경 × 코드 병합이 텍스트 충돌 없이 성공.

### 4.6 2계층 · `not yet on integration`의 조상 판정 방향이 반대다 `[기존]`

**원문**

`skills/resume/SKILL.md:139-144`는 “integration tip이 current branch의 조상이면
`none`”이라고 한 뒤, 그렇지 않을 때만 integration이 담지 않은 commit의 카드 경로와
journal 경로를 센다.

**왜 위험한가**

로컬 작업 브랜치가 integration보다 앞선 정상 상태에서는 integration tip이 current의
조상이다. 바로 그 상태가 “integration이 담지 않은 commit이 있음”인데 문장은 `none`을
선택한다. C3가 추가한 봉쇄 journal 가시성도 이 guard를 통과하지 못한다.

**실측 장면**

- `integration`의 base에서 `work`를 만들고 로컬 commit 하나를 추가했다.
- `git merge-base --is-ancestor integration work`는 성공했다.
- `git rev-list --count integration..work`는 `1`이었다.
- 현재 문면은 첫 결과만 보고 `none`을 출력한다.

**발생 조건**: current가 integration과 같지 않고 integration을 포함한 채 앞서 있음 —
작업 브랜치와 봉쇄 로컬 커밋의 가장 일반적인 모양.

`git blame`상 잘못된 guard는 0.13.0 커밋 `67bebae`에서 들어왔고, 0.14.0은 그 아래에
journal 포함만 추가했다. 이전 검증을 통과한 탈출 결함으로 분류한다.

### 4.7 2계층 · 다중 점유 질문이 상태표보다 먼저 실행되어 더 높은 우선순위를 가로막는다

**원문**

- `skills/resume/SKILL.md:77-84` — 절차 3에서 내 점유가 둘 이상이고 지목이 없으면 즉시
  목록을 보이고 어느 것을 계속할지 묻는다.
- `skills/resume/SKILL.md:94-106` — verify projection과 journal 읽기는 그 뒤다.
- `skills/resume/SKILL.md:171` 이후 — 실제 다음 단계는 상태표 첫 일치 행이 결정한다.
- 같은 파일 `91-93`의 worktree 질문은 이미 “보고 시점, matched row가 work일 때만”으로
  수리돼 있다.

**왜 위험한가**

질문 시점에는 아직 이 호출이 claim을 계속할지 알 수 없다. active `routing prepared`,
layer-opening marker, product verification running처럼 claim보다 먼저 처리해야 하는 상태가
있어도 사용자에게 카드 선택부터 요구한다.

**구체적 장면**

1. 내 claim 두 개와 `product verification running` 줄이 함께 있다.
2. 사용자가 “계속해 줘”라고 한다.
3. 절차 3은 journal을 읽기 전에 두 카드 중 하나를 고르라고 묻고 대기한다.
4. 상태표가 선택해야 할 verify 재개는 불필요한 응답 전까지 지연된다. 답을 받아도 실제
   matched row는 verify라서 방금 고른 카드를 계속하지 않는다.

**발생 조건**: 내 claim 2+ × 대화에 카드/단위 지목 없음 × claim보다 높은 상태표 행 존재.

### 4.8 2계층 · 상태 질문을 tweak에서 제외하는 진입 조건이 원문에 없다

**원문**

- `skills/resume/SKILL.md:59-63` — 현재 대화의 각 항목이 세 질문을 통과하면 tweak로 간다.
- `skills/principles/SKILL.md:547-554` — 세 질문은 전이 변경, 결정/충돌, 다음 작업자 함정뿐이다.
- `docs/usecase-matrix_ko.md:134-137` — H12 상태 질문은 “변경이 아니므로 tweak 대상이
  아니다”라고 판정한다.

**왜 위험한가**

“어디까지 됐어?”는 세 질문 모두 “아니오”다. 그러나 저장소 변경을 요청하는 항목인지 묻는
진입 조건은 없다. 한 독자는 일반 resume으로 가고, 더 문자적인 독자는 tweak로 가서 만들
변경·검사·커밋을 찾지 못한다.

**구체적 장면**

1. 사용자가 상태만 묻는다.
2. 세 질문은 전부 “아니오”라 Tweak Entry가 절차 1~7을 건너뛴다.
3. canonical tweak lane은 “변경하고 검사하고 커밋하라”고 요구한다.
4. 세션은 상태를 보고하지 못한 채 막히거나, 불필요한 변경 대상을 추측한다.

**발생 조건**: 변경 의사가 없는 질문/설명 요청 × 세 질문만으로 진입 판정.

### 4.9 2계층 · 경량 판정의 유계 읽기에서 glossary가 빠져 있다

**원문**

- `skills/principles/SKILL.md:557` — tweak는 product.md, arch.md, design.md,
  code-style.md만 읽는다.
- `skills/work/SKILL.md:121-122` — 정식 구현자는 glossary.md를 읽는다.

**왜 위험한가**

버튼 문구는 tweak의 대표 사례이면서 glossary의 직접 소비자다. 판정 근거를 “요청과 이

**구체적 장면**

1. glossary.md가 제품에서 `workspace`만 쓰고 `project`는 다른 개념이라고 고정한다.
2. 사용자가 버튼 라벨을 `Projects`로 바꾸라고 한다.
3. 네 문서에는 충돌이 없어 tweak로 판정되고 코드가 커밋된다.
4. 정식 work가 항상 읽는 용어 정본과 UI 문구가 갈라진다.

**발생 조건**: 관련 결정이 glossary에만 있음 × 문구/레이블 tweak × 다른 네 문서에는 같은
결정이 없음.

## 6. 설계 긴장 — 결함과 분리

### 6.1 봉쇄 로컬 기록은 같은 브랜치에서는 복구되지만 다른 브랜치에서는 자동 발견되지 않는다

현재 C1은 대화에만 있던 요청을 로컬 commit으로 바꾸므로 원래의 무흔적 소실은 닫는다.
다만 새 세션이 다른 worktree/branch에서 시작하면 resume은 그 branch의 journal을 읽지 않는다.
`docs/design.md`가 이미 **Stranded flows**로 기록한 가시성 문제와 같은 뿌리다. 로컬 ref가
남아 있으면 복구 가능하므로 새 결함으로 세지 않았다.

같은 Git 저장소 안에서는 local branch의 미통합 journal commit을 유계 열거하는 방법이
기술적으로 가능하다. 서로 다른 clone이고 공유 원격도 막혔다면 공용 write point 없이 다른
clone의 기록을 자동 발견하는 것은 불가능하다.

### 6.2 같은 카드 두 터미널은 기존 판정대로 보장 밖이다

디스크의 `.wip-<id>.`는 같은 id의 터미널을 구분하지 않는다. 터미널 id·lock·격리 worktree
중 하나 없이 이를 완전히 막을 수 없다는 현재 판정은 타당하다. 이번 감사가 새로 확인한 것은
“다른 카드라도 같은 파일 경로를 동시에 만질 때”의 커밋 귀속 문제다.

### 6.3 경량 차선의 비용 절감은 아직 절차 비용만 줄었다

순수 tweak가 카드·journal·검토를 제거한 효과는 실제다. 그러나 principles 770줄을 읽는
고정비는 남는다. 실행 리포트가 D11로 분리하고 현재 최선이지 종착이 아니라고 한 판정은
정직하다. 정확성 결함과 같은 라운드에서 정본 분할을 섞지 않겠다는 보류 이유도 유효하다.

### 6.4 설치 갱신과 실행 중 세션의 skill catalog 갱신은 다르다

두 CLI의 설치 목록과 0.14.1 cache는 정상이다. 이 감사가 시작된 오래된 Codex 세션의 초기
skill catalog는 0.12.0 경로를 기억했고 그 cache 경로는 이미 없었다. 새 세션은 설치 목록을
다시 읽지만, 실행 중 세션이 plugin update를 실시간으로 반영한다고 기대해서는 안 된다.
이는 패키지 내용 결함보다 운영 수명주기 제약이다.

## 7. 해결 방향 — 소견과 분리한 기술 선택지

### 7.1 우선순위와 가능성

| 소견 | 기술적 해결 가능성 | 권장 방향 | 남는 한계 |
|---|---|---|---|
| 4.1 혼합 요청 | 가능하나 설계 선택 필요 | 단기에는 혼합 요청 전체를 정식 경로로 보내고, 항목별 fast lane은 durable disposition 설계 뒤 열기 | 효율 일부 후퇴 |
| 4.2 detached HEAD | 완전 해결 가능 | tweak 전 symbolic branch 존재를 기계 확인하고, 없으면 branch 선택/생성을 사용자에게 요청 | 드문 경우 질문 1회 |
| 4.3 동일 경로 혼입 | 부분 완화 가능, 무조정 절대 보장은 불가능 | 대상 경로의 사전 dirty 검사 + 예상 diff 대조; 겹치면 checkpoint/defer/격리 worktree로 전환 | 검사와 commit 사이 race는 lock/격리 없이는 남음 |
| 4.4 HEAD 민감 복구 | 완전 해결 가능 | 전체 복원 대신 작은 **HEAD 안정성 게이트**로 prepared route와 찢어진 verify transition을 먼저 재개 | 검사할 상태 종류를 정본에서 정확히 열거해야 함 |
| 4.5 낡은 integration | 완전 해결 가능(로컬 권위 기준) | 분류 전에 integration tip이 HEAD의 조상인지 확인; 아니면 동기화/중지 | 원격 자체가 보이지 않으면 최신 remote 보장은 불가능 |
| 4.6 보고 수 | 완전 해결 가능 | 조상 문장 대신 `integration..HEAD`의 실제 commit/path 집합을 계산하고 집합이 빌 때만 `none` | 없음 |
| 4.7 질문 선점 | 완전 해결 가능 | 다중 claim 질문도 worktree 질문처럼 matched row가 work일 때 보고 시점으로 이동 | 없음 |
| 4.8 상태 질문 | 완전 해결 가능 | 세 질문 앞에 “저장소 산출물 변경 요청인가” 진입 조건을 둔다 | 질문/설명 분류 한 단계 추가 |
| 4.9 glossary | 완전 해결 가능 | 기존 glossary.md를 경량 유계 읽기 집합에 포함 | 고정 읽기 한 파일 증가 |
| 5.1 unit 기록 | 완전 해결 가능 | 이 차선에서 canonical recognition의 입력을 각 항목의 텍스트로 한정 | 항목 자체가 모호하면 `01` fallback 또는 질문 필요 |
| 5.2 정본 표류 | 완전 해결 가능 | AGENTS와 design pair에서 native plugin 한 채널로 옛 행을 dated correction | 런타임 수리 아님 |

#### 7.1.1 해결 가능성 판정을 실제 동작으로 읽는 법

**작은 기계 게이트로 닫히는 소견은 4.2와 4.4~4.9, 5.1이다.** 이들은 새 상태 모델을 만들지
않아도 현재 절차가 이미 의존하는 사실을 실행 직전에 확인하거나, 권위표가 선택된 뒤 질문하도록
순서를 옮기면 된다. 예를 들어 symbolic branch 검사는 detached HEAD에서 커밋하기 전에 멈추게
하고, `integration..HEAD` 집합 계산은 조상 관계를 문장으로 추정하지 않고 실제 보고 대상을
계산한다. 예상 결과는 정상 동선에 새 대화를 거의 추가하지 않으면서 위험 좌표에서만 질문·동기화·
중지를 발생시키는 것이다. 다만 “완전 해결 가능”은 제안한 규칙을 적기만 하면 끝난다는 뜻이
아니다. 각 게이트의 양성·음성 fixture와 기존 정상 동선의 회귀 검사가 함께 있어야 그 판정을
구현 완료로 바꿀 수 있다.

**4.1은 구현 난도가 아니라 보장 조합을 먼저 선택해야 하는 문제다.** 순수 tweak만 fast lane에
남기는 단기안은 새 durable 형식 없이 조용한 누락을 막을 수 있고, 예상 결과도 명확하다. 혼합
요청은 조금 느려지지만 모든 항목이 하나의 복구 가능한 정식 흐름에 남는다. 반대로 혼합 요청의
항목별 속도를 유지하려면 item id, kind, 완료 commit, source 소비 조건을 정본으로 만들어야 한다.
이 방식도 기술적으로 가능하지만 consumer·병합·중단 복구·이관까지 함께 바뀐다. 따라서 이
소견의 “설계 선택 필요”는 해결 불가능을 뜻하지 않고, 안전성과 상태 복잡도 중 어느 비용을
선택할지 소유자 결정이 필요하다는 뜻이다.

**4.3은 목표 보장 수준에 따라 해결 가능성의 답이 달라진다.** 사전 dirty 검사와 예상 diff
대조를 넣으면 이미 같은 파일을 만지고 있는 흔한 중첩은 발견해 checkpoint, defer, 격리
worktree로 보낼 수 있다. 그러면 우발적인 동승 커밋의 대부분은 예방할 수 있을 것으로 예상된다.
그러나 검사 직후 다른 세션이 같은 파일을 수정할 수 있으므로 검사와 commit 사이의 race는
남는다. 세션별 hunk 귀속을 절대 보장하려면 lock, 독립 index, worktree 격리처럼 Git 외부의
조정점을 받아들여야 한다. 아무 조정점도 추가하지 않으면서 동일 작업 트리·동일 파일·동시 편집·
완전 분리를 모두 요구하는 것은 기술적으로 불가능하다.

**5.2는 런타임 결함은 아니지만 미래 변경의 판단 기준을 흐릴 수 있다.** 현재 설치와 실행은
native plugin 한 채널로 작동하므로 옛 생성 prompt 설명 때문에 지금 작업이 즉시 실패하지는
않는다. 그러나 다음 설계 AI가 AGENTS와 design의 오래된 행을 현재 의무로 받아들이면 사라진
생성물을 다시 만들거나 검증 범위를 잘못 정할 수 있다. dated correction으로 기각 계보를
보존하면서 현재 채널을 명시하면 실행 동작은 바꾸지 않고 유지보수 권위만 다시 맞출 수 있다.
예상 효과는 현재 사용자 흐름의 변화가 아니라 이후 설계·감사의 잘못된 출발점을 제거하는 것이다.

### 7.2 혼합 요청에서 동시에 지킬 수 없는 네 조건

다음 네 가지를 durable link 없이 동시에 보장할 수는 없다.

1. 혼합 요청을 항목별로 tweak와 카드로 나눈다.
2. tweak는 journal/card를 전혀 만들지 않는다.
3. 원 요청 journal 줄은 카드 계획 커밋에서 한 번에 삭제한다.
4. 어느 지점에서 세션이 죽어도 완료/미완료 항목을 디스크만으로 복원한다.

4를 지키려면 tweak commit과 원 요청 항목 사이의 durable link가 하나는 필요하다. 선택지는
다음 두 갈래다.

**선택지 A — 최소·안전 우선(권장 단기안).** 순수 tweak 요청만 fast lane으로 유지한다.
비-tweak가 하나라도 섞인 요청은 항목 전체를 기존 maintenance/card 흐름으로 보낸다. 새 상태가
없고 즉시 닫을 수 있지만, 실행 리포트가 선택한 “혼합 요청에서 tweak 여러 건” 효율은 포기한다.

**선택지 B — 항목 효율 유지.** 요청을 durable item 목록으로 만들고 각 item에 stable ordinal
또는 hash, kind, 완료 commit을 기록한다. 카드 계획은 모든 tweak item의 완료 commit과 모든
card item의 계획 착지가 확인된 뒤에만 source를 소비한다. 이 방식은 기술적으로 가능하지만
새 canonical format·consumer·병합·중단 복구·이관이 필요하다. 단순 문장 한 줄 수리가 아니다.

commit subject만 보고 복구하는 절충안은 권장하지 않는다. 현재 `<what>`은 원문과 byte-identical
locator가 아니고, 봉쇄 로컬 commit은 다른 branch에서 보이지 않을 수 있어 다시 추측이 된다.

### 7.3 경량 차선에 필요한 최소 preflight

전체 resume 1~7을 되살릴 필요는 없다. 다음 네 검사는 state restoration이 아니라 tweak
commit의 안전 전제다.

1. **이름 있는 ref** — detached HEAD면 진행하지 않는다.
2. **통합 신선도** — 현재 HEAD가 현재 integration tip을 포함한다.
3. **HEAD 민감 transition 부재** — `routing prepared`와 canonical verify/routing write prefix가
   있으면 그 transition을 먼저 끝낸다.
4. **대상 경로 격리** — 편집 전 이미 dirty한 대상 경로는 세션 귀속을 추측하지 않는다.

이 네 검사는 tree 전체, HANDOFF, journal 전문을 모델 컨텍스트에 넣지 않고 Git과 작은 projection
명령으로 판정할 수 있다. 따라서 G6의 비용 절감 방향을 유지하면서 4.2~4.5를 닫을 수 있다.

### 7.4 동일 파일 동시 작업의 솔직한 기술 경계

사전 dirty 검사만으로 발생률은 크게 줄지만 완전 보장은 아니다. 두 세션이 모두 clean을
확인한 직후 같은 파일을 바꾸는 race가 남는다.

- **추가 장치 없이 가능한 것**: edit 전 blob id 기록, commit 전 실제 diff를 예상 patch와
  대조, 예상 밖 hunk가 있으면 commit하지 않기.
- **강한 보장**: 사용자 생성 격리 worktree에서 작업하고 merge 시 충돌 처리, 또는 path 단위
  lock/CAS를 둔다.
- **불가능한 것**: 같은 working tree·같은 path·동시 편집·lock 없음·세션 id 없음이라는 네
  조건을 유지하면서 Git이 최종 blob을 세션별로 자동 분해해 주는 것.

이는 managed worktree를 기본으로 되살리자는 제안이 아니다. 평소 비중첩 흐름은 지금처럼
가볍게 두고, 실제 같은-path dirty가 관측될 때만 격리로 승격하는 조건부 경로다.

## 8. 추가해야 할 검증 좌표

수리를 승인한다면 다음 fixture가 있어야 같은 결함이 정적 문구 검사만 통과해 돌아오지 않는다.

1. **branch graph 4칸** — equal / current ahead / integration ahead / diverged에서
   `not yet on integration` 실제 path 수.
2. **same-path two-session** — 한 파일 두 hunk 중 외부 hunk가 tweak commit에 타지 않아야 함.
3. **detached tweak** — 종료 commit을 포함하는 이름 있는 ref가 정확히 하나 이상.
4. **mixed request cut points** — 첫 tweak 전, 첫 tweak 후, card planning 후 세 번 죽여도 item
   완료 집합이 같음.
5. **read-only request** — 상태 질문·설명 요청은 Tweak Entry가 아니라 normal resume/domain
   entry로 감.
6. **two claims × higher row** — verify running, prepared route, layer marker 각각에서 claim 선택
   질문 0회.
7. **prepared route × tweak** — tweak가 먼저 HEAD를 바꾸지 않고 route가 prefix로 재개됨.
8. **stale integration × design decision** — 최신 결정을 포함하기 전 tweak 분류 불가.
9. **glossary-only conflict** — 버튼 문구가 정본 용어와 충돌하면 tweak가 아닌 경로로 감.
10. **multi-unit pure tweak** — 항목별 unit이 02·03이면 commit도 02·03으로 분리되고 `01`로
    합쳐지지 않음.

현재 테스트의 `a commit names its own paths whatever else the working tree has staged`
(`scripts/git-state-transitions.test.js:95-106`)은 **다른 파일 경로** 격리만 증명한다. tweak
invariant (`scripts/repository-invariants.test.js:1051-1077`)도 문구 존재와 중복 부재를
증명할 뿐 위 실행 좌표를 걷지 않는다. 기존 테스트를 약화하지 말고 이 좌표를 별도로 더해야
한다.

## 9. 공격했으나 버틴 영역

- **자유 병렬의 기본 전이** — 같은 unit의 세 번째 점유가 질문 없이 성립하고, `parallel:`은
  legality가 아니라 정보로만 남는다. 상호성 술어와 `+` 그룹 점유 경로는 배포 원문에서
  제거됐다.
- **고아 점유 판정** — 정합성 1항의 번호를 보존한 채 owner.md와 맞지 않는 id를 잡는다.
- **명시적 파킹** — 사용자 요청이 없으면 release하지 않고, evidence card의 무출구도 막는다.
- **봉쇄 허용/대기 열거** — 네 append 종류와 최종 task commit만 계속하고, 발급·점유·소비·
  verify 상태·문서 변경은 기다린다. 정본 밖의 “안전한 줄” 판단어가 없다.
- **3-way journal 병합** — base의 소비 줄은 복원되지 않고 base에 없던 양쪽 추가는 남는다.
  merge fixture가 실제로 통과했다.
- **verify journal 세 계급** — 정본 형식, target 없는 cross-task decision, attributed open item이
  retain되고 나머지는 anomaly다.
- **발급/점유 경쟁 분리** — 같은 카드 claim 경쟁과 같은 번호의 서로 다른 card mint가 다른
  규칙으로 간다.
- **Design head 부재 분기** — 문서 없음·legacy·고정 경계 비유일은 mapping을 열지 않는다.
- **은퇴 관측 게이트** — 전문은 principles 한 곳에 있고 product는 이름만 참조한다.
- **저장소 루트와 하위 폴더 진입** — `git rev-parse --show-toplevel` 한 문장으로 중첩
  devflow 생성을 막는다.
- **플랫폼 배포 바이트** — 저장소·Claude cache·Codex cache 핵심 파일이 같고 두 CLI가
  0.14.1 enabled 상태를 보고했다.
- **언어 전략** — `_ko`는 소유자 검토 정본, 영문은 AI 배포물이라는 이중 언어 구조와
  구조 동형성 검사가 유지된다. 이번 소견은 한국어의 표현 다양성 때문에 나온 것이 아니라
  Git 상태와 라우팅 좌표의 부재에서 나왔다.

## 10. 감사 한계와 종료 선언

- 실제 제품 `nanomia-ade`의 한 사이클은 실행하지 않았다. 사용성·carry 품질·오분류율은
  여전히 현장 관찰 대상이다.
- 원격 보호 브랜치·네트워크 단절은 로컬 Git fixture로 흉내 내지 않았다. 로컬 branch,
  worktree, ancestry, commit snapshot 동작은 실제 Git으로 확인했다.
- Claude와 Codex의 새 대화에서 모든 시작 대사를 모델별로 반복하지 않았다. 설치 상태와
  배포 바이트 동등성까지만 확인했다.
- 이번 보고 뒤 구현이 바뀌지 않았으므로 “수리분 재감사”는 아직 대상이 없다.

한 번의 소스 전수 대조, 변경 축 좌표 스윕, 세 Git fixture, 전 소견 자기 반증을 마쳤다.
같은 문장을 표현만 바꾸는 추가 라운드는 열지 않는다. 다음 단계는 소유자가 7절의 수리
방향을 선택하는 것이며, 승인 전에는 스킬을 고치지 않는다.
