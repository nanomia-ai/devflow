# v0.16.0 구현 보고 — coordinator는 선언된 역할이고 devflow는 그대로다

작성 2026-08-15 · 계획 `plan_ko.md`의 §2 파일 지도대로 구현했고, 두 지점에서 계획을 벗어났다.
그 둘은 §3에 근거와 함께 기록한다.

## 1. 무엇이 실렸나

| 대상 | 내용 |
|---|---|
| `skills/principles/coordinator.md` + `_ko` | 신규 역할 계약 아홉 조항. 호출하는 스킬이 없는 첫 역할 계약 |
| `scripts/session-start.js` | 조건부 한 줄 — devflow 단계를 수행할 에이전트를 디스패치하는 경우에만, 계약의 절대 경로를 계산해 제시 |
| `hooks/hooks.json` | SessionStart `timeout: 5` |

| `README.md` + `_ko` | 사람용 요지와 포인터 |

| `AGENTS.md` | 쌍 등록 |
| `scripts/*.test.js` | 배선·경계 단언 |

**기존 스킬 여덟 개와 규칙 정본·세 판정 정본·planning-evidence·역할 계약 넷은 diff 0이다.**
`skills/` 아래 변경은 새 파일 하나뿐이고, 어떤 스킬도 그 파일을 읽지 않는다는 것을 기계 검사가
지킨다 — 진입 고정비 증가는 훅 한 줄뿐이다.

## 2. 왜 — devflow는 바뀔 필요가 없었다

호환성 점검이 오케스트레이터의 의무 아홉을 뽑았을 때, 셋은 devflow가 이미 감지하고 있었다
(카드 모호성은 resume이 묻고, 잘못된 커밋은 정합성 이상이 되고, 손 편집은 승인 신선도가
무효화한다). 감지할 수 없는 셋 — 사람 관문 대리 응답, 파일 전체 재작성, 지식이 디스크 밖으로만
흐르는 것 — 은 전부 신뢰 경계 바깥이라 어떤 메커니즘으로도 막을 수 없다. 그래서 빠진 것은
메커니즘이 아니라 계약이었고, DD-19의 역할 계약 형식이 이미 그 자리에 있었다.

devflow가 이 형태를 이미 상정하고 있었다는 증거도 셋 확인했다: DD-53(한 폴더 여러 세션이
정상), split 병렬 조건의 `a single agent's compile error`, 매트릭스의 기존 H28×A18 행.

## 3. 계획 이탈 2건

**이탈 1 — F3(규칙 정본 앵커 한 줄) 철회.** 계획은 AGENTS의 "인가된 예외는 principles 안에서
선언한다"를 근거로 정본에 한 줄을 넣기로 했으나, 구현 직전 재검토에서 그 규칙의 전제가 맞지
않음을 확인했다. 계약의 아홉 조항 중 정본 규칙에 예외를 만드는 것이 하나도 없고 — 전부 정본이
정한 것을 흐름 밖 행위자에게 적용한다 — 게다가 그 한 줄은 예외를 선언하지 않고 파일 이름만
부르므로 규칙이 요구하는 생존도 주지 못한다. 반대로 "다른 에이전트를 디스패치하는 세션"이라는
주어가 기획 축의 격리 조사를 띄우는 세션까지 포함해 정상 흐름에 새 모호성을 만들었다. 소유자
결정으로 철회했고, 계약의 존재·역할은 문서 지도와 DD-70이 기록한다. 결과로 기존 스킬 diff 0을
얻었고, 기계 검사는 "정본이 계약을 지목하는가" 대신 **"어떤 스킬도 계약을 참조하지 않는가"**
라는 더 강한 단언이 됐다.

**이탈 2 — 결정 상태 형식 확장.** DD-70이 DD-52의 조건부 선제 점유를 정정하는데, DD-52는 이미
DD-62 정정을 달고 있고 상태 형식이 정정을 하나만 허용했다. 저장소 자신의 규칙이 "일부만 물러난
결정은 표시하라"고 요구하는데 형식이 그것을 표현할 수 없었으므로, 셋째 상태가 정정 참조를 하나
이상 받도록 규칙 문장과 검사 정규식을 넓혔다. 상태 종류는 여전히 셋이고 기존 항목은 전부 그대로
통과한다.

## 4. 검증

교차 루프와 신선 컨텍스트 감사를 계획 §7대로 돌렸다.

| 단계 | 결과 |
|---|---|
| 한국어 독립 검증(신선) | 소견 3 — 명백 1·판단 2 |
| 재검토 | 채택 3 · 기각 0 · 소유자 판단 0 |
| 수리 적용 + 유계 재검증 | 3건 착지, 세 장면 문자 재걷기 통과 |
| 영문 최종 검증(같은 세션, 재감사 지위) | **신규 소견 0** · 이전 소견 셋 폐쇄 확인 · 기계 검사 95/95 |

채택된 소견 셋은 전부 **제 설계가 놓친 것**이었다.

1. **DD-52와의 충돌** — DD-52는 "오케스트레이터가 통합을 쥐는 환경"에서 선제 점유를 탈출구로
   뒀는데, DD-70이 그 탈출구만 막고 대체 규칙을 주지 않아 그 환경의 워커가 최초 점유에서
   봉쇄에 걸릴 수 있었다. 계약이 "코디네이터는 통합 브랜치를 체크아웃한 채로 두지 않는다"를
   흡수해 닫았다.
2. **소유자 없는 규칙** — "한 카드는 한 번에 한 세션"의 현재 거처가 전부 **사람 배정자**를
   전제한다("사용자 몫"·"사용자 의도"). 오케스트레이션에서 배정자는 코디네이터인데 계약이
   그것을 이어받지 않아 규칙이 주인을 잃었다. 예측 장면은 재시도 정책이 살아 있는 워커의
   카드를 재배정하고, 모든 워커가 같은 id를 상속하므로 두 번째가 그 점유를 이어받는 것이다.
3. **부분 흡수** — 계약 8조가 verify의 거부 조건을 "대상 능력 폴더"로만 좁혔는데, 실제로는
   트리 어디든 `devflow/` 밖 미커밋이 있으면 미검증이 기록되고 유령 수정 카드가 생기며 그
   번호가 영구 소모된다. 병렬 구현 중에는 그것이 기본 상태다.

**흡수 누락 렌즈**를 이 라운드에 추가한 것이 셋 중 둘을 잡았다. 그 렌즈를 넣은 이유는 구현
도중 README에 이미 있던 오케스트레이션 규칙("워커를 띄우기 전에 카드를 발급해 통합에
착지시킨다")이 포인터로 대체되며 사라질 뻔했기 때문이다. 저장소가 그 주제로 이미 말하고 있던
것을 전수로 확인하지 않은 것이 원인이었고, 같은 종류를 더 찾는 것이 그 렌즈의 임무였다.

## 5. 부수 수리 — Codex 훅

호환성 확인 중 devflow의 Codex 훅이 이 환경에서 동작하지 않음을 발견하고 openai/codex 소스로
원인을 확정했다. **파일은 이미 규격에 맞다** — `CLAUDE_PLUGIN_ROOT`는 Codex가 공식 호환으로
주입하고 `${...}`를 셸이 아니라 Rust 문자열 치환으로 처리하므로 Windows cmd.exe에서도 동작하며,
`hooks/hooks.json`은 Codex의 기본 경로이고 출력 JSON도 SessionStart 스키마와 일치한다.
`codex-hooks.json` 분리나 `commandWindows` 추가는 불필요하고 재신뢰만 유발한다.

**유일한 원인은 신뢰다** — `~/.codex/config.toml`에 devflow 항목이 없어 `Untrusted`로 스킵된다.
Codex TUI의 `/hooks`에서 한 번 신뢰해야 하고 CLI 서브커맨드는 없다.

그 조사가 **실제 결함 하나**를 찾았다: SessionStart 기본 타임아웃이 600초라 훅이 멈추면 세션이
10분 잡힌다. `timeout: 5`를 넣었다. 신뢰 해시가 바뀌므로 사용자의 신뢰 동작을 한 번으로 묶기
위해 이 라운드에 함께 실었다.

## 6. 한계

- 계약에는 강제력이 없다. 무시하는 오케스트레이터를 막는 장치는 없고, 그것이 devflow가
  선언한 신뢰 경계다.
- 훅은 devflow 상태가 이미 있는 저장소에서만 발화한다. 상태 생성 전에 시작한 오케스트레이터
  세션은 README·폴백 문서 경로로만 닿는다. 다만 병렬 점유의 위험은 트리가 생긴 뒤에만
  존재하므로 포인터는 그것이 처음 문제가 되는 순간보다 먼저 도착한다.
- 실전 오케스트레이션 사이클은 0회다. 계약의 아홉 조항이 실제 마찰을 줄이는지는 측정되지
  않았다.
