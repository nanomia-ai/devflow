## 0. 한 문장 목적지와 경계

**product·arch·adopt·split은 별도 사용자 스킬 없이 필요한 사실을 스스로 확인하고, 사용자의
결정 묶음을 구속하기 전에 더 나은 실질 대안 하나가 있는지 유계로 재검토하며, split은 페이지·
목록·모달 같은 하위 덩어리도 카드 네 필드가 유일해질 때까지만 기획한다. verify에서 완료된
수리의 신호가 다시 non-pass이면 같은 수리 계보를 기계적으로 복원하고, 새 수정 카드는 직전
수리 라운드의 증거를 기존 카드 필드로 물려받으며, 두 번째 재관측부터는 사람에게 돌아간다.**

이번 라운드는 다음을 만들지 않는다.

- 사용자가 따로 호출해야 하는 research·diagnosis·repair 스킬.
- 새 역할, 새 기획 문서층, 원시 조사 파일, 보편 점수표, 상시 출력 절차.
- product의 partial 디스크 상태나 planning-frontier 상태.
- 조사 카드용 새 failure route, repair episode, 자동 가설·예측 의식.
- `.stale.` 재분할 지식 착지 규칙. 이 축은 현재 백로그의 실전 관찰 경계를 존중해 보류한다.
- reviewer·work·resume·baseline-predicates의 새 동작.

정상적인 작은 프로젝트, 일반 work, reviewer에는 추가 질문·상태 commit이 없다. 정상 pass도
사용자 왕복과 상태 쓰기는 늘지 않지만, 회귀 label이 있는 능력 검증은 verifier 실행 전에 현재
묶음에 비례하는 기계 route 투영을 한 번 읽는다. product·arch·adopt는 companion 통독이 진입
고정비이고, split은 유지보수 등급 판정이나 verify-origin 라우팅에서만 필요한 정확한 절을 읽는다.

## 1. 왜 계획 3이 필요한가

계획 2는 기획 축의 대부분을 구현 가능한 수준까지 닫았다. 특히 planning-evidence companion,
질문 프런티어, product·arch·adopt의 사실 권위 분리, split 0/1/2a/2b, 구속 전 재검토,
F-A 최초 신호 보존, clean reviewer/verifier, 재관측 2 이상 사람 관문은 그대로 보존한다.

구현 전 검증은 수리 축에서 다섯 실패 경로를 확인했다.

| # | 계획 2의 문제 | 구체적 실패 경로 | 계획 3의 교정 |
|---|---|---|---|
| P3-1 | root가 있는 label과 없는 label의 한 실행 혼재를 전부 판정 불가로 봄 | 기존 수리 C1과 무관한 새 실패 G가 함께 나오면 G의 정상 라우팅까지 막힘 | 항목별 root 판정 뒤 root별로 묶는다. 모호한 항목만 막고 나머지는 계속한다 |
| P3-2 | verifier가 반환한 label을 실패 이력에 영속화하지 않음 | 결과 기록 뒤 라우팅 전에 중단되면 다음 세션은 새 카드의 `읽을 것`에 넣을 신호 카드를 복원하지 못함 | label-bearing 항목에 `신호 카드` 필드를 영구 기록한다 |
| P3-3 | 상속 집합을 최대 두 장이라고 단정함 | 정본 라우팅은 `C1+C2+C3`처럼 한 장 이상을 허용하므로 일부 카드를 누락하거나 계획의 상한이 거짓이 됨 | 현재 신호 카드와 직전 수리 라운드의 정확한 route 카드 집합을 정본 카드 번호 순서로 쓴다 |
| P3-4 | `읽을 것`의 모든 `.done.` 카드에 work 가설·예측을 강제함 | 정상 유지보수 카드가 과거 완료 카드를 참고해도 수리 진단 절차가 오발동함 | work은 diff 0. route를 아는 split이 카드의 `왜`·`금지`·`읽을 것`에 증거를 넣는다 |
| P3-5 | verify에 별도 `함정` 승격 배선을 추가함 | 기준선 정본이 이미 새 완료 카드와 직접 `읽을 것`을 갱신 입력으로 받는데 하위 문서가 같은 선택 규칙을 중복함 | baseline-predicates와 verify의 특수 승격 문구는 diff 0. 기존 전면 갱신을 forward-test한다 |

추가 판단 둘도 여기서 닫는다.

- 계획 2의 U7/D22는 이번 핵심 문제보다 넓고, 실전 마찰 뒤에만 규칙을 넣는 기존 백로그와
  긴장한다. v0.15.0 구현에서는 제외한다. 이는 삭제가 아니라 별도 후속 후보의 보류다.
- 한국어 원본 검토는 계획 승인으로 대신할 수 없다. 구현은 기획 묶음과 수리 묶음의 `_ko`
  원본을 각각 한 번 검토받은 뒤에만 대응 영문을 쓴다.

## 3. 사용자가 보게 될 작동 장면

1. 새 프로젝트는 product → arch → 선택적 design → split로 간다. 별도 research 명령은 없다.
2. 기존 프로젝트는 adopt로 들어간다. 코드·고정 버전의 외부 계약·소유자 의도가 서로의 권위를
   빼앗지 않는다.
3. 사용자 질문 전에는 AI가 현재 저장소 사실·외부 계약 사실·실행 사실을 허용된 범위에서 먼저
   닫는다. 가치 선택만 사용자에게 간다.
4. 결정 묶음을 닫기 직전 현재 성공 판정과 확인된 제약에 더 맞는 실질 대안이 있으면 하나만
   비교한다. 없으면 추가 출력이 없다. 사용자가 다시 선택하면 그 묶음은 닫힌다.
5. 페이지·목록·모달 같은 하위 덩어리는 이름이나 크기가 아니라 카드의 목적지·왜·금지·완료
   신호가 유일한지로 판단한다. Layer 0가 열리지 않아도 §5 U5의 진전 조건을 통과하는 프런티어만
   이어 가며, 같은 미결 집합을 표현만 바꿔 다시 묻지 않는다.
6. 최초 검증 non-pass는 현행 수정 카드로 간다. 그 카드가 완료된 뒤 같은 신호가 다시 non-pass일
   때만 수리 계보의 `재관측 1`이 된다.
7. 새 수정 카드는 직전 실패·이전 수리 카드의 정확한 경로와, 증거가 허용하는 한 줄짜리 결과를
   받는다. 구현자는 그 증거를 읽되 특정 진단 방법을 강제받지 않는다.
8. 같은 계보가 다시 non-pass이면 자동으로 세 번째 수리 카드를 만들지 않는다. 전체 계보와 현재
   증거를 사람에게 보고하고 `라우팅: 대기`를 유지한다.

## 5. 기획 축 구현 명세

### U1 · planning-evidence companion

**왜.** 같은 규칙을 네 스킬에 복제하면 문구가 갈라지고, principles 본문에 넣으면 work·verify까지
매번 읽는다.

**목적지.** 네 planning 소비자가 같은 미지수 분류와 정지 조건을 쓰되, 각 단계의 소유권은
유지한다.

필수 heading과 내용:

```text
미지수 네 종류        현재 저장소 사실 / 외부 계약 사실 / 실행 사실 / 소유자 결정
차단 사실과 후속 사실  차단이면 답·충돌·불가 중 하나까지 다음 단계 금지
출처 소유권            누가 그 사실을 바꿀 수 있는가로 권위를 정함
정지 조건              settled / conflicted / unavailable
영속화                 결론 + 현재 결정에 미친 영향 + 정확한 출처만 기존 거처에 남김
격리 조사              답만 필요한 내부·외부 근거 탐색의 선택적 격리, 같은 탐색 범위는 한 조사자에 묶고 구조 이해는 메인 소유
실제 제시 선택지 기준  한 선택지가 뒤 질문의 필요·선택지·추천 기본값을 바꾸면 의존
구속 전 재검토          네 조건을 통과하는 실질 후보 하나가 있을 때만 보임
```

구속 전 재검토 조건은 다음 넷이다.

1. 현재 증거 또는 이미 허용된 조사 trigger의 증거로 설명할 수 있다.
2. 사용자 결과·제품 경계·되돌리기 비용·검증 가능성 중 하나를 실질적으로 바꾼다.
3. 이름이나 표현만 다른 안이 아니라 다른 trade-off가 있다.
4. 현재 단계의 소유권 안에서 비교할 수 있다.

후보가 없으면 출력·질문·조사·기록 0. 후보가 여럿이면 성공 판정과 사용자 우선순위가 하나를
가를 때만 하나를 제안하고, 가르지 못하면 현재 안을 유지한다. 사용자가 재선택하면 같은 묶음은
재귀 재검토하지 않는다.

조사와 질문의 분기는 다음 기계 기준으로 구현한다.

- 사용자가 조사를 명시하면 결정 영향과 무관하게 요청 범위만 조사한다. 그 결과가 현재 단계를
  막는 사실이 아니면 조사 결과를 답하고 원래 프런티어를 계속한다.
- 자동 조사는 아직 settled가 아닌 사실의 가능한 결과 중 하나가 현재 후보를 제거·추가하거나,
  추천 기본값·Layer 0 필드·검증 가능성 중 하나를 바꿀 때만 실행한다. 어느 결과도 바꾸지 않으면
  조사하지 않는다.
- 그 사실이 닫히지 않으면 현재 선택의 허용 여부나 완료 검증을 결정할 수 없는 경우 `차단`이다.
  안전한 기본값으로 현재 결정을 구속할 수 있고 나중 결과가 최적화만 바꾸면 `후속`이다.
- 사실을 소유한 출처 또는 실행 결과가 답하면 settled, 권위가 같은 출처가 양립하지 않으면
  conflicted, 허용된 도구·권한으로 확인할 수 없으면 unavailable이다. conflicted·unavailable인
  차단 사실은 사용자에게 정확한
  충돌·부재와 바뀌는 결정을 보고하고 멈춘다. 후속 사실은 현재 소유 문장에 상태와 영향만 남긴다.

조사의 길이나 내부·외부 구분만으로 직접 수행과 격리를 가르지 않는다. 다음 판단을 위해 코드
흐름·문서 구조·도메인 맥락 자체를 이해해야 하면 메인이 직접 읽는다. 그 밖에는 이미 정확한 경로·
심볼·URL을 알거나, 출력 상한을 건 읽기·검색 한 번이 새 경로·출처를 따라가지 않고 사실을 닫으면
메인이 직접 확인한다. 답은 유계하고 결론과 근거 좌표만으로 다음 판단이 가능하지만 새로 발견한
경로·출처를 따라가야 하거나, 둘 이상을 대조하거나, 같은 결정에 독립 사실 확인이 2개 이상이면
플랫폼이 격리 실행을 지원할 때 같은 탐색 범위의 질문들을 조사자 하나에게 함께 맡긴다. 질문별·
출처별 조사자를 만들지 않는다. `adopt`의 대표 흐름
추적과 `arch`가 구조를 선택하기 위해 필요한 원자료 이해는 메인이 소유하되, 그 안의 위치·사용처·
버전처럼 유계한 하위 질문만 격리할 수 있다. 같은 탐색 범위란 현재 결정 하나에 필요하고 허용할
저장소 경로와 외부 도메인·버전을 한 브리프에 유계하게 열거할 수 있는 질문 집합이다. 원자료
이해가 필요한지 답만 필요한지 갈리면 메인이 소유한다.

조사자는 저장소와 외부 1차 출처를 읽기·검색만 하며 재위임·파일 쓰기·제품 코드·test·prototype
실행·결정을 하지 않는다. 반환은 `settled`·`conflicted`·`unavailable` 중 하나, 질문별 결론,
내부의 정확한 경로·
행·심볼 또는 외부의 출처·버전·조회 시점, 적용 경계와 남은 충돌뿐이며 탐색 transcript와 원시
출력을 싣지 않는다. 실행으로만 닫히는 사실은 메인이 현재 단계가 허용한 안전한 실행 또는 기존
검증 창구에서 관측하고, prototype이나 코드 변경이 필요한 조사는 기존 조사 카드와 work 경로로
보낸다. 소유자 결정과 구속 결정은
조사자에게 맡기지 않는다. 메인은 구속 결정을 바꾸는 핵심 근거 좌표만 확인하고 전체 탐색을
반복하지 않은 채 영향 판단과 기존 거처 영속화를 소유한다. 차단 사실이면 조사 반환 전 의존
결정을 구속하지 않고, 독립 작업만 계속할 수 있다. 격리 실행이 없으면 같은 범위를 직접 조사한다.

| 미지수 | 답의 소유자 | 첫 행동 |
|---|---|---|
| 현재 저장소 사실 | 현재 code·config·manifest/lockfile·test·실행 결과 | 질문하지 않고, 이미 아는 좌표·유계 검색 한 번은 직접 확인하고 새 경로 추적·대조·반복은 위 격리 기준 적용. 실행은 기존 검증 창구로 관측 |
| 외부 계약 사실 | 고정 버전의 공식 문서·명세·소스·1차 API | 저장소에서 버전을 먼저 찾고 그 버전·조회 시점을 고정한 뒤 위 격리 기준 적용. 최신 문서로 구버전을 증명하지 않음 |
| 실행 사실 | 현재 환경에서 허용된 안전한 호출·렌더링·상태 전이의 관측 | 직접 실행. 쓰기·비용·권한이 필요하면 차단 여부에 따라 정확한 허가 요청 또는 후속 거처로 이동 |
| 소유자 결정 | 가치·우선순위·위험 감수·사용자 경험을 정하는 사용자 | 확인된 사실과 추천 이유를 붙여 질문하고 답 전에는 닫지 않음 |

소비자별 발동 지점도 고정한다.

| 소비자 | 사실 확인 지점 | 구속 전 재검토 지점 | 넘지 않는 경계 |
|---|---|---|---|
| product | 현재 프런티어를 사용자에게 묻기 전 | 답을 반영한 뒤 다음 프런티어 생성 또는 최종 확인 전 | stack·DB를 선택하지 않음 |

후속 사실의 거처도 새로 판단하지 않는다. product는 `열린 질문`, arch는 안전한 기본값을 가진
`잠정값`과 `해소 카드`, split은 목적지·완료 신호를 추측하게 만드는 미지수일 때 기존 `조사 카드`를
쓴다. adopt에서 나온 미래 결정은 그 결정을 소유하는 product·arch·split로 보낸다. 어느 거처에도
맞지 않으면 새 파일이나 임의 카드에 쓰지 않고 정확한 소유 단계와 함께 보고한다.

### U2 · product

**왜.** 사용자가 확인할 수 없는 사실이 질문으로 가고, 고정 총순서는 어떤 제품에서 성공 판정이나
화면 제약이 앞선 해결 방식 선택을 뒤집는다는 사실을 놓친다.

**목적지.** 여섯 판단을 유일하게 쓸 수 있을 때까지 사실은 AI가 닫고 가치 결정만 묻는다.

- 같은 프런티어의 독립 질문은 최대 5개, 보통 3~5개로 묶는다.
- 실제 선택지 하나가 뒤 질문의 필요·선택지·기본값을 바꾸면 단건으로 먼저 묻는다.
- 사용자의 자유 입력 뒤에는 그 실제 답으로 남은 의존을 다시 계산한다.
- 명시 조사는 항상 좁게 실행한다. 자동 조사는 현재 결정을 바꿀 사실일 때만 실행한다.
- product의 자동 사실 확인은 stack·DB를 결정하지 않는다. 그 선택은 arch 소유다.
- 능력 한 줄은 번호·이름·사용자 결과·그 결과가 성공 판정에 필요한 이유를 한 번만 가진다.
- 목표 라운드 예산을 소진하고도 계속할 때 확정 내용과 남은 질문을 대화로 한 번 요약한다.
  파일·상태·commit은 만들지 않는다.

의미 밀도는 새 반복 양식을 만들지 않고 기존 거처를 조합해 완성한다. `문제`는 바꾸려는 현재,
`해결 방식`은 선택과 이유·버린 방식, `성공 판정`은 바라는 관측 결과를 소유한다. 능력 행만
사용자 결과와 그 결과가 성공 판정에 필요한 이유를 한 번 보강한다. 같은 왜를 정체성·경계·카드에
복제하지 않는다.

### U3 · arch

**왜.** 모델 기억의 후보가 지원 플랫폼·버전·라이선스·배포 환경에서 이미 죽어 있을 수 있고,
차단 사실과 나중에 측정할 잠정값이 섞일 수 있다.

**목적지.** 사용자에게 올리는 후보는 생존 사실과 verify channel 실행 가능성이 확인돼 있다.

- 구성요소 뒤, stack 선택 전에 후보를 죽이는 사실만 확인한다.
- 되돌리기 어렵고 경계가 비자명하며 실제 trade-off가 있을 때만 counter-design 하나를 비교한다.
- 현행 비교표 금지는 stack 질문 형식에 한정한다. 조건부 두 설계까지 금지하지 않는다.
- 차단 사실은 확인 전 진행을 막고, 잠정값은 안전한 기본값과 해소 카드를 가진다.
- verify channel은 이름의 존재가 아니라 현재 환경에서 실행 가능한지 확인한다.

arch의 의미 밀도도 기존 거처를 쓴다. 구성요소와 stack은 이미 `선택 + 근거 1줄`, 비자명하고
되돌리기 어려운 경계는 기존 ADR, 불확실한 수치는 잠정값+해소 카드, 바라는 관측은 실행 가능한
verify channel이 소유한다. product의 사용자 결과와 성공 판정을 arch에서 다시 서술하지 않는다.

### U4 · adopt

**왜.** 현재 코드, 고정 버전의 외부 계약, 미래 의도는 서로 다른 질문의 권위다.

**목적지.** 관찰이 해석이나 미래 결정으로 조용히 승격되지 않는다.

- 현재 구현은 코드, 외부 가능성은 해당 버전의 1차 출처, 미래 방향은 소유자가 결정한다.
- 후보별 내부 증거표는 대화 안에서만 쓰고 파일로 저장하지 않는다.
- 외부 버전을 확인하지 못하면 `버전 미확인`으로 남기며 최신 문서로 증명하지 않는다.
- 확인 묶음 전 관찰·해석·결정 preview를 구분한다.
- 구속 전 재검토는 현재 동작 보존과 목표 방향이 실제 다른 결과를 낼 때만 보인다.

### U5 · split 0/1/2a/2b

**왜.** Layer 0와 작업 카드 사이에서 작은 도메인 덩어리의 기획을 필요한 깊이만큼 이어 갈
장치가 없다.

| 등급 | 기계 조건 | 행동 |
|---|---|---|
| 0 | 정확한 기존 출처에서 카드 네 필드가 각각 한 문장으로 유일 | 질문 0, 카드 작성 |
| 1 | 한 묶음의 답으로 네 필드가 유일 | 추천이 붙은 묶음 하나 뒤 카드 작성 |
| 2a | 실제 선택지나 실제 답이 Layer 0 필드를 바꾸거나 ADR 3조건을 통과하는 결정을 요구 | 카드 없이 owning stage로 환류. 2b보다 우선 |
| 2b | Layer 0는 보존되지만 한 묶음 뒤에도 카드 필드에 유효 문장이 둘 이상 | 같은 유지보수 대화에서 다음 의존 프런티어를 계속 |

Layer 0 필드는 product의 정체성·능력·경계·성공 판정과 arch의 구성요소·stack·코드 구조·데이터·
검증 창구다. 페이지·목록·모달은 예시일 뿐 trigger가 아니다. 2b 답은 카드 네 필드 중 하나에
착지해야 하며, 못 하면 2a다. 새 용어가 확정되면 발견→갱신 표의 glossary 한 줄 경로를 쓴다.
능력 설계 구역·새 기획 파일·새 상태는 만들지 않는다.

2b는 직전 답이 네 필드 중 하나의 유효 문장을 줄이거나 새 실제 의존을 드러낸 동안만 다음
프런티어를 만든다. 같은 미결 집합이 그대로면 같은 질문을 바꾸어 반복하지 않는다. 정확히 남은
필드와 추천 하나를 보여 사용자 결정을 기다리거나, 실행 사실이면 기존 조사 카드, Layer 0면
2a로 보낸다. 이 비교는 대화 안에서만 하며 새 상태로 저장하지 않는다.

## 6. 수리 축 최종 명세 — L-B″

### 6.1 용어와 저장 형식

- **신호 카드**: 현재 회귀 완료 신호를 소유한 `.done.` 작업 카드 번호. verifier에게는 현재
  항목의 label이고, 과거 의미가 아니다.
- **수리 계보 root**: `<product | 고정 능력 번호>@<그 계보 최초 실패의 출처 id>`.
- **재관측 n**: 완료된 수리 경계의 현재 신호가 다시 pass를 주지 못한 verify 실행 차수.
  중간 pass는 새 수를 만들지 않고 과거 최댓값도 지우지 않는다.
- **직전 수리 라운드**: 같은 root에서 완료된 `라우팅: 수정 카드`를 가진 항목 중, root 최초
  항목을 0으로 보고 현재 `재관측`보다 작은 가장 큰 라운드. 같은 라운드 항목들의 완료된 수정
  카드 route를 모두 포함한다.

실패 이력 줄의 정확한 형식과 필드 순서:

```text
- 출처 id: <id>; timestamp: <ts>; <실패: … | 미검증: …>; 라우팅: 대기
- 출처 id: <id>; timestamp: <ts>; <실패: … | 미검증: …>; 신호 카드: <번호>; 라우팅: 대기
- 출처 id: <id>; timestamp: <ts>; <실패: … | 미검증: …>; 신호 카드: <번호>; 수리 계보: <root>; 재관측: <양의 정수>; 라우팅: 대기
```

주 시나리오·적대 입력·폐쇄 게이트처럼 완료 카드 label이 없는 항목은 첫째 형식이다. 현재 회귀
label은 있지만 과거 root에 연결되지 않는 최초 non-pass는 둘째다. root에 정확히 하나 연결되는
재발은 셋째다. `신호 카드`·`수리 계보`·`재관측`은 실패 이력과 함께 영구 보존되고 `New entries`
셈에 영향을 주지 않는다. 기존 항목을 소급 보강하지 않는다.

0.15.0 전에 만들어져 아직 `라우팅: 대기`인 구형 항목에 `신호 카드`가 없으면 기존 수정 route를
그대로 수행하되 상속 대상을 추측하지 않는다. 그 수정 카드가 완료된 뒤 현재 label이 다시
non-pass이면 과거 route 값으로 root를 복원하고 그 새 재발 항목부터 세 필드를 쓴다. 따라서
구형 기록을 날조하지 않으면서 다음 수리 경계부터 새 계약에 들어온다.

### 6.2 clean verifier와 결과 기록

1. verify 메인이 회귀 목록을 만들 때 각 실행 가능한 완료 신호에 신호 카드 번호를 붙인다.
2. 회귀 label이 하나 이상이면 §6.3의 route 투영을 실행해 각 label의 기존 root 후보가 0개 또는
   1개인지 확인하고 그 결과를 이번 실행 동안만 보관한다. 이상이면 verifier를 부르지 않는다.
3. verifier는 `(신호 카드 label, 실행할 완료 신호)`를 받아 실제 실행한다.
4. verifier는 label을 판정 근거로 사용하지 않는다. non-pass 결과를 해당 label과 함께 돌려준다.
5. 과거 verify.md·이전 카드·진행 로그·root·재관측 수는 받지 않는다.
6. reviewer 입력과 반환은 바꾸지 않는다.

### 6.3 verifier 전 유계 route 투영

회귀 목록에 label이 하나 이상일 때, verify 메인이 verifier를 부르기 직전에 다음 exact scope를
기계 질의한다.

```text
현재 검증 대상 key의 verify.md
트리 루트 verify.md
현재 회귀 묶음의 신호 카드가 속한 능력들의 verify.md
```

질의는 파일 본문을 모델에 주지 않고 현재 label 집합을 입력으로 받아 내부에서 기존 완료 route를
다음처럼 역색인한다.

```text
entry root = entry에 수리 계보가 있으면 그 값
             없으면 <그 파일의 검증 대상 key>@<entry 출처 id>

route_index[각 `라우팅: 수정 카드` 번호] += entry root의 집합
```

모델에 내는 결과는 기준 id 한 줄과 다음 두 행 종류뿐이다.

```text
base: <투영에 사용한 integration tip의 축약하지 않은 전체 commit object ID>
label: <현재 번호>; candidate roots: <root의 JSON 배열>
root: <현재 label에서 찾은 유일한 root>; max recurrence: <0 이상의 정수>;
previous route cards: <§6.1 직전 수리 라운드의 완료된 수정 route 카드 번호 JSON 배열>
```

`max recurrence`는 route 종류와 관계없이 같은 root의 재관측 최댓값이다. `max recurrence: 0`의
previous route는 root 최초 항목의 route이고, 그 뒤에는 §6.1의 직전 수리 라운드 route다. 가장
최근 재관측이 문서 교체·product 재실행이면 그 값은 유지하되 비카드 route를 직전 수리 라운드로
세지 않는다. 같은 카드 번호가 같은 root의 여러 항목에 다시 나타나도 후보 root는 하나다. 중복
root를 제거한 집합의 크기로만 0·1·2 이상을 판정한다. 실패 본문·시나리오·회귀·표준·잠정값과 현재
label에 닿지 않는 항목은 출력하지 않는다.
따라서 출력은 파일의 영구 실패 이력 길이가 아니라 현재 label 수와 직전 route 카드 수에
비례한다. 회귀 label이 없는 제품 검증과 label 없는 항목만 있는 능력 검증에서는 이 투영을
실행하지 않는다.

같은 root의 직전 수리 라운드 항목이 여러 개이면 그 값의 **모든 완료 route 카드**를 합집합으로
내고 정본 카드 번호 순서로 정렬한다. 한 항목만 고르지 않는다. 후보 root에 속한 항목의 root·
재관측·route 필드 중 하나라도 형식상 해석되지 않으면 부분 집계하지 않고 판정 불가다.

이 scope가 닫힌 이유도 구현 문장과 fixture가 증명한다. 능력층 실패의 수정 카드는 현행 6단계상
같은 능력 폴더에 생기므로 그 카드가 회귀 label이면 label 능력의 verify.md에 최초 항목이 있다.
제품층 실패의 최초 항목은 항상 트리 루트 verify.md에 있다. 현재 검증 대상이나 1홉 `의존` 카드가
다른 능력에 있으면 각각 첫째·셋째 경로가 그 파일을 더한다. 따라서 현재 label의 root를 가진
파일이 이 세 경로 밖에 남는 정상 route는 없다.

결과를 쓰기 직전에 integration tip이 `base`와 다르면 집계 결과를 재사용하지 않는다. verify의
기존 공유 상태 동기화·revision 신선도 판정을 다시 시작하고 새 tip에서 투영과 필요한 실행을
다시 한다. 동시 라우팅이 같은 카드 번호를 다른 root에 추가한 사이의 stale 분류를 commit하지
않는다.

결과 commit 뒤 route 전에 중단되면 같은 질의를 현재 pending source의 `신호 카드`·root·재관측
값으로 다시 실행한다. 이때 `previous route cards`는 현재 재관측보다 작은 값 중 가장 큰 **완료된**
수리 라운드의 route만 반환한다. 아직 `라우팅: 대기`인 현재 항목을 직전 라운드로 세지 않는다.

현재 label의 후보 root가 둘 이상이거나, 그 후보를 만드는 기존 필드가 해석되지 않으면 verifier를
실행하거나 verify.md를 쓰지 않는다. 정확한 label·후보 root·원문 항목을 `수리 계보 판정 불가`로
보고하고 사람의 정합화 뒤 전체 verify를 다시 시작한다. 의미로 하나를 고르거나 일부 label만
실행하지 않는다. 이것은 정상 mixed 실행이 아니라 기존 계보가 한 카드 번호를 둘 이상의 root에
사용한 정합성 이상이다.

### 6.4 항목별 root 판정과 mixed 실행

각 non-pass 항목을 독립적으로 판정한다.

```text
label 없음        → 현행 새 실패 항목
label root 0개    → 새 root의 최초 항목: `신호 카드`만 기록
label root 1개    → 기존 root의 재발: `신호 카드` + `수리 계보` + `재관측` 기록
label root 2개+   → §6.3의 판정 불가, 결과 전체 미기록
```

verifier가 non-pass로 반환한 각 항목을 §6.3에서 보관한 집계 결과에 대입한다. 같은 root로 돌아온
항목이 한 실행에 여러 개면, 쓰기 전 그 root의 `max recurrence`를 한 번 고정하고
모두 같은 `재관측 = 최댓값+1`을 쓴다. 각 항목은 기존 정본대로 자기 출처 id와 자기
`라우팅: 대기`를 가진다. 서로 다른 root와 root 없는 새 항목은 독립적으로 기록한다.

따라서 한 실행에서 기존 root R의 C1과 무관한 새 실패 G가 함께 non-pass이면 R만 한 번
전진하고 G는 새 root의 독립 `라우팅: 대기` 항목이 된다. 두 항목을 의미가 비슷하다는 이유로
합치지 않고, 혼재했다는 이유로 둘 다 막지도 않는다. 실제 route 처리는 기존 정본의 경로·출처
id 순서를 지킨다. R이 재관측 2 이상이라 사람 결정을 기다리며 먼저 서 있으면 G도 그 결정 뒤에
처리된다. 이는 G의 계보·route를 잃는 것이 아니라 기존 전역 대기 우선순위가 만드는 지연이며,
이번 라운드는 새 병렬 route 상태로 우회하지 않는다.

### 6.5 route와 카드 상속

실패 이력의 출처 id가 가장 작은 `라우팅: 대기` 항목부터 처리하는 현재 순서를 유지한다. 한
판정의 여러 실패는 각각 자기 route를 갖는다.

label-bearing 항목으로 수정 카드를 만들 때 split이 새 카드에 넣는 상속 집합은 다음과 같다.

```text
{현재 항목의 신호 카드}
∪ {같은 root의 직전 수리 라운드가 `라우팅: 수정 카드`에 기록한 카드 전부}
```

- 새 root의 최초 항목은 아직 같은 root의 과거 라운드가 없으므로 신호 카드 하나만 받는다.
- 재관측 1은 root 최초 항목의 route 카드 전부와 현재 신호 카드를 받는다.
- 사람이 재관측 2 이상에서 추가 수리를 승인했다면 이후 재관측은 가장 최근에 승인·완료된
  수리 라운드만 받는다. 계보 전체를 재귀로 읽지 않는다.
- 중복은 제거하고 정본 카드 번호 순서로 정렬한다. `C1+C2+C3`이면 세 장 모두이며 “최대 두
  장” 같은 임의 상한을 두지 않는다.
- 번호마다 route operations가 끝난 뒤의 최종 트리에서 정확한 카드 경로가 하나여야 한다.
  능력 재개봉이 조상 폴더의 `.done`을 제거하면 같은 operations 안의 rename을 적용한 최종 경로를
  `읽을 것`에 쓴다. 최종 경로가 없거나 둘 이상이면 추측하지 않고 route를 만들지 않는다.

verify는 현재 source를 split에 넘길 때 저장된 값으로 계산한 카드 번호 집합과 현재 non-pass
증거를 함께 준다. split은 route operations의 최종 경로를 계산해 새 카드의 `읽을 것`에 넣고
다음 두 필드를 기존 카드 문법 안에서 작성한다. 이 전달값은 별도 상태가 아니다. 중단 전에는
계산을 다시 할 수 있고, `라우팅 준비` 뒤에는 카드의 최종 바이트가 operations에 영속한다.

- `왜`: 현재 non-pass 증거와 직전 수리 라운드가 이 신호를 pass로 만들지 못했다는 결과.
- `금지`: 직전 카드의 진행 로그와 현재 실행 증거가 **동일 접근을 그대로 반복하면 같은 결과가
  난다**고 직접 뒷받침할 때만, 그 동일 접근의 무변경 반복을 한 줄로 금지. 근거가 없으면
  금지를 발명하지 않는다.

목적지는 신호 통과 자체가 아니라 그 신호가 지키던 능력 서술이 참이 되는 것이다. 완료 신호는
현행 DD-24대로 verifier의 재현 절차 또는 미검증 이유가 해소됐음을 실제 실행하는 점검이다.

work은 새 규칙을 받지 않는다. 기존 계약대로 카드와 모든 정확한 `읽을 것`을 통독하고 구현
방법은 스스로 정한다. 별도의 원인 가설·예측 출력은 강제하지 않는다.

### 6.6 재관측 관문과 무한 루프 상한

| 상태 | 자동 행동 |
|---|---|
| 새 root 최초 non-pass | 현행 수정 카드 route |
| 재관측 1 | 직전 수리 증거를 상속한 현행 수정 카드 route |
| 재관측 2 이상 | 자동 카드·실행 0. `라우팅: 대기` 유지, root·신호 카드·과거 route·현재 결과를 사람에게 보고 |

재관측 2 이상에서 사람은 현재 허용된 route 중 하나를 명시할 수 있다. 그 선택 전에는 새 카드나
출처 id를 만들지 않는다. 사람이 추가 수정 카드를 승인해도 이후 non-pass는 다시 사람 관문으로
돌아오므로 자동 루프는 다시 열리지 않는다.

실패 사다리는 한 work 실행의 prompt 보강·tier 상승·사람 호출을 소유한다. 이 수리 계보는
완료된 카드가 verify 경계를 건넌 뒤 다시 non-pass인 경우만 센다. 둘을 같은 카운터로 합치거나
새 사다리를 만들지 않는다.

### 6.7 폐쇄와 지식 착지

별도의 “수리 지식을 함정으로 승격” 규칙을 추가하지 않는다. 기준선 정본의 표준 갱신 집합은
이미 이번 폐쇄의 새 완료 카드와 그 카드의 직접 `의존`·`읽을 것` 경로를 읽는다. 따라서 현재
수리 카드, 직전 수리 카드, carry와 진행 로그가 기존 전면 갱신의 입력이 된다.

- 증상·재현 조건·원인·대안 네 칸이 현재 코드에서 다시 확인되면 기존 정본대로 `함정` 행이
  될 수 있다.
- 네 칸이 없으면 모든 수리를 억지로 `함정`으로 만들지 않는다.
- 현재 행위·불변식·진입점 등 다른 기존 절이 더 정확한 거처면 그 절을 쓴다.
- L18 forward test가 이 경로를 증명한다. 실패하면 구현 문구를 더하기 전에 실제 어느 입력이
  빠졌는지 보고하고 baseline 정본의 소유 경계를 다시 검토한다. verify 하위 문서에 예외를
  숨기지 않는다.

### 6.8 중단 복구

| 중단 지점 | 디스크 상태 | 다음 진입의 유일 행동 |
|---|---|---|
| verifier 반환 뒤 결과 쓰기 전 | 새 기록 없음 | verify 전체 재실행 |
| verifier 전 route 투영의 판정 불가 | 실행·새 결과 없음 | 사람 정합화 뒤 verify 전체 재실행 |
| 완성된 결과 쓰기 중 | 기존 partial Record | verify의 현행 완성본 복구 뒤 결과 commit |
| 결과 commit 뒤 route 전 | `신호 카드`·root·재관측·`라우팅: 대기` 영속 | resume의 기존 행이 verify로 보내고 같은 source를 route |
| `라우팅 준비` 뒤 | 기존 prepared 객체 | principles 14번 접두 복구 |
| 카드 생성 뒤 계획 commit 전 | 기존 층 열기 마커와 prepared prefix | split의 기존 복구 |
| 카드 계획 commit 뒤 work 전 | 승인된 카드와 정확한 `읽을 것` | 기존 split→work 경로 |
| 카드 완료 뒤 능력 폐쇄 전 | `.done.` 카드와 진행 로그 | 다음 verify가 같은 signal label을 구성 |

resume은 `수리 계보`나 `재관측`을 해석할 필요가 없다. 활성 `라우팅: 대기`를 verify로 보내는
기존 유계 투영이면 충분하므로 diff 0이다.

## 7. 기존 경계와의 대조

### 7.1 DD-24·DD-30·DD-41

- 최초 `fail`의 재현 절차와 `미검증` 구분, 수정 카드 route, 완료 신호 출처를 바꾸지 않는다.

### 7.2 DD-48·DD-56·DR-31

- reviewer와 verifier는 과거 카드나 진행 로그를 받지 않는다.
- 구현자만 새 카드의 정확한 `읽을 것`을 통해 직전 수리 라운드를 읽는다.
- 상속 집합은 현재 signal과 직전 route 값에서 기계적으로 나오며, “관련 기록”이나 최근 N개가
  아니다.
- 계보 전체가 아니라 직전 수리 라운드만 읽으므로 비용은 열린 수리 묶음에 비례한다.

### 7.3 DR-08·DR-09

- root는 기존 verify key·source id·route 카드 번호만 쓴다. UUID·증상 fingerprint·typed
  evidence graph가 없다.
- work에 별도 root-cause 단계·가설 문서를 만들지 않는다. split은 기존 카드 필드에 확인된
  결과만 전달하고 구현 방법은 열어 둔다.

### 7.4 DD-22·DD-23 회고

구속 전 재검토는 현재 결정 묶음의 후보 하나를 비교하는 메인의 내부 판단이다. 능력·제품 폐쇄
뒤의 retrospector, strain evidence, 회고 기록을 호출하거나 대신하지 않는다.

### 7.5 문서 계층과 glossary

2b 답은 카드 필드에 착지하고, 새 용어만 발견→갱신 표의 정확한 glossary 행을 밟는다. 대상
소유 스킬 고정은 문서 전체 재실행의 소유를 뜻하고, 표가 지정한 한 줄 갱신은 그 절차를 걷는
현재 스킬이 수행한다고 principles에 한 줄로 단일화한다. glossary 변경이 Design head를 바꾸는
기존 비용은 숨기지 않으며 다음 resume이 기존 신선도 규칙으로 처리한다.

### 9.4 독립 감사와 추가 타당성 검사

구현 감사의 렌즈는 감사 지침의 넷뿐이다.

| 렌즈 | 이 라운드의 사냥감 |
|---|---|
| 반증자 | 정본 충돌·판단어·죽은 참조·기각 계보 재제안·clean role 오염 |
| 문자 실행 워커 | P1~P8(특히 P2a~P2g)·A5·B4·S4~S6·L1~L22의 실제 대사와 중단 복구 |
| 기록 소실 감리 | 조사 결론·사용자 결정·신호 카드·root·직전 route·카드 필드·baseline까지 producer→consumer→cleanup |
| 뺄셈 감사 | 새 배포 문장마다 삭제 시 다시 열리는 정확한 실패 경로. 짝이 없으면 삭제 |

네 렌즈가 끝난 뒤 **별도 타당성 검사**를 한 번 더 수행한다. 앞 렌즈의 소견 수를 늘리는 것이
목적이 아니며 0건은 유효하다. 다음 질문만 다시 묻는다.

1. 같은 문제를 더 적은 필드·더 짧은 읽기·기존 정본만으로 해결할 수 있는가.
2. 선택하지 않은 대안이 실제 L1~L22 중 하나에서 권장안보다 더 좋은 결과를 내는가.
3. 권장안의 이점이 새 상태·프롬프트·사용자 왕복 비용보다 큰가.
4. 문제를 해결하지 않는 설명이나 예방적 하네스가 남았는가.
5. 설계가 새 증거 없이 D22·partial product·완전 진단 같은 보류 축을 다시 열었는가.

대체안을 채택하려면 원문 근거와 구체적 실패 경로, 정본 호환성, 상태·prompt 비용, L1~L22
비교 결과를 모두 낸다. 더 낫다는 인상만으로 계획을 뒤집지 않는다.

### 9.5 종료 조건

다음이 모두 참이면 텍스트 검증을 멈추고 구현으로 넘긴다.

- 규칙 충돌·소실 경로 0.
- root·신호 카드·재관측·직전 수리 라운드가 모든 수리 좌표에서 저장값만으로 유일함.
- 정상 pass의 추가 사용자 왕복·상태 쓰기 0, 일반 work·reviewer의 추가 행동 0.
- 자동 수리 카드는 재관측 1 뒤 더 생기지 않음.
- 남은 소견은 표현 등급 또는 수렴형 단일화뿐이고, 수리가 해석을 새로 열지 않음.
- 추가 타당성 검사에서 뒤집을 가치가 있는 우월 대안 0.

수리 뒤에는 수정분을 한 번 재감사하고 L6·L9·L10·L14·L18·L20을 다시 걷는다. 그 재감사
소견이 수렴형 수리로 닫히면 종료한다. 같은 문장을 세 번째 고치거나 구체적 오독 두 가지 없이
“혼동될 수 있다”만 남으면 관찰로 강등하고 텍스트 루프를 멈춘다.

| V8 | D22가 이번 목적 달성에 필요한가 | 아님. 기존 마찰 관찰 경계를 앞질러 범위를 넓히므로 제외 |

이 검증 뒤에도 계획 자체는 §9.4의 네 렌즈와 추가 타당성 검사를 받아야 한다. 작성자가 자기
의도를 이미 안다는 한계 때문에 이 절은 독립 감사를 대체하지 않는다.

## 14. 작성 후 검증과 별도 타당성 검사 결과

### 14.1 첫 검증 — 문자 실행·좌표·기록 소실

작성 완료본을 §9.4의 네 렌즈와 다섯 질문으로 다시 걸었다. 이 패스에서 다음 다섯 보강이 필요했고 모두 본문에
반영했다.

| 발견 | 실패 경로 | 반영 |
|---|---|---|
| 기획 명세가 원칙 이름만 남아 구현자가 다시 설계할 여지 | “자동 조사”를 배경 조사로 넓히거나 명시 조사까지 결정 영향 조건으로 막음 | §5 U1에 명시/자동 분기, 차단/후속 술어, 네 미지수의 소유자·첫 행동, 소비자별 발동 지점을 고정 |
| 사용자가 요구한 `무엇·왜·바라는 결과`가 능력 행 외에는 암시적 | 새 세션이 arch의 근거를 product 이유로 중복하거나 반대로 이유를 생략 | product·arch의 기존 거처 조합을 §5 U2·U3에 명시하고 새 반복 양식은 만들지 않음 |
| 2b의 종료는 필드 유일성만 있고 무진전 질문 반복 출구가 없음 | 모호한 답 뒤 같은 질문을 표현만 바꿔 계속 물어 작은 기획이 grilling으로 변함 | 직전 답이 유효 문장을 줄이거나 새 실제 의존을 연 경우만 계속하고, 아니면 추천/기존 조사 카드/2a 중 한 출구를 쓰도록 §5 U5와 S6에 고정 |
| 같은 root의 같은 재관측에 route가 여러 개면 직전 카드 집합이 한 항목 선택에 따라 달라짐 | L8 다음 재발이 형제 수리 카드 일부만 읽음 | §6.3이 최댓값의 모든 완료 route를 합집합·정본 순서로 내도록 고정 |
| route 투영의 세 파일 scope가 결론만 있고 폐쇄성 증명이 없음 | 구현자가 안전을 이유로 프로젝트 전체를 읽거나 정상 교차 능력 root를 놓침 | 능력층·제품층·1홉 의존별로 최초 항목이 세 경로 중 하나에 있음을 §6.3과 fixture에 명시 |

그 뒤 L6·L9·L10·L14·L18·L20·L21·L22를 문자 그대로 다시 걸었다. root 후보 0/1/2+, 같은
재관측의 여러 route 합집합, 현재 pending 항목 제외, `C1+C2+C3`, 구형 pending 전환은 저장된
필드만으로 한 결과가 나왔다. 표 열 수, L1~L22의 연속성, 절 참조, 비용 합계 `186~280`도 다시
계산했다. 새 규칙 충돌·무기명 소실 경로는 남지 않았다.

### 14.2 검증 루프 밖의 별도 타당성 검사

첫 검증의 문장을 더 고치는 관점이 아니라, 문제별로 다른 설계가 더 나은 결과를 내는지 다시
비교했다.

| 문제 | 비교한 대안 | 얻는 것 | 잃는 것·반례 | 최종 판정 |
|---|---|---|---|---|
| 능동 조사 | 별도 research 스킬 또는 모든 결정 전 조사 | 방법론을 크게 담기 쉬움 | 호출 절차·간접 load·작은 프로젝트 고정비, 사용자의 자연 발동 요구와 충돌 | companion+단계 trigger+답만 필요한 근거의 격리 조사 유지 |
| 더 나은 안 탐색 | 답마다 재검토 / 단계 끝에서만 재검토 | 전자는 교정 기회 최대, 후자는 가장 가벼움 | 전자는 왕복·재귀, 후자는 앞 선택이 뒤 프런티어를 오염 | 결정 묶음당 1회·무후보 무출력 유지 |
| 기획 중단 복구 | planning-frontier 상태 영속 | 질문 위치와 답을 더 정확히 복원 | 새 상태·commit·resume 고정비, 메시지→첫 쓰기 구간도 완전 제거 못함 | D13-A 대화 요약 유지, 실측 비용이 클 때만 재개방 |
| 재발 식별 | 의미 fingerprint / 전체 history 모델 읽기 | 이름이 달라도 비슷한 증상을 묶음 | 원인 동일성을 추측하고 역사 비례 비용, DR-08·DD-56과 충돌 | 저장된 카드 번호 route의 정확 일치 유지 |
| `신호 카드` 필드 | route 뒤 label을 역산하거나 결과+route 원자화 | 영구 필드 1개 절약 | 결과 commit 뒤 승인·split 전 중단 L14에서 label 복원 불가 | 필드 유지 |
| 투영 시점 | non-pass 뒤에만 route 투영 | 정상 pass의 기계 읽기 1회 절약 | 계보 이상을 verifier 실행·결과 생성 뒤 발견하고 stale 동시성 판정도 늦음 | verifier 전 투영 유지, 실제 비용 측정 |
| 투영 범위 | 프로젝트의 모든 verify.md | scope 누락 우려 최소 | 영구 역사·프로젝트 크기 비례 읽기. §6.3의 폐쇄성 증명상 추가 정확도 없음 | 세 경로 유계 scope 유지 |
| 사람 관문과 무관 실패 | 재관측 2+ root를 미루고 G부터 route / root별 defer 상태 | 독립 실패 G가 먼저 진행 | 기존 전역 우선순위 변경 또는 새 상태·resume·cleanup 필요, 사람 관문을 뒤로 굶길 수 있음 | 기존 순서 유지, L21의 지연을 명시 |
| 수리 지식 전달 | work에 진단 의식 추가 / repair episode 신설 | 더 많은 추론·전체 계보 기록 | 정상 `.done.` 참조 오발동 또는 새 상태·역할·승인 체계 | split이 기존 카드 필드에 직전 증거만 전달 |
| 폐쇄 지식 | verify 전용 함정 승격 규칙 | 수리 지식을 눈에 띄게 강제 | 기준선 전면 갱신의 선택 정본 중복, 모든 수리를 함정으로 과승격 | 기존 baseline 갱신 forward-test 유지 |

뒤집을 가치가 있는 우월 대안은 없었다. 특히 정상 pass의 projection 비용과 L21의 전역 지연은
실재하는 비용이지만, 각각 결과 뒤 계보 이상과 새 병렬 상태라는 더 큰 실패 경로를 피하기 위한
의식적 선택이다. 이를 장점으로 포장하지 않고 §10에서 실측한다.

### 14.3 최종 재감사와 한계

14.1의 다섯 보강 자체를 다시 읽었다. 새 조사 표는 companion의 기존 네 분류를 구체화할 뿐 새
출처 서열을 만들지 않고, 의미 밀도 문장은 기존 product·arch 거처를 가리킬 뿐 필드를 늘리지
않으며, 2b 무진전 출구는 대화 안의 반복만 막고, route 합집합·scope 증명은 새 상태를 만들지
않는다. 삭제하면 각각 14.1의 실패 경로가 다시 열리므로 예방적 장식도 아니다.

추가 원문 대조에서도 P3-1~P3-5는 모두 배포 원문과 일치했다. 답만 필요한 근거 탐색은 새
스킬·역할·파일 없이 U1의 조사자 하나로 격리했다. 비카드 route가 끼면 “직전 수리 라운드”가 두 방식으로 읽히던
경계는 재관측 수에는 포함하되 완료 수정 카드 route의 최근 라운드에서는 건너뛰도록 §6.1·§6.3·
L20을 단일화했다. D22 제외와 work diff 0은 각각 기존 관찰 경계와 일반 `.done.` 참조 오발동을
보존하는 판단이므로 유지했다. 그 밖의 비용 관찰은 새 판단어나 중복 규칙을 정당화하지 못해
구현 계약으로 승격하지 않았다.

따라서 이 계획은 **설계 판단 미결 0, 구현 착수 가능**으로 판정한다. 다만 실제 한국어·영문 배포
문장과 fixture는 아직 만들어지지 않았으므로 구현 통과를 주장하지 않는다. 작성자의 자체 검증은
구현 뒤 서로 다른 컨텍스트에서 수행할 §9.4의 독립 감사를 대체하지 않는다. 그 감사가 구체적
반례를 내면 새 주제를 여는 대신 이 계획의 해당 계약 안에서 수리하고 수정분만 재감사한다.

### 14.4 격리 조사 보강 뒤 재검증

소유자의 실전 관찰인 “짧은 출처 확인과 내부 탐색도 반복되면 메인 컨텍스트를 크게 쓴다”를
U1에 대입했다. 길이와 외부 여부를 trigger로 삼던 문안은 짧은 다중 파일 탐색을 메인에 남기고,
반대로 구조 이해가 필요한 긴 원자료를 조사자 요약에 맡길 수 있어 양쪽 목적을 모두 놓쳤다.
trigger를 원자료 이해 소유와 탐색 모양으로 교체하고 다음 경로를 문자 실행했다.

| 입력 | 유일한 경로 | 유실·비용 판정 |
|---|---|---|
| 이미 아는 파일·심볼·URL 또는 출력 상한을 건 조회 한 번 | 메인 직접 확인 | 조사자 호출 고정비 0 |
| 답만 필요하지만 새 내부 경로를 따라가거나 여러 파일을 대조 | 읽기 전용 조사자 한 명 | 메인은 결론·근거 좌표·적용 경계만 받아 탐색 부산물 0 |
| 같은 결정에 짧은 내부·외부 확인이 2개 이상 | 한 유계 브리프로 묶어 조사자 한 명 | 질문별·출처별 중복 조사자 0 |
| `adopt` 대표 흐름 또는 `arch` 구조 선택 | 메인이 원자료를 직접 이해, 유계 하위 질문만 격리 | 조사자 요약에 의한 구조 이해 유실 0 |
| 실행으로만 닫히는 사실 | 메인의 허용된 안전 실행 또는 기존 검증 창구 | 읽기 조사와 실행 증거의 권위 혼합 0 |
| prototype·코드 변경이 필요한 조사 | 기존 조사 카드와 work | 경량 조사자의 무기명 변경 0 |
| 소유자 결정·구속 결정 | 조사자는 근거만, 소유자와 메인이 결정 | 권한 위임 0 |
| 격리 실행 미지원 | 같은 범위를 메인이 직접 조사 | 플랫폼별 결론 차이 0 |

반증 패스에서는 “같은 탐색 범위”가 새 판단어가 되는 경로를 찾았다. 이를 현재 결정 하나와 한
브리프에 열거 가능한 저장소 경로·외부 도메인·버전의 교집합으로 닫았다. “조사가 길다”와 “탐색
부산물이 많다”는 trigger에서는 제거하고 새 경로 추적·둘 이상 대조·독립 확인 2개 이상의 관측
조건으로 바꿨다. 원자료 이해와 답만 필요한지가 갈리는 경우 메인 소유로 수렴하므로 이해도 저하가
조용히 통과하지 않는다.

기록 소실 관점에서는 조사 반환의 결론·정확한 근거 좌표·적용 경계·충돌이 기존 U1 영속화 규칙의
`결론 + 현재 결정에 미친 영향 + 정확한 출처`로 이어진다. 원시 transcript를 버려도 구속 근거는
남고, 메인이 결정적 좌표를 확인하므로 요약만 신뢰하지 않는다. 뺄셈 관점에서는 구조 이해의 메인
소유를 빼면 `adopt` 역산이 조사자 요약에 종속되고, 직접/격리 기계 분기를 빼면 짧은 반복 탐색의
컨텍스트 비용이 다시 열리므로 둘 다 하중을 받는다.

이 보강은 새 사용자 명령·등록 스킬·역할·상태·파일층을 만들지 않고 DD-67의 조사 trigger만
정밀화한다. product·arch·adopt·split의 소유권과 코드 실행·변경 경로도 바꾸지 않는다. 새 규칙
충돌·소실 경로는 0건이며, 남은 성능 주장은 실제 발동 수·반환 문자 수·전면 재탐색 수로 §10에서
측정한다. 작성자의 자체 재검증이므로 구현 뒤 §9.4의 서로 다른 컨텍스트 감사를 대신하지 않는다.
