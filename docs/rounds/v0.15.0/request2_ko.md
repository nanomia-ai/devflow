## 0. 이 라운드가 도달하려는 곳

### 0.1 한 문장 요청

**기획 증거 규율·split 2b·L-B 수리 계보라는 첫 계획의 강점은 보존하되, 중간 정리를
`D13-A의 작은 예외`로 숨기지 말고 대화 요약과 영속 상태를 분리하며, 소유자가 명시하지 않은
결정을 무이의 진행으로 확정하지 않고, 사용자 선택 뒤에는 더 나은 실질 대안이 있는지 한 번
능동적으로 재검토하며, 최초 검증 실패의 기존 재현·`unverified`·수정 카드 계약을 중복 구조
없이 보존하는 두 번째 계획을 만든다.**

### 0.2 왜 맷 포콕의 스킬을 참고했는가

이 라운드의 출발점은 맷 포콕의 스킬 체계를 통째로 이식하는 것이 아니다. 다음 다섯 장점을
devflow의 기존 진입점과 문서 계층 안에서 필요한 순간에만 차용하는 것이다.

- `grilling`은 결정 트리의 현재 프런티어를 질문하고 각 질문에 권장 답을 붙이되, 사실 조사는
  AI가 하고 가치 선택은 사용자가 하게 한다.
- `domain-modeling`은 용어·시나리오·코드 사이의 모순을 공격하고, 실제 trade-off가 있는
  되돌리기 어려운 결정만 ADR 후보로 좁힌다.
- `prototype`은 UI 선택이 아직 열려 있을 때 서로 충분히 다른 후보를 실제로 비교하게 한다.
- `diagnosing-bugs`는 가설보다 먼저 빠르고 재실행 가능하며 실패를 드러내는 신호를 요구한다.
- `code-review`는 독립된 두 검토 축을 두지만, 그 자체가 실패 이력을 다음 수리로 넘기는
  영속 루프 계약은 아니다.

참고 원문은 다음 고정 revision으로 추적한다.

- [grilling](https://github.com/mattpocock/skills/blob/8b78b531ab965735c5dc74f6f7a219e1e37326df/skills/productivity/grilling/SKILL.md#L5-L17)
- [domain-modeling](https://github.com/mattpocock/skills/blob/8b78b531ab965735c5dc74f6f7a219e1e37326df/skills/engineering/domain-modeling/SKILL.md#L37-L66)
- [prototype](https://github.com/mattpocock/skills/blob/8b78b531ab965735c5dc74f6f7a219e1e37326df/skills/engineering/prototype/SKILL.md#L7-L20)
- [diagnosing-bugs](https://github.com/mattpocock/skills/blob/8b78b531ab965735c5dc74f6f7a219e1e37326df/skills/engineering/diagnosing-bugs/SKILL.md#L15-L54)
- [code-review](https://github.com/mattpocock/skills/blob/8b78b531ab965735c5dc74f6f7a219e1e37326df/skills/engineering/code-review/SKILL.md#L4-L9)

중요한 경계가 있다. 위 원문에는 **모든 사용자 선택 뒤에 항상 더 나은 안을 찾는 일반 규칙**은
없다. 이번 요청의 능동 재검토는 프런티어·권장 답·대조 후보·실행 신호에서 얻은 힌트를
devflow에 맞게 유계화하는 자체 설계다. 맷 포콕의 기존 계약이라고 잘못 인용하지 않는다.

### 0.3 권장 작동 장면

1. 새 프로젝트는 지금처럼 product → arch → 선택적 design → split로 들어간다. 기존
   사용자 명령이나 별도 research 단계를 하나 더 외울 필요가 없다.
2. 기존 프로젝트는 지금처럼 adopt로 들어간다. 조사나 대안 탐색은 현재 결정을 실제로
   바꿀 수 있을 때 기존 단계 안에서 자연스럽게 발동한다.
3. product·arch·adopt의 결정 묶음과 split의 작은 기획이 닫히기 직전, AI는 현재 선택보다
   실질적으로 나은 대안이 있는지 한 번 재검토한다. §6.2의 네 조건을 통과한 대안이 없으면
   아무 말도 더 하지 않고, 있으면 하나만 비교·권장한 뒤 최종 선택은 사용자에게 돌린다.
4. 최초 기획이 아무리 잘 되어도 페이지·목록·모달 같은 하위 덩어리에서 카드의 목적지·왜·
   금지·완료 신호가 아직 하나로 정해지지 않으면 split 2b가 필요한 만큼만 더 묻는다.
5. verifier의 최초 non-pass가 재현 절차를 가진 `fail`인지, 실행 결과를 얻지 못한
   `unverified`인지 구분하고 현재 수정 카드 라우팅과 DD-24를 보존한다. 더 나은 최초 신호
   처리를 제안하려면 새 카드 종류나 라우팅 문법을 만들지 않고 같은 경계 안에서 호환성을
   증명한다.
6. reviewer·verifier의 독립성, 현재 역할 분리, 기존 파일 구조와 진입점은 그대로 보존한다.

### 0.4 우선순위와 비목표

우선순위는 **기획 판단의 질 → 하위 덩어리의 가벼운 기획 → 수리 수렴 → 선택한 경우에만
D13 영속 복구**다. D13이 이 라운드 전체를 대표하게 만들지 않는다.

다음은 비목표다.

- 새로 직접 호출해야 하는 사용자 스킬·새 역할·상시 보이는 절차를 추가하지 않는다.
- 모든 답마다 여러 후보를 만들거나, AI가 “최적임”을 증명하게 하지 않는다.
- 더 나은 대안이 없다는 보고를 매번 출력하지 않는다.
- 대안 탐색만을 위해 외부 조사를 자동 실행하지 않는다. 이미 정한 결정 영향 trigger가 참일
  때만 조사한다.
- 질문·카드마다 회고를 실행하지 않는다. 기존 능력/제품 회고의 위치와 역할은 보존한다.

### 0.5 후속 계획 작성자의 판단 범위

이 요청서는 그대로 베껴 구현할 명령문이 아니라, 현재까지 가장 타당한 **후보 기준선**이다.
후속 계획 작성자는 기존 축마다 정본·실패 경로·비용을 다시 대조하고 더 나은 안이 있는지
검토한다. 다만 그 판단은 다음 경계 안에서 수렴해야 한다.

- 대체안은 이 문서가 이미 연 축과 같은 문제를 더 정확하거나 더 작게 해결할 때만 제시한다.
  기존안과 대체안의 실패 경로·정본 호환성·프롬프트 및 상태 비용을 나란히 보인다.
- 더 나은 대안이 0개라는 판정은 유효하다. 이 문서가 이미 요구하거나 비교한 범위 밖의 새
  주제·새 스킬·새 역할·새 상태·새 라우팅 문법을 탐색 성과처럼 추가하지 않는다.
- 새 구조가 정말 필요하면 본안에 조용히 섞지 않고, 기존 기준선에서 제외된 **별도 소유자
  선택**으로 보고한다.
- 결론은 독립 질문을 계속 늘리지 말고, 구현할 수 있는 권장 조합 하나와 반드시 남는 소유자
  선택만 제시한다.

## 1. 이 요청서가 필요한 이유

첫 계획은 요청서의 대부분을 정확히 소화했다. 특히 다음 판단은 유지할 가치가 있다.

1. `research` 사용자 스킬을 새로 만들지 않고 planning-evidence companion을 네 planning
   소비자가 필요할 때 읽는다.
2. 현재 검토·검증 루프가 이미 실패 이력·수정 카드·완료 신호·회귀를 남긴다는 사실을
   인정한다.
3. reviewer·verifier의 무상태성은 결함이 아니라 독립성 자산으로 보존한다.
4. 검증 수렴의 실제 공백을 “기록 없음”이 아니라 “완료된 수리의 신호가 다시 non-pass일 때
   같은 수리 계보로 소비하는 규칙 없음”으로 좁힌다.
5. 페이지·모달·목록처럼 Layer 0를 바꾸지 않는 덩어리는 split 안에서 필요한 만큼만 더
   기획하고, Layer 0가 열리면 즉시 상위 단계로 돌린다.
6. L-B의 계보가 모든 중단 지점에서 기계적으로 복원되지 않으면 축소판을 출고하지 않고
   L-A로 강등한다.

그러나 첫 계획에는 구현 전에 분리·보완하거나 잘못된 가정을 철회해야 할 네 종류의 문제가
남았다.

- **승인 경계:** 권장과 열림 일부가 “진행 위임 뒤 이의가 없었다”는 이유로 확정으로 바뀌었다.
- **구조 분류:** 미완 product.md를 디스크에 두고 다음 단계를 막는 마커가 새 영속 상태인데도
  현재 commit 경계를 유지하는 D13-A의 국소 예외로 분류됐다.
- **기획 능동성:** 조사와 질문 의존은 설계했지만, 사용자가 고른 안을 현재 성공 판정과
  제약에 다시 대조해 더 나은 실질 대안 하나를 제안하는 일반 경계가 없다.
- **최초 수리 신호의 중복 설계:** 넓은 최초 실패를 조사 카드로 보내자는 안은 현재 verifier의
  재현 절차, `unverified`, verify의 수정 카드 라우팅과 DD-24를 충분히 대조하지 않아 정의되지
  않은 라우팅 문법을 추가한다.

앞의 둘을 그대로 두면 기존 체계를 바꾸는 권한과 비용이 잘못 표시된다. 뒤의 둘을 그대로
두면 계획이 사용자의 답을 기계적으로 받아 적거나, 이미 있는 최초 신호 계약 위에 새 카드
흐름을 중복해 라우팅과 복구를 오히려 모호하게 만든다.

## 2. 권위와 변경 규칙

### 2.1 문서 사이의 관계

1. 현재 배포 원문과 현재 유효한 DD/DR이 시스템 사실의 정본이다.
2. `request_ko.md`는 최초 요청의 설계·선택지·예측을 보존한다.
3. `handoff_ko.md`는 소유자의 **명시 결정 기록**과 감사 수리 사양을 제공한다.
4. `request2_ko.md`는 첫 계획을 다시 만들 때의 추가 요구다. 첫 요청의 사실을 조용히
   바꾸지 않고, 첫 계획에서 드러난 문제와 이후 사용자가 보강한 방향을 다룬다.
5. 후속 계획은 위 입력을 파일별 구현 계획으로 번역하되 구현 승인을 대신하지 않는다.
6. **후속 계획의 결정 지위**를 판정할 때는 이 문서 §3의 원장이 handoff·첫 계획의 상충하는
   표기보다 우선한다. 이는 과거 발화를 지우는 규칙이 아니라, 그 기록을 이번 계획에서
   `확정 / 권장·확인 대기 / 필수 파생 변경·확인 대기` 중 무엇으로 쓸지 정하는 범위 규칙이다.
7. §3이 다루지 않은 시스템 사실은 현재 배포 원문과 DD/DR을, §3이 다루지 않은 소유자 결정은
   handoff의 명시 기록을 따른다. 어느 쪽인지 가를 수 없으면 추측하지 않고 소유자에게 묻는다.

### 2.2 확정의 기준

- 사용자의 명시 선택 또는 사용자가 확인한 문서의 `확정` 행만 확정이다.
- “결이 갈리면 묻고 아니면 진행”은 분석·계획 작성을 계속할 권한이다. 열려 있던 구조
  선택을 확정으로 바꾸는 일반 위임으로 쓰지 않는다.
- 사용자가 상세 설계를 듣고 이의 없이 다음 형식을 지시했다는 사실은 검토를 계속해도 된다는
  증거이지, 상세 설계의 모든 필드를 승인했다는 증거가 아니다.
- 한 선택이 논리적으로 다른 부품을 필요로 해도, 그 부품이 기존 계약을 바꾸면
  `필수 파생 변경`으로 제시하고 소유자의 확인을 받는다. “유일한 후보”라는 판단은 승인과
  같은 말이 아니다.

### 2.3 기존 체계 위에 더하는 규칙

다음 계획은 각 변화에 `보존 추가 / 국소 계약 변경 / 구조 변경 / 기존 결정 반전` 중 하나를
붙인다. `구조 변경`에는 새 파일뿐 아니라 다음도 들어간다.

- 디스크에 남아 다음 세션의 단계를 바꾸는 새 표지.
- producer·consumer·cleanup을 가진 새 필드나 문법.
- 기존 파일의 존재가 뜻하던 상태를 둘 이상으로 가르는 변화.
- resume·직접 스킬 호출의 우선순위를 바꾸는 변화.

새 파일이 없다는 이유만으로 구조 변경을 국소 문구 변경으로 낮추지 않는다.

## 3. 결정 원장 재구성

다음 계획은 결정을 네 묶음으로 나눈다.

### 3.1 handoff에 명시 선택으로 기록된 묶음

## 4. 첫 계획에서 그대로 보존할 설계

### 4.1 기획 증거 규율

- 별도 사용자 research 스킬을 만들지 않는다.
- `skills/principles/planning-evidence_ko.md`와 영문 쌍을 canonical companion으로 둔다.
- 소비자는 product·arch·adopt·split 네 곳으로 유계한다.
- 현재 저장소 사실·외부 계약 사실·실행 사실·소유자 결정의 네 분류를 유지한다.
- 차단/후속, 출처 소유권, settled/conflicted/unavailable 정지 상태를 유지한다.
- 결론+영향+출처만 현재 소유 문장에 남기고 원시 조사 파일은 기본 생성하지 않는다.
- 명시 조사의 자연 발동과 자동 조사의 결정 영향 trigger를 분리한다.

### 4.2 product·arch·adopt

- product의 여섯 판단·목차·제거 질문·Layer 0 소유권을 유지한다.
- arch의 구성요소→stack→코드 구조→데이터→검증 창구 소유권을 유지한다.
- adopt의 현재 구현·외부 계약·소유자 의도 분리를 유지한다.
- 조사 결과가 하위 단계에서 product의 문제·능력·경계·성공 판정을 조용히 바꾸지 못한다.
- arch의 후보 생존 사실 확인, 차단 사실/잠정값 구분, 검증 창구 실행 가능성 확인을 유지한다.
- adopt의 versioned external research와 관찰/해석/결정 preview를 유지한다.

### 4.3 split 0/1/2a/2b

- 0: 정확한 기존 출처에서 카드 네 필드가 유일하면 질문 0.
- 1: 한 묶음으로 카드 네 필드가 유일해지면 한 묶음 뒤 종료.
- 2a: 실제 제시할 선택지 또는 실제 답이 Layer 0 필드를 바꾸면 카드 없이 상위 단계 환류.
- 2b: Layer 0는 보존되지만 한 묶음 뒤에도 카드 필드가 비유일하면 같은 유지보수 대화에서
  다음 프런티어 묶음을 계속한다.
- 2a와 2b가 함께 참이면 2a가 이긴다.
- 2b의 착지는 카드 필드, ADR 3조건을 통과한 ADR, 확정 용어의 glossary뿐이다.
- 능력 설계 구역·새 기획 파일·새 상태를 만들지 않는다.
- “페이지·모달·목록”은 trigger가 아니라 예시다. 판정은 위 필드 조건으로만 한다.

### 4.4 L-B 수리 계보

- reviewer contract는 diff 0이다.
- verifier는 과거 카드·verify.md·진행 로그를 받지 않는다.
- 현재 회귀 신호의 완료 카드 번호 label만 verifier 입력·반환에 붙인다.
- 메인이 기존 verify.md와 카드 번호를 연결하며 역할이 이력을 해석하지 않는다.
- route 투영은 현재 대상 key·트리 루트·현재 회귀 묶음 label 카드가 속한 능력들의
  verify.md로 유계한다.
- 첫 재관측은 접근 해소/clean diagnosis/조사 중 정확히 하나만 통상 승인 경로로 제안한다.
- 같은 계보의 두 번째 이후 non-pass는 `라우팅: 대기`를 유지하고 사람을 부른다.
- 정상 pass·일반 work·reviewer에는 추가 실행·질문·상태 commit이 없다.
- 계보가 유일 복원되지 않으면 의미로 고르지 않고 L-A로 강등한다.
- 자동 사건 key·revision 판정이 바뀌지 않으면 verification-predicates는 고치지 않는다.
- resume 변경은 기존 유계 투영과 `라우팅: 대기` 복구만으로 부족하다고 문자 실행 워커의
  걷기가 증명할 때만 조건부로 넣는다.

### 4.5 기획 산출의 의미 밀도

- 사용자가 원한 것은 다음 세션이 결정의 `무엇`만 보지 않고 `왜`와 `바라는 결과`까지 읽는
  것이다.
- 모든 문장에 네 필드를 반복하지 않는다. 제품 전체·능력 하나·비자명한 경계·어려운
  아키텍처 결정이 각각 기존 소유 절에서 의미 삼각형을 한 번만 완성하는 D5 방향을 보존한다.
- 빈 `왜`를 AI가 지어내지 않는다. 근거가 없으면 질문 또는 조사 trigger로 보내고 확정
  이유처럼 착지시키지 않는다.
- 후속 계획은 능력 한 줄만 보강하고 끝내지 말고, product·arch의 각 기존 거처가 무엇·왜·
  결과 중 어느 변을 소유하는지 원 요청 §6.5와 대조한다.
- 같은 목적을 여러 파일에 복제하지 않고, 하위 문서는 상위 의미를 다시 서술하는 대신 필요한
  정확한 출처를 가리킨다.

## 5. D13을 다시 가르는 방법

“중간 정리”는 서로 다른 두 요구를 한 이름으로 부를 수 있다. 다음 계획은 먼저 어느 요구인지
가른다.

| 요구 | 보장 | 디스크 변화 |
|---|---|---|
| 대화 중 정리 | 긴 인터뷰 중 지금까지 확정된 것과 남은 질문을 사용자에게 한 번 보여 줌 | 없음. 세션이 끝나면 A의 재질문·재조사 비용을 그대로 수용 |
| 세션 간 복구 | 다음 세션이 확정된 판단과 남은 질문에서 이어감 | 있음. 영속 상태·라우팅·cleanup 계약 필요 |

### 5.1 D13-A — 현재 commit 경계 + 대화 중 정리

이 안은 원 요청의 A를 그대로 지킨다.

- 목표 라운드 예산을 소진하고도 계속할 때 확정 내용과 남은 질문을 대화로 한 번 요약한다.
- `product.md`·`glossary.md`는 여섯 판단과 종료 게이트를 통과한 최종 확인 전에는 내구
  상태로 쓰거나 commit하지 않는다. 대화 안의 확인 초안은 이 금지에 들지 않는다.
- 세션이 끊기면 마지막 확정 Layer 0에서 다시 도출·재조사·재질문한다.
- resume·arch·split·principles·상태 predicate는 바꾸지 않는다.
- 사는 것: 가장 작은 변경, 기존 Layer 0 의미 완전 보존.
- 못 사는 것: 중간 요약 뒤 세션이 끊기면 요약의 디스크 복구.

**최소 변경이 우선이면 이 안이 가장 작다.** 다만 handoff의 D13 기록은 “중간 착지해
핸드오프 개념으로 남김”까지 말하므로, 소유자가 그 영속 의도를 유지한다면 A만으로 요구를
충족했다고 판정하지 않는다.

### 5.2 D13-C — 초기 product의 부분 확인 상태

세션 간 복구가 실제 요구라면 첫 계획의 `[막음:]` 안을 A의 예외라고 부르지 않고 D13-C라는
구조 변경 후보로 다룬다. 후속 계획은 다음 계약을 모두 채우기 전 C를 본안에 넣지 않는다.

#### 범위

- **최초 product 작성에만** 허용할지 명시한다. 경량 권장은 최초 작성으로 한정이다.
- 이미 arch·tree가 있는 product 재실행에는 기본 적용하지 않는다. 그 상태에서 미완 product를
  commit하면 기존 work·split·verify가 불완전 Layer 0를 읽을 수 있으므로 별도 전역 봉쇄가
  필요하다.
- 최초 작성 한정이면 진입 시 `product.md`가 없고 arch·tree도 없는 정확한 조건을 쓴다.

#### 상태 정체성

- partial과 final을 구분하는 정확한 디스크 술어를 하나 정한다.
- `[막음: <판단 이름>]`을 쓴다면 허용 판단 이름은 product의 여섯 판단으로 정확 열거한다.
- 마커 없음·하나 이상·잘못된 판단 이름·해석 불가능 문장·부분 파일의 필수 heading 누락을
  각각 어떻게 판정할지 쓴다.
- 오래된 정상 product.md에는 마커가 없으므로 final로 읽을 수 있어야 한다. 별도 이관을
  요구하는 전역 status 필드는 기본 권장하지 않는다.

#### producer·consumer·cleanup

| 역할 | 필수 행동 |
|---|---|
| product producer | 확정된 판단과 남은 blocker를 한 묶음으로 보여 사용자 확인 뒤 쓴다. 추측한 판단을 채우지 않는다 |
| product continuation | 마커가 있으면 이미 확정된 문장을 다시 묻지 않고 blocker부터 계속한다. 원문이 모순되면 자동 수리하지 않고 보고한다 |
| resume | arch 존재 여부보다 먼저 partial product를 product로 보낸다 |
| arch | partial이면 1~5단계·능력 문서 생성을 시작하지 않고 product를 안내한다 |
| split | `product.md` 존재만으로 통과하지 않는다. partial이면 트리·카드를 만들지 않고 product를 안내한다 |
| final cleanup | 여섯 판단·조사 게이트·사용자 확인을 통과한 같은 commit에서 blocker 마커를 전부 제거한다 |

직접 `design` 호출처럼 arch가 없는 상태를 이미 거부하는 소비자는 기존 거부가 partial에도
충분한지 원문으로 증명한다. “보통 arch를 거친다”는 소비자 누락의 근거가 아니다.

#### commit과 복구

- 부분 확인 commit이 기존 Layer 0 commit인지 새 commit class인지 명시하고, 기존 commit
  discipline과 동시에 지킬 수 있음을 보인다.
- 부분 파일은 능력 문서의 `Design head` 입력이나 트리 생성 입력이 될 수 없다.
- 메시지 수신 뒤 부분 commit 전 중단, 부분 commit 뒤 중단, 최종 확인 뒤 cleanup commit 전
  중단을 각각 걷는다.
- partial 상태를 새 상태로 인정하므로 producer·consumer·cleanup의 정합성 검사를 둔다.
- 규칙 정본까지 늘려야 한다면 모든 스킬의 고정비를 별도 측정하고, 하위 스킬에만 예외를
  선언하지 않는다.

#### 기존 계보 대조

- DR-01의 “중간 인계 문서는 반쪽 진실을 넘긴다”는 이유와 무엇이 다른지 반박한다.
- DD-33의 대화 결정 즉시 착지와 사용자 확인 게이트를 어떻게 보존하는지 쓴다.
- DD-28의 새 문서층 금지는 지키되, 새 문서가 없다는 사실만으로 새 상태가 아니라고 주장하지
  않는다.
- DD-59의 journal 기명 미결과 product의 `열린 질문`은 서로 다른 기존 거처다. `[막음:]`이
  같은 결정을 두 거처에 복제하거나 제3의 “열린 결정” 이름을 만들지 않는지 대조한다.
- design-backlog의 “Layer 0 draft confirmation state” 보류 사유를 읽고, C가 그 선택을
  부분적으로 여는 이유와 구형 markerless 파일의 의미를 기록한다.

### 5.3 D13-B — 예약 planning-frontier 상태

원 요청의 B는 질문 전에 정확한 재개 지점을 남기는 가장 강한 안이다. 초기 Git·journal 상태·
resume 우선순위·상태 소비 비용이 크므로, “확정된 부분만 한 번 복구”가 목적이면 C보다 과하다.
다음 계획은 소유자가 B를 다시 선택하지 않는 한 본안에 넣지 않는다.

### 5.4 권장 조합

1. handoff에 기록된 세션 간 인계 의도를 유지한다면 **C의 완전한 상태 계약을 preview한 뒤
   명시 선택**이 잠정 권장이다. 상태 계약이 과하면 요구를 줄일지 소유자가 고른다.
2. 중간 정리가 대화 품질 목적뿐이라고 소유자가 교정하면 **A + 대화 요약**.
3. 질문 실행 전부터 재개 질문 자체를 보존해야 하면 **B를 별도 구조 선택으로 재검토**.

후속 계획은 A와 C를 섞어 “현재 경계 유지”라고 쓰지 않는다. C를 권장하면 A 대비 추가
파일·읽기·상태·fixture를 정직하게 다시 계산한다.

## 6. 질문 프런티어와 능동 재검토

### 6.1 product 질문 의존은 고정 총순서로 만들지 않는다

첫 계획의 `문제 → 해결 방식 → 능력 구성 → {경계·성공 판정·화면}` 고정 순서는 요청서보다
강한 새 방법 계약이다. 어떤 제품에서는 성공 판정이 해결 방식 후보를 먼저 줄이고, 화면·창구가
능력 경계를 바꾼다. 다음 계획은 여섯 판단의 전역 총순서를 정본으로 추가하지 않는다.

대신 현재 제시할 질문 사이의 의존을 다음 유계 조건으로 판정한다.

> 앞 질문에 실제로 제시할 선택지 중 하나라도 뒤 질문의 필요 여부·선택지·추천 기본값을
> 바꾸면 두 질문은 의존한다. 뒤 질문은 같은 묶음에 넣지 않고 앞 답 뒤에 만든다.

보완 규칙:

- 가능한 모든 답을 상상하지 않고 실제 제시할 선택지만 쓴다.
- 사용자가 제시하지 않은 답을 자유 입력하면 그 실제 답으로 남은 질문을 다시 판정한다.
- 답 뒤 같은 묶음의 질문이 무효화됐음을 발견하면 영향받은 질문만 다음 묶음에서 다시 연다.
- 의존하지 않는 경계·성공 판정·화면 질문은 같은 프런티어에 함께 있을 수 있다.
- 여섯 판단 완성·차단 사실 해소·사용자 확인이라는 종료 게이트는 그대로다.

이 조건은 “선행 판단”이라는 무제한 판단어를 줄이면서도 도메인마다 다른 탐색 순서를 허용한다.
다음 계획이 다른 기계 조건을 제시하려면, 같은 입력에서 질문 묶음이 달라지는 두 독해를 막는
구체적 예를 함께 낸다.

### 6.2 선택 뒤 재검토의 세 안

이 절의 `결정 묶음`은 새 파일·상태·출력 형식이 아니다. product의 현재 질문 프런티어,
arch의 한 구속 결정, adopt의 관찰/해석/결정 preview, split의 한 카드 필드 확정을 통칭한다.
각 단계의 정확한 지점은 §6.3이 정한다.

| 안 | 작동 | 이점 | 비용·위험 | 판정 |
|---|---|---|---|---|
| R-A · 개별 답마다 | 답 하나마다 다른 안을 다시 찾음 | 가장 잦은 교정 | 왕복·조사·프롬프트가 늘고 사용자의 결정을 계속 흔듦 | 기각 권장 |
| R-B · 결정 묶음마다 한 번 | 현재 묶음의 답을 반영한 뒤, 다음 의존 질문을 만들거나 묶음을 닫기 전에 한 번 재검토 | 잘못된 고착을 막으면서 무출력 정상 경로 유지 | 묶음당 내부 판단 1회 | **권장·확인 대기** |
| R-C · 단계 최종 확인 직전만 | product/arch/adopt 또는 작은 기획 전체가 끝날 때 한 번 재검토 | 가장 가벼움 | 앞선 선택이 뒤 질문을 오염시킨 뒤라 재작업이 커질 수 있음 | 차선 |

R-B의 “한 번”은 사용자에게 질문을 하나 더 보낸다는 뜻이 아니다. 현재 사실·성공 판정·경계·
되돌리기 비용·검증 가능성에 선택을 다시 대조하는 내부 판단이다. 다음 조건을 모두 만족하는
대안이 있을 때만 사용자에게 보인다.

1. 현재 증거 또는 §4.1의 기존 조사 trigger가 허용한 증거로 설명할 수 있다.
2. 표현 취향이 아니라 사용자 결과·제품 경계·되돌리기 비용·검증 가능성 중 하나를 실질적으로
   바꾼다.
3. 이미 선택한 안의 이름만 바꾼 것이 아니라 서로 다른 trade-off를 가진다.
4. 현재 단계의 소유권 안에서 비교할 수 있다. Layer 0를 바꾸는 split 대안은 비교를 계속하지
   않고 2a로 환류한다.

조건을 통과한 후보가 없으면 추가 출력·질문·파일 기록은 0이다. 통과하면 **후보 하나만** 현재
안과 짧게 비교하고 권장 이유를 말한 뒤 사용자가 결정한다. 후보가 여럿이면 기록된 성공 판정과
사용자 우선순위가 하나를 가를 때만 제안한다. 그 근거로도 갈리지 않으면 임의의 후보를 “더
낫다”고 고르지 않고 현재 선택을 유지한다. “객관적”이라는 말은 보편 점수표를 뜻하지 않는다.
현재 성공 판정과 확인된 제약에 어느 안이 더 잘 맞는지 추적 가능하게 비교한다는 뜻이다.

### 6.3 단계별 투영

| 단계 | 재검토 지점 | 대안이 실질적인 경우 | 지켜야 할 경계 |
|---|---|---|---|
| product | 결정 묶음의 답을 반영한 뒤, 다음 묶음 생성 또는 최종 확인 전 | 해결 방식·능력 구성·MVP 경계·성공 판정이 사용자 결과를 다르게 만듦 | 사실은 AI가 확인하되 가치 선택은 사용자. 여섯 판단 소유권 유지 |
| arch | 구성요소·후보 사실을 확인한 뒤 되돌리기 어려운 선택을 구속하기 전 | 경계가 비자명하고 실제 trade-off가 있는 counter-design | D9의 조건부 두 설계를 이 규칙의 arch 투영으로 사용. 단순 stack 취향에는 발동하지 않음 |
| adopt | 관찰·해석·미래 결정을 preview한 뒤 확인 전 | 현재 동작 보존과 목표 방향의 개선이 서로 다른 결과를 냄 | 현재 사실을 미래 의도로 승격하지 않고 최종 방향은 사용자에게 돌림 |
| split | 카드 네 필드가 처음 유일해진 시점, 카드 착지 전 | Layer 0 안에서 목적지나 완료 신호를 더 직접 검증할 수 있는 안이 있음 | 일반 아이디어 단계로 확장하지 않음. Layer 0 변화면 2a, 없으면 한 후보 뒤 카드를 닫음 |

design은 이번 라운드의 소비자에 추가하지 않는다. UI 후보가 실제 실행 가능한 비교물까지
필요한지는 design 자신의 후속 라운드에서 판단한다. 맷 포콕의 prototype을 근거로 이 범위를
조용히 넓히지 않는다.

### 6.4 기존 회고와의 경계

이 재검토는 **구속 결정 전의 기획 교정**이다. DD-22·DD-23의 회고는 능력 또는 제품을 실제로
닫은 뒤, 이름 붙은 대안·프로젝트의 긴장 증거·추정 전환 비용이 함께 있을 때 상위 문서 개선을
검토한다. 둘을 합치지 않는다.

- 질문·결정 묶음·카드마다 retrospector를 실행하지 않는다.
- 능동 재검토는 strain evidence나 회고 기록을 새로 만들지 않는다.
- 사용자가 대안을 보고 다시 선택하면 그 묶음은 닫힌다. 선택된 대안을 또 재검토해 재귀하지
  않는다.
- 최종 선택과 그 선택을 가른 이유·바라는 결과는 §4.5의 의미 삼각형 또는 기존 ADR 3조건이
  지정한 현재 거처에 남긴다. 모든 기각 후보를 저장하는 새 로그는 만들지 않는다.
- 이미 닫힌 결정을 다시 여는 조건은 새 사실, 기존 결정과의 모순, 또는 성공 판정을 바꾸는
  결과가 생긴 경우뿐이다. 단순히 다른 후보를 생각해냈다는 이유로 재개하지 않는다.

### 6.5 프롬프트 비례성

후속 계획은 이 축을 새 등록 스킬·새 역할·새 상태·새 사용자 호출로 만들지 않는다. product·
arch·adopt·split의 기존 판단 지점에 짧게 투영하고, 다음을 비용 관문으로 삼는다.

- 정상 무후보 경로의 추가 사용자 질문·출력·도구 실행·commit은 0.
- 네 소비자의 배포 본문 순증은 합계 12줄 안팎을 **측정 목표**로 삼는다. 모호성을 막는 데
  필요한 문장을 자르도록 강제하는 합격 술어는 아니다. 초과하면 각 초과 문장이 막는 정확한
  실패 경로와 더 짧은 표현이 불충분한 이유를 보인다. 줄을 억지로 합쳐 문자 수를 숨기지 말고
  줄·문자·호출당 고정 읽기량을 함께 보고한다.
- 이 규칙 하나를 위해 새 companion을 만들지 않는다. 네 투영의 의미를 일치시키기 어렵다는
  구체적 실패 경로가 발견되면, 새 정본의 고정 읽기 비용과 함께 별도 구조 선택으로 올린다.
- 대안 수 N개·보편 점수표·“최적 증명”·무후보 보고를 추가하지 않는다.

## 7. L-B를 구현 계획으로 옮길 때의 정밀화

### 7.1 한 용어, 한 경계

- `재관측 1`: 완료된 수정 카드의 현재 완료 신호가 처음 pass를 주지 못한 verify 실행.
- `재관측 2 이상`: 같은 수리 계보에서 이후 verify 실행이 다시 pass를 주지 못함.
- principles·verify·work·verifier·테스트·계획의 모든 문장은 `재관측 2 이상`으로 맞춘다.
- `재관측 2`라고만 써 세 번째 이후를 문법 밖에 두지 않는다.

### 7.2 첫 재관측의 카드 표현

“새 카드가 아니라 첫 재발”과 “진단 강화 카드 하나”를 한 문장에 쓰지 않는다. 정확한 결과는
다음이다.

- verify.md에는 새 출처 id를 가진 재발 항목이 생긴다.
- root와 재관측 수는 기존 수리 계보를 이어받는다.
- 접근 해소·정확 실패·불안정/넓은 신호 중 현재 관측된 갈래에 맞는 **새 승인 카드 하나**를
  통상 라우팅으로 제안한다.
- 새 카드라는 사실과 새 계보라는 사실은 다르다. 카드는 새 것이지만 계보는 기존 것이다.

### 7.3 깨끗한 역할 보존

verifier 변경은 반환 형식뿐이라고 축소하지 않는다. 회귀 신호의 현재 label이 입력에도
들어가고 non-pass 반환에도 나온다. 따라서 구현 감사는 다음을 별도 확인한다.

- label은 현재 신호를 식별할 뿐 과거 실패 설명·원인·수리 횟수를 전달하지 않는다.
- verifier는 label을 판정 근거로 쓰지 않고 실행 결과와 증거를 해당 label에 대응시킨다.
- 메인만 route 투영과 과거 실패 이력을 읽는다.
- reviewer 입력·반환·세 번 사람 관문은 diff 0이다.

### 7.4 계보 복원과 비용

- 현재 대상 key·트리 루트·현재 회귀 묶음 label 카드의 능력 verify.md만 읽는다.
- 교차 능력 `의존` 1홉에서 들어온 label도 같은 범위에 포함한다.
- 읽기량은 프로젝트 전체 역사나 전 능력 수가 아니라 현재 회귀 묶음 크기에 비례해야 한다.
- 한 label이 둘 이상의 root에 풀리거나 한 실행이 서로 다른 root label을 함께 내면 의미로
  고르지 않고 `수리 계보 판정 불가`로 사람에게 보낸다.
- literal walk에서 모든 중단 지점의 root·재관측·다음 행동이 유일 복원되지 않으면 L-B 전체를
  L-A로 강등한다.

### 7.5 새 root 후보의 최초 실패 신호 — 현재 계약을 기준선으로 둔다

현재 verifier 계약은 `fail`에 재현 절차를 포함하고, 실행 결과나 접근을 얻지 못하면 원인을
추측하지 않고 `unverified`를 반환한다. verify는 두 결과를 모두 기존 **수정 카드** 라우팅으로
보내며, DD-24는 verifier의 재현 절차를 그 수정 카드의 완료 신호로 사용한다. 따라서 최초
non-pass가 수리 가능한 신호를 남기는 기본 계약은 이미 존재한다.

첫 초안의 F-B는 넓거나 불안정한 최초 신호를 기존 조사 카드로 보낸 뒤, 현재 failure-history의
`라우팅`에 그 조사 카드 번호를 연결하려 했다. 그러나 규칙 정본이 허용하는 정확한 라우팅 결과는
수정 카드·문서 환류·product 재실행이며, verify도 fail/unverified에서 수정 카드를 만든다. 한 번의
라우팅 결과가 조사 뒤 통상 수정 라우팅으로 되돌아오는 두 단계 상태도 정의돼 있지 않다. 조사
카드를 수정 카드처럼 기록하면 카드 종류의 의미가 무너지고, 새 문법을 만들면 이번 라운드의
보존 추가 범위를 넘는다.

| 안 | 작동 | 이점 | 비용·위험 | 판정 |
|---|---|---|---|---|
| F-A · 현재 최초 신호 계약 | verifier 재현 절차 또는 `unverified`를 보존하고 현재 수정 카드 route와 DD-24를 사용. 완료된 수리의 후속 non-pass부터 L-B | 새 상태·문법·정상 경로 비용 0, 현재 정본과 일치 | 집계 수준 신호의 원인 축소는 승인된 수정 카드 안에서 이뤄짐 | **이번 라운드 기준선** |
| F-B · 조사 카드 route | 넓거나 관측상 불안정한 최초 신호를 조사 카드에 연결한 뒤 수정 route로 복귀 | 구현 추측 전 신호 축소 의도 | 현재 정확 라우팅 문법과 불일치하고 두 단계 복귀 상태가 없음 | **현재 설계로 기각** |
| F-C · 모든 실패의 완전 진단 | 모든 non-pass에서 복수 가설·반증 순서를 고정 | 가장 엄격함 | 단순 실패에도 방법 처방과 고정비가 큼 | 기각 |

후속 계획 작성자는 이 축에서 더 나은 대체안을 **최대 하나** 제안할 수 있다. 다음 네 조건을
모두 증명하지 못하면 F-A를 유지한다.

1. 규칙 정본의 정확한 기존 라우팅 결과와 기존 카드 종류·상태만 사용한다.
2. verifier의 재현 절차, `fail`/`unverified` 구분, 깨끗한 역할을 보존한다.
3. 정상 pass의 추가 실행·질문·기록이 0이고 자동 카드 발행이 재귀하지 않는다.
4. 조사나 중단을 포함해도 원래 source와 다음 행동이 세션 간 유일하게 복원된다.

이 조건은 “더 좋은 안을 찾지 말라”는 금지가 아니다. 새 문법을 숨겨 넣지 않은 채 같은 최초
신호 문제를 더 잘 푸는 안만 비교 대상으로 남기는 수렴 경계다.

## 8. 후속 계획의 파일별 표가 추가로 답할 것

첫 계획의 다섯 칸은 유지한다.

`현재 정확한 문장/형식 → 추가 또는 교체 → 막으려는 실패 경로 → 보존 불변식 → 소유자 결정·DD/DR`

여기에 각 행이 다음 질문을 답한다.

1. **승인 지위:** 확정 / 권장·확인 대기 / 필수 파생 변경·확인 대기.
2. **변경 등급:** 보존 추가 / 국소 계약 변경 / 구조 변경 / 기존 결정 반전.
3. **읽기 비용:** 정상 진입 고정비인지, trigger 뒤 조건부 읽기인지.
4. **중단 복구:** 새 디스크 값이 있으면 producer·consumer·cleanup과 중단 지점.
5. **직접 호출:** resume을 거치지 않은 A3 진입에서도 같은 상위 경계를 지키는지.
6. **뺄셈 근거:** 새 문장을 지우면 다시 열리는 정확한 실패 경로.
7. **상태 표지:** 계획 머리말의 감사 전/후·구현 승인 전/후 상태가 실제 완료한 패스와
   어긋나지 않는지.
8. **능동 재검토:** 어느 결정 묶음에서 내부 재검토하고, 후보 없음·후보 있음·사용자 재선택 뒤
   각각 어떤 추가 출력과 종료가 있는지.
9. **회고 경계:** 구속 결정 전 재검토가 DD-22·DD-23의 능력/제품 종료 뒤 회고를 호출하거나
   대신하지 않는지.
10. **최초 신호:** F-A의 verifier 재현 절차·`unverified` 구분·현재 수정 카드 route·DD-24가
    보존되는지. 대체안을 제안하면 §7.5의 네 조건과 정확한 복구 경로를 충족하는지.
11. **프롬프트 비용:** 새 스킬·역할·상태 없이 어느 기존 판단 지점에 몇 줄·몇 문자가 늘며,
    후보 없음과 정상 pass 경로의 추가 실행이 0인지.

D13-A를 고르면 partial 관련 행·마커·테스트는 파일 표에서 모두 빠져야 한다. D13-C를 고르면
product와 arch만 적고 끝내지 말고 §5.2의 소비자·정합성 검사 전부를 행으로 배선한다.

## 9. 고정 시나리오 추가·교체

첫 요청의 P/A/B/S/E/R/L 시나리오, 첫 계획의 S4, handoff의 L11은 유지하되 선택한 D13에 맞춰
R 시나리오를 다시 쓴다.

### 9.1 승인 출처

**Q1 · 권장안의 무이의 확정 금지**

- 입력: D1~D3·D5·D7~D9·D11이 권장이고 사용자는 “결이 갈리면 묻고 아니면 계획을 계속”이라고
  말함.
- 기대: 후속 계획은 권장 조합으로 제안하지만 확정이라고 쓰지 않는다.
- 실패: handoff나 후속 계획에 “무이의 진행이므로 확정”을 새로 적음.

### 9.2 product 질문 의존

**P5 · 성공 판정이 해결 방식을 가르는 경우**

- 입력: 문제는 확정됐지만 “오프라인에서도 성공해야 하는가”의 답이 해결 방식 후보를 바꿈.
- 기대: 고정 총순서 때문에 해결 방식을 먼저 닫지 않고, 실제 선택지가 뒤 질문을 바꾸는지로
  둘을 다른 프런티어에 둔다.

**P6 · 독립 질문은 함께 묶임**

- 입력: 능력 구성은 확정됐고 경계 질문과 화면 진입 질문의 실제 선택지가 서로를 바꾸지 않음.
- 기대: 둘을 같은 묶음에 둘 수 있다. 의존 검사가 모든 질문을 단건으로 만들지 않는다.

### 9.3 능동 재검토

**P7 · 사용자 선택보다 강한 제품 대안이 보임**

- 입력: 사용자는 모바일 앱만을 선택했지만 확인된 성공 판정에는 현장 PC에서의 동시 처리가
  필수이고, 웹 우선안이 같은 MVP 경계에서 그 결과를 더 직접 충족함.
- 기대: 현재 묶음을 확정하기 전에 웹 우선안 하나만 결과·경계·비용으로 비교하고 권장한다.
  사용자가 어느 안을 고르든 선택과 이를 가른 이유를 기존 의미 거처에 남기고, 다시 대안을
  재귀 탐색하지 않은 채 다음 의존 질문으로 간다.
- 실패: 사용자의 첫 답을 이유 없이 그대로 확정, 세 후보 이상 확장, 자동으로 사용자 선택을
  덮어씀.

**P8 · 실질 대안이 없음**

- 입력: 사용자의 경계 선택을 다른 표현으로 바꾼 후보만 있고 결과·비용·검증 가능성은 같음.
- 기대: 내부 재검토 뒤 추가 출력·질문·조사 0으로 다음 질문 또는 확인으로 간다.
- 실패: “더 나은 대안이 없습니다”를 매 묶음 출력하거나 표현 후보를 새 결정처럼 제안.

**A5 · arch의 가역적 취향 선택**

- 입력: 두 라이브러리가 모두 현재 경계와 검증 창구를 만족하고 교체가 국소적이며 확인된
  trade-off가 없음.
- 기대: D9 비교를 발동하지 않고 이미 확인된 기준으로 하나를 권장한다.
- 실패: 능동 재검토를 이유로 모든 stack 선택에 두 설계·점수표를 강제.

**B4 · adopt의 현재 동작과 목표 방향이 갈림**

- 입력: 코드는 수동 승인만 구현하지만 소유자는 점진적 자동화를 원하고, 외부 계약상 두
  경로가 모두 가능함.
- 기대: 관찰을 미래 의도로 둔갑시키지 않고 `현재 보존`과 `점진 자동화` 중 결과가 더 나은
  후보 하나를 비교·권장한 뒤 사용자가 결정한다.

**S5 · 작은 기획이 카드로 닫히는 순간**

- 입력: 목록 필터 카드의 네 필드는 유일해졌지만 현재 완료 신호는 내부 함수 호출만 보고,
  동일 Layer 0 안에서 사용자 화면 결과를 검증하는 신호가 가능함.
- 기대: 화면 결과 신호 하나를 더 직접적인 안으로 제시한 뒤 카드를 닫는다. 새 능력·기획
  파일·상태를 만들지 않는다.

### 9.4 split 2b

**S4 · Layer 0 보존 덩어리**

- 입력: 관리자·성공 판정은 이미 확정된 정산 페이지에서 목록·필터·상세 모달의 카드 필드가
  첫 묶음 뒤에도 비유일함.
- 기대: 2b가 다음 프런티어 묶음을 계속하고, 어느 답도 Layer 0를 열지 않으면 카드 필드로
  닫힌다.
- 실패: 한 묶음 뒤 무조건 product로 환류, 능력 설계 구역이나 새 기획 파일에 착지, 질문이
  카드 필드를 유일하게 만들었는데도 계속 반복.

### 9.5 D13-A를 고른 경우

**R1-A2 · 대화 중 정리 뒤 중단**

- 목표 라운드 예산 뒤 확정 내용과 남은 질문을 한 번 요약한다.
- 파일·commit 변화 0.
- 세션이 끝나면 다음 product는 마지막 확정 Layer 0에서 재도출·재조사·재질문한다.
- 이전 답을 추측하거나 중간 요약이 복구된다고 주장하지 않는다.

### 9.6 D13-C를 고른 경우

**R1-C · 최초 partial 착지**

- 진입 시 product.md·arch·tree가 없다.
- 예산 소진 뒤 확정 판단과 blocker를 사용자에게 한 묶음으로 확인받는다.
- 정확한 partial 술어와 blocker가 한 commit에 착지한다.

**R2-C · resume 재개**

- partial product와 glossary만 존재한다.
- resume은 arch보다 product를 먼저 고르고, product는 확정 판단을 다시 묻지 않고 blocker부터
  계속한다.

**R3-C · 직접 split 호출**

- partial product가 있고 arch·tree가 없다.
- split은 product 존재만 보고 트리를 만들지 않으며 product를 안내한다.

**R4-C · 손상된 partial**

- 알 수 없는 판단 이름, 해석 불가능 마커, 필요한 heading 누락을 각각 넣는다.
- 자동 추측·자동 삭제 없이 정확한 원문과 기대 형식을 보고한다.

**R5-C · 최종 cleanup**

- 여섯 판단과 조사 게이트를 모두 닫고 사용자가 최종 문서를 확인한다.
- 같은 최종 commit에서 blocker가 전부 사라지고 다음 resume은 arch를 고른다.

**R6-C · 기존 프로젝트 product 재실행**

- arch·tree가 이미 존재한다.
- 최초 작성 한정안을 골랐다면 C를 발동하지 않고 현재 product 재실행 경계를 따른다.
- 전역 partial을 고른다면 work·split·verify까지 막는 완전한 소비자 계약 없이는 계획 실패다.

### 9.7 L-B와 최초 신호

**L11 · 한 실행의 기존 계보와 새 계보**

- 입력: 수정 카드 C1의 완료 신호와 원 카드의 다른 완료 신호가 한 verify 실행에서 함께
  non-pass이고, route 투영상 하나만 기존 root에 연결됨.
- 기대: 기존 root는 그 실행에서 재관측 1로 한 번만 전진하고, root 없는 신호는 새 계보로
  정상 라우팅된다. 두 결과를 의미가 비슷하다는 이유로 합치지 않는다.

**L12 · 첫 재관측의 새 카드/기존 계보 구분**

- 기대: 새 failure-history 출처 + 기존 root/재관측 1 + 새 승인 카드 정확히 하나.
- 실패: 카드를 만들지 않음, 새 root를 만듦, 카드 둘 이상을 자동 제안.

**L13 · 세 번째 이후 non-pass**

- 기존 최댓값이 2인 계보의 다음 non-pass.
- 기대: `재관측 3`을 기록하되 `재관측 2 이상` 사람 관문을 그대로 사용하고 새 카드를
  자동 제안하지 않는다.

**L14 · 깨끗한 verifier**

- verifier 입력에는 현재 신호·현재 card label·verify channel만 준다.
- 과거 실패 원인·수리 카드 본문·재관측 수·verify.md를 주지 않아도 현재 판정과 label 반환이
  가능해야 한다.

**L15 · 최초 fail의 재현 계약**

- 입력: verifier가 명명된 명령 또는 단계, 실패한 assertion·실제 출력을 얻음.
- 기대(F-A): `fail`과 재현 절차를 남기고 현재 수정 카드 route로 간다. DD-24에 따라 그 재현
  절차가 카드의 완료 신호가 되며 조사 카드나 새 라우팅 문법을 만들지 않는다.
- 실패: 재현 절차를 버림, 조사 카드를 수정 카드처럼 라우팅, L-B 재관측을 수리 완료 전부터 셈.

**L16 · 실행 결과 없음 또는 접근 불가**

- 입력: 필요한 환경·권한·외부 창구에 접근할 수 없어 verifier가 결과를 얻지 못함.
- 기대(F-A): 실패 원인을 추측하지 않고 `unverified`를 반환하며, 현재 정본의 missing-evidence
  수정 카드/접근 해소 경계를 따른다.
- 실패: 증거 없이 `fail`로 단정하거나 모든 접근 문제에 새 조사 route를 만듦.

**L17 · 최초 신호 대체안의 정본 호환성**

- 입력: 후속 계획이 집계 수준 fail을 조사 카드에 먼저 보낸 뒤 수정 route로 돌아오자고 제안함.
- 기대: 현재 규칙 정본의 정확한 라우팅 결과와 세션 간 복구를 증명하지 못하면 그 대체안을
  기각하고 F-A를 유지한다. 조사 카드를 `수정 카드`라고 이름만 바꾸어 통과시키지 않는다.
- 실패: 새 라우팅 문법이나 두 단계 상태를 보존 추가로 숨김, “의도상 유사함”으로 카드 종류를
  합침.

## 10. 검증 절차 — 항목을 합쳐 비용을 숨기지 않는다

### 10.1 후속 계획 독립 감사

구조 변경을 포함할 수 있으므로 감사 정본의 독립 렌즈 넷을 구분한다.

1. **반증자:** 규칙 충돌·판단어·죽은 참조·기각 계보 무반박 재제안을 찾는다.
2. **문자 실행 워커:** Q1·P5~P8·A5·B4·S4·S5와 선택한 D13 시나리오, L11~L17을 실제
   대사로 걷는다.
3. **기록 소실 감리:** 사실·사용자 답·partial blocker·재관측 기록의 producer→consumer→cleanup을
   전수한다.
4. **뺄셈 감사:** 후속 계획의 새 배포 문장마다 삭제 시 다시 열리는 실패 경로를 짝짓는다.
여기에 네 **특화 판정 항목**을 붙인다. 새 렌즈 이름을 만들지 않는다.

- 깨끗한 역할: 반증자와 문자 실행 워커가 verifier label이 현재 신호 식별자를 넘어 과거
  의미를 주입하는지 각각 확인한다.
- 수리 계보: 문자 실행 워커와 기계 fixture가 route·카드 번호·label·source id만으로 L-B
  root와 최댓값을 복원한다.
- 능동 재검토: 반증자와 뺄셈 감사가 기존 회고를 중복 호출하는지, 무후보 경로에 보이는
  절차가 생겼는지, 각 새 문장이 실제 P7/P8/S5 실패 중 무엇을 막는지 확인한다.
- 최초 신호: 문자 실행 워커와 fixture가 `fail`의 재현 절차와 결과 없음의 `unverified`를 구분하고
  현재 수정 카드 route·DD-24를 보존하는지 확인한다. 대체안이 있으면 §7.5의 네 조건과 정확한
  라우팅 결과·중단 복구를 반증한다.

기록 소실 감리와 뺄셈 감사는 같은 사냥감이 아니며, 깨끗한 역할 항목도 일반 규칙 충돌
검색만으로 통과 처리하지 않는다. 비용을 줄이려면 보고 형식을 압축하되 네 렌즈를 삭제하지
않는다. 0건은 유효하다.

### 10.2 좌표 스윕

planning 축:

```text
진입       resume | product 직접 | arch 직접 | split 직접
product    없음 | partial(D13-C일 때) | final
프로젝트   최초 | arch 있음 | tree 있음
중단       질문 전 | 답 뒤 | partial commit 뒤 | final cleanup 전
```

능동 재검토 축:

```text
단계       product | arch | adopt | split
후보       없음 | 실질 대안 하나 | 표현만 다른 안 | Layer 0를 바꾸는 안
시점       묶음 답 반영 뒤 | 구속 전 | 사용자 재선택 뒤 | 새 사실로 재개
결과       무출력 계속 | 비교·권장 | 2a 환류 | 닫힌 결정 유지/정당한 재개
```

L-B 축:

```text
계보 위치  새 root 생성 전 | 재관측 1 | 재관측 2 이상 | pass
신호       정확 실패 | 넓은 실패 | 간헐 | 접근 불가
label      root 없음 | root 하나 | root 둘 이상 | 교차 능력 의존
진입       verify 계속 | 상태 기록 뒤 중단 | 카드 생성 뒤 중단 | resume
```

각 칸을 `정의됨 / 해당 없음 / self-evident / gap`으로 판정한다. D13-A면 partial 열은
`해당 없음`이고 관련 배포 문장·테스트도 없어야 한다.

### 10.3 수리와 재감사

- 첫 독립 감사는 보고만 한다.
- 명백 결함과 판단거리를 나눈다.
- 소유자가 채택한 수리만 후속 계획에 반영한다.
- 수리된 문장만 같은 기준으로 한 번 재감사한다.
- 규칙 충돌·소실 경로 0, 남은 것이 양독 단일화·표현 등급뿐이고 수리가 해석을 새로 열지
  않으면 텍스트 감사를 멈춘다.

## 11. 크기와 사용성 예산

첫 계획의 축별 예산 측정은 유지한다. 후속 계획은 선택한 D13에 따라 합계를 따로 낸다.

| 조합 | 예산 원칙 |
|---|---|
| D13-A + planning + L-B | 첫 요청의 170~270줄 봉투를 기준으로 다시 계산 |
| D13-C + planning + L-B | A 대비 producer·consumer·정합성 검사·fixture의 순증을 별도 행으로 명명 |
| D13-B + planning + L-B | 원 요청의 예약 상태 비용을 별도 구조 축으로 계산하고 자동 허용하지 않음 |

추가 요구:

- principles 고정비와 조건부 companion 읽기를 분리해 센다.
- 소스 파일 순증뿐 아니라 product·split·verify 각 호출의 실제 추가 읽기량을 센다.
- 능동 재검토는 product·arch·adopt·split 네 소비자의 줄·문자 순증을 별도 축으로 센다.
  목표 12줄 안팎을 넘으면 줄마다 막는 실패 경로를 대되, 초과만으로 실패 처리하지 않는다.
  같은 의미를 더 짧게 유지할 수 없거나 네 투영의 의미가 갈리는 구체적 근거가 있을 때만
  companion을 별도 구조 선택으로 비교한다.
- F-A 보존 자체의 배포 순증 목표는 0이다. 최초 신호 대체안을 제안할 때만 verify-origin route의
  줄·문자·fixture 순증을 별도 축으로 세며 정상 pass의 추가 실행·질문·commit은 0이어야 한다.
- D13-C는 정상 최종 product와 모든 카드 작업에 영구 고정비를 만들지 않는지가 핵심 지표다.
- L-B는 정상 경로 실행·질문·commit 증가 0과 label prompt 비용 증가를 따로 쓴다.
- 예산 초과 시 설명을 더하지 않는다. 뺄셈 감사에서 실패 경로가 없는 문장을 먼저 뺀다.

첫 실제 사이클에서 최소한 다음을 관측한다. 이것은 통과 점수가 아니라 과잉 여부를 판별할
자료다.

- 결정 묶음 수, 내부 재검토 수, 사용자에게 실제로 제시한 대안 수, 사용자가 대안을 채택·수정·
  기각한 수, 재검토 때문에 늘어난 질문 수.
- 새 root 후보의 `fail`/`unverified` 수, 재현 절차가 보존된 수정 카드 수, 첫 수정 뒤 재관측 1에
  이른 수. 최초 신호 대체안을 채택한 경우에만 그 분기와 복구 결과를 별도 측정한다.
- 단순 흐름에서 추가 질문·도구 실행이 0이었는지와 각 entry skill의 실제 prompt 문자 증가.

## 12. 후속 계획의 필수 산출 형식

후속 계획은 다음 순서로 쓴다.

1. **북극성:** §0.3의 여섯 작동 장면과 §0.4의 비목표를 짧게 재진술하고 각 변경 단위가 어느
   장면을 실현하는지 연결.
2. **판정 요약:** 첫 계획에서 보존·교체·보류할 것.
3. **결정 원장:** 확정과 권장·확인 대기, 필수 파생 변경·확인 대기 분리.
4. **권장 조합과 남은 선택:** §3.2의 기획 후보 묶음, §3.3의 L-B 계약 묶음, R-B를 각각
   검증한 뒤 구현할 수 있는 권장 조합 하나로 수렴한다. D13 A/C/B처럼 결과가 실제로 갈리는
   소유자 선택만 preview한다. 최초 신호는 F-A를 기준선으로 두고 §7.5를 통과한 대체안이 있을
   때만 한 안을 함께 비교한다.
5. **파일별 다섯 칸 표:** §8의 열한 추가 질문까지 포함.
6. **변경 단위:** 왜·목적지·예상 장면. 구현 방법을 불필요하게 고정하지 않음.
7. **기존 경계 대조:** 능동 재검토↔DD-22/23 회고, F-A 또는 증명된 대체안↔기존 failure route와 L-B,
   D13-C↔DR-01·DD-28·DD-33·DD-59를 각각 구분.
8. **구현 순서:** `_ko` 먼저, 사용자 확인, 영문 동형성, 축별 측정.
9. **검증:** §9·§10의 시나리오·렌즈·좌표·강등 조건.
10. **크기 예산:** D13 조합과 능동 재검토의 별도 합계. 최초 신호 대체안이 있을 때만 그 순증을
    별도 합계로 추가.
11. **승격:** 새 DD 후보·기각 계보 반박·matrix 행·backlog 처분.
12. **구현 승인 관문:** 소유자가 후속 계획을 명시 승인하기 전 배포 파일 변경 없음.

후속 계획이 첫 계획을 인용할 때는 “그대로”만 쓰지 않고 어느 행을 보존하는지 이름으로 지목한다.
첫 계획의 잘된 부분을 전부 다시 장문 복제할 필요는 없지만, 구현자가 두 계획을 합성해야만
파일 범위를 알 수 있게 만들어서는 안 된다. 후속 계획 하나가 선택된 조합의 완전한 구현 목록을
가져야 한다.

후속 계획 작성자는 §0.5의 범위에서 이 후보 기준선을 반증할 수 있다. 그러나 각 축마다 새 후보를
늘어놓는 것으로 검토를 대신하지 않는다. 대체가 필요하면 같은 실패 경로를 더 낮은 또는 같은
구조·프롬프트 비용으로 닫는 한 안을 권장 조합에 넣고, 나머지는 기각 이유만 짧게 남긴다.

## 13. 완료 조건

다음이 모두 참일 때만 request2가 요구한 두 번째 계획이 검토 준비 상태다.

1. 무이의 진행을 근거로 권장안을 확정한 행이 0이다.
2. D13의 대화 요약과 영속 복구가 한 이름으로 섞이지 않는다.
3. D13-A면 새 상태·resume/arch/split marker 문장이 0이다.
4. D13-C면 새 상태임을 표시하고 producer·직접/간접 consumer·cleanup·손상 복구·중단 fixture가
   모두 있다.
5. product 질문 의존은 근거 없는 전역 총순서가 아니라 실제 제시할 선택지의 영향으로 판정된다.
6. 의미 삼각형이 제품·능력·비자명한 경계·어려운 아키텍처 결정의 기존 거처에 한 번씩만
   놓이고, 빈 이유를 AI가 지어내지 않는다.
7. R-B를 고르면 결정 묶음당 내부 재검토 1회, 후보 없음의 추가 출력·질문·조사 0, 후보 있음의
   비교 후보 최대 1개가 같은 계약으로 적힌다.
8. product·arch·adopt·split의 재검토 지점과 단계 소유권이 §6.3에 맞고, design을 조용히
   소비자에 추가하지 않는다.
9. 능동 재검토가 DD-22·DD-23 회고를 질문·카드 수준으로 이동시키거나 대신하지 않는다.
10. 사용자 재선택 뒤 재귀 탐색하지 않고, 닫힌 결정은 새 사실·모순·성공 판정 변화 없이 다시
    열지 않는다.
11. 최종 선택과 이를 가른 이유·바라는 결과는 기존 의미 거처 또는 ADR에 남고, 모든 기각
    후보를 저장하는 새 로그는 없다.
12. split 2b가 능력 설계 구역·새 파일·새 상태를 만들지 않는다.
13. reviewer diff 0과 verifier의 과거 이력 금지가 유지된다.
14. `재관측 2 이상`이 principles·verify·work·테스트에서 같은 뜻이다.
15. 첫 재관측에서 “새 카드”와 “새 계보”가 구분된다.
16. 최초 non-pass는 F-A의 verifier 재현 절차·`fail`/`unverified` 구분·현재 수정 카드 route·
    DD-24를 보존하고, 수리 완료 전에는 L-B의 재관측을 세지 않는다.
17. 조사 카드를 수정 카드로 라우팅하거나 정의되지 않은 두 단계 route를 보존 추가로 숨기지
    않는다. 최초 신호 대체안이 있으면 §7.5의 네 조건과 정확한 세션 간 복구를 모두 증명한다.
18. 교차 능력 의존을 포함한 L-B route 투영이 현재 회귀 묶음에 비례한다.
19. 계보 유일 복원 실패 시 L-A 강등이 구현자 자기 판정과 독립 감사 양쪽에서 보수적으로
    작동한다.
20. 뺄셈 감사를 독립 렌즈로 실행하고, 깨끗한 역할·능동 재검토·최초 신호 판정을 지정된
    서로 다른 렌즈에서 수행한다.
21. D13 조합과 능동 재검토의 줄·문자·호출별 읽기량 예산이 각각 다시 계산된다. 최초 신호
    대체안이 있을 때만 그 순증을 별도 계산한다.
22. 예측 점수를 실측 성과로 쓰지 않고 첫 실제 사이클의 측정 항목을 남긴다.
23. 후속 계획은 §3.2 기획 후보와 §3.3 L-B 계약을 독립 선택지 숲으로 되돌리지 않고 검증된
    권장 조합 하나로 제시한다. 소유자가 그 조합과 D13의 실제 선택, 필요한 판단거리를
    명시적으로 확인하기 전 구현하지 않는다.
24. 계획 머리말과 별도 감사 기록이 같은 검증·승인 상태를 말한다.

## 14. 요청서의 항목별 자가 검증

### 14.1 검증 성격과 방법

이 절은 **작성자가 같은 세션에서 수행한 자기 검토**다. 독립 반증이나 구현 후 감사를
대체하지 않는다. 다음 네 질문으로 §0~§13의 요구를 각각 다시 대조했다.

1. 원 요청·handoff·첫 계획·현재 배포 원문 중 어느 출처에 기대는가.
2. 그 출처보다 강한 새 계약을 사실이나 확정으로 둔갑시켰는가.
3. 문장을 빼면 어떤 구체적 실패가 다시 열리는가.
4. 기존 방향을 보완하는 범위를 넘어선 판단은 소유자 선택으로 남겼는가.

### 14.4 수리 후 판정

- §0~§13의 각 핵심 요구에는 출처, 막는 실패 경로, 승인 지위가 있다.
- 현재 자기 검토에서 남은 **규칙 충돌·기존 요구 손실·무단 확정은 0건**이다.
- D13-C 최초 작성 한정, product 의존 조건, 기획 후보 묶음, D15~D17 계약 묶음, R-B는 합리적
  권고이지 소유자 확정이 아니다. F-A는 새 기능 선택이 아니라 현재 계약의 기준선이고, F-B는
  현재 설계로 기각했다.
- D18의 능동 재검토 목적과 D19의 무거운 새 절차 금지는 사용자 방향이다. 빈도·배포 문구·
  줄 예산은 후속 계획의 검증과 소유자 확인을 거친다. 12줄은 경직된 합격 술어가 아니다.
- 후속 계획 작성자는 같은 축을 더 잘 닫는 대체안을 제안할 수 있으나, 더 나은 안이 0개인
  결과도 받아들이고 최종적으로 권장 조합 하나로 수렴한다.
- 실제 문구의 실행 가능성과 구현 파일 전체 좌표는 후속 계획의 독립 감사에서 다시 검증해야 한다.

## 15. 한 문장 판정

**첫 계획은 폐기 대상이 아니라 정밀화 대상이다. 기획 후보 묶음·의미 삼각형·split 2b·L-B
계약 묶음과 결정 묶음마다 한 번의 무출력 기본 재검토를 권장 기준선으로 검증하고, 최초 신호는
현재 verifier·수정 카드·DD-24 계약을 보존하며, D13은 ‘대화 요약 A / 초기 영속 복구 C /
질문 전 복구 B’의 실제 선택만 소유자에게 남긴다. 후속 계획 작성자는 같은 축의 더 나은 안을
증명할 수 있지만, 새 주제를 열지 않고 구현 가능한 권장 조합 하나로 수렴해야 한다.**
