## 1. 이번 라운드가 고치려는 것 — 두 문장으로

**기획이 사용자에게 숙제를 떠넘기지 않게 한다.** 그리고 **검증이 같은 실패를 두 번째
만났을 때 그것을 알아보게 한다.**

예를 들면 이런 차이다.

> 지금까지: "확장 API가 오프라인 저장을 허용하나요?" ← 이건 사용자가 아니라 문서와
> 코드가 답할 수 있는 질문인데 사용자에게 갔다.
>
> 이제부터: 그 답은 AI가 해당 버전의 문서에서 직접 찾는다. 사용자에게는
> "저장이 실패하면 조용히 버릴까요, 알림을 띄울까요?" 같은 **가치 선택만** 간다.

수리 쪽도 마찬가지다.

> 지금까지: 수리했던 기능이 또 깨지면, 검증은 그것을 처음 보는 실패처럼 다뤘다.
> 이전에 뭘 시도했고 왜 실패했는지가 다음 수리에 전달되지 않았다.
>
> 이제부터: 실패마다 "어느 카드의 완료 신호였나"가 기록되고, 재발이면 직전 수리
> 카드들이 새 수리 카드의 읽을 목록에 자동으로 들어간다. 같은 게 세 번째 깨지면
> 자동 수리를 멈추고 사람에게 온다.

## 2. 지금까지 만든 것 (기획 묶음, 한국어 원본 7파일)

| 파일 | 내용 한 줄 |
|---|---|
| `planning-evidence_ko.md` (신규 75줄) | 규율의 본체 — "모르는 것"을 넷으로 분류하고, 각각 누가 답하는지·언제 멈추는지를 정함 |
| product | 질문을 3~5개씩 묶되, 앞 답이 뒤 질문을 바꾸는 것은 단건으로 먼저 물음 |
| arch | 후보 기술이 실제로 살아 있는지(버전·플랫폼·라이선스) 확인한 뒤에만 사용자에게 올림 |
| adopt | "코드가 말하는 현재"와 "문서가 말하는 가능성"과 "소유자가 정하는 미래"를 섞지 않음 |
| split | 페이지·모달 같은 작은 덩어리는 이름이 아니라 "카드 네 칸이 유일하게 채워지는가"로 판단 |
| design 문서 2종 | 위 결정을 DD-67로 정본에 기록 |

핵심 안전장치 하나만 꼽으면 **"후보가 없으면 출력도 없다"**다. 결정을 묶기 직전 더
나은 대안을 한 번 되돌아보되, 실질적인 대안이 없으면 아무것도 보여주지 않는다.
정상적인 작은 프로젝트는 이번 라운드로 질문이 하나도 늘지 않는다.

## 3. 교차 검증이 실제로 잡아낸 것

GPT가 만들고 → Claude가 백지 상태에서 검증하고 → GPT가 그 소견을 반박 시도한 뒤
판정하고 → Claude가 적용하는 루프를 한 바퀴 돌렸다. 결과:

- **잡았다 ①: 뒤집힌 정의.** "결정할 수 **있을** 때 차단"이라고 적혀 있었다. 원래
  의도는 "결정할 수 **없을** 때 차단". 화재경보기 배선이 거꾸로 연결된 셈이라 —
  연기가 나면 침묵하고 평소에 울리는 — 한 단어짜리 수정이지만 네 스킬의 멈춤/진행
  판단이 통째로 반대로 갈 뻔했다.
- **잡았다 ②: 낡은 참조.** product의 능력 표기 형식을 새로 바꿨는데, adopt 한 곳이
  옛 형식 이름을 그대로 들고 있었다.
- **기각 1건.** "설계 색인의 문장과 본문 절 제목이 살짝 다르다"는 소견은, 문서를
  고치는 세션이 반드시 본문을 열게 되어 있어 실제 오독이 일어날 수 없음을 확인하고
  표현 취향으로 기각했다. (원하면 통일 가능 — 소유자 선택.)

## 4. plan3에서 벗어난 것이 있나 — 없다

- 바뀐 파일은 계획된 7개뿐(기계 확인). 버전·영문·수리 축·금지 목록 전부 무변경.
- 줄 예산도 전부 안쪽: 신규 75줄(상한 75), product +28, arch +32, adopt +33, split +30.
- 구현 재량 안의 판단 2건은 공개한다: split 새 절의 위치를 "요청 기록이 먼저"라는
  기존 순서에 맞게 옮긴 것, adopt에서 "성공 판정에 필요한 이유"는 코드가 아니라
  소유자가 답하는 쪽으로 분류한 것. 둘 다 계획의 의도를 지키기 위한 정렬이었다.
