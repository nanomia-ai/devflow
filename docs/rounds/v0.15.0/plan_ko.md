# v0.15.0 계획 — 사실은 AI가 먼저 닫고, 덩어리는 필요한 만큼 기획하며, 같은 수리의 재발은 알아차린다

상태: 계획 초안 (독립 계획 감사 전 · 구현 승인 전) · 작성 2026-08-14
입력: `request_ko.md`(동결 원본) + `handoff_ko.md`(검증 완료 완성본 — 소유자 결정 6건과
정정 채널 R/D). **구현자는 요청서를 handoff §10.2의 R/D 정정 독해로 읽는다** — 요청서
자체는 이 라운드 내내 무수정이다.

이 계획의 각 변경 단위는 셋을 함께 말한다: **왜**(무엇이 관측되었나), **설계**(어느 파일의
어느 문장을 어떻게), **기대 작동**(구현 뒤 실제로 벌어져야 하는 장면 — 구현자가 자기 해석을
대조할 기준). 요청서 §4.4의 규율대로 각 파일 행은 다섯 칸을 가지며, "개선"이라는 말로
교체를 추가처럼 표시하지 않는다.

---

## 1. 왜 — 이 라운드가 필요하다고 관측된 것

1. 기획 3단계(product·arch·adopt)가 **AI가 스스로 확인할 수 있는 사실을 사용자에게 묻는다**
   — 사용자가 추측으로 답하면 잘못된 전제가 Layer 0에 오래 보존된다(요청서 §2.1).
2. 질문 묶음 사이의 결정 의존 순서가 없어 앞 답이 뒤 질문을 무효화한다(§2.1, R9 정정 독해).
3. arch의 스택 추천이 모델 기억에 의존하고, 후보를 무효화할 차단 사실과 나중에 실측할
   잠정값의 경계가 없다(§2.1).
4. adopt에서 외부 계약이 "devflow 밖 문서" 서열에 묶여 코드와 한 서열로 읽힌다(§2.1, R9).
5. 작은 요청은 형식상 완전한 카드가 되지만 제품 결정(트리거·빈 상태·실패 동작)이 빠질 수
   있다(§2.3).
6. **최상위 기획과 카드 분할 사이에 중간 규모 덩어리의 기획을 좁히는 과정이 없다**(소유자
   관측 2026-08-14 — 이 라운드의 핵심 추가 입력).
7. 검증에서 닫힌 수정 카드의 신호가 다시 실패해도 새 실패·새 카드로만 보여, 소유자가 매번
   승인하는 동안 같은 종류의 수리가 수렴 상한 없이 반복될 수 있다(§2.5·§11.1).
8. 긴 기획 인터뷰가 중단되면 확정 전 대화 전체가 재작업이 된다(소유자 요청 — 중간 정리).

## 2. 무엇을 — 세 축, 한 릴리스

- **축 1 · 기획 증거 규율**: 공통 companion 하나 + 네 소비자(product·arch·adopt·split)의
  유계 분기. 미지수를 네 종류(저장소 사실·외부 계약 사실·실행 사실·소유자 결정)로 갈라
  사실은 먼저 닫고 결정만 묻는다.
- **축 2 · 중간 규모 기획**: split 유지보수 등급을 0/1/2a/2b로 — Layer 0가 열리면 상위
  환류(2a), Layer 0 보존 덩어리는 프런티어 묶음 반복(2b, 카드 착지만). product에는 긴
  기획의 중간 정리 1회.
- **축 3 · 검증 수렴(L-B)**: 회귀 신호에 완료 카드 번호 label을 붙이고, 재발을 카드
  번호로만 판정해 첫 재발은 진단 강화 카드 하나, 두 번째부터는 사람 관문.

D12 확정대로 한 릴리스(0.15.0)에 싣되 §6의 순서로 축 1·2를 먼저 닫고 측정한 뒤 축 3을
얹는다. 어느 축도 reviewer 계약·능력 문서 소유권·카드 승인 체계를 바꾸지 않는다.

## 4. 변경 단위 상세 — 왜 · 설계 · 기대 작동

### U1 · planning-evidence companion

**왜**: 같은 40줄을 네 스킬에 복제하면 수리 때 갈라지고, principles에 넣으면 work·verify까지
매번 읽는 전역 고정비가 된다(요청서 §5.2). **설계**: 요청서 §5.3(4분류 표)·§5.4(차단/후속
판정)·§5.5(출처 소유권 표)·§5.6(정지 3상태)·§5.7 기본안 A(영속화 — 결론+영향+출처만 기존
소유 문장에)·§5.8(병렬은 선택 최적화·재위임 금지)을 45~65줄로 압축한 정본 companion 쌍.
소비자는 넷뿐이고 각자 자기 trigger·착지·금지를 자기 SKILL에 쓴다. **기대 작동**: 결제
서비스 기획에서 "부분 환불을 지원하나요?"가 사용자에게 가지 않는다 — AI가 공급자 공식
문서(외부 계약 사실)를 먼저 확인하고, "이 제약 아래 MVP에 부분 환불을 넣을까요? 권장은
…"(소유자 결정)만 묻는다. 외부 의존이 없는 작은 CLI에서는 조사가 0회 발생한다.

### U2 · product

**왜**: §1의 1·2·8. **설계**: ① 인터뷰 규칙의 묶음 기준을 교체한다(D6) — "같은 프런티어의
독립 질문 최대 5개(보통 3~5개). 의존 때문에 묶을 수 없는 결정은 단건으로 묻고, 답으로 열린
결정들은 묶을 수 있으면 능동적으로 다시 묶는다." ② §6.2의 7단계 절차(유일하게 쓸 수 없는
판단 찾기 → 선행 확인 → companion 분류 → 사실 먼저 → 결정 묶음 → 새 묶음 → 여섯 판단
완성 시 정지)를 인터뷰 규칙 앞에 — "선행"이 판단어로 남지 않게 여섯 판단의 선행 관계를
구현 문장이 열거한다: 문제 → 해결 방식 → 능력 구성 → {경계 · 성공 판정 · 화면·창구}(뒤
셋은 서로 독립, 전부 능력 구성 뒤). ③ §6.3 자동 조사 trigger/비trigger(명시 요청은 항상
좁게 실행 — D7). 자동 조사(외부 계약 확인)가 "개발 얘기 금지"의 위반이 아님을 한 줄로 경계
표시한다 — 스택·DB 결정은 계속 arch 몫이고 이것은 사실 확인이다. ④ §6.4 glossary 3동작. ⑤ §6.6 능력 한 줄(번호+이름+사용자 결과+성공 판정
연결 — D5 의미 삼각형, 새 필드 없음). ⑥ §6.7 종료 게이트. ⑦ **중간 정리**(D13): 목표
라운드 예산을 소진하고도 계속하기로 한 시점에, 확정된 판단까지를 사용자 확인으로 Layer 0
커밋에 중간 착지하고 남은 질문을 `열린 질문` 절에 `[막음: <판단 이름>]` 표기로 남긴다.
최종 완료가 표기를 지운다 — §6.6("막는 질문은 남길 수 없다")·§6.7("여섯 판단이 모두
쓰였다")은 최종 완료의 게이트로 남고 중간 착지에만 이 표기의 예외가 열린다(표시된 국소
계약 변경). **기대 작동**: 능력 2개짜리 프로젝트는 지금과 똑같이 1~2라운드로 끝난다(질문
증가 0). 능력 6개 프로젝트에서 3라운드를 소진하고 계속하기로 하면, "지금까지 확정: 문제·
해결 방식·능력 5개 — 남은 것: ⑥번 능력의 경계[막음: 경계], 성공 판정 2개[막음: 성공
판정]" 형태의 부분 초안이 확인되고 함께 만든 glossary와 같은 Layer 0 커밋 관행으로
착지되며, 세션이 죽어도 다음 세션은 남은 질문 두 개부터 잇는다. arch를 부르면 시작하지 않고 "product가 끝나지 않았습니다 — 남은 질문 2개"라고 안내만 한다.

### U3 · arch

**왜**: §1의 3. **설계**: ① 1~2단계 사이에 후보 생존을 가르는 사실만 열거·확인(지원
플랫폼·버전 호환·라이선스·런타임·배포 환경·보안 경계·창구 가능성 — §7.2). ② 조건부 두
설계(§7.3): 되돌리기 어렵고 경계가 비자명한 결정만 구조 두 개를 짧게 — 현행 "비교표
금지"는 스택 질문 형식에 한정됨을 같은 자리에서 명시(검토가 남긴 경계 주의의 해소). ③ 차단/잠정 경계 표(§7.4)와
안전 실행 4순서(§7.7). ④ 창구는 존재가 아니라 실행 가능성까지(§7.5). ⑤ 진입부에 중간
정리 게이트 한 줄. **기대 작동**: "이 런타임이 대상 OS를 지원하나"는 지금 확인되고, "batch
크기"는 잠정값+해소 카드로 남는다. 지원 안 되는 후보는 사용자 선택지에 오르지 않는다.

### U4 · adopt

**왜**: §1의 4. **설계**: 증거 서열 문장 곁에 세 질문 권위 분리(§8.2 표 — 현재 구현은
좁은 실행·코드가, 외부 계약은 lockfile 버전의 1차 출처가, 원하는 방향은 소유자 확인이
답한다), 후보별 내부 증거표(§8.3 — 파일로 저장하지 않음), 버전 우선 외부 조사(§8.4 —
버전이 없으면 `버전 미확인`), 확인 묶음 전 관찰/해석/결정 3갈래 preview(§8.5), 종료
게이트(§8.7). **기대 작동**: 구버전 결제 SDK 저장소에서 "지금은 전체 환불만 한다"(관찰),
"공급자 계약은 부분 환불도 지원한다"(외부 계약), "앞으로 지원할까?"(소유자 결정)가 한
문장으로 섞이지 않고 각각 제시된다.

### U5 · split — 등급 0/1/2a/2b

**왜**: §1의 5·6. **설계**: 유지보수 2단계 뒤에 등급 판정을 둔다. 0(네 필드가 정확한 기존
출처에서 유일 — 질문 없이 계속) / 1(한 묶음으로 유일해짐 — 추천 붙은 묶음 하나, 경계가 갈리는 경우에만 구체적
시나리오 하나) / 2a(제시할 선택지 하나라도 Layer 0 필드를 바꿈 — 카드 없이 소유 단계로
환류. 2b와 겹치면 2a가 이김) / **2b**(Layer 0 보존인데 한 묶음 뒤에도 카드 필드에 유효한
문장이 둘 이상 — 같은 유지보수 대화에서 다음 프런티어 묶음을 계속. 판정 입력은 실제 제시할
선택지와 실제 답뿐. 착지는 카드 필드+ADR 3조건 통과 시 ADR+확정 용어 glossary뿐 — 능력
설계 구역·새 파일·새 상태 금지. 어느 묶음의 답이든 Layer 0를 열면 즉시 2a. 덩어리는 규모
이름이 아니다 — 페이지든 그 안의 모달·목록·필터든 이 조건으로만 판정). 사실이 비면
companion 분류(§9.3), 중단 복구는 유지보수 줄 계약 그대로(§9.6 — 카드 착지 전 중단이면 원
요청에서 재판정·재질문). companion은 유지보수·조사 분기에서 정확한 heading 범위만
읽는다(안 B — heading 이름을 배포 문장에 열거, DR-25 회피). **기대 작동**: "저장 버튼
라벨 변경"은 경량 차선(split에 안 옴), "필터 모달에 날짜 범위"는 묶음 하나 뒤 카드,
"정산 페이지의 목록·필터·상세 모달 고도화"(관리자 정의·성공 판정은 기존 그대로)는 묶음
두세 번으로 카드들이 유일해질 때까지 기획이 좁혀지고, "새 관리자 역할이 필요하다"는 답이
나오는 순간 카드 없이 product로 올라간다.

### U6~U9 · 검증 수렴 (L-B)

**왜**: §1의 7 — 기록은 이미 충분한데(실패 이력·출처 id·수정 카드·회귀) 기록 사이의 계보를
소비하는 수렴 제어가 없다. **설계**: verify 2단계가 회귀 목록을 만들 때 각 완료 신호에
완료 카드 번호를 label로 붙인다(메인이 구성하므로 번호는 손에 있다). verifier는 non-pass
회귀의 카드 번호를 반환에 포함하되 과거 이력은 계속 받지 않는다(label은 현재 신호다 —
DD-48). 메인은 **신설** 유계 route 투영 — 범위: 현재 검증 대상 key의 verify.md·트리 루트
verify.md·현재 회귀 묶음의 label 카드가 속한 능력들의 verify.md(교차 능력 `의존` 1홉이
회귀에 들어오므로 — 읽기는 역사가 아니라 묶음 크기에 비례, DD-56 보존) — 로 과거
`라우팅: 수정 카드 <번호>`를 얻어, 실패한 label이 정확히 한 root에 있으면 재발로 판정한다.
재관측 기록·분기·복합 label·상한은 요청서 §11.3의 문법 그대로 — 단 R8의 단일화 독해로:
분기의 "다른 실패도 함께 냄"은 "그 신호 하나가 여러 실패를 함께 냄"이다(재관측 1: 접근
해소/clean diagnosis/조사 카드 중 정확히 하나 — D16; 재관측 2 이상: 6단계가 그
`라우팅: 대기`를 라우팅하지 않고 카드·신호·조사 답·관측을 보고하며 소유자 선택 전 새
실행·출처 id·카드 금지). principles의 사다리 절에 3~5줄 연결. work은 재관측 1의 정확 실패 카드에서만 기존
깨끗한 진단을 소비해 가설 1+예측 1을 진행 로그에 남긴다. **기대 작동**: 시간대 버그 수정
카드 02.3b가 닫힌 뒤 몇 주 후 재검증에서 02.3b의 재현 절차가 또 실패하면 — 새 카드가 아니라
"02.3b 수리의 첫 재발"로 보고되고 진단 강화 카드 하나가 제안된다. 그 계보가 한 번 더
돌아오면 자동 제안 없이 전체 이력이 소유자에게 온다. 무관한 새 실패 G는 02.3b의 횟수를
올리지 않는다. 통과하는 검증의 추가 실행·질문·commit은 0이다. literal walk에서 계보가 모든
중단 지점에서 유일 복원되지 않으면 **축 3 전체를 L-A로 강등**하고 배포 파일을 고치지
않는다(§11.5 유지 — 조기 강등이며, L-B 유지의 확정은 §7 렌즈 ③ 독립 패스 몫).
