## 4. 권장 조합과 남은 선택

**권장 조합 하나**: `D13-A` + `기획 후보 묶음 전체(D1~D3·D5·D7~D9·D11·D18-R-B)` +
`split 0/1/2a/2b` + `L-B′(D15·D16′·D17 + 상속 + 함정 배선)` + `D22 재분할 대칭` +
`F-A 최초 신호 계약 보존`.

**결과가 실제로 갈리는 소유자 선택은 남지 않았다.** D13은 A로 확정됐고, 새 구조 선택
(D13-C · D13-B · L-C · 중간-C)은 전부 본안 밖으로 분리했다. **남는 것은 갈래가 아니라
확인이다** — §3.2의 기획 후보 묶음 하나, §3.3의 L-B 계약 묶음 하나, 그리고 §3.4 다섯 판단의
수용 여부. 그 확인이 §12의 구현 승인 관문이다.

**최초 신호는 F-A가 기준선이다.** request2 §7.5의 네 조건을 통과하는 대체안을 이 계획은
제안하지 않는다 — 현재 계약(verifier의 재현 절차 · `fail`/`미검증` 구분 · 현재 수정 카드
route · DD-24)이 이미 최초 non-pass를 수리 가능한 신호로 남기고 있고, 이 계획이 더하는 것은
그 뒤 **재발**에만 걸리기 때문이다. F-A 보존 자체의 배포 순증은 0이다.

### 5.4 README 무수정 판정 (F17의 확정 내용)

**이번 라운드는 README를 고치지 않는다.** 근거 셋:

1. 사용자가 부르는 명령이 하나도 늘거나 바뀌지 않는다 — companion은 등록 스킬이 아니다.
2. 2b가 바꾸는 것은 **질문 라운드 수**인데, README는 질문 수를 계약으로 적은 적이 없다.
3. 능동 재검토의 정상 경로는 **무출력**이라 사용자가 볼 것이 없다.

D11의 "preview 뒤 필요할 때만"은 이 판정으로 소진된다. 실전 첫 사이클에서 사용자가 2b의
반복 질문을 예상 밖으로 느꼈다고 보고하면 그때 한 단락을 검토한다 — 그것은 다음 라운드의
입력이지 이번 구현의 미결이 아니다.

**재검토 축**(§8-8): 내부 재검토는 F1의 한 절이 소유하고 네 소비자가 그 절을 읽는다. 후보
없음 → 추가 출력·질문·조사·기록 0. 후보 있음 → 후보 **하나만** 현재 안과 비교하고 사용자가
결정한다. 사용자 재선택 뒤 → 그 묶음은 닫히고 재귀 탐색하지 않는다.

**회고 경계**(§8-9): 구속 결정 **전**의 교정이며 DD-22·DD-23의 사후 회고를 호출하지도
대신하지도 않는다. retrospector를 부르지 않고 strain evidence·회고 기록을 만들지 않는다.

**최초 신호**(§8-10): F-A 그대로. verifier의 재현 절차, `fail`/`미검증` 구분, 현재 수정 카드
route, DD-24를 전부 보존하고 배포 순증 0. L-B′의 재관측은 **수리가 완료된 뒤**부터만 센다.

## 6. 변경 단위 — 왜 · 목적지 · 예상 장면

### U1 · planning-evidence companion

**왜.** 같은 40줄을 네 스킬에 복제하면 수리 때 갈라지고, 규칙 정본에 넣으면 work·verify까지
매번 읽는 전역 고정비가 된다. 그리고 이번에 추가되는 두 규칙(실제 제시 선택지 기준 · 구속 전
재검토)의 소비자가 정확히 같은 넷이다.

**목적지.** `product`·`arch`·`adopt`·`split`이 미지수를 같은 네 종류로 가르고, 사실은 먼저
닫고 결정만 묻고, 같은 정지 조건에서 읽기를 멈추며, 구속 결정 전에 한 번 재검토한다.

**담을 것.**

```
## 미지수 네 종류        현재 저장소 사실 / 외부 계약 사실 / 실행 사실 / 소유자 결정
## 차단 사실과 후속 사실  차단이면 답·충돌·불가 중 하나가 나올 때까지 다음 단계 금지
## 출처 소유권            "누가 그 사실을 바꿀 수 있는가"로 소유자를 정한다
## 정지 조건              settled / conflicted / unavailable — 개수·시간이 아니다
## 영속화                 결론 한 문장 + 그 결론이 현재 결정에 미친 영향 + 정확한 출처
                          원시 조사 파일을 만들지 않는다
## 병렬 조사              선택 최적화다. 재위임 금지. 없어도 같은 결론에 도달한다
## 실제 제시 선택지 기준   앞 질문에 실제로 제시할 선택지 중 하나라도 뒤 질문의 필요 여부·
                          선택지·추천 기본값을 바꾸면 두 질문은 의존한다
## 구속 전 재검토          네 조건을 모두 통과하는 대안이 있을 때만 후보 하나를 보인다
```

위 절 이름은 **문안의 뼈대이지 완성문이 아니다** — 실제 문장은 구현이 압축하고, split이
유계로 읽을 때 열거하는 것은 **배포(영문) 파일의 정확한 heading 이름**이다. 그 열거와 실재의
결합은 F13의 기계 검사가 지킨다.

**「실제 제시 선택지 기준」이 한 곳에 사는 이유**: 이 술어는 세 곳에서 쓰인다 — product의
묶음 판정(D6), split의 2a/2b 등급 판정(D10), 그리고 재검토의 4조건 중 넷째. 세 곳이 각자
정의하면 같은 요청이 스킬마다 다르게 판정된다.

**구속 전 재검토의 네 조건과 단계별 지점** (companion 안의 한 절):

| 조건 | 내용 |
|---|---|
| 1 | 현재 증거 또는 이미 허용된 조사 trigger가 허용한 증거로 설명할 수 있다 |
| 2 | 표현 취향이 아니라 사용자 결과·제품 경계·되돌리기 비용·검증 가능성 중 하나를 실질적으로 바꾼다 |
| 3 | 이미 선택한 안의 이름만 바꾼 것이 아니라 서로 다른 trade-off를 가진다 |
| 4 | 현재 단계의 소유권 안에서 비교할 수 있다 |

| 단계 | 재검토 지점 | 지켜야 할 경계 |
|---|---|---|
| product | 묶음의 답을 반영한 뒤, 다음 묶음 생성 또는 최종 확인 전 | 사실은 AI가, 가치 선택은 사용자. 여섯 판단 소유권 유지 |
| arch | 후보 사실을 확인한 뒤 되돌리기 어려운 선택을 구속하기 전 | D9의 조건부 두 설계가 arch 투영이다. 단순 스택 취향에는 발동하지 않는다 |
| adopt | 관찰·해석·미래 결정을 preview한 뒤 확인 전 | 현재 사실을 미래 의도로 승격하지 않는다 |
| split | 카드 네 필드가 처음 유일해진 시점, 카드 착지 전 | 일반 아이디어로 확장하지 않는다. Layer 0 변화면 2a |

조건을 통과한 후보가 없으면 **추가 출력·질문·조사·기록이 전부 0이다.** 후보가 여럿이면
기록된 성공 판정과 사용자 우선순위가 하나를 가를 때만 제안하고, 그것으로도 갈리지 않으면
현재 선택을 유지한다. `design`은 이번 소비자에 추가하지 않는다.

**예상 장면.** 결제 서비스 기획에서 "부분 환불을 지원하나요?"가 사용자에게 가지 않는다 —
AI가 공급자 공식 문서를 먼저 확인하고 "이 제약 아래 MVP에 부분 환불을 넣을까요? 권장은 …"만
묻는다. 외부 의존이 없는 작은 CLI에서는 조사가 0회, 재검토 후보도 0이라 출력이 늘지 않는다.

### U2 · product

**왜.** 사실 질문이 사용자에게 가고(§1-1), 묶음 사이 의존 순서가 없어 앞 답이 뒤 질문을
무효화한다(§1-2).

**목적지.** 여섯 판단을 유일하게 쓸 수 있을 때까지, 사실은 AI가 닫고 결정만 묻는다.

**담을 것.** ① 묶음 기준 교체(D6) — "같은 프런티어의 독립 질문 최대 5개(보통 3~5개). 의존
때문에 묶을 수 없는 결정은 단건으로 묻고, 답으로 열린 결정들은 묶을 수 있으면 다시 묶는다."
의존 판정은 companion의 「실제 제시 선택지 기준」을 쓴다 — **여섯 판단의 고정 총순서를 쓰지
않는다.** ② companion 읽기와 프런티어 순서. ③ 자동 조사 trigger/비trigger, 명시 요청은 항상
좁게 실행(D7), 그리고 **자동 조사는 "개발 얘기 금지"의 위반이 아니라는 경계 한 줄** — 스택·DB
결정은 계속 arch의 몫이고 이것은 사실 확인이다. ④ glossary 3동작. ⑤ 능력 한 줄의 의미
삼각형(번호+이름+사용자가 얻는 결과+그 결과가 성공 판정에 필요한 이유). ⑥ 종료 게이트.
⑦ 라운드 예산을 소진하고도 계속하기로 한 시점에 **확정된 것과 남은 질문을 대화로 한 번
요약**한다 — 파일·커밋 변화 0.

**축 규칙을 폐기하면 무엇을 잃는가 (정직하게).** 현행 "축이 하나(대상·가치 / 경계 / 미결)"는
한 묶음의 인지 부하를 낮추는 장치였고, 프런티어 기준은 번복을 막는 장치다. 둘은 다른 것을
산다. 인지 부하는 **최대 5개 상한**이 대신 막는다. 서로 독립인 경계·성공 판정·화면 질문이 한
묶음에 함께 오는 것은 request2 §6.1이 명시적으로 허용한 결과다.

**예상 장면.** 능력 2개짜리 프로젝트는 지금과 똑같이 1~2라운드로 끝난다(질문 증가 0). 능력
6개 프로젝트에서 3라운드를 소진하고 계속하면 "지금까지 확정: 문제·해결 방식·능력 5개 / 남은
것: ⑥번 능력의 경계, 성공 판정 2개"를 한 번 보여 준 뒤 계속한다. 세션이 죽으면 마지막 확정
Layer 0에서 다시 도출하고 답을 추측하지 않고 다시 묻는다 — 이것이 A가 사는 것과 못 사는
것이다.

### U3 · arch

**왜.** 스택 추천이 모델 기억에 의존하고, 후보를 무효화할 차단 사실과 나중에 실측할 잠정값의
경계가 없다.

**목적지.** 후보를 사용자에게 올리기 전에 그 후보를 죽일 수 있는 사실이 닫혀 있다.

**담을 것.** ① 1~2단계 사이에 후보 생존을 가르는 사실만 열거·확인(지원 플랫폼·버전 호환·
라이선스·런타임·배포 환경·보안 경계·창구 가능성). ② 조건부 두 설계(D9) — 되돌리기 어렵고
경계가 비자명한 결정만. 같은 자리에 **현행 "비교표 금지"는 스택 질문 형식에 한정됨**을 명시.
③ 차단/잠정 경계 표와 안전 실행 4순서. ④ 창구는 존재가 아니라 실행 가능성까지.

**예상 장면.** "이 런타임이 대상 OS를 지원하나"는 지금 확인되고, "batch 크기"는 잠정값+해소
카드로 남는다. 지원되지 않는 후보는 사용자 선택지에 오르지 않는다.

### U4 · adopt

**왜.** 외부 계약이 "devflow 밖 문서" 서열에 묶여 코드와 한 서열로 읽힌다.

**목적지.** 현재 구현·외부 계약·소유자 의도가 각각 자기 질문에만 권위를 갖는다.

**담을 것.** 세 질문 권위 분리 표 · 후보별 내부 증거표(파일로 저장하지 않음) · 버전 우선 외부
조사(버전이 없으면 `버전 미확인`) · 확인 묶음 전 관찰/해석/결정 3갈래 preview · 종료 게이트.

**예상 장면.** 구버전 결제 SDK 저장소에서 "지금은 전체 환불만 한다"(관찰), "공급자 계약은
부분 환불도 지원한다"(외부 계약), "앞으로 지원할까?"(소유자 결정)가 한 문장으로 섞이지 않는다.

### U5 · split — 등급 0/1/2a/2b

**왜.** 작은 요청은 형식상 완전한 카드가 되지만 제품 결정(트리거·빈 상태·실패 동작)이 빠질 수
있고, 최상위 기획과 카드 분할 사이에 중간 규모 덩어리를 좁히는 과정이 없다.

**목적지.** 요청의 카드 네 필드가 유일해질 때까지 필요한 만큼만 묻고, Layer 0가 열리는 순간
멈춰서 위로 보낸다.

**담을 것.** 유지보수 2단계 뒤 등급 판정.

| 등급 | 조건 | 행동 |
|---|---|---|
| 0 | 정확한 기존 출처에서 카드 네 필드가 각각 한 가지 문장으로 써진다 | 질문 없이 계속 |
| 1 | 한 묶음의 답으로 네 필드가 유일해진다 | 추천 붙은 묶음 하나 + 경계가 갈리는 경우에만 구체적 시나리오 하나 |
| 2a | 실제 제시할 선택지 또는 실제 답 하나라도 Layer 0 필드를 바꾸거나, **ADR 3조건(되돌리기 어렵다 · 비자명하다 · 실제로 대안을 검토했다)을 통과하는 결정을 요구한다** | 카드 없이 소유 단계로 환류. **2b와 겹치면 2a가 이긴다** |
| 2b | Layer 0는 보존되는데 한 묶음 뒤에도 카드 필드에 유효한 문장이 둘 이상 | 같은 유지보수 대화에서 다음 프런티어 묶음을 계속 |

Layer 0 필드는 product의 정체성·능력 목록·경계·성공 판정과 arch의 구성요소·stack·코드 구조·
데이터·검증 창구다. 판정 입력은 **실제 제시할 선택지와 실제 답뿐**이다(companion 기준).
사용자가 제시하지 않은 답을 자유롭게 쓰면 **그 실제 답으로 등급을 다시 판정한 뒤** 카드를 쓴다.
"덩어리"는 규모 이름이 아니다 — 페이지든 그 안의 모달·목록·필터든 위 조건으로만 판정한다.

**2b의 착지와 그 지식이 상위로 올라가는 길** (소유자 지적 반영):

```
2b의 모든 답은 카드 네 필드 중 하나에 착지한다
  └ 착지하지 못하는 답이 있으면 그것은 상위 소유이므로 2a다

착지 과정에서 새 용어가 확정되면 발견→갱신 표의 그 행으로 함께 착지시킨다
  · 「새 용어가 필요해짐 → glossary.md 1줄」
  이것은 규칙 정본이 공인한 수정 경로이지 split의 새 권한이 아니다 (F6의 명확화가 못박는다)

능력 설계 구역·새 기획 파일·새 상태는 만들지 않는다 (DR-20/21, 중간-C 반증)

이후 지식이 다음 세션에 닿는 경로:
  카드 → 구현 → 능력 폐쇄 → 능력 문서 검증 구역(현재 행위 · 진입점 · 함정)
  → 다음 세션의 work이 깊이 1 번호로 그 문서를 자동으로 읽는다 (DD-44)
```

**ADR은 착지 집합에서 뺀다 — request2 §4.3의 축소이고 그 이유는 구체적이다.** 발견→갱신 표에
"2b가 되돌리기 어려운 결정을 냈다"는 방아쇠를 가진 행이 없다. 가장 가까운 행은 「스택·모듈
경계·데이터가 **안 맞음** → arch.md (+ADR 검토)」인데, 2b의 답이 모듈 경계나 데이터를 건드리면
그것은 이미 Layer 0 필드 변화라서 **2a**다. 건드리지 않는 답은 arch 수준에서 "되돌리기 어렵다"를
충족하기 어렵다. 즉 `2b 안에서 ADR 3조건을 통과하는 결정`이라는 집합은 비어 있거나 2a와 같다.
표에 없는 방아쇠를 위해 표에 행을 더하는 것은 규칙 정본 변경이고, 이 라운드의 보존 추가 범위를
넘는다. 그래서 **ADR 3조건을 통과하는 결정을 요구하는 답은 위 등급 표에서 2a의 조건 자체로
들어간다** — 별도 예외 규칙이 아니라 등급 판정의 일부다. ADR 3조건의 판정과 작성은 arch가
이미 소유하고 있고, 그런 결정은 실제로 모듈 경계·데이터를 건드리므로 arch의 정상 실행이
맞는 응답이다.

**정직한 잔여**: 카드 폐쇄 전에는 그 의도가 카드 안에만 있다. 카드는 커밋되므로 소실은
아니지만, 능력 문서에 접히는 것은 폐쇄 뒤다.

**예상 장면.** "저장 버튼 라벨 변경"은 경량 차선이라 split에 오지 않는다. "필터 모달에 날짜
범위"는 묶음 하나 뒤 카드. "정산 페이지의 목록·필터·상세 모달 고도화"(관리자 정의·성공 판정은
기존 그대로)는 묶음 두세 번으로 카드들이 유일해질 때까지 좁혀지고, 그 과정에서 확정된 용어
하나가 glossary에 오르며, "새 관리자 역할이 필요하다"는 답이 나오는 순간 카드 없이 product로
올라간다.

### U6 · 검증 수렴과 루프 상속 (L-B′)

**왜 — 원문 대조로 확인한 두 공백.**

```
[공백 A] 같은 실패를 다시 알아보지 못한다
  회귀 목록은 완료 신호만 담고 어느 카드에서 왔는지 표시가 없다 (2단계)
  실패면 무조건 새 출처 id를 부여한다 (4단계)
  라우팅은 출처 id 최솟값 하나를 고를 뿐 과거와 대조하지 않는다 (6단계)
  실패 이력은 영구 보존되지만(DD-30) 어느 규칙도 그것을 읽지 않는다
  → 같은 완료 신호가 열 번 실패해도 열 개의 무관한 새 실패로 보인다

[공백 B] 알아봐도 이전 시도를 물려받지 못한다
  의존      수정 카드는 기본 `없음`
  읽을 것   유지보수 2단계의 후보 집합이 문서뿐이라 카드가 들어갈 수 없다
  승계 줄   질의가 `Covered cards` 밖 `.done.` 카드로 유계 — 폐쇄가 그 카드를 집합에 넣는 순간 사라진다
  함정 표   유일하게 열린 통로 — 기준선 표준 갱신 집합이 `Covered cards` 밖 카드를 입력으로 삼는다
            그러나 "수리한 실패를 함정으로 남겨라"는 문장이 없다 → 우연에 맡겨져 있다
```

**목적지.** 완료된 수리의 신호가 다시 실패하면 그것을 같은 계보로 알아보고, 다음 시도가 이전
시도가 반증한 것을 손에 쥔 채 시작하며, 두 번째 재발부터는 사람이 전체를 본다. 그리고 그
지식은 계보가 끝난 뒤에도 능력 문서에 남는다.

**담을 것.**

1. **label** — verify 2단계가 회귀 목록을 만들 때 각 완료 신호에 그 신호를 소유한 완료 카드
   번호를 붙인다. 메인이 목록을 구성하므로 번호는 이미 손에 있다.
2. **verifier 반환** — non-pass 회귀 항목의 카드 번호를 반환에 포함한다. 과거 이력은 계속
   받지 않는다 — label은 서사가 아니라 현재 신호의 식별자다(DD-48).
3. **유계 route 투영 (신설)** — 메인은 verify.md 본문 전체를 열지 않고, 이 계획이 새로
   정의하는 기계 투영만 쓴다. **이 투영은 신설이다** — 기존 resume의 유계 verify 투영은
   완료된 라우팅 값을 출력하지 않는다.
   범위는 **현재 검증 대상 key의 verify.md · 트리 루트 verify.md · 현재 회귀 묶음의 label
   카드가 속한 능력들의 verify.md** 셋이다. 회귀 묶음은 `의존` 1홉으로 교차 능력 카드의 완료
   신호를 담을 수 있으므로 셋째가 필요하다. 읽기는 프로젝트 역사가 아니라 **현재 묶음 크기에
   비례**하므로 DD-56의 이유를 지킨다. 이 투영은 정확한 경로 몇 개에 대한 기계 질의이며
   닫힌 폴더 투영이 금지한 카드 본문 읽기가 아니다.

   **출력 필드는 정확히 다섯이고 그 밖은 출력하지 않는다** — 파일마다 그 파일의
   `검증 대상 key`(트리 루트면 `product`, 능력이면 상태 접미사를 뺀 고정 능력 번호), 그리고
   실패 이력 항목마다 `출처 id` · `라우팅` 값 · 있으면 `수리 계보` · 있으면 `재관측`.
   `실패:`·`미검증:` 본문, 시나리오·실행·회귀·표준·잠정값 절은 출력하지 않는다.
4. **재발 판정과 기록** — 실패한 항목의 label(완료 카드 번호)이 그 투영이 낸 과거
   `라우팅: 수정 카드 <번호>` 값들에 **정확히 한 번** 나타나면 재발이다. root key는
   `<product | 고정 능력 번호>@<그 계보 최초 실패의 출처 id>`이며 폴더 rename에 흔들리지 않는다.
   재발 항목도 DD-30대로 **새 출처 id와 자기 `라우팅: 대기`를 가진 새 실패 이력 항목**이고,
   여기에 `수리 계보: <root key>`와 `재관측: <같은 root의 현재 최댓값+1>`을 함께 쓴다.
   **카드는 새 것이고 계보는 기존 것이다 — 둘은 다른 사실이다.**
   `재관측`은 동일 원인 실패 횟수가 아니라 **완료된 수리 경계의 현재 신호가 pass를 주지 못한
   verify 실행 횟수**다 — 그래서 미검증을 실패라고 오기하지 않으면서 같은 상한에 넣는다.
   중간 pass는 그 실행을 세지 않지만 최댓값을 지우지도 않는다. 한 실행에서 같은 root로
   돌아온 항목이 여럿이면 쓰기 전에 최댓값을 한 번 고정하고 전부에 같은 값을 쓴다.
   **줄 형식은 기존 항목에 두 필드를 `라우팅` 앞에 끼우는 것이다** — 필드 순서는 고정이고
   재발이 아닌 항목에는 두 필드가 없다:

   ```text
   - 출처 id: <id>; timestamp: <ts>; <실패: … | 미검증: …>; 라우팅: 대기
   - 출처 id: <id>; timestamp: <ts>; <실패: … | 미검증: …>; 수리 계보: <root key>; 재관측: <n>; 라우팅: 대기
   ```

   두 필드는 실패 이력 항목의 일부이므로 재검증의 verify.md 덮어쓰기에서 **기존 실패 이력과
   함께 보존된다**(DD-30) — 새 Record가 지우지 않는다. 재발 항목도 실패 이력 항목이므로
   **`New entries` 셈에 들어간다**(DD-41의 완성 판정이 그대로 성립한다).
   **판정 불가의 처분은 하나다**: 한 label이 둘 이상의 root로 풀리거나, root 있는 label과 없는
   label이 한 실행 결과에 섞이거나, 기존 항목의 두 필드가 해석되지 않으면 — 의미로 고르지
   않고 `수리 계보 판정 불가`와 정확한 항목·후보 key를 사람에게 보고하고 그 항목을 라우팅하지
   않는다.
5. **상속 — 라우팅이 지목하고 split이 `읽을 것`에 넣는다.**
   ```
   적용 조건: 실패한 항목이 회귀 신호이고 label(완료 카드 번호)을 가질 때
     주 시나리오·적대 입력 실패처럼 label이 없는 항목에는 상속 대상이 없다 — 현행 그대로다

   지목하는 집합 = { 그 항목의 label 카드 } ∪ { 이 계보의 과거 `라우팅: 수정 카드` 값에 있는 카드 전부 }
     재관측 0(첫 실패): 계보가 없으므로 label 카드 하나 — 그 신호를 만든 원 구현 카드다
     재관측 1:          label 카드는 그 계보가 라우팅했던 수정 카드다. 한 root가 `C1+C2`로
                        라우팅됐다면 둘 다 들어가므로 **최대 두 장**이고,
                        재관측 2 이상은 카드를 만들지 않으므로 그 위로 자라지 않는다
     집합은 저장된 값(label과 과거 라우팅 값)에서 기계적으로 나온다 — 새 필드를 만들지 않는다

   split의 유지보수 2단계가 이 경로들을 `읽을 것`에 넣는다 — 그 단계의 후보 집합에
   "verify 라우팅이 지목한 카드 경로"를 더하는 것이 이 계획의 추가분이다
   ```
6. **재관측 1 — 카드 하나** (D16′).
   ```
   라우팅은 현행 그대로 수정 카드 하나 — 새 라우팅 값도, 새 카드 종류도 만들지 않는다
     완료 신호 = 실패 재현 절차 또는 미검증 이유가 해소됐음을 실행해 증명하는 점검 (현행 계약)
     접근 부재도 이 하나다 — 현행 "미검증 이유 해소" 수정 카드가 곧 접근 해소 카드다
     신호가 넓어 진단이 막히면 work의 기존 고착 탈출이 그 카드 앞에 조사 카드를 끼운다

   목적지는 "신호가 통과한다"가 아니라 **그 신호가 지키던 능력 서술이 참이 된다**로 쓴다
   ```

   **work의 트리거는 상속 그 자체다.** work은 verify.md를 읽지 않으므로 "이것이 재관측
   카드다"를 알 수단이 없다 — 그래서 계보를 알 필요가 없게 만든다:

   > `읽을 것`에 `devflow/tree/` 아래의 `.done.` 작업 카드 경로가 있으면 그 카드를 통독하고,
   > 구현을 시작하기 전에 기존 깨끗한 컨텍스트 진단을 먼저 소비해 원인 가설 1과 그 가설이
   > 맞을 때 관측될 예측 1을 진행 로그에 남긴다.

   `읽을 것`에 카드 경로가 들어오는 경로는 이 계획이 만드는 verify 라우팅 하나뿐이므로
   트리거는 정확히 상속이 일어난 자리에서만 발화한다. **work은 `수리 계보`도 `재관측`도
   모른다** — 계보 기계는 verify와 split 안에만 산다. 이 트리거는 재관측 1뿐 아니라 **최초
   실패의 수리 카드에서도 발화한다**: 소유자 지시(D21)가 "첫 번째 실패부터 더 나은 개선안을
   도출하라"이고, 이 트리거의 비용은 verify-origin 수리 카드 하나당 진단 한 번이다.
7. **재관측 2 이상 — 사람 관문.** `라우팅: 대기`를 유지하고 지금까지의 카드 번호·원 신호·
   관측 결과만 보고한다. 소유자 선택 전에는 새 실행·출처 id·카드를 만들지 않는다. 새 상태를
   만들지 않으므로 resume이 기존 우선순위대로 같은 보고를 복원한다. **비용은 정직하게 적는다**:
   `라우팅: 대기`는 전역 선행이므로 소유자가 미루면 다른 능력의 진행도 함께 멈춘다. 계보별
   미루기는 새 상태가 필요하므로 이번 범위 밖이다.
8. **폐쇄가 지식을 접는다.** 능력 폐쇄에서 검증 구역을 갱신할 때, 이번 폐쇄가 수리한 실패 중
   **재현 조건이 현재 코드에 남아 있는 것**은 `함정` 행(증상·재현 조건·원인·대신 할 것)의
   후보로 삼는다. 재현 조건이 코드에서 사라졌으면 적지 않는다 — 기준선 정본의 "이번 능력 코드
   범위에서 다시 확인된 것만 남긴다"를 그대로 지킨다. 이 배선이 없으면 그 지식은 계보가 끝나는
   순간(수리 카드가 `Covered cards`에 들어가는 순간) 승계 줄 질의에서 사라진다.
9. **규칙 정본 연결 3~5줄** — 실패 사다리 절이 verify 교차 폐쇄의 수리 계보와 재관측 2 이상
   사람 관문을 가리킨다. **새 사다리를 만들지 않는다.**

**예상 장면.**

```
02.3b-fix-timezone (C1) 완료 신호: 브라우저에서 3/1 00:00 KST 주문이 목록에 뜬다
  진행 로그: 가설 = 로컬→UTC 변환 누락 / 반증 = 서버는 이미 UTC. 실제 원인은 목록 쿼리의 반열린 구간
  통과 → 폐쇄 → 함정 행: 경계일 누락 / 로컬≠서버 TZ / 반열린 구간 / shared/time.ts의 toUtcRange

3주 뒤 다른 변경 뒤 재검증에서 그 신호가 다시 실패
  지금:   새 출처 id · 새 수정 카드 · 구현자는 다시 "TZ 변환이겠지"부터 시작한다
  L-B′:  "02.3b 수리의 첫 재발" · 새 카드의 `읽을 것`에 02.3b.done.md
          → 구현자가 반열린 구간이 이미 원인이었음을 알고 시작한다
          → 진행 로그에 가설·예측을 먼저 남긴다
  또 재발하면 카드를 발급하지 않고 계보 전체가 사람에게 간다
  무관한 새 실패 G는 02.3b의 재관측 수를 올리지 않고 정상 라우팅을 받는다
  통과하는 검증의 추가 실행·질문·commit은 0이다
```

**resume 무변경의 근거 (이 계획이 walk로 확정한다 — 구현 때 다시 판정하지 않는다).**

```
재발 항목은 새 출처 id + `라우팅: 대기`를 가진 실패 이력 항목이다
  → resume 표의 기존 행 "어느 verify.md든 실패 이력에 `라우팅: 대기`가 있음 → verify"가 그대로 받는다
재관측 2 이상의 사람 관문도 `라우팅: 대기`를 유지한다
  → 같은 행이 verify로 보내고, verify가 재관측 값을 보고 보고만 한다. 새 상태가 없다
resume의 유계 verify 투영은 활성 상태만 출력하면 된다
  → resume은 라우팅하지 않고 단계만 고르므로 `수리 계보`·`재관측`을 출력할 이유가 없다

중단 지점 셋을 걸었다
  ① 재발 판정 뒤 항목 쓰기 전 사망  → verify.md 무변경 → 다음 verify가 같은 투영으로 다시 판정
  ② 항목 쓰고 라우팅 전 사망        → `라우팅: 대기` → 위 기존 행이 복원
  ③ 카드 생성 뒤 계획 커밋 전 사망  → 층 열기 마커와 계획 커밋의 기존 복구가 그대로
```

따라서 **resume은 이번 라운드에서 diff 0이다.** 독립 감사가 이 walk를 뒤집으면 그것은 감사
소견이지 계획이 남긴 미결이 아니다.

**강등 조건.** 문자 실행 워커의 walk에서 "과거 실패 → 수정 카드 번호 → 현재 실패한 회귀
번호 → 계보 root·재관측·상속 대상"을 **모든 중단 지점에서 유일하게 복원하지 못하면** L-B′를
억지로 통과시키지 않고 축 3 전체를 L-A로 강등하고 배포 파일을 고치지 않는다. 구현자의 자기
walk는 **조기 강등만** 할 수 있고, L-B′를 **유지한 채 출고하는 판정**은 §9.4의 「수리 계보」
특화 판정(문자 실행 워커 + 기계 fixture)이 소유한다.

### U7 · `.stale.` 재분할의 지식 착지 (D22)

**왜.** 상위 결정이 진행 중이던 카드를 뒤집으면 그 카드는 `.stale.`이 되고, 며칠어치 실행
증거를 담은 진행 로그가 어느 소비자에게도 닿지 않는다. 승계 줄 질의는 `.done.` 카드만 보고,
교체 카드의 `읽을 것`에도 아무도 넣지 않는다.

**그런데 이것은 새 장치가 필요한 문제가 아니다.** 두 사실이 그것을 말한다.

```
① split은 이미 `.stale.` 카드를 읽는다
   재분할 절: "마커가 정확히 지목한 폴더와 `.stale.` 카드, 출처 절, … 를 읽는다.
              이 목록 밖의 문서는 열지 않는다"
   → 읽기는 이미 있고 착지 지시만 없다

② 승격에는 그 착지 절차가 있고 재분할에만 없다
   승격 9단계: "진행 로그가 있었다면 먼저 전역 결정을 발견→갱신 표로 착지시킨다. …"
   → 비대칭이다
```

**목적지.** 무효가 된 카드의 실측이 표가 지정한 거처로 나가고, 무효가 된 결론은 나가지 않는다.

**담을 것.** split 재분할 절, 교체 카드를 만들기 전에 한 줄:

> 무효 카드의 진행 로그에서 발견→갱신 표의 행에 해당하는 것을 먼저 그 행으로 착지시킨다
> (승격 9단계와 같다). 그 착지는 별도 구속 결정 커밋이며 이 층의 계획 커밋에 동승하지
> 않는다. 그 밖의 내용은 옮기지 않는다.

**표가 필터인 이유.** 살아남을 관측만 표에 행이 있다.

```
브라우저 도구가 다운로드 완료를 관측 못 함 → 「확인 수단이 새로 생기거나 바뀜」 arch.md verify_channel
SDK의 금액 필드가 문자열이라 정밀도가 깨짐  → 「공용 계약에 대해 코드에서 확인된 것」 기명 미결/위험/ADR
10만 행에서 메모리 300MB → 청크로 40MB     → 「상위 문서의 잠정값이 실측됨」 arch.md 잠정값 행 교체
Excel 로케일에는 UTF-8 BOM이 필요           → 표에 행이 없다 → 나가지 않는다 (CSV 자체가 사라졌으므로 옳다)
```

**정직한 잔여.** 표를 빠져나가는 것은 "이 능력 안의, 공용 계약도 확인 수단도 잠정값도
코딩 방식도 아닌, 실행으로만 아는 함정"뿐이다. 그 거처는 능력 문서 `함정` 표이고 그 표는
폐쇄가 **현재 코드에서 재확인해** 쓴다. 재현 조건이 코드에 남아 있으면 다음 폐쇄가 잡고,
남아 있지 않으면 다음 구현자가 그 코드를 다시 짜야만 만나며 그러면 앞의 경우가 된다.
**따라서 잔여의 등급은 「조용한 자료 소실」이 아니라 「한 사이클 늦은 재발견」이다.**

**예상 장면.** "정산은 CSV 대신 회계 API로 간다"는 결정으로 03.4가 `.stale.`이 되면, split이
교체 카드 03.4b를 만들기 전에 위 세 줄을 각각 arch.md의 verify_channel·위험·잠정값 행으로
먼저 착지시킨다. BOM 발견은 갈 곳이 없어 그대로 `.stale.` 카드에 남는다 — 그것이 옳다.

## 7. 기존 경계 대조 — 무엇을 열지 않았는지

### 7.1 이 계획의 진단이 원문 대조에서 확인된 것

§6 U6의 「왜」 블록이 그 대조 결과다. 공백 A는 확정이고, 공백 B는 **통로가 하나 열려 있으나
배선이 없다**로 정정했다(첫 진술 "물려받지 못한다"는 과했다). 그래서 U6-5가 계보 안의
상속이고 U6-8이 계보 밖으로 나가는 배선이다.

### 7.2 능동 재검토 ↔ DD-22·DD-23 회고

| | 능동 재검토 | 회고 |
|---|---|---|
| 시점 | 구속 결정 **전** | 능력·제품이 실제로 닫힌 **뒤** |
| 입력 | 현재 사실·성공 판정·확인된 제약 | devflow 산출물 전체 + 긴장 증거 |
| 산출 | 후보 하나의 비교(또는 무출력) | 소견 — 판정이 아니다 |
| 역할 | 없음(메인의 내부 판단) | retrospector |

DD-22의 기록된 이유("AI는 자기 기획을 의심하지 않는다")를 **반박하지 않는다** — 재검토는
구속 전에 같은 병을 한 번 더 막을 뿐, 사후 평가를 대신하지 않는다. 질문·카드마다
retrospector를 부르지 않고 strain evidence를 새로 만들지 않는다. 사용자가 대안을 보고 다시
선택하면 그 묶음은 닫히고 재귀 탐색하지 않는다.

### 7.3 2b의 glossary 착지 ↔ 「대상 소유 스킬은 고정이다」

규칙 정본은 코어 문서 수정 경로를 둘로 연다 — "**이 절차** 또는 해당 스킬의 재실행". 「이
절차」는 문서 계층 절차와 발견→갱신 표이고, 표 아래에 "위 표에 따른 갱신(**잠정값 교체, 신호
문구 수정 등**)은 그 자체로 공인된 수정 경로다"가 못박혀 있다. 괄호 안의 두 예시가 결정적이다 —
잠정값 표와 신호 문구는 각각 arch.md와 작업 카드가 소유하는데 **그 갱신을 실제로 수행하는 것은
work의 환류다.** 즉 정본은 이미 "소유 스킬이 아닌 세션이 표를 밟아 한 줄을 고치는 것"을
정상 경로로 보고 있다. 따라서 split이 표의 행을 밟아 glossary 한 줄을 쓰는 것은
**새 예외가 아니라 이미 공인된 경로**다.

다만 바로 뒤 문장 "대상 소유 스킬은 고정이다"가 그 경로까지 막는 것으로도 읽힌다 — 두 독해가
서로 다른 행동을 낳는다(2b가 용어를 확정하지 못해 과잉 환류하거나, 쓰거나). 그래서 F6에
명확화 한 줄을 둔다: **그 고정은 문서를 다시 쓰는 재실행의 소유를 말하며, 표가 지정한 한 줄
갱신은 그 표를 밟는 스킬이 수행한다.** 이 명확화는 새 권한을 주는 것이 아니라 이미 있는 두
문장의 관계를 하나로 줄이는 수렴형 수리다.

**따라오는 비용을 감춘다면 부정직할 것이다**: glossary.md 한 줄은 `Design head`(product·arch·
glossary)를 바꾸므로 전 능력의 설계 진술이 가설로 강등되고, 다음 resume이 arch·adopt의 설계
구역 재도출로 라우팅한다(Layer 0 인터뷰는 하지 않고 확인 묶음 한 번). 이는 **기존 성질**이며
새로 생기는 것이 아니다 — 다만 2b가 그 경로를 더 자주 밟게 되므로 백로그 관찰로 등재한다(F16).

### 7.4 D22 ↔ DR-12 · 승격 9단계

DR-12는 "문서 간 모순을 1~4단계 **대신** 발견→갱신 표로 보내는 재서술"의 기각이다. D22는
1~4단계를 대체하지 않는다 — 4단계(재분할) **안에서** 무효 카드의 관측을 표로 보낼 뿐이고,
1~4단계의 부수 효과(`.stale.` 표시·재분할)는 그대로다. 재제안이 아니다.

**부수 관찰(이번에 고치지 않는다)**: 승격 9단계 자신도 표 착지가 11단계의 계획 커밋에
동승하는지가 두 갈래로 읽힌다(11단계의 열거에 없으므로 별도여야 하나 명시가 없다). 이번에
새로 넣는 D22 문장은 그 모호성을 갖지 않게 커밋 경계를 명시하되, 기존 승격 문장은 건드리지
않고 백로그 관찰로만 등재한다(F16) — 봉합된 것을 이 라운드에서 다시 열지 않기 위해서다.

### 7.5 상속 ↔ DR-31 · DD-56 · DD-48 · DR-08

| 기록 | 기각·결정 사유 | 이 계획이 걸리지 않는 이유 |
|---|---|---|
| DR-31 | "미수확 카드의 진행 로그 전문 읽기는 실현 불가(카드마다 수백 줄) / 최근 N장은 N이 판단어" | 상속은 계보가 **기계적으로 지목한 정확한 카드 최대 두 장**이다. 전량도 아니고 N도 아니다 |

### 7.6 F-A ↔ 기존 failure route

최초 non-pass의 **신호 계약 네 요소는 한 글자도 바뀌지 않는다**. verifier가 `fail`에 재현
절차를 담고, 결과를 얻지 못하면 원인을 추측하지 않고 `미검증`을 반환하며, verify가 둘 다
수정 카드로 라우팅하고, DD-24가 그 재현 절차를 완료 신호로 승격한다. L-B′의 **재관측 계수는
수리가 완료된 뒤**부터만 센다. 조사 카드를 `라우팅:` 값에 연결하지 않고 두 단계 route 상태도
만들지 않는다.

**최초 실패에서 유일하게 더해지는 것**은 그 수정 카드의 `읽을 것`에 신호를 낸 완료 카드 경로
하나가 들어가는 것이다(U6-5). 그것은 F-A의 네 요소 — 재현 절차 · `fail`/`미검증` 구분 ·
라우팅 값 · 완료 신호의 출처 — 어디에도 닿지 않고 카드의 읽기 집합만 정확히 한 경로 넓힌다.
이 문장을 "F-A를 바꾼다"로 읽지 않도록 여기 명시한다.

### 7.7 D13-A ↔ 백로그 「Layer 0 초안 확인 상태의 디스크 표현」

이 보류 항목은 열지 않는다. A는 디스크 표현을 만들지 않으므로 그 선택을 부분적으로도 열지
않는다. 중간 요약은 대화 산출이며 복구를 약속하지 않는다 — 세션이 끊기면 마지막 확정 Layer
0에서 다시 도출하고, 답을 추측하지 않고 다시 묻는다. **이 계획은 그것을 "소실 0"이라고
표현하지 않는다.**

### 9.4 독립 렌즈 넷 + 특화 판정 항목 넷

**렌즈는 감사 지침 §3-3의 넷뿐이다 — 새 렌즈 이름을 만들지 않는다**(§6: "렌즈는 3절 3항의

| ① 반증자 | 규칙 충돌·판단어·죽은 참조·기각 계보 무반박 재제안 (문장 대 문장 인용) |

**§5 종료 조건 판정 (지침 §5, 사전 고정한 문구 그대로).** 3차 패스의 소견 둘은 전부 수렴형
수리(조건 통합 하나 · 죽은 참조 교체 하나)이고 해석을 새로 여는 문장이 없다.

4차 패스는 문장을 다듬는 라운드가 아니라 **렌즈를 바꾼 라운드**였다(지침 §3-3: 같은 렌즈의
재실행은 같은 경로만 다시 걷는다). "이 계획이 정합한가"에서 "이것만으로 구현할 수 있는가"로
질문을 바꾸자 여섯이 나왔고 — 그중 21·22·23·24는 **1~3차 패스가 구조적으로 볼 수 없던
클래스**(문장 사이의 일관성이 아니라 구현자에게 필요한 정보의 부재)다. 전건 수리했다.

**종료 선언.** 규칙 충돌 클래스 0 · 소실 경로 클래스 0 · 설계 판단 미결 0 · 유예 항목 0.
4차 패스의 여섯 수리는 전부 **추가**(원재료 지도 · 형식 명세 · 트리거 교체 · 네 확정)이고
해석을 새로 여는 문장이 없다. 5차 패스는 같은 두 질문을 다시 물을 뿐이므로 열지 않는다.
**다음 검증 수단은 이 텍스트가 아니라 구현과 §9.4의 독립 감사다.**

**§5 종료 조건 판정**: 이 패스는 **계획 텍스트에 대한 자기 검토**이므로 규칙 충돌 클래스는
위 3·4·5·6의 수리로 닫았고 남은 소견은 없다. 소실 경로 클래스 0. 수리는 전부 수렴형(교체·
철회·정정·대칭 회복)이며 해석을 새로 여는 문장이 없다. **다만 이 판정은 자기 검토의 것이다** —
독립 감사(§8-13)가 그 자리에서 다시 평가한다. 기계 검사는 현 상태에서 전부 통과(현재 변경은
라운드 기록 하나뿐이므로 배포 검사에 닿지 않는다).

**한계**: 실전 사이클 0회 — §10의 측정 항목은 전부 예측이다. L-B′의 기계 복원 유일성은
텍스트로 판정할 수 없고 §9.1의 fixture와 렌즈 ③의 몫이다. 맷 포콕 snapshot 원문은 재실사하지
않았다(요청서 §0.4의 커밋 고정만 확인).
