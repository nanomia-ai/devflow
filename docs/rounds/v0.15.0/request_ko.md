# v0.15.0 요청서 — 사실은 먼저 찾고, 결정만 묻는다

상태: **다음 설계 계획의 입력 요청서** · 작성 2026-08-14 · 배포 스킬 변경 전

이 문서는 구현 계획도 승인안도 아니다. 소유자와 대화를 이어가며 요구·선택지·검증 결과를
다듬고, 다음 `plan_ko.md`가 이 요청서를 입력으로 구현 가능한 문장을 설계한다. 지금 단계에서
바뀐 배포 동작은 없고 버전도 올리지 않는다.

**보존 원칙.** devflow는 여러 차례의 적대 검증과 수리로 현재의 문서 소유권·상태 전이·commit
경계·복구 체계를 얻었다. 이번 요청의 기본 방향은 그 시스템을 교체하는 것이 아니라 그 위에
기획 증거와 작은 범위 보강을 더하는 것이다. 후속 계획 작성자는 기존 문장 하나를 바꾸기 전에
그 문장이 막는 실패 경로와 연결된 DD/DR을 찾아야 한다. 기존 결정을 뒤집는 편이 실제로 더
낫다고 판단해도 요청서나 계획에 기정사실로 넣지 않는다. 기록된 채택 이유를 먼저 반박하고,
보존안과 전환안의 효과·비용·이관·실패 경로를 나란히 제시해 **소유자가 선택한 뒤에만** 전환안을
계획에 넣는다. 명백한 자기모순 수리 외의 판단 변경을 AI가 승인으로 대체하지 않는다.

---

## 0. 이 요청서는 무엇인가

v0.15.0에서 `product`·`arch`·`adopt`의 기획 깊이를 높이는 방법을 정한다. 함께 드러난
작은 범위 기획의 공백 때문에 `split`의 유지보수 진입도 접합부만 다룬다. 별도 축으로
`work → 검토 → verify → 수정 카드`가 이미 남기는 결과와, 그 결과를 다음 반복이 소비해
수렴하는 규칙의 공백도 다룬다. 목표는 질문이나 검증을 많이 하는 것이 아니다. AI가 스스로
확인할 수 있는 사실은 먼저 확인하고, 실패했다면 이미 얻은 증거를 버리지 않은 채 다음 시도의
질을 높이며, 소유자만 내릴 수 있는 결정만 짧고 정확하게 묻는 것이다.

이 요청서가 다음 계획 세션에 주는 것은 넷이다.

1. **왜** — 현재 스킬의 어느 문장이 어떤 실패 경로를 남기는가.
2. **무엇을** — 어느 파일의 어느 절에 어떤 동작을 더하거나 바꾸는가.
3. **무엇을 사는가** — 그 문장이 어떤 오판·질문 낭비·지식 소실을 막는가.
4. **어떤 결과가 보여야 하는가** — 구현 뒤 시나리오에서 무엇이 관측되어야 성공인가.

### 0.1 한 문장

**맷 포콕의 결정 프런티어와 “사실은 AI의 몫, 결정은 사용자의 몫”, 좁고 재현 가능한 실패
신호를 devflow 안으로 들이되, 별도 조사 스킬·별도 조사 문서·무제한 인터뷰·전역 TDD는
들이지 않고 기존 Layer 0·깨끗한 역할·디스크 복구 위에 유계 보강한다.**

### 0.2 차가운 시작 — 다음 AI가 먼저 알아야 할 것

devflow는 코드가 아니라 AI가 문자 그대로 실행하는 프롬프트 묶음이다. 새 프로젝트는
`product → arch → design(선택) → split`, 기존 코드가 있는 프로젝트는 `adopt → split`로
들어온다. `product.md`와 `arch.md`는 이후 모든 작업이 다시 읽는 Layer 0이고, 능력 문서는
Layer 0에서 태어나 구현·검증을 거치며 자란다. 그래서 기획 인터뷰가 조금 부족한 문제와
Layer 0가 계속 흔들리는 문제는 같은 등급이 아니다. 이번 변경은 전자를 보완하면서 후자의
안정성을 그대로 지켜야 한다.

현재 역할은 다음과 같다.

| 단계 | 현재 소유권 | 이번에 건드리지 않는 경계 |
|---|---|---|
| `product` | 문제·해결 방식·능력 구성·경계·성공 판정·화면/창구 | 스택·DB·프레임워크를 결정하지 않는다 |
| `arch` | 구성요소·스택·코드 구조·데이터·검증 창구 | 제품의 문제·능력·성공 판정을 조용히 바꾸지 않는다 |
| `adopt` | 기존 코드에서 Layer 0와 능력 설계 구역 역산 | 기존 코드 전체를 재기획하거나 과거 카드를 소급 생성하지 않는다 |
| `split` | 한 층의 작업 카드와 실행 제안 | 구현 방법을 쓰지 않고 `목적지·왜·금지·완료 신호`까지만 쓴다 |

### 0.3 이 요청서의 권위와 변경 규칙

- 이 파일은 다음 계획의 입력 기록이며 배포 계약이나 구현 승인이 아니다.
- 결정 원장의 `확정`만 후속 계획의 선택으로 쓸 수 있다. `권장`과 `열림`은 계획·구현 세션이
  임의로 확정하지 않는다.
- 소유자가 방향을 바꾸면 기존 문장을 조용히 덮지 않는다. 결정 원장에서 이전 안과 바뀐
  이유를 함께 남긴다.
- 구현이 시작되면 `_ko`를 먼저 고치고 영문에 번역한다. 이 요청서는 번역 대상이 아닌
  한국어 전용 라운드 기록이다.
- 이 요청서 자체는 `docs/design.md`의 기존 결정 행을 하나도 움직이지 않는다. 후속 계획이
  소유자에게 승인된 뒤에도 기본은 기존 결정을 보존하는 추가 결정이다. 기존 결정을 뒤집는
  선택지는 해당 행의 기록된 이유를 반박하고 소유자가 전환안을 명시적으로 고른 경우에만,
  기존 계보의 `replaced`·`partially corrected` 규칙까지 포함해 계획할 수 있다.

## 1. 소유자가 원하는 것

이번 라운드는 “리서치를 추가하자”보다 넓고, “맷 포콕 흐름을 이식하자”보다 좁다.

### 1.1 얻고 싶은 것

1. 사용자가 `/research` 같은 별도 순서를 기억하지 않아도 된다.
2. 사용자가 조사를 명시하면 현재 기획 단계가 자연스럽게 수행한다.
3. 사용자가 말하지 않아도 현재 결정을 바꿀 수 있는 사실이 비어 있으면 AI가 먼저 찾는다.
4. 새 프로젝트의 `product`와 `arch`, 기존 프로젝트의 `adopt`가 같은 원칙으로 움직인다.
5. 프로젝트 전체뿐 아니라 페이지·모달·리스트 같은 작은 범위도 필요한 만큼만 기획한다.
6. 작은 범위 때문에 맷 포콕식 전수 질문이나 엄격한 검증을 매번 돌리지 않는다.
7. 다음 세션의 AI가 “무엇”뿐 아니라 “왜”와 “바라는 결과”를 읽어 소유자의 의도를
   과소해석하지 않는다.
8. 결과를 낸 뒤 사실·결정·검증을 다시 대조하는 루프가 사람 개입 없이 가능한 곳까지 돈다.
9. devflow의 강점인 고정 Layer 0, 능력 문서, 카드 상태, 검증 창구는 약해지지 않는다.
10. 현재 검토·검증 루프가 이미 남기는 기록을 정확히 인정하고, 없는 문제를 만들지 않는다.
11. 같은 실패를 고친 결과가 다시 깨지면 새 실패처럼 처음부터 반복하지 않고 이전 신호·수리·
    시도 수를 다음 선택이 소비한다.
12. 정상 통과 경로에는 반복 실행·새 사용자 질문·새 기록 파일을 추가하지 않는다.

### 1.2 원하지 않는 것

- `/grill → /research → /domain-modeling → /product`를 사용자가 손으로 이어 붙이는 흐름.
- 간단한 CLI나 버튼 하나에도 긴 인터뷰를 강제하는 흐름.
- 조사할 것이 없는데 “최신 사례”를 찾으며 토큰과 시간을 쓰는 흐름.
- 조사 때마다 저장소에 임의의 Markdown 노트를 남기는 흐름.
- 시장 수요·사용자 고통·조직의 정책을 웹 검색으로 대신 결정하는 흐름.
- 외부 문서의 최신 설명을 오래된 브라운필드 의존성의 실제 계약으로 착각하는 흐름.
- 하위 단계가 조사 결과를 구실로 product의 능력·경계·성공 판정을 조용히 바꾸는 흐름.
- 조사 서브에이전트가 다시 조사 서브에이전트를 낳는 재귀 위임.
- “프런티어가 빌 때까지”를 핑계로 모든 가능한 질문을 캐는 무제한 기획.
- 모든 기능과 모든 수정에 red-green 순서·최소 재현·가설 3~5개를 강제하는 전역 TDD/진단 절차.
- 깨끗한 reviewer·verifier에게 과거 실패 이력을 주어 독립 판단을 오염시키는 흐름.
- 별도 `repair.md`·수리 컨트롤러 역할·무제한 자동 수정처럼 새 상태 기계를 먼저 만드는 흐름.
- 아직 존재하지 않는 수정 카드를 미리 승인한 것으로 간주해 현재 카드별 승인을 우회하는 흐름.

### 1.3 직전 라운드의 순서와 이번 소유자 지시

v0.14.2 리포트의 다음 순서는 `실전 → 정본 소비자별 분할(D11) → 중단 복구 비례성`이었다.
이번 소유자 지시는 `docs/rounds/v0.15.0`을 열어 기획 깊이와 조사 결합을 먼저 설계하라는
새 입력이다. 이 요청서를 만드는 일은 그 순서를 덮지 않는다. 다만 v0.15.0을 실제 배포할 때는
다음 둘을 명시적으로 받아들여야 한다.

- v0.15.0은 D11과 섞지 않는다. 조사 규율과 정본 분할을 같은 릴리스에 넣으면 어느 축이
  프롬프트 성능을 바꿨는지 알 수 없다.
- 실전 부재는 사라지지 않았다. 아래 점수와 결과는 설계 예측이며, 실제 프로젝트 한 사이클이
  관측값으로 교체하기 전에는 효율 향상을 실측 사실로 쓰지 않는다.

## 2. 현재 상태 진단

### 2.1 잘하는 것과 비어 있는 것

| 단계 | 현재 강점 | 현재 공백 | 구체적 실패 경로 |
|---|---|---|---|
| `product` | 여섯 판단을 고정하고 능력 수에 따라 질문량을 조절한다. 질문은 묶음이고 추천 기본값이 있다 | 질문이 “AI가 찾을 사실”인지 “사용자가 정할 결정”인지 가르지 않는다 | API·규정·도메인 사실이 비어 있음 → AI가 사용자에게 묻거나 기억으로 기본값을 제안 → 사용자가 추측에 동의 → product.md가 잘못된 전제를 오래 보존 |
| `product` | 능력마다 제거 질문을 해 MVP를 줄인다 | 결정 의존 순서를 명시하지 않는다 | 아직 해결 방식이 정해지지 않았는데 경계 질문이 같은 묶음에 섞임 → 앞 답이 뒤 질문을 무효화 → 다음 라운드에서 번복하거나 그대로 확정 |
| `product` | 정체성 문단과 성공 판정이 전체 목적과 결과를 보존한다 | 능력 한 줄이 기능 이름+설명에 머물 수 있다 | 다음 세션이 기능의 존재 이유를 잃음 → 이름이 가리키는 구현은 만들지만 어떤 성공 판정을 위해 필요한지 모르며 과소·과잉 구현 |
| `arch` | 구성요소부터 도출하고 스택 후보·추천·파생 결정을 묻는다 | 후보와 추천을 지지하는 최신 사실 획득 규칙이 없다 | 모델 기억 속 오래된 호환성·지원 정책으로 추천 → 소유자가 “추천”을 근거로 승인 → 첫 카드에서 비호환 발견·재설계 |
| `arch` | 실측할 수 없는 값을 잠정값과 해소 카드로 분리한다 | 지금 알아야 할 차단 사실과 나중에 실측할 잠정값의 경계가 없다 | 후보 자체를 무효화할 사실까지 잠정값으로 미룸 → 여러 카드가 잘못된 골조 위에서 진행한 뒤 해소 카드가 뒤집음 |
| `arch` | 검증 창구가 없으면 끝나지 않는다 | 창구를 “이름으로 정함”과 “실제로 쓸 수 있음”의 구분이 약하다 | 브라우저/명령이 있다고 서술했지만 현재 환경에서 실행 불가 → work가 검증 시점에 처음 멈춤 |
| `adopt` | 코드 우선·대표 흐름 추적·문서 필터로 브라운필드를 유계 역산한다 | 현재 동작, 외부 계약, 소유자가 원하는 동작을 서로 다른 권위로 가르지 않는다 | 코드는 현재 동작을 보여 주고 외부 공식 문서는 제공자 계약을 보여 주는데 둘을 한 서열로 취급 → 코드가 외부 계약을 증명하거나 최신 문서가 구버전 동작을 증명하는 것으로 오독 |
| `adopt` | 코드가 답할 수 없는 경계·성공 판정은 소유자에게 묻는다 | 역산된 현재 동작이 원하는 제품 방향으로 굳어지는 위험을 대화에서 따로 드러내지 않는다 | 기존 코드의 우연한 제약을 product 경계로 역산 → 사용자가 차이를 알아채지 못한 채 전체 초안을 승인 → 과거 구현이 미래 의도로 승격 |
| `split` | 유지보수 요청을 기록한 뒤 현재 흐름을 추적하고 정확한 카드 필드를 쓴다 | 페이지·모달·리스트 같은 작은 범위의 의도 완성도를 점검하는 경량 단계가 없다 | 요청 문장만으로 그럴듯한 목적지를 만들 수 있음 → 카드가 형식은 완전하지만 트리거·빈 상태·실패 시 행동 같은 제품 결정이 빠짐 → 구현 후 리뷰가 누락을 처음 발견 |

### 2.2 공통 원인

공통 원인은 조사 도구의 부재가 아니다. **미지수를 누가, 언제, 어떤 증거로 닫는지에 대한
분류가 없다.** 그 결과 세 가지가 섞인다.

1. 환경·코드·공식 문서가 답할 수 있는 사실.
2. 실행해 보아야만 답할 수 있는 사실.
3. 소유자의 가치·위험 감수·제품 의도에 따라 달라지는 결정.

이 셋을 모두 질문으로 보내면 사용자가 추측을 대신한다. 모두 AI가 답하면 AI가 제품을 대신
결정한다. 모두 조사 카드로 보내면 Layer 0가 약해지고 간단한 기획이 느려진다.

### 2.3 작은 범위 기획 공백은 실제로 존재하는가

존재한다. 현재 `split`은 다음 두 게이트가 강하다.

- 목적지를 한두 문장으로 쓸 수 없으면 사용자에게 묻는다.
- 사실 미지수가 목적지·완료 신호를 추측으로 만들면 조사 카드를 둔다.

그러나 **한두 문장으로 쓸 수 있는 것과 제품적으로 충분한 것은 같지 않다.** 예를 들어
“필터 모달에서 날짜 범위를 선택할 수 있다”는 목적지는 문법상 완전하지만 다음 결정은
여전히 비어 있을 수 있다.

- 적용 버튼이 필요한가, 선택 즉시 반영하는가.
- 닫았다 다시 열면 미적용 선택을 복구하는가.
- 빈 범위·역전 범위·시간대 경계를 어떻게 다루는가.
- 리스트 결과가 0건일 때 어떤 상태를 보여 주는가.

이 중 무엇이 중요한지는 요청마다 다르다. 그래서 전체 체크리스트를 카드마다 붙이는 것도
오답이다. 필요한 것은 누락 목록이 아니라, **현재 목적지를 바꿀 미결정이 있는지를 한 번
판정하고 있을 때만 짧게 묻는 경량 기획**이다.

### 2.4 `research`를 새 사용자 스킬로 만들면 왜 부족한가

별도 스킬은 발견성 문제를 사용자에게 돌린다. 더 큰 문제는 실행 신뢰성이다. 맷 포콕
저장소의 2026-07~08 실사용 보고에도 다음 문제가 확인되어 있다.

- [`ask-matt`가 대상 SKILL.md를 열지 않고 단계를 건너뛰라고 한 사례 #614](https://github.com/mattpocock/skills/issues/614):
  라우터의 요약이 실제 절차를 대신하면서 중요한 spec 단계를 건너뛰었다.
- [`grill-me`가 `grilling` 없이 설치되어 동작하지 않은 사례 #685](https://github.com/mattpocock/skills/issues/685):
  별도 스킬 간 의존을 패키지 규약이 보장하지 않는다.
- [`grilling` 설명에 기록된 간접 로드 실패](https://github.com/mattpocock/skills/blob/8b78b531ab965735c5dc74f6f7a219e1e37326df/docs/productivity/grilling.md):
  `grill-with-docs`가 이름을 적어도 하위 primitive가 실제로 로드되지 않는 문제가 여러
  하네스와 모델에서 보고됐다.
- [`research` 설명에 기록된 재귀 위임·정지 조건·죽은 조사 파일 문제](https://github.com/mattpocock/skills/blob/8b78b531ab965735c5dc74f6f7a219e1e37326df/docs/engineering/research.md):
  한 조사에서 중복 에이전트가 생기고, 읽기 종료 기준이 없고, 나중 세션이 조사 파일을
  자동으로 읽지 않는다.
- [`wayfinder`가 사람 결정을 AI 추천으로 닫은 사례 #540](https://github.com/mattpocock/skills/issues/540):
  조사·prototype·사람 인터뷰라는 유형이 실행 순간의 게이트가 아니면 주변의 “계속 해결”
  문맥이 결정을 삼킨다.

이 사례들은 맷 포콕의 발상이 나쁘다는 증거가 아니다. **좋은 primitive를 여러 스킬의 이름
연결에 의존시켰을 때 문자 실행이 흔들린다**는 증거다. devflow는 이미 상대 경로로 읽는
정본 companion과 소비자 검사를 갖고 있으므로, 사용자 진입점이 아닌 companion이 더 맞다.

### 2.5 현재 검토·검증 루프는 정말 결과를 남기지 않는가

아니다. “reviewer와 verifier가 결과를 남기지 않아 같은 일을 반복한다”는 진단은 절반만 맞고,
그대로 설계 근거로 쓰면 기존 체계를 잘못 뒤집는다. **두 역할은 의도적으로 무상태지만, 그
역할을 부르는 바깥 절차는 이미 강한 상태를 남긴다.**

| 층 | 현재 남는 것 | 다음 반복이 이미 쓰는 방법 | 정확히 비어 있는 것 |
|---|---|---|---|
| `work` 구현 | 점유 카드의 진행 로그, 실패한 실행 결과, 가설과 반증, wip checkpoint | 세션 재개 지점, 같은 가설·같은 오류 두 번의 고착 탈출 | verify에서 생긴 같은 증상의 여러 수리 카드가 한 반복 계보라는 판정 |
| reviewer | 지적은 현재 대화로 돌아오고 즉시 수정·재검토, diff가 바뀌면 완료 신호 재실행 | 한 work 호출 안에서 최대 세 검토 순환 | 해소된 지적의 영구 목록. 이것은 깨끗한 검토자에게 줄 입력도 아니며, 현재 진행 로그가 필요 결정·실행 결과를 기록함 |
| verifier | 통과/실패/미검증과 재현 절차를 메인에게 반환 | 메인이 같은 실행에서 verify.md와 새 출처 id를 기록 | verifier 자신은 과거를 읽지 않음. 이는 편향 제거 자산이므로 결함이 아님 |
| `verify` 메인 | verify.md의 revision·실패 이력·출처 id·라우팅·실행 근거, 수정 카드 | 실패마다 수정 카드, 재현 절차를 완료 신호로 승격, 완료 카드 신호를 이후 회귀에 포함 | 새 출처 id가 앞선 어느 수리 카드의 같은 신호 재발인지 연결하는 기계 규칙 |
| 재폐쇄·resume | 폴더 전체 회귀 재실행, 대기 라우팅과 중단 상태 재개 | 고친 결함이 회귀 신호로 남아 다시 관측됨 | 같은 신호의 반복 횟수, A↔B 진동, 불안정 pass/fail을 보고 다음 행동을 바꾸는 수렴 판정 |

따라서 현재 루프는 **기억과 회귀 누적**을 이미 갖는다. 특히 검증 실패의 재현 절차가 수정
카드 완료 신호가 되고, 그 완료 신호가 이후 능력 전체 회귀에 들어가는 것은 “지난 결과를
반복하지 않도록 남긴다”는 소유자의 의도를 실제로 구현한다. 이 강점은 보존 대상이다.

부족한 것은 기록의 양이 아니라 **기록 사이의 계보를 소비하는 수렴 제어**다. 같은 증상을
수리한 카드의 완료 신호가 다시 실패해도 현재 문법은 새 출처 id와 새 수정 카드를 만들 수 있다.
출처 id는 유일성·순서를 보장하지만 같은 실패 정체성은 아니다. failure ladder도 일반 재투입과
work 안의 같은 가설 반복을 제한하지만, verify의 여러 폐쇄 사이에서 같은 신호가 되돌아오는
횟수를 세지는 않는다. 그래서 다음 경로가 열려 있다.

1. `F → fix A → F → fix B → F`가 각각 새 검증 실패와 새 카드로 보인다. 카드마다 실행 제안
   승인은 받으므로 **사람 없이 자동으로 도는 무한 루프는 아니지만**, 사용자가 매번 승인해도
   “같은 수리가 또 실패했다”는 별도 판정 없이 같은 종류의 카드를 계속 제안할 수 있다.
2. 전체 회귀가 `A 실패 → A 수정/B 손상 → B 수정/A 손상`을 계속 잡지만 진동이라는 판정이 없다.
3. 같은 신호가 pass/fail을 오가도 한 번의 통과가 안정성 증거인지 운 좋은 실행인지 가르지 않는다.
4. 원격 접근 불가는 한 점유 카드가 살아 있는 동안 `증거 대기`로 중복 실행을 막는다. 그러나
   그 카드가 완료된 뒤 다음 verify에서도 접근이 안 되면 새 미검증과 다음 카드가 생길 수 있다.
   새 수렴안은 기존 증거 대기를 보존하면서 이 **순차 증식**에도 상한을 둬야 한다.

“역할에게 역사를 주자”가 해법은 아니다. reviewer와 verifier의 격리를 깨면 구현자가 한 설명과
이전 수리의 인상이 판정을 색칠한다. 역사는 메인·verify.md·카드가 소유하고, 깨끗한 역할에는
그 반복에서 실행할 **현재 신호만** 주는 것이 현재 설계와 맞다.

## 3. 맷 포콕에게서 차용할 것과 버릴 것

### 3.1 차용할 핵심

| 원리 | 원 저장소의 역할 | devflow에서의 번역 |
|---|---|---|
| 결정 프런티어 | 선행 결정이 끝난 질문만 같은 라운드에 묶는다 | 여섯 product 판단과 arch 단계의 의존을 내부적으로 정렬한다. 같은 묶음의 질문은 서로의 답에 의존하지 않아야 한다 |
| 사실/결정 분리 | 환경이 답할 사실은 AI가 찾고, 결정은 사용자에게 기다린다 | 모든 미지수를 네 종류로 분류하고 사실 질문을 사용자 묶음에서 제거한다 |
| 추천이 붙은 질문 | 사용자는 빈칸을 채우지 않고 제안에 반응한다 | 현재 devflow의 추천 기본값을 유지하되, 사실 근거를 먼저 붙인다 |
| 구체적 시나리오 | 개념 경계를 edge case로 압박한다 | 능력·경계·성공 판정 또는 작은 목적지를 실제로 바꿀 모호성에만 시나리오 하나를 쓴다 |
| 1차 출처 조사 | 공식 문서·소스·명세·1차 API를 따라간다 | 현재 결정을 소유한 출처를 우선하고, 버전·조회 시점·충돌을 드러낸다 |
| 대화로 못 푸는 질문 분리 | 상태 모델·UI는 버리는 prototype으로 본다 | arch의 차단 질문은 안전한 실험, split 이후의 질문은 조사 카드로 보낸다 |
| ADR 희소성 | 되돌리기 어렵고 비자명하고 실제 대안이 있을 때만 | 현재 devflow의 ADR 3조건을 그대로 유지한다 |
| red-capable 신호 | 사용자가 말한 정확한 증상을 같은 명령으로 고정한다 | verifier의 관측을 수정 카드 완료 신호와 이후 회귀에 쓴다. 코드 입력이 그 사이 안 바뀐 경우만 fix 전후 동일 증거이고, 바뀐 경우는 현행 한계로 명시한다 |
| 재현 최소화 | 실패를 유지하는 가장 작은 장면으로 가설 공간을 줄인다 | 현재 신호가 넓거나 불안정할 때만 기존 조사 카드가 좁고 agent-runnable한 신호를 산출한다 |
| 반증 가능한 가설 | 원인 후보가 관측 가능한 예측을 가진다 | 검증 재발의 clean diagnosis에는 원인 가설 하나와 그 가설을 깨는 관측을 요구한다 |
| 원래 장면 재실행 | 작은 회귀 테스트 통과만으로 끝내지 않는다 | 좁힌 신호 뒤에도 verifier가 원래 주 시나리오·적대 입력·폴더 전체 회귀를 수행한다 |

### 3.2 그대로 차용하지 않을 것

1. **프런티어가 빌 때까지 무제한 질문.** devflow는 여섯 판단과 현재 카드 필드라는 종료
   목적지가 있다. “가능한 모든 결정”이 아니라 “현재 산출물을 유일하게 쓸 수 있게 하는
   결정”이 끝나면 멈춘다.
2. **한 질문씩 긴 왕복.** 현재의 묶음 질문이 사용자 효율에 더 맞다. 프런티어를 라운드의
   의존 조건으로만 차용한다.
3. **조사마다 Markdown 한 장.** 새 문서층·죽은 기록·신선도 표류를 만든다. 원시 조사
   메모는 영속하지 않는다.
4. **서브에이전트가 의미론의 전제.** 병렬 위임은 속도 최적화일 뿐이다. 플랫폼이 지원하지
   않아도 같은 답에 도달해야 한다.
5. **CONTEXT.md를 domain마다 재귀 생성.** devflow에는 이미 glossary, product, arch,
   능력 문서, 카드가 있다. 같은 개념의 다섯 번째 집을 만들지 않는다.
6. **prototype을 생산 코드 가까이에 자동 생성.** Layer 0 전에는 쓰기 권한·위치·삭제
   생애가 불분명하다. 안전한 scratch 실행이 불가능하면 멈추거나 잠정값/조사 카드로 보낸다.
7. **3에이전트 병렬 설계.** 기존 차용 경계에서 이미 기각했고, 이번 관찰도 그 이유를
   반증하지 않는다.
8. **모든 버그에 가설 3~5개와 사용자 checkpoint.** 어려운 진단에는 유용하지만 정상 수정의
   고정비가 되고 카드별 승인·깨끗한 역할 경계와 겹친다. 검증 재발에서만 가설 하나+예측을 쓴다.
9. **전역 red-green.** `diagnosing-bugs`의 강점은 테스트라는 형식이 아니라 정확한 증상을
   fix 전후 같은 수단으로 보는 것이다. CLI·HTTP·브라우저·측정도 허용하고 기능 구현 전체에
   순서를 강제하지 않는다.
10. **맷 방식의 code-review 직접 이식.** 두 축 분리는 유용하지만 devflow reviewer는 이미
    의도·논리·범위와 저장소 표준을 깨끗한 한 역할에서 본다. 수리·재검토·세 번 사람 관문까지
    가진 현재 쪽이 닫힌 루프이므로 교체 근거가 없다.

### 3.3 이 차용이 새로 사는 것

- 사용자에게 가던 사실 질문이 AI의 증거 획득으로 이동한다.
- 질문 묶음 안의 선후관계 충돌이 줄어든다.
- glossary가 단어 모음에서 실제 경계 검사 도구로 강화된다.
- stack 추천이 모델 기억이 아니라 현재 출처에 묶인다.
- 브라운필드에서 코드·외부 계약·소유자 의도가 각각 자기 질문에만 권위를 가진다.
- 페이지·모달·리스트는 전체 product 재실행 없이 한 번의 경량 보강을 받을 수 있다.
- 검증에서 나온 수정은 같은 정확한 실패 신호를 완료 신호와 이후 회귀로 소비해 “무엇을
  고치려 했는지”가 흔들리지 않는다. 여러 수리 카드 사이 입력이 바뀌면 fix 직전 red를 다시
  보장하지 않는 현행 한계는 남긴다.
- 반복 실패는 새 카드의 연속이 아니라 이전 수리의 재발로 판정되어 clean diagnosis·조사 카드·
  사람 관문 중 더 강한 다음 행동으로 바뀐다.

### 4.3 구현 때 추가할 새 계보

구현이 확정되면 `DD-67` 후보로 다음 한 문장을 기록한다.

> 기획의 미지수는 현재 출처로 확인할 사실, 실행으로 확인할 사실, 소유자 결정으로 나누고,
> product·arch·adopt·split은 사용자 질문 전에 사실을 닫되 원시 조사 문서를 새로 만들지 않는다.

근거에는 이번 소유자의 사전 차용 허락, 현재 스킬의 실패 경로, 맷 포콕 저장소의 차용 원리와
간접 로드·재귀 조사·죽은 파일 반례를 함께 적는다. `docs/design.md`의 차용 절도 다음처럼
정밀화한다.

- 새로 차용: 결정 프런티어, 사실/결정 분리, 경계 시나리오, 1차 출처 규율.
- 계속 비차용: 무제한 grilling, 조사 파일 계층, 간접 스킬 의존, 3에이전트 병렬 설계.

수정 수렴 선택지가 확정되면 별도 다음 번호 후보로 다음 의미를 기록한다. 기획 증거 규율과
검증 수렴은 소비자·실패 경로가 다르므로 한 DD에 합치지 않는다.

> 검증-origin 수정은 verifier가 낸 정확한 신호를 수정 카드 완료 신호와 이후 회귀에 보존하고, 그 신호가
> 완료된 수정 카드 뒤 다시 실패하면 깨끗한 역할을 오염시키지 않은 채 유계 진단 또는 사람
> 관문으로 승격한다.

이 후보는 DD-24·30을 대체하지 않고 반복 소비를 더한다. 자동 승인까지 선택하면 DD-25의
카드별 승인 이유를 반박하는 **별도 반전 결정**이 필요하며 같은 후보에 숨기지 않는다.

### 4.4 보존 영향 원장 — 후속 계획이 임의로 넘을 수 없는 경계

후속 계획은 각 변경을 `보존 추가 / 국소 계약 변경 / 구조 변경 / 기존 결정 반전` 중 하나로
표시한다. `보존 추가`만 기존 체계 위의 기본 경로다. 나머지 셋은 연결된 D번호·DR번호와 현재
문장을 인용하고, 소유자 결정 번호 없이는 구현 목록에 넣지 않는다.

후속 `plan_ko.md`의 파일별 행에는 다섯 칸이 필요하다: `현재 정확한 문장/형식`, `추가 또는
교체`, `막으려는 실패 경로`, `보존되는 불변식`, `소유자 결정·DD/DR 근거`. “개선”이라는 말만으로
교체를 추가처럼 표시하면 계획 검증 실패다. 더 나은 반전안이 발견되면 본안에 섞지 않고
`보존안 / 반전안 / 왜 기존 이유가 더는 성립하지 않는지 / 이관과 되돌리기` 네 항목의 preview로
소유자에게 먼저 돌린다.

## 5. 전체 설계 — 공통 기획 증거 규율

### 5.1 흐름

```text
현재 단계의 다음 판단
        │
        ▼
그 판단을 바꿀 미지수가 있는가? ── 아니오 ──→ 기존 절차 계속
        │ 예
        ▼
미지수의 주인은 누구인가?
  ├─ 저장소·환경의 현재 사실 ──→ 정확 경로/실행 결과 확인
  ├─ 외부 계약의 사실       ──→ 그 사실을 소유한 1차 출처 확인
  ├─ 실행해야 아는 사실      ──→ 단계별 안전 실험 또는 잠정값/조사 카드
  └─ 소유자의 결정           ──→ 사실을 붙인 추천안으로 질문
        │
        ▼
지금 판단을 막는가?
  ├─ 예  ──→ 답·충돌·불가 중 하나가 나올 때까지 다음 단계 금지
  └─ 아니오 ─→ 열린 질문 / arch 잠정값 / split 조사 카드로 정확히 착지
```

### 5.2 하나의 companion, 네 소비자

새 사용자 스킬 대신 다음 쌍을 만든다.

- `skills/principles/planning-evidence_ko.md`
- `skills/principles/planning-evidence.md`

이 파일은 모델이 자동 호출하는 등록 스킬이 아니다. `product`·`arch`·`adopt`·`split`만 상대
경로로 읽는 정본 companion이다. 공통 분류와 정지 조건은 여기 한 번만 쓴다. 각 소비자는
자기 단계의 trigger·착지 위치·금지를 자기 SKILL.md에 쓴다.

이 선택의 이유는 구체적이다.

- 네 파일에 같은 40줄을 복제하면 번역·수리 때 네 규칙이 갈라진다.
- `principles/SKILL.md`에 넣으면 work·verify·resume까지 매번 읽어 전역 고정비가 된다.
- 새 `research` 스킬로 만들면 하위 skill load의 성공이 절차의 전제가 된다.
- companion은 이미 세 predicate 정본에서 쓰고 테스트하는 배포 방식이다.

### 5.3 미지수 네 종류

| 종류 | 기계 판정 | 우선 행동 | 사용자에게 묻는 경우 |
|---|---|---|---|
| 현재 저장소 사실 | 답이 현재 코드·config·lockfile·테스트·실행 결과에 있고 소유자 선호가 바뀌어도 답이 같다 | 정확한 경로를 열거나 기존 검증 창구로 실행 | 접근 권한이 없고 그 사실이 현재 판단을 막을 때만, 필요한 경로·명령을 정확히 말해 요청 |
| 외부 계약 사실 | 답을 제3자 API·공식 문서·명세·소스가 소유하며 버전·날짜에 따라 달라질 수 있다 | 버전이 보이면 그 버전의 1차 출처, 없으면 현재판과 “버전 미확인”을 분리 | 1차 출처가 없거나 서로 충돌하고 소유자가 위험을 선택해야 할 때 |
| 실행 사실 | 말·문서만으로는 답이 없고 호출·렌더링·부하·상태 전이 관찰이 답을 만든다 | 현재 단계가 허용하는 안전 실험, 아니면 잠정값/조사 카드 | 쓰기·비용·권한이 필요한 실험이 현재 판단을 막을 때 |
| 소유자 결정 | 가치·우선순위·위험 감수·사용자 경험·조직 정책이 달라지면 답도 달라진다 | 확인한 사실과 추천 근거를 붙여 묶음 질문 | 항상. AI가 답 대신 닫지 않는다 |

혼합 질문은 쪼갠다. “OAuth를 지원하나요, 그러면 쓸까요?”에서 첫 절은 사실이고 둘째는
결정이다. 사실을 먼저 확인한 뒤 그 결과가 붙은 결정만 사용자에게 보낸다.

### 5.4 지금 막는 것과 나중에 닫을 것

다음 중 하나면 **차단 사실**이다.

1. 답이 바뀌면 product의 문제·해결 방식·능력·경계·성공 판정 중 하나가 달라진다.
2. 답이 바뀌면 arch 후보 하나가 실행 불가·보안 불가·검증 불가가 된다.
3. adopt의 대표 흐름이나 외부 경계를 다른 능력으로 분류하게 된다.
4. split 카드의 목적지 또는 완료 신호를 서로 다른 행동으로 읽게 된다.

차단 사실은 “나중에 알아보자”로 넘기지 않는다. 다음 중 하나가 나와야 단계가 진행한다.

- 그 사실을 소유한 1차 출처의 답.
- 현재 환경에서 재현한 실행 답.
- 서로 충돌하는 출처 목록과 무엇이 결정 불가인지에 대한 보고.
- 도구·권한 부재 때문에 확인할 수 없다는 정확한 중단 보고.

답이 바뀌어도 현재 구조가 유효하고, 구현·부하·실사용에서만 수치를 얻을 수 있으며,
대체 경로가 이미 있으면 **후속 사실**이다. product의 비차단 열린 질문, arch의 잠정값,
split의 조사 카드 중 정확히 한 곳으로 보낸다.

### 5.5 출처 순서와 소유권

“1차 출처”를 권위 있는 것처럼 보이는 사이트로 판정하지 않는다. **누가 그 사실을 바꿀 수
있는가**로 소유자를 정한다.

| 주장 | 그 사실을 소유하는 출처 |
|---|---|
| 현재 저장소가 어떤 버전을 쓰나 | lockfile·manifest·실제 설치 출력 |
| 그 버전의 API가 무엇을 보장하나 | 그 버전의 공식 문서·명세·소스·1차 API 응답 |
| 현재 코드가 실제로 무엇을 하나 | 실행 결과·테스트·코드·config. 질문에 맞는 좁은 증거부터 |
| 사용자가 무엇을 원하는가 | 사용자 확인과 확정 product.md |
| 시장에 수요가 있나 | 조사 자료는 신호일 뿐이다. 소유자의 문제 판단을 대신하지 않는다 |
| 법·보안 정책이 무엇을 요구하나 | 적용 관할·시점의 공식 법령·규제기관·보안 표준. 불명확하면 전문 판단 필요를 숨기지 않는다 |

브라운필드에는 하나의 전역 서열을 쓰지 않는다. 코드는 “현재 구현”, 외부 1차 출처는 “외부
계약”, 사용자는 “원하는 방향”에 각각만 권위를 가진다.

### 5.6 조사 정지 조건

출처 개수나 경과 시간으로 멈추지 않는다. 현재 판단을 바꿀 사실 목록을 먼저 좁히고, 각
사실이 다음 상태 중 하나가 되면 멈춘다.

```
settled     사실을 소유한 출처 또는 실행 결과가 답함
conflicted  둘 이상의 소유 출처가 충돌하고 충돌 범위가 드러남
unavailable 필요한 도구·권한·버전이 없어 확인 불가가 드러남
```

관련 배경을 넓게 이해했다는 느낌은 정지 조건이 아니다. 차단 사실이 모두 위 셋 중 하나이고,
결정 묶음을 쓸 수 있으면 읽기를 끝낸다. 후속 사실을 발견했다고 현재 조사를 확장하지 않는다.

### 5.7 영속화 — 최종 결론만 소유 문서에 남기고, 중간 복구의 한계를 정직하게 둔다

별도 조사 파일을 기본으로 만들지 않는다. 최종적으로 남는 내용은 다음뿐이다.

| 결과 | 착지 위치 |
|---|---|
| product 결정을 바꾼 외부 사실 | 그 결정이 사는 `해결 방식`·`경계`·`성공 판정` 문장에 짧은 출처 포인터 |
| arch 선택을 바꾼 사실 | `스택`의 이유, `잠정값`의 출처, 또는 조건을 모두 통과한 ADR |
| adopt가 해석한 기존 기록 | 현재 `기존 기록`의 정확 경로 규칙. 외부 사실은 arch 선택/리스크에만 |
| split 이전에 닫힌 사실 | 카드의 목적지·금지·완료 신호에 결론 반영. 긴 근거가 필요하면 조사 카드 진행 로그 |
| 충돌·확인 불가 | 차단이면 정확한 사실 질문·시도한 출처·필요한 도구/결정을 보고하고 진행 중단, 후속이면 열린 질문/잠정값/조사 카드 |

URL만 남겨 다음 세션이 의미를 다시 추측하게 하지 않는다. **결론 한 문장 + 그 결론이 현재
결정에 미친 영향 + 정확한 출처**가 최소 단위다. 반대로 조사 과정·검색어·읽은 페이지 전체는
남기지 않는다. 현재 결정을 바꾸지 않는 보충 조사는 대화 안에서만 보고하고, 소유자가 별도
내구 산출 위치를 지정하지 않는 한 Layer 0에 넣지 않는다.

**기본안 A(권장) — 현재 commit 경계를 유지한다.** `product`·`arch`·`adopt`는 사용자 확인 전
중간 사실·답변을 새 상태로 만들지 않는다. 중단되면 마지막 확정 Layer 0에서 같은 판단을 다시
도출하고 필요한 사실을 재조사하며, 사용자 답을 추측하지 않고 다시 묻는다. `split`은 원 요청이
이미 `유지보수 라우팅 대기`에 남으므로 같은 질문을 재구성할 수 있지만, 답 직후 card commit 전
중단이면 답은 다시 물어야 한다. 명시한 보충 조사도 보고 전 중단이면 다시 실행한다. 이것은
새로 생기는 소실이 아니라 현재 기획 대화가 가진 잔여 구간이며, v0.15는 이를 “소실 0”으로
표현하지 않는다.

**대안 B — 강한 프런티어 복구.** 소유자가 재질문·재조사보다 중간 commit을 택하면 generic
journal 줄 재사용으로는 부족하다. 다음 전체가 한 묶음으로 필요하다.

1. 규칙 정본에 stage·최종 착지 위치·실행할 사실 질문 또는 사용자 질문·결론 상태를 담는 새
   예약 planning-frontier 줄과 정확한 전이 commit을 정의한다.
2. 외부 조사나 사용자 질문 **전에** 그 줄을 먼저 착지한다. 병렬 사실은 개별 결과가 아니라
   시작 전에 열거한 질문 묶음 하나로 기록한다.
3. 결과가 모두 모이면 settled/conflicted/unavailable로, 사용자 답이 오면 decision으로 줄을
   교체한다. 교체 전에 죽으면 새 세션은 기록된 질문을 재실행하거나 정확히 다시 묻는다.
4. `resume`은 그 줄의 stage로 먼저 라우팅하고, 최종 Layer 0 또는 plan commit은 자신이 소비한
   정확한 줄만 삭제한다.
5. 최초 product에서도 쓰려면 최종 문서 전 Git·room·journal을 만드는 UX를 받아들인다.

B를 고른 뒤 구현자가 상태를 다시 설계하지 않도록 후보 계약도 고정한다. 정본 후보는 다음
필드를 JSON 문자열로 담는 예약 줄 하나다: `room`, `stage(product|arch|adopt|split)`,
`destination`, `question_set`, `state(research-pending|decision-pending|conflicted|unavailable|
decision-settled|fact-settled)`, `result`, `sources`. 한 room에는 최대 한 줄이며, integrity check는
중복·알 수 없는 stage/state·해석 불가능 JSON을 잡는다. 첫 기록과 각 교체는 journal만 담는
`<stage> — planning frontier` 구속 결정 commit이다. 봉쇄 중에는 미결/결정 append처럼 로컬
commit을 허용하고 통합이 열리면 게시한다. `resume`은 자기 room의 줄만 실행 대상으로 삼고
남의 줄은 열린 planning 상태로 보고한다. 정상 verify 전이·손상 복구 다음, 일반 product 재실행·
유지보수 요청·work보다 앞에서 stage로 보낸다. 트리가 없는 표에서는 product.md 존재 판정보다
앞선다. 최종 Layer 0/plan commit만 자기 room의 정확한 줄을 삭제한다. 이 후보 형식·우선순위·
commit 범위 중 하나라도 달라지면 D13을 다시 열어야 한다.

대안 B조차 사용자 메시지 수신과 첫 파일 쓰기 사이를 원자화하지 못한다. 보장하는 것은 답의
무손실이 아니라 **무엇을 다시 물어야 하는지의 무손실**이다. 새 예약 상태·resume 경로·초기
commit 비용이 이번 핵심인 기획 품질보다 넓으므로 기본안 A를 권장하며, D13에서 소유자가 B를
고르면 파일 범위와 크기 예산을 먼저 다시 연다.

### 5.8 병렬 조사는 선택 최적화다

- 플랫폼이 병렬 작업자를 지원하고 독립적인 사실 질문이 둘 이상이면 위임할 수 있다.
- 작업자가 이미 위임받은 조사라면 다시 위임하지 않고 직접 수행한다.
- 병렬 조사 완료를 기다리는 동안 그 결과에 의존하지 않는 프런티어만 진행한다.
- 메인 세션이 출처와 결론을 대조하고 결정 묶음에 넣는다. 조사 작업자가 제품 결정을 닫지
  않는다.
- 병렬 도구가 없어도 같은 분류·출처·정지 조건을 메인 세션이 수행한다.

## 6. `product` 개선 명세

### 6.1 그대로 둘 것과 바꿀 예산 의미

- 판단 여섯 가지와 product.md 목차.
- 능력 1~3개는 1~2라운드, 4~7개는 세 라운드를 **목표 예산**으로 삼고, 8개 이상은 분할을
  제안하는 범위 비례 원칙.
- 한 묶음은 최대 5개, 보통 3~5개의 추천 기본값이 붙은 독립 질문. 남은 결정이 1~2개뿐이면
  숫자를 맞추기 위해 질문을 만들지 않고 짧은 마지막 묶음으로 묻는다.
- 능력별 제거 질문.
- 개발 기획을 arch로 미루는 경계.
- 성공 판정의 검증 가능성 게이트.
- 사용자 확인과 Layer 0 커밋.

### 6.2 새 절차

현재 `인터뷰 규칙` 앞에 다음 의미를 넣는다. 실제 문장은 구현 때 압축한다.

1. 여섯 판단 중 현재 초안으로 유일하게 쓸 수 없는 판단을 찾는다.
2. 그 판단의 선행 판단이 확정됐는지 본다. 안 됐으면 선행 판단부터 다룬다.
3. 현재 판단을 바꿀 미지수를 공통 companion으로 분류한다.
4. 사실은 조사·코드 읽기·안전한 실행으로 먼저 닫는다.
5. 소유자 결정만 같은 프런티어끼리 최대 5개 묶음으로 묻는다. 보통 3~5개지만 남은 결정이
   적으면 그대로 묻는다.
6. 답 때문에 새 결정이 생기면 다음 묶음을 만든다. 미리 전체 질문을 작성하지 않는다.
7. 여섯 판단을 product.md 형식으로 유일하게 쓸 수 있으면 멈춘다. 가능성 공간 전체를
   소진하려 하지 않는다.

이 구조는 맷 포콕의 프런티어를 가져오지만 devflow의 범위 비례 비용 신호를 없애지 않는다.
목표 라운드를 소진했는데 여섯 판단 중 하나가 여전히 유일하게 써지지 않으면 조용히 종료하지
않는다. 새 차단 결정과 범위 증가를 보고하고, 마지막 짧은 묶음을 계속할지 프로젝트를 나눌지
소유자에게 묻는다. 한 묶음 안의 질문이 서로 의존한다는 것을 답 뒤에 발견하면 영향을 받은
질문만 다음 묶음에서 다시 연다.

### 6.3 product가 자동 조사하는 조건

자동 조사는 여섯 판단을 바꿀 수 있는 사실일 때만 한다. 사용자가 명시한 조사는 별도 trigger다.
현재 여섯 판단을 바꾸지 않아도 요청한 좁은 질문을 실행해 보충 결과로 보고하되, product 진행을
막거나 product.md에 억지로 넣지 않는다.

- 사용자가 특정 사실·시장·규정·경쟁 방식·외부 서비스의 현재 상태를 조사하라고 명시했다.
  이 항목은 자동 조사와 달리 결정 영향 여부가 실행 조건이 아니다.
- 해결 방식의 실행 가능성이 외부 계약에 달렸다.
- MVP 경계나 성공 판정이 법·규정·플랫폼 정책·제3자 한도에 달렸다.
- 같은 용어가 외부 도메인에서 명확한 계약 의미를 가지며 현재 정의와 충돌할 수 있다.

다음은 자동 조사하지 않는다.

- “좋은 제품이라면 보통”이라는 일반론을 모으기 위해.
- 사용자의 실제 문제·우선순위·지불 의사를 웹에서 증명하기 위해.
- 이미 사용자가 정한 가치 결정을 더 권위 있어 보이게 만들기 위해.
- 여섯 판단 중 어느 것도 바꾸지 않는 경쟁사 기능 목록을 만들기 위해.

### 6.4 도메인 언어 보강

`glossary.md` 산출은 유지하고 다음 세 동작만 더한다.

1. 사용자가 기존 glossary와 다른 뜻으로 같은 단어를 쓰면 즉시 차이를 제시한다.
2. 한 단어가 둘 이상의 능력·행위자를 가리키면 정확한 후보 용어와 각각의 경계를 추천한다.
3. 관계의 모호성이 능력·경계·성공 판정을 바꿀 때만 구체적 시나리오 하나로 압박한다.

맷 포콕처럼 확정 순간 canonical 파일에 바로 쓰지는 않는다. 현재 backlog에 “Layer 0 draft
confirmation state의 디스크 표현이 없다”는 관찰이 남아 있기 때문이다. 대화 초안에 반영하고,
product.md·glossary.md를 한 묶음으로 보여 사용자 확인 뒤 기존 커밋 경계로 착지시킨다.

### 6.5 “무엇·왜·바라는 결과” 아이디어의 판정

모든 항목에 `무엇/왜/결과/근거` 네 필드를 강제하는 안은 기각을 권한다. 이유는 세 가지다.

- 같은 제품 목적이 정체성·능력·성공 판정에 반복돼 서로 다른 시점에 낡는다.
- AI가 빈 `왜` 칸을 그럴듯한 설명으로 채워 오히려 거짓 확신이 늘어난다.
- work가 매 카드마다 읽는 Layer 0가 능력 수에 비례해 커진다는 DR-18의 원인이 돌아온다.

대신 **의미 삼각형을 한 번씩만** 둔다.

| 단위 | 무엇 | 왜 | 바라는 결과 |
|---|---|---|---|
| 제품 전체 | 정체성 문단의 해결 방식 | 문제 절 | 정체성 둘째 문장 + 성공 판정 |
| 능력 하나 | 능력 이름과 사용자에게 생기는 결과 | 그 결과가 어느 성공 판정에 필요한지 한 구절 | 능력 한 줄의 결과 서술 |
| 비자명한 경계 | 안 만들 것 | 이번 MVP에서 제외해야 하는 이유 | 지켜지는 범위 또는 실패 방지 |
| 어려운 아키텍처 결정 | 선택 | 근거·대안 | 결과. 세 조건을 통과하면 ADR |
| 작업 카드 | 목적지 | 왜 | 완료 신호 |

즉 새 필드를 늘리기보다 기존 문장의 의미를 정밀하게 쓴다. 다음 세션은 의도를 읽을 수 있고,
구현 방법은 계속 열려 있다.

### 6.6 product.md 형식의 정확한 변화

목차는 늘리지 않는다. 주석과 작성 규칙만 다음처럼 강화한다.

- `해결 방식`: 선택한 방식의 이유 + 실제로 검토하고 버린 방식만 한 줄씩.
- `능력`: `번호 + 이름 + 사용자가 얻는 결과 + 그 결과가 성공 판정에 필요한 이유`를 한
  문장 안에. 구현 구성요소는 쓰지 않는다.
- `경계`: 비자명하거나 다시 열릴 가능성이 큰 제외에만 이유를 붙인다.
- `성공 판정`: 외부 사실에 의존하면 판정 문장 뒤에 버전/시점이 포함된 정확한 출처 포인터.
- `열린 질문`: 여섯 판단을 막는 질문은 남길 수 없다. 후속 질문만 두고, 어느 다음 단계가
  소유하는지 한 구절로 적는다.

### 6.7 product 종료 게이트

다음이 모두 참이어야 확인 초안을 제시한다.

- 여섯 판단이 모두 쓰였다.
- 각 질문 묶음의 질문끼리 선행관계가 없었다. 발견된 선행관계는 다음 묶음에서 재확인했다.
- 조사 가능한 사실을 사용자에게 선호 질문처럼 묻지 않았다.
- 차단 사실은 `settled/conflicted/unavailable` 중 하나다.
- conflicted/unavailable가 남으면 어느 판단을 확정할 수 없는지 드러냈고, 확정할 수 없는
  판단이 있으면 product를 끝내지 않았다.
- 각 능력 한 줄이 구현이 아니라 사용자 결과와 포함 이유를 말한다.
- glossary의 같은 단어가 두 개념을 가리키지 않는다.

### 6.8 예상 장면

**작은 로컬 CLI.** 외부 계약이 없고 사용자가 문제·경계를 분명히 말했다. 자동 조사 0회,
기존 1~2라운드 그대로 끝난다.

**결제 서비스.** 부분 환불 지원 여부가 MVP 능력을 바꾼다. AI가 해당 결제사의 현재 공식
문서와 API 버전을 먼저 확인한다. 사용자에게는 “지원하나요?”가 아니라 “이 제약 아래 MVP에
부분 환불을 넣을까요? 권장은 …”만 묻는다.

**시장 아이디어.** 사용자가 수요를 모른다. AI가 경쟁사 존재를 조사할 수는 있지만 그것을
문제 검증으로 승격하지 않는다. 문제와 우선순위는 소유자 증거가 없다고 정직하게 남는다.

## 7. `arch` 개선 명세

### 7.1 왜 arch에서 조사 강화가 가장 큰가

product는 가치 판단 비중이 높고, adopt는 현재 코드라는 강한 로컬 증거가 있다. arch는
호환성·지원 정책·배포 제약·보안 경계처럼 시간에 따라 바뀌는 외부 사실 위에서 추천한다.
현재 스킬에는 후보 2~3개와 추천을 제시하라는 규칙은 있지만, 추천 전에 무엇을 확인할지와
언제 읽기를 멈출지가 없다. 따라서 v0.15의 조사 투자 우선순위는 `arch > adopt > product`다.

### 7.2 절차의 변화

현재 다섯 단계는 유지하고 1과 2 사이에 **후보를 가르는 증거 확인**을 넣는다.

1. product 능력에서 구성요소를 도출한다.
2. 후보 생존을 가르는 사실만 열거한다: 지원 플랫폼, 버전 호환성, 라이선스, 필수 런타임,
   배포 환경, 보안·데이터 경계, 검증 창구 가능성.
3. 로컬 제약이 있으면 먼저 읽고, 외부 사실은 그 사실을 소유한 현재 1차 출처로 확인한다.
4. 살아남은 후보 2~3개만 추천 묶음에 올린다. 사실상 불가능한 후보를 비교표 채우기용으로
   넣지 않는다.
5. 사용자가 고른 스택의 파생 결정 프런티어를 만든다. 사실은 먼저 확인하고 결정만 묻는다.
6. 코드 구조·데이터·검증 창구를 닫는다.

### 7.3 조건부로 두 번 설계한다

기존 비차용인 “3에이전트 병렬 설계”는 유지한다. 대신 다음 두 조건을 모두 만족하는 결정은
같은 세션에서 서로 다른 구조 두 개를 짧게 만든다.

1. 나중에 되돌리기 어렵다.
2. 한 구조를 먼저 쓰면 다른 구조가 보이지 않을 만큼 경계가 비자명하다.

두 구조는 이름만 다른 후보가 아니라 구성요소 경계·데이터 소유·검증 창구가 달라야 한다.
실제 trade-off가 확인되면 사용자에게 추천과 함께 제시한다. 최종 결정이 ADR 3조건까지
통과할 때만 ADR로 남긴다. 단순 라이브러리 선택에는 이 절을 쓰지 않는다.

### 7.4 차단 사실과 잠정값의 경계

| 질문 | 지금 조사 | 잠정값 |
|---|---|---|
| 답이 후보를 실행 불가·보안 불가·검증 불가로 만드나 | 예 | 아니오 |
| 문서·소스·현재 환경으로 Layer 0 전에 답할 수 있나 | 예 | 구현·부하·실사용이 있어야만 답하면 후보 |
| 모르는 동안 안전한 기본값과 교체 경로가 있나 | 없으면 차단 | 있으면 잠정값 |
| 답이 product 능력·경계·성공 판정을 바꾸나 | arch 중단 후 product로 되돌림 | arch가 임의로 품지 않음 |

예를 들어 “이 런타임이 대상 OS를 지원하는가”는 지금 조사한다. “실사용에서 batch를 32와
64 중 얼마로 할까”는 잠정값이다. “외부 API가 exactly-once를 보장하지 않아 결제 능력의
성공 판정이 바뀐다”면 arch 안에서 우회 결정을 만들지 않고 product로 돌린다.

### 7.5 검증 창구는 존재가 아니라 실행 가능성까지

현재 표를 유지하면서 다음을 더한다.

- 현재 플랫폼이 제공한 도구 이름과 접근 가능 여부를 실제로 확인한다.
- 기존 프로젝트면 arch.md에 적을 실행 명령을 한 번 실행할 수 있는지 adopt가 확인한다.
- 새 프로젝트에서 명령이 아직 없으면 “첫 작업으로 만든다”는 현재 규칙을 유지하되, 그
  카드가 만들어지기 전에는 무엇으로 첫 결과를 확인할지 리스크에 쓴다.
- 도구가 없으면 이름을 추측해 기록하지 않고 현재처럼 설치·연결을 안내한 뒤 멈춘다.

### 7.6 arch.md의 정확한 변화

새 목차는 만들지 않는다.

- `스택`: `선택 — 결정 근거`를 유지한다. 시간 민감 외부 사실이 선택을 갈랐을 때만 정확한
  출처와 버전/조회 시점을 같은 항목에 둔다.
- `잠정값`: 현재 표를 유지한다. `출처`는 차용 링크뿐 아니라 “어떤 실측이 아직 없나”를
  말할 수 있어야 한다.
- `리스크`: 가장 먼저 깨질 곳과 확인 방법에, conflicted/unavailable 후속 사실이 있으면
  그 영향 범위를 넣는다.
- `비범위`: 조사하지 않기로 한 배경 지식이 아니라 이번 아키텍처가 감당하지 않는 것만
  유지한다.
- ADR: 현재 3조건을 바꾸지 않는다. 조사 파일을 대신하는 저장소가 아니다.

### 7.7 안전한 실행 질문

arch가 문서만으로 못 닫는 차단 사실을 만났을 때 순서는 다음이다.

1. 현재 환경의 읽기 전용 명령이나 기존 verify channel로 답할 수 있으면 실행한다.
2. 프로젝트 밖의 명시적 disposable workspace에서 비용·권한·외부 상태 변경 없이 답할 수
   있으면 질문과 폐기 조건을 먼저 밝히고 실행한다.
3. 패키지 설치·유료 호출·외부 write·실데이터가 필요하면 임의로 진행하지 않는다. 정확한
   실험과 필요한 권한을 사용자에게 제시한다.
4. 차단이면 답 전까지 arch를 끝내지 않는다. 후속이면 잠정값과 미발급 해소 카드로 보낸다.

### 7.8 예상 장면

**Next.js와 배포 환경.** 모델 기억으로 “지원될 것”이라 하지 않는다. 대상 런타임·공식
배포 문서·현재 버전의 제약을 확인한 뒤 후보를 줄인다. 사용자는 사실이 아니라 비용·운영
trade-off를 결정한다.

**실시간 처리량.** batch 크기는 실제 부하 전에는 모른다. arch가 자료 조사를 끝없이 하지
않고 안전한 기본값을 잠정값으로 두며 해소 카드를 요구한다.

**검증 도구 부재.** frontend인데 브라우저 조작 도구가 없다. “나중에 눈으로 확인”을 쓰지
않고 현재 게이트대로 멈춘다.

## 8. `adopt` 개선 명세

### 8.1 기존 원칙을 바꾸지 않는다

- 인터뷰로 새 제품을 만들지 않고 코드에서 역산한다.
- 후보마다 대표 흐름 하나를 끝까지 추적한다.
- devflow 밖 문서는 주장이고 코드와 대조한다.
- 코드가 답할 수 없는 안 만들 것·성공 판정·문제/해결 방식은 소유자에게 묻는다.
- 기존 완료 코드를 카드로 소급하지 않는다.
- 기존 화면은 사실상의 디자인 정본이다.

### 8.2 하나의 증거 서열을 세 질문으로 나눈다

현재 “devflow 밖 문서보다 코드가 진실”은 현재 구현을 역산할 때 옳다. 그러나 외부 계약과
원하는 방향까지 같은 서열로 읽으면 오독한다. 다음 세 질문을 따로 판정한다.

| 질문 | 권위 순서 | 무엇을 증명하지 못하나 |
|---|---|---|
| 지금 이 저장소가 무엇을 하나 | 좁은 실행 결과·테스트 → 코드/config → 대조된 저장소 문서 → 유계 commit 이력 | 그것이 소유자가 계속 원하는 행동인지는 증명하지 못함 |
| 외부 경계가 무엇을 보장하나 | lockfile의 실제 버전 → 그 버전의 공식 문서·명세·소스·1차 API | 현재 코드가 계약을 올바르게 구현했다는 것은 증명하지 못함 |
| 앞으로 무엇을 원하나 | 확정 devflow 문서 → 이번 사용자 확인 | 기존 코드가 그렇게 되어 있다는 것은 증명하지 못함 |

### 8.3 대표 흐름의 내부 증거표

1단계에서 후보마다 다음을 내부적으로 채운다.

| 항목 | 내용 |
|---|---|
| 후보 이름 | product 능력 후보 |
| 외부 진입점 | 정확 경로/route/command |
| 관찰 결과 | 사용자가 밖에서 보는 현재 행동 |
| 소유 경계 | 이 후보가 소유하는 상태·책임 |
| 비소유 경계 | 다른 후보나 외부 제공자 책임 |
| 외부 의존 | manifest/lockfile에서 확인한 이름·버전 |
| 근거 경로 | 대표 흐름에서 실제로 연 정확 경로 |
| 남은 종류 | 현재 사실 / 외부 사실 / 실행 사실 / 소유자 결정 |

이 표는 새 파일로 저장하지 않는다. capability 후보를 합치거나 나누는 근거를 사용자에게
보이는 작업대다. 확정 뒤 결론은 기존 product·arch·능력 문서 형식에만 들어간다.

### 8.4 adopt가 외부 조사를 하는 조건

- 대표 흐름이 외부 API·파일 형식·프로토콜의 의미에 의존하고, 코드만으로 계약을 알 수 없다.
- 현재 의존성 버전의 지원 종료·보안 제약이 arch 리스크나 검증 창구를 바꾼다.
- 저장소 문서와 코드의 충돌이 외부 계약을 서로 다르게 인용한다.
- 사용자가 도입과 함께 특정 외부 사실을 확인하라고 요청했다.

먼저 lockfile·manifest에서 버전을 찾는다. 버전이 없으면 최신 문서를 과거 동작의 증거로 쓰지
않고 `버전 미확인`으로 남긴다. 최신 문서는 앞으로의 선택 후보를 설명할 수는 있지만 현재
구현을 증명하지 못한다.

### 8.5 현재 동작이 미래 의도로 굳는 것을 막는 preview

사용자 확인 묶음 전에 다음 세 갈래로 보여 준다.

- **관찰됨** — 코드·실행에서 확인된 현재 동작.
- **해석됨** — 그 동작에서 역산한 문제·해결 방식·경계 후보.
- **소유자 결정 필요** — 안 만들 것·성공 판정·현재 제약을 유지할지.

사용자가 확인하면 표준 product.md가 Layer 0 의도가 된다. 그러므로 확정 파일에 `관찰/의도`
필드를 영구 추가할 필요는 없다. 확인 전 차이를 보이지 않고 전체 초안을 “역산 결과” 한
덩어리로 내는 것이 문제다.

### 8.6 재설계 금지와 개선 후보의 처리

조사 중 더 나은 구조를 발견해도 adopt가 조용히 반영하지 않는다.

- 현재 코드를 정확히 설명하는 Layer 0를 먼저 완성한다.
- 외부 계약 위반처럼 현재 설명 자체를 틀리게 만드는 것은 리스크·열린 질문으로 드러낸다.
- 제품 방향을 바꾸는 개선은 product 결정으로, 구성요소·stack·verify channel을 바꾸는 개선은
  arch 결정으로 분리한다.
- 사용자가 도입 뒤 개선을 원하면 현재 규칙대로 `유지보수 라우팅 대기`로 보존하고 split로
  보낸다.

### 8.7 adopt 종료 게이트

- 모든 후보가 외부 진입점의 대표 흐름 하나에 연결되었거나 질문 묶음에 남았다.
- 현재 구현·외부 계약·소유자 의도의 권위가 섞이지 않았다.
- 외부 계약을 인용한 경우 실제 의존성 버전과 맞거나 버전 미확인을 표시했다.
- 성공 판정은 소유자가 답했고 검증 가능하다.
- 개선 후보를 현재 설명에 몰래 넣지 않았다.
- verify channel은 실제 기존 명령·도구로 확인했거나 정확한 중단을 냈다.

### 8.8 예상 장면

**구버전 결제 SDK.** 최신 공식 문서가 아닌 lockfile 버전의 문서·소스를 본다. 현재 코드가
부분 환불을 막고 있어도 외부 계약이 지원하면 “현재 구현”과 “제공자 계약”을 분리한다.
사용자가 앞으로 지원할지 결정한다.

**README와 코드 충돌.** README는 세 역할을 말하고 코드는 두 역할만 가진다. 코드가 현재
동작의 증거다. README를 폐기하거나 미래 의도로 승격할지는 사용자 결정이다.

**리팩터링 욕구.** 대표 흐름이 얕은 helper 숲을 드러내도 adopt는 구조를 바꾸지 않는다.
정확한 현 상태를 arch에 쓰고, 개선 요청은 도입 뒤 카드로 보낸다.

## 9. 작은 범위 기획 — `split` 접합부

### 9.1 왜 이번 범위에 포함하는가

product·arch·adopt만 고치면 새 프로젝트와 도입의 첫 Layer 0는 좋아지지만, 소유자가 지적한
“페이지를 만든 뒤 모달과 리스트를 차례로 고도화하는 구간”은 그대로 남는다. 맷 포콕의
재귀적 장점은 같은 질문 깊이를 작은 단위에도 적용할 수 있다는 점이다. 그러나 devflow가
그 깊이를 그대로 복제하면 작은 변경이 느려진다.

권장안은 별도 `shape` 스킬이 아니라 `split` 유지보수 2단계의 짧은 **목적지 보강 분기**다.

### 9.2 세 등급

| 등급 | 조건 | 행동 |
|---|---|---|
| 0 · 바로 분할 | 정확한 기존 출처에서 task card 네 필드가 각각 한 가지 문장으로 써지고, 사용자에게 보이는 미결 분기가 없다 | 질문 없이 기존 split 계속 |
| 1 · 한 번 보강 | 제시할 선택지 각각이 아래 Layer 0 필드를 보존하고, 한 묶음의 답으로 네 필드를 한 가지 문장으로 만들 수 있다 | 추천이 붙은 질문 묶음 한 번 + 경계가 갈리는 경우 구체적 시나리오 하나 |
| 2 · 상위로 환류 | 제시할 선택지 하나라도 아래 Layer 0 필드를 바꾸거나, 한 묶음 뒤에도 카드 필드 하나에 유효한 문장이 둘 이상 남는다 | card를 만들지 않고 정확한 소유 단계로 보냄 |

여기서 Layer 0 필드는 product의 정체성·능력 목록·경계·성공 판정, arch의 구성요소·stack·코드
구조·데이터·검증 창구다. “가능한 답”을 무한히 상상하지 않고 AI가 실제 제시할 선택지만
사전 판정한다. 사용자가 제시하지 않은 답을 자유롭게 쓰면 그 **실제 답**으로 등급을 다시
판정한 뒤 card를 쓴다. 모달의 적용·닫기·미적용 선택지가 Layer 0를 보존하면서 한 묶음에서
함께 닫히면 등급 1이고, 실제 답이 새 역할이나 새 결제 정책을 요구하면 질문 개수와 무관하게
등급 2다.

### 9.3 사실이 비어 있을 때

- 로컬 코드가 답하면 split이 현재 유지보수 2단계에서 읽는다.
- 좁은 외부 사실이 바로 답하고 카드 목적지를 바꾸면 공통 companion으로 지금 확인한다.
- 실행해 봐야 하고 구현과 분리 가능한 답이면 기존 조사 카드를 앞에 둔다.
- 답이 Layer 0를 바꾸면 조사 카드로 우회하지 않고 product/arch로 먼저 돌린다.

### 9.4 질문 형식과 종료

- 한 묶음은 카드 네 필드를 유일하게 만드는 데 필요한 독립 질문 최대 5개이며, 각 질문에 추천
  기본값을 붙인다. 1~2개면 숫자를 맞추기 위해 질문을 추가하지 않는다.
- 이미 current code가 답한 질문은 묻지 않는다.
- 경계가 갈리는 한 장면만 구체적으로 걷는다. checklist 전수는 하지 않는다.
- 답 뒤 카드 네 필드를 유일하게 쓸 수 있으면 끝낸다.
- 답 뒤 카드 필드 하나라도 유효한 문장이 둘 이상 남거나 Layer 0 필드가 열리면 split에서 두
  번째 grilling을 시작하지 않고 상위 단계로 보낸다.

### 9.5 예시

| 요청 | 등급 | 이유와 결과 |
|---|---|---|
| “저장 버튼 라벨을 보관으로” | 경량 변경 차선 | 상태·전이·공유 계약이 안 바뀌면 split 자체에 안 옴 |
| “필터 모달에 날짜 범위 추가” + 현재 리스트 계약 명확 | 1 | 적용 시점·닫기 동작이라는 상호작용 축 한 번 확인 후 카드 생성 |
| “관리자 전용 정산 페이지 추가”인데 관리자 정의·정산 성공 판정 없음 | 2 → product | 대상·능력 경계·성공 판정이 바뀜 |
| “캐시를 Redis로 바꿔 성능 개선”인데 병목 미측정 | 2 → arch 또는 조사 카드 판정 | 구성요소 선택과 실행 사실이 섞임 |
| “외부 API가 cursor pagination을 지원하면 목록을 전환” | 사실 확인 후 0 또는 조사 카드 | 지원 여부가 문서로 닫히면 카드, 실제 동작이 필요하면 조사 카드 |

### 9.6 영속성과 중단 복구

원 요청은 현재처럼 `유지보수 라우팅 대기` 줄에 먼저 착지한다. 질문 전에는 원문이 복구
기록이다. 기본안 A에서는 답을 받은 뒤 card와 plan commit으로 바로 진행하지만 그 사이에
중단되면 다음 세션이 원 요청과 현재 Layer 0에서 같은 질문을 만들고 답을 다시 묻는다. 답을
추측하거나 원 요청만 소비하지 않는다. 질문 답이 product/arch를 바꾸면 해당 단계의 기존
확인·commit 경계를 따른다. split에서 닫힌 답은 card의 `목적지·왜·금지·완료 신호`가 기록이다.
D13에서 대안 B가 선택된 경우에만 §5.7의 예약 planning-frontier 상태와 소비 규칙을 적용한다.
별도 기획 파일은 어느 안에서도 만들지 않는다.

## 10. `design`과 기존 조사 카드의 자리

### 10.1 design은 이번에 바꾸지 않는다

UI의 색·타이포·토큰·component-library 전략은 여전히 `design`이 소유한다. product는 화면·창구와
사용자 결과, split의 작은 범위 보강은 상호작용 목적지를 다룬다. 시각 해법을 둘이 침범하지
않는다.

product 질문 중 “어떤 화면이어야 하는가”가 나오면 화면의 존재·사용자 결과까지만 product에서
닫고, 구체적 레이아웃은 design으로 미룬다. split 중 기존 화면의 작은 상호작용이 비면 목적지
보강으로 닫되 design token이나 component library를 재결정하지 않는다.

### 10.2 조사 카드는 살아 있다

공통 기획 증거 규율이 조사 카드를 대체하지 않는다.

| 시점 | 도구 |
|---|---|
| Layer 0 결정을 지금 바꿀 외부 사실 | product/arch/adopt의 즉시 조사 |
| Layer 0를 안전하게 유지한 채 구현·부하·실호출에서만 얻는 사실 | arch 잠정값 + split 조사 카드 |
| 유지보수 카드 목적지를 추측하게 만드는 사실 | split 조사 카드 |
| 이미 카드가 열린 뒤 구현 중 발견한 미지수 | 현재 checkpoint → split이 조사 카드 추가 |

조사 답이 상위 문서를 반증하면 현재 환류 규칙이 그대로 작동한다. 새 companion은 그 경로를
복제하지 않는다.

## 11. `work`·`verify` 수렴 루프 — 세 선택지

### 11.1 먼저 고칠 진단 문장

이번 축은 “검토와 검증이 역사를 남기지 않는다”를 전제로 하지 않는다. 현재 구조의 판정은
다음 한 문장이다.

> reviewer와 verifier는 깨끗한 무상태 역할이고, work 진행 로그와 verify.md·수정 카드·완료
> 신호·폴더 전체 회귀는 이미 상태를 남긴다. 부족한 것은 기록이 아니라, 완료된 수리의 정확한
> 신호가 다시 실패했을 때 그 기록을 같은 수리 계보로 읽고 다음 행동을 강화하는 소비 규칙이다.

reviewer 쪽에는 독립적인 무한 루프가 없다. 한 호출에서 `지적 → 수정 → 재검토`, diff가 바뀌면
완료 신호 재실행, 세 번째 실패에서 사람이라는 종료가 있다. 해소된 지적을 별도 영구 목록으로
남기지 않지만 필요한 구현 결정·실행 결과는 카드 진행 로그가 소유하며, reviewer에게 그 역사를
주는 것은 DD-19를 약화시킨다. 이번 선택지는 reviewer contract를 바꾸지 않는다.

verify 쪽에는 **교차 폐쇄의 무상한 반복 가능성**이 남는다. 각 실행은 끝나고 각 실패는
내구화되며 새 카드마다 사용자 승인을 받으므로, 현행만으로 사람 없는 무한 루프가 생긴다고
말하면 틀리다. 다만 같은 완료 신호가 되돌아와도 새 출처 id·새 수정 카드로 시작할 수 있어,
사용자가 매번 승인하는 동안 `검증 → 카드 → work → 검증`에 별도 수렴 상한이 없다. 이는 상태
소실이나 승인 우회가 아니라 반복을 한 계보로 소비하지 않는 문제다. 아래 세 안은 이 경로를
서로 다른 비용으로 다룬다.

### 11.2 L-A — 현행 유지와 관측

**동작.** 배포 문장을 바꾸지 않는다. verifier의 current 실패 기록이 이미 수정 전의 red
증거이고, 그 재현이 수정 카드 완료 신호가 되어 work 뒤 실행되며, verify가 원래 장면과 폴더
전체 회귀를 다시 실행한다. DD-24가 stale로 만드는 것은 통과 증거이지 과거 failure가 아니다.
한 verify가 F1·F2를 내고 C1이 코드를 바꾼 뒤 C2를 시작하면 F2가 이미 사라졌을 수 있지만,
능력 verify는 카드가 모두 `.done`이기 전 재실행할 수 없다. work에서 같은 신호를 무조건 한 번
더 실행하는 절차는 추가하지 않는다. 이것은 현행 수용 한계이며, 없애려면 일반 버그 진단과
실행 순서를 별도로 다시 열어야 한다.

**사는 것.** 새 하네스 비용과 기존 결정 충돌이 0이다. §14.4의 재발률·카드 수·추가 시간만
현장 report에서 관측해 실제 문제가 있는지 먼저 증명한다. 반복 재발이 거의 없다면 가장
경제적인 선택이다.

**못 사는 것.** 완료된 수정 카드의 신호가 다음 폐쇄에서 다시 실패해도 그 재관측 횟수와 앞선
수리를 연결하지 않는다. A↔B 진동과 반복 미검증은 사용자 승인을 매번 거쳐 새 카드로 진행할
수 있다. 즉 현재 루프의 강점과 승인 관문은 인정하지만, 승인된 반복들이 수렴하지 않는
가능성은 수용한다.

**예상 비용.** deploy 순증·추가 실행·추가 질문 0. 측정 항목과 report 비용만 있다.

### 11.3 L-B — 기존 기록을 소비하는 유계 수렴안 **(권장)**

L-B는 현재 신호 고리를 바꾸지 않고 새 파일·새 역할 없이 verify.md와 카드 번호를 수리 계보로
연결한다.
“같은 실패처럼 보임”이라는 의미 판단을 쓰지 않고 다음 기계 식별만 쓴다.

1. verify가 능력 회귀 묶음을 만들 때 각 완료 신호에 정확한 완료 카드 번호를 붙인다.
2. verifier는 실패 또는 미검증인 회귀 신호의 카드 번호와 실행 증거를 반환한다. 여전히 과거
   카드·verify.md·diff는 받지 않고 현재 묶음과 verify channel만 본다. 실패와 미검증을 같은
   결함이라고 부르지는 않지만, 어느 쪽도 현재 완료 신호가 수리 경계를 다시 신뢰하게 만들지
   못한 **재관측 한 번**으로 센다.
3. 메인은 모든 verify.md 본문을 열지 않고 정본 경로 순서의 기계 투영으로
   `검증 대상 key·실패 출처 id·라우팅된 수정 카드 번호·기존 수리 계보 key·재관측 최댓값`만
   얻는다. 검증
   대상 key는 트리 루트면 `product`, 능력이면 상태 접미사가 아닌 고정 능력 번호다. 그 번호가
   과거 실패 이력의 `라우팅: 수정 카드 <번호>`에 정확히 한 번 있으면 **완료된 수리의 재발**이다.
   최초 failure history의 `<검증 대상 key>@<출처 id>`를 수리 계보 key로 쓴다. 경로를 쓰지
   않으므로 능력 폴더가 `.done`에서 열리거나 다시 닫혀도 key가 움직이지 않는다. source id와
   고정 능력 번호를 조합할 뿐 별도 UUID나 증상 fingerprint를 만들지 않는다.
4. 재발 관측도 DD-30대로 새 출처 id와 자기 `라우팅: 대기`를 가진 **새 실패 이력 항목**이다.
   실제 실패인지 접근 부재 미검증인지 불안정 미검증인지 그대로 보존하고, 세 경우 모두
   `재발 카드`, `수리 계보 key`, `재관측 <같은 key 항목의 현재 최댓값+1>`을 함께 남긴다.
   `재관측`은 동일 원인 실패 횟수가 아니라 **완료된 수리 경계의 현재 신호가 pass를 주지 못한
   verify 실행 횟수**다. 따라서 미검증을 실패라고 오기하지 않으면서도 미검증 카드가 직렬로
   무한 발급되는 경로를 같은 상한에 넣는다. 그 항목에서 카드가 만들어지면 다음 재관측은 기존
   라우팅 결과와 key별 최댓값을 따라 같은 계보와 재관측 수를 기계적으로 복원한다. root
   항목 자체는 재관측 0이며 아직 재발 항목이 없으면 최댓값 0이다. 한 카드
   번호가 둘 이상의 root에 있으면 어느 root도 올리지 않고 `수리 계보 판정 불가`와 후보 key를
   보고해 사람 관문으로 간다. 정확히 하나의 완료 카드를 가리키지 않거나 능력 key가 현재
   정확히 하나의 verify.md로 해결되지 않으면 정합성 이상이다. 어느 경우에도 의미로 고르지
   않는다.
5. 카드 번호가 과거 수정 라우팅에 없으면 새 수리 계보다. 기존 경로로 새 출처 id와 수정 카드를
   만들며 다른 계보의 횟수를 올리지 않는다.

중간 pass는 그 verify 실행을 non-pass로 세지 않지만 기존 재관측 최댓값도 지우지 않는다. pass로
수를 0으로 되돌리면 `실패 → pass → 실패`와 A↔B 진동이 매번 첫 재관측으로 돌아가 상한을
우회한다. 이는 “같은 원인”의 영구 낙인이 아니라 같은 완료 수리 경계가 지금까지 몇 번 신뢰를
잃었는지를 보존하는 보수적 선택이다. 오래 뒤의 무관한 변화까지 같은 경계로 묶는 비용이 싫으면
소유자는 L-A를 고른다.

여기서 기계적으로 같은 것은 **결함 원인이나 오류 문구가 아니라 완료된 수리 카드의 계약**이다.
한 완료 신호가 복합일 수 있고 실행 불가가 드러나면 같은 카드의 문구가 교체될 수도 있다.
L-B는 “같은 버그가 또 났다”고 주장하지 않는다. “과거 실패를 닫았다고 완료된 카드 C의 현재
완료 신호가 다시 실패했다”를 같은 **수리 계보**로 센다. 서로 다른 하위 검사가 차례로 실패해도
같은 수리 경계가 반복해서 신뢰를 잃은 것이므로 두 번째 재관측에서 사람이 전체 경계를 보는
것이 목적이다. 원인 동일성을 자동 판정하지 않는 이 보수적 상한을 소유자가 원치 않으면 L-A를
고른다.

한 실행 결과가 동일한 명령을 공유한 카드 label 여러 개에 붙으면 먼저 각 label의 root key를
기계적으로 구한다. 모든 label이 같은 root 하나로 모일 때만 그 verify 실행의 재발 한 번으로
센다. root가 둘 이상이거나 root 있는 label과 없는 label이 섞이면 어느 root도 올리지 않고
`수리 계보 판정 불가`로 사람에게 카드 번호·후보 key를 보여 준다. 전부 root가 없으면 새 실패
하나로 라우팅하되 조사 카드가 카드별로 구분되는 신호를 먼저 만든다. 같은 실행 결과를 label
수만큼 실패로 복제하지 않는다.

정확한 행동은 다음과 같다.

```text
새 실패
  → 현재 verify 라우팅 그대로 수정 카드
  → current verifier 실패를 카드 출처로 보존 → fix → 같은 완료 신호 통과 → 원래 장면+폴더 전체 회귀

완료된 수정 카드의 신호가 처음 pass를 주지 못함 (`재관측 1`)
  ├─ 접근 불가·실행 결과 없음
  │    → 현재 미검증 항목에서 접근·결과 공백을 해소하는 수정 카드 하나만 통상 라우팅
  │    → work가 그 카드의 기존 증거 대기에 들어가면 카드가 끝날 때까지 verify 재실행 불가
  ├─ 접근은 됐지만 같은 revision·같은 신호에서 pass/fail이 함께 관측됐거나 신호가 스스로
  │  `간헐적`이라고 보고한 불안정 미검증
  │    → 현재 미검증 항목에서 조사 카드 하나만 통상 라우팅
  │    → 산출물은 유계 표본의 증상/실패율과 agent-runnable 신호 가능 여부
  ├─ 실제 실패 + label 하나가 완료 신호 하나를 지목하고 그 증거가 현재 재현의 정확한 증상 한 개를 판정
  │    → 새 수정 카드 안에서 깨끗한 컨텍스트 진단
  │    → 원인 가설 하나 + 그 가설이 맞을 때 관측될 예측 하나를 진행 로그에 착지
  └─ 그 밖의 실제 실패: aggregate 안에만 있음·다른 실패도 함께 냄·간헐적·원래 증상을 직접 판정 못함
       → 조사 카드 하나만 통상 라우팅해 더 좁은 실행 신호의 가능 여부와 근거를 산출

같은 수리 계보의 두 번째 이후 non-pass (`재관측 2 이상`; 실패·미검증 어느 쪽이든)
  → 지금까지의 카드 번호·원래 신호·조사 답·관측된 결과만 보고하고 사람 호출
  → 두 번째 보조 조사/접근 해소 카드 또는 세 번째 ordinary repair card를 자동 제안하지 않음
```

이 사람 호출을 새 상태로 만들지 않는다. 현재 실패 이력 항목의 `라우팅: 대기`를 유지하고,
resume은 기존 우선순위대로 verify로 돌아와 같은 보고만 복원한다. 소유자가 미루면 새 출처
id·카드·verify 실행을 만들지 않는다. 소유자가 현재 정본의 최종 라우팅 가운데 구체적인 수정
카드·문서 교체·product 재실행을 고르면 그 선택만 기존 라우팅 쓰기 순서로 착지시킨다. 추가
카드를 고르는 것은 L-B의 자동 권고가 아니라 **계보·재관측 2 이상을 본 소유자의 명시적
예외**이며,
재관측 수를 초기화하지 않는다. 따라서 새 `사용자 결정 대기` 문법이나 네 번째 최종 라우팅 값을
숨겨 넣지 않는다.

그 대신 현재 `라우팅: 대기`의 우선순위도 그대로 산다. resume은 이 행을 일반 work·새 요청·다른
능력 검증보다 먼저 verify로 보내므로, 소유자가 결정을 미루면 **그 계보만이 아니라 devflow의
다른 진행도 같은 보고 앞에서 멈춘다.** 이는 L-B가 새로 만든 봉쇄가 아니라 현재 미해소 검증
실패의 전역 우선순위를 보존한 결과다. 계보 하나만 미루고 다른 작업을 계속하려면 사건 절의
`사용자 결정 대기`와 비슷한 skip/priority·resume 소비 규칙이라는 새 상태가 필요하다. 그 구조
변경은 L-B에 숨기지 않고 L-C 또는 별도 후속안에서 소유자가 선택한다.

clean diagnosis는 새 등록 역할이 아니다. work의 기존 고착 탈출과 같은 방식으로 카드의 진행
로그 절을 뺀 본문·현재 실패 신호·관측 증거만 깨끗한 컨텍스트에 주는 일회성 진단이다. 구현
이력·이전 설명을 주지 않는다. 진단이 코드를 고치거나 통과 판정을 내리지 않으며, 메인 work가
가설과 예측을 진행 로그에 기록한 뒤 구현한다.

불안정 신호는 모든 검증을 세 번 돌리는 전역 규칙으로 해결하지 않는다. 같은 입력 revision과
같은 신호 안에서 pass/fail이 함께 관측되거나, 신호 자체가 “간헐적”을 보고하면 한 번의 pass로
닫지 않고 미검증으로 둔다. 조사 카드의 목적지는 “항상 통과하는 테스트”가 아니라 **관측한
실패율 또는 정확한 증상을 판정할 수 있는 agent-runnable 신호가 가능한지와 그 근거**다. 완료된
조사 카드의 신호는 현행 verify 규칙대로 답과 근거만 메인이 확인하고 verifier 회귀 목록에서는
뺀다. 이미 끝난 원 카드의 완료 신호를 몰래 바꾸거나 조사 결과를 자동 pass로 쓰지 않는다.
다음 verify에서 원 신호가 pass면 닫고, 다시 실패·미검증이면 `재관측 2` 사람 관문이 조사 답을
소비한다. 따라서 조사 결과의 소비자는 자동 verifier가 아니라 그 유계 관문의 결정 보고이며,
같은 조사 카드를 두 번째로 만들지 않는다. 신호마다 필요한 표본이 다르므로 전역 `N회`를 정본에
박지 않는다.

이 상한은 의도적으로 보수적이다. 재관측 1이 접근 부재였고 접근 해소 카드 뒤 처음으로 정확한
코드 실패가 보이더라도 그것은 이미 재관측 2이므로 자동 clean diagnosis를 새로 열지 않고
사람에게 간다. 접근 문제와 코드 결함을 별도 원인으로 추측해 횟수를 리셋하면 그 분류 자체가
semantic detector가 되고 순차 미검증 루프가 다시 열린다. 자동 수리 기회를 하나 더 사는 쪽이
중요하다면 L-B의 상한을 흐리지 말고 상태·예산을 명시하는 L-C를 고른다.

한 failure root가 `수정 카드 C1+C2`처럼 여러 카드로 라우팅될 수 있다. 같은 verify 실행에서
C1과 C2가 모두 실패해도 재관측을 두 번 올리지 않는다. verify가 새 항목을 쓰기 **전** root별
현재 최댓값을 한 번 고정하고, 그 실행에서 같은 root로 돌아온 항목 전부에 같은 `재관측
<최댓값+1>`을 쓴다. 다음 verify 실행에서 다시 돌아와야 다음 재관측이다. 한 실행에서 카드 수가
많다는 이유로 즉시 사람 관문을 열지 않는다.

L-B가 기계적으로 잇는 범위는 현재 능력 회귀에 들어온 비-`.stale.` `.done.` 카드와 current-form
route뿐이다. `.stale.` 카드 신호는 현재 회귀 입력이 아니고, route가 없는 legacy 실패는 카드
번호로 연결할 수 없다. 이 경우 비슷한 문구라는 이유로 과거 root를 복원하지 않고 새 실패로
다룬다. `.stale.` 교체는 사용자 승인 계획을 거치므로 이 경계가 사람 없는 무한 반복을 만들지는
않지만, 과거와 의미상 같은 결함을 새 root로 셀 수 있는 한계는 report에 남긴다. 이를 없애려면
stale replacement lineage라는 별도 상태가 필요하므로 L-B에 숨기지 않는다.

A↔B 진동을 별도 semantic detector로 만들지 않는다. 현재 활성 카드에서 과거 수정 카드 A의 신호가 B 수정 뒤
다시 실패하면 A 계보의 재발로 이미 잡힌다. 서로 다른 두 계보가 번갈아 한 번씩만 재발해도
각 계보는 자기 유계 관문을 향해 전진한다. 사용자 보고에는 “이전 완료 신호의 재발”과 관련
카드 번호를 보여 진동 가능성을 드러낸다.

**왜 권장하는가.** 새 파일이나 역할 없이 현재 실패 이력·출처 id·수정 카드·회귀라는 자산을
실제로 소비한다. 정상 pass와 일반 work/reviewer에는 추가 실행·질문·commit이 없고, 반복이 관측될 때만
진단 강도가 오른다. DD-19의 깨끗한 역할, DD-25의 카드별 승인, DD-08의 TDD 비차용을 지키면서
현재 verify 교차 폐쇄에서 승인 뒤에도 같은 유형의 카드가 계속 제안될 수 있는 경로에 유한
상한을 둔다.

**정직한 비용.** 정상 pass도 기존 회귀 신호에 카드 번호 label을 붙여 verifier 입력과 메인의
파싱이 조금 늘어난다. 추가 실행·질문·commit은 0이지만 prompt 비용까지 0이라고 주장하지 않는다.
verify.md 실패 이력 문법, verifier 반환, 검증 묶음의 카드 번호, resume 유계
투영의 변경 필요 여부와 repository invariant를 함께 판정해야 한다. verification predicate가 이
판정을 소유하지 않으면 중복해 고치지 않는다. “한 문장 추가”가 아니다.
실패 계보를 정확히 복원하지 못하면 L-B를 축소 구현하지 않고 L-A로 내려야 한다.

### 11.4 L-C — 명시적 repair episode와 사전 승인 예산

L-C는 실패마다 별도 수리 episode를 열어 신호·가설·시도·결과·남은 자동 예산을 한 상태로
관리한다. 소유자가 미리 허용한 범위에서 진단 카드와 한 번의 수리 카드를 자동 승인하고, 예산
소진·경계 변화·같은 실패 재발 때만 사람을 부를 수 있다. 사람 개입 최소화와 관측성은 가장
높다.

그러나 이 안은 현재 체계 위의 작은 보강이 아니다.

- 새 카드가 만들어지기 전에 승인 범위를 기록하고, 나중 카드의 목적지·금지·완료 신호가 그
  범위 안인지 판정해야 하므로 DD-25의 “존재하는 정확한 카드별 승인” 이유를 다시 열어야 한다.
- episode를 새 파일로 두면 DD-28·DR-09와 충돌하고, verify.md에 넣어도 producer·consumer·cleanup·
  중단 복구·동시 수리 병합 문법이 새 상태 기계가 된다.
- 자동 진단이 product/arch 경계를 발견했을 때 예산을 소비할지 중단할지, 원격 증거가 오래
  대기할 때 episode를 닫을지, 두 능력 실패가 한 shared 원인을 가질 때 누가 소유할지까지
  설계해야 한다.
- 자동 승인이 있어도 외부 write·비용·권한·Layer 0 변경은 사람 없이 진행할 수 없으므로 완전
  무인이라는 약속은 거짓이다.

따라서 L-C는 **현장 관측으로 L-B의 카드 승인 왕복이 실제 병목임이 확인된 뒤** 별도 라운드에서
검토할 후보이지 v0.15 기본안이 아니다. 소유자가 L-C를 선택하면 이번 planning 개선과 분리하고,
DD-25·28의 기록된 이유를 반박한 preview와 상태 전이 표를 먼저 승인받는다.

### 11.5 세 안의 선택 판정

| 기준 | L-A 현행 관측 | L-B 유계 수렴 | L-C repair episode |
|---|---|---|---|
| 현재 구조 보존 | 가장 높음 | 높음 | 낮음 |
| 같은 실패 반복 방지 | 낮음 | 높음 | 가장 높음 |
| 정상 경로 추가 비용 | 없음 | 카드 label prompt·파싱만 증가 | 상태 확인 비용 가능 |
| 실패 경로 추가 비용 | 없음 | 재발 때만 진단/조사 | 모든 episode 상태 관리 |
| 중단 복구 | 현재 수준 | 기존 verify.md·카드로 복원 | 새 상태 전이 전체 필요 |
| 사람 없는 수리 범위 | 현재 승인 카드 안 | 현재 승인 카드 안 | 사전 승인 예산까지 가능 |
| 재발 결정을 미룬 범위 | 현행 실패 라우팅이 전역 선행 | 기존 `라우팅: 대기`라 전역 선행 | 새 episode를 고르면 계보-local 대기 설계 가능 |
| 잘못된 계보 판정 위험 | 없음 | 카드 번호 규칙으로 낮춤 | episode scope 판정이 새 위험 |
| prompt·구현 복잡도 | 낮음 | 중간 | 매우 높음 |
| 이번 라운드 권고 | 보수적 대안 | **권장** | 현장 근거 전 보류 |

권장 선택은 **L-B**다. 단, 후속 계획의 literal walk에서 “과거 실패 → 수정 카드 번호 → 현재
실패한 회귀 번호 → 계보 출처 id”를 모든 중단 지점에서 유일하게 복원하지 못하면 L-B를 억지로
통과시키지 않는다. 그때는 L-A를 v0.15에 넣고 L-B를 다음 라운드로 분리한다. L-C는 카드별 승인 왕복이
실제 수렴 병목이라는 실측 없이 선택하지 않는다.

### 11.6 자동화가 약속할 수 있는 범위

L-B를 골라도 현재 devflow는 완전 무인이 아니다. 새 수정 카드의 실행 제안 승인, product 문구
변경, 외부 권한·비용·write, 재관측 2 이상은 사람 관문이다. L-B가 사람 없이 개선하는 범위는
**이미 승인된 카드 안의 구현·신호 실행·깨끗한 검토·검증과, 다음 사람 관문에 도달하기 전
증거의 품질 향상**이다. 이 경계를 “사람 개입 없는 루프”라고 과장하지 않는다.

완전 무인보다 중요한 안전 성질은 다음 세 가지다.

1. 같은 실패 신호를 고치지 못한 채 ordinary repair를 자동으로 무제한 제안하지 않는다.
2. 새 실패는 이전 실패의 횟수에 잘못 합치지 않는다.
3. 사람을 부를 때는 원래 신호·수리 카드·가설·관측 결과가 디스크에서 복원된다.

| D17 | 자동 수리 승인 | 현재 카드별 승인 유지. 사전 승인 episode는 L-C를 고를 때만 별도 반전안 | 권장 | DD-25 보존, “완전 무인” 과장 방지 |

### 13.1 다음 대화에서 먼저 확인할 결정

전부 한꺼번에 묻지 않는다. 첫 독립 감사가 중간 소실을 찾았고, 수리 재감사는 generic journal
재사용이 복구 경로가 아니며 메시지→파일 쓰기 원자성을 만들 수 없음을 찾았다. 따라서 거짓
“소실 0” 대신 D13을 명시적 비용 선택으로 먼저 확인한 뒤 가장 큰 제품 조합을 다룬다.

1. D13 — 재질문·재조사를 허용하는 A와 새 정본 상태·초기 commit을 사는 B 중 어느 쪽인지.
2. D14 — 현재 기억을 정확히 인정한 뒤 L-A/L-B/L-C 중 어느 수렴 비용을 살지. 권장은 L-B다.
3. D4 — 작은 범위 기획을 이번 릴리스에 포함할지.
4. D5 — 의미 삼각형의 밀도가 소유자가 원한 “왜·결과”를 충분히 보존하는지.
5. D10 — 작은 범위 한 묶음 뒤 상위 환류가 너무 이른지, 사용성에 맞는지.

이 다섯 결정이 바뀌면 파일 범위·크기·검증 좌표가 함께 바뀐다. 나머지는 그 뒤 확정한다.

## 14. 객관 평가와 결과 예측

### 14.1 평가 방법

아래 점수는 실측이 아니라 **같은 시나리오에 세 설계를 적용한 구조 예측**이다. 1~5점,
가중치 합 100이다. 무엇이 좋아 보이는지가 아니라 각 설계가 문장으로 보장하는 경로만
점수에 넣었다.

| 지수 | 가중치 | 현재 devflow | 맷 방식 직접 이식 | 권장 융합안 |
|---|---:|---:|---:|---:|
| 사실 근거 정확도 | 15 | 2.0 | 4.2 | 4.5 |
| 결정 프런티어 완성도 | 15 | 3.4 | 4.6 | 4.5 |
| 프로젝트 전체 일관성 | 15 | 4.8 | 3.0 | 4.8 |
| 작은 범위 기획 적합도 | 15 | 2.3 | 4.6 | 4.2 |
| 사용자 왕복 효율 | 10 | 4.2 | 2.6 | 4.3 |
| 사람 없는 사실 수렴 | 10 | 3.0 | 3.8 | 4.3 |
| 중단 복구·다음 세션 도달 | 10 | 4.8 | 3.2 | 4.4 |
| prompt·실행 비용 | 10 | 3.2 | 2.4 | 3.1 |
| **가중 합계 / 100** | **100** | **67.9** | **73.2** | **86.2** |

점수 근거:

- 현재안은 Layer 0와 디스크 복구가 강하지만 사실 조사와 작은 범위 보강이 명시돼 있지 않다.
- 직접 이식은 결정 발굴과 사실 조사에 강하지만 무제한 질문, 스킬 간 로드, 조사 파일
  소비·신선도, 재귀 위임에서 실제 rough edge가 있다.
- 융합안은 Layer 0·카드·확인 게이트를 유지하고 조사와 프런티어만 내부 primitive로 넣는다.
  기본안 A는 중간 대화를 재질문·재조사할 수 있으므로 복구 점수를 현재보다 낮춰 과장하지
  않는다. planning 소비자의 읽기 양이 늘어 prompt 비용도 현재보다 소폭 나빠질 수 있다.

### 14.2 수정 수렴 선택지 평가

이 표는 planning 점수와 섞지 않는다. 같은 검증 실패가 수리 뒤 재발하고, 중간 세션이 한 번
종료되며, 한 신호가 간헐적으로 흔들리는 고정 시나리오에 각 안을 적용한 구조 예측이다. 점수가
높을수록 좋고, `구현 단순성`은 복잡도가 낮을수록 높은 점수다.

| 지수 | 가중치 | 현재 devflow | 맷 진단 직접 이식 | L-A 현행 관측 | L-B 유계 수렴 | L-C episode |
|---|---:|---:|---:|---:|---:|---:|
| 같은 수리 경계의 무상한 반복 방지 | 20 | 2.5 | 3.0 | 2.5 | 4.7 | 4.9 |
| 깨끗한 판단 독립성 | 15 | 5.0 | 3.5 | 5.0 | 4.8 | 4.0 |
| 디스크 복구·도달성 | 15 | 4.8 | 2.5 | 4.8 | 4.8 | 4.5 |
| 종료 상한의 명확성 | 15 | 3.0 | 2.5 | 3.0 | 4.9 | 4.9 |
| 실패 신호의 질 | 15 | 3.5 | 5.0 | 3.5 | 4.2 | 4.7 |
| 정상 경로 비용 | 10 | 5.0 | 2.5 | 5.0 | 4.5 | 3.0 |
| 구현 단순성 | 10 | 5.0 | 3.0 | 5.0 | 3.5 | 1.5 |
| **가중 합계 / 100** | **100** | **78.9** | **63.5** | **78.9** | **90.9** | **82.9** |

현재 점수가 낮지 않은 이유는 사용자의 기억이 맞기 때문이다. 실패 이력·수정 카드·신호
회귀·세션 복구가 이미 강하다. 맷 직접 이식은 신호 품질은 가장 강하지만 그 자체에는 devflow의
카드 승인·내구 상태·전역 반복 상한이 없어 전체 흐름으로는 낮다. L-A는 싸지만 반복 정체성을
닫지 못한다. L-A는 현행 유지라 같은 점수다. L-C는 반복 방지 자체는 가장 강해도 아직 없는 상태 기계와 승인 의미가 점수를
깎는다. L-B는 현재 자산을 가장 많이 재사용하면서 열린 교차 폐쇄 루프만 닫아 권장된다.

예측 민감도도 기록한다. `구현 단순성` 가중치를 10에서 20으로 두 배로 올리고 반복 방지를
20에서 10으로 낮춰도 L-B가 L-A보다 근소하게 앞선다. 반대로 실제 현장에서 반복 재발이 거의
없다면 L-B의 편익은 발생하지 않으므로 L-A가 더 경제적이다. 그래서 후속 report는 재발률과
추가 실행 시간을 반드시 측정해야 하며 90.9를 성과 수치로 인용하지 않는다.

### 14.3 시나리오별 예측

| 시나리오 | 현재 | 직접 이식 | 권장 융합안의 예상 결과 |
|---|---|---|---|

| 최신 API 제약이 MVP를 바꿈 | 사용자 추측·모델 기억 위험 | 조사 강함, 별도 파일/skill 연결 필요 | product가 1차 출처 확인 후 결정만 묻고 product 문장에 결론 착지 |
| stack 호환성이 핵심 | 추천 근거가 기억에 의존 | research 후 grill, 연결 성공에 의존 | arch가 후보 전 차단 사실 확인, 불가능 후보 제거 |
| 오래된 SDK 브라운필드 | 코드는 강하지만 외부 version 계약 구분 약함 | repo context는 읽지만 최신 자료 오용 가능 | adopt가 lockfile version과 현재 코드·미래 의도를 분리 |

| UI 느낌을 말로 못 정함 | design까지 미루거나 추측 | prototype 강함 | split 조사 카드 또는 design으로 보내고 Layer 0 전 생산 코드 쓰기 금지 |

| 완료된 수정 신호 첫 non-pass | 새 실패·미검증과 새 카드가 될 수 있음 | 다시 진단하지만 내구 계보·상한 없음 | 카드 번호로 같은 계보를 복원하고 신호 상태에 따라 카드 하나만 제안 |
| 같은 계보 두 번째 non-pass | 새 출처 id·카드가 계속 가능 | 진단 반복 상한 없음 | 사람 관문, 수리·조사·접근 해소 카드 추가 금지 |
| 새로 생긴 다른 실패 | 새 출처 id·카드 | 새 진단 | 과거 계보에 합치지 않고 현재 정상 라우팅 |
| A↔B 회귀 진동 | 전체 회귀가 매번 잡지만 진동 소비 없음 | 원래 장면은 재실행하나 상한 없음 | 실패한 완료 카드별 계보가 각각 전진해 유계 관문에 도달 |
| 간헐적 pass/fail | 한 번 통과로 닫힐 수 있음 | 재현율을 높이는 loop가 강함 | 한 번의 pass를 통과로 쓰지 않고 조사 카드 한 장의 답을 다음 non-pass 사람 관문에서 소비 |
| 원격 증거 계속 부재 | 미검증 기록은 남지만 재검증마다 새 카드 가능 | 사용자에게 증거 요청, 내구 상태 약함 | 접근 해소 카드 한 장 뒤에도 non-pass면 사람 관문. 직렬 카드 증식 금지 |

### 14.4 구현 뒤 측정할 수치

실제 프로젝트와 고정 시나리오에서 다음을 센다.

1. **발견 가능한 사실을 사용자에게 물은 횟수.** 목표 0.
2. **현재 결정을 바꾸지 않는 자동 조사 횟수.** 목표 0.
3. **단순 프로젝트의 추가 질문 묶음.** 현재 대비 증가 0.
4. **작은 범위 등급 0/1/2 분포와 사용자 교정 횟수.** 1이 모든 요청을 삼키면 과잉이다.
5. **외부 사실을 근거로 한 구속 결정 중 정확 출처가 없는 수.** 목표 0.
6. **조사 원문용 새 Markdown 파일 수.** 목표 0.
7. **차단 사실이 잠정값/조사 카드로 잘못 밀린 수.** 목표 0.
8. **adopt에서 현재 동작과 원하는 방향을 사용자가 교정한 수.** 0이 좋은 것이 아니다.
   교정이 드러나는 것이 preview의 목적이다.
9. **planning 소비자별 추가 읽기 줄 수와 문자 수.** companion 포함 전·후 실측.

29. **L7 간헐적 신호** — 같은 revision의 유계 실행에서 pass/fail이 함께 나온다. `재관측 1`

### 15.4 좌표 스윕

구조 변경 뒤 다음 축을 곱한다.

```
단계       product | arch | adopt | split-maintenance
미지수     저장소 사실 | 외부 사실 | 실행 사실 | 소유자 결정
영향       차단 | 후속
출처 상태  settled | conflicted | unavailable
규모       카드 네 필드 확정 | 한 묶음으로 확정 | Layer 0 변화
도구       직접 가능 | 병렬만 가능 | 불가
```

각 칸을 `정의됨 / 해당 없음 / gap`으로 판정한다. 모든 조합을 장문의 시나리오로 걷지 않는다.
특히 다음 교차를 놓치지 않는다.

- product × 실행 사실 × 차단 × 도구 불가.
- arch × 외부 사실 × conflicted.
- adopt × pinned version 없음 × 최신 공식 문서만 있음.
- split × 한 묶음으로 확정 예상 × 답이 Layer 0 변화를 새로 엶.
- 모든 단계 × settled 또는 사용자 답 × 최종 착지 전 중단 × D13-A/B.
- 어느 단계든 병렬 작업자가 다시 위임하려는 경우.

수정 수렴 축은 별도로 다음을 곱한다.

```text
신호 출처   새 시나리오 | 일반 완료 카드 | verify-origin 완료 카드
관측        안정 실패 | 안정 통과 | 같은 revision 안 pass/fail | 실행 불가
계보        없음 | 첫 failure→C1 | 첫 재발→C2 | 두 번째 재발
시점        최초 verify | fix 직전(입력 동일|변경) | fix 뒤 | verify 회귀 | 상태 기록 뒤 중단 | 라우팅 뒤 중단
영향        같은 신호 | 다른 새 신호 | 다른 계보 신호 | 상위 문서 반증
```

각 칸을 `정의됨 / 해당 없음 / self-evident / gap`으로 판정한다. 특히 `새 실패×기존 계보`,
`구형 기록×재발`, `완료 카드 번호가 둘로 해결됨`, `카드가 .stale`, `원격 증거 대기 중 재검증`,
`접근 해소 카드 완료 뒤 다시 접근 불가`, `flaky 조사 완료 뒤 원 신호가 다시 미검증`,
`D13-B planning 상태와 D14-L-B verify 상태가 동시에 존재`를 따로 걷는다.

5건, 도달성 감리는 2건, 문자 실행 워커는 1건을 냈다. 같은 경로를 중복 보고한 항목은 아래
6개 실패 원인으로 합쳤다. 첫 패스에서 0건으로 꾸미지 않고 요청서 자체의 입력으로 쓴다.

| 소견 | 판정 | 이 요청서에 반영한 수리 | 재감사에서 볼 것 |
|---|---|---|---|
| S2 답변 뒤 card 전 중단이면 답 소실 | 유효한 기존 잔여 구간. 첫 수리안의 “소실 0” 주장은 명백 결함 | §5.7에서 A의 재질문과 B의 질문-before 상태를 분리. 어느 안도 메시지→쓰기 원자성을 주장하지 않음 | A는 원 요청 보존·재질문, B는 정확 질문 복구를 보이는가 |
| settled/conflicted/unavailable 뒤 최종 문서 전 중단이면 결론·출처 소실 | 유효한 중간 복구 공백. generic 줄 재사용은 불완전 | A는 재조사를 수용, B는 새 정본 상태 전체를 조건부 범위로 명시 | 소유자가 비용을 고르고 그 안의 보장만 주장하는가 |
| 3~5개 질문·라운드 상한·여섯 판단 완료가 동시에 성립하지 않음 | 명백 충돌 | 최대 5개, padding 금지, 라운드는 목표 예산으로 재정의 | 마지막 1~2개와 예산 초과에서 경로가 하나인가 |
| 명시 조사도 여섯 판단을 바꿀 때만 한다는 문장과 D7 충돌 | 명백 충돌 | 명시 요청은 항상 좁게 실행, 자동 trigger만 결정 영향 요구 | 비영향 명시 조사도 실행되되 product를 막지 않는가 |
| “한 축/두 축/유일함”이 모델 판단이라 1과 2가 흔들림 | 명백한 판단어 | 카드 네 필드와 정확한 Layer 0 필드 변화로 등급을 정의 | 같은 요청이 질문 개수 해석에 따라 달라지지 않는가 |
| 새 companion·명시 조사 형태의 canon 승격 범위 누락 | 명백 누락 | 문서 지도·용어 행·H42·정확 소비자 검사를 파일 지도에 추가 | 구현자가 design/map/matrix를 빠뜨릴 수 있는가 |

첫 수리분 재감사는 6건을 냈다. 중복을 합치면 네 실패 원인이다.

| 재감사 소견 | 판정과 2차 수리 |
|---|---|
| 사실/답 수신과 checkpoint 쓰기 사이에도 소실 구간이 남음 | 프롬프트로 원자화할 수 없다. D13-A 재실행과 B의 질문 복구로 보장을 낮춰 정확히 씀 |
| generic journal 줄은 생성 commit·봉쇄·resume 라우팅이 없음 | generic 재사용을 폐기. B는 새 예약 상태+principles+resume 전체일 때만 허용 |
| 병렬 결과 도착과 “즉시 한 줄” 규칙이 충돌 | checkpoint 규칙을 기본안에서 제거. B는 조사 전에 질문 묶음 하나를 기록하고 미완이면 묶음 전체를 재실행 |
| “가능한 답” 집합과 D13 인계 순서가 열림 | 실제 제시 선택지와 사용자의 실제 자유 답으로만 재판정하고, 인계는 D13부터로 맞춤 |

2차 수리분 재감사는 처음에 2건을 냈다. 같은 라운드의 request를 plan 전에 여는 배선이 없다는
죽은 소비 경로와, 이름 변경 뒤 “계획 감사/계획에 수리”가 남아 아직 없는 plan을 선행 조건으로
요구한 순환이었다. `AGENTS.md` 배선에 `현재 round request → handoff → plan` 순서를 추가하고,
§17을 `요청서 정리 → 후속 계획 → 소유자 구현 승인 → 구현`으로 분리해 수리했다.

그 수리만 본 마지막 독립 재감사는 **0건**이었다. request는 구현 승인으로 읽히지 않았고,
미확정 결정을 plan이 임의 확정하는 길도 없었다. §4.4의 보존 영향 원장은 D13-B를 포함한
구조 변경을 소유자 선택 전 구현 목록에 넣지 못하게 했고, 남은 `plan_ko.md` 표기는 모두 미래
산출물 또는 그 감사만 가리켰다. 이 요청서 감사 루프는 규칙 충돌·새 무기명 소실 경로 0,
채택 수리의 수렴이라는 §15.5 종료 조건으로 닫는다. D4·D5·D10·D13은 결함이 아니라 다음
대화에서 소유자가 고를 설계 판단이라 열린 채로 남긴다. 이 판정은 당시의 planning 축에 대한
것이다. 뒤에 추가된 수정 수렴 축은 아래 별도 재검증 기록으로 판단하며, D14~D17을 이 0건
판정에 소급해 포함하지 않는다.

### 15.7 수정 수렴 축의 독립 재검증과 판정

수정 수렴 축은 기존 reviewer·verifier·work·verify와 맷 포콕의 고정 snapshot을 따로 읽은
비교 렌즈부터 시작했다. 이 비교는 명백 결함 0건과 판단 후보 1건을 냈다. 후보는 일반 사용자
버그가 verify를 거치지 않고 work로 바로 들어올 때도 수정 전 정확 증상 신호를 요구할지였고,
이번 D14의 verify-origin 계보와 범위가 달라 차용하지 않았다.

요청서의 L-B 초안은 다음 순서로 독립 반증했다. 숫자는 중복 문구가 아니라 각 패스가 반환한
소견 수다.

| 패스 | 소견 수 | 실제로 닫은 실패 경로 |
|---|---:|---|
| 최초 수리 계보 반증 | 6 | 숨은 fix 직전 red 재실행, 증거 대기 죽은 경로, stale/legacy 연결 과장, 겹치는 분기, 복합 label 중복 합산, 정상 prompt 비용 0 주장 |
| 첫 수리 재감사 | 5 | failure stale 오기, 접근 부재의 카드·횟수 불일치, 분기 중첩, rename에 깨지는 path key, 비용 문장 충돌 |
| 두 번째 수리 재감사 | 2 | 미검증의 반복 문장 충돌, flaky 미검증의 죽은 분기 |
| root·라우팅 재감사 | 0 | `product|고정 능력 번호@출처 id`, 새 항목별 출처 id·라우팅 소유권, clean role·복합 신호·중단 복구가 수렴함 |
| 신선한 각도의 직렬 카드 감사 | 2 | flaky 조사 답의 자동 소비자가 없고, 완료된 접근 해소 카드 뒤 접근 부재가 다시 오면 카드가 직렬 증식함 |
| `재관측` 재설계 감사 | 명백 결함 2 + 판단 1 | `재관측 3+` 죽은 상태, self-reported flaky 분기 누락, 접근 부재 뒤 첫 실제 실패도 사람으로 가는 보수적 비용 |
| 마지막 채택 수리 재감사 | **0** | `재관측 2 이상` 단일 관문, flaky 두 입력, 직렬 접근 카드 상한, 기존 `라우팅: 대기` 복구가 모두 닫힘 |
| 독립 라우팅 우선순위 감사 | 명백 결함 0 + 판단 1 | `라우팅: 대기`를 미루면 같은 계보뿐 아니라 다른 work·요청·능력 verify도 멈춘다는 범위를 확인 |
| 전역 봉쇄 비용 반영 재감사 | **0** | 현행 우선순위 보존을 L-B의 비용으로 명시하고, 계보-local defer는 새 상태가 필요한 L-C/후속 선택으로 분리 |

이 과정에서 권장안은 “실패만 세고 미검증은 그대로 둔다”에서 **완료된 수리 경계의 current
신호가 pass를 주지 못한 verify 실행을 `재관측`으로 센다**로 바뀌었다. 그래서 실패와 미검증을
같은 원인이라고 주장하지 않으면서도 flaky 조사 카드와 접근 해소 카드의 순차 무한 발급을
같은 상한으로 닫는다. 조사 답은 자동 verifier 입력이 아니라 재관측 2 이상 사람 보고가
소비하고, 사람 호출은 새 상태가 아니라 기존 `라우팅: 대기`를 유지한다. 소유자가 미루면 다음
세션이 같은 보고를 복원할 뿐 새 실행·출처 id·카드를 만들지 않는다.

마지막 두 재감사의 0건은 **요청서 문장의 도달성과 규칙 충돌**에 대한 판정이다. L-B의 실제 수렴
성능, prompt 증가, 오탐 상한은 아직 구현·fixture·실전 report를 거치지 않았으므로 증명된 값이
아니다. D14~D17은 결함이 아니라 소유자가 고를 열린 결정이며, 후속 plan은 90.9 예측치를 성과
수치로 바꾸거나 L-B를 이미 승인된 설계로 취급하면 안 된다.

## 17. 요청서에서 계획·구현으로 가는 순서

### 17.1 요청서 정리

1. 복구 비용 D13과 수정 수렴 D14를 독립 선택으로 소유자와 확인한 뒤 D4·D5·D10을 조정한다.

## 18. 크기 예산

현재 계획 소비자는 이미 무겁다. 특히 v0.14.0 report는 arch 약 1,400줄, resume 약 1,636줄
읽기를 기록했고 D11을 다음 큰 비용 축으로 남겼다. 이번 릴리스가 그 문제를 모른 척하면 안
된다.

| 파일 | 순증 목표(영문 실줄) | 초과 시 행동 |
|---|---:|---|
| planning-evidence | 45~65 | 예시를 라운드 문서로 내리고 실행 규칙만 남김 |
| product | 20~35 | 기존 인터뷰 규칙과 합치고 중복 설명 삭제 |
| arch | 30~45 | 후보·잠정값·verify 절에 분산 복제하지 않고 companion 참조 |
| adopt | 25~40 | 내부 증거표를 절차 문장으로 압축하되 세 권위는 유지 |
| split | 20~35 | D4 미확정이면 이번 릴리스에서 제외 |
| D14-L-A | 0 | 현행 유지·관측안. deploy 파일을 고치지 않음 |
| D14-L-B 추가분: principles+work+verify+verifier | 30~50 | 계보 형식·두 분기·상한만 배포하고 비교 근거는 round 문서에 둠 |
| D14-L-B 조건부 resume | 0~8 | 기존 유계 투영으로 복원되면 0. 새 필드가 라우팅 선택에 필요함을 증명할 때만 추가 |
| AGENTS/tests/design | 행동에 필요한 만큼 | 보고·근거는 round report로 이동 |
| D13-B 추가분: principles+resume | 20~35 | 예약 상태 형식·전이·라우팅·소비만 두 정본에 두고 조사 분류는 companion에 둠 |

planning 기본안 A의 deploy prompt 순증 목표는 140~220줄이다. D14-L-A를 함께 골라도 같고,
권장 L-B를 고르면 170~270줄이다. D13-B까지 고르면 190~305줄이다. 그중 principles
증가분은 모든 스킬의 고정비이므로 3~5줄을 넘기지 않는 것을 목표로 한다. 두 큰 구조 선택인
D13-B와 D14-L-B를 함께 골랐다는 이유만으로 305줄 상한을 자동 허용하지 않는다. planning 축과
수렴 축을 차례로 적용·측정하고, 각 축의 실패 경로 없는 문장을 뺀 뒤 합계를 다시 승인받는다.

구현 report는 줄·단어·문자·대략적 토큰을 전후로 실측한다. 소스 순증뿐 아니라 호출별 실제
읽기량을 따로 센다. L-B는 정상 work/verify의 추가 실행·질문·commit이 0이어야 하고, 재발 때만
추가 읽기·실행 시간이 발생해야 한다. 목표를 넘으면 “좋은 설명”을 더하는 방식이 아니라 실패
경로 없는 문장을 뺀다.

## 19. 적용 뒤 예상되는 하루

### 새 프로젝트

사용자가 “결제 정산 도구를 만들자. 공급자 API도 조사해 줘”라고 말한다. product는 제품
질문과 API 사실을 한 묶음으로 던지지 않는다. 공급자 공식 계약에서 정산 지연·환불 제약을
먼저 확인하고, 그 제약 아래 어떤 사용자와 MVP 경계를 택할지만 묻는다. capability 한 줄은
“정산”이라는 이름보다 사용자가 얻는 결과와 성공 판정에 필요한 이유를 남긴다.

arch는 그 결과를 받아 후보를 만들기 전에 대상 런타임·SDK·검증 수단을 확인한다. 지원되지
않는 후보는 사용자에게 올리지 않는다. 부하에서만 알 batch 크기는 잠정값으로 남기고,
되돌리기 어려운 데이터 경계만 두 구조를 비교한다. 다음 세션은 링크만 보는 것이 아니라
선택 이유와 기대 결과를 arch.md에서 읽는다.

### 기존 프로젝트

adopt는 lockfile의 SDK 버전, 현재 코드 흐름, README 주장을 따로 본다. “지금은 전체 환불만
한다”, “공급자 계약은 부분 환불도 지원한다”, “앞으로 부분 환불을 원하는가”를 한 문장으로
섞지 않는다. 사용자가 마지막 결정을 내린 뒤 표준 product.md가 확정된다.

### 작은 기능

몇 주 뒤 사용자가 “정산 목록에 날짜 필터 모달을 넣자”고 한다. 현재 capability·리스트
계약에서 목적지는 거의 유일하지만 적용 시점만 비었다. split은 한 묶음으로 적용·닫기·0건
상태를 추천과 함께 묻고 카드 네 필드로 닫는다. 전체 product를 다시 열지 않고, 별도 기획
문서도 만들지 않는다. 반대로 새 관리자 역할까지 필요하다는 답이 나오면 카드를 만들지 않고
product로 돌린다.

### 수정이 한 번 되돌아올 때

정산 목록의 시간대 경계가 verifier에서 실패해 수정 카드 C1이 생긴다. 그 current 실패가 카드의
출처다. C1은 같은 브라우저 재현을 완료 신호로 받아 수정 뒤 통과시키고, verify는 원래
목록 장면과 폴더 전체 회귀를 다시 실행한다. 같은 verify에서 나온 다른 수정이 먼저 코드를
바꿔 이 실패가 이미 사라질 수 있는 현행 한계는 남고, work가 숨은 재실행 순서를 만들지 않는다.

며칠 뒤 다른 변경 뒤 C1의 신호가 다시 실패한다. 새 verifier는 과거 설명을 받지 않고 현재
신호만 실행한다. 메인이 실패한 회귀 label C1을 verify.md의 과거 수정 라우팅과 연결해 첫
재발로 판정한다. 신호가 안정적이면 새 승인 카드 안의 clean diagnosis가 원인 가설과 관측 예측을
남기고, 간헐적이면 조사 카드가 신호부터 좁힌다. 같은 계보가 한 번 더 되돌아오면 새 ordinary
repair를 발급하지 않고 지금까지의 카드·신호·관측을 사용자에게 보여 준다. 다른 새 결함이라면
C1 횟수를 올리지 않고 정상 실패 경로로 간다.

## 20. 이번 보장 밖과 다음 후보

- 조사 결과의 사실 정확도를 수학적으로 보증하지 않는다. 출처 소유권·version·충돌 표시는
  오판을 드러내는 장치다.
- 사용자가 모든 추천에 수동 동의하는 문제를 prompt만으로 완전히 막지 못한다.
- 실제 시장 조사 방법론, 고객 인터뷰 모집, 통계 설계는 이번 범위가 아니다.
- production에서의 지속적인 외부 사실 freshness 검사도 이번 범위가 아니다.
- prototype 전용 생애·branch·삭제 규칙을 새로 만들지 않는다. 기존 조사 카드와 안전한
  scratch 실행까지만 쓴다.
- D11 정본 소비자별 분할과 일반 사용자 버그를 위한 독립 진단 스킬은 섞지 않는다. 이번
  work/verify 범위는 verifier가 이미 실패·미검증을 기록해 만든 수정 카드와 그 완료 신호의
  재발뿐이다. 최초 버그 탐색 전체를 새 방법론으로 바꾸지 않는다.
- D13은 planning frontier 복구에만, D14는 verify-origin 수리 수렴에만 한정한다. 둘의 상태·
  비용·결정 번호를 합쳐 하나의 “루프”로 구현하지 않는다.
- D13-A에서는 최종 문서 전 조사 결론과 사용자 답을 다음 세션이 그대로 복원한다고 보장하지
  않는다. 재조사·재질문하되 추측하지 않는 것이 계약이다.
- 현장 실측 전에는 §14의 예측 점수를 성과 수치로 인용하지 않는다.

다음 후보는 실전 결과로만 연다.

- planning-evidence를 product/arch/adopt별 더 작은 projection으로 나눌 필요가 있는가.
- 작은 범위 등급 1의 질문 묶음이 실제로 한 번에 닫히는가.
- 반복되는 외부 사실에 freshness를 붙일 소비 경로가 필요한가, 아니면 매번 재조사가 싼가.
- UI/상태 모델 prototype을 design·split 사이에 정식으로 둘 필요가 있는가.
- L-B의 카드별 승인 왕복이 실제 병목이면 L-C 사전 승인 예산을 열 가치가 있는가.
- 재발률이 매우 낮아 L-B 계보 문법보다 L-A 신호 보존만 유지하는 편이 나은가.

### 21.1 완료 정의

이 요청서는 다음이 모두 참일 때만 “후속 계획 작성 입력 완료”다.

1. 결정 원장 전 행이 `확정`, `열림`, `이번 범위 제외` 중 하나이고 `열림`에는 선택지·영향·다음
   질문이 있다.
2. 요청서 독립 감사의 명백 결함이 0이다.
3. 각 배포 파일 변화가 왜·무엇·의도·예상 결과 넷을 갖는다.
4. P/A/B/S/E/R/L 시나리오가 결정 조합과 맞게 갱신됐다.
5. 크기 예산이 다시 계산됐다.
6. 소유자가 이 요청서를 바탕으로 `plan_ko.md` 작성을 명시적으로 승인했다.
