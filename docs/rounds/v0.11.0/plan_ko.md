## 0. 이 문서의 위치

핸드오프는 **문제와 제약**을 정의했다. 이 문서는 그 위에서 **설계를 확정하고 실행 순서를
정한다.** 핸드오프를 반복하지 않는다 — 다시 적은 곳은 판정이 바뀐 곳뿐이다.

**2판 개정 사유**: 1판을 외부(GPT)가 검토해 9건을 제기했고, 전부 현행 텍스트에 대고
재검증했다. **8건 타당(그중 4건 차단급) · 1건 무효.** 재검증 중 내가 추가로 찾은 결함 2건도
함께 반영했다. 판정 전문은 **11절**에 있다. 1판에서 바뀐 곳: 3.4 · 3.5 · 3.7 · 3.8 · 3.10 ·
5절 · 8절.

읽는 순서: 1절(의도 카드) → 2절(진단) → 3절(설계) → 4절(기각한 대안) → 5절(결정표)
→ 6절(변경 표면) → 7절(승계 검사) → 8절(검증 계획) → 9절(완료 조건) → 10절(위험)
→ 11절(외부 검토 판정).

**바쁘면 1절 · 2.2 · 3.1~3.4 · 5절 · 11절만 읽어도 판단할 수 있다.**

## 1. 의도 카드 — 드리프트 방지 장치

> 이 한 쪽은 **캠페인의 모든 에이전트에게 첫 입력으로 그대로 전달되고**, 모든 소견 판정은
> 여기의 항목을 인용해야 한다. 전 세션이 실패한 이유는 국소 최적화가 골격 질문을 가린 것이다
> (핸드오프 7.1). 이 카드가 그 재발을 막는 장치다.

**만들려는 것**: 능력 하나마다 파일 하나. 그 능력이 **무엇을 위해 있고, 무엇을 구현하며,
어디까지가 자기 것인가**를 기획 시점부터 담고, 검증 폐쇄마다 **실제로 확인된 현재**를 갱신한다.

**통과해야 하는 7가지** (핸드오프 2절, 축약 없이):

| # | 의도 | 통과 판정 |
|---|---|---|
| I1 | MVP 기획 단계부터 자리를 잡는다 | 첫 능력을 만들기 시작하는 시점에 그 문서가 이미 존재하는가 |
| I2 | product·arch에서 도메인을 추론할 수 있다 | 초기 내용이 실재하는 필드에서 기계적으로 도출되는가 |
| I3 | 도메인은 유연하다 (추가·삭제·개명) | 셋 다 정의된 절차가 있는가 |
| I4 | AI가 지시 없이 그 문서에 도달한다 | 카드 배선에 의존하지 않는 경로가 있는가 |
| I5 | 도메인 단위로 전문성이 자란다 | 폐쇄마다 개선되고, 그 개선이 다음 작업에 소비되는가 |
| I6 | 오해할 수 없는 프롬프트 | 새 문장마다 관측 가능한 디스크·git 조건으로 환원되는가 |
| I7 | 흐름 단위 검증 | 문장이 아니라 프로젝트 생애 단위로 워크했는가 |

**어기면 그 자체로 결함인 것** (핸드오프 1절): 양 플랫폼 동일 해석 · 설계는 한글/배포는 영문 ·
풍부한 방향성과 최소 하네스(**실패 경로 없는 문장은 결함**) · 기각 계보 반박 후 뒤집기 ·
한 개념 한 이름 · 정합성 점검은 보고만 · 지식층은 실행축을 막지 않는다.

**이번 재설계가 명시적으로 하지 않는 것**: 연대기 부활 · 인덱스 파일 · 버전 필드 ·
3중 다이제스트 복원 · 무유계 읽기 · 카드당 문서 2개 이상 읽기 · 규칙 정본 분할(별건) ·
**도메인 간 회귀 실행 확장**(2판에서 보고로 축소, 3.7 참조).

## 3. 설계

### 3.1 한 문장

> **능력 문서는 두 구역을 가진다. 설계 구역은 arch(브라운필드는 adopt)가 Layer 0 확정 직후
> 별도 커밋으로 쓰고 `Design head`가 지배한다. 검증 구역은 verify가 폐쇄 때 고정 경계 제목부터
> 파일 끝까지 전면 교체하고 `Scope head`·`Covered cards`가 지배한다. 두 구역은 서로의 출력이
> 아니고, 각 구역은 자기 신선도 도장을 자기 작성자가 찍는다.**

### 3.2 핵심 통찰 — 현행 12절은 **이미** 두 구역이다

```
코드 진술 (Scope head)  : 주 흐름 · 수명주기 · 진입점 · 함정 · Verify        ← 관측
문서 진술 (Docs head)   : 목적 · 개념 모델 · 현재 행위 · 불변식 · 하지 않기로 한 것  ← 결정
```

**두 번째 그룹에서 「현재 행위」 하나만 빼면 그것이 정확히 설계 구역이다.** 옵션 E는 구조
개편이 아니라 **이미 존재하는 절 그룹의 탄생 시점을 앞으로 옮기는 것**이다.

곁들여 현행 결함 하나가 교정된다: 「현재 행위」는 코드가 만드는 관측인데 `Docs head`가
지배한다. 검증 구역으로 옮기면 제자리를 찾는다.

### 3.3 문서 계약 — 13절

`devflow/project/capabilities/NN-<이름-슬러그>.md`. 정체성은 **능력 번호**(불변).

**구역 경계는 정확히 하나의 H2 제목이다**: `## Verified state`. verify의 쓰기 대상은
**"그 제목부터 파일 끝까지"**로 정의된다. 그 제목이 정확히 한 번 나오지 않으면 verify는
쓰지 않고 `baseline no-op: <사유>`를 보고한다(기존 비차단 경로).

- **총 상한 ~185줄** (설계 ~45 + 검증 ~140). **첫 12줄이 도메인 그 자체.**
- 9절의 **상대 능력 번호 열은 산문이다.** 기계는 경로만 읽는다. 번호가 낡아도 기계는 옳다.
- 코드나 다른 문서에 사는 계약의 **본문**을 옮겨 적지 않는다 — 위치와 불변식만.
- 검증된 내용이 없는 절에는 정확히 `None.`. 근거 없이 발명하지 않는다.
- **`external` 함정은 비구속 증거다.** work은 그 URL을 자동으로 열지 않고, 구속 결정을 뒤집지
  못한다. 삭제는 사람만 한다.

### 3.4 기계 블록 7필드 · 필드별 소유 · 신선도 3그룹

```text
Capability number: 02                          # arch·adopt 소유
Design head: <Design head 명령의 출력>          # arch·adopt 소유 — verify는 그대로 통과시킨다
Verified at: <YYYY-MM-DDTHH:MM:SSZ | none>     # verify 소유
Covered cards: ["02.1","02.2","02.2b"]         # verify 소유 · 중복 없음 · 정본 카드 번호 순서
Scope paths: ["src/payment/...", ...]          # verify 소유 · = capability code scope (불변)
Consumed paths: ["src/customer/contract.ts"]   # verify 소유 · 신규
Scope head: <Scope head 명령의 출력>            # verify 소유
```

**필드별 소유가 「구역당 한 작성자」를 완성한다.** 폐쇄의 전면 교체는 verify 소유 5필드만
바꾸고, `Capability number`와 `Design head`는 바이트 그대로 통과시킨다.

**명령**

- **Design head 명령**: `git log -1 --format=%H -- devflow/project/product.md
  devflow/project/arch.md devflow/project/code-style.md devflow/project/glossary.md
  devflow/project/design.md`. 이 다섯 경로는 고정이고, design.md가 없으면 그 경로는 출력에
  기여하지 않는다. **`decisions/`는 넣지 않는다**(사유는 5.2 D18).
- **Scope head 명령**: `Scope paths ∪ Consumed paths`의 각 원소를 `:(literal)` 경로 지정자
  하나씩으로 `git log -1 --format=%H --`에 넘긴다. **합집합이 비면 명령을 실행하지 않고
  코드 진술을 곧바로 가설로 판정한다** — 경로 지정자 없는 `git log -1`은 저장소의 마지막
  커밋을 돌려주므로 실행하면 안 된다.
- **`Consumed paths`는 새 추적이 아니다.** verify의 Standards 게이트는 이미 현재 위상을
  추적하다가 **"다른 능력의 경계 앞에서 멈춘다".** 그때 **멈춘 경계 경로들이 곧 `Consumed
  paths`다.** 계산 비용 0. (G3 해결: `Scope paths`는 손대지 않는다)

**쓰기 시점과 커밋 순서 — `Design head`가 태어나자마자 낡지 않게 하는 유일한 조건**

> **능력 문서 커밋은 그 arch/adopt 실행의 마지막 커밋이다.** 그 실행이 확정한 Layer 0 문서가
> 전부 착지한 뒤에 `Design head`를 계산하고, 능력 문서들만 한 커밋(`arch — capabilities` /
> `adopt — capabilities`)에 담는다. 그 커밋은 Design head 명령의 다섯 경로를 건드리지 않으므로
> 저장된 값이 커밋 직후에도 유효하다.

Layer 0 커밋과 능력 문서 커밋 사이에서 중단되면 Layer 0만 남고 문서가 없다 — 그 상태는
6절의 resume 라우팅 행이 회수한다.

**수용 한계 1건 추가**: multi에서 리베이스가 Layer 0 커밋 해시를 바꾸면 `Design head`가
움직여 설계 구역이 **보수적으로** 가설이 된다. 얕은 클론의 기존 수용 한계와 같은 부류이며,
재확인 비용이 0이므로(work이 product·arch를 이미 읽는다) 별도 장치를 만들지 않는다.

**신선도 판정 — 그룹이 셋이 된다** (G2 해결)

| 그룹 | 절 | 지배 비교 |
|---|---|---|
| **설계 진술** | 1·2·3·4 | `Design head`만. **판정 1·3의 지배를 받지 않는다** |
| **코드 진술** | 5~11 | `Scope head` 비교 + `Covered cards` 비교 |
| 어느 쪽도 아님 | 12·13 | ADR 경로는 **work이 읽을 때** 존재만 확인, 기계 블록은 비교자 자신 |

1. Scope head 명령 출력 = `Scope head` → 코드 진술 신선. 다르거나 비면 **가설**.
   합집합이 비면 명령 없이 **가설**.
2. Design head 명령 출력 ≠ `Design head` 이거나 비면 **설계 진술이 가설**.
3. 그 능력 폴더 아래 비-`.stale.` `.done.` 카드 번호 집합 ≠ `Covered cards` →
   **코드 진술이 가설**. 폴더가 없으면 빈 집합으로 본다.

**탄생 시점의 값**: `Verified at: none` · `Covered cards: []` · `Scope paths: []` ·
`Consumed paths: []` · `Scope head: none` · `Design head: <실제 값>`.
→ **판정 1이** 코드 진술을 가설로 만든다(정확하다 — 아직 검증된 것이 없다).
판정 3은 `[] = []`로 일치하므로 아무 말도 하지 않는다.
→ 판정 2가 설계 진술을 신선으로 준다(정확하다 — 방금 Layer 0에서 도출했다).
**필드 집합이 항상 7개라 「형태 관용(버전 필드 없음)」이 그대로 산다.**

**가설의 재확인 비용**: 설계 진술의 권위 경로는 product.md·arch.md — work이 **이미 통독하는
문서**다. 설계 구역의 가설 강등은 **추가 읽기 0으로 자가 치유된다.**

### 3.5 쓰기 주체 — 구역당 정확히 한 명

| 구역 | 쓰는 자 | 언제 | 무엇을 |
|---|---|---|---|
| 설계 (1~4절 + 2필드) | **arch** (브라운필드 **adopt**) | 그 실행의 **마지막 커밋** | product.md의 비은퇴 능력 **전부** + 골조(01) |
| 검증 (`## Verified state` ~ 끝) | **verify** | 능력층 폐쇄(`boundary — begin NN`) | 그 능력 하나 |

**기각 계보 정식 반박 — "한 작성자가 파일 하나를 폐쇄에서 전면 교체"** (`design.md:86`)

| 기록된 사유 | 반박 |
|---|---|
| 동시성 | 두 작성자는 **서로 겹치지 않는 직렬 순간**에만 쓴다(Layer 0 확정 / 능력층 폐쇄). 둘 다 이미 승인 게이트가 있는 단일 작성자 순간이고, multi에서는 둘 다 통합 브랜치의 구속 결정이다 |
| 공유 | 두 구역은 **바이트 분리**돼 있고 고정 H2 제목이 경계다. 어느 쪽도 상대 구역을 자기 출력의 입력으로 쓰지 않는다 |
| 신뢰 | 설계 구역은 정본이 아닌 **계획**이며, 자기 신선도 도장(`Design head`)을 자기 작성자가 찍는다. 검증됨을 주장하지 않는다 |
| (전제 자체) | 「한 작성자」는 원래도 절대적이지 않았다 — 사람의 삭제와 개명 행이 이미 예외다(`baseline-predicates.md:171-175`) |

**자기 치유의 이전 — 반드시 명시해야 하는 것**

현행 내구성은 "형태가 다른 파일은 가설이고 **다음 폐쇄의 전면 교체가 치유한다**"였다.
verify가 설계 구역을 보존하면 **그 치유자가 사라진다.** 따라서 치유 책임을 옮긴다.

- **설계 구역의 치유자는 arch다.** arch/adopt는 실행할 때마다 비은퇴 능력 **전부**의 설계
  구역을 전면 교체한다(바이트 안정 규칙 적용 — 재도출이 같으면 바이트 그대로).
- **검증 구역의 치유자는 verify다**(현행 유지).
- `## Verified state` 제목이 정확히 한 번 나오지 않으면 verify는 **쓰지 않고**
  `baseline no-op:`을 보고한다. 실행축은 막지 않는다.
- work은 문서를 읽을 때 절 집합이 계약과 다르면 **한 줄 보고**하고 그 구역을 가설로 다룬다.
  자동 교정하지 않는다(정합성 점검 문화 그대로).

**폐쇄가 설계 진술을 반증하면**: 문서를 고치지 않고 **발견→갱신 표**(사용자 확인 게이트
포함)로 간다. 그 결과 `Design head`가 움직이고 다음 arch 실행이 설계 구역을 재도출한다.
폐쇄는 막지 않고 한 줄 보고한다. **새 탐지기를 만들지 않는다.** (G5)

**왜 arch인가**(G10): product는 arch보다 먼저 돌아 코드 구조를 모른다. split은 브라운필드에서
아예 돌지 않는다(G1). arch·adopt만이 도출 원천 5개를 전부 쥔다.

**「한 층씩 연다」와 충돌하지 않는 이유** — 반드시 계보에 남긴다:

> 「한 층씩 연다」가 막는 것은 **태스크 분해**의 선행이다("코드를 써 봐야 알게 된다").
> product.md의 능력 목록과 arch.md의 구성요소·코드 구조는 **이미 전 능력에 대해 한 번에
> 확정된다.** 설계 구역은 그 확정의 **능력 단위 해상도**일 뿐 새 추측이 아니다.
> 게으른 채로 남는 것은 태스크다.

### 3.6 도달 — 배선을 규칙으로 바꾼다 (규칙이 준다)

**신설 1문장** (읽기 집합, `work`):

> 점유한 카드의 **깊이 1 조상 폴더의 앞 번호**를 취한다. `devflow/project/capabilities/`에
> 그 번호를 가진 문서가 있으면 work은 그 문서와 그 문서 「구속 ADR」 절이 열거한 정확
> 경로들을 읽는다. 열거된 ADR 경로가 없으면 한 줄 보고하고 추측하지 않는다.

- **번호로 키잉하므로 골조(01)도 잡힌다** — 골조는 정본상 능력이 아니므로 "속한 능력"이라는
  표현으로는 문자적으로 발동하지 않는다.
- **삭제 3곳**: split의 카드 형식 배선 문단 · 정합성 점검 16번 · 그 배선을 전제한 문장들.
- **보존**: 구속 ADR 전달 — 배선 대신 문서에서 직접 읽으므로 오히려 최신값이 된다(G6).
- **연구 카드 예외도 삭제한다** — 예외가 하나 줄고 조사 카드도 도메인 맥락을 받는다.

**대화형 진입(I4)** — 세 겹, 전부 저비용:

1. resume이 이미 읽는 파일명 목록을 **보고에 넣는다**(G8). **은퇴 능력의 파일명은 제외한다**
   (product.md의 능력 목록이 은퇴 여부를 준다).
2. resume의 스킬 설명문에 능력 문서 언급 한 절.
3. (선택) 훅의 `additionalContext`에 경로 포인터 한 줄. "훅은 아무것도 주입하지 않는다"는
   기각의 사유는 **다음 단계 분류 중복**과 **journal 내용 중복**이었다 — 경로 포인터는 어느
   쪽도 중복하지 않는다.

### 3.7 관계 — 3층 (2판에서 층 3을 축소)

| 층 | 무엇 | 비용 | 2판 변경 |
|---|---|---|---|
| 1 · 이해 | 9절 「소비하는 계약」(소비하는 쪽만 기록) + 8절 "어디서 진입" 열 | 0 (같은 문서) | — |
| 2 · 신선도 | **`Consumed paths`**가 Scope head 명령의 입력에 합류 | 0 (읽지 않고 해시만) | `Scope paths`에 얹지 않는다(G3) |
| 3 · 인지 | A 폐쇄 시, **소비자 목록을 한 줄 보고**한다 | 폐쇄에서 기계 블록 N개 읽기 | **실행 확장을 철회하고 보고로 축소** |

**층 3을 보고로 낮춘 이유**(G4의 진짜 해결):

- "소비자마다 Verify 8단계"는 소비자 수를 제한하지 못한다. 8×N은 상한이 아니다.
- 현행 정본은 이 공백을 **이미 관찰 항목으로 기록**해 두었다(`design.md`: "공유 코드 변경이
  의존 능력의 회귀를 다시 돌리지 않는다 … 잦아지면 재검토"). **관찰 조건이 아직 발화하지
  않았다.** 실패 경로가 관측되기 전에 하네스를 키우는 것은 1절 전제 위반이다.
- 실행 확장은 **실행 순서**(verify 2단계 회귀 목록 vs 5단계 코드 범위), **실패 라우팅**
  (공급자 폴더인가 소비자 폴더인가), **순환**의 세 문제를 함께 열지만, 보고는 어느 것도 열지
  않는다.

**층 3의 정확한 형태**: 폐쇄 시 다른 능력 문서의 **기계 블록만** 읽어(본문 아님)
`Consumed paths`가 이 능력의 `Scope paths`와 겹치는 능력들을 뽑고, 한 줄 보고한다 —
`이 능력의 계약을 소비하는 능력: 05, 07 — 그 문서의 코드 진술은 이제 가설이다`.
비차단이며 카드는 아무것도 더 읽지 않는다. 사용자는 필요하면 기존 사용자 요청 이벤트로
그 능력의 검증을 요청한다.

**경로 일치 판정**(GPT 지적): `Consumed paths`의 한 원소는 `Scope paths`의 한 원소와
**문자열이 같거나**, arch.md가 그 능력에 정확히 매핑한 **폴더 원소 아래에 있을 때** 일치한다.
그 외에는 일치가 아니다.

**복제 금지**: R3(공유 엔티티)·R5(제약)·R6(수명주기 결합)은 **강제하는 쪽의 3절 불변식에
한 번만** 적고, 반대편은 9절에서 경로로 가리킨다. R4(파생)는 절을 만들지 않는다(번호 순서가
계보다). R7(화면 조합)은 product.md 소유.

**은퇴·개명·분할이 자동으로 처리되는 이유**(G9 정정): 능력이 은퇴하거나 분할되어 **경로가
바뀌거나 사라지면** 소비자의 Scope head 명령 출력이 움직여 **소비자의 코드 진술이 자동으로
가설이 된다.** 즉 "경로가 불변이라서" 안전한 것이 아니라 "경로가 바뀌면 감지되어서" 안전하다.
개명은 경로를 바꾸지 않으므로 기계가 무영향이고, product.md가 바뀌어 `Design head`가 움직이므로
설계 구역의 이웃 이름 표기는 가설로 표시된다.

### 3.8 무엇을 축적하는가 — **절 스키마가 필터다** (2판 전면 개정)

1판의 T1~T3은 폐기한다. 이유와 대체는 다음과 같다.

**T1은 자기 파괴적이었다.** "진입점 파일을 읽어 알 수 있으면 넣지 않는다"를 문자대로 적용하면
주 흐름·수명주기·현재 행위·소비하는 계약·진입점이 **전부 코드에서 알 수 있으므로 제외**되어
검증 구역이 비어 버린다. 그리고 설계 구역에서는 코드가 없어 자동 참이므로 **유효 정의역이
없다.** 삭제한다.

**T2·T3은 판정이 아니라 서술 지침이었다.** 핸드오프가 "셋 다 관측 가능한 질문"이라고 적은
것은 사실이 아니다 — "모르면 깨지는가"는 반사실 판단이고, "다른 능력에서도 참인가"는 다른
능력을 조사해야 답할 수 있어 읽기 경계를 연다. **판단어를 판단어로 대체할 수 없다.**

**대신 세 겹으로 간다. 셋 다 이미 존재하거나 기계적이다.**

| 겹 | 장치 | 왜 기계적인가 |
|---|---|---|
| ① **절 스키마** | 13절 각각이 고정된 형식과 필수 칸을 갖는다 | "버튼 텍스트를 바꿨다"는 **들어갈 칸이 없다.** 함정은 증상·재현 조건·원인이 필요하고, 불변식은 검증 가능한 진술이어야 하며, 현재 행위는 1행 = 1 사용자 행위다. **판정이 아니라 구조가 배제한다** |
| ② **절별 제외 열** | 3.3 표의 마지막 열 (R2 복원) | 구체적 예시 형태. "하나의 예가 다섯 규칙을 이긴다"는 정본 원칙과 같은 꼴 |
| ③ **상한 + 전면 교체 + 연대기 금지** | 절별 상한, 총 ~185줄, 구역 전면 교체 | 누적이 불가능하다. 추가가 아니라 **교체**이므로 사소한 변경은 아무 줄도 늘리지 않는다 |

**서술 지침 2줄** (판정이 아니라 지침임을 문장 자체가 밝힌다):

- arch.md · code-style.md · glossary.md가 **이미 담고 있는 진술은 여기 다시 쓰지 않고
  가리킨다.** — 제2 정본 방지. 작성자가 **이미 읽는 문서**만 비교하므로 읽기 경계가 늘지 않는다.
- 근거가 없으면 발명하지 않고 `None.`을 쓴다. (현행 유지)

**소유자의 실경험에 대한 답**: "버튼 텍스트 하나 바꾸는 데도 핸드오프를 읽고 다시 써야 했다"는
상태가 재현되지 않는 이유는 판정이 아니라 **구조**다 — 버튼 텍스트가 들어갈 절이 없고,
문서는 추가가 아니라 교체이며, 연대기 절이 없다. 탈락한 것은 사라지지 않는다: 작업 안의 일 →
진행 로그 / 코드 변경 → 커밋 / 무엇을 했는가 → 카드 파일명 / 휘발성 인계 → HANDOFF /
카드 횡단 결정 → journal / 구속 결정 → ADR·arch·product.

**변경 인지**(D11): `Covered cards`와 현재 `.done.` 집합의 차집합이 델타이고, **그 카드
파일명이 곧 변경 목록**이다. 한 문장으로 명시한다. 연대기 절은 부활하지 않는다.

### 3.9 첫 화면 — 4줄

```markdown
# <능력 번호> <능력 이름>
목적: <무엇을 위해 있고 무엇을 구현하는가 — 한 줄>
경계: 내 것 <...> · 내 것 아님 <이웃 능력 번호와 이름>
이 문서의 설계 구역은 Layer 0 확정 시점, 검증 구역은 마지막 검증 폐쇄 시점이다. 신선도는 맨 끝 기계 블록으로 판정한다.
```

- H1 형식을 고정한다(작업 카드의 `# <번호> <제목>`과 같은 꼴) — 판단어 금지를 **첫 줄**에서
  어기지 않기 위해.
- 「경계」 줄이 **R1(소유 경계) 복원**이자 관계의 설계 시점 기록이다. 이웃을 **번호**로 지목한다.
- 4번째 줄이 **D16의 (b)안**이다. **"이후 M장"은 도출값이므로 저장 금지.**
- 첫 12줄 = 위 4줄 + 개념 모델 ~8줄.

### 3.10 골조(01) — 문서를 준다 (단, 첫 번째 절단 후보)

`01-foundation.md`. **설계 구역만** 가진다: `## Verified state` 아래 절들은 `None.`,
`Verified at: none`. 폐쇄 갱신 대상이 아니다. 3.6의 **번호 키잉** 규칙으로 골조 카드가 도달한다.

- `capabilities/` 폴더에 능력이 아닌 파일이 하나 있게 되므로, **"이 폴더는 깊이 1 트리 단위마다
  문서 하나를 담는다"**를 한 문장으로 명시한다.
- 3.8에서 T3를 폐기했으므로 "공유 계약은 arch·code-style로 빠져야 한다"는 상쇄가 없다.
  arch.md의 코드 구조는 스케치이고 code-style의 「이 프로젝트의 선택」은 한 줄짜리다.
  **공유 계약의 불변식과 경계는 어느 쪽에도 없다.**
- **정직한 반대 근거**: `design.md`의 관찰 항목은 "골조가 공유 계약을 많이 갖게 되면 재검토"다.
  그 **관찰 조건은 아직 발화하지 않았다.** 유보의 사유가 비용/가능성이었고 옵션 E가 그것을
  소멸시킨다는 점이 채택 근거이지만, 실패 경로가 관측된 것은 아니다.
- 따라서 **이 항목은 캠페인에서 압력이 나오면 가장 먼저 잘라내는 후보로 표시한다.**
  잘라내도 나머지 설계는 무영향이다.

### 3.11 스위치 — 제거한다

`capability_baseline` 행을 없애고 능력 문서를 **항상 켠다.**

| 기록된 기각·유보 사유 | 반박 |
|---|---|
| "모든 프로젝트에 강제되는 **제2 도메인 핸드오프층**"(v0.9.21) | 그 문장이 겨눈 것은 **중개노트 형태**다 — 1,739줄, 60~68% 연대기, 무유계 읽기, 수기 신선도. 채택안은 능력당 1파일 · ~185줄 상한 · 연대기 금지 · 카드당 읽기 O(1) · 기계 신선도다. **동일한 대상이 아니다** |
| **"옵션 A(현행 유지)는 소형 선형 프로젝트에 충분하다"** (제안서 §3) | 그 판정은 **옵션 D**를 잰 것이다 — 첫 폐쇄 전까지 아무것도 주지 않는 문서. 옵션 E는 기획 시점부터 존재하므로 "충분한가"의 대상이 다르다. 또 문서 크기는 도메인 크기에 비례한다: 자명한 능력의 설계 구역은 6줄이고 빈 절은 `None.`이다 |
| 프로젝트별 소유자 선택(제안서 §10) | 선택지를 남기는 비용이 텍스트 전반의 yes/no 분기다. 소유자 방향은 "MVP·대형 구분 없이 같아야 함"이며, 선례 v0.9.17이 소유자 방향을 정당한 반박 근거로 확립했다 |
| 강제성 | 되돌리기 비용은 arch 질문 1개 복원이다. **지금 이관 비용이 0**이라 되돌리기도 지금이 가장 싸다 |

**제거는 규칙을 줄인다**: arch 질문 1개 · 배선 술어 · "부재 = no" · `no→yes`/`yes→no` 전이 ·
"비활성 파일은 이상이 아니다" 절 · verify·split·resume의 yes/no 분기가 사라진다.

### 3.12 명시적 비목표

- 연대기 절 · 인덱스 파일 · 버전 필드 · 다이제스트 3종 복원 · 자동 glob 첨부
- 카드 하나가 **다른 능력의 문서를 읽는 규칙** (O(1) → O(n))
- **도메인 간 회귀의 실행 확장** (2판에서 철회 — 보고로 축소, 3.7)
- 정합성 점검의 자동 교정
- 규칙 정본의 소비자별 분할 — **별건**
- `Scope paths`의 의미 변경 · `capability code scope` 재정의
- resume이 문서 **내용**을 읽는 것

### 5.2 이 기획이 추가하는 결정

| # | 결정 | 권고 |

| **D17** | 브라운필드 설계 구역의 작성자 | **adopt.** 이미 능력 후보마다 대표 흐름을 추적한다. **기존 브라운필드 업그레이드 경로**도 함께 만든다: adopt의 "할 일 없음" 조건에 "모든 비은퇴 능력이 문서를 가진다"를 더하고, resume 라우팅을 `Brownfield: yes → adopt / no → arch`로 분기 |

## 8. 검증 계획 — 캠페인 2회 + 좌표 전수 점검

### 8.1 전 세션의 실패와 이번의 교정

| 실패 | 교정 |
|---|---|
| 작은 수정 → 전체 재감사 순환 (40+ 에이전트) | **수리는 배치로 모아 한 번**, 재감사는 **변경분에 한정** |
| 텍스트 먼저 쓰고 텍스트 검증 | **설계 확정 먼저** — 승인 전 `skills/` 무수정 |
| "자기 정합적인가"만 물음 | **의도 적합성 렌즈(L3) 필수** |
| 매 재감사가 맥락을 재도출 | **의도 카드 + 시나리오 픽스처 고정** |
| 최초 기획이 잊혀짐 | **의도 카드 · 델타 원장 · 승계 검사표** |
| 워크가 경로만 훑고 커버리지를 못 봄 | **좌표 전수 점검을 산출물로 요구**(AGENTS.md 6번) |

### 8.2 6단계

```
1단계  설계 확정        (본 문서) — 소유자 승인
2단계  캠페인 1 (설계)  4렌즈 병렬 + 기계 1 + 좌표 전수 점검
3단계  소견 판정 → **결함/판단거리를 분리해 소유자에게 보고 → 승인** → 설계 동결
4단계  텍스트 한 배치   _ko 전부 → 영문 전부 → 설치기 재생성 → 테스트 → CHANGELOG·계보
5단계  캠페인 2 (텍스트) 3렌즈 병렬 + 기계 4 + 좌표 전수 점검 갱신
6단계  수리 배치 1회 → 변경분 한정 재감사 1회 → 릴리스
```

3단계의 소유자 승인은 AGENTS.md 「보고 후 승인」이 요구하는 것이다. 명백한 문자적 결함은
바로 고치되 판단거리와 분리해 보고한다.

### 8.3 렌즈 배치

**공통 입력**: 1절 의도 카드 · 본 문서 · 현행 `baseline-predicates.md` · 핸드오프 2절 표.
**공통 지시**: "**0건도 유효한 결과다**".

| 캠페인 | 렌즈 | 등급·사고량 | 임무 |
|---|---|---|---|
| 1 | **L1 반증** | 최상위 · 최대 | 3절의 구조 결정 9개 공격: 두 구역 / `Design head` 커밋 순서 / 3그룹 / 구역별 작성자·치유자 / `Consumed paths` / 층 3 보고 축소 / 스위치 제거 / 골조 / 번호 키잉 읽기 |
| 1 | **L2 문자 실행** | 최상위 · 최대 | 판단 없이 문자 그대로. 8.4의 생애 워크 |
| 1 | **L3 의도 적합성** | 최상위 · 최대 | I1~I7 각각 **통과/미달 + 근거 문장 인용**. 이번에 없었던 렌즈 |
| 1 | **L4 뺄셈/과잉 하네스** | 최상위 · 높음 | 새 문장마다 실패 경로 요구 · 삭제해도 안 깨지는 문장 · 한 개념 두 이름 · 판단어 |
| 1 | 기계 M0 | 표준 | **델타 원장**: 현행 계약 ↔ 신설 계약 ↔ `27afcc2` 3자 전수. 삭제 항목마다 "의도적(사유)/누락" 판정 |
| 1·2 | **좌표 전수 점검** | 메인 | 축 = {구역} × {작성자} × {생애 사건: 생성·개명·분할·은퇴·업그레이드·중단} × {모드: solo/multi, greenfield/brownfield}. **모든 칸을 정의됨/해당없음/자명/공백으로 판정** |
| 2 | **N1 반증(텍스트)** | 최상위 · 최대 | 쓰인 문장에 대한 반증 |
| 2 | **N2 문자 실행(텍스트)** | 최상위 · 최대 | 실제 SKILL 텍스트만 들고 생애 워크 재실행 |
| 2 | **N3 교차 파일 정합** | 최상위 · 높음 | 배선 잔재 · 절 번호 참조 · 한 개념 두 이름 · 스위치 잔재 |
| 2 | 기계 | 스크립트 | 한글 스캔 · ko↔en 구조 동형성 · `repository-invariants.test.js` · 설치기 재생성 · 양 플랫폼 재설치 |

**기계로 되는 것에 에이전트를 쓰지 않는다.** 목표: **총 9~11 에이전트**(전 세션 40+).
등급 표기는 devflow 카드의 T-등급 관례를 따른다(구체 모델 배정은 세션 시점에 결정).

### 8.4 시나리오 워크

| 워크 | 경로 |
|---|---|
| W1 새 MVP | product → arch(**문서 N개 + 커밋 순서**) → 첫 split → 첫 카드 → 첫 폐쇄 → 둘째 능력 → 유지보수 → 1년 뒤 복귀 |
| W2 브라운필드 | adopt(**문서 N개 역도출**) → 유지보수 카드 → 첫 폐쇄 (**G1**) |
| W3 기존 프로젝트 업그레이드 | 0.10.x 프로젝트가 0.11.0을 받는다 — 문서 없음 → 라우팅 → 생성 (**D17**) |
| W4 팀 | 합류 → 도메인 인계 → 병렬 작업 → 소화 |
| W5 사고 | Layer 0 커밋과 능력 문서 커밋 사이 사망 · `## Verified state` 손상 · 설계 구역 형태 손상 · 능력 개명·분할·은퇴 · arch 재실행 |

| W7 AI 진입 | 지시 없이 "이 도메인 설명해줘" (**I4**) |
| W8 승계 | 7절 18성질 각각을 산출물의 문장으로 지목 |

### 8.5 정지 규칙 (2판 개정)

> 6단계의 변경분 한정 재감사 **이후**에 나오는 소견은 다음 기준으로 가른다.
> **텍스트로 재현 가능한 실패 경로를 제시한 소견은 고친다** — 문자적 규칙 충돌이든 아니든.
> **판단거리·문구 취향·근거 없는 위험 추정은 `docs/design.md`의 관찰 항목으로 보낸다.**
> 이 단계의 모든 수정은 **변경한 줄에 한정된 재읽기**를 동반한다(AGENTS.md 4번). 새 캠페인은
> 열지 않는다. 이 규칙은 **소유자만** 해제한다.

1판의 "문자적 충돌만 수리"는 실제 실패 경로를 가진 결함을 관찰 항목으로 보내도록 강제해
AGENTS.md 검증 프로토콜과 충돌했다. 위 형태는 **비용은 묶고 결함은 놓치지 않는다.**

**소유자 판단이 필요한 것 4가지**(나머지는 이 문서의 권고로 진행 가능):

1. **D3 스위치 제거** — 되돌리기는 싸지만 방향 결정이다.
2. **D5 상한 ~185줄** — 중개노트가 1,100~1,700줄이었다. **10배 압축이 의도적 선택인지** 확인.
3. **D24 설계 구역이 흐름·진입점을 담지 않는 것** — 핸드오프 §5 도출표보다 초기 내용이 줄었다.
   더 담아야 한다고 보면 대안 K로 되돌린다.
4. **D7 골조 문서** — 관찰 조건이 발화하지 않은 상태의 선제 채택이다.
