# v0.11.0 도메인 지식층 재설계 구현 보고서

날짜: 2026-08-11
대상: `handoff-domain-knowledge_ko.md`의 소유자 의도와
`plan-domain-knowledge_ko.md` 2판을 devflow의 Claude·Codex 배포 계약에 구현한 결과

## 1. 결론

구현 결과는 **진행 기록을 또 하나 만드는 인계층이 아니라, 능력마다 하나씩 존재하는 현재형
도메인 입구**다. 새 프로젝트에서는 첫 카드 전에, 브라운필드에서는 대표 흐름을 역산한 직후에
생긴다. 이후 능력 검증이 통과할 때 실제 코드에서 얻은 지식만 같은 파일의 검증 구역에 다시
쓴다. work은 카드에 경로를 복제하지 않고 깊이 1 능력 번호로 이 문서에 자동 도달한다.

AI의 도메인 판단 능력은 유지했다. 시스템이 강하게 고정하는 것은 파일 정체성, 절 순서, byte
소유권, 입력 집합, Git 신선도, 읽기 상한, 복구 전이뿐이다. 개념을 어떻게 요약하고 어떤 불변식을
선택할지는 정해진 증거와 상한 안에서 AI가 판단한다. 필터를 별도 판단어로 덧대지 않고 절 스키마와
제외 열이 내용 경계를 맡게 해 프롬프트 누더기를 피했다.

## 2. 최종 구조

### 2.1 한 파일, 두 구역

경로는 `devflow/project/capabilities/NN-<name>.md`다. 골조는 항상
`01-foundation.md`다. 같은 파일에서 정확히 하나인 `## Verified state` H2가 byte 경계다.

| 구역 | 작성자 | 최초 시점 | 이후 시점 | 신뢰 입력 |
|---|---|---|---|---|
| 설계 구역 | arch, 브라운필드는 adopt | 확정된 Layer 0 뒤 | Layer 0의 능력 설계가 바뀔 때 전면 교체 | product.md · arch.md · glossary.md의 `Design head` |
| 검증 구역 | verify | 빈 골조로 초기화된 뒤 첫 능력 통과에서 실내용 생성 | 능력 통과 폐쇄마다 전면 교체 | `Scope head` · `Covered cards` · `Verified at` |

arch와 adopt가 파일을 처음 만들 때, 또는 경계 손상 파일의 기존 검증 서술 폐기를 사용자가
명시적으로 선택했을 때 빈 검증 골조를 만드는 것은 초기화 예외다. 그 뒤에는 verify만 경계부터
EOF까지 쓴다. 반대로 verify는 경계 앞 byte를 고치지 않는다. “한 작성자” 원칙은 파일 전체가
아니라 겹치지 않는 byte 구역마다 성립한다. resume은 손상 파일을 쓰지 않고 사용자가 지목한
정상 Git revision의 완전 복구와 손실을 명시한 초기화라는 두 선택만 연결한다. 보고하는 HEAD
blob ID는 출처 표지이며, 손상된 현재 blob 자체를 정상 복구본으로 오인하지 않는다.

### 2.2 문서 계약

계획서의 “13절과 끝의 7필드 블록”을 문자 그대로 복제하지 않았다. 그렇게 하면 arch 소유 필드
2개가 verify가 전면 교체하는 suffix 안으로 들어가 소유권이 다시 겹친다. 구현 계약은 내용 절을
보존하면서 설계 메타데이터와 검증 메타데이터를 물리적으로 분리한 14개 계약 행과 고정 경계 1개다.

| 범위 | 담는 것 | 담지 않는 것 |
|---|---|---|
| 첫 4줄 | 번호·이름, 목적, 경계, 신뢰 안내 | “최신” 같은 상대 표현 |
| 설계 본문 | 개념 모델, 능력 고유 불변식, 하지 않기로 한 것, 현재 서술이 인용하는 ADR | 코드 타입·필드 나열, 아직 안 만든 기능, 다른 능력에도 똑같이 참인 규약 |
| 검증 본문 | 실제 주 흐름, 필요한 수명주기, 사용자 행위, 정확 진입점, 소비 계약, 재현 가능한 함정, 이번에 실행한 검증 | 계획된 행위, 문구·레이아웃만의 변화, 관련 폴더 통째, 과거 통과 연대기 |
| 메타데이터 | 능력 번호, 두 head, 검증 시각, 덮은 카드, 범위와 소비 경로 | 버전 필드, 진행률, 담당자, 다음 작업 |

약 45줄의 설계 구역과 약 140줄의 검증 구역, 합계 약 185줄은 자동 절단선이 아니라 보고 상한이다.
초과 작성은 성공하고 실제 초과 절과 행·노드·단계 수를 보고한다. 능력 분할은 제품 변경이므로
사용자가 결정한다.

### 2.3 신선도와 가설

설계 구역은 product.md, arch.md, glossary.md에 마지막으로 닿은 커밋을 저장한다. 검증 구역은
`Scope paths ∪ Consumed paths`에 마지막으로 닿은 커밋과 현재 완료 카드 집합을 저장한다. 합집합이
비면 경로 없는 `git log -1`을 실행하지 않고 `none`을 쓴다. 저장값과 현재값이 다르면 해당 진술
그룹만 가설이다.

가설은 실패나 삭제가 아니다. 사용 직전에 설계 진술은 Layer 0의 정확 절에서, 검증 진술은 기존
읽기 집합 안의 코드나 카드에서 다시 확인한다. 기준선은 정본이 아니며 코드 충돌은 현재 코드가,
구속 결정 충돌은 문서 계층이 이긴다. Binding ADR은 head 집합에 넣지 않고 파일에 적힌 정확 경로를
읽을 때마다 확인한다. ADR 하나가 모든 능력을 무의미하게 가설로 만드는 과잉 하네스를 피한 선택이다.

### 2.4 자동 도달과 관계

work은 점유 카드 경로에서 `devflow/tree/` 바로 아래 조상의 앞번호를 정수로 비교해 같은 번호의
기준선 하나를 연다. split은 카드에 기준선이나 ADR 경로를 복제하지 않는다. resume은 도메인 질문일
때 골조 의미·독립된 `01` 또는 product.md의 완전한 능력 이름·독립 번호로 한 파일을 고른다.
일치가 없으면 골조와 비은퇴 후보를, 둘 이상이면 일치 후보만 제시해 묻고 본문은 열지 않는다.
기대 집합 전부를 명시적으로 요청할 때만 전체를 연다.

관계의 기계 정체성은 소비하는 능력의 `Consumed paths` 정확 경로에 한 번만 산다. 같은 순서의
`소비하는 계약` 행은 사람에게 경로·공급자 번호·기대를 보여 주는 투영이다. 이 경로는 검증 신선도에는
들어가지만 Standards와 Audit의 능력 코드 범위를 넓히지 않는다. 공급자 폐쇄·분할·은퇴에서는
유계 메타데이터와 그 표의 경로·번호 열만 읽어 등록 소비자와 각자의 현재 상태를 한 줄로 보고한다. 다른 능력의 검증 실행이나
카드 생성을 자동으로 일으키지 않는다.

verify 소비자 보고의 세 상태는 판단어가 아니다. `fresh`는 `Verified at`이 `none`이 아니고,
Scope·Consumed 경로 합집합이 비지 않고, 현재 Scope head와 완료 카드 집합이 저장값과 같으며,

필드를 읽을 수 있지만 하나라도 거짓이면 `hypothesis`, 필드가 없거나 해석할 수 없거나 Git 비교를
실행할 수 없으면 `unknown`이다.

| `Concept model`과 `conceptual model` 병용 | 같은 절을 두 이름으로 읽을 수 있음 | 배포 절 이름 `Concept model`로 통일 |
| 도메인 진입의 중복·형태 이상 셀 공백 | 선택 파일이 손상되거나 전부 요청 중 일부가 없을 때 본문을 추측할 수 있음 | 번호별 shape gate, 이상 본문 미개방, 전부 요청은 유효 파일만 계속 |
| 도메인 진입 중 ADR 부재 처리 없음 | resume이 비슷한 ADR을 검색하거나 설계 진술을 사실로 말할 수 있음 | 정확 경로 보고·설계 가설화·대체 검색 금지 |
| 활성 work의 경계 손상 처리 없음 | 0개·2개 경계에서 설계 구역을 추측해 reviewer에 줄 수 있음 | 본문 미개방·유계 보고·기준선 부재 투영으로 작업 계속 |
| “능력 문서만”과 ADR 동승 충돌 | ADR 승계는 ADR·카드·능력 문서를 같은 구속 결정에 넣어 통상 마지막 커밋 형태와 양립하지 않음 | ADR 승계를 정확 경로 치환만 허용하는 별도 기계 예외로 명시 |
| 경계 손상 복구 주체 없음 | resume은 보고만 하고 arch/adopt는 무조건 무연산이라 확인 뒤에도 복구를 실행할 작성자가 없음 | resume은 blob 복구·손실 초기화 두 선택만 제시하고, 확인된 초기화만 arch/adopt의 통상 묶음 절차로 실행 |
| 손상된 현재 blob을 복구 원본으로 지목 | 같은 손상 byte를 복원해 경계 수가 그대로 남음 | HEAD blob은 출처로만 보고하고 사용자가 지목한 revision의 경계 수를 먼저 확인 |
| 트리 전 이름 접미사 규칙 없음 | product.md만 있는 두 플랫폼이 서로 다른 slug로 같은 번호의 파일 둘을 만들 수 있음 | split의 트리 이름과 같은 product.md 이름 텍스트를 쓰고 별도 정규화를 금지 |
| 도메인 0매치·골조 단일 진입 없음 | “이 도메인”이나 골조 요청이 정상 resume으로 빠지거나 문서를 추측함 | 0매치 후보 질문, 복수 후보 질문, 골조 의미·`01` 분기를 명시 |
| reviewer 입력과 기준선 없음 문구 불일치 | 받지 않은 Layer 0를 보라고 하며 구속 ADR 본문도 없어 독립 심사가 불가능 | 받은 카드·공유 문서로 판정하도록 고치고 존재하는 정확 ADR을 유계 입력으로 추가 |
| retrospector가 Design head 원천 일부를 못 받음 | 가설 설계 진술을 product 설명 일부와 arch만으로 재확인하며 glossary 변경을 놓침 | 능력·제품 사건 모두 product.md·arch.md·glossary.md와 ADR을 제공 |
| 같은 경로의 공급자 재배정 미탐지 | 분할 때 파일 경로는 그대로인데 arch 소유 번호만 바뀌면 옛 공급자 번호를 신선한 사실로 설명 | `소비하는 계약` 경로·번호 열을 유계 투영하고 현재 arch 매핑과 비교 |
| 카드 변경 목록이 추가만 표시 | 덮었던 완료 카드가 `.stale.` 또는 missing으로 빠지면 가설이지만 목록은 비어 원인을 설명하지 못함 | 현재 완료 집합과 `Covered cards`의 대칭 차이 및 현재 경로·상태를 보고 |
| 마지막 본문 항목의 사람 삭제 | 형식상 허용된 삭제가 빈 절을 만들어 정확한 `None.` 계약을 깨뜨림 | 마지막 항목은 삭제 예외에서 빼고 구역 작성자가 `None.`으로 치환 |
| reviewer의 ADR 입력이 “모든 Binding ADR” | 저장소 전체를 찾는 무유계 읽기로 해석될 수 있음 | 설계 구역에 적힌 정확 경로 중 존재하는 파일만 제공 |
| 소비자 상태에 `Verified at`·실패 분기 없음 | 빈 골조를 fresh로 보고하거나 `unknown`과 `hypothesis`를 임의 판정 | fresh의 모든 양조건과 두 실패 분기를 정본에 고정 |
| 은퇴·분할 보고가 경로 소유 변경에 종속 | 경로가 그대로인 은퇴·분할에서 등록 소비자 보고가 생략됨 | 은퇴·분할은 무조건, 그 밖의 구속 결정만 경로 소유 변경 때 보고 |
| 중단된 개명 prefix에서 옛 경로 제외 | product 커밋 뒤 옛 파일 삭제가 섞이면 알려진 중단 상태로 복구하지 못함 | 같은 번호의 옛 경로 삭제와 최종 경로 추가를 허용하고 HEAD 검증 구역으로 재도출 |

| S3가 소비자끼리 비교 | 실제 긴장은 소비자와 그 경로의 공급자 사이인데 이웃 소비자를 잘못 비교 | 정확 소비 경로와 행의 상대 능력 번호로 공급자·소비자 한 쌍만 비교 |
| 전면 교체가 `external` 함정을 침식 | 코드 범위에서 재확인할 수 없는 행이 사람 승인 없이 다음 폐쇄에서 사라짐 | HEAD 행 바이트 보존과 사람 전용 삭제 승인을 동시에 고정 |
| 소비자 투영의 후보 집합 없음 | 은퇴 파일을 포함하거나 빠진 기대 파일을 건너뛰고 `없음`으로 보고할 수 있음 | 현재 기대 집합의 다른 비은퇴 번호를 순회하고 첫 0개·중복·해석 실패에서 판정 불가 |
| 경로 불변 은퇴·분할의 일치 집합 없음 | 보고 의무는 있지만 어떤 공급자 경로로 소비자를 찾을지 정의되지 않음 | 원래 능력의 저장 Scope paths를 입력으로 고정 |
| work 읽기 목록이 형태 게이트보다 앞섬 | 경계 손상 파일의 본문·ADR을 먼저 읽은 뒤 “읽지 말라”는 뒤 규칙에 도달 | 앞 목록은 경로만 선택하고 아래 게이트 통과 뒤에만 본문·ADR 개방 |
| begin 복구의 “파일 부재”가 두 뜻 | 작업 트리 삭제 prefix를 HEAD 기준선 부재 무연산으로 오판 | 작업 트리 상태와 HEAD 원본 조건을 분리하고 유일한 경계 하나 HEAD에서만 재생성 |
| 도메인 진입의 Layer 0·골조 부재 공백 | product 자체가 없거나 `01` 파일이 없을 때 본문을 열거나 가짜 설명을 만들 수 있음 | 미초기화 보고와 모든 선택 번호의 일반 부재 분기, 형태별 복구 주체를 명시 |
| 사람 직접 삭제 뒤 커밋 경계 없음 | 다음 work 커밋과 섞이거나 arch가 HEAD 재도출로 되살릴 수 있음 | 다음 스킬 전에 삭제만 단독 커밋하도록 완료 경계를 고정 |
| 손상된 `Binding ADRs` 절에서 경로 추출 | 고정 경계 하나만으로 본문을 허용하면 AI가 깨진 절에서 비슷한 ADR을 추측할 수 있음 | 유효한 절의 정확 경로만 열고 절 자체가 해석 불가이면 경로 0개·설계 가설 |
| v0.10 카드의 기준선 `읽을 것` 잔존 | 구형 문서를 형태 게이트 전에 열거나 개명 뒤 부재 경로로 오판 | 카드 필드에서는 구형 배선으로 무시하고 번호 자동 진입만 사용 |
| 정상 v0.10 기준선이 경계 손상으로 분류 | 기존 검증 지식을 버리는 초기화만 제시하고 업그레이드 직후 도메인 지식이 퇴행 | 정확한 12절·6필드만 식별해 설계는 재도출하고 검증 본문·호환 메타데이터는 기계 이관 |

## 12. 읽기 비용

기존 work의 고정 카드 읽기 예산은 약 16,600토큰이다. 검증 구역 상한 140줄을 약 2,000토큰으로
보면 약 12% 증가다. 설계와 검증을 모두 상한인 185줄까지 채워 약 2,640토큰이 되어도 약 16%다.
실제 작은 능력은 `None.` 절 때문에 더 작다. 카드마다 문서 한 개만 읽으므로 능력 수 N에 따른
증가는 없고 O(1)을 유지한다. 제품 사건 회고만 기대 집합 N개를 읽으며 이미 제품층 사건으로
명시적으로 경계가 잡혀 있다.

## 13. 사용자가 실제로 쓰는 방법

### 13.1 새 프로젝트

product 인터뷰에서 문제·능력·경계를 확정하고 arch에서 구조를 확인한다. arch가 Layer 0를 먼저
커밋한 뒤 골조와 모든 능력의 설계 구역을 제시한다. 이때 사용자는 각 문서 첫 화면의 목적·경계·
개념·불변식이 자신의 언어와 맞는지만 집중해 확인하면 된다. 이후 split부터는 별도 지시 없이
work이 카드 번호로 해당 문서를 읽는다.

### 13.2 이미 코드가 있는 프로젝트

adopt가 외부 진입점·상위 모듈·기존 문서에서 능력 후보를 열거하고 후보마다 대표 흐름 하나를
추적한다. 그 증거로 Layer 0와 설계 구역을 만든다. 기존 명세는 복제하지 않고 arch.md의
`Existing records`에 정확 경로만 인덱싱한다. 첫 유지보수 카드가 통과하면 검증 구역이 실제 코드
기준으로 채워진다.

### 13.3 중기에 합류하거나 v0.10.x 프로젝트를 올릴 때

먼저 resume을 부른다. Layer 0는 완성됐지만 능력 문서가 없으면 Brownfield 값에 따라 arch 또는
adopt가 문서만 만든다. product 인터뷰나 전체 코드 역산을 반복하지 않는다. 이미 작업을 점유한
세션은 그 카드를 먼저 끝내며, reviewer에는 카드와 실제로 받은 공유 문서로 심사하라는 부재 투영을 쓴다.
구형 카드의 기준선 `읽을 것` 경로는 별도 이관 없이 번호 자동 진입으로 넘겨 두 읽기 경로가 생기지 않는다.
정확한 v0.10 기준선이 이미 있으면 손상 초기화로 버리지 않는다. arch·adopt가 설계 구역은 현재
Layer 0에서 만들고, 옛 검증 본문·timestamp·카드 집합·범위는 내용 판단 없이 새 형식으로 옮긴다.
다만 옛 `Scope head`는 소비 경로를 입력으로 삼지 않았으므로 `none`으로 바꾼다. 이관 직후 검증
구역은 가설이며 그 능력이 다음 검증을 통과하면 새 계약으로 갱신한다.

### 13.4 도메인 전문성을 키울 때

도메인 지식을 별도 메모에 수동 누적하지 않는다. 카드의 완료 신호가 실제 행위를 검증하고 능력
pass가 날 때 verify가 현재 흐름·행위·진입점·계약·함정·검증법을 통째로 다시 쓴다. 이후 카드가
같은 번호 문서를 자동 소비한다. 상위 설계가 변하면 설계 구역만, 코드·카드·소비 계약이 변하면
검증 구역만 가설이 되어 필요한 진술만 현재 권위에서 재확인한다.

### 13.5 AI에게 도메인을 설명시키는 말

“결제 능력을 설명해 줘”, “05에 들어가기 전에 경계와 함정을 알려 줘”, “골조의 공유 계약을
알려 줘”, “모든 능력의 경계와 신선도만 비교해 줘”처럼 자연어로 요청한다. 앞의 세 요청은 파일
하나, 마지막 요청은 기대 집합 전부를 연다. 이름이 빠졌거나 둘 이상이면 AI가 번호·이름 후보만
보여 주고 고르게 한다. AI는 경로 → 목적·경계 → 개념·불변식 → 검증된 현재 행위·진입점 → 소비 계약·함정 →
두 신선도 → 기준선 뒤 완료 카드 집합의 대칭 차이 순서로 답한다. 가설이나 `None.`을 현재 사실로 꾸미지 않는다.

### 13.6 사람이 편집하는 경계

사람은 Layer 0와 설계 구역을 확정하고, 잘못됐다고 확인한 본문 행·항목을 절이 비지 않는 범위에서
삭제할 수 있다. 마지막 항목이면 작성 스킬이 절을 `None.`으로 치환한다. 고정 골격·메타데이터는
건드리지 않는다. 직접 삭제한 사람은 다음 devflow 스킬 전에 그 삭제만 단독 커밋한다. 자동
시스템이 그 삭제를 대신 커밋하지 않으며 다른 변경과 섞지 않는다. 새 문장 추가나 재작성은 arch/adopt 또는
verify를 다시 실행해 구역 전체의 일관성을 회복한다. 능력 이름 변경·분할·은퇴는 파일을 직접
옮기기보다 product 재실행으로 시작해야 번호·소비자·복구 전이가 함께 움직인다.

## 14. Claude와 Codex 양쪽의 동작

실행 정본은 공통 `skills/`에 있어 두 플랫폼의 의미가 갈리지 않는다. Claude plugin은 companion을
상대 경로로 읽는다. Codex installer는 같은 companion을 생성 prompt에 내장한다. baseline
predicates는 설계 구역 작성자인 arch·adopt와 신선도·복구 소비자인 resume·verify에만 내장된다.
work과 reviewer에는 카드당 전체 정본을 중복 주입하지 않고 필요한 자동 읽기·투영 규칙만 둔다.

adopt가 받는 product·arch 참조는 extractor가 출력 계약까지만 잘라 전달한다. arch의 새 능력 문서
실행 절까지 복제하면 adopt prompt 안에 다른 작성자의 절차가 생기므로 그 H2 직전에서 멈춘다.
두 manifest는 v0.11.0이고 같은 SessionStart hook을 가리킨다. Windows installer의 UTF-8 BOM도
보존한다.

## 15. 경계가 정해진 환경 한계와 확정된 선택

아래 항목은 미해결 구현 결함이 아니다. 각 경우의 안전한 축소 동작이나 자동화하지 않기로 한
경계가 정본에 있고, 이번 릴리스에 남은 구현 조치는 없다.

- 골조 문서는 공유 경계 재발견 비용을 줄이는지 아직 현장 증거가 없다. 검증 구역은 독립 능력
  검증 대상이 없어 `None.`으로 남는다. D7에 따라 유지하되 효과가 반증되면 첫 절단 후보다.
- 등록 소비자 보고는 인지 장치다. 공유 변경이 잦고 실제 누락이 관찰되기 전에는 교차 능력 회귀나
  카드 생성을 자동화하지 않는 것이 확정된 안전 경계다.
- 얕은 clone에서 필요한 과거 commit이 없거나, Git이 추적하지 않은 경로만 있거나, Windows의 매우
  긴 경로 제한이 있는 환경은 기존 Git 운영 한계다. head를 얻지 못하면 진술을 가설로 낮추며
  성공한 것처럼 가장하지 않는다.
- dynamic dispatch처럼 정확 파일 경로만으로 관계를 못 잡는 경우는 현재 추적 증거 안에서
  `Consumed paths`를 생산할 수 있을 때만 기록한다. 기록되지 않은 관계를 없다고 단정하지 않는다.
- 제품 사건 회고는 product.md가 정한 비은퇴 기대 집합 N개만 읽는다. 저장소 전체 검색으로
  확장되지 않는다.

## 16. Claude 재검토 요청점

아래는 열린 결함 목록이 아니라, 이번 검증에서 모두 정본의 결정적 분기와 대조한 독립 재공격
좌표다. Claude 검토에서는 구현을 다시 늘리기보다 같은 경로가 실제 텍스트에서도 닫혀 있는지
우선 공격하는 편이 가치가 높다.

- Layer 0 커밋과 capability-design 커밋 사이에서 세션이 죽었을 때 HEAD만으로 정확히 회복되는가.
- 개명·분할·은퇴 전후의 옛 소비 경로가 한 줄 보고에서 사라지지 않는가.
- 브라운필드의 구조 변경에서 arch와 adopt가 같은 byte를 쓰는 경로가 남았는가.
- 기준선이 없는 활성 claim을 reviewer가 이유 없이 막거나, 반대로 가설을 사실로 받는가.
- `## Verified state`가 0개·2개인 파일에서 어떤 writer도 경계를 추측하지 않는가.
- 경계 손상 복구가 같은 손상 blob을 다시 쓰거나 알려진 정상본을 찾는 무유계 이력 검색을 하는가.
- reviewer와 retrospector가 자기 계약에 실제로 주어진 입력만으로 freshness와 구속 결정을 판정하는가.
- 제품 사건이 아닌 회고가 두 능력의 불변식 충돌을 발명할 수 있는가.
- 한국어 사용자 요청이 영어 deploy prompt의 예시 문자열과 다르다는 이유로 도메인 진입에 실패하는가.
- 새 문장 중 삭제해도 실행이 전혀 달라지지 않는 과잉 하네스가 있는가.

## 17. 최종 판단

핸드오프가 요구한 사용성은 구현됐다. 도메인 문서는 프로젝트 초기에 태어나고, 중기 합류에서는
resume을 통해 한 장으로 진입하며, 실제 능력 검증을 거칠수록 현재 코드에 맞는 전문 지식으로
성장한다. AI는 자동으로 문서를 찾되 신선하지 않은 진술을 맹신하지 않는다. 시스템 제약은 강하지만
도메인 해석 자체를 규칙 목록으로 대체하지 않았고, 관계 자동화도 관찰 증거보다 앞서 확장하지 않았다.
최종 검증 기준으로 알려진 재현 가능 결함이나 미결 구현 경로는 없다.
