# v0.18.9 라운드 기록 — 「첫 실사용이 벽 둘을 드러냈고, 관문 둘이 그것을 다시 못 일어나게 한다」

이 라운드의 산출물은 뺄셈 그 자체가 아니라 **뺄셈을 안전하게 만드는 두 관문**이다.
바이트는 한 자도 줄지 않았다. 그 사실을 §7 에 정직하게 적는다.

---

## 1. 이 라운드가 시작된 이유

devflow 는 릴리스가 스물여섯 번 지나도록 **실제 프로젝트에서 한 사이클을 완주한 기록이 0**이었다.
그때까지의 모든 개선은 문서를 읽고 추론해서 한 것이다. 0.18.8 을 배포한 뒤 **첫 실사용 시험**을
돌렸다 — 같은 요청·같은 사용자 답·다른 모델로 두 세션이 「팀 회고 보드」를 devflow 로 만들고,
지휘자가 사용자 역할로 답하며 전부 기록했다.

**두 세션 다 막혀서 끝났다. 그것도 루프의 반대쪽 끝에서.**

```
세션 A (Claude Opus medium)  커밋  7 · 카드  0 · 제품 코드      0 B   ← 루프의 입구에서
세션 B (Codex sol medium)    커밋 81 · 카드 12 · 제품 코드 26,278 B   ← 루프의 출구에서
                             양쪽 능력 폐쇄 0 · MVP 성공 기준 4 중 3 실패
```

기록은 `handoff/kl/v0188/test-logs/` 넷(합 397 KB)에 있다.

## 2. 두 벽 — 그리고 그 공통점

### 벽 ① — 신규 프로젝트가 시작조차 못 한다

세션 A 는 정본대로 루트 층 표식을 쓰고, 정본대로 중간에 상태를 확인했다가 영구 정지했다.

```
정본: principles/SKILL.md:575  능력은 02, 03, … 번호를 받는다
      split/SKILL.md:88-94     그 번호들을 층 열기 표식의 children 에 써라
코드: project-state.mjs:12     CARD_NUMBER = "[0-9]+[a-z]*(?:\\.[0-9]+[a-z]*)+"
                                                                          ↑ 점을 최소 한 개 요구
결과: integrity: kind=blocking item=12  → 라우팅과 모든 트리 쓰기 정지
```

그리고 정본이 정한 복구 절차(`:492-496`, *"제안 교체본 전체를 사용자에게 제시하라"*)가
**제시할 수 있는 유효한 교체본이 없어 비어 있었다.**

세션 A 의 마지막 문장:

> **"절차를 어겼으면 안 막혔을 것이다. 정경 형식을 정확히 지켰기 때문에 막혔다.
> 규율을 지키는 세션을 규율이 막는 자리가, 신규 프로젝트의 첫 split 에 있다."**

### 벽 ② — 능력이 한 번도 안 닫힌다

세션 B 는 능력 02 를 구현하고 닫으려는데, 편향 제거를 위해 요구되는 **깨끗한 새 세션이 브라우저
도구를 못 잡았다**(30초·120초 timeout, 명시적 attach 도 실패). 메인 세션은 같은 도구로 같은
시나리오를 이미 통과시켰다. 제품 결함이 아니라 도구 고장인데 규칙이 그것을 제품 실패처럼 다뤄
카드가 `02.3 → 02.4 → 02.5` 로 증식했고, 상태 도구는 완료 불가로 판명된 카드를
`ready=true blockers=[]` 로 다음 세션에 내밀었다.

### 공통점

**둘 다 하네스가 제품이 아니라 자기 자신을 검사하다가 닫힌 자리다.** A 의 마커는 *중단 복구*를
위해 존재하는데 중단되지 않은 세션을 막았고, B 의 깨끗한 검증자는 *편향 제거*를 위해 존재하는데
이미 검증된 제품의 폐쇄를 막았다.

**선은 층(Layer 0/1)이 아니라 성질이다** — 값을 낸 것은 전부 「고장 나도 아무것도 잠그지 않는
방향 제시」였고, 막힌 것은 전부 「자기 기계가 고장 나면 제품 작업까지 잠그는 하네스」였다.

## 3. 살아남은 것 — 반증을 시도했으나 버텼다

**틀을 바꾸는 답은 데이터가 지지하지 않는다.** 「Layer 1 을 전혀 다른 것으로」와 「규칙 정본을
없앤다」를 실제로 검토하고 반증했다. Layer 1 에서 값을 낸 것이 전부 사라지기 때문이다.

| 기제 | 실측 |

### ★ DD-81 — `channel unavailable` (결정 색인에 행을 못 넣었다. §6 참조)

**무엇**: 검증자의 `unverified` 사유가 **채널 획득 실패**(tool bind/attach/timeout, 시나리오를
한 단계도 실행하기 전)이면, **재발 몇 번째든 첫 항목부터** 카드를 만들지 않고 사람에게 간다.
메인 세션이 쓰는 사유 형식은 `unverified: channel unavailable — <실패한 정확한 명령>; timeout=<값>`.

**실사용 장면**: 세션 B 가 81 커밋을 쌓고도 능력을 한 번도 못 닫았다(§2 벽 ②).

**DD-68 과의 관계 — 반증이 아니라 범위 구분이다.** DD-68 은 **제품에 대한** non-pass 를 다뤘고,
**채널 고장은 정의상 제품 정보가 아니다.** 그러므로 DD-68 의 기록된 이유는 부정되지 않는다.
DD-68 의 상태는 `active, partly corrected by DD-81 (v0.18.9)` 이다.

**빠져나갈 구멍을 막는 장치**: 사유에 **실패한 정확한 명령과 timeout 값**을 적게 한 것.
모델이 제품 결함을 도구 고장으로 분류해 빠져나가려면 그 두 값을 지어내야 한다.

**시험이 못 닫는다** — 관문 B 가 지난다.

### ★ DD-82 — 정본 두 규칙이 한자리에서 다른 행동을 가리킬 때

**무엇**: 두 정본 문장이 함께 적용되고 다른 행동을 내면 **양쪽 원문·좌표·택한 쪽과 이유를
보고하고 계속한다.** 조용히 고르지 않는다.

**실사용 장면 일곱** — 같은 ADR 세 조건으로 한 세션은 SSE 를, 다른 세션은 SQLite 를 ADR 로
올렸다(**정확히 반대 결론**) · 코드 구조 표의 `3+ capabilities` 와 `Under 20 files` 가 동시 참 ·
능력 문서 제목 순서 · `slug` 대 「slug 정규화 금지」 · 계획 순서 · `always ask` 의 수신자 ·
영어 identity 틀. 그중 제목 순서는 **한 세션은 조용히 메웠고 다른 세션은 보고한 뒤 골랐다.**

**왜 「멈춘다」가 아니라 「계속한다」인가**: 멈추게 하면 산문 충돌 하나마다 세션이 서고,
그것이 이 라운드가 고치려는 병(하네스가 제품 작업을 잠그는 것)을 새로 만든다. 멈춤은 기존
게이트(Layer 0 변경 확인 · binding decision)가 정한다.

**★ 이 규칙은 새것이 아니다.** `AGENTS.md` 「Hard boundaries」의
*"Report before judgment calls are applied."* 가 **유지보수자용 문서에만 있었고 런타임 세션은
받은 적이 없었다.** 새 규칙을 쓴 것이 아니라 있는 규칙을 옮긴 것이다.

devflow 는 **기계로 검사되는** 불일치에는 심판 기계를 이미 갖고 있다(무결성 12–15항 → 원문·
기대 형식·교체본 제시 → 사용자 확인 → 착지, `principles:492-501`). **산문 대 산문에는 그 기계가
없었다.** DD-11 은 움직이지 않는다 — DD-11 은 **문서 사이의** 모순을 다루고 DD-82 는
**정본 자신의 두 규칙이 함께 적용되는 경우**를 다룬다.

## 5. ★ 관문 둘 — 이 라운드의 산출물

### 왜 만들었나

**이번에 시간을 버린 이유가 이것이다.** 「논리적 완성도가 충분한가」를 문서 검토와 `node --test`
로만 답했고 둘 다 초록이었는데, **시험 272개가 전부 초록인 채로 신규 프로젝트가 시작조차 못 했다.**
그 272개는 **도구를 만든 쪽이 쓴 픽스처로 도구를 검사**한다.

**실측**: 정경 저널 13종이 `project-state.test.js` 에 이름으로 등장하는 횟수 —
`capability note` **0** · `evidence-finalizing` **0** · `layer opening` **1**(중첩 경우만) ·
`re-split pending` **1** · `capability closing` **1**.

### 관문 A — 정본이 쓰라는 예약 줄 전부를 배포본 파서에 먹인다

유효 15(13 헤드 × 정확한 형식) + **무효 13**(헤드마다 필수 필드 하나 훼손 — 이것이 관문의
자가 점검이다) + **덮개 자물쇠 둘**(표의 헤드 집합 == `RESERVED_JOURNAL_HEADS` ==
`principles/SKILL.md` 형식 블록에서 뽑은 집합). **줄 번호가 아니라 헤드 문자열로 정본을 읽는다.**
10초 상한. `node --test` 안에 들어 있고 별도 명령이 아니다.

### 관문 B — 능력 하나를 끝까지 닫아 본다

**검증 계약을 바꾸는 릴리스마다 한 번, 사람 손으로. 자동화하지 않는다** —
자동화하면 그것이 다시 자기 자신을 검사하는 하네스가 된다.

이번 실행: 격리된 `CODEX_HOME` 에 후보를 설치하고(사용자의 실제 `~/.codex` 는 건드리지 않았다)
임시 저장소에서 「할 일 목록」한 장짜리 웹 페이지를 능력 하나로 만들었다.

### ★ 관문 B 가 첫 실행에서 잡은 것 — 다섯

1. **HANDOFF 경로 advisory** — `item 5` 가 `snapshot.cards` 만 뒤지는데 대상은 **대기 능력 파일**.
   도구는 그게 뭔지 안다(같은 출력에 `next: ready.waiting-capability`). 아는데 대조 집합에 안 넣는다
2. **arch 채널 확인의 표면 불일치** — 세션이 `getDefault()` 가 고른 Chrome 을 확인해 놓고
   `arch.md` 에는 `get("iab")` 를 적었다. **P4 가 겨눈 바로 그 장면에서 P4 가 불충분했다**
3. **prepared-route 개행 비대칭** — `readFile`(`:175`)은 CRLF 를 LF 로 정규화하는데
   `state.contents` 는 원문이다. 실측: **문자열 길이 2551, 첫 차이 index 2551** — 완전히 같은데
   거부됐다. `core.autocrlf` 가 Git for Windows 기본값이므로 **Windows 사용자가 상위 문서 환류를
   하면 그 기제가 통째로 막힌다**
4. **감리가 진짜 결함을 찾았다** — 비원자적 저장으로 중단 시 JSON 이 잘려 다음 기동까지 막는다.
   증거 등급 `presumed`(파괴적 실험은 하지 않았다). 사용자가 채택했다
5. **locator 가 base 를 안 본다** — 정본 `:242-244` 는 prepared object 의 `base` 커밋에서
   해석하라는데 `:1274` 는 작업 트리만 본다. **닫힌 능력 재개 경로에서만 발화한다**

**넷은 코드 결함이고, 시험 301개가 전부 초록인 채로 살아 있었다.**
그리고 성격이 갈린다 — ①②는 문서를 꼼꼼히 읽으면 찾을 수도 있었다.
**③④⑤는 실행 없이는 원리적으로 못 찾는다**(이 기계의 git 설정 / 감리가 실제로 코드를 읽어야
나오는 것 / 재개방 경로를 실제로 밟아야 나오는 것).


**실증된 것**: 신규 프로젝트 시작 · 능력 폐쇄 · 검증 구역 교체 · **첫 폐쇄의 감리와 회고** ·
소견 채택/비채택의 착지 · **닫힌 능력 재개 → 수리 → 전체 재검증 → 재폐쇄**(devflow 가 한 번도
밟은 적 없던 경로) · **검증이 거짓 통과를 잡는다**(카드의 `/\\r?\\n/` 가 문자 역슬래시라 exit 1 인데
앞선 work 가 한 단계 디코딩된 것을 실행해 잘못 pass 로 봤다).

**부수 관측 둘**: 첫 회고의 소견 둘이 **전부 이미 처리된 것을 다시 짚었다**(채택 0) —
「감리와 회고가 서로의 결과를 보는가」가 다음 관측의 핵심이다. 그리고 감리·회고 event key 가
**폐쇄 횟수가 아니라 canonical key** 라서 같은 key 면 재폐쇄해도 새 event 를 만들지 않는다.

## 6. ★ 결정 색인이 예산에 부딪혔다 — DD-81·DD-82 의 행이 못 들어갔다

`docs/design.md` 는 **26 KiB 고정 예산**이고 헤드룸이 **81 B** 인데, DD-81·DD-82 행 둘 +
DD-68 상태 접미사가 **약 450 B** 필요했다.

**그 시험의 주석이 이 일을 예견해 놓고 금지해 뒀다:**

```
scripts/repository-invariants.test.js:347-352
  The decision index grows one row per decision forever while this budget stays fixed, so the
  two collide on a schedule.  v0.18.1 found the collision …
  Raised once, minimally.  The structural answer — splitting or relocating the index —
  is a decision the backlog carries; do not raise these again to fit one more row.
```

**예산을 올리지 않았다.** 그것은 기록된 지시를 반증하지 않고 뒤집는 일이고
(`AGENTS.md` 진입 게이트: *"refute a recorded reason before overturning a decision"*),
이번 충돌이 오히려 그 이유를 확증한다. 그리고 `design.md` 는 **항상 읽히므로 그 크기가 진입
비용**인데, 뺄셈을 미룬 라운드가 항상 읽히는 문서를 키우는 것은 앞뒤가 맞지 않는다.

**그래서 DD-81·DD-82 의 이유를 이 문서가 소유한다**(§4). 백로그에
「DD-81·82 는 색인 분할 라운드에서 착지하고 그때까지 이유는 이 라운드 기록이 소유한다」와,
색인 분할의 **딱딱한 발동 조건「다음 결정이 색인 행을 필요로 하는 순간」**을 적었다.
헤드룸 81 B, 행 하나 약 200 B — **다음 결정은 무조건 걸린다.**

## 8. ★ 이 라운드가 남긴 진단 — 다음 라운드의 축

**소유자 의문**: *"AI 가 명확한 규칙이 있었는데도 무시했을 수도 있다. 그렇다면 스킬 설계 자체에
의문을 가질 수 있다."*

두 모델이 맹검으로 분류했고 **건수는 갈렸는데 진단은 갈리지 않았다** — 결론이 세는 방식에
의존하지 않는다는 뜻이다.

```
Codex   (다) 7건   「비차단 2차 의무의 선택적 마모」
Claude  (다) 확정 3 + 준확정 2   「결과가 즉시 관측되지 않는 의무는, 다른 행위에 얹혀 갈 때 마모된다」
```

**★ 기계적 판별식:**

> **자기 커밋을 갖는 산출물은 81 커밋 내내 한 번도 안 빠졌다** — 카드 상태 rename · task 커밋 ·
> `verify.md` · 진행 로그 · 커밋 메시지 형식.
> **남의 커밋에 얹혀 가는 산출물만 마모됐다** — 다이제스트 · HANDOFF · `capability note` ·
> arch 채널 확인. 정본이 HANDOFF 를 *"it only rides here"*(`principles:817`)라고 **스스로 승객으로
> 배선한다.**

**「AI 가 주도적이라 못 따른다」는 두 모델 다 기각했다.** 같은 기록에서 세션들이 자기에게 불리한
규칙 넷을 정확히 지켰기 때문이다 — 한 줄이면 풀리는데 영구 정지를 택함 · 지휘자의 잘못된 요구를
정본 원문으로 거부 · fallback 가능한데 hard constraint 라고 안 함 · verdict 가 pass 가 아니니
폐쇄 절차 전부를 안 밟음.

**무효인 전제는 「명확하게 쓰면 실행된다」이지 「AI 가 규칙을 따른다」가 아니다.**
유효한 형태는 **「명확하게 쓰고, 자기 커밋을 갖게 하거나, 결과가 그 자리에서 관측되게 하면
실행된다」**. 그리고 devflow 는 그 기제들을 이미 갖고 있다 — **이 의무들에만 안 걸었다.**

**독립 확증**: 기록 이해도 측정(깨끗한 세션에게 `devflow/` 만 주고 질문 여덟)이 **다른 방법으로
같은 목록**을 냈다. Claude 세션은 「틀렸다」 0건(HANDOFF 에서 될 뻔), **Codex 세션은 바로 그
HANDOFF 를 따라 실행 불가능한 다음 단계로 갔다.**

## 10. 미검증 — 실행하지 않은 것은 통과가 아니다

- **두 번째 능력** — 관문 B 는 능력 하나

- **카드 두세 장 넘는 규모**
- **능력 문서 검증 구역의 문법** — 관문 B 에서 한 번 채워졌지만 표본 1
