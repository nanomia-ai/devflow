# v0.18.3 수리 보고 — 도구가 정본의 약속을 지키고, 정본은 쪼개지 않기로 실측했다

날짜: 2026-08-20
비교 기준: `fa05d82` (v0.18.2 착지 시점)
배포 diff: **18 파일 / +108 / −108** (`git diff --stat`, CHANGELOG·매니페스트 포함)

유지보수 프로토콜 §5 에 따라 별도 폴더 없이 직전 라운드 안에 기록한다. 무엇이 바뀌었는지는
CHANGELOG `0.18.3` 항목이 소유한다. 이 문서는 **어떻게 알았고 무엇이 남았는가**만 담는다.

## 왜 이 라운드가 시작됐나

0.18.2 착지 직후의 검증이 **배포된 문장이 약속한 것을 배포된 도구가 하지 않는 자리 둘**을
잡았다. 둘 다 0.18.2 가 만든 것이 아니라, 0.18.2 가 정본을 옮기면서 드러난 접합부다.
그리고 전수 중복 보고서가 **같은 규칙이 두 자리에서 말해지는 곳 넷**을 냈다.

## 실제 배포 (Actually shipped)

**도구 수리 둘** (`scripts/project-knowledge.mjs`)
- `--capability` 가 0 채움 번호를 받는다. 정본이 골조를 `01`, 첫 능력을 `02` 로 번호 매기고
  캡슐 폴더가 그 문자열을 그대로 잇는데, 도구는 `02` 를 「양의 정수가 아니다」로 거절했다.
  **다섯 스킬이 이름으로 부르는 정본 호출이 세션이 실제로 손에 쥔 번호로는 실패했다.**
- 색인이 캡슐의 마지막 변경 커밋 날짜를 `changed` 로 낸다. 정본은 세션에게
  `git log -1 --format=%ad --date=short` 를 실행하라고 했으나 **아무것도 그것을 전달하지
  않았다.** 도구가 `git log` **한 번**으로 전 캡슐분을 얻어 투영에 담고, 고르는 일이 읽으므로
  축약 투영에도 남긴다. 머리말 칸을 만들지 않으므로 **저작 0 · 유지 0 · 드리프트 0**이다.

**중복 제거 넷** (전수 보고서가 채택한 것만)
- product 의 의존 질문 두 줄 → 기획 증거 정본에 맡김
- resume 의 경계 손상 행 → 트리거만 두고 정본 복구 절을 가리킴
- arch·adopt 의 기준선 작성 계약 재서술 삭제 (캡슐 다섯 단계·기대 집합·입력 도출은 보존)
- verify·resume 이 캡슐 본보기 두 편을 안 읽음 — **본보기 원문 diff 0**. 본보기는 캡슐 형식의
  유일한 계약이므로 arch·adopt 는 계속 전량 읽는다

**접합부 하나** — arch·adopt 의 캡슐 가공 절이 삭제된 불릿을 「아래 설계 확인 묶음」으로
가리키던 끊긴 참조를 정본을 가리키게 고쳤다 (4자리 · +92 B).

**가늠자 — 진입별 고정 입력 실측 절감**

| 진입 | 절감 |
|---|---:|
| resume | **−5,438 B** |
| verify | **−4,744 B** |
| arch | −1,618 B |
| adopt | −1,579 B |
| product | −197 B |

저장소 순감 **8,135 B**. 삭제 범위 바이트가 전수 보고서의 예상치와 **전부 정확히 일치**했다.

## 검증

1. **기계 검사** — `node --test "scripts/*.test.js"`: **123/123 통과**
   (0.18.2 의 122 + 0 채움 시험 1).
2. **도구 동작을 실행으로 확인** — `--capability 01/02/002` 통과, `0/abc` 거절. 시험이
   `2`/`02`/`002` 통과와 `0`/`00`/`abc`/`-1` 거절을 못 박는다.
3. **예산 유지 확인** — 100캡슐 축약 색인 시험이 `changed` 를 포함하고도 24 KiB 예산 안에서
   100편 전부를 낸다. 날짜 한 칸이 색인을 넘치게 하지 않는다.
4. **낡은 단정 정리** — `scripts/repository-invariants.test.js` 의 단정 여섯을 갱신했다.
   전부 「성질은 살아 있고 사는 자리가 정본으로 옮겨졌다」는 낡음이고, 두 쌍은 이미 정본
   단정과 순수 중복이었다.

**신선도 판정이 아니다** — `changed` 는 캡슐이 마지막으로 바뀐 날이다. 캡슐은 그대로인데
그것이 기술한 코드만 바뀐 경우를 이 날짜는 **보지 못한다.** 고르는 데 쓰는 사실이지
믿어도 되는지에 대한 판정이 아니다.

## ★ 실측이 「하지 않기로」 정한 것 — 이 라운드의 핵심 결과

가장 큰 단일 부하는 `principles/SKILL.md` **67,205 B** 이고 **여덟 진입 스킬 전부가 통독**한다.
훅이 무조건 resume 으로 보내므로, devflow 상태가 있는 저장소에서 세션은 아무 일도 하기 전에
**약 148,000 B ≈ 37k 토큰**을 쓴다.

이것을 소비자별로 나누는 것은 **DR-44** 가 보류시킨 백로그 항목이고, 보류 이유는
*"work 가 필요로 하는 규칙이 verify 전용 제목 아래에 놓이면 아무 오류 없이 사라진다"* 였다.
**이번에 실측했다.** 21개 상·하위 절을 여덟 스킬·역할 계약 넷·훅과 대조했다.

| 실측 | 값 |
|---|---:|
| 여덟 스킬이 전부 실행하는 상위 절 | **46,593 B (파일의 69%)** |
| 소비자 3명 이하인 행 6개 — 분할로 얻을 수 있는 **최대치** | **16,366 B** |

**그런데 소비자 적은 절이 전부 보편 절과 얽혀 있다.**
- Identity 만 읽으면 room id 없는 commit 제목을 만든다. Commit Discipline 만 읽으면 그 id 를
  **어느 room 에서 가져올지** 추측한다.
- journal 형식만 읽으면 malformed 줄이 조용히 통과한다. 정합성 점검만 읽으면 기대 교체값을
  만들 근거가 없다.

**그러므로 DR-44 의 기록된 이유는 「주장」에서 「실측」으로 올라간다. 정본은 쪼개지 않는다.**

참고로 어떤 판정은 저장소 자신의 소비자 시험이 그 실패를 이미 시끄럽게 만든다고 봤으나,
그 시험이 잡는 것은 **배선 어긋남**이고 실측이 보여 준 위험은 **내용 배치**다. 다른 층위다.

## 남은 한계 (Remaining limitations)

- **토큰 무게는 여전히 미달이다.** 원인이 실측됐고 뻔한 처방(정본 분할)은 실측으로 위험이
  확인됐을 뿐, **대안은 아직 없다.**
- **실사용 미검증.** 실제 프로젝트에서 전 주기를 새 규격으로 걷지 않았다. 0.18.2 에서 이월된
  한계가 그대로 남는다.
- **0.18.3 뒤의 맹검 이해도 재측정은 실행하지 않았다.** 이 라운드의 삭제분이 이해도를
  떨어뜨리지 않았다는 것은 아직 텍스트 대조로만 말할 수 있다.
