# devflow 감사 가이드라인 — 외부 감사자를 위한 정본

지위: **공용 감사 수단** (버전 없는 상시 문서 · 배포 산출물 아님 · 한국어 전용)
대상 독자: devflow 텍스트를 감사하는 **독립 컨텍스트의 AI**(GPT 등)와 그 감사를 발주하는
소유자. 이 문서의 규칙은 v0.9~v0.14의 16개 릴리스에서 실제로 결함을 찾고, 실제로 오판도
저지르면서 다듬어진 것이다 — 각 규칙 뒤의 사건이 근거다.

---

## 0. 감사의 대상이 무엇인지부터

devflow는 코드가 아니라 **AI가 문자 그대로 실행하는 프롬프트 텍스트**다. 따라서:

- 모호한 단어 하나 = 이 도구를 쓰는 모든 프로젝트의 결함.
- "상식적으로 이렇게 읽겠지"는 없다 — 감사자는 **가장 문자적인 독자**를 상정한다.
- 문장의 아름다움·간결함·스타일은 감사 대상이 아니다. **행동이 갈라지는가**만이 대상이다.

판정의 최상위 기준은 소유자의 세 축이다:

```
① 내구성   이 변수에서 크게 망가지지 않는가 — 최악은 조용한 자료 소실
② 토큰     AI가 진입할 때 지나치게 소모하지 않는가
③ 분별     남겨야 할 기록과 아닌 것을 옳게 가르는가
```

"크게 망가짐"의 서열: 조용한 자료 소실 ≫ 구조 갈라짐 ≫ 잘못된 행동 ≫ 출구 없는 정지 ≫
비용. 소견의 심각도는 이 서열로 매긴다 — 시끄러운 실패는 조용한 실패보다 한 단계 낮다.

## 1. 감사 전에 — 입력과 오염 통제

**읽어야 하는 것** (전문, 요약본 금지):

- 감사 범위의 배포 파일 원문 (`skills/**/*.md` 영문 — AI가 실행하는 것은 영문이다)
- `docs/design.md` — 결정표와 기각 계보. **기각된 안을 모르고 재제안하는 소견은 반려된다**
- `docs/usecase-matrix_ko.md` — 유즈케이스 전수표. 감사의 커버리지 도구다 (4절)
- 직전 실행 리포트(`docs/v*-execution-report_ko.md`) — 직전 루프가 어디서 멈췄는지

**읽지 말아야 하는 것** (오염):

- 구현 세션의 대화·수리 의도 설명 — 의도를 알면 문자적 독해가 죽는다. 감사자의 무지가
  자산이다.
- 이전 감사의 소견 목록(재감사가 아닌 한) — 같은 경로만 다시 걷게 된다.

**사전 고정** — 감사를 시작하기 전에 다음을 문서로 못박는다. 시작 후에 바꾸면 무한 루프의
입구가 된다:

1. 감사 범위 (파일 목록 또는 "변경분만" — 변경분이면 그 커밋 범위)
2. 채택 기준 (2절의 클래스만, 표현 선호 불채택)
3. 종료 조건 (5절)
4. 산출 형식 (6절)

## 2. 무엇이 결함인가 — 채택되는 소견의 클래스

**모든 소견은 두 가지를 갖춰야 채택된다: 원문 정확 인용(파일·행) + 구체적 실패 경로
(어떤 입력·디스크 상태에서 → 문자적 독자가 어떤 단계를 밟아 → 무엇이 잘못되는가).**
실패 경로를 못 대는 소견은 소견이 아니라 인상이다.

채택 클래스 (전부 실제로 결함을 배포한 적이 있는 것들):

| 클래스 | 판정 | 실례 |
|---|---|---|
| **규칙 충돌** | 문자 그대로의 두 문장을 동시에 지킬 수 없다 | 봉쇄 목록이 원격 증거 카드의 최종 커밋을 계속/대기 양쪽에 걸었다 (0.14.0 반증) |
| **판단어** | 기계 검사 없는 단어로 두 독자가 다른 행동에 이른다 | "id를 담는다" — 부분 문자열/토큰 양독 (0.14.1 재감사) |
| **한 개념 두 이름** | 같은 것이 두 이름을 가져 다음 편집에서 갈라진다 | "capability file"과 "baseline" (용어표로 봉인됨) |
| **두 개념 한 이름** | 다른 것이 한 이름을 공유해 오적용된다 | auditor의 2모드 겸용안 기각 사유 |
| **무한한 읽기 규칙** | 읽기 집합이 유계로 열거되지 않는다 | "관련 기록을 읽는다" 류 |
| **죽은 참조** | 제거된 개념·존재하지 않는 이름을 참조한다 | 병렬 절의 옛 허가 모델 잔존 (0.14.0 반증) |
| **조합 결함** | 문장 하나하나는 옳은데 둘이 만나면 막히거나 샌다 | 방 없는 세션 × 봉쇄 × tweak = 처분 미정 (0.14.1) |
| **정본 밖 예외** | 정본 규칙의 예외가 하위 문서에만 선언됐다 | 정본이 이기므로 그 예외는 죽은 문장이다 |
| **뺄셈 대상** (역클래스) | 지워도 어떤 행동도 안 변하는 문장 | "준비된 카드는 즉시 점유할 수 있다" 중복 (0.14.1) — 무엇이 이미 그 행동을 담보하는지 명명해야 채택 |
| **소실 경로** | 어떤 조건 교집합에서 기록이 흔적 없이 사라진다 | 봉쇄 중 요청이 대화에만 존재하다 증발 (라운드 2의 유일한 최상급) |

**불채택** (발견해도 소견이 아니다): 표현 선호 · 스타일 · "더 명확할 수 있다"(구체적 오독
없이) · 재설계 제안 · 가상의 개선 아이디어. 이런 것은 "관찰"로 강등해 따로 적는 것까지만.

## 3. 지켜야 할 것 / 하지 말아야 할 것

**지켜야 할 것:**

1. **0건은 유효한 결과다.** 결함을 찾으라는 지시를 받은 감사자는 결함을 제조하는 경향이
   있다 — 이 저장소의 기록된 병이다. 깨끗하면 깨끗하다고 쓰고, 어떤 문장이 그 경로를
   받치는지 인용하라.
2. **소견과 수리안을 분리하라.** 실측된 사실: 수리안의 오류율은 소견보다 높다(라운드 2에서
   수리안 35건 중 1건은 그 자체가 틀렸고 1건은 기록된 결정을 반증 없이 뒤집으려 했다).
   수리안은 "선택지"로만 제시하고, 소견의 채택 여부와 묶지 마라.
3. **렌즈를 분리하라.** 반증자(규칙 충돌 사냥) · 문자 실행 워커(시나리오를 그대로 걷기) ·
   기록 소실 감리(지식 채널 전수) · 뺄셈 감사(추가 문장 전수)는 서로 다른 결함을 찾는다.
   같은 렌즈의 재실행은 같은 경로만 다시 걷는다 — 라운드가 바뀌면 렌즈를 바꿔라.
4. **걷기와 좌표 스윕을 구분하라.** 걷기(시나리오 실행)는 걸은 경로의 결함만 찾는다 —
   수렴해도 "걸은 경로가 깨끗하다"는 뜻이지 공간이 소진됐다는 뜻이 아니다. 구조 변경
   뒤에는 축을 곱한 좌표 스윕(칸마다 권위·다음 행동·커밋 경계·복구·검사가 있는지)으로
   커버리지를 본다. 경로의 **부재**는 걷기로는 절대 안 보인다 — 라운드 2의 교차 소비
   함정이 그렇게 모든 걷기를 통과했다.
5. **외부 도구의 동작은 실행해서 확인하라.** Git이 어떻게 동작하는지를 텍스트 추론으로
   판정하지 마라 — 0.13.0에서 구현자와 외부 검증자가 **같은 오판**("한 폴더 동시 쓰기
   불가")을 내렸고 실측이 둘 다 뒤집었다. 실측할 수 없는 환경이면 그 소견에 "실측 필요"를
   달아 판정을 보류하라.
6. **계보를 존중하라.** 기록된 결정을 뒤집자는 소견은 design.md의 그 행이 적은 이유의
   반증을 포함해야 한다. 반증 없는 뒤집기 제안은 형식 미달로 반려된다 — 단, "이 기록된
   이유가 이런 사실로 반박된다"는 소견은 언제나 환영이다.
7. **새 텍스트 첫 패스의 두 자릿수 소견은 정상 패턴이다.** 시스템 회귀가 아니다. 이전
   검증을 통과한 텍스트에서 나온 것([기존] 표기)만 탈출 결함으로 세라 — 그 수가 품질
   지표다.
8. **기계로 검사 가능한 것은 기계로.** 문구 존재·잔존 개념·용어 일관성은 grep/스크립트가
   눈보다 정확하다. 단, 기계 검사의 한계도 알아라 — 이 저장소의 테스트가 한때 모순된 두
   문장을 각각 통과시킨 적이 있다. 기계 검사는 존재를 확인하지 의미를 확인하지 않는다.
9. **자기 소견을 한 번 의심하라.** 취합 전에 "이 소견을 기각할 근거가 원문에 있는가"로 전
   항목을 재검한다. 라운드 2에서 이 자기 점검이 틀린 수리안 하나를 사전에 잡았고, 취합
   과정에서 잃어버린 소견 하나를 복원했다 — 취합 자체도 오류 경로이므로 중간 산출물을
   보존하라.

**하지 말아야 할 것:**

1. **텍스트를 늘리는 처방을 기본값으로 삼지 마라.** 적대 검증은 언제나 추가 방향으로
   민다 — 이 저장소의 이름 붙은 병이다. 추가를 제안하려면 그 문장이 막는 구체적 실패
   경로를 대고, 대안으로 "빼서 닫는 길"이 없는지 먼저 봐라.
2. **통째 수용도 통째 기각도 하지 마라.** 남의 소견(이전 감사·다른 모델)을 다룰 때는
   항목별로 원문에 대조해 채택/강등/기각을 갈라라.
3. **요약본을 감사하지 마라.** 대상은 디스크의 원문뿐이다. 리포트와 원문이 다르면 원문이
   이긴다.
4. **판정 불가를 추측으로 메우지 마라.** 정보가 부족하면 "판정 불가 + 필요한 실측·질문"을
   명시하고 넘어가라.
5. **범위를 스스로 넓히지 마라.** 변경분 감사에서 저장소 전체의 재설계 소감을 내는 것은
   감사가 아니다. 범위 밖에서 우연히 본 진짜 결함은 "범위 밖 발견"으로 따로 한 줄만.
6. **완료 증거로 개수를 쓰지 마라.** "테스트 N개 통과"·"소견 N건 처리"는 진행의 기록이지
   의미 안전성의 증거가 아니다.

## 4. 유즈케이스 매트릭스의 사용법

`docs/usecase-matrix_ko.md`가 커버리지 도구다. 감사에서의 사용 순서:

1. 감사 대상 변경이 **어느 칸에 닿는지** 먼저 표시한다(사람 축 H × AI 축 A).
2. 그 칸의 기존 판정(정합/긴장/공백)이 이 변경 뒤에도 참인지 원문 대조로 재판정한다.
   칸에 "검증 시 확인할 것"이 있으면 그것이 최소 조건이다.
3. 변경이 **새 유즈케이스를 만들면** 행을 추가하라고 보고한다 — 매트릭스는 상시 문서라
   감사가 발견한 형태도 축적 대상이다.
4. 매트릭스의 한계를 그대로 인용하라: 이 목록은 귀납이다. 매트릭스 전 칸 통과는 "구조적
   으로 걸을 수 있는 칸은 깨끗"이지 전수 증명이 아니다.

## 5. 무한 루프 방지 — 종료 조건은 개수가 아니라 클래스

무한 루프의 원인은 하나다: **종료 조건을 소견 개수에 걸면 영원히 안 끝난다** — 소견은
항상 나온다. 라운드마다 문장 해석이 조금씩 달라지며 같은 자리를 맴돌게 된다.

**종료 조건 (라운드 시작 전에 이 문구대로 고정하라):**

```
다음이 모두 참이면 텍스트 감사를 멈춘다 —
  · 이번 라운드의 소견 중 규칙 충돌·소실 경로 클래스가 0
  · 남은 소견이 전부 "양갈래 독해의 단일화" 또는 표현 등급
  · 그 수리가 전부 수렴형(모호어→기계 검사, 또는 삭제)이고 해석을 새로 여는 문장이 없음
멈춘 뒤에는 동의어를 바꾸는 새 라운드를 열지 않는다 — 그것은 품질을 올리지 않는다.
다음 검증 수단은 텍스트가 아니라 실전이다.
```

**개인 차원의 회로 차단기** (하나라도 걸리면 그 소견을 관찰로 넘기고 손을 뗀다):

- 같은 문장을 세 번째 고치고 있다
- "혼동될 수 있다"고 쓰기 시작했는데 구체적인 오독 두 가지를 못 대겠다
- 수리안이 앞 라운드의 수리를 되돌리고 있다 (진자 운동 — 두 안 모두 관찰로)
- 소견의 근거가 원문이 아니라 "지난 라운드의 내 소견"이다

**수리 뒤의 재감사는 유계로:** 수리된 문장만 대상으로, 같은 채택 기준으로, 한 번.
재감사의 소견이 전부 수렴형 수리로 닫히면 거기서 종료 선언을 기록한다 — 0.14.1이 이
형태의 이행 기록이다(소견 27 → 수리 17 → 재감사 소견 7 → 수리 7 · 신규 충돌 0 → 종료).

## 6. 운영 절차와 산출 형식

**절차** (이상적 결과에 이르는 순서):

```
0  사전 고정      범위 · 채택 기준 · 종료 조건 · 산출 형식 (1절)
1  기계 검사      테스트 · 배포물 한글 0 · 잔존 개념 grep · ko↔en 구조 동형성
2  렌즈별 패스    반증자 → 문자 실행 워커 → (구조 변경 시) 좌표 스윕 → 뺄셈 감사
                  가능하면 각 렌즈를 별도 컨텍스트로. 시나리오는 실제 대사로 걷는다
3  매트릭스 대입  닿는 칸 재판정 (4절)
4  자기 점검      "이 소견을 기각할 근거가 원문에 있는가"로 전 항목 재검 (3절 9항)
5  보고           아래 형식. 수리는 하지 않는다 — 보고 후 소유자 승인이 리듬이다
```

**보고 형식** — 소견은 심각도 계층으로 나눈다:

```
1계층  조용한 자료 소실이 가능한 곳          (발생 조건 교집합까지 명시)
2계층  세션이 멈추거나 잘못 행동할 수 있는 곳
3계층  정밀도·중복·표류 — 지금은 무해하나 편집 횟수에 비례해 악화되는 것
설계 긴장  결함이 아니라 목적과의 거리 측정 — 관찰 후보
```

항목마다: **무엇을(원문 인용 + 위치) / 왜 위험한가 / 예상되는 문제(구체적 장면) /
발생 조건(교집합이면 교집합으로)**. 마지막에 반드시: 검사했으나 깨끗했던 영역의 목록
(무엇을 공격했고 왜 버텼는지 — 0건 보고의 신뢰는 여기서 나온다), 그리고 이 감사의 한계
(안 걸은 경로, 실측 못 한 주장).

**명백 결함과 판단거리의 분리**: 텍스트 자신이 선언한 규칙의 위반·문자 그대로의 충돌은
"명백"으로, 설계 선택이 걸린 것은 "판단거리"로 나눠라. 소유자는 전자를 바로 승인하고
후자를 선택지로 받는다.

## 7. 예외 상황의 처치

| 상황 | 처치 |
|---|---|
| 원문과 리포트·기획서가 어긋난다 | 디스크의 원문이 정본이다. 어긋남 자체를 소견으로 |
| 소견이 소유자의 기록된 결정과 충돌한다 | "뒤집기 제안"으로 분리하고 기록된 이유의 반증을 포함하라. 반증이 없으면 내지 마라 |
| 실측 없이는 판정할 수 없다 | 판정 보류 + 정확한 실측 절차를 제안 (실행 가능한 명령 수준으로) |
| 자기 수리안이 틀렸음을 발견했다 | 조용히 고치지 말고 철회를 기록하라 — 철회 기록이 감사 신뢰도의 데이터다 |
| 대상 텍스트가 자기 언어(한국어/영문) 쌍을 가진다 | 실행되는 쪽(영문)을 감사하고, 쌍의 의미 불일치는 별도 클래스로 보고 |
| 감사 중 도구가 이상 동작한다 (예: 프록시된 grep의 오탐) | 도구를 바꿔 재확인하고 그 사실을 기록하라 — 이 저장소에서 실제 있었던 일이다 |
| 두 감사자의 소견이 충돌한다 | 원문 대조로만 판정한다. 다수결·권위로 하지 않는다 |

## 8. 발주자(소유자)용 — 감사 브리핑 템플릿

새 GPT 세션에 다음을 함께 준다:

```

1. 이 문서 (audit-guideline_ko.md) 전문
2. 감사 범위: <파일 목록 | 커밋 범위>의 원문

4. 지시문: "위 가이드라인의 채택 기준과 종료 조건을 따르라. 소견마다 원문 인용과
   구체적 실패 경로를 붙여라. 수리하지 말고 보고만 하라. 0건은 유효한 결과다.
   렌즈는 <반증자|문자 실행 워커|좌표 스윕|뺄셈 감사> 중 <하나>다."
```

렌즈 하나당 세션 하나가 이상적이다. 여러 렌즈를 한 세션에 몰면 앞 렌즈의 발견이 뒤
렌즈의 독해를 오염시킨다.

## 9. 이 문서 자신의 한계

이 가이드라인도 귀납이다 — 16개 릴리스에서 나온 결함 종류로 만들었고, 아직 안 나온
종류는 못 덮는다. 실전(실제 프로젝트 사이클)이 새 결함 클래스를 내면 2절의 표에 행을
추가하라. 그리고 이 문서가 감사자에게 요구하는 것 전부를 이 문서 자신도 받는다 — 여기
적힌 규칙 중 실패 경로를 못 대는 것을 찾으면 그것이 소견이다.
