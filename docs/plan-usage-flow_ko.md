### 30초 요약

> devflow는 **"사람"은 모델링했지만 "동시에 흐르는 작업"은 모델링한 적이 없다.** 트리와 능력
> 문서는 이미 도메인 축인데, 점유·연속성·지식 도달만 사람 축에 묶여 있었다. 그래서 터미널 두
> 개가 곧 정합성 이상이고, 유지보수에서 배운 것이 다음 유지보수에 닿지 않는다.
>
> **모드를 하나로 통합하고(D6), 그 위에서 세 성질을 능력 번호 축으로 옮긴다.** 능력 번호는 이미
> 디스크에 있는 좌표라 새 식별자가 필요 없다. 통합이 정본을 줄여 나머지 추가분의 비용을 낸다.

읽는 순서: 1(축) → 2(지식 4층) → 3(기계 열) → 4(유계 수리) → 5(동선 검증)
→ 6(**실현 가능성과 한계**) → 7~9(승계·배치·핀) → 10(작업 규율) → 12(기각 계보)
→ 13(**다음 세션에게**).
**바쁘면 0 · 1 · 3 · 6절만 읽어도 판단할 수 있다.**

**이 문서 하나만 읽고 시작할 수 있게 썼다.** 앞선 대화를 참조하지 않는다.
`docs/handoff-usage-flow_ko.md`는 문제 제기 원본이고, **판정과 설계는 이 문서가 정본**이다 —
둘이 다르면 이 문서가 이긴다(핸드오프의 방향 2는 12절 X1에서 기각됐다). 배포 산출물이 아니라
작업 문서이므로 영문 쌍도 CHANGELOG 항목도 필요 없다.

## 1. 축 — 이 재설계의 전부

### 1.1 지금 어긋난 것

devflow의 상태는 이미 두 축으로 나뉜다.

```
도메인 축 (능력 번호)              사람 축 (방)
  devflow/tree/04-payment/           devflow/HANDOFF.md
  capabilities/04-payment.md         devflow/users/<id>/
  tree/04-payment/verify.md
```

그런데 작업의 세 성질이 **잘못된 축**에 붙어 있다.

| 성질 | 붙은 축 | 벌어지는 일 |
|---|---|---|
| 점유 | 사람 (`.wip.` 하나) | 터미널 두 개 = **정합성 점검 1번 이상(異常)** |
| 연속성 | 사람 (HANDOFF 하나) | 두 터미널이 경계에 닿으면 **나중 것이 앞 것을 덮어쓴다** |
| 지식 도달 | 카드 사슬 (`Depends`) | 유지보수 카드는 의존이 없어 **사슬이 끊긴다** |

원인은 하나 — **사람 하나 = 작업 흐름 하나**라는 가정. 실제로는 한 사람이 터미널 다섯 개로 다섯
도메인을 동시에 돌린다.

### 1.2 옮긴다

```
모드      솔로 / 팀 두 갈래   →   하나
점유      사람당 1개          →   사람 × 능력당 1개
연속성    HANDOFF 한 파일     →   능력별로 트리·문서·미수확 지식에서 도출 (새 파일 0)
지식 도달 의존 사슬만         →   같은 능력이면 자동, 다른 능력이면 journal 능력 번호 줄
순서      정의 없음           →   정본 후보 순서
```

## 2. 지식이 쌓이는 네 층

소유자가 이전에 쓰던 중계 노트의 성질은 **"최신은 자세히, 오래된 건 축약, 도메인 단위"**였다.
devflow는 그것을 네 층으로 이미 갖고 있었고, 빠진 것은 **1층이 아무에게도 읽히지 않는다**는 것뿐이었다.

```
Tier 0 · 코드                 결과물의 정본. "모델과 API가 무엇인가"의 답은 항상 여기다
   ▲ 색인
Tier 1 · 미수확 카드의 승계 줄  마지막 폐쇄 이후 완료된 카드들의 carry: 줄. work이 자동으로 읽는다
         폐쇄가 일어나면 Tier 2로 수확되고 이 목록은 0으로 리셋된다
   ▲ 수확 (verify, 능력 폐쇄 시)
Tier 2 · 능력 문서            capabilities/NN-*.md · 185줄 상한 · 폐쇄마다 통째 재생성
   ▲ 승격 (발견→갱신 표)
Tier 3 · Layer 0 · journal    확정 지식의 종착
```

**"최신은 자세히, 오래된 건 축약"이 자동으로 성립한다.** 자세한 층(카드 진행 로그 전문)은 사람이
열면 그대로 있고, 기계가 읽는 것은 압축된 승계 줄이며, 폐쇄가 그것을 다시 한 번 압축한다.

### 2.1 왜 이미 수확된 카드의 로그는 안 읽는가 — 모순이 아닌 이유

- **그 작업의 결과물은 코드에 있다.** 카드 로그가 아니다.
- **능력 문서는 그 코드로 가는 색인이다.** `Entrypoints`가 정확 경로를, `Current behavior`가
  동작을, `Concept model`이 식별자와 관계를, `Invariants`가 반드시 참인 것을, `Consumed
  contracts`가 다른 도메인과의 접점을 준다. work은 거기서 경로를 얻어 **코드를 직접 읽는다** —
  3주 전 로그로 모델을 재구성하지 않는다. 그 사이 누가 고쳤을 수 있으므로 코드가 더 진실하다.
- **진행 로그가 담는 것은 다른 종류다**(왜 그렇게 했나, 무엇을 버렸나, 실패의 인과). 그중 지속적인
  것은 이미 승격 경로가 있고, 남는 것은 그 작업에만 의미 있는 비계다.

### 2.2 흔들리는 지점을 미리 열거한다

| | 상황 | 판정 |
|---|---|---|
| A | 능력 문서가 **가설** | 사실로 믿지 않고 코드에서 재확인한다. 정본에 이미 있음. **동작** |
| B | **첫 폐쇄 전** — 검증 구역이 `None.` | `Covered cards`가 비어 있어 그 능력의 완료 카드 전부가 Tier 1이 된다. 자동으로 메워진다. **동작** |
| C | 유지보수 카드는 의존이 없다 | **M3이 닫는다** |
| D | 재폐쇄를 미뤄 Tier 1이 쌓인다 | 승계 줄이라 카드당 1~3줄. 20장이어도 60줄. **동작** |
| E | 능력이 185줄 상한 초과 | 정본이 허용하고 보고한다. 분할은 사용자 결정. **동작** |
| F | 다른 능력의 모델을 알아야 함 | `Consumed contracts`가 정확 경로를 준다. 상대 문서 전체는 안 읽는다. **동작** |
| G | 다른 능력에 대해 알게 된 것 | Tier 1은 같은 능력 안에서만 흐른다. **M5가 닫는다** |

## 3. 설계 — 기계 열

### M1 · 모드 통합 (D6) — 이 배치의 토대

**솔로 모드를 없앤다.** 방은 항상 존재하고, 모드 판단이 모든 스킬에서 사라진다.

| 지금 | 통합 후 |
|---|---|
| `users/` 없으면 솔로, 있으면 팀 | **하나.** 방이 항상 있다 |
| 정본에 모드 조건문 **59줄** | 조건 없음. 전환 절차 삭제 |
| 솔로: `02.4.wip.md` / 팀: `02.4.wip-jmp.md` | 항상 `02.4.wip-jmp.md` |
| 솔로: `02.4 signup` / 팀: `jmp 02.4 signup` | 항상 `jmp 02.4 signup` |
| `integration:`·`merge:`는 팀 전용 | 항상. **혼자면 지금 쓰는 브랜치** |

**혼자 쓸 때 추가 규칙은 자동으로 무의미해진다** — 통합 브랜치가 현재 브랜치면 "통합에 착지"는
그냥 커밋이고, "통합 tip을 포함"은 항상 참이고, digest 대상은 전부 내 접두사라 0건이다.

**측정된 비용**(추측이 아니라 실측):

- **읽기(토큰) 비용 증가 0.** 정본은 지금도 그 59줄을 전부 읽는다. 솔로는 "무시하라"고 말할 뿐이다.
  통합하면 모드 결정·전환 절차·이중 권위 문구가 사라져 **20~30줄 순감**이다.
- 세션당 git 명령 약 4개(신원 해석 · digest · fetch · 정합성 8번).
- **카드당 커밋 1개**(점유 커밋). 이것이 유일한 실질 비용이며, 동시에 **워크트리 지원의 열쇠**다.

#### 신원은 어떻게 고정되는가

`owner.md`가 **선언**이고 git이 **열쇠**다. 새 저장 공간도, 새 설정 파일도 없다.

```
devflow/users/jmp/owner.md      ← 두 줄이 전부
  id: jmp
  git: "Jaemin Park", jmp@example.com
```

- **절차**: `git config user.name` · `user.email` 두 값을 읽고, `devflow/users/*/owner.md`(각 2줄)의
  `git:` 줄과 대조해 내 방을 찾는다.
- **빈도**: 세션당 한 번, 트리·journal·공유 문서에 **처음 쓰기 직전**에만. 캐시하지 않는다 —
  캐시는 낡을 수 있고 캐시하지 않아도 명령 하나다.
- **비용**: git 명령 2개 + 2줄 파일 N개(N = 방 수). 혼자면 N=1.
- **git 설정이 없으면**: git 자체가 `user.email` 없이 커밋을 거부한다. **devflow가 일할 수 있는
  저장소라면 신원은 이미 있다.** 해결 불가한 세션(CI·봇)은 지금처럼 읽기 전용이다.

두 가지 예외를 각각 한 줄로 막는다(6.7 W5).

- **신원이 바뀌면** 매칭이 실패해 방이 하나 더 생긴다 → 방이 있는데 매칭이 안 되면 **기존 방들을
  보여주고 묻는다**(새 사람인가, 신원이 바뀐 것인가). 임의로 만들지 않는다.
- **비-Git 프로젝트**는 신원이 없다 → 방이 정확히 하나면 그것이 나이고, 둘 이상이면 이상으로 보고한다.

#### 기존 프로젝트 업그레이드 — 실행자는 기존 소유권으로 쪼개진다

정본의 솔로→다중 전환 절차를 업그레이드 절차로 재지정한다. **resume은 파일을 쓰지 않으므로
resume이 실행할 수 없다**(6.7 W1). 소유권대로 나눈다.

| 부분 | 실행자 | 근거 |
|---|---|---|
| arch.md에 `integration`·`merge` 추가 | **arch** | `Brownfield` 필드 한 개만 추가하는 기존 선례와 같은 형태 |
| 방 생성 | 신원 해석 단계 | 이미 정본에 있다("매칭 없음 → 한 번 묻고 방을 만든다") |
| 내 점유 카드 `.wip.` → `.wip-<id>.` · HANDOFF 이동 | **work** | 자기 점유와 HANDOFF는 work 소유 |

**새 실행자 0, 소유권 위반 0.** 정합성 6번(무기명 `.wip.`, 루트 HANDOFF)은 삭제하지 않고
**업그레이드 미완의 탐지기**로 의미만 바뀐다.

#### 통합에서 충돌하는 규칙 하나 — 병렬 그룹 (6.7 W2)

지금 솔로는 "승인된 병렬 그룹을 한 번에 통째로 점유", 팀은 "항상 하나씩"이다. 합치면 충돌한다.
→ **그룹 통째 점유를 유지한다.** 그것을 허가하는 것은 카드에 적힌 상호 병렬 승인이고, 팀의
"구성원에게 분배"는 같은 승인을 다르게 소비하는 것일 뿐이다. 한 사람이 통째로 잡는 것과 여럿이
나눠 잡는 것을 **둘 다 허용**한다.

### M2 · 능력 축 점유 (D1)

`Only one .wip. at a time` → **깊이 1 단위(능력·골조)당 하나, id별.**

```
터미널 A ──▶ 04-payment/04.4-refund.wip-jmp.md      점유 1
터미널 B ──▶ 03-customer/03.9-filter.wip-jmp.md     점유 2   ← 정상
터미널 C ──▶ 04-payment/04.5-….wip-jmp.md           같은 능력 둘 → 충돌로 잡힌다
```

- 정합성 1번: "`.wip.` 2개 이상" → "**같은 깊이 1 단위 안에** 2개 이상이고 상호 병렬 승인도
  evidence-wait도 설명하지 못한다". 두 예외는 같은 능력 안의 예외이므로 위치가 정확히 맞는다.
- work: 내 점유가 여럿일 수 있다. 정본 후보 순서로 첫 번째를 고른다.
- resume: 내 점유를 전부 나열하되, **전문 읽기는 진행할 하나만**(6절 L3).
- **동시 실행 가능 여부는 이미 있는 병렬 조건을 그대로 따른다** — 파일이 겹치지 않고 개발 서버를
  공유하지 않을 것. 새 조건 0.

### M3 · 승계 줄 (D2)

work이 카드를 시작할 때, 그 카드의 깊이 1 단위 아래에서 **능력 문서의 `Covered cards`에 없는
`.stale.` 아닌 `.done.` 카드**들의 승계 줄을 읽는다. 그 여집합은 이미 신선도 비교를 위해 계산된다.

**승계 줄** — work이 `.done.` 직전, 착지 점검 뒤에 진행 로그에 붙이는 고정 형식:

```text
YYYY-MM-DDTHH:MM:SSZ carry: <이 능력의 다음 카드를 틀리게 만들 수 있는 사실 | none>
```

- 이미 있는 `remote evidence check` 줄과 같은 관용구다. 새 개념이 아니다.
- **이미 문서·journal·코드에 착지한 것은 적지 않는다.** 착지 점검(0.9.18)이 먼저 돌고, 승계 줄은
  **착지할 행이 없는 잔여** — 능력 국소의 함정, 반증된 접근, 미문서화 측정값 — 만 담는다.
- 읽기 비용이 **카드당 1~3줄 × 미수확 카드 수**로 유계가 된다.
- 진행 로그 전문은 읽지 않는다(6절 L2가 그 이유다). 사람은 언제든 열어볼 수 있다.
- 이 집합은 reviewer·verifier에게 주지 않는다 — 둘의 무지가 자산이다.
- verify가 폐쇄 때 검증 구역의 `Traps`·`Current behavior`로 수확한다. 카드는 이미 갱신 입력이다.

### M4 · 작업 단위는 카드 (D3)

**아무것도 만들지 않는다.** 카드 = 완료 신호 하나 = 커밋 하나. 세션의 시작도 끝도 기록하지 않는다.
터미널이 조용히 죽어도 카드는 디스크에 남고 진행 로그가 정확한 다음 지점을 말한다.

이 절은 추가가 아니라 **기각 기록**이다. "세션 묶음", "날짜 묶음", "flows 폴더"는 전부 닫는 기점을
요구하고, 닫는 기점은 조용히 죽는 세션에서 반드시 샌다.

### M5 · 다른 능력으로 보내는 관측 (D4)

```text
YYYY-MM-DDTHH:MM:SSZ capability note: capability: <NN>; note-json: <JSON string containing the observation>
```

- **누가 쓰나**: 발견→갱신 표 한 행 — "지금 작업 중이 아닌 다른 능력에 대해, 코드에서 확인된
  관측을 얻었다".
- **누가 수확하나**: `<NN>`이 폐쇄될 때 검증 구역 갱신 입력에 포함되고, 같은 폐쇄의 journal 정리에서
  삭제된다. 현재 코드 범위에서 재확인되지 않는 줄도 삭제한다 — 근거는 정본에 이미 있다("재현
  조건이 현재 코드에서 사라진 함정만 삭제한다"). **수명이 정의되어 journal이 무한히 자라지 않는다.**
- 팀 공유다. 남이 그 능력을 열어도 보인다.

### M6 · 같은 능력 안에서의 전환 (D5)

M2 이후 **다른 도메인으로 갈 때는 절차가 필요 없다** — 그냥 그 능력의 카드를 점유한다. 절차가
필요한 경우는 같은 능력 안에서 갈아탈 때뿐이다.

```
① 현재 diff와 진행 로그를 `NN.N wip: <중단 사유>` 체크포인트로 착지 (변경이 없으면 커밋도 없다)
② 점유 접미사를 제거해 대기로 되돌린다 — 진행 로그는 카드에 남는다
③ 정본 후보 순서로 라우팅. 체크포인트를 먼저 통합하고 해제를 구속 결정으로 착지시킨다
```

중간 인계 금지와 충돌하지 않는다 — 파킹은 인계가 아니라 해제다. 코드는 체크포인트에, 로그는
카드에, 상태는 트리에 온전히 남는다.

### M7 · HANDOFF 축소 (D7)

```markdown
# HANDOFF · <YYYY-MM-DDTHH:MM:SSZ>
## Next single step          <!-- one tree path | none -->
## Open decisions (needs a human)
```

- `Just learned`·`Traps` → 같은 능력이면 카드의 승계 줄, 다른 능력이면 `capability note`.
  **덮어쓰기로 확실히 사라지던 것이 이제 남는다.**
- `Next single step`은 **필수**가 된다(정본 후보 순서의 승계 단위 입력). 대기·점유 카드가 하나도
  없을 때만 `none`. → work의 "네 절이 다 비면 빈 파일도 정상"과 README의 같은 문장을 함께 고친다.
- **업그레이드 마이그레이션**: 업그레이드 후 첫 경계는 기존 두 절의 내용을 먼저 착지시킨 뒤
  덮어쓴다(발견→갱신 표 · `capability note` · 현재 카드의 승계 줄). 착지 후에만 덮어쓴다.
- 터미널 여러 개가 덮어써도 잃을 것이 거의 없다.

### M8 · 정본 후보 순서

**놓이는 곳**: `principles/SKILL.md`, 정본 순서 두 개 다음의 짧은 별도 절.

> **Canonical candidate order.** A selection order among candidates, not a comparison order for
> paths or card numbers.
>
> A candidate's **unit** is the first path component below `devflow/tree/`, or the number on an
> unopened capability's waiting file.
>
> The **session unit** is the unit the user named in the current conversation, by the canonical
> recognition below. The **carried unit** is the unit whose number leads the path in
> `## Next single step` of the room's HANDOFF, when a unit with that number exists.
>
> **Canonical recognition.** A complete product.md capability name, a standalone number token
> compared with unit numbers as integers, or text identifying foundation or a standalone `01`,
> selects that unit. A standalone task-card number resolving to exactly one card selects that
> card and its unit. Zero or more than one resolution selects nothing.
>
> Order: the card named by the user; then candidates in the session unit; then candidates in the
> carried unit; then the rest. Within a unit and among the rest, canonical card-number order.
>
> Where a matched routing row can be satisfied by more than one unit and the row names no
> selection order, take candidates in this order. It never changes which row matches, never makes
> an unready card ready, and never grants or withholds a claim. A row naming its own order keeps
> it. Staleness governs trust in HANDOFF's statements; the carried unit is only an ordering key
> and is used even when HANDOFF is stale.

인식 기계는 이미 도메인 진입에 있다. 정본으로 올리고 resume·baseline-predicates의 서술을 인용으로
바꾼다 — **순감(-7줄)**.

### M9 · 인식의 재배선 — 세 출구

| 출구 | 배선 | 닫는 동선 |
|---|---|---|
| 순서 | 세션 지목 단위 → M8 | U3 · U4 · U13 · U15 |
| 유지보수 | 대화의 변경 요청 → resume 새 행 → split이 기존 `maintenance routing pending`을 쓴다 | U5 |
| 설명 → 착수 | 도메인 진입이 고른 단위가 그 세션의 세션 지목 단위다 | U6 |

**새 라우팅 행**: `| 현재 대화에 사용자가 낸 변경 요청이 있고, 그것을 보존하는 저널 줄·verify
항목·점유 카드가 아직 없다 | split — maintenance routing |`
위치는 `A card of mine is claimed` **아래**, 모든 복구 행보다는 **아래**. 모드 중립이라 그린필드/
브라운필드 비대칭이 사라진다.

### M10 · resume 보고 · work 카드 선택

**보고** — 제안 + 사유 + 대안 + 신선도:

```
"…The next step is <one step> (<selected by: your request | the last handoff | canonical order>);
 also open: <other units with a candidate under the same row | none>.
 <the proposed unit's baseline projection line, when it has a capability document>.
 Proceed?"
```

사유 한 절이 "임의로 골랐다"를 구조적으로 불가능하게 만든다. 대안 목록은 능력 수로 유계다.
신선도 한 줄은 work이 이미 쓰는 형식을 그대로 재사용한다. 세션 지목 단위에 후보가 없으면 그
사실을 한 절로 말한다.

**work의 카드 선택** — 판단어 제거:
1. 이 세션이 이미 정확한 카드 경로를 보고하고 승인받았다면 **그 카드**.
2. 아니면 준비된 대기 카드를 **정본 후보 순서**로 정렬한 첫 번째.

1번이 없으면 resume이 05.4를 승인받았는데 work이 02.1을 잡는 **같은 세션 안의 모순**이 생긴다.

## 4. 유계 수리

| # | 결함 | 수리 |
|---|---|---|
| **R1** | 재개된 능력이 「신선」으로 보고된다 — 신선도 비교가 `.done.` 집합만 보므로 유지보수 `.wip.` 카드가 집합을 바꾸지 않는다. **방금 깨졌다고 신고된 행이 검증된 사실로 전달된다** | 비교 하나 추가: 폴더가 `.done`이 아니고 `.stale.` 아닌 미완 카드가 있으면 검증 진술은 가설. 폐쇄 시점엔 발화하지 않는다. 카드 집합은 이미 열거되므로 추가 읽기 0. 소비자 투영에도 같은 조건 |
| R2 | split이 능력 문서를 한 번도 읽지 않아 매핑을 이름 한 줄로 결정한다 | 매핑 단계 한정으로 후보 능력 문서의 **고정 첫 4줄**을 읽는다. `Boundary: owns …; does not own …`가 매핑 오라클이다. 4줄 × 능력 수 |
| R3 | 잘못 매핑된 카드에 회수 경로가 없다 | **카드 회수** — 점유된 적 없고 태스크 커밋이 이름을 부른 적 없는 대기 카드는 바로잡는 계획 커밋에서 삭제하고 번호를 은퇴시킨다. 태스크 커밋이 담았으면 옮기지 않고 journal 한 줄로 기록 |

| **R6** | Binding ADR·Consumed path에 걸린 가설은 재확인이 구조적으로 불가능해 리뷰가 이의를 반환한다 | 설계 가설: 그 구역의 유효한 Binding ADRs가 이름한 **이미 연** 경로를 권위에 추가. 검증 가설: **재확인 목적에 한해** `Consumed paths`를 코드 탐색 경계에 포함(Standards 게이트·Audit 범위는 확장하지 않는다 — 그 금지 문장 유지) |
| **F8** | `Next single step` 필수화가 "빈 HANDOFF도 정상"과 모순 | work·README를 같은 배치에서 수정 |
| **F9** | 정합성 5번 오경보 — 가리키던 대기 카드가 점유되면 그 경로가 사라진다 | 이미 있는 결함. 정본의 관용구(상태 접미사 제거 후 정확히 하나)로 판정 |
| **F12** | `1 태스크 = 1 커밋`이 무엇을 담는지 정본에 없다 | **그 카드가 바꾼 경로와 카드 자신만.** 리뷰 diff도 같은 범위. 다른 흐름의 미커밋 변경을 쓸어 담지 않는다 |
| **F13** | 워크트리마다 방 파일 사본이 달라 합칠 때 충돌한다 | 병합 규칙 — `Open decisions`는 합집합, `Next single step`은 최신, 마커는 자손 해시(**마커 규칙은 이미 정본에 있다**) |

## 6. 실현 가능성 — 한계와 그 처리

### L1 · 해결 불가 — 같은 워킹 트리에서 검증을 동시에 돌리는 것

git의 워킹 트리는 하나다. 터미널 A가 04를, B가 03을 고치면 두 변경이 한 트리에 섞인다.

| 지점 | 결과 |
|---|---|
| 편집 | **문제없음.** 서로 다른 파일이면 충돌하지 않는다 |
| 커밋 | 경로를 명시적으로 스테이징한다 → **F12가 이것을 정본에 못박는다** |
| 리뷰 diff | 같은 범위로 제한 → F12 |
| **verify** | "devflow 밖 경로가 미커밋이면 `unverified`" → **다른 흐름의 미커밋 코드가 있으면 검증이 통과할 수 없다** |
| **audit** | 같은 이유로 막힌다 |
| 완료 신호 | **빌드를 공유한다.** B가 컴파일을 깨면 A의 신호가 실패한다 |

**완화하지 않는다.** 그 게이트는 "재현할 수 없는 검증 금지"의 구현이고, 능력 범위로 좁히면 공유
코드를 누가 고치는 중일 때 **거짓 통과**가 난다. 안전 장치를 편의로 바꾸는 거래다.

**정직한 결론: 편집은 병행되고, 검증과 빌드는 직렬화된다.** 그리고 이것은 새 제약이 아니다 —
devflow는 이미 병렬 조건을 "파일 무겹침 + 개발 서버 무공유"로 정의해 두었다. 동시 터미널에 그
조건을 그대로 적용한다. **새 규칙 0.**

완전한 격리를 원하면 워크트리를 쓴다(L1-a).

### L1-a · 배치별 판정

| 배치 | 점유가 서로 보이나 | 커밋 격리 | 검증 | 판정 |
|---|---|---|---|---|
| **한 워킹 트리 + 터미널 여럿** | ✅ 파일 이름이 즉시 | ⚠️ F12로 명시 | ⚠️ 직렬 | **지원.** 가장 흔한 배치 |
| **워크트리 여럿** | ✅ 점유 커밋이 통합 브랜치에 | ✅ 완전 | ✅ 각자 깨끗 | **지원.** M1의 점유 커밋이 열쇠, F13이 방 파일 병합을 정의 |

모드 통합(M1) 덕분에 두 배치가 **같은 기계**로 지원된다. `flows/` 폴더도, 두 겹 식별자도, 닫는
기점도 필요 없다. 말씀하신 두 아이디어가 이미 있는 기계와 대응한다 — **"같은 작업에 동시 접근
금지"는 점유 커밋**이고, **"파일 할당"은 arch의 Code structure A(`src/<capability>/`)**다.

**워크트리의 남는 비용 하나**: 검증과 폐쇄는 통합 브랜치에서 돈다. 워크트리 하나를 통합 브랜치에
두거나, 검증할 때 통합으로 옮겨야 한다. 이것은 의미상 옳다 — 검증은 "통합된 것"을 확인하는 것이고,
`Code revision`이 애초에 저장소 전체에서 계산된다.

### L2 · 해결함 — 미수확 지식 읽기 비용

진행 로그 전문을 읽으면 카드마다 수천 줄이 된다. **실현 불가능하다.** → 승계 줄(M3)로
카드당 1~3줄. 20장이어도 60줄.

### L3 · 해결함 — 여러 점유 시 resume 읽기량

정본은 "내 점유 카드를 전문 읽는다"이므로 N배가 된다. → **진행할 단위의 것만 전문 읽고, 나머지는
경로·상태·번호만 보고한다.**

### L4 · 해결함 — 업그레이드 시 데이터 손실

M7이 HANDOFF 두 절을 없애는데 기존 파일에는 내용이 들어 있다. → **업그레이드 후 첫 경계는 옛 내용을
먼저 착지시킨 뒤 덮어쓴다.** 옛 `.done.` 카드에 승계 줄을 소급 생성하지는 않는다 — "브라운필드를
소급 백필하지 않는다"와 같은 판단이다.

### L5 · 해결함 — `capability note` 누적

폐쇄 때 수확을 시도하고, 현재 코드 범위에서 재확인되지 않는 줄은 삭제한다. 수명이 정의된다.

### L6 · 확인함 — 나머지 보편 상황

| 상황 | 판정 |
|---|---|
| CI·봇 세션 | 신원 미해결 → 읽기 전용. 변화 없음 |
| 한 사람 두 기계 | 마커 충돌 규칙이 이미 있다 |
| 같은 능력을 두 사람이 다른 카드로 | 허용된다(id별 판정) |
| **비-Git 프로젝트** | Git 게이트가 이미 건너뛴다. 방과 id는 파일이라 만들 수 있고, 커밋 기반 단계는 무의미해진다. "복구 불가" 경고가 이미 있다 |
| **feature 브랜치를 쓰는 1인** | 검증이 통합 브랜치에서 돈다. `integration:`을 자기 작업 브랜치로 두면 오늘과 같다 |
| 능력 20개 규모 | 트리 전문 나열은 이미 관찰 항목(트리 아카이브 규칙). 범위 밖 |
| 모노레포 | 능력이 모듈에 대응한다. 변화 없음 |
| revert | 트리가 상태를 소유하므로 되돌리면 복구된다 |

### 6.7 · 작성 후 재검증 — 워크플로를 끝까지 걸어서 찾은 것

설계를 쓴 뒤 **기존 프로젝트 업그레이드 → 같은 폴더 터미널 셋 → 유지보수 → 폐쇄**를 처음부터 끝까지
걸었다. 여섯 개가 나왔고 전부 반영했다. 각 항목은 "걷지 않았으면 나오지 않았을 것"이다.

| # | 걸으면서 드러난 것 | 반영 |
|---|---|---|
| **W1** | **업그레이드 실행자가 없다.** resume은 파일을 쓰지 않으므로 방 생성·개명·필드 추가를 할 수 없다 | 기존 소유권으로 삼분 — arch(필드) · 신원 해석(방) · work(개명·HANDOFF). M1에 표로 반영 |
| **W2** | **병렬 그룹 점유가 통합에서 충돌한다.** 솔로는 그룹 통째, 팀은 하나씩 | 그룹 통째 점유를 유지하고 분배도 허용. M1에 반영 |
| **W3** | **점유가 여럿일 때 resume이 미커밋 변경을 잘못 귀속한다.** 같은 폴더의 다른 터미널 편집물을 내 카드 것으로 읽는다 | 진행할 카드에 대해서만 대조하고, 나머지는 귀속하지 않은 채 보고. L3에 합류 |
| **W4** | **커밋 격리가 태스크 커밋만으로 부족하다.** 점유·계획·경계 커밋도 남의 미커밋 파일을 쓸어 담을 수 있다 | F12를 **모든 devflow 커밋**으로 확대 |
| **W5** | **신원이 바뀌면 방이 하나 더 생긴다.** 비-Git 프로젝트는 신원 자체가 없다 | 매칭 실패 시 기존 방을 보여주고 묻는다 · 비-Git은 방 하나만 유효. M1에 반영 |
| **W6** | 완료 신호가 저장소 전체를 돌리면 다른 흐름의 깨진 코드에 걸린다 | 규칙이 아니라 **문서화된 귀결**로 남긴다 — 신호를 능력 범위로 좁히는 것이 권장. 이미 있는 병렬 조건과 같은 성질 |

확인만 되고 문제없던 것: HANDOFF의 `Open decisions`는 이미 "미해소 항목 반드시 이월"이라 터미널
간 덮어쓰기에서 살아남는다. `Next single step`은 마지막이 이기지만 점유가 있으면 점유가 이기므로
무해하다. 훅·설치기는 영향 없다.

### 6.8 · "못하는 것"의 정확한 크기

L1을 하자로 읽지 않도록 정확히 적는다. **이것은 새 제약이 아니다.**

- 오늘도 미커밋 코드가 있으면 능력 검증은 `unverified`를 기록한다. 이번 설계가 만든 것이 아니라,
  이미 있던 안전 장치가 동시 작업에서 **눈에 보이게** 된 것뿐이다.
- 발화 빈도가 낮다. 능력 폐쇄는 능력이 끝날 때, 또는 유지보수 카드가 끝났을 때만 일어난다.
- 그때 필요한 조치는 "다른 터미널이 커밋 하나 찍기"가 전부다.
- 완화하면 **거짓 통과**가 생긴다 — 공유 코드를 누가 고치는 중인데 통과로 기록되는 것. 그쪽이
  훨씬 나쁜 하자다.

## 8. 배치와 예산 — 한 기획, 세 배치

한 번에 쓰되 **세 배치로 나눠 각각 검증한다.** 이유는 일정이 아니라 **원인 격리**다 — 모드 통합은
기계적이고 대량이며, 새 의미와 섞으면 캠페인이 원인을 분리하지 못한다.

### 배치 1 — 모드 통합 (M1)

의미 변화 없음, 순수 구조. 모든 `multi:` 접두사 제거, 솔로 분기 삭제, 전환 절차를 업그레이드
절차로 재지정, 정합성 6번 의미 재지정, 이중 권위 문구 통합, arch의 `integration`·`merge` 상시화,
README의 "두 모드" 절 재작성.
**추정 순감 -25줄 / 접촉 문장 약 60개.**

### 배치 2 — 축 이동 (M2 · M8 · M9 · M10 · F12 · F13 · F9)

능력 축 점유, 정본 후보 순서, 인식 재배선, 보고 형식, work 카드 선택, 커밋 격리, 방 파일 병합 규칙.
**추정 순증 +30줄**(인식 인용 축약 -7 포함).

### 배치 3 — 지식층 (M3 · M5 · M6 · M7 · R1 · R4 · R5 · R6 · F8 · L4)

승계 줄, `capability note`, 파킹, HANDOFF 축소와 마이그레이션, 유계 수리.
**추정 순증 +31줄.**

### 배치 4 (선택) — R2 · R3 · README 확장

**추정 +17줄.**

재검증(6.7)이 찾은 W1~W5의 반영분 **+7줄**은 배치 1(W1·W2·W5)과 배치 2(W3·W4)에 나눠 실린다.

**전체 순증 약 +43줄**(배치 4 포함 시 +60). 모드 통합의 순감이 나머지 추가분의 비용을 낸다.
설치기 구조 변경 없음 — 새 동반 문서가 없다.

**양 언어**: 배치마다 `_ko` 먼저 → 영문 → 구조 동형성 → 한글 0(README 1) → 설치기 재생성 →
테스트 → 배치 검증. 버전 범프와 CHANGELOG는 마지막 배치에서 한 번.

## 10. 이 저장소를 고치는 세션의 작업 규율

> **범위 선언.** 이 절은 **devflow를 수정하는 작업**에만 적용되고, devflow가 사용자 프로젝트에서
> 하는 일과 무관하며, **스킬 텍스트에 한 글자도 반영되지 않는다.**

1. **좌표 스윕을 먼저.** 만지는 모든 식별자·필드·규칙에 대해 배포물 전체에서 그것을 언급하는
   **모든 문장**을 기계적으로 열거한 뒤 설계를 제출한다. (HANDOFF = 5파일 15곳, 모드 분기 = 8파일
   59줄 — 이 스윕을 건너뛰어 F8·F9를 놓쳤다.)
2. **배치 단위 검증.** 배치마다 동선 렌즈 → 문자 실행 → 뺄셈. 배치를 섞지 않는다.
3. **정지 규칙.** 배치별 재감사 1회 이후의 소견은 **텍스트로 재현 가능한 실패 경로를 제시한 것만**
   고친다. 나머지는 `docs/design.md` 관찰 항목으로.
4. **뺄셈 예산.** 배치별 상한(8절). 초과분은 같은 크기의 삭제 또는 소유자 승인.
5. **자기 중단 신호.** 같은 문장을 세 번째 고치고 있다 / "혼동될 수 있다"로 시작하는데 구체적
   오독을 못 댄다 / 예산을 넘겼는데 삭제할 문장을 못 찾는다 → 즉시 멈추고 관찰 항목으로.

| X1 | **기록된 초점 필드** — HANDOFF에 `## Focus` 한 줄(능력 번호)을 두어 "오늘은 A"를 durable하게 저장 | 핸드오프가 기록한 근거("그 사실이 어디에도 남지 않는다")가 **거짓이다.** 선언은 한 걸음 안에 점유 rename이나 begin 커밋으로 착지하고, 경계 너머는 `Next single step`이 나른다. 남는 구멍은 "선언했는데 디스크 변화 0으로 세션 종료" 하나뿐이고 비용은 문장 하나. 그 하나를 막는 값은 작성자 3명(resume은 파일을 안 쓴다) + 낡음 판정 + 은퇴 대상 판정 + 복구 규칙. **아직 관측된 적 없는 마찰이므로 "실제로 만난 결함에서만 하네스가 자란다"에 걸린다.** 되돌리려면 후보 순서의 첫 항에 한 항 넣으면 되고 나머지 설계는 안 바뀐다 |
| X2 | **`flows/` 폴더** — 터미널마다 상태 폴더를 만들어 동시성을 표현 | 터미널은 **조용히 죽는다.** 닫는 기점이 없어 폴더가 영원히 남고 청소 규칙이 필요해진다. 폴더가 늘면 AI가 한 번에 목록을 못 본다. 능력 축은 사라지지 않으므로 닫을 필요가 없다 |
| X3 | **사람 아래 두 겹 식별자** — `users/<사람>/flows/<흐름>/`, 카드는 `.wip-jmp.pay.` | "id별"로 쓰인 규칙 전부(정합성 8항목·커밋 접두사·방 경로·점유 접미사)가 **"사람별 × 흐름별"로 갈라진다.** devflow에서 가장 섬세한 영역(복구·정합성)이 두 배가 된다. 모드 통합(D6)이 같은 문제를 **순감**으로 푼다 |
| X4 | **팀 기능(multi)을 1인 동시성 해법으로 전용** | 범주 혼동이다. 팀은 사람을 구분하는 것이고 1인 동시성은 다른 문제다. D6이 모드를 없애면서 이 구분 자체가 사라진다 |
| X5 | **도메인 노트 새 계층** — 능력별 작업 노트 파일을 새로 만든다 | 중계 노트는 **이미 4층으로 존재한다**(2절). 코드 · 미수확 카드 · 능력 문서 · Layer 0. 세 번째 집을 만드는 것이고, v0.11.0이 기각한 "1,100~1,700줄 중계 노트 2차 핸드오프 층"과 경계가 맞닿는다 |
| X6 | **미수확 카드의 진행 로그 전문 읽기** | **실현 불가.** 로그 하나가 수백 줄이고 첫 폐쇄 전에는 그 능력의 카드 전부가 대상이라 카드마다 수천 줄. 승계 줄(`carry:`)이 카드당 1~3줄로 대체 |
| X7 | **최근 N장만 읽기** (N=3 등) | N이 판단어이자 임의 숫자다. 근거가 없고, 이미 능력 문서로 축약된 것을 다시 읽어 중복이 생긴다. `Covered cards` 여집합은 **기계적 경계**이고 이미 계산되고 있다 |
| X8 | **verify의 "devflow 밖 미커밋" 게이트를 능력 범위로 좁히기** | 공유 코드를 누가 고치는 중일 때 **거짓 통과**가 난다. 안전 장치를 편의로 바꾸는 거래다. 6.8 |
| X9 | **세션·날짜 단위 작업 묶음 파일** | 전부 닫는 기점을 요구하고, 닫는 기점은 조용히 죽는 세션에서 반드시 샌다. 카드가 이미 "완료 신호 하나 = 커밋 하나"로 그 역할을 한다 |
| X10 | **능력마다 별도 HANDOFF** | 기존 기각 유지(능력 수에 O(n)). M7은 반대 방향 — HANDOFF를 **줄인다** |
| X11 | **devflow가 워크트리를 만들거나 관리** | design.md의 기각("핵심 편집이 잦아 병합 비용 > 병렬 이득")은 **뒤집지 않는다.** 이번 설계는 devflow가 워크트리를 만드는 것이 아니라, 사용자가 **이미 만든** 워크트리와 호환될 뿐이다 |

## 13. 다음 세션에게 — 이 문서 하나로 시작할 수 있게

이 문서는 앞선 대화를 참조하지 않고 읽을 수 있게 썼다. `docs/handoff-usage-flow_ko.md`는 문제
제기 원본이고, **판정과 설계는 이 문서가 정본**이다. 두 문서가 다르면 이 문서가 이긴다
(핸드오프의 방향 2는 여기서 기각됐다 — X1).

### 13.1 절대 반복하지 말 것 — 이 대화에서 실제로 저지른 것

| 실수 | 무엇이 벌어졌나 | 어떻게 막나 |
|---|---|---|
| **좌표 스윕 없이 제출** | 시나리오 워크만 하고 "내가 바꾼 필드를 언급하는 다른 모든 문장"을 세지 않아, 가벼운 검토에서 결함 둘(F8·F9)이 즉시 나왔다. 기획의 완성도가 무너진 것으로 읽힌다 | 만지는 **모든 식별자·필드·규칙**에 대해 배포물 전체에서 언급 문장을 기계적으로 열거한 뒤 제출한다. 실측: HANDOFF = 5파일 15곳, 모드 분기 = 8파일 59줄 |
| **쓰기만 하고 걷지 않음** | 설계를 다 쓴 뒤 워크플로를 끝까지 걸었더니 6건이 더 나왔다(W1~W6). 걷지 않았으면 구현 중에 터졌을 것 | 설계를 쓴 **다음에** 업그레이드 → 동시 터미널 → 유지보수 → 폐쇄를 한 번 끝까지 건다 |
| **결정 사항을 서술형으로 나열** | "무엇을 할 것이다"로 적어 소유자가 답할 수 없었다 | 판단이 필요하면 **선택지**로 낸다. 모든 선택지에 프리뷰, **권장 표시와 근거**를 붙인다 |
| **질문을 함축적으로 씀** | "HANDOFF 두 절" 같은 축약으로 이해가 막혔다 | 배경 → 지금 무엇이 문제 → 이 선택이 무엇을 가르는지까지 풀어 쓴다 |
| **안전 장치를 하자처럼 표현** | "못하는 것 하나"라고 써서 불안 요소로 읽혔다. 실제로는 오늘도 같은 동작이다 | 결함과 안전 장치를 구분해 쓰고, 발화 빈도와 필요한 조치를 함께 적는다 |
| **소유자 아이디어를 무조건 채택하거나 무조건 기각** | 둘 다 안 된다 | 실현 가능성을 판단해 근거와 함께 채택하거나 대안을 낸다. 기존 구조도 실패한 설계면 뒤집되 기록된 기각 사유를 먼저 반증한다 |

### 13.2 설계의 순서 — 이것이 이번 교훈의 핵심

> **동선을 먼저 쓰고 계약을 나중에 쓴다.** 텍스트를 공격하는 검증은 언제나 텍스트를 늘리는 쪽으로만
> 민다. 그 루프에는 "이게 사용자에게 존재해야 하는가"를 묻는 지점이 없다. 5절의 U×C 격자가 그 지점이다.

캠페인의 첫 렌즈는 **동선 렌즈**다. 격자를 그대로 주고 각 칸에서 `동작/마찰/불가`를 판정하되,
마찰·불가에는 **구체적 대사와 그 다음에 실제로 일어나는 일**을 쓰게 한다. "규칙이 없다"가 아니라
"사용자가 X라고 말하면 AI는 Y를 한다"로. 매 패스에 **"소견 0건은 유효한 결과"**를 명시한다.
문자 실행·반증·과잉 하네스 감사는 그 다음이다.

### 13.3 시작 지점

1. `AGENTS.md`의 게이트를 읽는다(_ko 먼저, 용어표, 구조 동형성, 한글 0, CHANGELOG).
2. `docs/design.md`의 결정표와 기각 계보를 읽는다. **이 기획이 뒤집는 것은 없다** — 방향 2는
   핸드오프의 제안이었을 뿐 design.md의 결정이 아니었다.
3. 이 문서의 3절(기계 열)과 8절(배치)을 실행 계획으로 삼는다.
4. **배치 1(모드 통합)부터.** 의미 변화가 없고 순감이라 가장 안전하며, 나머지 배치의 예산을 낸다.
5. 배치마다 좌표 스윕 → 텍스트 → 동선 렌즈 → 문자 실행 → 테스트 핀 → 다음 배치.
