# v0.9.21 Redesign Validation Report — Shared Contract for Claude and Codex

## 1. Comparison baseline and scope

- Previous baseline: v0.9.20 at commit `94ed4d99670f71b981bc439f93b319505fc36725`.
- New runtime baseline: v0.9.21 commit `8c190173b399a3cb2e1aa922c372158ec1c95282`.
  This report, the capability-knowledge proposal, and their invariant checks are a later
  non-runtime documentation-and-validation commit.
- Goal: give AI ample product, structural, and verification direction without deciding
  the implementation method for it. The same disk state must lead to the same next stage
  across session interruption, brownfield work, multiple workers, Claude, and Codex.
- Non-goals: having devflow create or assign Git worktrees, backfilling existing code as
  task cards, or forcing domain-knowledge documents on every project.
- Validation method: devflow was not invoked to validate itself. The repository source,
  previous commit, and three reference projects were compared through independent
  refutation, literal execution, over-harness audit, and a coordinate sweep.

## 2. Executive conclusion

The core philosophy of v0.9.20 was sound. Product identity, a tree opened one layer at a
time, task cards, completion signals, and separated verification roles form a foundation
that can serve long-running projects as well as small MVPs. The gap was not the philosophy
but the disk-state contract. When a session ended during approval, adoption classification,
failure routing, product verification, capability closing, or event handling, another AI
could interpret the same state differently.

v0.9.21 specifies **the inputs, landing points, and resume conditions of state
transitions** instead of prescribing implementation methods. Claude and Codex still choose
how to code, but they are not free to repeat or lose an already-recorded fact. Task-card
and verification predicates are each defined once in companions with different consumer
sets, while the hook no longer interprets state and emits only two lines routing to resume. Prompt size remains materially larger after that
subtraction. There is no evidence that the structure has collapsed into patchwork, but
there is also no evidence that this version is the size optimum. Adopt the correctness
improvement; if real use reveals attention dilution, reduce further without reopening a
closed failure path.

## 4. Contract changes from before to after

| Axis | v0.9.20 and earlier operation | v0.9.21 | Why it changed |
|---|---|---|---|

| Execution proposal | Approval existed in conversation but left no trace after a session | Card Approval, parallel, and Review fields land in a planning commit | Let the next AI distinguish before from after approval |
| Dependencies and shared predicates | “Dependency-free” language conflicted with real completed dependencies, and stages could interpret approval, revisions, and event keys differently | A card is ready when each listed number resolves to exactly one `.done.` card. `state-predicates` alone owns Depends and Approval; `verification-predicates` alone owns revisions and event keys; each reaches only its consumers | Prevent permanent waiting after a prerequisite, guessed legacy status, and partial definitions across platforms |
| Task boundary | Depended on Git's rename display and message interpretation | The final task commit contains the claim and progress log. | Remote evidence | Recovery between checkpoint and journal was incomplete | evidence-wait, evidence-finalizing, and failure transitions each have disk predicates and commit boundaries | Prevent duplicate CI judgment and a second final task commit |
| Verification freshness | Product and capability passes could be reused after an input changed | Bind Product, Verification, Code, and Capability revisions. | Failure and finding source | Second-resolution timestamp locator | Never-reused positive source id per verify.md section; findings use event id plus number | Resolve several same-second failures and findings to one exact source each |
| Product verification | Deleting request lines erased run ownership and the brownfield trigger | A requested→running→result→reported single-flight state, with every transition committed | Prevent request deletion, new requests, and adoption-complete state from being confused after interruption |
| Audit and Retrospective | pending existed, but zero findings, user decisions, and document routes could remain uncommitted | Commit pending, result, and decision states. Before output, preserve base, final result, and ordered write/move/delete operations in `routing prepared`; require the current checkout to be an exact prefix of those operations. Complete unresolved scope nonblockingly and leave dirty Audits unselected | Prevent a once-only event from disappearing, repeating, waiting forever, or guessing lost payload after interruption |
| Multiple checkouts | Assumed local HEAD was shared state | Routing, integrity, and initial claims use the integration tip. Before a task boundary, integrate its final/checkpoint commit with arch's merge method | Do not miss another worktree's state or expose `.done.` on integration without its code |
| Platform connection | Codex fallback and a global hook copied only parts of the shared procedure | Claude and Codex consume the same English skill and role contracts. | Long-lived knowledge | glossary, journal, and existing handoffs were produced without complete consumer paths | Explicitly consume existing glossary, journal, and direct Depends. | Git and verification interruption | An open rebase or merge, unfinished gates after verifier success, and intermediate capability closure could be interpreted as ordinary work | All 8 entry skills return an open Git operation first when inside a Git work tree. ## 5. Objective judgment of “rich direction, light harness”

The earlier version was not wholly light-harness. Status suffixes, one-layer splitting,
commit discipline, and role separation are strong operating constraints. Their force was
applied to memory and responsibility boundaries rather than implementation methods. The
redesign preserves that distinction.

| Kind | What the new version fixes | What remains for AI |
|---|---|---|
| Direction | Product identity, Destination, Trust boundary, success criteria, and verify channel | The concrete implementation and exploration order |
| Durable state | Card status, source id, revision, marker, and commit boundary | Tools and coding method inside that state |
| Quality roles | Inputs and judgment authority of reviewer, verifier, auditor, and retrospector | Each role's reasoning and findings |
| Parallel safety | Claims and shared integration state | Distribution of approved independent work |

The absolute amount of text and state harness is therefore stronger, but no additional
method prescription takes away implementation reasoning. Duplicates with no surviving
failure path were removed: repeated integrity calls in split and resume, the capability-
folder rename disjunct, work's ordinary-task recovery, commit-subject, and repository-wide
search prescriptions, repeated readiness predicates in split/work/resume, and resume procedure
duplicated by the hook.

## 7. Claude and Codex compatibility

- The canonical deployed meaning is the English `SKILL.md` and role contracts consumed
  by both platforms.
- Claude discovers plugin skills and `hooks/hooks.json` through its native mechanism.
- Codex uses skills and hooks from `.codex-plugin/plugin.json`. The local installer
  registers this repository as a marketplace and places each skill's canon and required
  role contract in 8 slash prompts. Task-card predicates reach split, work, verify, and
  resume; verification predicates reach only verify and resume.
- The Codex fallback AGENTS points to shared resume. SessionStart emits two activation
  lines naming state presence and resume. Neither owns a stage table or injects file content.
- There is no model-specific semantic policy for matching reasoning style. Only role
  inputs, disk state, and completion conditions are fixed.
- Raw Git revisions use a POSIX native pipe and a Windows `cmd /d /s /c` binary pipe so
  both deliver the same bytes. The PowerShell object pipeline is forbidden.

This compatibility does not guarantee that both models produce code of equal quality. It
is a transport contract preventing them from deriving different stages from the same
project state.

## 9. Validation of the JGNote-style capability-knowledge combination

The need for the combination is confirmed, but merging task units into domain units is
rejected. A team must be able to claim different cards inside the same domain
concurrently, and tree, cards, and users must continue to own execution order and
completion state.

The recommended candidate is **the last successfully refreshed passing capability baseline +
current cards outside Covered cards**. The baseline compresses user behavior, UI/API/data
contracts, current code entrypoints, reproduced traps, and executable regression, and records
the numbers it already summarizes in Covered cards. It excludes chronology, assignee,
progress, and next work. work does not automatically reread every change card; it keeps its
existing read set. At final closure, verify reads the standard refresh set once and adds the
Covered-history extension only when the stored-Covered comparison changed. The full contract
and simulations are in `docs/capability-knowledge-proposal.md`.

A refresh replaces each section from current evidence and deletes unsupported statements;
it never appends a newer account below the old one. When no contract or trap has been
verified, `None.` prevents invention. Without opening card bodies, work compares Covered
cards with the current set of non-`.stale.` `.done.` numbers and treats the whole baseline
as a hypothesis when they differ. While a capability remains open for a long time, current
code and cards are authoritative and compressed refresh waits for the next final closure.

The reason not to split frontend and backend into separate baselines is a verification
boundary, not taste. Devflow has no independent closure for an `arch.md` component, so it
cannot decide which capability settles a shared component. `arch.md`, delegated ADRs, and
code own shared backend or platform knowledge; a vertical capability baseline preserves
only the contract affecting it and exact shared paths. Add no second baseline before a real
independent component-verification boundary exists.

The proposal enrolls through a `<stable-key>.pending.md` marker in a planning commit and
creates or refreshes the baseline only at final capability closure after the verifier and
both gates pass. Freshness uses normalized path/blob-hash pairs for Covered cards and direct
Depends, a capability product digest, a capability code digest, and Verification revision.
A set union hashes a shared dependency path once; a historical-stale dependency retained by
a done card is a freshness input, never narrative evidence. Separating the stored-Covered
comparison digest from the complete current card list's final replacement-Covered digest
prevents a new card or stale replacement from causing permanent lock or immediate mismatch
at the next closure. When Product revision differs but the target row inside the unique
`## Capabilities` section has the same product digest, the change belongs to another capability
row. The baseline does not become immediately stale merely because its own update creates a commit.
An exact candidate template also fixes machine-judged fields and section order so Claude and
Codex can write and read the same file. An immutable product capability number and the whole
current row find the same baseline after a rename. Digests use HEAD blobs, canonical path
order, and binary-safe bytes to exclude Windows/POSIX line-ending drift. Binding-adrs-json
and Existing-records-json are separate: the former enters every future card's `Read first`,
while the latter enters only after it again matches current change scope. External references
remain nonbinding evidence and must be captured in an ADR before they govern work. This is an
interoperability contract required before runtime adoption, not another owner policy.

The adopted integrity check rejects orphan, duplicate, or simultaneous baseline/enrollment
files outside a valid closing prefix, mismatches between an internal key and filename, and
format, JSON, or Covered-order errors. It separates a normal freshness change in the current
row or card state from a malformed file, and neither auto-corrects nor supplies an anomalous
file to split or work.

Adoption extends verify's begin transaction in passing-Record → closing-marker carrying the
payload → baseline-write → enrollment-delete only for that same create order. The marker
preserves the baseline's final bytes and validates an uncommitted prefix separately from an
already-landed begin commit. An empty array is allowed only for ineligibility or a named
baseline-only unresolved input and preserves the marker-head baseline/enrollment pair. A
nonempty array fixes the final baseline bytes and enrollment absence; descendants cannot alter
that post-state. When a multi integration tip advances first, the old begin is not rebased;
revisions, gates, and payload are rebuilt at the new tip. An unresolved baseline-only input
preserves the existing baseline and enrollment for retry at the next closure, while an
unresolved capability code scope remains blocked by the existing Standards gate. The three
existing final-closure operations remain unchanged.

Runtime adoption stops for three owner choices.

1. Enrollment policy: enroll an existing capability in its first maintenance-card plan and
   create at that cycle's final closure; enroll while planning its first implementation layer
   and create at its first final closure; or enroll in a user-selected plan and create at the
   next final closure. All three use the same `.pending.md` as disk evidence.
2. Stable-key owner: a product capability row, first tree number, or filename slug.
3. Retirement preservation: leave the file unchanged and derive retirement from current
   product and tree state, or migrate to a `.retired.` filename.

The recommendations are respectively enrollment by the first maintenance card followed by
that cycle's final closure after the verifier and both gates pass, the exact terminal
` [stable-key=<stable-key>]` field on the product capability row, and preserving the same
file. The first-implementation and explicit-selection policies use the same `.pending.md`
as durable enrollment evidence. These choices change documentation
cost and migration compatibility, so they were not settled on the owner's behalf.

## 10. Remaining limits and risks

- v0.9.21 is not a worktree orchestrator. It only avoids losing shared state when the user
  already uses several checkouts.
- When arch does not map capability code scope exactly, current entrypoints must be traced;
  verification stops as unverified when the boundary is not unique.
- Brownfield never runs whole-product verification automatically. Requiring an explicit
  request avoids declaring an arbitrary portion of existing code fully verified.
- `routing prepared` can duplicate a large file's final content in the working tree for one
  route. The payload is bounded to one route and `devflow/` outputs and is absent from the
  completed commit, but the transient size cost remains.
- The proposed baseline payload leaves its complete final content once in the begin commit's
  journal blob for recovery. It spends Git-history size instead of adding a separate two-state
  protocol and hash.
- Verification revision combines all of arch, code-style, and glossary, so a change to another
  capability also leaves the baseline a hypothesis until the next closure. It avoids a full
  reread on every work invocation, but conservative invalidation still has a cost.
- Product revision likewise makes product-related statements hypotheses in work until the
  target-row digest check at the next final closure, even when only another capability row
  changed. Row isolation reduces cost only at verify time.
- Code revision likewise names the latest commit that changed anything outside devflow
  across the whole project, so unrelated code changes make code-related statements
  hypotheses in work until the next closure. A matching capability code digest avoids a
  full refresh in verify, but the conservative work-time cost remains.
- A capability that does not close for a long time does not refresh its compressed baseline.
  A mismatch between current done numbers and Covered cards prevents false freshness but
  cannot remove the cost of reading current cards and code.
- Without an independent component-verification boundary, shared backend or platform
  knowledge has no separate compressed baseline. It remains in arch, delegated ADRs,
  existing records, and code. If repeated rediscovery becomes observable, design that
  verification boundary before adding another baseline kind.
- Tests validate wording contracts, installation, and the presence of state producers and
  consumers. Only operation of the new version in ADE and RDSF can establish sustained
  model attention on long projects.
- The capability knowledge baseline remains a proposal. Current runtime does not
  automatically produce a JGNote-level compressed domain snapshot.

## Final judgment

This redesign did not replace the original philosophy with another system. It closed the
missing disk contracts required for that philosophy to survive a large service and a long
time horizon. Deterministic resume is more likely on both Claude and Codex. Because the
effective prompt grew substantially, however, v0.9.21 is objectively a **verifiable
baseline that secures state integrity first**, not a finished final form.

JGNote-style expertise is worth combining next. The safest route is not to replace the
tree with domain documents, but to add the most recently refreshed passing baseline after the owner settles
the three lifecycle choices.
