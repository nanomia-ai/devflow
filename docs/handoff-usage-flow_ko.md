## 0. 이 문서의 성격

이 문서 하나만 읽고 시작할 수 있게 쓴다. 앞선 대화를 참조하지 않는다.
배포 산출물이 아니라 작업 문서다. 반영은 정본(`skills/`)과 계보(`docs/design*.md`)에만 한다.

**앞선 핸드오프 `docs/handoff-domain-knowledge_ko.md`는 종결됐다**(v0.11.0~0.11.1로 착지).
이 문서는 그 다음 층위의 문제를 다룬다 — 도메인 지식층은 잘 만들어졌는데 **사람이 그것을
쓰는 동선이 설계된 적이 없다.**

읽는 순서: 1절(진단) → 2절(실패의 역사) → 3절(사용 동선 목록) → 4절(현재 점검)
→ 5절(근본 공백) → 6절(방향 3안) → 7절(작업 범위) → 8절(검증) → 9절(완료 조건)
→ 10절(승계) → 11절(미결).

**바쁘면 1 · 2.2 · 3.1 · 5 · 6 · 7절만 읽어도 판단할 수 있다.**

## 1. 한 문장 진단

> **devflow는 프로젝트의 상태를 완벽히 모델링하고 사용자의 상태를 전혀 모델링하지 않는다.**
> 트리는 *무엇이 가능한가*를 안다. *지금 무엇을 하려는가*는 어디에도 없다.

세션이 끊길 때 실제로 잃는 것은 트리가 아니다 — 트리는 디스크에 있다. 잃는 것은 **의도**다.
그것을 나르라고 만든 `HANDOFF.md`가 나르는 것은 `## Next single step` 즉 **프로젝트의 다음 한
걸음**이지 **그 사람의 초점**이 아니다.

### 1.1 기계 수준 증거 (전부 v0.11.1 원문에서 확인)

| # | 사실 | 위치 |
|---|---|---|
| E1 | `work`은 "준비된 **다음** 대기 카드를 점유한다"고만 말한다. A·B·C에 준비된 카드가 있을 때 "다음"이 무엇인지 **정의가 없다** | `skills/work/SKILL.md:80-82` |
| E2 | `HANDOFF`의 초점 필드는 `## Next single step`이고 주석이 `<!-- one tree path -->`다 — **단일 작업열을 구조적으로 가정** | `skills/work/SKILL.md:341` |
| E3 | resume의 보고는 `"The next step is <one step>. Proceed?"` — 여러 능력이 열려 있어도 **선택지를 제시하지 않는다** | `skills/resume/SKILL.md:103-107` |
| E4 | 사용자 의도가 라우팅에 들어가는 지점은 도메인 진입 두 절뿐이고, 둘 다 `"파일이나 상태를 바꾸지 않는다"` | `skills/resume/SKILL.md:16-57` |
| E5 | `conversation`이라는 단어는 resume 전체에 **한 번** 나오며 `브라운필드: 예 + 트리 없음` 예외 안이다. 그린필드+트리에는 같은 절이 **없다** | `skills/resume/SKILL.md:261` |
| E6 | **필요한 인식 기계는 이미 있다** — "완전한 능력 이름 하나 또는 독립된 번호 토큰, 정수 비교; 0개면 후보 제시하고 묻고, 2개 이상이면 일치 후보만 묻는다". 그런데 **읽기 전용 설명기에만 연결돼 있다** | `skills/resume/SKILL.md:25-31` |

**E6이 이 문서에서 가장 중요한 사실이다.** 답은 이미 시스템 안에 있고, 출력이 잘못 연결돼 있다.

## 2. 실패의 역사 — 반복하지 말 것

### 2.1 무엇이 반복됐나

| 라운드 | 무엇을 물었나 | 놓친 것 |
|---|---|---|
| v0.9.x (캠페인 15회+) | "이 문장이 자기 정합적이고 문자대로 실행 가능한가" | **"이것이 소유자가 요청한 것을 제공하는가"** — 그래서 MVP 기획 단계의 도메인 문서 공백(P1)이 15회를 통과했다 |
| v0.11.0 기획 | 위에 **의도 적합성 렌즈(I1~I7)** 를 추가했다. 실제로 잡았다 | I1~I7은 **문서층의 의도**였다. **사람의 작업 동선**은 여전히 렌즈가 아니었다. 같은 부류의 누락이 한 층 위에서 반복 |
| v0.11.0 구현 | 계약·복구·형식·양 플랫폼 | 같음 |
| v0.11.1 검증 | 중단·손상 문자 실행 · 과잉 하네스 · 명명 · ko↔en | 전부 **"깨지는가"** 렌즈. **"쓸모 있는가"** 렌즈는 마지막에 한 번 돌았고 **한 번에 7건**이 나왔다 |

### 2.2 방법론적 근인 — 이것이 진짜 교훈이다

> **사용 동선이 설계의 입력이었던 적이 한 번도 없다. 항상 검증의 사후 점검이었다.**

계약을 먼저 설계하고, 그 계약을 확인하려고 시나리오를 걸었다. 순서가 거꾸로다. 동선을 먼저
쓰고 거기서 필요한 능력을 도출한 다음 계약을 설계했어야 한다.

여기에 **자기강화 메커니즘**이 붙는다. 검증을 "텍스트를 공격하는" 방식으로 하면 **모든 소견이
텍스트를 늘리는 방향으로만 밀어붙인다.** 그 루프 안에는 *"이게 사용자에게 존재해야 하는가"*를
묻는 지점이 없다. 그래서 시스템은 **내부 정합성으로 최적화되며 사용성에서 멀어진다.**
v0.11.1이 그 증상이다 — 중단·손상 경로는 극도로 정교한데, 사용자가 "오늘은 A를 하고 싶다"고
말할 방법이 없다.

### 2.3 교정 — 다음 세션의 작업 순서

1. **동선을 먼저 확정한다**(3절). 계약 문장을 한 글자도 쓰지 않는다.
2. 동선마다 **AI가 그 지점에서 할 수 있어야 하는 것**을 적는다(3.2).
3. 그 요구에서 **필요한 최소 기계**를 도출한다. 기존 기계로 되는 것은 새로 만들지 않는다.
4. 그 다음에 계약을 쓴다.
5. 검증 캠페인의 **첫 번째 렌즈는 동선 렌즈**다. 문자 실행·반증은 그 다음이다.

### 2.4 잘 된 것 — 버리지 말 것

실패만 기록하면 다음 세션이 좋은 것까지 버린다. 아래는 캠페인을 통과해 얻은 자산이다.

- **캠페인 규율**: 설계 확정 → 독립 반증 → 적용 → 재감사. 매 라운드 실결함을 냈다.
- **테스트 핀**: `scripts/repository-invariants.test.js`가 정본의 핵심 속성 문구를 직접 고정한다.
  v0.10의 약점(제안서를 고정하고 정본은 안 지킴)이 v0.11에서 해소됐다. **이 자산을 유지하고,
  이번에 만드는 규칙에도 핀을 붙여라.**
- **두 구역 계약**(설계/검증)과 **HEAD 기준 복구**, **번호 키잉 자동 도달**, **유계 투영**
  (work·reviewer·retrospector가 정본 전체를 읽지 않는 것).
- **읽기 비용 O(1)**: 카드 하나가 능력 문서 하나만 읽는다. **이번 설계가 이것을 깨면 안 된다.**

## 3. 사용 동선 목록 — 이번 설계의 입력

**이 절이 이 문서의 핵심 산출물이다.** 다음 세션은 여기서 출발해야 하고, 여기 없는 동선을
발견하면 먼저 이 목록에 추가한 뒤 설계한다.

### 3.1 사용자 동선 (U)

| # | 동선 | 사용자가 하는 말/행동 | 기대하는 결과 |
|---|---|---|---|
| **U1** | 신규 개시 | product → arch → (design) → split | 골조와 첫 능력의 카드가 생긴다 |
| **U2** | **같은 능력 이어하기** (컨텍스트 포화 후 새 세션) | "이어서 하자" | 직전에 하던 그 자리로 정확히 돌아간다 |
| **U3** | **다른 능력으로 전환** ← 소유자가 지목한 핵심 | "오늘은 A 작업할게" | A의 다음 할 일로 초점이 옮겨지고, **다음 세션에도 유지된다** |
| **U4** | **여러 능력이 동시에 열림** | (아무 말 없이) "이어서" | 시스템이 임의로 고르지 않고 **선택지를 제시한다** |
| **U5** | 특정 기능 고장 신고 | "고객 관리 필터가 이상해" | 그 능력에 유지보수 카드가 생기고 도메인 지식이 카드 작성에 쓰인다 |
| **U6** | 도메인 이해 후 착수 | "고객 관리 설명해줘" → "좋아, 그럼 여기 손보자" | 설명 다음에 **그 자리에서** 작업으로 이어진다 |
| **U7** | 기록된 진술 교정 | "이 불변식 이제 틀렸어" | 어디를 고쳐야 하는지 안내받고 실제로 고쳐진다 |
| **U8** | 능력 추가 | "결제 기능 추가할래" | product 재실행 → 문서·트리·번호가 함께 생긴다 |
| **U9** | 능력 은퇴·분할 | "이건 둘로 나눠야겠어" | 번호·소비자·복구가 함께 움직인다 |
| **U10** | 장기 공백 후 복귀 | (6개월 뒤) "어디까지 했지?" | 상태와 **무엇을 믿어도 되는지**를 함께 듣는다 |
| **U11** | 브라운필드 도입 후 첫 유지보수 | adopt → "이 부분 고쳐줘" | 역산된 도메인 지식이 카드에 쓰인다 |
| **U12** | 세션 사망 후 복구 | (새 세션) | 중단 지점이 정확히 복구된다 |
| **U13** | 팀 합류·도메인 인계 (multi) | "나는 B를 맡을게" | 남의 초점과 충돌하지 않고 B로 들어간다 |
| **U14** | 상태만 확인 | "지금 상황 어때?" | 작업을 시작하지 않고 보고만 받는다 |

### 3.2 AI 동선 (A) — 각 지점에서 AI가 할 수 있어야 하는 것

| # | 능력 | 현재 |
|---|---|---|
| **A1** | 지금 무엇을 할지 안다 | 있음 (resume 상태표) |
| **A2** | 그 일이 속한 도메인을 안다 | 있음 (work의 깊이 1 번호 규칙) |
| **A3** | 그 도메인에서 무엇을 믿어도 되는지 안다 | 있음 (세 비교, 가설 강등) |
| **A4** | 모르는 것을 어디서 확인할지 안다 | **부분** — ADR·소비 경로가 권위 목록 밖(7절 R6) |
| **A5** | 배운 것을 어디에 적을지 안다 | **부분** — 골조·외부 함정은 적을 자리가 없다(7절 R4·R5) |
| **A6** | **사용자의 말을 상태 변경으로 바꿀 수 있다** | **없음** ← 근본 공백 |

### 3.3 연속성 축 (C) — 모든 동선에 곱해진다

| # | 축 |
|---|---|
| C1 | 같은 세션 안 |
| C2 | 경계에서 끊고 새 세션 |
| C3 | **작업 중 사망** 후 새 세션 |
| C4 | 장기 공백(수개월) |
| C5 | 다른 기계·다른 사람(multi) |

**설계 규칙: U × C의 모든 칸에서 A1~A6이 성립해야 한다.** 특히 U3 × C2가 소유자가 지목한 칸이다.

## 4. 현재 상태 점검 — 동선별 판정

| # | 판정 | 근거 |
|---|---|---|
| U1 | **동작** | product·arch·split 경로 정상. v0.11.0이 능력 문서를 Layer 0에 붙였다 |
| U2 | **동작** | 점유 카드가 있으면 resume 상태표가 정확히 그 자리로 보낸다 |
| **U3** | **불가** | 초점을 바꿀 수단이 없다. 사용자가 "A 하자"고 해도 상태표는 디스크만 보고 C를 가리킨다(E3·E4) |
| **U4** | **불가** | resume은 `<one step>`만 제시한다. `work`의 "다음 카드"는 정의가 없어 세션·플랫폼마다 다른 카드를 고를 수 있다(E1·E3) |
| **U5** | **불가** | 대화형 요청을 받는 라우팅 행이 없다. 브라운필드에는 있고 그린필드+트리에는 없다(E5). 첫 매칭 행이 **다른 능력의 카드**를 제안한다 |
| **U6** | **끊김** | 설명은 훌륭하다(읽기 전용, 유계, 신선도 동반). 그러나 `"이 답은 파일이나 상태를 바꾸지 않는다"`로 끝나고 **작업으로 이어지는 다리가 없다** |
| **U7** | **막다른 길** | 설계 구역은 arch 소유이고 입력은 Layer 0다. Layer 0가 그대로면 arch는 같은 바이트를 재도출하고 바이트 안정 규칙이 재작성을 금지하며 `"바뀐 파일이 없으면 확인을 묻거나 커밋하지 않는다"`. **오류도 안내도 없이 교정이 폐기된다** |
| U8 | 동작 | product 게이트가 설계 구역 갱신으로 라우팅한다(v0.11.0) |
| U9 | 동작 | 개명·분할·은퇴에 번호·소비자·복구 규칙이 있다 |
| U10 | **부분** | 상태는 보고하지만 **신선도가 재진입 보고에 없다**. 무엇을 믿어도 되는지는 카드를 점유해야 알게 된다 |
| U11 | 동작 | adopt가 역산 설계 구역을 쓴다 |
| U12 | **강함** | v0.11.1이 여기에 집중했다 |
| U13 | **미확인** | multi에서 초점 개념이 없으니 "내가 B를 맡는다"가 표현되지 않는다. 방 단위 HANDOFF가 그릇은 되나 필드가 없다 |
| U14 | 동작 | resume 보고 후 승인 전 정지 |

**14개 중 6개가 불가·끊김·막다른 길이고, 그 6개가 전부 "사용자가 무엇을 하고 싶은지"를
시스템에 말하는 순간에 몰려 있다.**

## 5. 근본 공백 — 하나의 진단

증상 6개(U3·U4·U5·U6·U7·U13)는 서로 다른 결함이 아니다. **같은 공백의 여섯 얼굴이다.**

```
트리          = 무엇이 가능한가            ← 완전히 모델링됨
verify 기록   = 무엇이 확인됐는가          ← 완전히 모델링됨
능력 문서     = 그 도메인이 무엇인가       ← v0.11.0이 완성
HANDOFF       = 세션 사이 휘발 맥락        ← 있으나 "프로젝트의 다음 걸음"만 담음
???           = 지금 이 사람이 무엇을 하려는가   ← 없음
```

이것을 **초점(focus)** 이라고 부르자. 초점은 **진행이 아니다** — 그래서 "진행 상태는 문서가
아니라 파일 트리다"(철학 3)를 어기지 않는다. 트리는 여전히 무엇이 *합법*인지 정한다. 초점은
합법인 것들 중 **무엇이 먼저인지**만 정한다.

### 5.1 곁들여 드러나는 것 — 초점 없는 HANDOFF의 오염

`HANDOFF`는 경계마다 **통째로 덮어쓰는** 휘발 맥락이다. 그 안의 `Just learned`·`Traps`는
직전에 하던 능력의 것이다. **초점이 C에서 A로 바뀌어도 HANDOFF는 C의 맥락을 A의 작업에
그대로 들이민다.** 초점 개념이 없으니 "이건 다른 도메인의 맥락이다"라고 말할 방법이 없다.

## 6. 설계 방향 — 3안과 권고

### 방향 1 · 선택지 제시 (상태 추가 0)

여러 능력에 준비된 일이 있을 때 resume이 **하나를 고르지 않고 목록을 제시하고 묻는다.**
`work`의 "다음 카드"에는 정본 카드 번호 순서를 준다.

- **장점**: 새 상태 0. 기존 승인 게이트를 그대로 쓴다. `work`의 판단어를 없앤다(그 자체로 결함 수리).
- **한계**: 세션마다 다시 답해야 한다. **U3 × C2를 풀지 못한다** — 사용자가 잃는 것이 바로
  "지난번에 A를 하기로 했다"는 사실인데 그것이 어디에도 남지 않는다.
- **판정**: 필요하지만 충분하지 않다. **무조건 채택하되 단독으로는 부족.**

### 방향 2 · 초점을 durable 상태로 (권고)

`HANDOFF`에 **한 줄**을 더한다: 초점 = 능력 번호 하나 또는 `none`.

- **거처가 HANDOFF인 이유**: 이미 세션 간 휘발 맥락의 집이고, 이미 경계 커밋에 동승하며,
  이미 multi에서 **방 단위**다 — 초점은 사람마다 다르므로 이것이 정확히 맞는 그릇이다.
  journal은 틀리다(공유 상태이고 카드 횡단 결정이 아니다). arch.md도 틀리다(설정이 아니다).
- **쓰기 시점**: 사용자가 말하면 **그 세션에서 즉시 라우팅에 반영**되고, **다음 경계 커밋에
  durable하게 착지**한다. 새 커밋 클래스가 필요 없다 — 승인이 세션에서 유효해지고 계획 커밋에
  착지하는 것과 같은 형태다.
- **작동**: **순서만 정하고 막지 않는다.** 초점의 일이 막히거나 소진되면 보고하고 나머지를 제시한다.
- **낡음**: 초점이 은퇴·폐쇄된 능력을 가리키면 보고하고 묻는다.
- **닫는 것**: U3 · U4 · U13 · `work`의 정의 없는 "다음" · HANDOFF 오염(초점이 바뀌면 이전
  휘발 맥락은 넘기지 않는다, 단 `열린 결정`은 기존 규칙대로 승계).

### 방향 3 · 의도를 입구에서 상태로 (권고, 방향 2와 함께)

**이미 있는 인식 규칙(E6)을 라우팅의 입력으로 승격한다.**

resume의 도메인 진입은 사용자 메시지에서 능력을 **기계적으로** 알아낸다 — 완전한 이름 또는
독립 번호 토큰, 정수 비교, 0개면 후보 제시하고 묻고 2개 이상이면 일치 후보만 묻는다. 이
기계를 읽기 전용 설명기에서 떼어 **초점 설정과 유지보수 라우팅에도 연결**한다.

- 인식된 능력 → 초점 설정.
- 변경 요청이면 → 기존 `maintenance routing pending` 줄로 착지(이미 있는 정본 형식).
- 인식 실패는 이미 정의된 안전한 퇴로가 있다(후보 제시하고 묻기).
- **닫는 것**: U5 · U6(설명 → 착수 다리) · 브라운필드/그린필드 비대칭(E5).

### 권고

> **방향 1 + 2 + 3을 함께 채택한다.** 셋은 경쟁 안이 아니라 한 설계의 세 부분이다 —
> 1은 즉시 안전망, 3은 입구, 2는 그것을 세션 너머로 나른다.
> **새로 만드는 기계는 필드 하나와 순서 규칙 하나뿐이고, 인식 기계는 이미 있는 것을 재배선한다.**

### 6.1 검토했으나 권고하지 않는 것

| 안 | 기각 사유 |
|---|---|
| journal에 초점을 둔다 | 공유 상태이고 카드 횡단 결정이 아니다. multi에서 사람마다 달라야 하는데 journal은 하나다 |
| 능력마다 별도 HANDOFF | 능력 수에 O(n). 휘발 맥락은 사람당 하나여야 한다 |
| resume이 초점 파일을 직접 쓴다 | resume은 파일을 쓰지 않는 스킬이다. 이 성질을 깨면 복구 규칙 여럿이 흔들린다 |
| 초점이 다른 능력의 카드를 **금지**한다 | 초점은 순서지 권한이 아니다. 금지하면 긴급 수정이 막히고 새 차단 경로가 생긴다 |
| 트리에 초점 폴더·마커 | 트리는 진행의 정본이다. 의도를 섞으면 한 자리 두 개념 |

### 7.1 구조 작업 (이번 설계의 본체)

| # | 항목 | 산출물 |

| **S2** | 라우팅 순서 규칙 | 초점이 상태표·카드 선택을 **정렬**하는 방식. 합법성은 불변 |
| **S3** | 인식 규칙 재배선 | E6의 기계를 초점 설정·유지보수 라우팅의 입력으로 |

| **S8** | 설명 → 착수 다리 | U6 |

### 7.2 유계 수리 (동선 워크가 찾은 것, 구조와 독립)

| # | 결함 | 수리 | 비용 |
|---|---|---|---|
| **R1** | 재개된 능력이 `신선`이라고 보고한다. 판정 3이 `.done.` 카드만 세므로 `.wip.` 유지보수 카드가 집합을 바꾸지 않는다 → **사용자가 방금 깨졌다고 신고한 「현재 행위」 행이 검증된 사실로 전달된다** | 판정 하나 추가: 폴더가 `.done`이 아니고 `.stale.` 아닌 미완 카드가 있으면 검증 진술은 가설 | 1줄, 카드 집합은 이미 열거됨 |
| **R2** | `split`이 능력 문서를 한 번도 읽지 않는다(`capabilities/` 언급 0회). **"어느 능력의 일인가"를 묻는 유일한 단계가 「경계」 줄을 못 본다** | split이 후보 능력 문서의 고정 첫 4줄만 읽는다(정본이 이미 그 목적으로 4줄을 고정해 뒀다) | 4줄 × 능력 수. **읽기 집합 확장이라 소유자 판정 필요** |
| **R3** | 잘못 매핑된 카드에 **폐기 경로가 없다**. `.stale.`은 상위 문서 진술 변경을 요구하는데 아무것도 안 바뀌었다 | 오매핑 카드의 회수 경로 정의 | 판정 필요 |
| **R4** | 외부 함정이 **정확한 출처 URL을 요구**한다. 문서화되지 않은 API 기벽은 URL이 없다(그래서 함정이다). 비-external로 쓰면 "코드에서 재확인된 것만" 규칙에 탈락 → **양쪽 다 막혀 폐기** | "출처가 없으면 관측한 카드 번호와 재현" 허용 | 1절 |
| **R5** | **골조는 구조적으로 기록 불가능하다.** 폐쇄 의식이 없어 검증 구역이 영구 `None.`인데, split은 공유 계약·교차 능력 경계·검증 창구를 전부 골조로 보낸다 | **D7 재판정** — 골조에 검증 구역 작성자를 주거나, 골조 문서를 자르거나, journal로 라우팅 | **구조 재검토** |
| **R6** | 설계 가설의 재확인처가 `product·arch·glossary`뿐인데 계약 5절은 "설계 진술이 인용하는 ADR"이다. work이 그 ADR을 열어놓고도 재확인 경로가 없어 리뷰가 이의를 반환 → 실패 사다리 | 권위 목록에 "그 구역 구속 ADR의 이미 연 정확 경로" 추가. 소비 경로도 코드 탐색 경계에 포함 | 각 1절 |

### 7.3 이번 범위 밖 (기록만)

- 세션 시작 읽기량 — 카드 400장에서 약 2,400줄이고 지배 항목은 **무유계 트리 목록**이다.
  `docs/design.md`의 **트리 아카이브 규칙**(보류 항목)이 이미 이것을 가리킨다.
- 규칙 정본 크기 — resume·verify가 세션마다 1,078줄. 소비자별 읽기 범위 분할(보류 항목).

### 7.4 명시적 비목표

- 초점을 **권한**으로 만들지 않는다(순서일 뿐).
- 능력마다 별도 HANDOFF·별도 상태 파일을 만들지 않는다.
- 카드 하나가 능력 문서 **하나만** 읽는 O(1)을 깨지 않는다.
- 트리에 의도를 섞지 않는다.
- 유지보수 라우팅에 새 저널 형식을 만들지 않는다(기존 `maintenance routing pending` 재사용).

## 8. 검증 프로토콜 — 이번엔 순서를 바꾼다

### 8.1 렌즈 순서 (2.2의 교정)

```
1단계  동선 확정        3절 목록을 소유자와 확정. 여기 없는 동선을 먼저 추가한다
2단계  설계 도출        동선 → 필요한 능력 → 최소 기계. 계약 문장은 아직 쓰지 않는다
3단계  캠페인 1 (설계)  ①동선 렌즈 ②반증 ③문자 실행 ④뺄셈 — **①이 먼저다**
4단계  보고 → 소유자 승인 → 설계 동결
5단계  텍스트 한 배치   _ko 먼저 → 영문 → 설치기 → 테스트 → 계보·이력
6단계  캠페인 2 (텍스트) 동선 렌즈 + 반증 + 문자 실행 + 기계 검사
7단계  수리 배치 1회 → 변경분 한정 재감사 1회 → 릴리스
```

### 8.2 동선 렌즈의 정의 (새 렌즈 — 이것이 없어서 여기까지 왔다)

에이전트에게 **3절의 U × C 표를 그대로 주고**, 각 칸에서 다음을 판정하게 한다.

- 사용자가 **원하는 것을 말할 수 있는가**
- 시스템이 그 말을 **상태로 바꾸는가**
- AI가 A1~A6를 **그 지점에서** 할 수 있는가
- 세션이 끊겨도 **그 의도가 살아남는가**

판정은 `동작 / 마찰 / 불가`이고, `마찰`·`불가`에는 **구체적 대사와 그 다음에 실제로 일어나는
일**을 적게 한다. "규칙이 없다"가 아니라 "사용자가 X라고 말하면 AI는 Y를 한다"로.

### 8.3 정지 규칙

변경분 한정 재감사 **1회** 이후의 소견은, **텍스트로 재현 가능한 실패 경로를 제시한 것만**
고친다. 판단거리·문구 취향·근거 없는 위험 추정은 `docs/design.md` 관찰 항목으로 보낸다.
이 단계의 모든 수정은 변경한 줄에 한정된 재읽기를 동반한다. 새 캠페인은 열지 않는다.
**소유자만 이 규칙을 해제한다.**

## 11. 소유자 판단이 필요한 것

1. **R2 — split이 능력 문서 첫 4줄을 읽는가.** 읽기 집합 확장이라 원칙이 걸린다. 실패 경로는
   명확하다(잘못된 능력에 카드가 착지하고 회수 경로가 없다). 비용은 4줄 × 능력 수.
2. **R5 — 골조 문서(D7) 재판정.** 이전 판정은 "관찰 조건 미발화, 첫 절단 후보"였다. 동선 워크가
   이것을 **"구조적으로 축적 불가능"** 으로 격상시켰다. 세 갈래: 검증 구역 작성자를 준다 /
   문서를 자른다 / journal로 라우팅한다.
3. **초점의 기본 동작.** 초점이 없을 때 resume이 (a) 항상 묻는가 (b) 하나뿐이면 그냥 진행하고
   여럿일 때만 묻는가. (b)를 권고하나 소유자 취향이 갈릴 수 있다.
4. **R3 — 오매핑 카드 회수.** 새 상태를 만들지 않고 기존 `.stale.` 규칙을 넓힐지, 아니면
   "계획 커밋 되돌리기"로 처리할지.

## 12. 다음 세션에게 — 한 가지만 기억한다면
