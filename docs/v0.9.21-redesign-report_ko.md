# v0.9.21 재설계 검증 리포트 — Claude·Codex 공통 계약

## 1. 대조 기준과 범위

- 이전 기준: commit `94ed4d99670f71b981bc439f93b319505fc36725`의 v0.9.20.
- 새 런타임 기준: commit `8c190173b399a3cb2e1aa922c372158ec1c95282`의 v0.9.21. 이 리포트와
  능력 지식 기획·불변조건 검사는 그 뒤의 비런타임 문서·검증 commit이다.
- 목표: AI에게 제품·구조·검증 방향은 충분히 주되, 구현 방법을 대신 결정하지 않는 범용 개발
  흐름을 만든다. 세션 중단, 브라운필드, 다중 작업, Claude·Codex 차이에서도 같은 디스크 상태가
  같은 다음 단계로 이어져야 한다.
- 비목표: devflow가 Git worktree를 만들거나 배정하는 것, 기존 코드를 소급해 작업 카드로
  기록하는 것, 모든 프로젝트에 도메인 지식 문서를 강제하는 것.
- 검증 방법: devflow 스킬을 실행해 자기 자신을 검증하지 않았다. 저장소 원문·이전 commit·세
  참조 프로젝트를 대조하고, 독립 반증·문자 그대로의 실행·과잉 하네스 감사·변경 좌표 점검을
  수행했다.

## 2. 결론 요약

v0.9.20의 핵심 철학은 유효했다. 제품 정체성, 한 층씩 여는 트리, 작업 카드, 완료 신호,
검증 역할 분리는 작은 MVP뿐 아니라 장기 프로젝트에도 쓸 수 있는 골격이다. 문제는 철학보다
디스크 상태 계약의 빈칸이었다. 승인, 도입 여부, 실패 라우팅, 제품 검증, 능력 폐쇄, 사건 처리
중간에 세션이 끝나면 다음 AI가 같은 상태를 다르게 해석할 수 있었다.

v0.9.21은 구현 방법의 하네스를 늘리기보다 **상태 전환의 입력·착지·재개 조건**을 명시했다.
Claude와 Codex는 코딩 방법을 계속 선택하지만, 이미 일어난 사실을 중복 실행하거나 잃어버릴
자유는 갖지 않는다. 작업 카드 판정과 검증 판정은 소비 범위가 다른 두 companion에 한 번씩
정의하고, 훅은 상태 해석을 버리고 resume 안내 두 줄만 남겼다. 이 감량 뒤에도 프롬프트 크기는 실질적으로 증가했다. 구조가 누더기로
붕괴했다고 판정할 근거는 없지만, 이 버전이 크기 최적점이라는 근거도 없다. 정확성 개선은
채택하고, 실사용에서 주의 분산이 관측되면 실패 경로를 보존하는 후속 감량이 필요하다.

## 4. 이전과 새 계약의 차이

| 축 | v0.9.20과 이전 운용 | v0.9.21 | 변경 이유 |
|---|---|---|---|
| 브라운필드 도입 | 신규 프로젝트와 같은 문서 모양, 대표 흐름 하나에 경계가 과도하게 의존 | `Brownfield`를 디스크에 기록하고 외부 진입점·모듈·기존 문서 후보마다 대표 흐름을 추적. 기존 기능 카드는 소급 생성하지 않음 | 기존 서비스를 새 MVP처럼 다시 분할하는 오판 방지 |
| 실행 제안 | 대화에서 승인됐지만 세션 뒤 흔적이 없음 | 카드의 Approval·parallel·Review가 계획 commit에 착지 | 다음 AI가 승인 전후를 구분 |
| 의존·공유 판정 | “의존 없음” 표현과 실제 완료 의존이 충돌했고 단계마다 승인·revision·사건 key를 다르게 해석할 수 있었음 | 번호 목록의 각 항목이 정확히 하나의 `.done.` 카드를 가리키면 준비됨. `state-predicates`가 의존·승인, `verification-predicates`가 revision·사건 key를 단독 소유하며 필요한 skill에만 전달 | 완료된 선행 카드의 영구 대기, 구형 판정 추측, 플랫폼별 부분 정의 방지 |
| 작업 경계 | Git의 rename 표시와 메시지 해석에 의존 | 최종 작업 commit은 점유 카드·진행 로그를 포함. 점유→완료는 HEAD 경로 부재·동일 번호/이름의 `.done.` 하나·byte 동일성으로 판정 | Windows에서 삭제+미추적으로 보이는 rename도 동일하게 복구 |
| 원격 증거 | checkpoint와 journal 사이 중단 복구가 불완전 | evidence-wait·evidence-finalizing·실패 전환마다 디스크 판별 조건과 commit 경계 존재 | CI 결과를 중복 판정하거나 최종 작업 commit을 두 번 만드는 경로 차단 |
| 검증 신선도 | 제품 판정과 능력 통과가 바뀐 입력에 재사용될 수 있음 | Product·Verification·Code·Capability revision에 결박. Capability는 대상 `.done.` 카드와 외부 직계 의존 카드의 정확한 HEAD 경로만 포함 | 회귀 입력이 바뀐 뒤 옛 통과를 재사용하지 않음 |
| revision byte | JSON 직렬화와 정렬 해석에 의존 | NUL을 포함한 raw `git ls-tree -r -z` byte를 그대로 hash | Unicode·separator·직렬화가 다른 플랫폼의 거짓 stale 방지 |
| 실패와 소견 출처 | 초 단위 timestamp locator | verify.md 절마다 재사용하지 않는 양의 출처 id, 소견은 사건 id+번호 | 같은 초의 여러 실패·소견도 정확히 한 출처를 가리킴 |
| 제품 검증 | 요청 줄을 지우면 실행 소유와 브라운필드 발동 근거가 사라짐 | requested→running→result→reported 단일 실행 상태, 각 전환을 commit | 중단 뒤 요청 삭제·새 요청 혼동과 도입 완료로의 잘못된 이탈 방지 |
| 감리·회고 | pending은 있었지만 영 소견·사용자 결정·문서 route가 미커밋으로 남을 수 있음 | pending·result·decision 상태 commit. 출력 전에 `라우팅 준비`에 base·최종 결과·순서가 있는 write/move/delete 연산을 보존하고 현재 checkout이 그 연산의 정확한 접두 상태인지 검사. 범위 미해결은 비차단 완료하고 dirty 감리는 선택하지 않음 | 한 번뿐인 사건의 누락·중복·영구 대기와 중단 뒤 payload 추측 방지 |
| 다중 checkout | 로컬 HEAD가 공유 상태라고 가정 | 라우팅·정합성·최초 점유는 integration tip을 사용. 작업 경계 전 final/checkpoint commit을 arch merge 방식으로 통합 | 다른 branch/worktree의 marker·점유를 놓치거나 코드 없이 `.done.`만 통합되는 상태 방지 |
| 플랫폼 연결 | Codex 폴백과 전역 hook이 공통 절차를 일부 복제 | Claude·Codex 모두 같은 영어 스킬·역할 계약을 소비. 어댑터와 hook은 파일 내용·단계를 판정하지 않고 공통 resume으로만 안내 | 플랫폼별 의미 drift와 stale 로컬 주입 제거 |
| 장기 지식 | glossary·journal·기존 핸드오프가 생산돼도 소비 경로가 불완전 | 존재하는 glossary·journal·직접 Depends를 명시 소비. 브라운필드는 정확한 기존 기록 경로만 색인 | 무유계 통독 없이 다음 카드에 유효 지식 전달 |
| Git·검증 중단 | 열린 rebase·merge와 verifier 통과 뒤의 미완 게이트, 능력 폐쇄 중간 상태를 일반 작업처럼 해석할 수 있었음 | 8개 진입 skill이 Git 작업 트리에서 열린 Git 작업을 먼저 돌려보냄. 현재 pass에 두 gate 결과를 요구하고, 능력 폐쇄는 `verify.md` → `journal.md` → 폴더 rename의 복구 가능한 접두만 허용 | 충돌 해소를 덮어쓰거나 gate를 건너뛰고, 폐쇄 중 revision 입력이 바뀌는 경로 차단. 비-Git 프로젝트에는 관문을 적용하지 않음 |

## 5. “방향은 많게, 하네스는 적게”에 대한 객관적 판정

이전 버전도 완전히 저하네스는 아니었다. 상태 접미사, 한 층 분할, 커밋 규율, 역할 분리 자체가
강한 운영 하네스다. 다만 그 강도는 구현 방법이 아니라 기억과 책임 경계에 쓰였다. 이번 개편도
같은 구분을 유지한다.

| 종류 | 새 버전이 고정하는 것 | AI에게 남기는 것 |
|---|---|---|
| 방향 | 제품 정체성·목적지·신뢰 경계·성공 판정·검증 창구 | 문제를 푸는 구체적 구현과 탐색 순서 |
| 영속 상태 | 카드 상태·출처 id·revision·마커·commit 경계 | 상태 안에서 사용할 도구와 코드 작성법 |
| 품질 역할 | reviewer·verifier·auditor·retrospector의 입력과 판단 권한 | 각 역할의 실제 추론과 소견 |
| 병렬 안전 | 점유권과 integration 공유 상태 | 승인된 독립 작업의 배분 방식 |

따라서 절대 문장량과 상태 하네스는 강해졌지만, 구현 사고의 자유를 빼앗는 방법 처방은 늘리지
않았다. 명확한 실패 경로 없이 중복된 규칙은 제거했다: split·resume의 중복 정합성 호출,
능력 폴더 rename 보조 판정, work의 일반 작업 복구 전문·commit 제목 재정의·저장소 전체 탐색
처방, split·work·resume의 준비 판정 중복, 훅의 resume 절차 복제가 그 대상이다.

## 6. 문자 그대로의 시나리오 결과

| 시나리오 | 디스크에서 읽는 것 | 예상 결과 |
|---|---|---|
| 신규 MVP를 순서대로 구현 | product 능력·대기 파일·한 층 marker·카드 승인 | 기존 장점 유지. 전부 선분할하지 않고 다음 층만 연다 |
| 화면을 보며 같은 능력을 반복 개선 | 닫힌 능력 재개봉·새 유지보수 카드·전체 회귀 | 변화량은 카드가 갖고 능력 전체 신호를 다시 실행한다 |
| JGNote 같은 브라운필드 도입 | Brownfield yes·능력별 Existing records 경로 | 기존 기능을 `.done.` 카드로 위조하지 않고 요청한 변화만 추적한다 |
| 같은 능력에서 두 사용자가 다른 카드를 수행 | 각 `.wip-<id>.`·integration의 계획 상태 | 작업 단위와 점유를 유지하며 같은 도메인도 병렬 가능하다 |
| 솔로 짧은 작업이 최종 commit 직후 중단 | 최종 제목·commit 속 점유 카드와 로그 | 최종 commit을 다시 만들지 않고 환류·`.done.` 경계만 마친다 |
| Git이 rename 대신 삭제+미추적으로 표시 | HEAD 점유 파일과 현재 `.done.` 파일 byte | 상태 label과 무관하게 같은 미완 경계로 판정한다 |
| 열린 rebase·merge 상태에서 어떤 skill을 직접 호출 | Git 작업 상태와 conflict index | 정상 라우팅·실행·변경 전에 계속/중단을 묻고 자동 중단하지 않는다 |
| 같은 초에 실패 세 건 발생 | 실패 이력 출처 id 1·2·3 | 각 수정 카드가 정확한 실패 하나를 출처로 가진다 |
| 제품 verifier 뒤 세션 중단 | committed running 또는 result marker | running이면 다시 실행하고 result면 실행하지 않고 route·사건·보고를 마친다 |
| 능력 판정 파일 작성 중 중단 | 현재 Record 완성 여부와 판정·폐쇄 게이트 결과 | 완성된 비폐쇄 결과는 다시 실행하지 않고 결과 커밋. 부분 작성은 2단계부터 다시 수행. 깨끗한 통과는 7단계 닫기 시작으로 분기 |
| 능력 verifier 통과 직후 게이트 전에 중단 | 현재 pass의 Standards·Provisional pending sentinel | verifier를 다시 부르지 않고 두 게이트를 실행하며, 현재 결과가 모두 있어야 폐쇄한다 |
| 능력 폐쇄 도중 중단 | `verify.md`·`journal.md`·폴더 rename의 현재 접두 | 이미 적용된 정확한 접두를 확인하고 남은 접미 동작만 수행한다 |
| 점유 작업 중 제품 검증이나 사건 요청 | 점유 접미사와 journal 요청 줄 | 요청은 남고 현재 카드의 경계 정리가 먼저 끝난다 |
| 폐쇄 직전에 core 문서로 갈 journal 결정을 발견 | 폐쇄 marker·정확한 대상·기존 revisions | marker를 보존해 대상 소유 skill로 보낸 뒤, 바뀐 revisions로 폐쇄 판정을 처음부터 다시 한다 |
| 소견 route 준비 직후 또는 연산 중 중단 | verify.md의 검증된 `라우팅 준비` payload | base에서 순서대로 write·move·delete를 재현하고 현재 checkout과 일치하는 접두 상태 뒤의 연산만 적용해 최종 결과와 함께 착지시킨다 |
| 감리 code scope가 하나로 결정되지 않음 | pending 사건과 정확한 미해결 이유 | 역할을 부르지 않고 이유를 남긴 완료 상태로 닫으며, 교정 뒤 사용자 요청으로 재실행할 수 있다 |
| 다른 worktree에서 통합 marker 생성 | integration tip의 project·tree·journal·verify | 로컬 점유보다 공유 전환을 먼저 포함한 뒤 다음 단계를 판정한다 |
| 구형 verify 기록 재개 | timestamp 원문과 파일 순서 | 원문을 보존해 출처 id를 부여한 commit 뒤 새 locator를 사용한다 |

## 7. Claude·Codex 호환성

- 배포 의미의 정본은 두 플랫폼이 함께 소비하는 영어 `SKILL.md`와 role contract다.
- Claude는 plugin의 skills와 `hooks/hooks.json`을 native 방식으로 발견한다.
- Codex는 `.codex-plugin/plugin.json`의 skills·hooks를 사용한다. 로컬 설치기는 같은 저장소를
  marketplace로 등록하고 8개 slash prompt에 각 skill의 규칙 정본과 필요한 role contract를
  포함한다. 작업 카드 판정은 split·work·verify·resume, 검증 판정은 verify·resume에만 포함한다.
- Codex 폴백 AGENTS는 공유 resume을 지목하고, SessionStart hook은 상태 존재와 resume 호출만
  알리는 두 줄을 출력한다. 둘 다 단계표나 파일 내용을 주입하지 않는다.
- 모델별 사고 스타일을 맞추는 별도 의미 규칙은 없다. 역할 입력·디스크 상태·완료 조건만
  고정한다.
- raw Git revision은 POSIX native pipe와 Windows의 `cmd /d /s /c` binary pipe가 같은 byte를
  전달하도록 제한한다. PowerShell object pipeline은 금지한다.

이 호환성은 두 모델이 같은 품질의 코드를 낸다는 보장이 아니다. 같은 프로젝트 상태를 다른
단계로 오해하지 않게 하는 운반 계약이다.

## 8. 프롬프트 비용과 누더기 위험

첫 표는 frontmatter를 포함한 영어 원문의 whitespace 단위 단어 수다. “실효”는 진입 skill에
principles와 그 skill이 실제로 읽는 predicate companion만 더한 의미 정본 비용이며 role contract와
설치 wrapper는 제외한다. 둘째 표는 role contract와 wrapper까지 포함한 실제 생성 Codex slash
prompt다. role contract는 깨끗한 위임 컨텍스트에 전달할 계약이지만 평면 prompt 안에도 물리적으로
동봉되므로 두 비용을 구분했다.

| 범위 | v0.9.20 | v0.9.21 | 증가 |
|---|---:|---:|---:|
| 9개 진입 SKILL 파일 | 10,347 | 22,841 | 120.7% |
| 작업 카드 `state-predicates` | 0 | 300 | 신규 |
| `verification-predicates` | 0 | 525 | 신규 |
| 진입 SKILL + 두 predicate | 10,347 | 23,666 | 128.7% |
| resume 실효 | 2,933 | 9,046 | 208.4% |
| split 실효 | 4,067 | 9,373 | 130.5% |
| work 실효 | 3,857 | 8,388 | 117.5% |
| verify 실효 | 3,748 | 11,186 | 198.5% |

실제 생성 prompt 수치는 최종 설치 결과로 다시 계산했다.

| Codex slash prompt | v0.9.20 | v0.9.21 | 증가 |
|---|---:|---:|---:|
| resume | 2,875 | 8,992 | 212.8% |
| split | 3,998 | 9,310 | 132.9% |
| work + reviewer | 3,997 | 8,537 | 113.6% |
| verify + verifier·auditor·retrospector | 4,221 | 11,767 | 178.8% |

합계 23,666개가 한 번에 들어가지는 않지만, 각 핵심 흐름의 실효 입력이 크게 늘어난 것은
명백한 비용이다. 증가분의 대부분은 기존에 없던 브라운필드·승인·중단 복구·실패 사건 상태를
정의한다. 단순 문장 장식으로 설명할 수 있는 증가는 아니다. 반면 이 수치만으로 주의 분산이
없다고 주장할 수도 없다.

이번 변경에서는 실패 경로가 사라지지 않는 중복만 뺐다. 작업 카드와 검증 predicate를 나눠
split·work가 쓰지 않는 revision·사건 525단어를 읽지 않게 했고, 훅의 상태 분류·HANDOFF 주입,
work의 폴더 폐쇄 중복도 삭제했다. 저장소 전체 검색은 점유 카드·직접 Depends·arch의 명시 범위·공유
계약 경로만 확인하는 유계 책임 검색으로 바꿨다. 반면 `라우팅 준비`는 한 번의 route 동안 출력 전체를
일시 중복할 수 있다. 커밋에는 남기지 않고 한 route로 범위를 제한했으며, 승인 payload 유실 뒤
추측하는 실패를 막기 위한 비용이다. 절차 정본을 더 쪼개는 감량은 실사용에서 잘못된 단계 선택,
정본 재독 누락, 지시 상충이 관측될 때 그 실패 경로를 보존하는 범위에서 판단해야 한다.

## 9. 중계노트식 능력 지식 결합 검증

결합의 필요성은 확인됐다. 그러나 작업 단위를 도메인 단위로 합치는 안은 기각한다. 팀은 같은
도메인 안에서도 서로 다른 카드를 동시에 점유할 수 있어야 하고, 실행 순서와 완료 상태는 계속
tree·카드·users가 소유해야 한다.

권고 후보는 **갱신까지 성공한 마지막 검증 능력 기준선 + Covered cards 밖의 현재 카드**다. 기준선은
사용자 동작, UI·API·데이터 계약, 현재 코드 진입점, 재현된 함정, 실행 가능한 회귀를 압축하고 이미
요약한 카드 번호를 Covered cards에 기록한다. 연대기, 담당자, 진행률, 다음 작업은 넣지 않는다.
work는 모든 변화 카드를 자동 통독하지 않고 기존 읽기 집합을 유지한다. verify는 최종 폐쇄에서 기본
갱신 집합을 한 번 읽고, 저장 Covered 비교가 바뀐 때에만 Covered history 확장을 더해 압축한다. 상세
계약과 시뮬레이션은 `docs/capability-knowledge-proposal.md`에 있다.

기준선 갱신은 새 절을 아래에 덧붙이는 방식이 아니라 각 절의 현재 근거를 교체하고 근거가 사라진
문장을 삭제하는 방식이다. 검증된 계약이나 함정이 없으면 `None.`을 써 추측 생성을 막는다. work는
카드 본문을 열지 않고 Covered cards와 현재 `.stale.` 아닌 `.done.` 번호 집합만 비교하며, 다르면
기준선 전체를 가설로 둔다. 능력이 오래 열린 동안에는 코드와 현재 카드가 정본이고 압축 갱신은 다음
최종 폐쇄까지 기다린다.

프론트엔드·백엔드를 별도 기준선으로 나누지 않은 이유는 취향이 아니라 검증 경계다. 현재 devflow에는
`arch.md` 구성요소 단위의 독립 폐쇄가 없어 공유 구성요소를 어느 능력이 확정하는지 정할 수 없다.
공유 백엔드·플랫폼 지식은 `arch.md`·위임 ADR·코드가 소유하고, 수직 능력 기준선은 그 능력에 미치는
계약과 정확한 공유 경로만 보존한다. 독립 구성요소 검증 경계가 실제로 생기기 전에는 제2 기준선을
추가하지 않는다.

제안서는 계획 commit의 `<stable-key>.pending.md` marker로 등록하고, verifier와 두 게이트를 통과한
최종 능력 폐쇄에서만 기준선을 생성·갱신한다. 신선도는 Covered cards와 직접 Depends의 정규화
경로·blob hash 쌍, 능력 product digest, 능력 코드 digest, Verification revision으로 판정한다. 공유
의존 경로는 집합 합집합으로 한 번만 hash하고, 완료 카드에 보존된 역사 stale 의존은 신선도 입력일
뿐 서술 근거로 쓰지 않는다. 저장 Covered 비교 digest와 현재 전체 카드의 최종 교체 Covered digest를
분리해 새 카드나 stale 대체가 영구 교착이나 다음 폐쇄의 즉시 mismatch를 만들지 않는다.
Product revision이 달라도 고유 `## Capabilities` 절 안의 대상 행을 포함한 product digest가 같으면 다른
능력 행의 변경으로 판정한다. 기준선 자체를 갱신한 commit 때문에 즉시 stale이 되는 순환은 만들지 않는다.
Claude·Codex가 같은 파일을 만들고 읽도록 기계 판정 필드와 절 순서도 정확한 후보 템플릿으로
정의했다. 불변 product 능력 번호와 현재 행 전체가 이름 변경 뒤에도 같은 기준선을 찾고, digest는
HEAD blob·정본 경로 순서·binary-safe byte를 써 Windows와 POSIX의 줄 끝 차이를 배제한다.
Binding-adrs-json과 Existing-records-json을 나눠, 전자는 모든 미래 카드의 `읽을 것`에 들어가고
후자는 현재 변경 범위와 다시 맞을 때만 들어간다. 외부 참조는 비구속 근거로 두며 작업을 지배하려면
먼저 ADR에 현재 해석을 남긴다. 이것은 소유자 정책이 아니라 런타임 채택 전에 필요한 상호운용
계약이다.

채택 정합성 점검은 유효한 폐쇄 접두 밖의 고아·중복·동시 기준선/등록 파일, 내부 키와 파일명 불일치,
형식·JSON·Covered 순서 오류를 차단한다. 현재 행이나 카드 상태가 달라진 정상 신선도 변화와 파일
형식 이상을 분리하며, 이상 파일을 자동 보정하거나 split/work의 읽을 것으로 전달하지 않는다.

채택할 때는 verify의 시작 transaction을 통과 기록→payload를 가진 폐쇄 marker→기준선 쓰기→같은
생성에서만 등록 파일 삭제 순서로 확장한다. marker는 기준선 최종 byte를 보존하고 미커밋 접두와 이미
착지한 begin commit을 따로 검증한다. 빈 배열은 연산 자격이 없거나 이름 붙인 기준선 전용 입력이
미해결일 때만 허용하고 marker-head의 기준선·등록 쌍을 그대로 보존한다. 비어 있지 않은 배열은 최종
기준선 byte와 등록 부재를 고정하며 descendant도 이 사후 상태를 바꿀 수 없다. 다중 tip이 먼저
전진하면 기존 begin을 rebase하지 않고 새 tip에서 revision·게이트·payload를 다시 만든다. 기준선 전용
입력이 미해결이면 기존 기준선·등록을 보존하고 다음 폐쇄에서 재시도하지만, 능력 코드 범위 미해결은
기존 Standards 게이트가 계속 폐쇄를 막는다. 기존 최종 폐쇄 세 동작은 그대로 둔다.

런타임 적용은 세 소유자 선택 때문에 멈췄다.

1. 등록 정책: 기존 능력의 첫 유지보수 카드 계획에서 등록해 그 주기의 최종 능력 폐쇄에서 생성, 첫 구현 층 계획에서 등록해 첫 최종 폐쇄에서 생성, 사용자가 선택한 계획에서 등록해 다음 최종 폐쇄에서 생성 중 무엇인가. 세 정책 모두 같은 `.pending.md`를 디스크 근거로 쓴다.
2. 안정 키 소유 위치: product 능력 행, 첫 트리 번호, 파일명 slug 중 무엇인가.
3. 은퇴 보존 방식: 같은 파일을 그대로 두고 현재 product·tree에서 은퇴를 판정, `.retired.` 이름 이관 중 무엇인가.

권고는 각각 첫 유지보수 카드로 등록한 뒤 verifier와 두 게이트를 통과한 그 주기의 최종 능력 폐쇄,
product 능력 행 말미의 정확한 ` [stable-key=<stable-key>]` 필드, 같은 파일 보존이다. 첫 구현 정책과
명시 선택 정책도 같은 `.pending.md`를 디스크 등록 근거로 쓴다. 세 선택은 문서
비용과 이관 호환성을 바꾸므로 사용자 대신 확정하지 않았다.

## 10. 남은 한계와 위험

- v0.9.21은 worktree 오케스트레이터가 아니다. 사용자가 이미 여러 checkout을 쓸 때 공유 상태를
  놓치지 않도록 만들었을 뿐이다.
- 능력 코드 범위가 arch에서 정확히 매핑되지 않으면 현재 진입점 추적이 필요하며, 경계가 하나로
  결정되지 않으면 미검증으로 멈춘다.
- 브라운필드는 제품 전체 검증을 자동 실행하지 않는다. 명시 요청을 요구하는 것은 기존 코드의
  전체 범위를 임의로 검증 완료라고 선언하지 않기 위한 선택이다.
- `라우팅 준비`는 큰 파일의 최종 내용을 한 route 동안 working tree에 중복할 수 있다. payload는
  단일 route와 `devflow/` 출력으로 제한되고 완료 commit에는 남지 않지만, 일시 크기 비용은 남는다.
- 제안된 기준선 payload는 복구를 위해 begin commit의 journal blob에 최종 내용을 한 번 남긴다.
  별도 2상태와 hash를 추가하지 않는 대신 git 이력 크기를 쓰는 선택이다.
- Verification revision은 arch·code-style·glossary 전체를 묶어 다른 능력의 변경도 기준선을 다음
  폐쇄까지 가설로 만든다. work마다 전면 재독하지는 않지만 보수적인 무효화 비용은 남는다.
- Product revision도 다른 능력 행만 바뀌어도 work에서는 다음 최종 폐쇄의 target-row digest 확인까지
  product 관련 문장을 가설로 만든다. 행 격리는 verify 시점에만 비용을 줄인다.
- Code revision도 devflow 밖의 프로젝트 전체에서 가장 최근에 변경된 commit이므로 무관한 코드
  변경이 work의 코드 관련 문장을 다음 폐쇄까지 가설로 만든다. 능력 코드 digest가 같으면 verify는
  전면 갱신을 피하지만 work 시점의 보수적 비용은 남는다.
- 능력이 장기간 닫히지 않으면 압축 기준선도 갱신되지 않는다. 현재 완료 번호와 Covered cards가
  다르면 기준선을 가설로 낮춰 거짓 최신상은 막지만, 카드와 코드를 읽는 비용을 제거하지는 못한다.
- 구성요소별 독립 검증 경계가 없으므로 공유 백엔드·플랫폼 지식을 별도 기준선으로 압축하지 않는다.
  그 지식은 arch·위임 ADR·기존 기록과 코드에 남아야 하며, 이것이 반복 비용으로 관측되면 먼저
  구성요소 검증 경계를 설계해야 한다.
- 테스트는 문구 계약·설치·상태 생산자와 소비자의 존재를 검증한다. 실제 장기 프로젝트에서
  모델 주의력이 유지되는지는 ADE와 RDSF의 새 버전 운용으로만 확인할 수 있다.
- 능력 지식 기준선은 제안일 뿐이다. 현재 runtime은 JGNote 수준의 압축된 도메인 최신상을 자동
  생산하지 않는다.

## 13. Claude 재검토 요청 사항

Claude가 이 변경을 검토할 때 다음 순서가 적합하다.

1. 이전 결과물의 품질로 새 스킬을 추정하지 말고 `94ed4d9`와 이 리포트 포함 commit의 원문을
   직접 대조한다.
2. 각 추가 문장에 실제로 막는 실패 경로가 있는지, 각 삭제 후보를 지워도 그 경로가 다른 정본에
   의해 완전히 닫히는지 밝힌다.
3. requested→running→result→reported, event pending→result→decision→route, claim→done을
   세션 중단 위치마다 문자 그대로 실행한다. write·move·delete 연산의 각 접두 상태, 부분 능력 판정,
   열린 Git 작업, 통과 게이트 sentinel, 능력 폐쇄의 각 접두, 점유 중 요청도 별도 실행한다.
4. Claude 친화성만 보지 말고 Codex의 flat prompt embedding, plugin hook, Windows pipe에서도 같은
   뜻인지 확인한다.
5. 능력 지식 제안의 세 선택을 runtime 명확성·문서 비용·브라운필드 이관 관점에서 독립적으로
   평가한다.

## 최종 판정

이번 개편은 기존 철학을 다른 체계로 교체한 것이 아니라, 그 철학이 큰 서비스와 긴 시간축에서
실제로 유지되도록 비어 있던 디스크 계약을 닫은 것이다. Claude와 Codex 양쪽에서 이전보다
결정적으로 재개할 가능성은 높아졌다. 동시에 실효 프롬프트가 크게 늘었으므로, v0.9.21은
“완성된 최종 형태”가 아니라 **상태 무결성을 먼저 확보한 검증 가능한 기준선**으로 보는 것이
객관적이다.

중계노트식 전문성은 다음 단계로 결합할 가치가 있다. 그러나 tree를 도메인 문서로 대체하지
않고, 소유자가 세 생명주기 선택을 확정한 뒤 마지막으로 갱신에 성공한 검증 기준선으로 추가하는 것이 가장 안전하다.
