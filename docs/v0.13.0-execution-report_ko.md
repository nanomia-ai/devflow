## 0. 이 문서를 읽는 법

**기획서와 이 문서가 다르면 이 문서가 이긴다.** 기획은 실행 전에 쓰였고, 실행이 기획의 판정
하나를 실측으로 반증했다(§3.1). 반증된 문장은 기획서에 그대로 두고 사유를 여기 남긴다 —
AGENTS.md의 "기각 사유를 먼저 반증하라"와 같은 규율이다.

```
읽어야 함
  ★ 이 문서                  실행 결과·판단·남은 것 전부
  CHANGELOG.md 최상단 항목    같은 내용의 영문 요약(배포 채널용)
  docs/design.md             0.13.0 결정 9행 + 기각 9건이 정본으로 들어갔다

읽을 필요 없음 (역사)
  docs/v0.13.0-plan-r2_ko.md            이 실행의 입력. 결정 계보는 design.md가 이제 정본
  docs/v0.13.0-plan_ko.md · *-validation-report_ko.md
```

**배포 산출물이 아니므로 영문 쌍은 없다. CHANGELOG 항목은 남겼다.**

## 3. 기획을 벗어난 판단 — 다음 세션이 인용할 것

### 3.1 ★ 기획의 D3 판별자를 실측이 반증했다 — 정정함

기획 D3: "거절됐을 때 통합 id가 **바뀌었으면** 정상 경쟁, **그대로면** 구조적 막힘."

실전 동시성 실행(워크트리 둘)이 그 규칙이 못 보는 경우를 만들었다:

```
A가 먼저 게시  →  devflow-main 이동
B가 그 뒤에 통합을 읽음  →  B가 기억한 id = 이미 이동한 값
B가 게시  →  거절 (B의 브랜치가 뒤처졌으므로 non-fast-forward)
B가 통합을 다시 읽음  →  id 그대로  →  기획 규칙은 "구조적 막힘"이라 오판
```

id 비교는 "내가 기억한 뒤에 남이 움직였나"만 본다. **뒤처진 채로 시작한 흐름은 잡지 못한다.**
정상 경쟁을 구조적 막힘으로 오판하면 D4의 탈출 경로로 보내 점유가 불필요하게 흩어진다 —
D3이 막으려던 바로 그 실패다.

**정정**: 분류는 조상 검사 하나로 한다.

```
통합 tip이 게시하려는 브랜치의 조상이 아님  →  정상 경쟁 (통합하고 재시도, 세 번까지)
통합 tip이 조상인데도 거부됨               →  구조적 막힘 (정확한 원인과 함께 보고)
```

기억한 id는 여전히 쓴다 — 바뀌었으면 판정의 근거가 낡았으므로 **최신 상태에서 다시
판정**하라는 신호다. 에러 문구로 분류하지 않는다는 D3의 취지는 그대로다.

두 실전 사례가 이 검사로 정확히 갈리는 것을 확인했고,
`scripts/git-state-transitions.test.js`의 `the ancestor test classifies a rejection where the
remembered id cannot`가 두 타이밍을 모두 고정한다. `docs/design.md`의 해당 결정 행도 이
계보를 담고 있다.

### 3.2 문단 3이 다섯 줄인 이유

기획은 「한 작업 폴더」 문단에 여섯 줄을 요구했다. 그중 "커밋은 자기 경로를 지정해서 만든다"는
**커밋 규율의 첫 항목과 같은 규칙**이라 복제가 된다. AGENTS.md는 정본 규칙의 중복을 결함
클래스로 이름 붙였다.

대신 커밋 규율의 그 항목이 **실제로 결함이었다는 것**을 실측이 보여 줬다 — 원문은 "그 커밋의
규칙이 열거한 정확한 경로만 **stage하고**"였는데, 남이 이미 stage해 둔 파일은 그 문장을 지켜도
커밋에 섞인다. 그래서 그 항목을 "이 working tree에 무엇이 stage돼 있든 커밋에는 그 커밋의
규칙이 열거한 정확한 경로만 담긴다"로 고쳤고, 문단 3에서는 뺐다.

**부수 실측**: `git commit -- <경로>`는 그 경로가 아직 tracked가 아니면 실패한다. 새 카드처럼
새 파일이면 `git add <경로>` 뒤 `git commit -- <경로>`가 필요하다 — pathspec이 인덱스의 나머지를
배제하는 장치다. 기획에는 없던 사실이고 fixture로 고정했다.

### 3.3 열린 결정을 journal로 옮긴 것은 기각 계보를 뒤집는 일이었다

기획 문단 3의 "인계장의 열린 결정은 기록장에 둔다"는 v0.7.0의 **기각 항목**이다("한 개념 두 집").
AGENTS.md는 기각을 되살리려면 사유를 먼저 반증하라고 요구한다.

반증: HANDOFF에서 그 절을 **통째로 없애면** 집이 정확히 하나가 되므로 "두 집"이 성립하지 않는다.
그리고 닫는 실패가 구체적이다 — HANDOFF는 통째로 덮어쓰고 한 사람의 두 세션이 방 하나를
공유하므로, 둘 다 덮으면 한쪽의 결정이 흔적 없이 사라진다. journal은 덧붙이기만 하고 이탈
경로에서 이미 기명 열린 결정을 받고 있었다. 이 반증을 `docs/design.md` 결정 행에 기록했다.

파급: `work`의 HANDOFF 템플릿에서 절 하나 삭제, 덮어쓰기 전 재읽기 문단 삭제(이월할 것이
없어졌다), `principles`의 HANDOFF 병합 규칙에서 합집합 절 삭제, 이탈 절차 축소, README 3곳.
**순 감소다.**

### 3.4 좌표 스윕이 찾은 세 칸 — 걷기로는 안 나왔다

1. **증거 대기 카드의 파킹** — 파킹은 해제인데, `evidence-wait` 줄이 지목하는 카드를 해제하면
   그 기록이 점유되지 않은 카드를 가리켜 정합성 13번이 이상으로 잡는다. 0.12.0부터 있던
   결함이다. → "증거 기록이 지목하는 카드는 파킹하지 않는다" 한 문장으로 닫음.
2. **split이 마커를 하나씩 처리** — D6은 여러 부모에 마커를 하나씩 쓰게 했는데, split의 기존
   규칙은 "timestamp가 가장 빠른 것 하나"를 처리한다. 그대로 두면 부모마다 계획 커밋과 승인이
   따로 생겨 D6의 "승인 한 번"이 깨진다. → 같은 `출처-json` 마커는 묶음으로 가져온다.
3. **split 4·5단계가 단수였다** — 1단계만 복수로 고치면 "매핑한 폴더에 카드를 추가한다"가
   단수로 남아 두 번째 단위가 조용히 사라진다. → 둘 다 복수형으로.

## 4. 실제로 돌린 것 — 15번 만에 처음

### 4.1 Git 성질 실측 (기획 0단계)

| 무엇 | 결과 |
|---|---|
| 체크아웃되지 않은 브랜치에 로컬 push | ✅ 원격 없이 성공 |
| non-fast-forward push | ✅ 거부, 브랜치 그대로 |
| 워크트리가 쥔 브랜치에 fast-forward push | ✅ `refusing to update checked out branch`, id 그대로 |
| **`git update-ref <ref> <new> <old>`를 남이 쥔 브랜치에** | ⚠️ **성공한다** — 그 워크트리를 조용히 어긋나게 만든다. push가 더 안전한 원시 연산이라는 근거 |
| 훅을 하위 폴더에서 | ❌ 기존 훅은 조용히 종료 (P-01 재현) |
| Codex 플러그인 설치 위치 | ✅ `~/.codex/plugins/cache/<마켓>/<플러그인>/<버전>/`에 **저장소 전체**. 모델이 그 절대 경로에서 자기 스킬을 읽는 것까지 직접 관측했다. 동반 문서(`../principles/…`)가 같은 캐시에 실존하므로 참조가 풀린다는 것은 **강한 추론**이다 — 프로브가 끝까지 열람을 보여주기 전에 샌드박스 오류로 끊겼다. 소유자의 첫 Codex 실전 세션이 최종 확인 지점 (L3의 전제) |

### 4.2 실전 1 — 한 터미널, 한 사이클

빈 저장소에 Layer 0 → 능력 문서 3개 → 루트 층 → 골조 층 → 카드 하나를 승인·점유·구현·
신호 실행·승계 줄·최종 작업 커밋·경계 정리까지 실제로 돌렸다. 커밋 11개.

확인된 것: 정본 점유→완료 이동의 **바이트 동일성**, `.done` 폴더 투영이 `Depends` 조회와
다음 번호 산출에 필요한 것을 전부 주는 것, 트리 전체 승인 판정이 깨끗한 트리에서 0을 내는 것,
모든 커밋이 자기 경로만 담은 것, 정합성 2·3·6 이상 0.

### 4.3 실전 2 — 한 폴더, 네 세션

| 시나리오 | 결과 |
|---|---|
| 네 카드를 각자 점유, 경로 지정 커밋 4개 | ✅ 인덱스 깨끗, 섞임 0 |
| 네 세션이 동시에 기록장에 덧붙임 | ✅ 20줄 전부 온전, 중복·깨짐 0 |
| 공유 파일의 다른 부분을 각자 부분 수정 | ✅ 둘 다 살아남음 |
| A가 자기 경로만 커밋, B는 다른 파일 stage 중 | ✅ A의 커밋은 `src/a.js` 하나, B의 stage 유지 |

### 4.4 실전 3 — 워크트리 둘, 통합은 무주

A가 폐쇄를 게시 → B가 거절당함 → **조상 검사로 정상 경쟁 판정** → 통합 후 재시도 → 성공.
그 뒤 세 번째 워크트리가 통합을 체크아웃하자 fast-forward push조차 거부 → **조상인데 거부이므로
구조적 막힘**. 두 사례가 §3.1의 정정된 검사로 정확히 갈렸다.
