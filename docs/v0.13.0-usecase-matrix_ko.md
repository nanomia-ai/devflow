# 유즈케이스 전수와 설계 대조 — 사람의 요청 형태 × AI의 진입 지점

작성: 2026-08-13 · 2판(폭 확장) · 기준: v0.13.0 작업 트리 · 분석 문서(배포 산출물 아님)

---

## 0. 이 문서의 렌즈

devflow의 존재 목적: **사람이 AI와 작업하며 쌓는 개발 데이터를 자동으로 축적하고, 그것을
다음 AI가 이해할 수 있게 만드는 것.** 모든 판정은 소유자가 준 세 축으로 한다.

```
① 내구성   이 변수에서 크게 망가지지 않는가 — 특히 데이터가 절대 누락되지 않는가
② 토큰     AI가 진입할 때 지나치게 소모하지 않는가
③ 분별     남겨야 할 기록과 아닌 것을 옳게 가르는가
```

판정 어휘: **정합**(세 축에 든다) · **긴장**(비용이 있으나 설계가 이유를 기록했다) ·
**공백**(설계에 답이 없다). 완벽은 없다 — 추구하는 것은 "어떤 변수에서도 **크게** 망가지지
않는 구조"이고, 크게 망가짐의 정의는 ①의 위반, 그중에서도 조용한 자료 소실이다.

2판 주기: 1판은 워크트리와 팀 축이 각각 한 행으로 얕았다 — 소유자 지적이 맞았고, 폭을
넓히자 실제로 새 공백 셋(§4.1)이 나왔다. 이 문서의 판정 중 [1판]은 유지, [2판]은 확장분이다.

## 3. 대표 교차 워크

1판의 워크(솔로 continue · 수정 리스트 · 사소 변경 · 도메인 질문 · 방치 복귀 · 파킹 · 게시
분류 · 위임·역할 · 복구 기계 · 플랫폼)는 판정 유지 — 상세는 3.1~3.15(1판 본문과 동일 결론:
정합 다수, H5 읽기 비례성·A2 재지불·A3 직접 호출은 긴장, H27×A12는 공백). 아래는 2판
확장분이다.

### 3.16 A4 — 하위 폴더 진입 [2판 신규 공백]

```
사용자가 packages/app에서 에디터를 연다. 훅은 이제 루트를 찾는다(P-01 수리).
그런데 스킬 텍스트에는 "저장소 루트를 해석하라"는 문장이 어디에도 없다.
resume이 cwd 기준으로 devflow/tree를 찾음 → 없음 → "트리 없음" 흐름
  → "이미 있는 구현 동작을 보존해야 합니까?" → 예 → adopt
  → packages/app/devflow/ 가 생긴다 — 저장소에 devflow 루트가 둘
```

**공백 — 크게 망가지는 축에 걸린다.** 데이터 유실은 아니지만 구조가 갈라진다: 이후 세션은
cwd에 따라 서로 다른 devflow를 읽고, 두 트리가 각자 자란다. 인터뷰 게이트(사용자가 질문을
받으므로 눈치챌 기회)가 유일한 방어라 완전 자동 파손은 아니나, "예"를 눌러 버리는 비용이
너무 크다. 훅 수리(P-01)가 이 패턴을 인지하고도 스킬 층으로 일반화하지 않은 내 누락이다.
수리 후보는 정본 한 문장: "모든 devflow 경로는 저장소 루트 기준이다 — 진입 시
`git rev-parse --show-toplevel`로 루트를 해석한다." (§5-P6)

### 3.17 H26·H30 — 좌초된 흐름: 지워진 워크트리·부재자의 머신 [2판 신규 공백]

```
점유 커밋은 통합에 착지한다(구속 결정) — 모두가 본다.
체크포인트는 자기 브랜치에 실린다 — 경계에서야 통합된다.
워크트리를 지우면(또는 팀원이 휴가 가면) 그 브랜치는 남지만 아무도 안 읽는다:
  D2 — 다른 HEAD는 권위가 아니다. 통합만 읽는다.
  W4 질문 — 워크트리 목록이 둘 이상일 때만. prune 뒤엔 하나 → 질문 없음.
다음 세션: 점유는 보이고 진행은 안 보인다 → 점유 시점 로그에서 다시 시작
  → 좌초된 브랜치에 있는 작업을 조용히 다시 구현한다
```

**공백 — 단, 데이터 소실은 아니다.** Git이 브랜치를 보존하므로 잃는 것은 가시성이고,
결과는 이중 구현 + 나중에 브랜치를 발견했을 때의 화해 비용이다. 이것은 D2가 고친 "완료했으나
통합 안 된 작업이 어느 상태에도 안 보인다"의 잔여 케이스다 — 점유(구속 결정)는 착지하므로
카드 상태는 옳지만, **점유 이후의 진행**이 브랜치에 좌초된다. 부재자 인수(H30)에서는 인가된
재배정 절차가 있으나 그 절차 어디에도 "그 사람의 체크포인트를 찾아보라"가 없다 — 미push
WIP가 개인 소유라는 일반 git 관행과 같은 트레이드오프이긴 하다. 수리 후보(관찰 등재 우선):
resume이 내 id 접두 커밋을 가진 비통합 로컬 브랜치를 한 줄로 열거("좌초 후보: flowX —
04.2 체크포인트 2건"). 유계 질의 하나로 가시성만 회복한다. (§5-P7)

### 3.18 H33 — 플러그인 버전 어긋남 [2판 신규 공백]

```
0.12 세션: 공유 상태 = 통합 tip ∪ 각 워크트리 HEAD · 열린 결정은 HANDOFF에
0.13 세션: 공유 상태 = 통합 tip 하나            · 열린 결정은 journal에
같은 저장소, 같은 날, 두 사람.
0.12 세션이 뒤처진 워크트리 HEAD에서 끝난 카드를 점유 상태로 되살려 읽는다 —
0.13이 고친 바로 그 결함이 팀의 반쪽에서 계속 산다.
```

**공백.** 대상 프로젝트 어디에도 "이 저장소는 devflow ≥N을 전제한다"가 기록되지 않는다 —
스킬은 사용자별 플러그인 설치라서 저장소가 버전을 고정할 수단이 없다. 자료 소실 경로는
아니고(양쪽 다 각자의 규칙으로는 정합) 판정 불일치·중복 실행류다. 수리 후보: 무거운 버전
게이트가 아니라 README 팀 절의 한 문단("팀은 플러그인 버전을 맞춘다 — 특히 0.12↔0.13은
공유 상태의 정의가 다르다") + 관찰 등재. (§5-P8)

### 3.19 H35 — 통합 force-push [2판]

digest 마커 재정박 절차는 있다(설계됨). 그러나 점유 커밋 자체가 이력에서 지워지면 카드가
대기로 되돌아가 보이고, 원 점유자의 로컬에는 점유가 남는다 — 이중 점유가 정당하게 성립한다.
정본은 "되돌릴 때는 revert — 이력을 지우지 않는다"로 자기 쪽 규율은 갖지만, 관리자의
force-push는 devflow 밖의 손이다. **판정: 보장 밖으로 명시하는 것이 정직하다** — 지금은
보장 밖 표에 이 행이 없다. (§5-보장 밖 후보)

### 3.20 H25 — 카드 도중 워크트리 이사 [2판]

점유는 통합에 있으므로 새 워크트리에서도 내 점유로 보이고, 이 폴더에 로컬 흔적이 없으므로
**W4 질문이 정확히 발화**한다("여기서 이어갈까, 원래 폴더에서 열까"). 미커밋 변경은 원
폴더에 남는다 — 질문이 그것을 상기시키는 구조다. **정합** — 이번 라운드의 W4가 설계 의도대로
이 케이스를 받는다.

### 3.21 H32 — 비도입자 혼재 [2판]

직접 커밋은 digest가 잡고(작성자·접두 판별), 손 편집은 그물이 계층별로 있다: 카드 손 편집 →
승인 신선도 붕괴 → 재승인, 능력 문서 임의 diff → 정합성 이상, journal 형식 파손 → 12번.
core 문서의 커밋된 손 편집은 결국 사람이 canon 소유자라 수용된다. **정합** — "비도입자와
충돌하지 않는다"는 0.8.0 설계 목표가 유지되고 있다.

### 3.22 H12 — 상태 질문만 [2판]

"어디까지 됐어?"의 정답은 resume의 보고 문단 하나인데, 그 문단을 만들기 위해 세션은 정본
1,543줄 + 투영들을 읽는다. 변경 의사가 없는 질문에 진입 고정비 전액이 든다. **긴장** —
H5의 읽기 비례성과 같은 뿌리(P1). 다만 보고의 정확성이 곧 이 스킬의 신뢰라서, 값싼 요약
경로를 만들면 그 경로가 낡은 보고를 만든다는 반론도 같다.

### 3.23 A13·A14·A15·A17·A18 — 나머지 AI 축 [2판]

- **A13 역할 사망**: 역할은 무상태·재파견이 설계라 깨끗하다. verify 사건은 pending 기록이
  디스크에 있어 재실행된다. **정합.**
- **A14 주입 기억 충돌**: "devflow 밖 기록은 주장이지 정본이 아니다" 조항이 정확히 이
  케이스다. **정합** — 이 스킬의 조용한 강점.
- **A15 구버전 흔적**: 방 올리기·legacy Depends·v0.10 이관·출처 id 이관 — 이관 기계가
  계층별로 있다. **정합**(이관 자체가 복구 기계 150줄 논쟁의 일부라는 비용 긴장은 기록됨).
- **A17 하위 등급 모델**: 카드에는 등급 체계가 있지만 **라우팅·계획 세션의 모델은
  무방비다** — 작은 모델로 resume을 돌리면 1,543줄 정본을 오독할 확률이 그만큼 오른다.
  사용자 선택의 영역이라 규칙 후보는 아니고, README 한 줄 감이다. **긴장(경미).**
- **A18 무지 worker**: 오케스트레이터 계약(worker 전에 통합에서 카드·점유 생성, worker는
  코드+로그만)이 design.md에만 있다 — 계약의 거처 문제(P4). **긴장.**

### 3.24 H16·H17·H19·H20 — 나머지 사람 축 [2판]

- **H16 전면 교체**: 공유 기반이면 골조 + 능력별 카드로 매핑이 갈린다. D6이 다중 단위를
  받치고, 스무 마커 한 begin도 형식상 문제없다. **정합**(실전 검증 전).
- **H17 긴급 우회**: devflow 밖에서 직접 고치고 커밋 — digest가 나중에 잡는다. 탈출구가
  있고 그 탈출이 기록망(digest)으로 회수된다. **정합** — 단 README가 이 탈출구를
  명시하지 않아 사용자가 "devflow를 켰으면 전부 devflow로 해야 하나"라고 오해할 수 있다.
- **H19 수동 revert**: revert가 공인 undo라 상태는 디스크에서 재판정된다. **정합.**
- **H20 비코드 카드**: 완료 신호가 "실행 가능한 확인"이면 문서도 된다(존재·린트·링크 검사).
  **정합(경계 사례).**

**P6. 저장소 루트 해석 한 문장** (3.16) — 정본에 "모든 devflow 경로는 저장소 루트 기준,

한 계급 전체. **권장 채택** — P-01과 같은 결함의 스킬 층 버전이라 근거가 이미 실측돼 있다.

**P7. 좌초 흐름의 가시성** (3.17) — (a) 관찰 등재만. (b) resume에 유계 질의 한 줄(내 id

**P8. 버전 어긋남** (3.18) — README 팀 절 한 문단 + 관찰 등재. **권장 채택**(문서만,
스킬 무변).

**보장 밖 표 추가 후보 둘** — 통합 브랜치의 force-push(3.19) · 라우팅·계획 세션의 모델
등급(3.23 A17). 표에 넣는 것 자체가 정직성 장치다.

## 6. 2판이 1판에 대해 말해 주는 것

1판의 워크트리·팀 축은 "설계가 이미 답한 케이스"를 확인하는 폭이었고, 2판이 넓힌 것은
"설계가 아직 질문받지 않은 케이스"다 — 그 차이에서 공백 셋이 나왔다. 같은 방법의 한계도
같이 적는다: 이 목록 역시 귀납이다. 아직 상상 못 한 형태는 못 덮고, 그것은 텍스트를 더
읽어서가 아니라 실전에서만 나온다(기획 §13-6과 같은 한계). 매트릭스의 역할은 전수 증명이
아니라, 실전이 시작되기 전에 **구조적으로 걷지 않고는 안 보이는 칸**을 최대한 줄여 두는
것이다.
