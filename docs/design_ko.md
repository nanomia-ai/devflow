# devflow 설계 문서 — 왜 이렇게 만들었나

이 문서는 devflow의 **"왜"의 정본**이다. 문서별 역할 분담:
무엇을 어떻게 쓰는지는 `README.md`, 수정 절차와 게이트는 `AGENTS.md`,
버전별 변경 이력은 `CHANGELOG.md`, 규칙의 정본은 `skills/principles/SKILL.md`.

**여기 기록된 결정을 뒤집으려면, 기록된 이유부터 반박해야 한다.**
기각된 안을 재제안하려면, 기록된 기각 사유부터 반박해야 한다.
이유 반박이 없는 번복·재제안은 검토를 통과하지 못한다.

## 기원과 철학

사용자(jmp)가 AI와의 개발 전 과정(기획→구현→검증)을 관리하기 위해 설계했다.
2026-08-05, 사용자와 v0 → v6 여섯 차례 왕복하며 개념을 확정한 뒤 구현했다.

핵심 철학 — 모든 수정은 이 기조를 지켜야 한다:

1. **풍부한 방향성 + 최소 하네스.** 최신 상위 모델은 방법을 안다. 목적지와 금지만 명확히
   주고 방법은 지시하지 않는다. 하네스는 모델 등급에 반비례해서만 강화한다.
2. **지식은 적지 않는다, 취향은 적는다.** 모델이 이미 아는 보편 원칙(인젝션 방어법 등)을
   적는 것은 세금이다. 이 프로젝트가 무엇을 우선하는지(선언)만 적는다.
3. **진행 상태는 문서가 아니라 파일 트리다.** 파일명 접미사(.wip./.done./.stale.)와
   위치가 정본. 문서에 진행률을 적으면 반드시 낡는다. 작업 진행은 접미사와 진행 로그가
   소유하고, 규칙 정본이 형식을 고정한 journal·verify.md 상태 줄은 전이 상태일 뿐 진행
   기록이 아니며, 문서에는 여전히 진행을 적지 않는다.
4. **1개념 1단어.** 스킬 이름 = 산출물 이름 = 그 개념의 유일한 단어.

## 구조 한눈에

```
Layer 0 (1회·상속): product → arch → [design] · 기존 코드는 adopt가 역산     Layer 1 (반복): split → work ⇄ verify
공통: resume, principles(규칙 정본)
대상 프로젝트에 생기는 것: devflow/{project/, tree/, journal.md, users/<id>/ 방}
배포: Claude 플러그인(.claude-plugin) + Codex 프롬프트 생성(codex/install.*)
```

## 주요 결정과 이유

| 결정 | 이유 |
|---|---|
| 산출 폴더명 `devflow/` (docs/ 아님) | 기존 프로젝트의 docs/와 충돌 방지 |
| 이름은 devflow — Claude는 `devflow:` 네임스페이스, Codex는 `devflow-` 파일명 접두 | 스킬 이름 충돌 원천 차단 + 자동완성 그룹핑. 최초 명칭은 nano-devflow였으나 실사용에서 명령이 불필요하게 길어 v0.9.0에서 단축 — 네임스페이스/접두 구조는 그대로이므로 충돌 차단 근거는 계속 성립 |
| 규칙 정본이 skills/principles/ 안에 있음 | skills.sh 표준(skills/만 복사하는 설치기)에서도 정본이 함께 이동 |
| Codex 프롬프트에 정본 동봉(파일 참조 아님) | Codex 프롬프트 폴더는 평면이라 상대 참조 불안정 |
| 훅은 SessionStart 하나만 | Stop은 매 턴 발화라 소음, PreCompact는 "진행 로그가 항상 디스크에" 규약으로 불필요. SessionStart는 압축 직후에도 발화해 셋을 겸한다 |
| 모델명을 파일에 안 적음 (T-상/중/하 등급만) | 모델명은 반드시 낡는다. 매핑은 split 실행 제안에서 세션 단위 결정 |
| Git worktree 운용을 devflow가 만들거나 관리하지 않음 | 병렬용: 코어 수정이 흔해 조율·병합 비용 > 병렬 이득. 전시용: 사용자가 "작업 중 화면 깨져도 무방" 확인 → 이점 소멸. 다만 사용자가 이미 여러 checkout·worktree를 쓰는 경우까지 무시한다는 뜻은 아니다. 복구 규칙은 현재 checkout과 통합 브랜치의 공유 상태를 구분한다 |
| TDD 절차 미채택 | 완료 신호 + "실행 없으면 미검증" + 커밋 규율이 TDD의 효과를 의식 없이 확보 |
| 1 작업 = 1 커밋 (검증 통과 후) | 되돌리기 = revert 하나, git log = 작업 이력, 작업 경계 = 핸드오프 지점 |
| 트리 소급 기록 금지 (브라운필드) | 기존 기능을 .done 카드로 채우는 것은 낭비. 트리는 도입 이후만 |
| 정합성 점검은 보고만, 자동 교정 금지 | 자동 교정이 오판하면 오염 가속 |
| 스킬 상호참조는 슬래시 없는 단계명 | 실제 명령이 도구마다 다름(`/devflow:x` vs `/devflow-x`) |
| install.ps1은 UTF-8 **BOM** 필수 | PowerShell 5.1이 BOM 없으면 ANSI 파싱 → 한글 스크립트 파손 (실제 재현함) |
| 다중 모드의 분할 축은 사람이 아니라 **진실의 범위** | 진실이 하나인 문서(project·tree·journal)는 공유, 사람에 속한 상태(HANDOFF·마커·신원)만 방(users/<id>/)으로 격리. 후보 4안을 각각 반증 fork로 검증(총 5회, 매회 실결함 적출)한 끝의 채택 — 기각 계보는 아래 절 |
| HANDOFF는 git에 커밋하되 전용 커밋 금지 — 경계 정리 커밋에 동승만 | 전용 HANDOFF 커밋이 이력을 오염시켜 revert된 실사례(2026-08-06)가 근거 |
| 설계는 한글, 배포는 영문 (이중 언어) | 사용자가 검토할 수 있는 언어가 한글, AI가 가장 잘 이해하고 토큰을 적게 쓰는 언어가 영문. 절차·대역표는 AGENTS.md |
| 검토·검증 역할의 조건은 스킬 본문이 싣는다 — agents/*.md는 Claude 포장 (v0.9.5) | principles를 skills/ 안에 둔 것과 같은 이유: skills/만 복사되는 설치에서도 조건이 함께 이동해야 플랫폼 간 처리 차이가 없다. 소유자 지적(2026-08-09)으로 발견 — 실행·수정 금지, 취향 배제, 추정 표시, 실패의 재현 절차 동반이 Claude 전용 파일에만 실려 있었다. 에이전트 파일은 같은 조건의 재서술이며, 둘이 어긋나면 결함이다. v0.9.6에서 승계·대체: 조건이 스킬 옆 계약 파일 하나로 이동하고 Claude 등록은 제거 — 아래 v0.9.6 행 |
| Codex 설치는 네이티브 플러그인 채널이 1차(마켓플레이스 등록 + plugin add), 생성 슬래시 프롬프트는 명시 호출 채널로 유지, 훅은 ~/.codex/hooks.json 별도 등록 (v0.9.9) | Codex가 Claude 형식 마켓플레이스를 그대로 소비하고 SKILL.md 스킬을 모델 자동 호출한다는 것을 실측으로 확인(깨끗한 Codex 세션이 devflow 스킬 8종을 전부 인지). 플러그인 전달 훅은 Codex에서 제거된 기능이라 훅 등록은 분리 유지. 종전 프롬프트 단일 채널은 이 기능들 이전의 통로로, 자동 호출이 Claude 전용이 되는 마지막 플랫폼 비대칭이었다. 재발 방지는 사전 점검표의 "설치 채널이 각 플랫폼의 현재 네이티브 메커니즘을 향하는가" 항목이 맡는다 |
| 역할 계약은 스킬 옆 동반 파일 하나(reviewer.md·verifier.md)이고, 모든 플랫폼이 깨끗한 컨텍스트에 원문 브리핑으로 수행한다 — Claude 에이전트 등록 없음 (v0.9.6) | A/B/C 실측(등록 에이전트 2회 · 프롬프트 브리핑 Claude 2회 · Codex CLI 1회, 결함 4종을 심은 동일 픽스처)에서 다섯 실행 모두 검출 4/4·계약 준수 동일 — 등록의 강건성 이점이 관측되지 않았다. 메커니즘 하나로 플랫폼 분기가 소멸한다. 성숙 선례는 superpowers(하네스 7+, 등록 없음, 계약 프롬프트 파일이 스킬 옆). 전달은 정적이어야 한다 — 원문 파일 브리핑(Claude·skills.sh) 또는 설치 시 동봉(Codex); 실측에서 유일하게 실패한 전송은 셸 보간이었다 |
| 브라운필드 진입은 전용 스킬 adopt — arch에서 분리 (v0.9.10) | arch가 개발 기획과 Layer 0 전체 역산이라는 두 개념을 한 이름에 담아, 진입 발견성이 죽고(역산 트리거가 스킬 설명 꼬리에만 존재) 본문 접합부가 모호했다(역산 뒤 인터뷰 절차·검증 창구 게이트의 적용 여부를 문자적 독자가 확정 못 함 — 소유자 지적 2026-08-10). 역산 절차와 필드 배분은 0.9.8 결정 그대로 이동 — 신규 문장은 진입 가드·증거 서열·게이트 포인터·design 한 줄로 유계, 0.9.8의 "재인터뷰는 낭비" 판정 유지. 산출 형식의 정본은 product·arch에 남고 adopt는 단계명 참조 + Codex 프롬프트는 설치기가 동봉(평면 폴더 결정과 같은 근거). adopt는 개발 문화의 표준 어휘다 — Nx 문서 절 "Adopting Nx", Next.js·React 공식 "Incremental Adoption", Tech Radar 최상위 링 "Adopt" |
| 감리(audit) — 사건 발동 깊은 점검, 소견은 판정이 아니다 (v0.9.15, 범위 수정 v0.9.21) | 근거는 소유자 실전 보고(2026-08-10, ade 운용): 단회 결과가 허점을 남기고, 실수가 실수로 인식되지 않은 채 검증을 통과한다. 관찰 항목 둘(능력층 표본 폭·MVP 스펙 맹점)의 이행. 상시 단계가 아니라 세 사건(제품층 1회 · 실패를 기록한 능력의 폐쇄 · 사용자 요청)만 발동 — "겪은 결함이 있을 때만 자란다"의 런타임 적용이라 깨끗하게 닫힌 능력은 비용 0. 수렴 장치: 비차단 소견 · 영 소견 유효 · 사용자 채택만 카드화 · 재폐쇄 무재실행(새 유출은 새 사건). v0.9.15의 읽기 범위인 "실행한 경로 + 능력 폴더"는 현재 구조를 대표한다는 전제가 브라운필드·평면 구조에서 성립하지 않고 카드 이력을 노출하면서 아직 실행하지 않은 현재 표면은 놓친다. 그래서 v0.9.21은 과거 commit·diff·카드 대신 arch가 정확히 매핑한 경로 또는 외부 진입점부터 공유 계약 경계까지의 현재 능력 코드 범위로 제한한다. 이중 독립 검증(반증 워크 · 전체 정합 감사)이 초안에서 방아쇠 앵커 오독(덮어쓰기로 사멸/영구 재발화) · 무유계 읽기 · 품질 사냥감(단순화 카드 先실험 계보 미반박)을 적출해 수리·삭제한 뒤의 채택 |
| 회고(retrospective) — MVP 경계에서 설계 대안을 사후 평가하는 4번째 역할, 소견은 판정이 아니다 (v0.9.16) | 근거는 소유자 증언(2026-08-10): AI는 자기 기획을 의심하지 않고, reviewer/verifier는 명확한 문제만 집으며, 더 나은 선택지는 아무도 묻지 않는다 — 감지가 스스로 일어나지 않으므로 "단순화 카드 먼저 실험" 관찰 항목의 전제(사용자가 알아챈다)가 반박된다. 판단어("더 나은")는 3요건으로 유계: 구체적 대안 명명 + 이 프로젝트의 긴장 증거 필수(수정 카드 밀도·`.stale.`·ADR 갱신 주석·미해소 잠정값 — 산출물에서 관측 가능한 것만; 반증이 초안의 탈출 카드·잠정값 이력을 관측 불능으로 적출해 삭제) + 전환 비용 추정 표시. 입력은 devflow 산출물뿐, 코드 0 — 읽기 완전 유계. auditor 2모드 겸용은 기각(맹검 축이 정반대 — 한 이름 두 개념). 발동은 제품층 판정 기록 뒤 1회 + 사용자 요청뿐, 비차단·영 소견 유효·채택만 카드/재기준선 (발동 목록은 v0.9.17에서 능력 첫 폐쇄가 추가됨 — 그 행 참조) |
| 회고는 능력이 처음 닫힐 때도 돈다 — 그 능력 범위로 (v0.9.17) | v0.9.16의 능력 단위 배제를 소유자 지시(2026-08-10)로 번복 — 기록된 두 근거의 반박: "긴장 증거가 얇다"는 입력을 능력 범위로 좁히면 비용도 함께 얇아지고 영 소견 유효가 무해하게 하며, 의존 능력들이 그 설계 위에 쌓이기 전의 조기 발견이 MVP 발견보다 싸다. "상시 단계가 된다"는 소유자가 이 리듬을 직접 지정했다 — 기획자는 사람이고 독주보다 큰 단위마다 한 번씩 확인하는 반응이 낫다는 운용 방향은 상상한 위험이 아니라 방향 그 자체다. 카드 단위 회고는 계속 없다 |

| 봉쇄 중에도 발급·점유·소비가 아닌 journal 덧붙임은 즉시 기록한다 (v0.14.0) | v0.13.0의 게시 문단은 journal 줄 생성까지 통합이 열릴 때를 기다리게 했는데, 그 동결의 실제 결과가 이 시스템이 가장 경계하는 무흔적 소실이었다 — 봉쇄 중 세션이 죽으면 사용자가 분명히 말한 요청이 대화에만 존재하다 증발한다(독립 검증의 유일한 최상급 위험). 원 근거였던 "조정점 없이는 전역 답이 없다"는 덧붙임에는 미치지 않는다 — 덧붙임은 전역 답이 필요 없는 로컬 증거이고 나중에 합쳐도 안전하다는 것이 그 결정 자신의 실측이다. 허용은 정확 열거다: 유지보수 요청 · capability note · 기명 미결/결정 · product 재실행 대기. 번호를 발급하는 layer opening, push가 필요한 증거 기록, 검증 상태 줄, 모든 소비(삭제)는 계속 대기한다. 최종 작업 커밋은 계속 목록에 명시한다 — 자기 브랜치 소관인데 어느 목록에도 없어 "이름 없이 기다리는 것은 없다"는 같은 문단의 자기 선언을 위반하고 있었다 |
| journal 병합 충돌은 합집합이 아니라 3-way다 (v0.14.0) | "합집합 — 양쪽 줄을 날짜순으로 다 남긴다"의 기록된 사유는 기록 보존이었는데, 실측 15·16이 같은 의미론(merge=union)을 이미 기각했다 — 한쪽이 소비해 지운 줄을 다른 쪽의 인접 추가가 부활시켜, 계획까지 끝난 요청이 되살아나 같은 수정이 새 번호로 두 번 계획된다. 보존이 아니라 유령 재생이다. 교체 규칙: 충돌 시 공통 조상(merge-base)의 journal blob과 대조해, 조상에 있던 줄이 한쪽에 없으면 소비이므로 복원하지 않고, 조상에 없던 줄은 추가이므로 양쪽 다 시간순으로 남긴다. 추가는 전부 보존되므로 원 사유(기록 보존)를 3-way가 더 잘 지킨다. 봉쇄 덧붙임 허용으로 병합 빈도가 늘므로 두 결정은 한 몸이다 |
| 공용 계약 관측의 셋째 갈래는 기명 미결 항목이다 (v0.14.0) | v0.13.0 K3 행의 "그 밖이면 journal 한 줄"은 계급도 소비자도 없는 줄을 만들었다 — 정본이 허용한 세 계급(정본 형식·교차 과제 결정·기명 미결) 어디에도 들지 않고, 골조는 폐쇄 의식이 없어 수확자도 없다. verify 분류기가 그 줄을 정합성 이상으로 거부하고, 막힘을 풀려는 손이 그 줄을 지우면 차단이 소실로 전환되는 접합부 결함의 뿌리다. ADR도 Risks도 아닌 공용 계약 관측은 "어디에 착지할지(또는 폐기할지) 사람이 결정할 기명 미결 항목"으로 쓴다 — 기존 미결 의미론(해소되면 표의 다른 행으로 착지한 뒤 삭제)이 소비자를 제공하므로 새 계급도 무기한 체류도 생기지 않는다. verify 분류기는 정본의 허용 내용과 정확히 같은 계급을 갖는다 — 쓰기 쪽을 넓히면 읽기 쪽 분류기를 같은 문장으로 맞춘다 |

## 차용과 그 경계

맷 포콕(mattpocock) skills 저장소에서 차용한 것: 조사 카드(prototype+wayfinder의 증류),
ADR 3조건(domain-modeling), 검증 이중축(code-review), code-style 지향 절의 가치 선언 일부
(codebase-design·tdd에서 절차를 빼고 취향만).

**차용하지 않기로 한 것**: 어휘 강제, Red-Green 절차, 냄새 12종 목록, 3에이전트 병렬 설계.

사용자 규칙: 이 저장소에서 추가 차용 시 반드시 사전 허락.

## 기각된 안 — 재제안하려면 기각 사유부터 반박할 것

v0.7.0에서 검토 후 기각:

- **중간 인계 문서** — 반쪽 진실을 넘긴다.
- **work의 카드 승격 트리거** — 조용한 범위 확장의 문. (기각된 것은 work 루프 안의
  상시 트리거다. 공인 경로는 유지된다: 규칙 정본의 발견→갱신 표가 "예상보다 클 뿐"을
  잡아 split의 승격 절차로 보낸다.)
- **훅의 journal 주입** — resume이 읽는 것의 중복.
- **verify-channel 문서 위치 이전** — arch 포인터로 충분.
- **열린 결정의 journal 이관** — 한 개념 두 거처. HANDOFF 이월 규칙으로 대체.

v0.8.0 다중 모드 설계에서 기각·흡수:

- **A안(공유 문서 + ID 표기)·C안(사용자별 폴더 분리)** — 채택안 D("진실의 범위")에 흡수됨.

  남기면 안 되는 팀" 전용의 답으로 남겨둔다. 일반 채택 경로에는 쓰지 않는다.

v0.9.4 루프 엔지니어링 검토에서 기각 (2026-08-09):

- **graph engineering 도입(타입 증거 그래프·오케스트레이션 에이전트)** — 트리·의존·상태
  접미사·revert가 이미 저비용 그래프다. typed graph 검색이 강한 ranker보다 11.2%p
  낮았다는 부정적 결과(p=0.0007)도 확인했다.
- **root-cause 문서화 단계** — 진행 로그가 이미 진단의 거처다. 별도 산출물 요구는
  방법 지정이다.
- **held-out·후보 비교 승격 게이트** — 프롬프트·하네스의 확률적 최적화 전용이다.
  devflow 자체의 유지보수는 AGENTS.md 반증 프로토콜이 그 역할을 이미 한다.
- **하네스 자동 진화(자기 프롬프트 재작성)** — "방향만 잡고 스스로를 고치지 않는다"는
  철학과 정면 충돌한다. 자가 개선은 빠져나간 결함의 신호 편입(v0.9.4 채택분)까지만.

v0.9.12에서 시도 후 철회 (2026-08-10):

- **모순 해소의 표 일원화** — 문서 간 모순을 1~4단계 대신 발견→갱신 표로 보내는 재서술.

- **resume이 파일명만 보고 도메인 질문에 답한다고 간주** — 경로를 보여 주는 것은 AI가 그
  문서를 읽는 실행 분기가 아니다. 번호·이름으로 정확히 하나를 여는 별도 유계 분기가 필요하다.

기타:

- **유지보수 재개봉 시 "관련 기록을 훑는다" 류의 규칙** — '관련'이 판단어라 문자적 AI가
  살찐 폴더 전체를 통독하는 읽기 폭발 위험. **무유계 읽기 규칙은 만들지 않는다.**
  (유계인 확정 문안은 아래 관찰 항목 참조.)
v0.12.0 사용 동선 재설계에서 기각:

- **기록된 초점 필드** — HANDOFF에 `## Focus` 한 줄로 "오늘은 이 능력"을 영속 저장. 근거로 든
  "그 사실이 어디에도 남지 않는다"가 거짓이다. 선언은 한 걸음 안에 점유 개명으로 착지하고,
  경계 너머는 `Next single step`이 나른다. 남는 구멍은 "선언만 하고 디스크 변화 0으로 세션
  종료" 하나이고 비용은 문장 하나인데, 막는 값은 작성자 셋(resume은 파일을 쓰지 않는다)에
  낡음 판정과 복구 규칙까지다. 아직 관측된 적 없는 마찰이므로 "실제로 만난 결함에서만
  하네스가 자란다"에 걸린다.
- **터미널마다 상태 폴더(`flows/`)** — 터미널은 조용히 죽는다. 닫는 기점이 없어 폴더가 영원히
  남고 청소 규칙이 필요해진다. 능력 축은 사라지지 않으므로 애초에 닫을 필요가 없다.
- **사람 아래 두 겹 식별자**(`users/<사람>/flows/<흐름>/`) — "id별"로 쓰인 규칙 전부가
  "사람별 × 흐름별"로 갈라져 복구·정합성이 두 배가 된다. 모드 통합이 같은 문제를 순감으로 푼다.
- **세션·날짜 단위 작업 묶음 파일** — 전부 닫는 기점을 요구하고, 닫는 기점은 조용히 죽는
  세션에서 반드시 샌다. 카드가 이미 "완료 신호 하나 = 커밋 하나"로 그 역할을 한다.
- **능력별 작업 노트 새 계층** — 중계 노트는 이미 네 층으로 존재한다(코드 · 미수확 카드 ·
  능력 문서 · Layer 0). 세 번째 집을 짓는 것이고, v0.11.0이 기각한 중계 노트 2차 핸드오프 층과
  경계가 맞닿는다.
- **미수확 카드의 진행 로그 전문 읽기 / 최근 N장만 읽기** — 전자는 실현 불가(카드마다 수백 줄),
  후자는 N이 판단어이자 임의 숫자다. `Covered cards` 여집합은 기계적 경계이고 이미 계산된다.
- **verify의 "devflow 밖 미커밋" 게이트를 능력 범위로 좁히기** — 공유 코드를 누가 고치는 중일 때
  거짓 통과가 난다. 안전 장치를 편의로 바꾸는 거래다. 동시 작업에서 편집은 병행되고 검증과
  빌드는 직렬화된다 — 새 제약이 아니라 이미 있던 안전 장치가 눈에 보이게 된 것이다.
- **devflow가 워크트리를 만들거나 관리** — 기존 기각("핵심 편집이 잦아 병합 비용 > 병렬 이득")을
  뒤집지 않는다. 이번 설계는 devflow가 워크트리를 만드는 것이 아니라 사용자가 이미 만든
  워크트리와 호환될 뿐이다.
- **resume 보고에 능력 문서 신선도 한 줄 추가** — 기획에는 있었으나 채택하지 않았다. 그 줄이
  막는 잘못된 행동이 없다. 승인은 단계를 고를 뿐이고 지식을 소비하는 것은 work이며, work이
  같은 줄을 보고하고 가설은 사용 전 재확인이 강제된다. 대신 "보통 재개는 본문을 읽지 않는다"를
  고쳐야 했다. 사유 절과 대안 목록은 사용자가 실제로 다른 단위를 고르게 하므로 채택했다.

v0.13.0 동시성 재설계에서 기각:

- **journal의 `merge=union`** — 실측으로 반증됐다. 한쪽이 요청을 소화해 줄을 지우고 다른
  쪽이 인접 위치에 덧붙이면 union이 소화된 요청을 부활시킨다. 한쪽이 `증거 대기`를
  `증거 마감`으로 교체하고 다른 쪽이 덧붙이면 두 레코드가 모두 남아 정합성 13번을 위반하는데
  처리 규칙이 없다. 지운 상태를 되살리는 합집합은 사람이 푸는 충돌보다 나쁘다.
- **devflow가 워크트리를 만들고 관리하는 것** — 안전 대책으로서는 실측이 반증했다. 워크트리
  둘이 공유 파일의 같은 자리를 고치면 병합에서 충돌하지만, 한 폴더의 두 세션은 뒤 수정이 앞
  위에 얹혀 충돌하지 않는다. 폴더를 나누는 것은 안전이 아니라 빌드 격리를 사는 일이므로,
  v0.9.x의 비관리 기각은 그대로 서 있고 뒤집을 필요가 없었다.
- **공유 파일용 원자 락 helper** — 실측으로 불필요해졌다. 자기 경로를 지정한 커밋과 덧붙이기
  전용 기록장이 락에 기대던 것을 이미 준다.
- **비교-교체 게시용 helper 스크립트** — 필요성이 논증된 적이 없다. `git push . HEAD:<브랜치>`가
  fast-forward 전용이고 `git update-ref <ref> <new> <old>`가 명시적 비교-교체이므로 helper가
  필요 없다. 게다가 실측에서 `update-ref`는 다른 워크트리가 체크아웃한 브랜치에도 성공해 그
  워크트리를 조용히 어긋나게 만든 반면 push는 거부했다 — 평범한 push가 더 약한 것이 아니라 더
  안전한 원시 연산이다. 스크립트를 더하면 devflow가 순수 프롬프트 텍스트라는 성질이 바뀐다.
- **`legacy signal migration` 마커 상태 기계** — 정본 25~40줄인데, 잔여 위험은 "다른 단위
  점유의 미커밋은 먼저 체크포인트한다"는 work의 기존 규칙이 이미 유계로 만든다.
- **은퇴 시 `능력 관측` 처분을 위한 6필드 상태 기계** — 정본 30~50줄인데, 은퇴 커밋 앞의 게이트
  하나면 닫힌다. 은퇴에서 증거 기록을 지우는 옆 조항과 같은 모양이다.
- **다른 워크트리에 대한 조상 인지 blob 투영** — 통합 브랜치 하나를 읽는 것으로 대체됐다. 다른
  HEAD가 권위가 아니게 되면 점유만 더하는 필터도 더할 것이 없다.
- **워크트리별 git 신원** — 기술적으로 가능하지만(`extensions.worktreeConfig` + `git config
  --worktree`) 따라오는 것 때문에 기각한다. 커밋 작성자를 바꾸므로 정합성 8번의 작성자 검사가
  말하는 바를 잃고, 폴더마다 방이 하나씩 남는데 그것을 닫는 것이 없으며, 한 사람이 여러 id로
  갈라져 공유 문서가 그것을 다시 화해시켜야 한다. "가능한가"를 "무엇이 따라오는가"보다 먼저
  답한 것이고, 이번 라운드가 그만두기로 한 실수가 바로 그것이다.
- **능력 지식 기준선 판정 정본을 읽는 계약과 쓰는 계약으로 분할** — 시도했다가 자기 조건에
  따라 접었다. 조항×소비자 행렬이 깨끗하지 않다. 정체성과 기대 집합, 문서 계약, 메타데이터와
  신선도, 쓰기 주체와 교체 경계, v0.10 이관, 허용 한계가 전부 arch·adopt·verify·resume 모두가
  직접 읽는 것이고 그것이 파일의 대부분이다. 읽기 쪽이라던 resume은 경계 손상 복구와 begin
  커밋을 위해 쓰기 자격 규칙이 필요하고, 쓰기 쪽인 verify는 도메인 진입의 역할 입력이 필요하다.
  모든 소비자가 두 파일을 함께 읽게 되며 그것이 기록된 접는 조건이다. 폐기가 아니라 보류다.
- **규칙 정본의 소비자별 분할** — 기각이 아니라 보류다. 실패 방식이 나쁘다 — work가 필요한
  규칙이 verify 전용 제목 아래로 가면 아무 에러 없이 사라진다. 결함 열 건을 함께 수리하는
  릴리스에 섞으면 어느 변경이 무엇을 깼는지 가릴 수 없다.

  다른 터미널의 능력 폐쇄를 설명 불가한 정합성 이상으로 만든다. 안전하고(잃는 것이 없으며 엄격한
  접두 구간 안전 장치가 작동한 것) 사용자가 읽을 수 없는 멈춤일 뿐이다. 실제로 만나는지 지켜본다.

  판정 변경을 **실측 반증**에 걸어 두었고, 사용자가 마음을 바꾼 것뿐이면 product 재실행 전체를
  물린다. 행을 더하기 전에 그 마찰을 실제로 만나는지 지켜본다.

  아무것도 해결하지 못하고 resume이 묻는다. 구조적으로 안전하지만 가장 자연스러운 표현이 왕복
  하나를 문다. 느슨하게 하면 흐릿한 매칭이 들어오므로 마찰이 실제로 보고되기 전에는 왕복을 택한다.

  판단어에 가깝고 `none`이 안전한 기본값이라 안 쓰는 쪽으로 기울 수 있다. 실패가 조용하다 —
  줄은 전부 `none`인데 다음 카드가 같은 함정에 다시 빠진다. 실전에서 carry 줄의 실제 분포를 본다.

  digest와 Scope head 신선도 강등이 사후 신호다. 오분류가 관측되면 게이트 문안을 재검토한다.

  무뎌질 수 있다.
- **좌초된 흐름** — 점유는 통합에 착지하지만 체크포인트는 자기 브랜치에 남아, 워크트리를 지우거나
  팀원이 자리를 비우면 그 진행이 아무도 읽지 않는 브랜치에 좌초되고 다음 세션이 조용히 다시
  구현한다. Git이 보존하므로 소실이 아니라 가시성 문제다. 예비안: resume이 내 id 접두 커밋을 가진
  비통합 로컬 브랜치를 한 줄로 열거하는 유계 질의 — 실전 관측 전에는 넣지 않는다.
- **플러그인 버전 어긋남** — 저장소가 요구 devflow 버전을 기록할 수단이 없어 0.12 세션과 0.13

  재폐쇄가 제안된다. 제안은 승인제라 실해는 소음이고, 경량 차선이 묶음 자체의 규모를 줄이므로
  지켜본다.

## 보류 중 — 다음 버전 후보

공개 후 이 목록은 GitHub Issues로 이관한다. 단, 기각 계보는 Issues가 아니라
이 문서에 남는다 (닫힌 이슈는 다음 AI가 읽지 않지만, 이 문서는 게이트가 강제로 읽힌다).

- **버그 진단 스킬** — 맷의 diagnosing-bugs("재현 루프가 스킬의 전부, 나머지는 기계적")를
  청사진으로. 한 사이클 실전 후 재평가.
- **트리 아카이브 규칙** — 발동 조건: resume의 트리 전체 목록 읽기가 부담될 때.
  이관 시 이름 보존, 유지보수 라우팅은 아카이브도 검색. 그 전엔 YAGNI.
- **GitHub 공개 + `npx skills add` 지원** — 구조는 이미 호환. v0.9.0 문서 개편이 그 준비다.
- **구버전 devflow 문서의 정합화(마이그레이션) 스킬** — 지금은 "정합화 카드 1장" 패턴으로
  충분(정합성 점검 + 모순=결함 규칙이 검출기). 공개 후 다수 프로젝트가 생기면 재평가하고,
  그때 `CHANGELOG.md`의 버전별 기록이 스킬의 입력이 된다.
- **Layer 0 초안 확인 상태의 디스크 표현** — 현재 파일만 보면 같은 내용의 확인 전 초안과
  확인 후 문서를 구분할 수 없다. 선택지는 (A) 확인 뒤에만 정본 경로에 쓰기, (B) 각 문서에
  확인 마커를 두고 구버전 무마커 문서의 이관 규칙까지 정하기다. 복구성·이관 비용이 달라
  소유자 선택 전에는 어느 쪽도 강제하지 않는다.
- **빈 프론트엔드 저장소에서 design 산출물을 만드는 시점** — 현행 token 파일·preview 실물은
  골조 카드보다 먼저 요구돼 실행 기반이 없을 수 있다. 선택지는 (A) design을 계획 문서까지만
  만들고 실물은 골조 카드로, (B) 골조 work 뒤 design으로 돌아오는 순서다. Layer 0과 작업
  트리의 경계를 바꾸는 결정이므로 소유자 선택 전에는 현행을 억지로 재배치하지 않는다.
- **규칙 정본의 크기** — 규칙 정본은 217줄(v0.9.9)에서 705줄(v0.13.0)로 자랐고 8개 스킬 전부와
  위임받은 구현자까지 이 문서를 통독한다. 판정 동반 문서까지 더하면 resume은 세션마다
  약 1,543줄, arch는 약 1,400줄을 읽는다. 모드 분기 제거로 30줄을 돌려받았지만 사용 동선과
  동시성 재설계가 그보다 더 썼으므로 이것이 여전히 가장 큰 미해결 비용이다. T-하 카드에는 저널 형식·
  정합성 15항목·라우팅 쓰기 순서·원격 증거 상태 기계·검증 상태 커밋이 한 번도 발화하지 않는다. 삭제가
  아니라 **소비자별 읽기 범위 분할**(구현자에게 필요한 것과 라우터·복구자에게 필요한 것)이
  비례적 해법이며, 디스크 데이터 형식을 바꾸지 않으므로 언제든 안전하게 수행할 수 있다.
  v0.11.0이 work·reviewer·retrospector에 유계 투영만 준 것이 이 분할의 첫 적용이다.
  v0.13.0은 같은 분할을 기준선 판정 정본에 시도했다가 접었다 — 그렇게 판정한 행렬은 기각
  계보에 있다.
- **중단 복구 기계의 비례성** — 규칙 정본 중 약 150줄이 "세션이 전이 도중에 죽으면 어떻게
  하나"에 답한다. 마커·begin 커밋·접두 비교·바이트 동일성 판정·`라우팅 준비` 명세·증거 대기
  상태 기계, 그리고 resume의 라우팅 49행 중 15~20행이 여기 속한다. 그 전이들은 몇 초짜리다 —
  세션은 긴 구현 중에 죽지 이름을 바꾸고 커밋하는 사이에 죽지 않는다. 그리고 devflow 자신의
  철학은 이상을 보고하고 승인 후에만 고치는 것인데 이 줄들은 전이를 자동으로 완성하려 든다.
  반쯤 된 상태를 알아보고 무엇이 반쯤인지 말한 뒤 묻는 쪽으로 바꾸면 탐지는 그대로 두고 자동
  완성만 없애며 크기는 약 1/3이 된다. v0.13.0에서 하지 않은 이유 셋 — 동시성과 완전히 다른
  축이라 섞으면 어느 변경이 무엇을 깼는지 못 가린다. v0.9.21의 기각 사유가 "중단이 아니라
  모호성"이었으므로 먼저 반증해야 한다. 그리고 그 150줄이 실제로 세션 품질을 떨어뜨리는지
  잰 적이 없다 — 그 답은 첫 실전 사이클이 준다.
