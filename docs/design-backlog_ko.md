# devflow 관찰 항목과 보류 후보

릴리스 기획이 여는 파일이다. 여기 있는 것은 결정이 아니다 — 실전 데이터가 생기기 전까지 규칙을 더하지 않기로 한 것들이다.

관찰 항목은 지우지 않는다. 무언가가 그것을 끝내면 취소선을 긋고 무엇이 언제 이행했는지를 붙여 「이행·종결된 관찰」로 옮긴다. 그냥 지우면 다음 세션이 같은 관찰을 근거 없이 다시 제안한다 — 기각 계보를 남기는 이유와 같다.

보류 후보도 같다. 착수해서 결정이 되면 그 항목에 착지한 `DD-nn`을 붙여 남기고, 접기로 하면 사유를 붙여 기각 계보로 보낸다. 어느 쪽이든 조용히 사라지지 않는다.

## 실전 관찰 항목 — 규칙 추가 없이 다음 사이클에서 지켜볼 것

- **호환 환류 실전 잔여는 유계 관찰로 남는다** (DD-96 seal과 integration-behind 수리가
  2026-09-02 기록) — 첫째, 상태 도구는 현재 Git 이력에서 차단형 reopen finding을 도출하며
  journal을 고친 뒤에도 그것을 지울 수 없다. 이것은 기록일 뿐이고 런타임 동작 변경 권한이
  아니다. Work가 아닌 writer가 실전에서 하나에 도달한 뒤에만 clearable-finding 설계를 다시
  연다. 후보는 현재 journal에서 reopen finding을 도출하고, 소비를 오래된 것부터 순회하며,
  이미 소비된 identity의 제거 검증은 건너뛰고, 소비된 nonmember 제거는 advisory로 다루는
  방식이다. 둘째, **R-1**은 비정본 direct Product/Design 진입에 관한 source-literal이지만
  실행하지 않은 residual이다. `skills/principles/scripts/project-state.mjs:1446`은 integration
  marker의 `landing = "pending"`을 유지하고, Product와 Design collector는 그 값을 읽지만 두
  spec은 `state.route`를 소비하지 않는다. 따라서 lagging worktree에서 hook의
  Principles→Resume route를 우회해 사용자가 어느 owner skill이든 직접 호출하면 쓰고, 기다린 뒤,
  다시 `pending`을 볼 수 있다. 정본 route는 `integrity.blocking`에 도달하고 소실이나 marker
  중복은 예측되지 않으므로 이것은 v0.20.0 release blocker가 아니다. 소유자가 이 concurrency
  state의 direct owner-skill invocation을 정본으로 만들거나 end-to-end 실전 실행이 loop를
  재현하면 kernel-only landing-state correction을 다시 연다.
- **정본 `C<n>` 행 파서의 수용된 한계** (v0.20.0 최종 수리 감사에서 2026-08-31 기록;
  `skills/principles/scripts/project-state.mjs:531-574`) — 선언된 번호의 빈칸은 이상 없이
  수용된다(`C1, C3` → `02, 04`). 별개로, `## Capabilities` 아래에서 한 행이라도 파싱되면
  나머지 내용 있는 행이 아닌 줄은 이상 없이 버려진다(`C1 Alpha …`와
  `- Palette export needed` → `02`만). 반대로 실제 행이 선언하지 않은 `C<n> `으로 시작하는
  문장은 능력으로 파싱된다(유효한 `C1 Alpha …` 옆의 `C3 comes later.` →
  `04-comes later..md`, `blocking=0 anomalies=0`). 두 동작은 이번 수리보다 앞서며 원문자 문법에도
  같다. 도달 범위는 Product 템플릿이 `generated`로 선언한 절을 소유자나 모델이 손 편집한 경우다.
  정본 갈래에 선언된 `User outcome:` 꼬리나 은퇴 표식을 함께 요구하는 정확한 guard는 꼬리가
  달라진 실제 행을 위의 조용한 탈락으로 바꾸므로 기각했고, 연속성·near-miss 이상도 앞서 기각했다.
  실제 `product.md`에서 조작되거나 빠진 행이 관측되거나, legacy prose 시험을 건드리지 않고 내용
  있는 미파싱 행을 전부 보이게 할 수 있을 때 다시 연다.
- **첫 번째가 아닌 `WRITE`의 템플릿 id 투영** (2026-08-31 v0.20.0 Phase 4 BEFORE와 Fable
  판정 기록) — Skill Rails v0.1.7은 첫 `WRITE`만 `template_text`로 투영하지만 뒤의 `WRITE`는
  `effects`와 `stage_artifacts`에 템플릿 id를 싣고, BEFORE 소비자 세 번(Claude 2·Codex 1)은 그
  id의 템플릿 파일을 찾아 썼다. AFTER 실행에서 첫 번째가 아닌 산출물이 명명된 템플릿과 다른
  모양으로 쓰이면 이 투영 경계를 다시 연다.
- **템플릿 주석을 통한 glossary 문법 전달** (2026-08-31 Fable의 Product/Adopt/Arch 실물 실행·
  파서 판정) — glossary 작성자에게 정확한 `term: definition` 형식이 닿는 곳은 제목 줄의 템플릿
  주석뿐이며, 이번에는 새 런타임 규칙을 두지 않는다. AFTER 실행이 내용 있는 glossary 줄을 쓰고도
  정의를 0개 파싱하면 `capability-rows-unparsed`에 대응하는 `glossary-terms-unparsed` 봉쇄를 다시
  검토한다.
- **유지보수 재개봉 시 기존 기록 도달** (2026-08-08 검증 완료 · 2026-08-11 문안 개선):
  유지보수 카드는 형식상 의존이 없어 work의 직접 의존 읽기가 발동하지 않을 수 있다. 승격
  기계(환류·journal 정리)가 구속 지식을 이미 공유 문서에 올려두므로 틈은 파국형이 아니라
  비용형(함정 재발견 재작업). rdsf 실사용(2026-08-11)이 시사 증거를 냈으나 참조 충돌이
  섞인 환경이라 확정 마찰로 인정하지 않았다 — 마찰 관찰 시 확정 문안(0.9.18 재검증이
준비 문안의 무가드 명령형과 무정의 명칭 '당겨 읽기'를 적출해 수리한 판)을 Direct 라우팅
  절에 넣는다: "유지보수 카드는 자신이 수정하는 것을 만들거나 고친 카드가 트리에 있으면
  `의존`에 지목한다 (트리 목록의 이름으로 찾아진다 — 여럿이면 전부). work가 지목된 직접
  의존 카드를 통독한다." (가드·복수 열거·소비자 명시,
  새 개념 0, 읽기 유계)
- 유지보수 국면에서 능력 폴더에 카드가 길게 이어 붙을 때(02.7…02.40) 중간 묶음 폴더 규칙이
  실제로 적용되는가.
- 연 단위 장기 지평의 문서 비대 — 대청소는 새 규칙이 아니라 product/arch 재실행(공인
  재기준선)으로.
- 간헐 실패(레이스 등)에서 태어난 수정 카드 신호는 재현 증명력이 약하다 — 단회 통과가
  결함 소멸을 과신시킬 수 있다. 마찰 관찰 시에만 문안을 검토한다.
- 수정 카드가 쌓이면 폴더당 회귀 신호 재실행 비용이 자란다 — 무거워지면 트리 아카이브
  규칙(보류 목록)과 함께 재평가한다.
- 위임 시 계약 파일이 실제로 원문 그대로 브리핑되는가(요약 전달 마찰) — 실측의 전송
  교훈이 실무에서 재현되면 문안 강화를 검토한다.
- 실패 사다리 3진(사람 호출)이 실전에서 반복 소진되는가 — 관측되면 경쟁 시도(독립 구현
2개 + 비교 선택)를 Direct 실행 제안의 선택지로 재평가한다. 미채택 근거는 판정자
  편향·비용 (0.9.13 리서치 기획).
- 장기 미폐쇄 능력의 회고 무발동 — 능력이 오래 닫히지 않으면(조사·유지보수가 길어질 때)
  회고의 세 사건이 발동하지 않는다. 사용자 요청 발동이 실제로 쓰이는지 지켜보고, 마찰
  관측 시 중간 사건 정의를 검토한다.
- 조사 카드의 정체성 주입 예외 — 조사 카드가 작업의 본체가 되는 프로젝트에서 닻 없는
  구간이 길어진다는 가설(rdsf). 표류가 재관측되면 예외의 기록된 근거("동결 로그라 효용
  없음")를 재평가한다.
- HANDOFF 이월 의무의 범위 — 현행은 '열린 결정'만 이월. 착지 게이트(0.9.18)가 영속
  지식을 정본으로 빼주므로 남는 틈은 작다 — 함정·배운 것의 소실이 재관측되면 검토한다.
- 골조(01)의 설계 구역이 실제 카드에서 공유 계약의 경계·불변식을 재발견하는 비용을 줄이는가.
  독립 검증 경계가 없어 검증 구역은 계속 `None.`이다. 사용 흔적이 없으면 도메인 지식층의
  첫 절단 후보다.
- 공유 코드(골조·공유 계약) 변경이 그 코드를 쓰는 능력들의 회귀를 다시 돌리지 않는다.
  기준선이 이를 가설로 감지할 수는 있어도 검증을 발동하지는 않는다. 공유 변경이 잦아지면
  재검토한다.
- **Design head 줄만 바뀐 일괄 확인의 반복** (v0.15.2 관찰 등재) — Layer 0 접촉 뒤 모든 능력
  문서의 일괄 diff가 `Design head` 줄뿐인 확인이 N회 반복되는지를 본다. 사용자가 그 반복에서
  확인 피로를 보고하면, 일괄의 모든 파일에서 유일한 diff가 그 줄인 경우 확인 질문 없이
  `arch — capabilities` 커밋을 착지하는 안을 다시 연다. DD-97 뒤 초기 Adopt는 같은 한 승인 아래
  별도 `adopt — capabilities` 커밋을 사용해 앞선 Layer 0 커밋을 새 능력의 최신 `Design head`로
  기록하고 각 캡슐을 그 소유자 옆에서 검증한다. 이는 여기서 관찰한 관리 상태의 반복 확인이
  아니다. synky에서는 Provisional 6행을
  정산하자 전 능력의 `Design head`가 6회 노후했다. 그 전에는 현재 확인 게이트를 유지한다.
- **`verify_channel`이 선택과 현재 실행 가능 상태를 한 값에 섞는다** (v0.17.0) — 값 문법과
  소비 규칙(파싱·planned 상태에서 정지)을 함께 정의해야 하므로 이번 라운드에서 고치지 않았다.
  관측 조건은 planned 상태의 means를 실행 가능한 것으로 오해해 verify가 잘못 호출된 사례 1건이다.
- **활성 점유가 설계 구역 갱신을 무기한 미룬다** (v0.17.0) — resume의 first-match 규칙에서
  활성 점유 행이 능력 문서 행보다 먼저다. 코드 정확성은 유지되므로, 능력 문서를 연 소유자나 새
  합류자가 낡은 내용으로 실제 오해한 사례가 1건 생길 때 다시 연다.
- **adopt 중간 사망은 대표 흐름 추적을 전량 잃는다** (v0.17.0) — adopt의 증거 표는 저장이
  금지되고 진행 마커도 없다. 실제 브라운필드 도입에서 adopt 재수행이 발생하면 중간 착지 비용을
  다시 잰다.
- **상위 문서 변경과 설계 구역 재파생이 같은 전이에 묶이지 않는다** (v0.17.0) — 발견→갱신 표에서
  재파생을 직접 배선한 것은 능력 개명·분할뿐이고, 흔한 스택·경계·데이터 변경은 의미 재검토 규칙에
  기대고 있다. 그 자리의 의미 검사를 놓친 사례가 뒤에 발견되면 전이 배선을 다시 연다.
- **능력 문서 byte가 배치 확인 없이 바뀌는 복구 경로가 둘이다** (v0.17.0) — 확인 뒤 중단된 쓰기의
  재생성과 ADR 승계의 기계적 경로 치환이다. 어느 경로든 예상 밖 diff가 실제로 생기면 확인 경계를
  재검토한다.
- **`Layer 0`가 능력 문서를 포함하는지 용어가 갈린다** (v0.17.0) — 실행 계약은 능력 문서를 Layer 0
  뒤로 분리하지만 `docs/blueprints/memory-fs-0.15.2_ko.md`와
  `docs/rounds/v0.12.0/handoff_ko.md`는 포함으로 읽히거나 직접 포함한다. blueprint와 역사
  기록은 그 시점의 기록이라 고치지 않는다.
- **이미 착지한 arch.md의 미기록 ADR을 사후 회수하는 정본 경로가 없다** (v0.17.0) — 발견→갱신 표의
  ADR 행은 기존 ADR의 부적합·잠정값 정산·결정 뒤집힘·코드 확인만 다룬다. DD-73의 사전 심사 뒤에도
  미기록 ADR이 사후 발견되는 사례가 1건 생기면, 그때 별도 발견→갱신 행을 추가할지 판단한다.
- verify.md는 실패 이력·감리·회고 절을 영구 보존해 무한히 자란다. resume은 유계 투영으로
  보호되지만 retrospector는 제품층에서 모든 verify.md를 통독한다.
- Layer 0는 문서마다 따로 착지하므로 arch.md만 커밋된 채 세션이 죽으면 resume은 설계 구역
  갱신으로 보내는데 arch의 건너뛰기 게이트는 `Layer 0 완성`이 조건이라 거짓이 되고 1~5단계를
  다시 돈다. 결과는 옳다 — 그 실행이 빠진 code-style.md를 실제로 만든다. 비용은 기본값이 붙은
  질문 묶음을 한 번 더 확인하는 마찰뿐이라 라우팅 행을 늘리지 않았다. 재인터뷰가 실제
  부담으로 관찰되면 그때 검토한다.
- **능력 은퇴가 능력 간 `의존`을 고립시킨다** (v0.12.0 동선 워크가 찾았고 거기서 고치지 않음).
  은퇴 폴더 밖의 카드가 그 안의 카드를 `의존`으로 지목하면 정합성 4번 이상이거나 영구 미준비가
  되는데, 은퇴는 `재분할 대기` 마커를 만드는 것이 명시적으로 금지돼 있어 아무것도 고치지 않는다.
  기존 결함이고 동선 축과 무관하다 — 은퇴가 의존자를 다시 쓸지 사용자가 재활성화할지는 별도 결정이
  필요하다.
- **터미널 둘이 journal로 서로의 폐쇄를 막는다** — 한 터미널의 미커밋 `유지보수 라우팅 대기` 줄이
  다른 터미널의 능력 폐쇄를 설명 불가한 정합성 이상으로 만든다. 안전하고(잃는 것이 없으며 엄격한
  접두 구간 안전 장치가 작동한 것) 사용자가 읽을 수 없는 멈춤일 뿐이다. 실제로 만나는지 지켜본다.

- **동일 완료 신호를 공유한 원 카드·수정 카드의 이중 label** (v0.15.0 감사 C2) — 수정
