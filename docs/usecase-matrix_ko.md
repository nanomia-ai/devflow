## 0. 이 문서의 렌즈

devflow의 존재 목적: **사람이 AI와 작업하며 쌓는 개발 데이터를 자동으로 축적하고,
그것을 다음 AI가 이해할 수 있게 만드는 것.** 모든 판정은 소유자가 준 세 축으로 한다.

```
① 내구성   이 변수에서 크게 망가지지 않는가 — 특히 데이터가 절대 누락되지 않는가
② 토큰     AI가 진입할 때 지나치게 소모하지 않는가
③ 분별     남겨야 할 기록과 아닌 것을 옳게 가르는가
```

판정 어휘: **정합**(세 축에 든다) · **긴장**(비용이 있으나 설계가 이유를 기록했다) ·
**공백**(설계에 답이 없다). 릴리스 플랜이 닫기로 한 칸은 `[예정]`으로 표시했다가 구현
대조 후 전환한다(0.14.0분은 전환 완료). 크게 망가짐의 정의는 ①의 위반, 그중에서도 조용한 자료 소실이다.

③의 정본 원칙(v0.14.0에서 확정): **변경의 크기가 아니라 남는 지식의 유무로 가른다.
diff가 이미 완전한 기록인 변경은 커밋으로 끝낸다. 향후 판단을 바꿀 수 있는 것 —
전이·결정·함정 — 만 문서로 올린다.**

### 3.15 H13·H43·H44·H45×A7·A13 — 실제 검증과 수리 재발 [5판 신규·11판 영향 칸 재판정]

정본 카드 번호 순서로 상속한다. 사람이 비카드 route를 승인한 라운드는 재관측 수에는 남지만
상속할 수리 라운드에서는 건너뛰고, 다음 non-pass도 사람 관문으로 돌아간다. A13 중단 재진입은
result commit 전이면 전체 verify를 다시 하고, commit 뒤면 저장된 신호 카드·root·재관측에서
재실행 없이 route를 복원한다. 검증 시 확인할 것: 새 root·재관측 1·2+·mixed root·rootless·
한 label의 root 2개 차단·C1+C2+C3 상속·비카드 route 건너뜀·정본 순서 fixture가 모두 통과하고,
사람 승인 없이 재관측 2+ 자동 카드가 0이다.

2026-08-23 v0.19.0 구현 대조에서 검증 장면의 경계를 시도한 시나리오 단계 하나로 고정했다.
한 클릭에서 함께 본 빈 화면·콘솔 오류·응답 없는 요청은 주 실패 하나의 근거와 재현 본문에
남아 출처 id와 root 하나를 만들고, 따로 시도해 독립적으로 재현된 단계만 별도 항목이 된다.
화면 채널은 실제 요소 값 읽기와 실제 상호작용 변화가 모두 기록된 경우에만 확인되며, verify가
기존 arch.md의 이 두 근거도 다시 확인한다. 시나리오 실행 전에 채널 획득이 실패하면 정확한
명령과 timeout을 `Executed:`에 커밋하되 제품 사실이 아니므로 실패 이력·카드·수리 계보에는
넣지 않는다. 상태 도구는 그 결과의 자동 재시도와 자동 제품 감리·회고를 억제하고 사람의 직접
능력 검증 또는 명시적 제품 검증 요청만 새 실행을 연다. 그동안에는 같은 Record에서 정확한
대상·verify 경로·실패 명령·timeout을 사람 대기 상태로 투영해, 자동 재실행을 없앤 결과가
다음 세션에서 사라지지는 않게 한다. 검증 시 확인할 것: 한 시도 다중 신호가
항목 하나이고 독립 시도 둘은 둘이며, 옛 채널 기록이 실제 두 프로브 없이 통과하지 않고,
`channel unavailable` 뒤 자동 재실행·자동 카드·새 root가 모두 0인 fixture가 통과한다.

머리말을 달고 형식을 놓친 줄은 조용히 안 읽히는 대신 `integrity.shape`로 그 카드 경로·구역·사유를
내고, 빠진 완료 증거(`carry`·완료 신호·검토·HANDOFF)는 그 경계의 승객이 커밋하기 전에 이름으로
나온다. **막지 않는 채널로 낸다**는 것이 이 판정의 값이다 — 사람의 산문은 계속 사람의 것이고
기계의 근접 실패만 보인다. 검증 시 확인할 것: 머리말 넷 각각의 근접 실패 fixture가
`integrity: kind=shape`를 내면서 `blocking=0`을 유지하는지, 그리고 증거가 빠진 카드의 경계
계산이 빠진 항목 이름을 빠짐없이 내는지. **미검증**: 이 투영을 실제로 읽은 세션이 커밋 전에
행동을 바꾸는지는 관측하지 않았다.

### 3.23 A3·A6·A17 — T-하 카드 입력과 완료 신호 산출물 책임 [13판 신규]

```
백업·내보내기 카드가 자동 기준선 문서만 이름 대고 저장소 소비 경로와
"현재 상태를 먼저 소비한다"는 제약을 빠뜨린 채 T-하 실행 준비가 된다.
완료 신호는 작업 전용 fixture 경로를 부르지만 목적지는 그 파일을 산출물로 소유하지 않는다.
```

**정합(문서 계약 + 저장소 gate)** (2026-08-23 v0.19.0). direct는 확정된 제공자·현재 소비자를
쓰는 T-하 카드에 최소한의 유계한 구체 코드 경로와 필수 순서·데이터 흐름 제약을 요구하고,
실제 그린필드·독립 작업만 명시적 해당 없음 형식을 쓴다. work는 대기 카드 점유와 점유 카드
재개 전에 이를 검사해 부실한 카드를 기존 direct 수리 경로로 돌려보낸다. 완료 신호는 기대 관측과
그 관측이 무엇을 증명하는지 말하고, 이름 댄 작업 전용 테스트·fixture 경로는 목적지의 정확한
산출물이어야 한다. 작업 전용 경로가 없는 넓은 suite 명령은 경로 선언에서만 면제되며 suite
전체 열거를 요구하지 않는다. 복합 카드는 여러 능력에 영향을 줄 수 있고, 경로 전수·능력별 카드
분리·도메인 진실 복제는 모두 금지된다. 검증 시 저장소 invariant fixture가 direct와 work의 두
소비자 계약, N/A 둘, 백업·내보내기 실패 모양, fixture 산출물 책임, 넓은 suite 면제를 함께
고정하는지 확인한다. **미검증**: 실제 T-하 제품 카드가 이 사전 점검으로 direct에 돌아가는
행동은 제품 simulation을 실행하지 않았다.

### 3.24 H2×A3·A10·A17 — 명시 Adopt의 기존 프로젝트 역산 [14판 신규]

```
유지 문서 또는 코드가 이미 크지만 현재 `.devflow` 루트와 현재 index 항목은 없는 저장소에서
사용자가 devflow:adopt를 직접 지목한다.
```

**정합(정적 계약)·실행 미검증** (2026-09-06 v0.23.13, DD-103 지식 착지·DD-106 반증 수렴 정정). 상태 도구만
`setup.unmanaged`를 증명하고, 명시 Adopt는 Principles나 Resume의 사전 분류 없이 그 상태를
직접 소비한다. SessionStart는 `.devflow/project/product.md`가 없으면 침묵하므로 빈 `.devflow/`
폴더만으로 Resume 안내가 살아나지 않는다. 정본 상태는 현재 `.devflow` 루트가 있거나 현재 index에
`.devflow` 항목이 있으면 부분 상태를 보호하고, 둘 다 없을 때만 무관리로 본다. 다른 ref의 이력과
shallow 여부는 멤버십을 바꾸지 않으며 index 관찰 실패는 보수적으로 `no-product`에 남는다.
devflow 이전의 유지할 프로젝트 자료가 전혀 없을 때만 Product로 가며,
문서나 코드의 존재 자체를 능력 증거 완료로 간주하지 않는다.
Adopt는 모든 유지 구현·테스트·API·스키마·설정·문서·명세·운영 기록을 실제 좌표와 함께 조사하고,
지식 단위와 보조 증거 묶음마다 이름 난 정확한 소유자 문서/K 경로·보조 증거·
대체/모순·이유 있는 비도메인 제외·드러난 미해결 중 하나를 부여한다. 원자료 하나가 여러 단위를
뒷받침할 수 있지만 같은 단위를 여러 현재 정본에 흩뜨리거나 복제하지 않는다. 외부 진입점·상위
모듈·서비스 경계에서 찾은 코드 기반 후보마다 한 실행 흐름을 추적하고,
유지 도메인 문서에만 존재하는 후보는 그 출처를 드러내되 실행 증거를 지어내지 않는다. 그 증거로
Product, Architecture, 해당 시 Design, code style, glossary, 능력 설계 구역과
깊은 영속 지식에 필요한 모든 소유자 인접 K를 한 제안으로 역산한다. K가 0개라면 모든 지식
단위가 상시 읽는 정본 소유자 문서의 정확한 자리에 완전히 착지했음을 보여야 한다. `Brownfield`는 도입 전 실행 구현의
존재만 기록하므로 문서 전용 프로젝트는 `no`다. 사람이 답할 것은 증거로 닫히지 않는 결정과
모순뿐이다. 구속 질문 전에는 전체 초안·단위별 처분과 정확한 target·load-bearing 좌표·Adopt 5단계가 연 동일 공통 기준선·지식 절(Foundation 범위 포함)·Arch
verification-channel 표의 Surface/Required channel 열과 첫 proposal·ADR 조건만 받은 clean context가
한 번 의미를 반증한다. 실제 wrong
action, 결정/기각 방향 소실, wrong owner, 필수 단위 미착지·현재 target 분산/복제, verification means 누락, 연 절에서 벗어난 문서 구조를 만드는 뒷받침된 모순·누락만
막는다. 최초 전수 반증은 한 번이고, 현재 권위로 모든 차단 원인을 고칠 수 있을 때 `revise`가 초안을
고친 뒤 반환 좌표·변경 target·직접 영향만 독립 재검사한다. 같은 원인의 제거 또는 엄격한 축소가
증명되는 동안만 계속하며 진전 없음·퇴행·닫힌 실패 재발, 사람 결정·권위 모순, 필수 초안·출처·직전
증거·clean context 부재는 막는다. Missing-channel action 열·producer transcript·이전 audit 결론·그 밖의
Arch 실행/검증-run/승인/쓰기/commit 지시는 입력하지 않는다. 반증 판단 상태 중 clear만 구속 질문과
승인 쓰기에 도달하며 revise는 같은 판단으로 돌아오고 blocked는 제안 앞에서 멈춘다. Product `C<n>`과
disk `NN`은 명시적으로 다른 좌표다. 구속 확인 전 쓰기 0, 거절·승인 전 중단 시 쓰기 0이다. 승인 하나 아래 후속
요청, Layer 0 소유자 문서(`product.md`가 문서 중 마지막), Product·Architecture·Design 소유 K를 쓰고 검증해
`adopt — layer 0`으로 먼저 착지시킨다. 그 커밋을 Design head로 쓴 능력 문서와 능력 소유 K를 쓰고 검증해
`adopt — capabilities`로 함께 착지시킨 뒤 자동 Product·Arch·Design·Direct·
Resume 선택은 0이다. 중단 시 현재 `.devflow` 루트와 index가 모두 없을 때만 무관리 재도출하고,
현재 증거가 생긴 뒤에는 정본 상태가 복구를 소유한다. `product.md` 쓰기와 첫 커밋 사이에는
`setup.layer0-uncommitted`가 marker보다 먼저 서고 Product와 Direct 직접 진입도 선택 route와 별개로
동시에 관찰된 이 setup 사실을 소비해 Resume으로 돌아간다. Direct는 request·research·card 효과를
내기 전에 돌아간다. Product가 없을 때 DD-92의 승인된 `00-project`
연구는 기존 교차-zone 순서를 유지한다. 사람은 정확한 승인 경계를 커밋하거나 폐기한다. 첫 커밋 뒤 두 번째 경계 쓰기 전은
기존 Resume→Arch 기준선 누락 복구다. 관리 상태의 설계 마커와 기준선 갱신은 Adopt를 재개하지 않고
Arch가 소유한다. 검증 시 확인할 것: (a) Codex와 Claude가 같은 직접 호출에서 첫 실행을 Adopt로
고르는지, (b) 빈 `.devflow/`나 Product 질문 없이 실제 조사에 들어가는지, (c) 문서가 방대할 때
모든 유지 자료가 처분되고 Product·Architecture·Design·Capability 소유자 모양의 문서/K tree와
`project --under` 색인이 이후 차가운 유지보수 세션에 충분한지, (d) 관리
상태 설계·기준선·지식 경로에 순환이 0인지와 Arch가 과거 `adopt`·현재 `arch` writer를 모두
출처 그대로 처리하면서 기존 단위를 제자리에서 갱신하고 유효한 출처와 미선택 마커를 보존하는지, (e) 후속 작업이 함께 요청되면 도입 커밋
경계에서 전체 요청이 보존되는지, (f) 문서 내부 상태·코드/테스트/운영 증거·경로·Git 이력·수정
시각을 함께 써서 구현/기획/리서치/대체 기록을 구분하되 이름이나 시각만으로 권위를 정하지 않고,
증거로 닫히지 않는 현재 의도 충돌만 정확한 좌표와 질문으로 사람에게 보내는지, (g) 두 커밋의 K가
각 소유자 문서 경계와 함께 착지하고 능력 문서의 Design head가 현재 값과 일치하는지, (h) 단위별
정확한 target과 Foundation 범위를 포함한 반증 입력·차단 기준·진전 기반 revise/유계 인과 재검사·
Evidence verification 기록이 지켜지고 미착지·분산·복제 finding이 남으면 구속 질문이 나오지 않는지.
사용자가 새 설치 뒤 테스트 브랜치에서 직접 확인하기로 했으므로 이 실제 행동은 **미검증**이다.

**정합 유지 — Adopt가 작업 언어를 쓰기 전에 제안하고 소유자 교정을 재제안한다**
(2026-09-07 v0.23.15 DD-107). Adopt는 전 자료 처분과 같은 유계 inventory에서 유지 문서·코드 주석·
명세·운영 기록의 의미 있는 사람 산문을 보고 우세 작업 언어를 제안한다. 명시 소유자 언어가 우선하고
식별자·경로·생성물·vendor text는 표에서 빠지며, 동률·실질적 다국어·희박·부재 근거는 불확실성으로
드러낸다. 제안서와 파생 Product 모두 같은 `Working language:` 값을 쓰기 전에 보여 준다. 교정은
승인이 아니며 Adopt는 수정한 전체 제안에 새 독립 의미 반증을 거친 뒤 기존 `prepare`의 REPORT→ASK
재진입으로 돌아간다. approve 전 WRITE·COMMIT은 0이다. Product의 새 프로젝트는 기존 ask 재진입으로
같은 확인을 한다. 기존 관리
프로젝트는 이 줄 부재만으로 차단하거나 이관 쓰기를 하지 않는다. 검증 시 확인할 것: 언어 제안·교정·
재제안 뒤에만 승인 쓰기가 열리고, 다국어·동률·희박·명시 선호 fixture에서 거짓 다수와 식별자 투표가
없는지. 실제 브라운필드 fresh-model 추론과 줄 부재 legacy artifact의 언어 보존은 이번 표적 검증
밖이므로 `unverified`다.

### 3.25 H51×A10 — 패키지 정보와 현재 프로젝트 작업의 진입 경계 [16판 신규]

```
devflow로 관리하지 않은 저장소에서 사용자가 설치된 devflow 패키지의 버전을 묻는다.
```

**정합(정적 계약)·모델 실행 미검증** (2026-09-03 v0.23.1). 패키지 정보 확인은 현재
프로젝트를 devflow로 운용하려는 의도도, 공통 작업 규약을 이 프로젝트에 적용하는 질문도 아니다.
SessionStart는 `product.md`가 없어 침묵하고, Product는 새 프로젝트 제품 기획 목적만 말하며
Principles를 일반 언급의 소유자로 지목하지 않는다. Principles의 선택 설명은 단계 이름 없이 현재
프로젝트를 devflow로 운용·재개·복구·점검하려는 의도 또는 공통 작업 규약의 적용 질문만 받는다.
따라서 설치 메타데이터를 보통의 읽기 전용 자료로 확인하며 devflow 단계는 발동하지 않는다.

이 선택 경계와 공통 규약 소비는 서로 독립이다. Product·Adopt를 포함해 이름을 명시한 단계가
실제로 들어오면 각 단계의 항상 읽는 purpose가 Principles의 정책 색인 하나를 열고, 첫 판단 전의
항상 적용 행과 요청·단계·관찰 입력·요청된 판단·결정된 값에 이미 해당하는 행만 읽는다. 반환된 Decision의 효과가 새
조건을 드러내면 첫 효과 전에 같은 색인에서 그 행만 추가로 읽는다. 이는 Principles 분류기로
재진입하거나 정책 tree 전체를 읽는 일이 아니다. reviewer·verifier·auditor·retrospector 역할은
coordinator가 고른 원문 계약만 받아 이 일반 단계 진입도 우회한다. 설치 후 같은 질문을 새 Codex와
Claude에 직접 물어보는 실사용은 사용자가 수행하기 전까지 **미검증**이다.
