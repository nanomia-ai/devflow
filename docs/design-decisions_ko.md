# devflow 결정과 기각 계보

이 파일이 결정의 유일한 집이고, 결정 색인은 여기서 생성된다(`node scripts/decision-index.mjs --lang ko`). 주제마다 그 주제의 결정 전문과 그 주제에서 기각된 안이 함께 산다 — 결정을 뒤집는 것과 기각안을 재제안하는 것이 같은 관문이기 때문이다.

**결정을 뒤집으려면 기록된 이유부터 반박한다. 기각된 안을 재제안하려면 기록된 기각 사유부터 반박한다.**

### DD-71 · 저장소 유지보수의 상시 진입은 design 전문과 원문에서 생성된 결정 색인이고, AGENTS가 상세 절차를 조건부로 배선한다. 이력은 온보딩이 아니다 (v0.16.2)

주제: 정체성 · 배포 · 플랫폼 | 도입: v0.16.2 | 상태: 유효 · 일부 정정 → DD-84 (v0.19.0)

관찰된 문제: 새 유지보수 세션은 자동 진입 `AGENTS.md` 30,716B와 항상 읽는 `design.md`
20,080B를 먼저 지불했고, 구조를 이해하려고 README 42,569B·CHANGELOG 63,177B·라운드
기록을 더 순회했다. Claude 기준선은 68,773 input-token cache 생성과 180.3초를 쓰고도 entry
skill 원문의 대부분을 열지 못했다고 보고했다. Codex의 기본 프로젝트 지침 한도 32KiB에도 루트
AGENTS 하나가 거의 닿아 하위 지침이 조용히 잘릴 여지가 있었다.

v0.19.0의 두 번째 관측: 그때 세운 구조가 결정 색인을 `design.md` 안의 **수동 표**로 남겨
두었고, 그 표가 세 가지를 낳았다. ① 원문과의 **8/80 표류** — 80행 중 8행의 문장이 결정 원문
제목과 달랐다. ② **예산 충돌** — 항상 읽는 고정량 32,679 B(AGENTS 6,136 + design 26,543) 중
14,012 B가 그 표였고 상한 26 KiB에 남은 자리가 81 B였다. v0.18.9의 결정 두 건이 행을 못 넣어
그 이유가 라운드 기록에 갇혔다. ③ 그 구조는 결정 수에 비례해 **항상 읽는 문서**를 키웠다.
따라서 이 결정의 상시 진입은 색인을 손으로 나르는 자리가 아니다.

v0.19.0 전후 실측(결정 80 → 84): 상시 진입량은 32,679 B에서 **31,370 B**로 바뀌었다
(AGENTS.md 6,136 → 6,142 · design.md 26,543 → 13,331 · 생성 색인 11,897). **바이트 감소는
1,309 B로 작다** — 이 변경의 산출물은 축약이 아니라 한 집·표류 0·그리고 결정 수에 비례하는
증가를 고정 크기 `design.md`와 그 26 KiB 상한 **밖으로** 옮긴 것이다. 생성 색인은 계속 상시
진입이며, 한 행당 비용은 175 B에서 141.6 B로 내려갔다.

원하는 동작: 새 세션은 전체 철학·구조·불변식·결정과 각 스킬의 존재 이유를 먼저 이해하고,
구체적 변경이 생기면 그 영향 범위의 실제 원문을 빠짐없이 연다. 역사와 조건부 운영 절차는 필요할
때만 읽으며, 이해도가 기존보다 낮아지면 토큰 절감과 무관하게 개편을 거부한다.

선택한 경계: **상시 진입은 `design.md` 전문과 `node scripts/decision-index.mjs` 출력 둘이다.**
`design.md`가 유일한 전체 의도 지도이고, 결정 색인은 그 안의 표가 아니라 결정 원문의 읽기 전용
투영이며 그 이유는 DD-84가 소유한다. `AGENTS.md`는 6KiB 이하의 자동 진입 게이트·배선만
소유한다. 상세 절차는 한 쌍의 `maintenance-protocol`에 절별로 살며 모든 절은 루트 배선에서
도달 가능해야 한다. README·CHANGELOG 전체·여러 라운드·blueprint는 온보딩이 아니다. 수동
`CURRENT.md`, 별도 maintenance map, 자유 메모층은 만들지 않는다. 생성 명령은 문서 역할이
아니므로 문서 지도에 새 집을 얻지 않는다. 실제 affected skill 원문을 읽기 전에는 지도만으로
삭제·이동·통합을 판단할 수 없다.

필요한 이유: `design.md`는 이미 origin·구조·문서 지도·불변식·스킬 의도 색인을 소유하고, 결정
색인은 그 원문에서 투영된다. 별도 지도를 추가하면 DD-28이 막은 두 번째 지식층과 신선도 경합이
생긴다. 반대로 AGENTS 안에 모든 세부 절차를 남기면 어떤 작업도 쓰지 않는 번역·라운드·README·
릴리스 규율을 매 세션 다시 지불한다. 이 경계는 의도 한 곳과 절차 한 곳을 유지하면서 읽기만
조건부로 만든다.

기각한 대안: 스킬 원문 축약·분할은 이 결정의 범위 밖이고 별도 세션에서만 다룬다. AI가 쓴 종합
요약과 `CURRENT.md`는 갱신 누락이 조용한 오판을 만들며, 새 maintenance map은 design과 같은
개념을 두 집에 둔다. README나 CHANGELOG를 온보딩 문서로 줄이는 안은 사람용 설명과 배포 이력을

### DD-79 · README는 사람의 문서이고 AI의 읽기 집합 밖에 산다 — 읽지도 갱신하지도 판정 근거로 삼지도 않으며, 이 선은 README가 돌아온 뒤에도 그대로다 (v0.18.5)

### DD-80 · 기계 판정의 실행자는 코드이고, 그 판정을 적은 문서는 마지막 런타임 독자가 옮긴 다음 릴리스에서 삭제된다 (v0.18.7)

주제: 정체성 · 배포 · 플랫폼 | 도입: v0.18.7 | 상태: 유효 · 일부 정정 → DD-83 (v0.19.0)

관측된 문제: `resume` 진입이 대상 프로젝트 파일을 한 글자 읽기 전에 정본 넷 **137,514 B**를
낸다(0.18.6 실측 — resume 30,477 + principles 67,498 + 상태 판정 정본 2,114 + 검증 판정 정본
3,495 + 기준선 판정 정본의 캡슐 게이트 밖 33,930). 그 정본의 대부분은 모델의 판단을 요구하는
규칙이 아니라 **디스크와 Git 사실만으로 참·거짓이 갈리는 계산**이다 — 정본 295행을 전수
분류하니 도구가 실행할 수 있는 것이 221행, 사람에게 하는 말과 의미 판단이 23행, 대화·승인이
걸리는 경계가 51행이었다. resume의 라우팅 표 48행 중 **대화 내용을 읽는 행은 한 줄**뿐이다.
그리고 그 계산은 산문이 문자로 적어 두었기 때문에 모델이 손으로 실행한다 — 「NUL로 나눠라,

원하는 행동: 그 계산을 읽기 전용 도구가 실행한다. `resume`은 도구를 **한 번** 부르고, 도구가
낸 상태 한 장에서 첫 번째로 비어 있지 않은 구역의 **행동측만** 산문에서 읽고, 보고하고,
승인을 받고, 스테이지를 부른다. 정본세는 없어지는 것이 아니라 **승인 뒤 실제로 진입하는
스테이지가 낸다.**

고른 경계 넷:

① 도구는 **정본과 같은 자리**(`skills/principles/scripts/project-state.mjs`)에 산다 — 정본을
부르는 것과 같은 상대 경로 규칙으로 닿고, 세 설치 채널 모두에서 정본과 함께 여행한다.
v0.18.6이 여덟 자리에서 없앤 `<플러그인 루트>` 해석 결함을 새 자리에 다시 만들지 않는다.

② 도구가 소유한 판정의 내부를 산문이 **재서술하지 않는다**(`baseline-predicates.md:348-349`가
캡슐 도구에 이미 쓴 문장).

③ **마지막 런타임 독자가 도구로 옮겨 간 릴리스의 다음 릴리스에서 그 술어 문서를 삭제한다.
과거는 git이 진다.** 사람에게 하는 문장·의미 판단·승인 규율은 산문의 소유다.

④ **도구는 사실을 내고 대화를 받지 않는다.** 부름은 `state` 하나이고 입력은 `--root`와
필터 하나(`--capability`)뿐이다. 출력은 우선순위 순 **구역 열넷**이고 **빈 구역도 줄을
찍으며**, 맨 끝의 `next:`는 첫 번째로 비어 있지 않은 구역과 그 종류다 — 사실에서 파생한
요약이지 계약이 아니다. 세션이 아는 것(지목된 카드·미룬 것·이 대화의 요청)은 도구에
부호화해 넘기지 않고 모델이 쓴다.

v0.19.0의 부분 정정(DD-83): 읽기 전용·무상태는 그대로이고, ④의 입력과 출력 계약만 좁혀졌다.
소비자가 하나도 없던 `--card`는 제거한다 — 파싱만 되고 아무 판정도 바꾸지 않았다.
`--capability`는 **판단 전 snapshot 필터가 아니라 판단 뒤 render 필터**다: 전역 정합성은 항상
전체 snapshot으로 계산하고, claim·ready·blocked·layer·carry처럼 능력별인 줄만 렌더에서
좁힌다. 단, 값비싼 능력 문서 detail은 전역 소비자가 없으므로 번호를 받았을 때 그 능력 하나만
계산한다. git·integrity·transition·marker·setup·request·event·product·complete 사실은 좁히지
않으며, 실제로 줄 것이 없으면 거짓 재호출 권고 대신 `narrow=none`을 보인다. 그리고 경계
완전성의 `missing`·`carry`와 `digest`·`origin`은 새 판정이 아니라 **같은 디스크·Git 사실
방출의 확장**이다.

왜 그 경계가 필요한가: 재서술을 허용하면 문서와 코드가 갈리고, 갈린 순간 어느 쪽이 정본인지
알 수 없다. 「사양서로 남긴다」는 두 번째 거처이고, 두 거처가 생기는 순간 그 둘을 묶을 기제가

④가 필요한 이유는 따로다: 세션 사실을 플래그로 부호화하려면 모델이 그 사실을 **먼저 기억하고

### DD-82 · 정본 두 규칙이 한자리에서 다른 행동을 가리키면 양쪽 원문과 택한 쪽을 보고하고 계속한다 (v0.18.9)

주제: 정체성 · 배포 · 플랫폼 | 도입: v0.18.9 | 상태: 유효

관측된 문제: 첫 실사용 시험에서 산문 대 산문 충돌이 일곱 장면 나왔다 — 같은 ADR 세 조건으로

원하는 동작: 두 정본 문장이 함께 적용되고 서로 다른 행동을 내면 조용히 고르지 않는다. 양쪽

필요한 이유: 이 규칙은 새것이 아니다. `AGENTS.md` 「Hard boundaries」의

확인 → 착지). **산문 대 산문에는 그 기계가 없었다.**

기각한 대안: **멈춘다** — 산문 충돌 하나마다 세션이 서고, 그것이 이 계보가 고치려는 병(하네스가
제품 작업을 잠그는 것)을 새로 만든다. 멈춤은 기존 게이트(Layer 0 변경 확인·binding decision)가
정한다. **DD-11로 덮는다** — DD-11은 **문서 사이의** 모순을 다루고 이 결정은 **정본 자신의 두
규칙이 함께 적용되는 경우**를 다룬다. DD-11은 움직이지 않는다.

영향 좌표: `skills/principles/SKILL{,_ko}.md`, `docs/rounds/v0.18.9/report_ko.md` §4.
재검토 조건: 보고만 하고 계속한 선택이 실제로 잘못된 산출물을 낳은 장면이 관측될 때.

### DD-83 · 정본이 이미 고정한 전이의 완전 상태와 디스크의 차이를 한 읽기 전용 계산이 진입과 각 승객의 커밋 직전에 보인다 (v0.19.0)

주제: 정체성 · 배포 · 플랫폼 | 도입: v0.19.0 | 상태: 유효

관측된 문제: 첫 실사용의 81 커밋을 대조했더니 **자기 산출물과 자기 커밋을 가진 의무는 한 번도
안 빠졌고**(카드 상태 rename · task 커밋 · `verify.md` · 진행 로그 · 커밋 메시지 형식),
**남의 커밋에 얹혀 가는 의무만 마모됐다**(다이제스트 marker 전진 · HANDOFF 갱신 · 최종 카드의
`carry:` · arch 채널 확인). 정본은 HANDOFF를 스스로 *"it only rides here"* 라고 승객으로
배선한다. 무효인 전제는 「AI가 규칙을 따른다」가 아니라 **「명확하게 쓰면 실행된다」**였다 —
같은 기록에서 세션들은 자기에게 불리한 규칙 넷을 정확히 지켰다.

원하는 동작: 의무마다 규칙이나 커밋을 늘리지 않는다. 정본이 이미 열거한 전이의 완전 상태와
현재 디스크 상태의 차이를 도구가 보여 주고, 모델이 그 사실을 보고 의미를 판단해 행동한다.

선택한 경계: 하나의 계산
`정본이 이미 고정한 전이의 완전 상태 − 현재 디스크 상태 = missing` 을 세션 진입과 각 승객을
실을 커밋 직전에 쓴다. 진입에서 부르면 **이미 빠진 것을 발견**한다. 최종 작업 커밋 직전에는
현재 점유의 `carry=absent|present`를, 경계 정리 커밋 직전에는 `missing=[carry|handoff]`를 보고
**각 탈것이 떠나기 전에 막는다.** 기존 출력 종류에 사실 필드를 붙인다(`finish-boundary missing=[…]` ·
`claim.mine carry=absent|present` · `layer.children-done carry=N`). 새 출력 종류는 디스크에
별도 대상이 있는 `ready.digest-behind` 하나만 허용한다. **도구는 rename·기록·stage·commit을
실행하지 않는다** — DD-80 ④의 읽기 전용·무상태가 그대로다. 기록은 새 필드를 복사하지 않고
기존 사실에서 투영한다: `report: origin=…` 은 카드 생성 커밋과 그 커밋에서 삭제된 요청·층
열기 표식에서 계산하고, 원래 입력이 없으면 `none`, 얕은 이력이나 다중 매칭이면 이유와 함께
`unknown` 이다. 카드에 새 `Origin:` 의무는 만들지 않는다.

필요한 이유: 관측된 실패는 전부 **감지 자체가 0**이었던 장면이다. 감지가 0인 곳에 쓰기 권한을
늘리면 해결되는 것은 없고 권한·입력·호출 의무만 새로 생긴다. 같은 계산을 진입과 각 실제 커밋
경계에 쓰면 복구와 예방이 한 정의를 공유하고, 승객을 실을 커밋이 떠난 뒤에 검사하는 한 커밋
늦은 경로도 남지 않는다.

기각한 대안: **별도 boundary writer**(도구가 rename·기록·commit을 실행) — 통합 merge/rebase를
품지 못하고, 새 권한·입력·호출 의무를 만들며, 지금 증거로는 추가 값이 없다. 사용자 선택이
아니라 증거상 열등한 안이다. **다시 여는 조건**은 실사용에서 「도구가 누락을 정확히 잡았는데
같은 세션이 경계를 닫지 못했다」가 실제로 나오는 것이다. **상태 조회의 쓰기 겸용** — 읽기
전용이 이 도구의 정체성이므로 한 부름 안에서 겸하면 그 정체성이 사라진다. **의무마다 새 국소
규칙** — 마모의 원인이 규칙 부족이 아니라 관측 부재라는 위 진단을 정면으로 부정한다.
**카드 `Origin:` 필드** — planning commit 성공과 무관한 새 승객을 하나 더 만든다.

영향 좌표: `skills/principles/scripts/project-state.mjs`, `scripts/project-state.test.js`,
경계 사실을 읽는 `skills/{work,split,verify,resume}/SKILL{,_ko}.md`.
재검토 조건: 위의 writer 재개 조건이 실사용에서 관측될 때. 또는 `missing` 이 실제로는 안 빠진
것을 빠졌다고 불러 세션이 헛일을 하는 장면이 나올 때.

### DD-84 · 결정 색인은 원문에서 생성되는 읽기 전용 투영이고, 수동 표는 사라진다 (v0.19.0)

주제: 정체성 · 배포 · 플랫폼 | 도입: v0.19.0 | 상태: 유효

관측된 문제: `docs/design{,_ko}.md` 의 80행 수동 결정표는 `docs/design-decisions{,_ko}.md` 의
제목과 같은 사실을 두 번 적었고, 실제로 갈라졌다 — 80행 중 **8행**이 원문 제목과 문장이
달랐다. 다섯(DD-65·71·72·78·79)은 표가 더 많은 의미를, 셋(DD-74·75·80)은 원문이 더 많은
의미를 가졌다. 그리고 표는 예산에 부딪혔다: `design.md` 26,543 B에 고정 상한 26 KiB, 남은
자리 **81 B**, 한 행 약 200 B. v0.18.9의 결정 두 건이 행을 못 넣어 그 이유가 라운드 기록에
갇혔고, 시험 주석은 *"do not raise these again to fit one more row"* 로 상한 인상을 이미
금지해 두었다.

원하는 동작: 한 사실은 한 집에 산다. 결정을 소유하는 곳은 결정 원문 하나이고, 색인은 그
원문에서 계산된다. 새 결정은 원문 한 곳만 늘린다.

선택한 경계: 읽기 전용 `node scripts/decision-index.mjs` 가 결정 원문의 제목과 metadata를
파싱해 주제별로 묶은 `ID | 결정 | 상태` 완전 색인을 출력한다. 기본은 영어이고 한국어 원문은
`--lang ko` 로 고른다. `docs/design{,_ko}.md` 에서 수동 표와 그 표를 손으로 유지하라는 문장을
제거하고, origin·철학·구조·문서 지도·불변식·스킬 의도 색인은 전문 진입에 그대로 남긴다.
표를 지우기 전에 **표가 홀로 가졌던 의미를 원문 제목에 합쳐 내용 손실을 0으로 만든다.**
생성 명령은 문서 역할이 아니라 원문의 투영이므로 문서 지도에 새 집을 만들지 않는다. 24 KiB는
실패 상한이 아니라 관측 경고다 — 넘으면 stderr에 경고하되 완전 색인은 자르거나 막지 않는다.

필요한 이유: 8/80 표류는 「한 사실 두 집」의 예정된 결과이고, 색인이 원문의 함수가 되면 그
표류의 경로 자체가 없어진다. 81 B 충돌도 같은 뿌리다 — 항상 읽는 design 문서가 결정 수에
비례해 자라는 구조였기 때문이고, 투영은 그 비례를 **고정 크기 `design.md`와 그 26 KiB 예산
밖으로** 옮긴다. 생성 색인 자체는 계속 상시 진입에 속한다.

기각한 대안: **수동 색인 파일 하나를 새로 만든다** — 두 집이라는 문제를 그대로 두고 파일만
하나 늘린다. **원문 파일 앞머리에 큰 색인 블록을 손으로 붙인다** — 같은 표류가 같은 방식으로
돌아오고, 결정 원문을 여는 비용에 색인 비용이 붙는다. **중복 열만 지운다**(주제·도입 열 삭제)
— 표류의 원인은 열 수가 아니라 같은 사실을 손으로 두 번 적는 것이므로 8/80이 다시 생긴다.
세 대안 다 원문 하나를 색인의 유일한 원천으로 만들지 못한다. **전체 다섯 열 투영** — 같은 84 결정에서
15,166 B로 채택한 주제별 투영 11,897 B보다 크고, 도입 버전은 움직이는 행의 원문을 열면
metadata가 바로 준다.

영향 좌표: `docs/design{,_ko}.md`, `docs/design-decisions{,_ko}.md`(제목 병합),
`AGENTS.md` 진입 게이트 1과 배선 첫 행, `docs/maintenance-protocol{,_ko}.md` §8,
`scripts/decision-index.mjs`(신규), `scripts/repository-invariants.test.js`.
재검토 조건: 24 KiB 경고가 실제로 난 출력에서 깨끗한 Claude·Codex 진입이 완전 색인을 소비하지
못할 때. 또는 투영을 못 부르는 진입 경로가 실제로 관측될 때 — 그때 되돌리는 것은 표가 아니라
**부를 수 있는 경로**다.

### DD-95 · 전역 설치된 devflow는 현재 흔적이 없는 저장소에서 침묵하고, 명시 의도와 이력 인식 상태 판정이 도입 경계를 보존한다 (v0.20.0)

주제: 정체성 · 배포 · 플랫폼 | 도입: v0.20.0 | 상태: 유효

관찰된 문제: 전역 설치된 플러그인의 SessionStart가 모든 Git 저장소에 devflow 안내를 넣고,
arch·design·split·work·verify·resume의 일반 개발 어휘와 product·adopt의 넓은 설명이 이를
묵시적 단계 진입으로 바꿀 수 있었다. 상태 도구도 `product.md`가 없는 처음부터 비도입인 저장소와
부분·과거 devflow 저장소를 모두 `setup.no-product`로 합쳐, 안전한 재개 경로가 설치 질문을 할 수
있었다. 이는 DD-92의 재검토 조건인 「지연 안내가 resume과 다른 행동을 유발함」의 실제 장면이다.

원하는 동작: devflow를 도입한 적 없는 보통 프로젝트에는 수동 안내도 남기지 않는다. 명시적
devflow 호출은 언제나 작동하고, 다른 devflow 스킬이 건넨 경로와 기존 관리 프로젝트의 흐름은
그대로 유지한다. 부분·삭제·얕은 이력·판정 실패 상태는 비도입으로 잘못 단정하지 않는다.

선택한 경계: SessionStart는 Git 루트를 찾은 뒤 현재 `devflow` 경로와
`devflow/project/product.md` 존재만 싸게 확인한다. 둘 다 없으면 출력 없이 0으로 끝나며, 하나라도
있으면 기존 주입 바이트를 그대로 낸다. 이 검사는 고정 pointer의 유무만 고르고 index·이력·상태
도구·zone·route를 읽지 않는 약한 비구속 판정이다. arch·design·split·work·verify·resume의 설명은
명시 호출, 다른 devflow 스킬의 route, 기존 devflow 관리 프로젝트만 진입 팔로 둔다. product와
adopt는 직접 호출, devflow 명명, 또는 Layer 0·devflow 능력 문서 같은 devflow 산출물을 요구하는
명시 의도만 진입으로 삼는다.

행동을 정하는 정본 판정은 `project-state.mjs` 하나에 남는다. 현재와 index의 devflow 흔적이 모두
없고, 전체 이력에서 devflow 경로가 없다는 사실까지 증명될 때만 `setup.unmanaged`를 낸다. 과거
흔적은 `setup.no-product`에 남고, shallow·Git 실패·해독 실패·불명확은 모두 기존
`setup.no-product`로 보수적으로 후퇴한다. resume은 domain orientation을 먼저 보존한 뒤
`setup.unmanaged`를 ASK·route·write 없이 한 보고와 DONE으로 끝내며, 사용자가 도입 의도를 밝힌
경우에만 product 또는 adopt를 선택지로 알린다.

경계가 필요한 이유: hook의 오판 비용은 비대칭이다. 관리 프로젝트에서 안내를 숨기는 false
unmanaged는 미지 세션 복구를 끊지만, 애매한 저장소에 안내를 한 번 더 보이는 false managed는
정본 상태 도구가 다음 진입에서 바로 정정한다. 따라서 hook은 현재의 압도적이고 싼 증거만 보고
pointer를 억제하고, index·전체 이력·unknown 판정은 행동을 소유한 상태 도구만 수행한다. DD-92가
막은 것은 hook의 route 판정과 파일 본문 주입이다. 이미 있던 Git-root 존재 검사가 보여 주듯 모든
파일시스템 읽기가 상태 계산이라는 전제는 기록된 이유가 아니며, 이번 경계는 route나 본문을 만들지
않는다. DD-05·DD-20·DD-83·DD-92·DD-93은 각각 훅 하나, 독립 adopt 발견성, 읽기 전용 상태 계산,
상태 소유권, P2 작성 정본이라는 기존 이유와 범위에서 그대로 유효하다.

기각한 대안: 새 init 스킬·도입 marker는 한 사실의 두 번째 집을 만든다. hook에서 index와 전체
이력까지 복제하면 모든 세션의 비용과 두 판정의 표류를 늘린다. 비도입 저장소에 고정된 부정 안내를
넣으면 침묵이라는 결과를 깨고 영구 context 세금을 만든다. `allow_implicit_invocation: false`는 관리
프로젝트의 유효한 선택까지 막는다. product·adopt의 일반 어휘를 그대로 열어 두면 hook 침묵 뒤에도
같은 결함이 두 입구로 되돌아온다.

영향 좌표: `scripts/session-start.js`, 여덟 스킬의 `.skill-rails/intent.json`과 생성 trigger 투영,
`skills/principles/scripts/project-state.mjs`, `skills/resume/spec.mjs`·`body.md`·fixture, 그 seam 시험,
A10(도입 전 또는 오발동) 매트릭스 칸, CHANGELOG. 새 매트릭스 행·용어·marker·init 파일은 없다.

재검토: 현재 devflow 프로젝트가 hook에서 침묵하거나, 명시 product/adopt 호출을 찾지 못하거나,
일반 비도입 요청이 downstream 스킬을 다시 고르거나, hook과 `setup.unmanaged`의 의도된 약한 차이가
pointer가 아니라 행동을 바꾸거나, SessionStart 지연이 유의하게 늘어날 때.

재검증이 이전 `실패 이력`·감리·회고 결과를 지워 최초 폐쇄와 재폐쇄를 구분하지 못했고, 판정 기록 뒤 역할 실행 전에 세션이 끝나면 한 번뿐인 사건이 영구 누락됐다. 같은 초에 여러 실패나 사건이 생기면 timestamp locator가 충돌하므로 각 verify.md 절은 재사용하지 않는 양의 `출처 id`를 부여하고, 채택 소견은 사건 id와 소견 번호의 쌍으로 식별한다. 구형 timestamp 기록은 원문을 보존한 채 파일 순서로 id를 받는다. 실패와 수정 가능한 미검증은 각각 자기 라우팅을 `실패 이력`에 남긴다. 능력층의 실패·미검증과 폐쇄 게이트 실패가 붙은 통과는 라우팅 전에 능력 결과 커밋으로 착지한다. 완성본만 실행 없이 복구하고 부분 작성은 2단계부터 다시 수행하며, 재실행 결과가 깨끗한 통과면 닫기 시작으로 간다. 사건의 `대기`·`결과`·`결정`은 역할 호출·사용자 질문·첫 라우팅 전에 각각 검증 상태 커밋으로 착지한다. 실패·소견 라우팅은 base commit·최종 결과·write/move/delete의 적용 순서를 검증 가능한 `라우팅 준비` 객체로 출력 전에 남긴다. 카드 초안을 포함한 현재 checkout은 그 순서의 정확한 접두 구간이어야 하며, 중단 뒤에는 남은 접미 구간만 적용해 compact 결과와 한 커밋으로 착지한다. 작업 중 요청한 제품 검증과 사건은 현재 점유를 선점하지 않는다. 감리 범위가 정확히 해석되지 않으면 이유를 남긴 완료 상태로 닫아 자동 사건의 영구 대기를 막는다. dirty 경계의 감리 요청과 자동 감리는 보존하되 선택하지 않으며 제품 결과 보고를 막지 않는다. 범위·경계를 교정한 뒤 다시 실행할 수 있다. 한 사건에서 채택한 소견이 여럿이면 소견별 `라우팅: 대기`를 두고 번호순 한 건씩 별도 계획 또는 구속 결정 커밋으로 착지시킨다. 제품 감리·회고의 키는 revision과 무관한 `product`라 각각 한 번만 실행하고, 사용자 요청만 timestamp 키로 반복할 수 있다. 재검증은 실패 이력과 사건 절 전체를 보존한다. 제품층 실패의 수정 위치는 split이 범위에 따라 골조 또는 능력으로 정한다

### DD-68 · 신호 카드는 완료된 수리의 후속 non-pass를 같은 root에 연결하고 직전 수리 증거를 상속하며 재관측 2 이상에서 사람에게 돌아간다 (v0.15.0)

### DD-81 · 채널을 못 얻어 생긴 미검증은 첫 항목부터 사람에게 가고, 사유가 실패한 명령과 timeout을 싣는다 (v0.18.9)

주제: 검증과 역할 | 도입: v0.18.9 | 상태: 유효

관측된 문제: 0.18.8 배포 뒤 첫 실사용 시험에서 세션 B가 81 커밋을 쌓고도 능력을 한 번도 못
닫았다. 편향 제거는 검증을 깨끗한 세션에서 돌리라고 요구하는데, 그 세션이 메인 세션은 이미
성공적으로 몰았던 브라우저 채널을 얻지 못했다. 도구 고장이 제품 실패로 처리돼 수정 카드가
늘었고, 상태 도구는 그 실행 불가능한 카드를 `ready=true blockers=[]`로 내놓았다.

원하는 동작: 시나리오를 한 단계도 실행하기 전에 채널 획득이 실패하면(도구 bind·attach·
timeout) 그것은 제품에 대한 정보가 아니다. 카드를 만들지 않고, 재발 몇 번째든 첫 항목부터
사람에게 간다.

여기서 사람에게 가는 항목은 실패 이력 항목이 아니라 커밋된 Record의 정확한 `Executed:` 결과다.
`Failure history`·수리 계보·카드는 계속 비어 있고, 상태 도구가 같은 영속 소유자에서 대상·verify
경로·명령·timeout을 사람 대기로 투영한다. 따라서 자동 재실행을 없앤 결과가 다음 세션에서
사라지지 않으며, 같은 사실을 담는 두 번째 기록도 생기지 않는다.

선택한 경계: 검증자의 `unverified` 사유 하나를 늘리고 그 형식을 고정한다 —
`unverified: channel unavailable — <실패한 정확한 명령>; timeout=<값>`. 실패한 명령과 timeout
값을 함께 적게 한 것이 빠져나갈 구멍을 막는 장치다: 제품 결함을 도구 고장으로 분류해
빠져나가려면 모델이 그 두 값을 지어내야 한다.

필요한 이유: DD-68은 **제품에 대한** non-pass의 재발을 다루고 재관측 2 이상에서 사람에게
돌린다. 채널 고장은 정의상 제품 정보가 아니므로 그 계단을 한 번 더 밟게 하면 실행 불가능한
카드가 한 장 더 생길 뿐이다. DD-68의 기록된 이유는 부정되지 않는다 — 범위가 갈릴 뿐이고,
그래서 DD-68은 대체가 아니라 일부 정정이다.

기각한 대안: **재발 1회를 그대로 태우고 2회째에 사람에게 보낸다** — 관측된 장면이 바로 「한 번도
못 닫음」이므로 한 바퀴를 더 도는 값이 없다. **사유를 자유 문장으로 둔다** — 실패한 명령과
timeout이 없으면 분류가 검사 불가능해지고 이 결정의 유일한 집행 장치가 사라진다.

영향 좌표: `skills/verify/SKILL{,_ko}.md`의 `unverified` 사유 목록,
`skills/arch/SKILL{,_ko}.md`의 verify channel 확인,
`skills/principles/scripts/project-state.mjs`의 영속 결과 투영,
`skills/resume/SKILL{,_ko}.md`의 사람 대기 소비, `scripts/project-state.test.js`,
`scripts/repository-invariants.test.js`, `docs/rounds/v0.18.9/report_ko.md` §4.
재검토 조건: 채널 획득 실패로 분류된 항목이 실제로는 제품 결함이었던 장면이 관측될 때.
시험이 이 결정을 못 닫는다 — 관문 B가 지난다.

### DD-87 · 여러 소유자에 걸친 한 요청은 승인 경계 하나를 유지한 채 여러 패스로 착지하고, 남은 마커와 이미 쓴 카드가 잔여 대상과 소비 읽기를 지닌다 (v0.19.0)

관측된 문제: split은 「한 번에 한 층만」과 「묶음은 계획 커밋 하나를 받는다」를 동시에 말한다.
스무 항목이 다섯 능력에 걸친 요청에서 두 문장은 함께 참일 수 없다. 문자 그대로 읽는 세션에게
남는 길은 셋뿐이었다 — 한 층 규율을 깨거나, 하나만 계획하고 나머지를 조용히 버리거나, 커밋
전에 컨텍스트가 끝나 다음 세션이 요청을 코드부터 다시 추적하는 것. 상태 투영에도 같은 구멍이
있었다: 요청을 지운 패스의 카드는 `origin`으로 요청 줄을 내는데, 아직 요청이 남아 있는 패스의
카드는 자기 층 열기 마커 줄을 냈다. 한 요청이 소유자마다 다른 origin으로 보고됐다.

원하는 동작: 한 요청은 소유자가 몇이든 출처 정체성 하나와 기획 경계 하나를 갖는다. 승인은
묶음 전체에 한 번이고, 착지는 패스가 감당하는 만큼 나뉜다.

선택한 경계: 새 묶음 식별자도 새 상태도 만들지 않는다. 이번 패스에 부모 전부가 들어가면 계획
커밋 하나로 끝내고, 들어가지 않으면 끝낸 부모만 착지시키며 그 부모의 마커만 지운다. 남아 있는
마커가 곧 정확한 잔여 대상이다 — 부모·이미 발급된 자식 번호·같은 출처. 원 요청 줄은 마지막
마커와 함께 나가므로 `request` 구역의 자리도 그대로다. 이미 쓴 카드는 그 패스가 근거로 삼은
유계 `읽을 것`을 지니고, 상태 도구가 후보마다 `readFirst`와 같은 출처 형제 집합을 투영한다.
그리고 origin은 이제 그 카드 생성 커밋이 지운 입력의 정체성 자체다 — 마커가 지목한 영속 출처
locator이지, 그 패스의 diff에 우연히 들어 있던 마커 줄이 아니다.

필요한 이유: 잔여 대상과 소비 읽기가 디스크에 없으면 다음 패스는 트리를 훑고 매핑을 다시
계산한다. 그 재계산은 조용히 다른 답을 낼 수 있고, DD-54가 막으려던 「절반만 계획하고 나머지를
잃는」 실패가 세션 경계를 통해 되돌아온다. origin이 소유자마다 다르면 resume이 사람에게 한
요청을 둘이라고 말한다.

기각한 대안: 부모마다 승인 — DD-54의 기록된 이유가 정확히 그것을 기각했다(스무 항목에 승인
여러 번). 묶음 식별자 신설 — 같은 출처 locator가 이미 정체성이므로 새 상태를 만들 이유가 없다.
계획 커밋 하나를 강제 유지 — 「한 번에 한 층만」과 정면으로 충돌하는 쪽을 남기는 선택이고,
관측된 실패가 바로 그 충돌이다.

`skills/resume/SKILL{,_ko}.md`의 `transition.layer-opening` 행,
`skills/principles/scripts/project-state.mjs`의 `cardOrigin`·`parseReadFirst`,
`scripts/project-state.test.js`의 D8 fixture. DD-54.
재검토 조건: 여러 패스로 나뉜 묶음이 부모 하나를 영영 끝내지 않고 남기는 장면이 관측되거나,

정확한 경로를 산출물로 선언한다. 그런 경로가 없는 넓은 suite 명령은 경로 선언에서만 면제되고
증명 진술에서는 면제되지 않는다. work는 점유·재개 전에 계약을 검사하고 부실한 카드를 기존
수리 경로로 split에 돌려보낸다.

필요한 이유: 자동 기준선 문서는 도메인을 설명하지만 기계적 실행자가 소비해야 할 현재 코드
edge를 식별하지 않는다. 명령은 카드가 이름 댄 assertion만 증명하며, 작업 전용 fixture가 명령
안에만 있으면 내구 소유자가 없다. 이는 실행 경계이지 구현 지시가 아니다. 복합 카드 하나는
여전히 여러 능력에 영향을 줄 수 있고, 경로는 전수가 아니라 유계로 남으며, 지식 승격은 카드

기각한 대안: 가능한 코드 경로 전부 — 무유계이고 카드를 코드 지도로 만든다. 능력마다 카드 하나

읽기를 T-하 근거로 인정 — 관측된 소비자 edge 누락을 재현한다. 넓은 suite의 테스트 전부 선언
— 책임은 늘지 않고 잡음만 는다. 구현 방법 처방 — 카드 하네스 경계와 충돌한다.

### DD-94 · 정확한 제목의 작업 커밋 뒤에는 미확정 증거가 COMMIT만 금지하고, 증거가 닫히고 상위 문서 환류가 없거나 호환 집합이 전부 소비됐을 때 경계 커밋 하나가 늦은 탈것이 된다 (v0.20.0)

주제: 작업 트리와 카드 | 도입: v0.20.0 | 상태: 유효

관측된 문제: 첫 그린필드 실사용 카드가 정본의 정확한 H1 제목으로 작업 커밋을 만든 뒤 검토와
`carry`가 아직 없자, work의 `boundary-incomplete` 관문이 모든 stage보다 먼저 영구 `BLOCK`했다.
그 결과 빠진 증거를 만들 수 있는 `review-reduction` 자체가 닿지 않았다. 이 관문을 단순 제거해
늦은 검토를 붙인 재현에서는 다른 소실이 드러났다. 유효한 `carry:` 뒤에 `review result:`를
덧붙이자 상태 도구가 진행 줄 전체의 마지막 줄만 읽어 물리적으로 남은 carry를 `absent`로
바꿨고, work는 같은 carry를 한 번 더 쓰려 했다. 이 사실은 `missing`과 현재 점유뿐 아니라 능력
폐쇄의 `children-done carryFacts`에서도 조용히 사라졌다.

원하는 동작: 정확한 H1 작업 커밋은 하나만 유지하고, 그 뒤에도 커밋하지 않는 완료·검토 증거
생산자는 닿을 수 있어야 한다. 한 증거 종류의 늦은 줄이 다른 종류의 유효한 사실을 철회하지
않는다. 증거가 닫힌 뒤에도 `feedback.action`이 미판정 또는 UNKNOWN이면 모든 경계 효과보다 먼저
그 판단을 요구한다. `none`은 기존 경계 커밋에 빠진 carry와 claim→done 이동을 싣는다.
`compatible`은 정확한 제안이 처음 보이거나 current인 동안 기존 의미 소유자 경로를 마쳐야 하며,
모든 정확한 lifecycle이 `consumed`이고 현재 카드의 current marker가 없을 때만 같은 경계 탈것으로
닫힌다. UNKNOWN·current·never-seen compatible 상태와 그 밖의 관측된 환류 값은 닫히지 않는다.

선택한 경계: 기존 `boundary-incomplete` BLOCK을 없애고, 작업 커밋이 이미 있으며 통합과 HANDOFF가
현재이고 finish-boundary 증거가 미확정인 동안 **`COMMIT` 동사만** 금지하는 `RESTRICT` 관문 하나로
바꾼다. 증거만 쓰는 완료 신호와 독립 검토는 계속 진행하지만, checkpoint나 두 번째 작업 커밋을
품은 갈래는 기계적으로 막힌다. 완료가 `pass`이고 검토가 `pass`·`waived`·`not-applicable` 중
하나로 닫힌 뒤에도 미판정 또는 UNKNOWN `feedback.action`은 경계 표보다 먼저 필요한 판단을 이름으로
대는 `BLOCK`으로 돌아간다. 판단이 알려진 뒤 `feedback.action=none`인 기존 두 행은 그대로다.
carry가 없으면 한 줄만 쓰고 claim→done 이동과 함께 경계 커밋에 싣고, 이미 있으면 다시 쓰지 않고
이동만 싣는다. `feedback.action=compatible`에는 DD-96 위에 세운 정확한 lifecycle을 소비하는 두 행이 더
있다. 모든 제안이 `consumed`이고 현재 marker가 없을 때만 같은 두 효과를 재사용하며, never-seen은
정본 transport를 먼저 쓰고 current는 Resume으로 계속 라우팅하고 UNKNOWN·invalid는 차단한다.
그 밖의 알려진 non-`none` 환류는 기존 `pending`의 `REPORT→WAIT`에 남는다.

같은 변화에서 `carryState`는 전체 진행 줄의 마지막 줄이 아니라 **마지막 유효 carry-kind 줄**을
고른다. signal과 review가 이미 쓰는 종류별 최신값 의미와 같으며, 잘못된 뒤쪽 carry 줄은 기존
`integrity.shape`로 계속 보이되 앞의 유효한 carry를 가리지 않는다. work collector의 구조화된
상태가 없는 fallback도 같은 선택을 쓴다. 상태 도구는 계속 읽기 전용이고 새 field·zone·형식·
writer를 만들지 않는다.

필요한 이유: `RESTRICT`는 판단값마다 복구 stage를 늘리지 않고 실제로 위험한 효과만 거부하므로
증거 생산자와 한 작업 한 커밋을 함께 보존한다. 종류별 마지막 유효 줄은 carry만 갖던 손실성
특례를 없애고 `missing`, 점유, 폐쇄 수확의 한 정본을 함께 고친다. 경계 커밋은 이미 HANDOFF와
상태 이동을 함께 싣는 공유 탈것이라 별도 커밋이나 writer를 만들지 않는다. DD-09·DD-15·DD-83은
그대로 유효하며, 이 결정은 DD-83의 두 재검토 조건 — 도구가 누락을 정확히 잡고도 같은 세션이
닫지 못한 장면, 실제로 있는 carry를 `missing`이라 부른 장면 — 에 대한 유계한 답이다.

기각한 대안: compatible 행을 `missing`까지 범용으로 넓히기 — 도입 당시 durable producer가 없어
기존 work→resume→work 무효과 순환만 넓혔다. 판단값별 recovery stage·conflict 행 추가 — 같은
COMMIT 위험과 기존 pending 동작을 중복한다. 두 번째 H1 또는 post-title checkpoint — DD-09를
어기고 마지막-card-commit 인식을 지운다. collector만 수리 — `missing`과 폐쇄 수확의 소실을
남긴다. carry를 다시 마지막에 쓰기 — 중복을 의도적으로 만든다. 새 carry field나 별도 boundary
writer — 한 사실 두 집과 새 권한을 만든다.

후속 출처 정정(DD-96): 위 `compatible` 기각과 none-only 경계는 durable producer가 없다는
DD-94 도입 당시 전제에 의존했다. DD-96의 정본 `compatible feedback pending` transport와 정확한
never/current/consumed lifecycle은 DD-94가 기록한 「durable producer가 생겨 pending 경로를 끝낼
수 있을 때」를 충족하므로 그 전제는 더 이상 consumed 상태에 적용되지 않는다. 이 정정은 범용
`compatible` 폐쇄를 허용하지 않는다. 증거 생산자는 계속 닿고, 미확정 증거에는 COMMIT이 금지되며,
정확한 H1 작업 커밋 하나·경계 탈것 하나·새 writer 없음은 유지된다. UNKNOWN·current·never-seen
compatible 상태도 계속 닫히지 않는다.

`skills/work/collectors/project-state-seam.test.mjs`,
`skills/principles/scripts/project-state.mjs`,
`skills/principles/references/delivery/commit-and-verification.md`,
`scripts/project-state.test.js`. 호환 환류 transport의 소유권은 DD-96에 남고, 이 결정은 그 정확한
consumed lifecycle이 늦은 경계를 끝내는 효과만 인정한다. 자동 활성화 gate는 이 결정 밖이다.
재검토 조건: 마지막 carry-kind 줄이 현재 사실이 아닌 공인 작성 흐름이 관측되거나, 늦은

### DD-96 · 호환 환류는 최초 완전 집합이 봉인된 카드 경계 payload로 보존되고, Resume이 한 의미 소유자씩 증명해 착지시킨다 (v0.20.0)

주제: 작업 트리와 카드 | 도입: v0.20.0 | 상태: 유효

관측된 문제: 깨끗한 Work 검토가 재사용 가능한 호환 환류를 발견해도 기존 `compatible` 갈래는
소유자에게 보고한 뒤 카드를 닫을 뿐 그 내용을 지속하지 않았다. 이를 K에 넣으면 카드 실행
증거와 현재 재사용 진실의 소유권이 섞이고, 자유 메모나 HANDOFF에 넣으면 정본 소비자와 원자적
완료 경계가 없다. 한편 단순한 소유자 파일 diff는 내용·출처·후속 함의가 실제로 착지했음을
증명하지 못한다.

원하는 동작: Work는 제목 커밋 전후 어느 경계에서도 호환 환류를 잃지 않는다. 한 카드에서
lifecycle이 아직 없을 때만 이미 수집된 pending·eligible 집합과 카드 target의 기계적 관계를
검증해 전체 소유자 집합을 완전하고 결정적인 payload로 한 번 원자 생산한다. 모든 줄이 정본
payload이고 source가 하나이며 owner가 중복되지 않고 모든 owner 경로가 존재하는 첫 after-state가
집합을 봉인한다. 이후의 차가운 재진입은 제안을 다시 발명하거나 pending 집합을 재구성하지 않고
봉인된 current·consumed lifecycle과 eligible 공집합 사실을 소비한다. Resume은 current 소유자를 기존
Product·Design·Arch·Adopt 단계로 전부 라우팅한다. 각 단계는 정확한 소유자에 Background,
Why/증거, Conclusion, implication, 카드@커밋 출처가 모두 있음을 정본 상태 재생으로 확인한 뒤에만
그 마커 하나를 삭제하며, 다른 소유자는 잔여 마커로 남는다.

선택한 경계: 정본 문법은 `compatible feedback pending: payload-json:` 한 줄이며 payload 키는
`owner`, `source`, `coordinates` 순서다. coordinates 키는 `target`, `background`, `why`,
`conclusion`, `implication` 순서이고 모두 비어 있지 않다. owner는 product, glossary, design,
arch 또는 정확한 능력 설계 문서뿐이다. source는 정확한 카드 경로와 전체 커밋 oid이고, 첫 집합의
모든 항목은 같은 source revision을 쓴다. 한 source card의 모든 호환 줄이 정본 payload이고 source가
하나이며 owner가 중복되지 않고 모든 owner 경로가 존재하는 첫 전이의 after-state가 그 완전한 정확
payload 집합의 seal이다. 한 줄이라도 받아들일 수 없으면 그 전이는 도입이 아니며, 어느 카드에도
귀속할 수 없는 invalid 줄은 그 전이의 모든 미봉인 카드를 보류한다. 그 뒤 같은 카드에서 기존 항목을 다시 도입하거나 새 owner·oid·좌표
paraphrase를 도입하면 무결성 차단이다. 별도 journal 문법, tombstone, note 계층은 추가하지 않으며
기존 Git lifecycle 이력이 seal과 소비 상태의 정본이다.

Work의 제목 전 최초 생산은 기존 카드 내용과 정확한 H1 커밋에 완전한 마커 집합 쓰기를 함께
싣는다. 제목 뒤 최초 생산은 journal만 만지는 별도 경계 커밋이고 카드를 수정하지 않는다. lifecycle
하나라도 생긴 뒤에는 Work가 수집된 lifecycle 사실이 `settled`이고 eligible 집합이 비었는지만
기계적으로 확인해 새 마커를 생산하지 않는다. 이 갈래에서 pending 집합은 비교 대상이 아니다.
current는 Resume으로 계속 라우팅되고 consumed는 영구 은퇴하며,
그 뒤 발견한 환류는 새 요청과 새 카드로 들어간다. 다른 카드 마커는 현재 작업을 가로채지 않고,
미판정 UNKNOWN은 필요한 판단으로 차단되며 `none`, staling, design-note 경로는 바뀌지 않는다.

Resume은 product와 glossary를 Product로, design을 Design으로, greenfield arch와 능력 문서를
Arch로, brownfield arch와 능력 문서를 Adopt로 보낸다. 소유자 단계는 먼저 정확한 내용을 쓰고
WAIT하여 상태를 다시 계산한다. 상태가 source와 다섯 좌표의 의미 착지를 증명한 재진입에서만
바이트 동일 마커 삭제와 정확한 소유자 diff를 한 커밋에 묶는다. 소유자 파일 변화는 삭제 권한의
필요조건일 뿐 의미 착지의 충분조건이 아니다.

왜: 이 경계는 DD-09의 한 사실 한 집, DD-83의 K 소유권, DD-87의 의미 소유자, DD-94의 단일
정확한 제목 커밋을 유지하면서 1000→30 요약 손실 없이 재사용 진실을 정본 소유자에게 전달한다.
첫 완전 수용 after-state를 seal로 쓰면 완전한 다중 소유자 생산과 부분 소비를 함께 보존하면서 새 oid나 바꿔 쓴
좌표로 같은 카드를 다시 여는 차가운 세션을 결정적으로 끝낸다. 카드는 실행과 출처를, journal은
현재 대기 수송을, Git 이력은 봉인·소비 lifecycle을, 소유자 문서는 현재 재사용 진실을 각각 가진다.
모든 seal 항목이 consumed이고 current가 없을 때만 Work 경계가 닫혀 Verify가 다음 소비자가 된다.

정본 소유자: 문법·Git seal 도출·검증·lifecycle 재구성·우선순위는 Principles 상태 도구, 원자 생산과
이미 수집된 집합의 기계적 정확성 guard는 Work, 전량 라우팅은 Resume, 의미 착지와 원자적 소비는
Product·Design·Arch·Adopt가 소유한다.
증거: `skills/principles/spec.mjs`, `skills/principles/scripts/project-state.mjs`,
`skills/work/spec.mjs`, `skills/resume/spec.mjs`, 네 소유자 skill의 compatible-feedback stage,
`scripts/project-state.test.js`, 각 skill의 실행 fixture.
재검토 조건: 정상 Git 이력에서 첫 완전 도입을 결정적으로 식별할 수 없는 실측 사례가 생기거나,
상태 재생이 동일 의미를 결정적으로 확인하지 못하거나, 여러 소유자의 원자적 공동 착지가 부분
소비보다 반드시 안전하다는 증거가 생길 때. 이력에서 도출한 차단형 호환 환류 finding은 현재
영구적이며 프로젝트 전체에 적용된다. Work가 아닌 writer가 현장에서 그 finding을 실제로 만난 뒤에
clearable-finding 설계를 재검토한다. 후보는 현재 journal에서 reopen finding을 도출하고, 소비를
오래된 것부터 순회하며, 이미 소비된 identity의 제거 검증은 건너뛰고, 소비된 nonmember 제거는
advisory로 다루는 방식이다.

### DD-47 · 점유는 깊이 1 단위 축, 선택은 정본 후보 순서 하나 (v0.12.0)

주제: 동시성 · 점유 · 통합 | 도입: v0.12.0 | 상태: 유효 · 일부 정정 → DD-60 (v0.14.0)

트리와 능력 문서는 이미 도메인 축인데 점유만 사람 축에 묶여 있었다. `.wip.`를 (id × 깊이 1 단위)로 키잉하면 새 식별자 0으로 동시 작업이 표현되고, 정합성 1번의 두 예외(상호 병렬 승인·증거 대기)는 원래 한 능력 안의 예외이므로 위치가 정확히 맞는다. 그 위에서 "다음에 무엇"을 묻는 자리가 여럿이라 답이 갈렸다 — 정본 후보 순서가 사용자 지목 카드 → 세션 지목 단위 → 승계 단위 → 나머지로 한 번만 정의한다. 이 순서는 어느 라우팅 행이 일치하는지를 바꾸지 않고 준비되지 않은 카드를 준비시키지도 않는다. 인식 기계는 도메인 진입에만 있던 것을 정본으로 올리고 resume·기준선 판정은 인용으로 바꿨다. 대화의 변경 요청 행은 기획이 제안한 「점유 카드 행 아래」가 아니라 그 위에 둔다 — 같은 요청의 영속 형태인 `유지보수 라우팅 대기` 행이 이미 점유보다 위에 있고, 점유가 여러 단위에 동시에 있는 것이 정상이 된 이상 아래에 두면 요청이 사실상 기록되지 않는다. 한 사람의 두 터미널은 같은 id를 쓰므로 디스크가 구분하지 못한다 — 그 한계는 감추지 않고 README에 적고, resume 보고의 승인 절차가 실제 분리 장치다. **v0.14.0에서 정정**: 점유 키의 단위 축 절반이 물러났다 — "한 id 한 단위 한 점유"는 1인 1터미널 가정으로 판명되어 자유 병렬로 대체됐고, 정합성 1번의 두 예외 문구도 함께 갔다(1번은 고아 점유 탐지로 재정의). 정본 후보 순서와 요청 기록 행 배치는 그대로 서 있다

### DD-49 · Git은 요건이고, 워크트리가 흐름 등록부다 (v0.12.0)

주제: 동시성 · 점유 · 통합 | 도입: v0.12.0 | 상태: 유효 · 일부 정정 → DD-51 (v0.13.0)

실측 뒤 무른 모서리 둘을 굳혔다. 비-Git 축소 동작은 승인·통합 tip·점유·접두·digest 마커가 아무것도 돌지 않을 때 각각 무엇을 뜻하는지를 정의해야 했다 — devflow가 아닌 것을 서술하는 정본 6줄이다. Git을 요건으로 두면 문장 하나로 그 6줄이 전부 사라진다. Git 없는 저장소는 복구도 점유도 되돌리기도 없으므로 약한 devflow가 아니라 같은 이름의 다른 물건이다. 워크트리 쪽에서는 "원격이 필요하다"는 기록을 실측으로 반증했다 — 한 저장소의 워크트리들은 객체 저장고를 공유하므로 `git push . HEAD:<브랜치>`가 원격 없이 로컬에서 착지하고, 한 폴더의 커밋이 fetch 없이 다른 폴더에서 보이며, 실제 제약은 "다른 워크트리가 체크아웃한 브랜치에는 쓸 수 없다" 하나뿐이다. 그래서 `git worktree list --porcelain`은 저장소가 열어 둔 폴더 목록이고, 사라진 폴더는 `git worktree prune`이 치운다. **v0.13.0에서 정정**: 이 행은 원래 그 목록을 기각된 `flows/` 폴더(X2)가 원했던 흐름별 영속 식별자라고 불렀고, 공유 트리 상태를 통합 tip과 각 워크트리 HEAD의 합집합으로 유도했다. 폴더 목록은 흐름의 정체성이 아니며 — 폴더에 흐름이 없을 수도, 죽은 흐름이 있을 수도 있다 — 합집합은 아래 행이 뒤집는다. devflow는 여전히 워크트리를 만들거나 관리하지 않는다 — git이 이미 갖고 있는 것을 읽을 뿐이다

### DD-51 · 공유 진실은 통합 브랜치 하나이고, 다른 워크트리의 HEAD는 권위가 아니라 증거다 (v0.13.0)

주제: 동시성 · 점유 · 통합 | 도입: v0.13.0 | 상태: 유효

v0.12.0은 공유 트리 상태를 통합 tip과 각 워크트리 HEAD의 합집합으로 읽었는데, 그 규칙은 양쪽으로 깨진다. 뒤처진 워크트리는 이미 끝난 카드를 점유 상태로 되살린다. 뒤처진 쪽을 빼도록 고치면 이번엔 살아 있는 형제의 점유가 사라지고 완료했으나 아직 통합되지 않은 작업이 어느 상태에도 없어 같은 카드가 두 번 실행된다. 두 실패 모두 카드 상태를 브랜치 단위 신선도로 판정하는 데서 온다. 최초 점유가 이미 구속 결정으로 통합에 착지하므로 통합만 읽으면 모든 점유가 보이고, 다른 HEAD를 읽는 것은 아무것도 주지 않으면서 낡은 상태만 들여온다. 그 폴더의 코드와 진행 로그는 여전히 그 흐름의 증거이며 통합될 때 들어온다 - 공유 상태 판정에 쓰지 않을 뿐이다

### DD-52 · 공유 전이는 기억해 둔 통합 id에 대고 게시한다 (v0.13.0)

주제: 동시성 · 점유 · 통합 | 도입: v0.13.0 | 상태: 유효 · 일부 정정 → DD-62 (v0.14.0), DD-70 (v0.16.0)

아무도 쥐지 않은 통합에서도 두 흐름이 같은 지점에서 동시에 밀면 한쪽은 진다. 그것은 실패가 아니라 동시성 제어가 작동한 것이다. 둘을 가르지 않으면 정상 경쟁을 "통합 불가"로 오판해 막힌 경로로 보내고 점유가 이유 없이 흩어진다. 첫 실측은 id 자체가 판별자가 될 수 있다고 보였다 — 정상 경쟁에서는 바뀌고, 워크트리가 그 브랜치를 쥐면 그대로인 채 거부되기 때문이다. 실전 동시성 실행이 그것을 반증했다. 형제 흐름이 이미 게시한 *뒤에* 통합을 읽은 흐름은 그 뒤 바뀌지 않는 id를 기억하게 되는데, 그 거절은 평범한 non-fast-forward다. 그래서 기계적 검사는 통합 tip이 게시하려는 브랜치의 조상인가이다 — 조상이 아니면 정상 경쟁, 조상인데 거부되면 구조적 막힘 — 이며 두 실전 사례가 이 검사로 정확히 갈린다. 에러 문구는 locale과 Git 버전에 따라 달라지므로 판별자가 아니다. 재시도는 세 번으로 묶고, 지속 경합은 실패 사다리로 세지 않고 보고한다. 통합에 정말 쓸 수 없으면 이미 점유가 착지한 카드의 코드 편집과 진행 로그 체크포인트만 계속한다 - 조정점이 없으면 누가 무엇을 발급했는지에 전역 답이 없지만, 코드와 진행 로그는 나중에 합쳐도 안전하다(서로 다른 카드, 그리고 done 개명 대 로그 추가에서 실측). 이 경계가 오케스트레이터가 통합을 쥐는 환경도 살려 두며, 그때 오케스트레이터는 worker를 띄우기 전에 통합에서 카드와 점유를 먼저 만들어야 한다. **v0.14.0에서 정정**: 봉쇄 중 계속 목록이 넓어졌다 — 최종 작업 커밋과, 발급·점유·소비가 아닌 journal 덧붙임(정확 열거 4종)도 계속한다. "코드와 로그만"의 동결은 그 라운드의 유일한 조용한 소실 경로(봉쇄 중 요청 증발)로 판명됐다(봉쇄 덧붙임 행 참조)

### DD-53 · 한 작업 폴더의 여러 세션은 정상이고, 그 안전은 락이 아니라 측정된 다섯 줄이다 (v0.13.0)

### DD-60 · 점유는 자유 병렬이고, 체크포인트는 이 세션이 만든 변경만 담는다 (v0.14.0)

"한 사람 한 깊이 1 단위 한 점유"의 기록된 근거(반쯤 된 작업의 확산 방지·점유 상태의 단순성)는 1인 1터미널 가정 위에 있었다. 소유자의 실제 방식은 터미널 여섯 이상이 한 능력의 기능들을 나눠 도는 것이고, 그 방식의 유일한 합법 경로가 선제 그룹 점유 하나뿐이라 그 문을 모르면 파킹 우회가 형제 세션의 미완성 diff를 임의 시점에 커밋하고 카드를 해제했다. 측정이 이미 자유 병렬의 안전을 보였다(자기 경로 커밋·덧붙이기 기록장·부분 수정 공존). 그래서 준비된 카드는 어느 터미널이든 즉시 잡고, 같은 단위의 내 기존 점유는 정보 한 줄로만 알린다 — 확산 가시성은 resume의 점유 목록 보고와 무지목 다중 점유 질문이 대신 맡는다. `parallel:` 필드는 승인 값 형식의 일부라 남기되 점유 합법성과의 결합을 끊고 정보 한 줄의 출처로 쓴다 — v0.9.23의 그룹 일괄 점유 절차와 상호성 술어는 존재 이유가 사라져 제거된다(카드 형식 이관 0). 체크포인트류 규칙은 전부 "이 세션이 그 카드에 만든 변경만"으로 통일한다 — 미커밋 변경은 세션 귀속이 불가능하므로 "다른 단위 점유의 미커밋을 먼저 체크포인트"의 무제한 독해는 다중 세션과 양립하지 않았다(전이를 만든 세션 자신에게는 그대로 성립하므로 legacy signal migration 기각의 유계 논거는 유지된다). 정합성 1항은 조건이 무의미해지므로 고아 점유(점유 id가 어느 방과도 불일치) 탐지로 재정의해 항 번호를 보존한다. 같은 카드를 두 터미널이 동시에 다루는 것은 기계로 막을 수 없고(터미널 무식별 — 워크트리별 신원 기각과 같은 실측) README 지침이 담당한다

### DD-62 · 봉쇄 중에도 발급·점유·소비가 아닌 journal 덧붙임은 즉시 기록한다 (v0.14.0)

주제: 동시성 · 점유 · 통합 | 도입: v0.14.0 | 상태: 유효

v0.13.0의 게시 문단은 journal 줄 생성까지 통합이 열릴 때를 기다리게 했는데, 그 동결의 실제 결과가 이 시스템이 가장 경계하는 무흔적 소실이었다 — 봉쇄 중 세션이 죽으면 사용자가 분명히 말한 요청이 대화에만 존재하다 증발한다(독립 검증의 유일한 최상급 위험). 원 근거였던 "조정점 없이는 전역 답이 없다"는 덧붙임에는 미치지 않는다 — 덧붙임은 전역 답이 필요 없는 로컬 증거이고 나중에 합쳐도 안전하다는 것이 그 결정 자신의 실측이다. 허용은 정확 열거다: 유지보수 요청 · capability note · 기명 미결/결정 · product 재실행 대기. 번호를 발급하는 layer opening, push가 필요한 증거 기록, 검증 상태 줄, 모든 소비(삭제)는 계속 대기한다. 최종 작업 커밋은 계속 목록에 명시한다 — 자기 브랜치 소관인데 어느 목록에도 없어 "이름 없이 기다리는 것은 없다"는 같은 문단의 자기 선언을 위반하고 있었다

### DD-63 · journal 병합 충돌은 합집합이 아니라 3-way다 (v0.14.0)

주제: 동시성 · 점유 · 통합 | 도입: v0.14.0 | 상태: 유효

"합집합 — 양쪽 줄을 날짜순으로 다 남긴다"의 기록된 사유는 기록 보존이었는데, 실측 15·16이 같은 의미론(merge=union)을 이미 기각했다 — 한쪽이 소비해 지운 줄을 다른 쪽의 인접 추가가 부활시켜, 계획까지 끝난 요청이 되살아나 같은 수정이 새 번호로 두 번 계획된다. 보존이 아니라 유령 재생이다. 교체 규칙: 충돌 시 공통 조상(merge-base)의 journal blob과 대조해, 조상에 있던 줄이 한쪽에 없으면 소비이므로 복원하지 않고, 조상에 없던 줄은 추가이므로 양쪽 다 시간순으로 남긴다. 추가는 전부 보존되므로 원 사유(기록 보존)를 3-way가 더 잘 지킨다. 봉쇄 덧붙임 허용으로 병합 빈도가 늘므로 두 결정은 한 몸이다

### DD-66 · 경량 차선은 커밋의 착지를 기계로 먼저 확인하고, 같은 파일 경합에서는 경량이 양보한다 (v0.14.2)

주제: 동시성 · 점유 · 통합 | 도입: v0.14.2 | 상태: 유효

v0.14.0 감사가 Git fixture로 재현한 셋의 수리다: 이름 없는 HEAD의 경량 커밋은 어느 브랜치에도 담기지 않고 reflog에만 남는다(4.2) · 경량 커밋의 HEAD 전진 하나가 base 커밋 id에 고정된 `라우팅 준비` 복구를 정합성 이상으로 바꾼다(4.4) · `git commit --only <경로>`는 같은 파일에 남은 다른 세션의 미완성 변경까지 담는다(4.3). 낡은 checkout의 문서로 내린 "아니오"가 통합에 이미 착지한 결정과 충돌하는 커밋을 만드는 경로(4.5)도 확인됐다. 그래서 차선은 수정 전에 기계 확인을 돈다 — 이름 있는 브랜치(`git symbolic-ref -q HEAD`) · 작업 트리 verify.md에 `라우팅 준비` 없음 · 읽을 수 있는 통합 tip이 HEAD의 조상 · 편집 직전 대상 경로에 이 세션이 만들지 않은 미커밋 변경 없음 — 그리고 커밋 직전 diff를 내 변경과 대조한다. 이것은 상태 복원이 아니라 착지 전제다: 트리·journal·HANDOFF·투영은 여전히 읽지 않고, 확인은 Git 명령과 유계 검색뿐이라 진입 비용 절감(G6)이 유지된다. 같은 파일 경합의 해소는 자기 변경은 스스로 되물리고 다시 적용할 수 있다는 사실 위에 선다 — 물러나는 쪽을 경량으로 고정해 상호 대기가 성립하지 않는다. 확인과 커밋 사이의 짧은 race는 잠금·세션 식별자 없이는 닫히지 않으므로 보장 밖 표에 남는다(잠금·터미널 식별자·관리형 워크트리의 기각은 유지). DD-61의 "그물 우회가 무해" 서술은 이 결정이 일부 정정한다

### DD-70 · `coordinator`는 devflow의 단계가 아니라 선언된 역할이며, 그 의무는 역할 계약 하나가 소유하고 devflow의 동작·상태는 오케스트레이션 여부로 분기하지 않는다

주제: 동시성 · 점유 · 통합 | 도입: v0.16.0 | 상태: 유효

DD-53은 한 작업 폴더의 여러 세션을 안전하게 만들었지만, 바깥에서 세션을 배정하는 행위자가 사람 관문을 대신 답하거나 파일 전체 재작성을 시키거나 지식을 디스크 밖 전달에만 두는 일은 신뢰 경계 밖이라 기존 상태 기계가 감지하지 못한다. 등록 스킬이나 새 상태를 만들면 devflow의 동작이 배정 방식에 따라 갈리고, 그 장치도 경계 밖 행동을 강제하지 못한다. 따라서 DD-19의 원문 브리핑 역할 계약 형식을 상속해 의무를 `skills/principles/coordinator.md` 한 곳에 둔다. 문서 지도와 이 결정은 계약의 존재·역할을 기록하고, 훅·README는 계약을 발견시키는 포인터만 가진다. 카드 번호 발급은 구속 결정이므로 병렬 구현 워커를 배정하기 전에 한 split 워커가 `split — begin <부모>`와 이어지는 계획 커밋을 통합 브랜치에 착지시킨다. 점유는 미리 대신 만들지 않으며, `coordinator`는 통합 브랜치를 체크아웃한 채로 두지 않는다. 카드를 맡은 워커가 work의 최초 점유 커밋으로 만들며, `coordinator`가 같은 소유자 id로 선점하면 점유가 여럿 생겨 무지목 resume이 카드를 묻는 모호성이 늘어난다. 기존 스킬·상태·커밋 종류·id·방은 바꾸지 않는다.

### DD-28 · 영속 지식은 새 문서층이 아니라 범위가 고정된 기존 기록의 소비 경로로 잇는다 (v0.9.21)

주제: 지식층과 능력 문서 | 도입: v0.9.21 | 상태: 유효 · 일부 정정 → DD-76 (v0.18.1), DD-91 (v0.19.0), DD-92 (v0.20.0)

glossary와 journal을 만들어도 arch·design·work·verify 및 위임자가 읽지 않았고, 함께 열린 의존 카드의 나중 결론도 다음 구현자에게 닿지 않았다. 고친 읽기 집합은 이름으로 완전히 열거된다: glossary·journal(존재할 때)과 카드가 직접 지목한 `의존`만. 브라운필드의 기존 핸드오프·사양 문서는 adopt가 능력별 정확한 경로만 arch.md `기존 기록`에 색인한다. 이 색인은 읽기 지시나 정본이 아니며, split이 현재 코드와 다시 대조해 카드의 `읽을 것`에 넣은 경로만 work가 연다. "관련 기록"이나 능력 폴더 전체 읽기는 계속 금지한다. Layer 0 완전성에는 glossary도 포함하고, resume은 그것만 없으면 확인된 다른 문서를 다시 쓰지 않은 채 브라운필드면 adopt, 신규면 product로 보낸다. 따라서 중계노트식 제2 도메인 핸드오프층을 강제하지 않고, 기존 정본·트리·짧은 기록 계층의 도달성만 닫는다. 회고도 사건별 입력 집합 하나만 받아 능력 범위와 전체 범위가 합쳐지지 않는다. 이 색인은 v0.9.18이 기각한 관찰 캐시 등록 필드와 다르다 — 기각 사유 셋(어느 규칙도 읽지 않는 필드, 밖 기록 지위 선언과의 중복, 관측 사실의 거처가 갈리는 표류 경로)을 `기존 기록`은 실질로 피한다: split이 각 경로를 다시 대조해 카드의 `읽을 것`에 넣는 규칙이 소비하고, 결정이 아니라 브라운필드 기존 기록의 색인이며, 거처는 arch.md 한 곳이다 (기각 계보의 그 항목 참조)

사실로 내보내지만, 이미 골조가 선 저장소에 준비된 카드가 있으면 resume은 규칙대로 work으로
계속 간다 — 미결 항목은 어느 라우팅 구역에도 들어가지 않으므로 `next:`를 바꾸지 않는다.
그리고 그 문장을 설계 구역에 착지시킬 수 있는 유일한 소비자인 arch·adopt의 설계 전용 진입은
`marker.design-note` 하나로만 열린다. 결과는 DD-86이 고치려던 그 소실이다 — 사람이 한 번
확정한 문장이 사실로만 보이고 아무도 가져가지 않는다.

원하는 동작: 그 정확한 형태의 줄 하나가 준비된 작업보다 먼저 그 줄이 이름 댄 능력의 설계
작성자에게 간다. 카드 번호는 여전히 소유자를 정하지 않는다.

선택한 경계: 새 예약 머리말도 새 문서층도 만들지 않는다. 기명 미결 항목 안에 정확한 형식
하나(`<id> 설계 미결 항목: 능력: <NN>; 문장-json: …; 카드-json: …`)를 두고, 그 형식이면서
HEAD에 있는 줄만 도구가 `marker.design-open-item` 한 종류로 라우팅한다. marker 구역은
claim·ready보다 앞이므로 준비된 카드도 점유도 그것을 앞지르지 않는다. resume은 그 줄의
`capability`·`statement`·`card`를 그대로 arch(Brownfield `아니오`) 또는 adopt(`예`)에
넘기고, 두 소비자의 설계 전용 진입이 `marker.design-note`와 이 종류를 함께 받는다. 소유자는
줄이 이름 댄 능력이고 카드 번호가 아니다 — 카드가 여러 능력의 일을 담고 있어도 쪼개지 않고,
`카드-json`은 확정이 일어난 자리일 뿐이라 그 카드가 이미 닫혔어도 라우팅은 성립한다. 착지는
같은 구속 능력 문서 커밋에서 바이트가 같은 줄을 지우며 끝나고, 그 삭제 하나가 기준선 판정
정본의 작성자 경계 예외에 함께 들어간다.

반증한 이유: DD-86은 "필요한 소비자는 이미 있었고, 없던 것은 그 소비자로 가는 한 행이었다"고
적었다. 그 소비자는 사람의 결정이었는데, 사람이 그 줄을 보려면 resume 보고를 읽어야 하고
resume은 준비된 작업이 있으면 합법적으로 work으로 간다. 설계 구역에 실제로 쓸 수 있는 소비자는
arch·adopt뿐이고 그 문은 다른 열쇠로만 열렸다. 없던 것은 표의 한 행이 아니라 라우팅이다. 이는
DD-86이 미리 등재한 재검토 조건("arch·adopt가 그 줄을 받고도 설계 구역에 착지시키지 못하는
장면")의 한 단계 앞 형태다 — 받지도 못했다. DD-86의 다른 판정(예약 머리말 금지·설계 형태의
능력 고정·짧은 형태 금지·같은 커밋 삭제)은 그대로 유효하다.

기각한 대안: 모든 기명 미결 항목을 라우팅 — 자유 산문 줄에는 이름 댄 소유자가 없어 어떤
소비자도 행동할 수 없고, 사람이 결정할 때까지 준비된 작업을 영구히 앞지른다. 새 예약 머리말 —
DD-86의 기록된 기각 이유가 그대로 선다(파서·관문 A·정본 형식 블록·소비자가 한 번에 는다).
소유자별로 카드를 쪼개기 — 카드는 구현 경계이지 지식 소유자가 아니고, 지식 착지를 위해 승인된
작업 경계를 바꾼다. 형식이 어긋난 줄을 진입 정지로 만들기 — 0.18.8이 정한 줄 단위 소유권을
뒤집어 사람의 산문이 다시 저장소를 막는다.

`skills/principles/scripts/project-state.mjs`의 구역 표·journal 파서·설계 라우팅 계산,
`skills/resume/SKILL{,_ko}.md`의 라우팅 표, `skills/arch/SKILL{,_ko}.md`와
`skills/adopt/SKILL{,_ko}.md`의 설계 전용 진입,

### DD-89 · 설계 미결 항목은 그 귀속이 기존 방을 이름 댈 때만 라우팅된다 (v0.19.0)

주제: 지식층과 능력 문서 | 도입: v0.19.0 | 상태: 유효

관측된 문제: DD-88의 정확 형식 인식기는 `<id>` 자리에 공백 없는 토큰이면 무엇이든 받았다.
journal 정본은 그 토큰이 기존 방 id 하나와 정확히 같을 때만 기명 줄을 기계 소유로 두며, 나머지
줄은 사람의 것이어서 판정 밖에 그대로 남아야 한다. 따라서 `ghost`에 귀속된 정확해 보이는 줄이
`marker.design-open-item`이 되어 준비된 작업을 앞지르고, 사람이 확정한 지식인 양 arch·adopt에
들어가 어떤 방도 소유하지 않았는데 착지 커밋에서 삭제됐다.

원하는 동작: 라우트는 정확한 구문과 기존 방 귀속을 함께 인식한다. 어느 경계든 실패한 줄은 보통
journal 줄로 남아 `next:`를 바꾸지 않고 설계 작성자가 소비하지 않는다.

선택한 경계: 파서는 구조화 후보에 id 토큰을 보존하고, 설계 라우팅 계산 하나는 그 id가 기존 방
집합의 id 하나와 정확히 같을 때만 후보를 받는다. 카드에서 의미상 능력 소유자를 다시 유도하거나,
카드의 현재 상태를 검사하거나, 복합 카드를 쪼개지 않는다. DD-88의 기명 능력 동작은 전부 그대로다.

필요한 이유: 방 검사가 없으면 사람의 줄이 기계 라우트에서 조용히 삭제된다. 이는 DD-88이 형식이
어긋난 줄을 진입 판정 밖에 두며 명시적으로 기각한 줄 소유권 소실이다.

기각한 대안: 근접 실패를 막힘으로 만들기 — 산문이 저장소를 멈추게 하며 0.18.8의 줄 경계를
뒤집는다. 공백 없는 id를 전부 귀속으로 보기 — 실패한 현행 상태다. 카드 번호를 대체 소유자로
쓰기 — 카드는 여러 능력을 담을 수 있고 지식 소유권은 의미로 정해지므로 DD-88이 기각했다.

영향 좌표: `skills/principles/SKILL{,_ko}.md`의 정확한 설계 미결 항목 문단,
`skills/principles/scripts/project-state.mjs`의 파서와 설계 라우팅 계산,
`scripts/project-state.test.js`의 C fixture, 매트릭스 3.21칸.
재검토 조건: 기존 방의 줄이 라우팅되지 않는 장면이 관측되거나, 방 신원이
`devflow/users/*/owner.md` 밖으로 이동할 때.

주제: 지식층과 능력 문서 | 도입: v0.13.0 | 상태: 유효

v0.7.0은 열린 결정을 journal로 옮기는 것을 "한 개념 두 집"으로 기각했는데, HANDOFF에서 그 절을 통째로 없애면 집이 정확히 하나가 되므로 그 사유가 반박된다. 지금 닫는 실패는 구체적이다 - HANDOFF는 통째로 덮어쓰고, 한 사람의 두 세션이 방 하나를 공유하며, 둘 다 덮으면 한쪽의 결정이 흔적 없이 사라진다. journal은 덧붙이기만 하고 이탈 경로에서 이미 기명 열린 결정을 받고 있었다. 구간 진단을 나눈다. 확정된 Layer 0 문서와 다음 문서 사이는 각 문서의 커밋과 resume이 보존하고, 한 문서를 확인받는 도중에는 승인 전 core-document 경로를 바꾸지 않는 계약 때문에 값싼 중간 착지가 없다. 결함은 arch.md·code-style.md가 착지한 뒤 arch의 최종 출력인 능력 문서가 하나도 없는 채 실행이 끝날 수 있다는 데 있다. DD-43은 첫 카드 전 도메인 경계와 개념이 항상 존재해야 한다고 정했지만, arch에는 가장 큰 단일 산출물을 시작하기 전의 컨텍스트 경계가 없었고 split은 파일 0장 상태를 막지 않았다.

경계는 다섯이다. product의 `해결 방식`은 이제 목표가 충돌할 때 무엇이 이기는지를 함께 소유한다 — 이 값을 요구하는 소비자가 정본에 둘 있는데(`arch:72`의 후보 tie-break, `planning-evidence:67`의 구속 전 재검토) 생산자가 없었고, 그 결과 synky `product.md:18`이 어디에도 정의되지 않은 속도·비용 원칙을 기각 근거로 인용했다. arch는 능력 문서 절 안에서 기대 문서 수를 먼저 말하고, 하네스가 컨텍스트를 경고하면 이 실행이 arch의 완료가 아님을 밝힌 채 확정된 Layer 0 커밋에서 멈춘다. 점유한 카드가 없는 다음 세션은 resume으로 들어와 그 절만 실행한다. split은 첫 트리 개방 때 `01`과 product.md 비은퇴 능력 번호 각각에 대해 `devflow/project/capabilities/` 바로 아래에 파일명의 첫 `-` 앞 토큰이 그 번호와 정확히 같은 소문자 `.md`가 있는지 확인하고 하나라도 없으면 멈춰 `resume` 재진입을 안내한다. 술어의 다섯 조각은 각각 실측된 우회를 막는다 — 토큰 일치는 접두 일치가 기대 번호 `10`과 `100`이 함께 있을 때 `100-*.md`로 `10` 누락을 가렸기 때문이고, 번호 파일만 보는 것은 `.gitkeep` 하나가 게이트를 통과시켰기 때문이고, 개수가 아니라 번호별 존재를 보는 것은 부분 생성이 통과한 뒤 work의 `baseline missing`과 verify의 `baseline no-op`이 지식 문서 없는 폐쇄를 허용했고 개수 비교에서는 보존된 은퇴 문서와 초과·중복 파일이 누락 번호를 가렸기 때문이며, `바로 아래`는 재귀 독법이 하위 폴더의 번호 파일로 우회했기 때문이고, 소문자 고정은 대소문자 비구분 환경이 `.MD`를 포착했기 때문이다. 기대 번호는 split이 이미 읽는 product.md 능력 목록에서 나오고 그 목록 행에 은퇴 표기가 있으므로 읽기 집합이 늘지 않는다. 스킬을 직접 부르지 않고 `resume`을 거치는 것은 arch의 능력 문서 전용 분기가 resume 라우팅으로만 열리기 때문이며, 그 회수는 점유한 카드가 없을 때 성립한다. 연기 실행은 이 게이트도 함께 건너뛴다. arch는 arch.md 확인 직전에 ADR 세 조건을 통과한 결정을 전부 열거해 각각 기록할지 확인하고, Components·Stack의 근거가 외부 계약 사실에 기대면 정확한 출처를 같은 줄에 남긴다. 이 ADR 심사 문장은 adopt가 출력 형식 참조로 읽는 범위 안에 놓았으므로 브라운필드도 같은 심사를 받는다 — 그 좌표가 브라운필드 적용의 유일한 근거이므로 옮기려면 이 이유를 먼저 반증한다. 착지 뒤에는 미기록 ADR을 되찾는 정본 경로가 없다는 것이 이 경계의 값이다.

이 배치는 resume의 능력 문서 행이 활성 점유에 선점되는 경로와 무관하게 첫 트리 입구에서 부재를 잡고, 브라운필드는 adopt가 같은 능력 문서 생애를 소유하게 한다. synky 실측에서 ADR 통과 후보 10건 중 8건이 기록되지 않았고 Stack 11줄의 외부 계약 출처는 0건이었다. 계획은 이 게이트를 0장에 두고 부분 생성은 기존 resume과 기준선 판정에 맡겼다. 시뮬레이션이 그 근거를 반증했다 — 자기 점유 상태에서는 `resume:219`가 미존재 기대 파일 행을 선점하고 work와 verify가 모두 계속하므로 능력 하나가 지식 문서 없이 닫힐 수 있다. 번호별 존재 확인이 그것을 닫는다. 개수 비교로는 닫히지 않았다 — 보존된 은퇴 문서와 초과·중복 파일이 누락 번호를 가렸다. 이 심사 뒤에도 미기록 ADR이 사후 발견되거나, 능력 목록과 문서 집합이 정당하게 다른 프로젝트에서 비은퇴 번호마다 문서 하나를 요구하는 것이 틀린 것으로 드러나면 이 경계를 다시 연다.

### DD-74 · 기획 기록층 — 기록 게이트가 확정 선택과 재현 가능한 관측을 즉시 착지시키고, 기록 도구가 현재 집합과 유계 개봉을 판정하며, 사람 삭제는 공인 예외다 (v0.18.0)

주제: 지식층과 능력 문서 | 도입: v0.18.0 | 상태: 대체됨 → DD-77 (v0.18.2)

관측된 문제: 실전 기획(synky) 6시간+ 뒤 남은 정본은 product.md 115줄과 glossary 21줄뿐이었다.
그 정본만 읽은 동일 모델 세션은 스택 결정 6개 중 0개를 일치시키고 디스크의 스파이크가 이미
증명한 항목의 재검증에 3~4일을 계획했으며, 1,048줄 대화 서사를 더 줘도 결정은 바뀌되
재검증은 줄지 않았다 — 결정은 기록으로 전달되고, 재검증을 줄이는 것은 재현 가능한 증거뿐이다.
앞선 세 기제(기획 JSON, journal 예약 줄, product.md 증분 착지)는 전부 같은 축 — 만든 것을
언제 누가 지우는가 — 에서 죽었다. 맥락 없는 제3 실행 검증은 문자적 세션이 affects 토큰을
지어 쓰고, 투영을 눈으로 거르고, 재현 명령을 지어 적으리라고 자기 신고했다.

선택한 경계: `devflow/project/decisions/`·`devflow/project/evidence/`의 결정·증거 기록과
고정 헤더 한 줄(v·kind·during 6값·affects 리터럴·scope·mode·evidence·checked-at·review-after·supersedes),
본문 상한 15줄; 기록 게이트 세 문장 + echo 3줄 + `record — <파일명>` 구속 결정 커밋;
기록 도구의 읽기 전용 하위 명령 다섯이 선택·역검색·삭제 판정의 유일한 수단이고 파일은 세션이 직접 쓰며 `validate`를 통과; 현재 집합 = 유효 전체 − supersedes 대상;
개봉 상한 3과 미개봉 현재 후보를 열거하는 bind 직전 확인; 승인 없는 관측의 정직한 등급
`mode: reported`(`reproducible`과 분리); 능력 문서의 설계
진술이 실제로 인용하는 현재 결정 기록의 구속 ADR 목록 편입(갱신은 arch·adopt만);
잔여 인용을 발견→갱신 표로 수리하는 사람 삭제 공인 예외.

경계가 필요한 이유: 불변+승계에는 소비·삭제·병합 생애주기가 없다 — 세 전임자를 죽인 그
축이다. 도구는 제3 검증이 하중 지점 둘(현재 집합 필터링·리터럴 토큰)에서 프롬프트만으로는
지켜지지 않음을 실측했기 때문에 존재하고, `mode: reported` 등급은 재현 경로 부재 검사와 다음 세션의 재현 실패로 드러날
날조보다 정직이 싸게 만든다. 도구는 무상태 읽기 전용이다 — 기록은 세션이 쓰고 삭제는
사람이 하며 도구는 판정만 한다.

기각 대안과 계보 반증: DR-14 — 읽히지 않는 등록 필드가 아니다: 소비자가 열거되고(생산자
여섯 — design·work 포함; arch·adopt·resume과 verify 회고의 `select` 투영; 카드 `읽을 것`;
구속 목록), 밖 캐시 처방이 아니라
devflow 소유이며, 현재값·이유·관측의 거처가 갈라져 있다. DR-25 — 판단어가 없다: 정확한
affects 리터럴, 도구가 계산하는 현재 집합, 상한 3, bind 직전 확인. DR-29 — 세션·날짜
묶음이 아니다: 기록은 닫기 의무가 없는 영구 결정 단위이고, 도구가 판정한 무참조 잎만
지워진다. DR-38 — 기록된 사유는 "helper의 필요성이 논증된 적 없다"였다; 제3 검증이 실측으로
논증했고, SessionStart 훅이 이미 같은 플러그인 상대 경로로 `scripts/` 코드를 실행하며,
도구는 무상태 읽기 전용이라 아무것도 쓰거나 지우지 않는다. 정본의 "그 밖에 기획 문서를 새로 만들지 않는다"는
뒤집힌 것이 아니라 자기 목록을 넓혔다.

영향 좌표: principles 쌍(기획 기록 절·발견→갱신 행·소유권), planning-evidence 쌍(기록
게이트와 투영), product·arch·design·split·work·resume·adopt·verify 쌍, baseline 판정 5행,
`scripts/project-records.mjs`, `scripts/repository-invariants.test.js`.
재검토 조건: 실전 6시간 A/B에서 게이트 누락 관측; 정상 split의 bind 중지 10% 초과; 현재
집합 투영 200줄 초과 보고; reported 등급 비율이 재검증 절감을 무력화.

### DD-75 · 기록의 승계 — 현재는 승계 기록 하나로 바뀌고, 낡은 증거는 역검색으로 의존 결정을 열거하며, 상충·동시 기록은 보존 뒤 사용자 확인 승계로 합쳐진다 (v0.18.0)

주제: 지식층과 능력 문서 | 도입: v0.18.0 | 상태: 대체됨 → DD-77 (v0.18.2)

불변은 역사의 성질이지 현재의 성질이 아니다: 모든 뒤집기의 비용은 전임을 supersedes로
지목하는 승계 기록 하나다. 측정 반증 없이 사용자가 확정 문장을 스스로 바꾸는 것은 발견→갱신
표의 정식 행이다 — 그 대화가 곧 확인이고 'owner decision'이면 근거로 족하다 — 이로써 그런
변경이 product 전체 재실행을 요구하던 백로그 관측이 정산된다. 증거가 낡으면(승계가 있거나
`Invalidates-when`이 참) `reverse-evidence`가 그것을 인용하는 현재 결정 기록을 열거하고,
각각은 재확인되거나 소유 단계로 돌아가며, 아무것도 자동 무효화되지 않는다(보고만 하고 자동
수정하지 않는다는 정합성 원리). 내용이 다르면 content-addressed 파일명이 이미 다르므로 같은
경로 충돌은 없다. 양립 불가한 현재 기록 둘은 발견 세션이 스스로 고르지 않고 사용자에게 1회
물어, 확인된 승계 하나가 둘을 supersede한다. 봉쇄
중 고유 기록 파일의 추가는 자기 브랜치 로컬 커밋으로 계속하되 공유 권위가 아니다 — 이는
DD-62를 일부 정정한다: 그 "push가 필요한 증거 기록"은 journal의 `증거 대기` 기록을
가리켰고, 두 개념은 이제 다른 이름을 가지며, 승계·삭제·Layer 0 변경은 계속 기다린다.

영향 좌표: DD-74와 같은 집합. 재검토 조건: 이 규칙이 분류하지 못하는 소실이나 이중 계획을
병합·동시성 장면이 만들 때.

### DD-76 · 도메인 지식 캡슐 — 능력 문서를 넘치는 지식은 같은 번호 아래 필요 개봉 캡슐로 살고, 출처 표기가 원문·종합·추정·다툼을 가른다 (v0.18.1)

주제: 지식층과 능력 문서 | 도입: v0.18.1 | 상태: 유효 · 일부 정정 → DD-77 (v0.18.2), DD-92 (v0.20.0)

관찰된 문제: 실전 브라운필드(jgnote property)의 한 능력 도메인 원문이 3,699줄이었다 — 185줄
능력 문서에 요약으로 눌러 담으면 지식이 소실되고, 안 담으면 다음 세션에 존재하지 않는다.
실물 가공 두 벌과 3팔 이해도 실측(가공본 A·B 대 원문 대조군 C, 동일 문항 13개)이 두 사실을
줬다: 방향 이해는 가공본으로 전달된다(3팔 전원이 방향 문항을 옳게 거부). 그러나 **가공이

보강 "교체한다")을 한쪽으로 밀어 확정 사실처럼 적었고, 가공자가 종합한 문장이 원문 문장과
구분되지 않았으며, 원문을 읽은 C의 정직한 모름이 가공본의 매끄러운 확신보다 정확했다.

선택한 경계: 능력 문서는 항상 읽는 지도로 유지하고(총 상한 약 185줄 유지, 실측 근거 없던
절별 행 수치는 소프트로 전환, 관통 의도의 무조건 도달 지점인 Intent 총론 절 추가), 넘치는
지식은 같은 능력 번호 아래 `NN-<이름>/K-NNN-<주제>.md` 캡슐로 내린다 — 첫 줄 knowledge
헤더(topic·use-when·state·synopsis)만 기계 투영하고 본문은 필요할 때만 연다. 저작 상한은
캡슐당 120줄 소프트+초과 보고, 개봉 상한은 카드당 합계 240줄/24KiB 하드+명시 승인 출구
(잠정값 — 실측 개봉 112~180줄). 출처 표기는 무표가 기본값이고(본문 무표=원문·확신, Intent
무표=종합) 닫힌 머리말 넷(`synthesis`·`code`·`conjecture`·`dispute C-n`)만 예외를 가른다 —
의무 부착안은 기각했다: 9할이 같은 값인 필수 칸은 소유자가 금지한 빈칸 양식이고, 교차
검증에서 의무 꼬리표를 단 실물이 잘못된 출처 날짜를 검사기 통과로 실어 형식 검증이 출처
검증이 아님을 실증했다. 원문 모순은 해소하지 않고 dispute 두 팔로 좌표와 함께 보존해
사람의 결정거리로 올린다. 무표 종합의 기계 미탐지는 쓰기 층 도장이 아니라 검증 층에서
막는다 — adopt 가공 절차의 깨끗한 세션 반증에 캡슐당 무표 문장 3개의 출처 표본 검사를
넣었다. 원문 처분(삭제·이동)은 절차에 없다 — 사람 전속.

기각 계보 반박: DR-30(능력별 작업 노트 새 계층 기각)의 사유는 "중계 노트는 이미 네 층으로
존재한다"였다 — 캡슐은 다섯째 자유 노트층이 아니라 능력 문서의 용량 초과분이 같은 번호
아래로 내려간 것이고, 작성자·확인·커밋이 능력 설계 커밋과 같으며 자유 기록이 아니라 고정
헤더·닫힌 표기·개봉 예산의 유계 계약이다. 신설을 정당화하는 것은 취향이 아니라 3,699줄
실측이다. DR-19(파일 둘 분리 기각 — "경로 둘·읽기 두 배")는 항상 읽는 경로에 대한
사유다 — 캡슐은 항상 읽지 않고 개봉 예산이 하드라 고정 읽기가 늘지 않는다. DR-25·DR-17
(무유계 읽기·자유 링크 기각)은 유지된다 — 캡슐 도달은 정확 경로(`읽을 것`)와 use-when
매칭뿐이고 개봉 합계가 하드 상한이다. DD-28의 "새 문서층 금지"는 DD-74와 같은 방식으로
자기 목록을 넓혔고, DD-42·43의 능력 문서 단독 소유와 DD-44의 번호 도달은 캡슐 폴더·헤더
투영 도달로 각각 일부 정정된다.

영향 좌표: 기준선 판정 정본(캡슐·출처 표기·개봉 예산 절), 규칙 정본(소유·능력 설계 커밋),
arch·adopt·split·work·resume·verify 쌍, `scripts/repository-invariants.test.js`.
재검토 조건: 이해도 문답 실패율(가공본만 읽은 세션이 원문 모순·종합을 오답), 개봉 예산 초과
보고 비율, dispute가 수집되지 않고 남는 비율, 캡슐 없는 능력에서 능력 문서 초과 보고가
반복될 때의 예산 재조정.

### DD-77 · 문서는 현재만 말한다 — 같은 개념이 갱신되면 그 개념의 자리를 덮어쓰고, 버린 방향은 그 결론 옆에 현재 사실로 산다 (v0.18.2)

주제: 지식층과 능력 문서 | 도입: v0.18.2 | 상태: 유효

관측된 문제: 정본 한 파일이 55줄 간격으로 자기와 반대말을 했다 — `SKILL.md:390`은 "고치거나
지우지 말고 뒤를 잇는 기록을 하나 더해라"였고 `:445-447`은 "수정은 기본이 교체다. 한 줄을
더했으면 낡은 줄을 지웠는지 확인해라. 자라기만 하는 문서는 죽은 문서다"였다. 앞은 기록
계층에만, 뒤는 문서에만 적용됐고 문자적으로 실행하는 세션은 그 구분을 정확히 지켰다 —
문서는 자라지 않고 기록 폴더만 영원히 자랐다. 대가가 실측됐다: 폐기된 결정 파일 하나를
연 채점 세션이 "문장이 단호했고 근거도 버린 대안도 있었다. 나는 다 풀었다고 생각했다 …
골라 열었다면 폐기된 결정을 현행이라고 자신 있게 보고했을 것이다. 577줄이라 통독이 됐으니
망정이지 5,770줄이었으면 나는 틀렸다"라고 적었다. 무효라는 사실이 그 파일 어디에도 없고
다른 파일의 `supersedes` 배열 안에만 있었기 때문이다.

원하는 행동: 같은 개념이 갱신되면 그 개념의 자리를 덮어쓴다 — 파일이 아니라 개념을. 버린
방향과 그 이유는 과거가 아니라 현재 사실이고 그 결론 옆에 산다: 무엇을 버렸고, 왜, 언제
다시 여는가. 읽는 조건만 다르다 — 그 결론을 뒤집으려 할 때만 연다. 지나간 판본은 git이
지고 평소에 읽지 않으며, 덮어쓴 커밋 제목이 개념 이름을 색인한다.

선택한 경계: 덮어쓰기를 무제한으로 두지 않는 네 조건이다. ① 덮어쓸 수 있는 것은 재계산
가능한 것뿐이다 — 실행 결과·관측·사람의 확인은 덮어쓰기 전에 그 문서가 그것을 두는 자리에
먼저 착지시킨다(어느 자리인지는 발견→갱신 표가 정한다). ② 갱신인가 버림인가는 독자의
행동으로 가른다 — 옛 문장을 지금 읽은 사람이 잘못된 행동을 하는가. 그렇다면 「버린 방향」
으로 남기고, 아니면 그냥 덮어쓴다. ③ 도입 시점(브라운필드)에는 덮어쓰지 않는다 — 코드로
확인한 것만 새로 쓰고, 나머지 옛 문서는 삭제도 승격도 하지 않고 출처로 남긴다. ④ 「한 사실,
하나의 거처」가 이 법칙의 전제 조건이 된다 — 사본이 다른 가지에 있으면 덮어쓸 자리를 못 찾아
모순이 남는다.

경계가 필요한 이유: DD-74의 핵심 논거는 "불변+승계에는 소비·삭제·병합 생애주기가 없다"였고,
그것이 앞선 세 기제를 죽인 축이었다. 법칙은 그 축을 회피하지 않고 답한다 — 그 개념을 갱신하는
세션이, 갱신하는 그 순간에, 그 개념의 하나뿐인 거처에서 덮어쓴다. 별도 소비·삭제·병합
생애주기가 필요 없는 것은 별도 파일이 없기 때문이고, 이것은 새 기제도 아니다: 발견→갱신 표
21행이 다른 모든 지식에 대해 이미 정확히 그렇게 한다("옆에 더하지 말고 교체한다" ·
"그 진술만 교체한다" · "그 정확한 경로를 교체하거나 지운다"). 회피의 청구서가 위의 실측이다 —
지우지 않으면 죽은 것이 살아 있는 척한다. DD-74가 자기 손으로 적은 재검토 조건 넷 중
"reported 등급 비율이 재검증 절감을 무력화"가 최댓값으로 충족됐다: 같은 재료를 현행 기록
계층으로 옮기자 증거 6편 중 6편이 `reported`였고 코드 좌표는 0/6이었다(실험 결과가 저장소
밖에 있어 `mode: reproducible`을 검사기가 거부한다). 그리고 형태는 값이 아니었다 — 같은
재료를 네 형태로 지어 같은 13문항에 걸었더니 넷 다 9/13이었고, "이 실험을 다시 해야 한다"를
네 형태 전부 0으로 만든 것은 기록 등급이 아니라 숫자 옆에 그 숫자가 참인 조건과 재현 명령을
같이 적은 것 하나였다. 강제할 프롬프트가 필요 없어지는 것이 강제를 잘하는 것보다 낫다:
현재 집합 필터링은 승계된 기록이 없으므로 거를 것이 사라지고, `affects` 리터럴 토큰은 한국어
괄호가 파서를 터뜨리는데 `(근거:`를 결정 32편 중 28편이 썼다.

기각한 대안: 기록 계층을 남기되 승계 대신 제자리 덮어쓰기로 바꾸는 안. 배선 전수가 그 안으로만
옮길 수 있고 이 법칙으로는 못 옮기는 항목을 하나도 내지 않아, 한 일에 두 기제를 유지할 이유가
없었다. 기존 ADR 파일은 이 기각과 무관하게 그대로 둔다 — 새 승계 관행만 쓰지 않는다.

영향 좌표: 정본 규칙 쌍(발견→갱신 표 앞의 법칙 문단, 삭제된 기획 기록 절, 소유권),
planning-evidence 쌍, 기준선 판정 쌍(캡슐 머리 두 줄·본문 낱말 넷·삭제된 `retired` 묘비),
product·arch·design·split·work·resume·adopt·verify 쌍, `scripts/project-knowledge.mjs`,
삭제된 `scripts/project-records.mjs`, `scripts/repository-invariants.test.js`.
재검토 조건: 이유를 소유 문서 안에 두는 것이 실제 프로젝트에서 소유 문서를 예산 밖으로 미는
것이 관측될 때. 또는 「같은 개념」의 자리를 못 찾아 사본이 남는 모순이 실제로 관측될 때.

### DD-78 · 정본 한 구간은 도구가 그 구간의 대상이 없음을 증명할 때만 읽지 않는다 — 기계가 가르고, HEAD와 워킹 트리를 둘 다 보고, 나머지 모든 답은 통독으로 무너진다 (v0.18.5, 범위 확장 v0.19.0)

주제: 지식층과 능력 문서 | 도입: v0.18.5 | 상태: 유효

관측된 문제: resume 진입이 프로젝트 파일을 한 글자도 읽기 전에 정본 147,921 B를 문다.
두 설계 팔이 서로를 모른 채 그 147,921 B를 절 단위로 분해했고 같은 결론에 닿았다 — 디스크
상태로 안전하게 가를 수 있는 자리는 정본 전체에서 캡슐 계약 한 구간뿐이다. 이유는 분량이
아니라 배치다: 정본은 **주제축**으로 묶여 있고 디스크 상태는 **상태축**으로 걸린다. 두 축이
어긋나 있어 대부분의 조건이 가리키는 규칙은 연속 구간이 아니다(`evidence-wait`는 정본 안에서
12지점에 흩어져 있고 그 복구 규칙은 40행짜리 단일 표다). 조건은 연속 구간만 가를 수 있다.

원하는 행동: 캡슐이 하나도 없는 프로젝트는 캡슐 계약을 읽지 않는다. 캡슐이 있을 수 있는
모든 상태에서는 지금과 똑같이 전부 읽는다. **그리고 첫 캡슐을 쓰는 세션은 막히지 않는다** —
캡슐이 아직 없다는 사실 자체가 곧 첫 캡슐을 써야 하는 상태이기 때문이다.

선택한 경계: 다섯이다. ① **가르는 것은 기계다.** 모델이 디스크를 보고 판정하지 않는다 —
`project-knowledge.mjs presence`가 한 줄로 답하고 스킬은 그 낱말만 본다. ② **fail-closed.**
`absent` 하나만 구간을 닫고 `present`·`unknown`·비정상 종료는 전부 통독으로 무너진다.
③ **HEAD와 워킹 트리 둘 다**를 본다 — 통합 브랜치에 실린 캡슐은 이 체크아웃이 아직 안 썼어도
실재하고, 워킹 트리에서 지운 캡슐도 HEAD에 남아 있다. ④ **정본은 1바이트도 안 옮긴다.**
구간을 쪼개지도, 새 문서를 만들지도 않는다. ⑤ **첫 작성자에게는 조건이 다르다**(v0.19.0).
resume·verify의 presence 게이트는 그대로다. arch와 adopt는 나머지 구역을 먼저 읽고,
**이름 있는 원문 문서를 실제로 가공하거나, 도출한 능력 문서가 예산을 넘기기 직전**에 이 구간을
연다. 판단이 불명확하면 읽는 fail-closed다. 캡슐 계약은 `baseline-predicates{,_ko}.md` 안의
241줄·16,076 B 연속 구역 그대로이고, 여기서도 1바이트도 안 옮긴다.

경계가 필요한 이유: 이 게이트의 유일한 현실적 실패는 「필요한데 안 읽는」이고, 그 경로는 둘뿐
이다. 하나는 술어가 자신 있게 틀리는 것 — v0.18.4가 실물로 보여 줬다. `project`는 이름이
규격에 안 맞는 폴더를 조용히 건너뛰고 `capsules=0`을 낸다(재현: 그 폴더에 캡슐을 두고
`project`를 돌리면 지금도 `capsules=0`이다). 그래서 `presence`는 캡슐을 **세지 않고**
capabilities 아래 직계 자식 디렉터리의 **존재**만 본다 — 이름이 무엇이든, 폴더가 비어 있어도
`present`다. 다른 하나는 다음 세대가 캡슐 없는 프로젝트도 실행해야 하는 규칙을 이 구간 안에
써 넣는 것이고, 열거형 봉인 시험이 그 자리를 지킨다. 두 경로 다 시험이 있다.

기각한 대안: **훅이 판정해 주입한다** — 술어가 훅(JS)과 스킬 문장 두 곳에 살아야 하고
(스킬은 훅 없이도 돌아야 한다), 두 판정이 어긋나면 오류 없이 갈린다. DD-05·DD-29와
DR-03(훅의 journal 주입 — resume이 읽는 것을 중복한다)이 그대로 성립한다.
**기존 `project`의 `capsules=` 출력을 쓴다** — 위의 실측이 그 수를 술어로 못 쓴다고 답했다.
**인증서(authority id·fingerprint)를 발급하고 보고 직전에 재대조한다** — 판정과 보고 사이의
race를 좁히지만, 그 사이에 캡슐을 만든 세션이 있다면 이 세션이 그 캡슐을 이미 못 본 것이
아니라 아직 안 만들어진 것을 안 본 것이다. 새 기제 하나를 잔여 위험 0이 아닌 곳에 쓴다.
**첫 작성자에게도 단순 부재(`absent`)를 조건으로 쓴다** — bootstrap deadlock이다. 캡슐이 없는
상태가 곧 첫 캡슐을 써야 하는 상태이므로, 부재를 조건으로 걸면 첫 캡슐은 영원히 안 생긴다.
그래서 arch·adopt의 조건은 디스크의 부재가 아니라 **작성 사건**이다.
**DR-44(소비자별 정본 분할)의 재제안이 아니다** — 아무것도 옮기지 않으므로 그 기각 이유를
반증할 필요가 없고, 반증하지도 않았다. v0.19.0의 범위 확장도 같다: DR-44가 적은 실패 모드는
「work가 필요한 규칙이 verify 전용 제목 아래로 들어가 오류 없이 사라진다」인데, 여기서는
**구역 이동 0 · 명시된 소비자 넷(resume·verify·arch·adopt) · 기계 봉인 시험** 셋이 그 경로를
각각 막는다.

정직한 회계: 이 게이트의 천장은 **16,076 B(10.87%)**다. 진입의 95.0%는 경쟁작이 아예 하지 않는
세 기능(중단 복구·동시성 안전·지식 수명주기)의 규칙 본문이고, 이 각도로는 안 줄어든다.

영향 좌표: `skills/resume/SKILL{,_ko}.md` 진입 문단, `skills/verify/SKILL{,_ko}.md` 진입 문단,
`skills/arch/SKILL{,_ko}.md`와 `skills/adopt/SKILL{,_ko}.md`의 캡슐 개봉 조건,
`skills/principles/baseline-predicates{,_ko}.md`의 캡슐 구역 경계,
`scripts/project-knowledge.mjs`의 `presence`, `scripts/project-knowledge.test.js`,
`scripts/repository-invariants.test.js`.

### DD-91 · glossary는 프로젝트 언어 정본이고 능력 머리의 개념 색인은 정의 없는 다중 발견 소비자이며, 확인된 새 용어는 기존 journal을 거쳐 설계 작성자가 원자적으로 승격한다 (v0.19.0)

주제: 지식층과 능력 문서 | 도입: v0.19.0 | 상태: 유효

관측된 문제: 실사용 프로젝트의 glossary에는 정의가 있었지만 능력 문서 머리에는 그 용어를
찾을 색인이 없었다. 새 세션은 보통 용어 하나의 능력을 찾으려 모든 본문을 열어야 했고, 여러
능력에 걸친 같은 용어는 카드 번호 하나를 의미 소유자로 오인하기 쉬웠다. 구현 중 확정된 중요
용어는 glossary 작성자까지 가는 중단 내성 경로도 없어 동의어가 다음 세션에서 갈라질 수 있었다.

선택한 경계: glossary.md가 하나뿐인 프로젝트 언어 정본이며 `term: definition`을 소유한다.
능력 문서의 고정 머리에는 `Concepts:` 한 줄을 두되 정확한 glossary 용어의 JSON 배열 또는
`none`만 쓴다. 정의는 복사하지 않고, 한 용어가 여러 능력 머리에 나올 수 있으며, 프로젝트
전체 용어는 어느 머리에도 없을 수 있다. resume의 정확 용어 질의는 일치한 능력 경로 전부를
반환하고 매핑이 없으면 glossary 정의와 프로젝트 루트 문맥만 반환한다. 번호·전체 이름·foundation·
카드 인식은 그대로다. 카드의 `Concepts:`는 필요할 때만 쓰는 정의 없는 발견 보조이며 카드
번호로 의미 소유권을 추론하지 않는다.

능력·카드·work에서 중요성이 확인된 새 용어는 사람이 확정한 정확 용어·정의·영향 능력 집합·
근거 locator를 기명 `glossary term` journal 줄 하나로 커밋한다. malformed·미커밋·알 수 없는
작성자 줄은 일반 항목으로 남는다. 도구의 `marker.glossary-term`이 일반 작업보다 먼저 기존
product 소유 glossary 작성자인 arch(브라운필드는 adopt)로 보낸다. 작성자는 glossary 정의를
먼저 구속 커밋하고 마커를 남긴 뒤, 같은 설계 배치에서 알려진 모든 영향 `Concepts:`와 Design
head를 갱신하고 마커를 지운다. 그 사이 마커가 다른 작업을 막으므로 중단 뒤에도 한 논리적
전환이며, 관측이 스스로 정본을 고치지 않는다. product·arch 단계의 확인은 정상 단계 경계에서
직접 착지할 수 있다.

기각한 대안: 정의를 능력 문서나 카드에 복사하는 안은 한 사실 두 거처다. 능력당 한 용어 또는
용어당 한 능력은 합성 작업을 거짓으로 만든다. 새 glossary 스킬이나 자유 노트층은 기존 product
소유와 journal 운송을 중복한다. 용어 후보를 자동 승격하는 안은 관측을 결정으로 바꾼다.

영향 좌표: 규칙 정본의 인식·journal 형식·발견→갱신·소유, 기준선 판정의 고정 머리,
product·arch·adopt·resume·split·work 쌍, project-state 도구와 집중 시험.
재검토 조건: 정확 용어 색인이 첫 진입의 관련 능력을 놓치거나 과도 태깅이 의미를 오도하는
실사용 장면, 또는 두 커밋 사이 마커가 정본과 머리의 불일치를 막지 못하는 장면이 관측될 때.

### DD-85 · tree 입력 revision hash는 process 경계에서 Git raw byte를 보존하며 Buffer 전달이 Windows 전용 shell pipe를 대체한다 (v0.19.0)

주제: Git 기계와 중단 복구 | 도입: v0.19.0 | 상태: 유효

DD-39는 기존 `cmd` binary pipe가 raw-byte hash와 같고 PowerShell 객체 파이프라인만
달랐음을 이미 측정했다. v0.19.0 S3 fixture는 이제 이관된 실행자를 직접 봉합한다.
그 결과는 정확한 `ls-tree -z` stdout `Buffer`를 입력한 `git hash-object --stdin`과 같다.
공백·shell metacharacter·Unicode가 든 경로도 그 byte를 그대로 보존한다. 첫 Git process의
정확한 stdout `Buffer`는 text decode나 shell parsing 없이 `git hash-object --stdin`의 stdin으로
넘어간다. 끝에 NUL byte 하나를 더하면 hash가 달라지고, 입력 Git 실패는 빈 hash가 아니라
`unresolved`로 남는다.

따라서 지켜야 할 경계는 특정 shell이 아니라 두 process 사이의 raw-byte 불변성이다. Windows
전용 `cmd /d /s /c` wrapper를 유지하면 같은 byte를 더 잘 보존하지 않으면서 quoting과 플랫폼
분기를 다시 만든다. PowerShell 객체 파이프라인은 실제 재현 사유가 그대로이므로 계속 금지한다.

영향 좌표: `skills/principles/scripts/project-state.mjs`의 tree-input hash 실행자,
`skills/principles/verification-predicates{,_ko}.md`의 raw-byte 불변식,
`scripts/project-state.test.js`의 S3 fixture, `scripts/repository-invariants.test.js`, DD-39.
재검토 조건: 지원 플랫폼에서 첫 Git process의 raw stdout `Buffer`를 직접 입력한 hash와 상태
도구 결과가 달라지거나, 두 Git process 사이 실행 경계가 바뀔 때. shell 선호만으로는 다시 열지 않는다.

### DD-39 · tree 입력 revision의 hash는 Windows에서 `cmd /d /s /c` 안의 이진 파이프로만 계산한다 (v0.9.21, 실행자 이관 v0.18.7)

주제: Git 기계와 중단 복구 | 도입: v0.9.21 | 상태: 유효 · 일부 정정 → DD-85 (v0.19.0)

실제 재현: 2026-08-11 이 저장소에서 PowerShell 5.1 객체 파이프라인이 `git ls-tree -r -z`의 NUL 포함 stdout을 건드려 hash를 실제로 오염시켰다 — POSIX 이진 파이프와 `cmd` 파이프는 같은 hash를, 객체 파이프라인만 다른 값을 냈다. install.ps1의 BOM 행과 같은 "실제 재현" 부류다. v0.18.7에서 이 계산의 실행자가 산문에서 상태 도구로 옮겨졌고, **경계는 코드 안에 그대로 보존된다** — POSIX는 네이티브 이진 파이프, Windows는 `cmd.exe /d /s /c` 안의 같은 파이프이며 NUL 포함 stdout을 문자열로 디코드하지 않는다. 실행자가 바뀐 것은 **경계가 불필요해졌다는 뜻이 아니다**: 기록된 이유를 반증한 프로토타입이 없으므로 이 행은 충족이 아니라 보존이고, 경계를 바꾸려면 등가성을 증명하고 새 결정을 기록해야 한다 (v0.18.7 구현에서 Node의 인자 전달이 명령 안 따옴표를 문자로 넘겨 revision을 `unresolved`로 만든 사고가 실제로 났고, 고친 것은 인자 전달이지 경계가 아니다)
