# 메모리 계층 파일 시스템 설계도 — devflow 0.15.2 스냅샷

작성 2026-08-15 · 기준 커밋 `9e8fbc4` · 이 문서는 **버전 스냅샷**이다.

## 0. 이 문서의 지위와 쓰는 법

devflow가 대상 프로젝트 안에 만드는 파일 시스템 — 우리가 "메모리 계층"이라 부르는 것 —
의 0.15.2 시점 설계도다. 세 가지 용도로 쓴다.

1. **이해**: 새 AI 세션이 이 문서 하나로 "무엇이 어디에 왜 있고, 어떤 결과를 기대하는가"를
   즉시 파악한다.
2. **대조**: 향후 개선이 이 구조를 바꿀 때, 바뀐 것이 무엇이고 그때는 왜 그랬는지를 이
   스냅샷과 대조한다.
3. **되돌림**: 개선이 잘못됐을 때 마지막으로 온전했던 계층 구조의 기준점이 된다.

형식 문자열·행 좌표의 정본은 언제나 배포 원문(`skills/**`)이다. 이 문서는 그 원문이 0.15.2
시점에 무엇이었는지의 **동결 사본 + 의도 해설**이며, 원문과 다르게 읽히면 그 버전의 원문이
이긴다. 설계도는 버전 단위로 이 폴더(`docs/blueprints/`)에 쌓이고, 기존 스냅샷은 고치지
않는다 — 다음 큰 구조 변화 때 새 버전 파일을 만든다.

## 1. 설계 철학 — 왜 파일 시스템이 기억인가

AI 세션은 언제든 죽는다. 컨텍스트는 압축되면 사라지고, 대화는 세션과 함께 증발한다.
그래서 devflow의 기억은 넷 중 어디에도 있지 않다: 모델의 컨텍스트(휘발), 대화 기록(휘발),
별도 DB(없음), 진행률 문서(반드시 낡는다). 기억은 오직 **git이 보존하는 파일 트리**에 있다.

이 선택이 낳는 네 개의 기둥:

1. **상태는 이름이다.** 작업의 진행 상태를 문서 안의 문장이 아니라 파일명 접미사
   (`.wip-<id>.` / `.done.` / `.stale.`)와 위치가 말한다. 문장은 낡아도 발각되지 않지만,
   이름은 스캔 한 번으로 전수 판정된다.
3. **커밋은 기억의 원자다.** "기록했다"는 "커밋했다"이다. 커밋 제목이 곧 전이의 이름이라,
   git log 자체가 프로젝트의 사건 연대기가 된다. 점유조차 파일 rename 커밋이다 — 락 파일이
   아니라 git 역사가 동시성의 심판이다.
3. **죽는 순간을 모른다는 전제.** 모든 쓰기는 "이 직후 세션이 죽으면 다음 세션이 무엇을
   보고 무엇을 해야 하는가"에 답을 갖게 설계됐다. 그래서 기록이 실행보다 먼저 온다(요청은
   코드를 읽기 전에 journal에, 진행 로그는 실행 전에, 마커는 구조 변경 전에).
4. **복구는 추측하지 않는다.** 부분 상태를 만나면 저장된 값만으로 유일하게 복원되거나,
   복원 불가면 정지·보고한다. 오판이 손상을 전파하는 것보다 멈추는 것을 택한다.

**기대하는 결과**: 세션 사망이 사실상 무해해진다(어느 지점에서 죽어도 resume의 상태표
한 행이 받는다). 지식이 세션을 넘어 쌓인다(carry 줄→다음 카드, 함정→능력 문서, 결정→핵심
문서). 같은 실패를 두 번째 만나면 알아본다(수리 계보). 이 성질들은 광고가 아니라 문자
실행으로 검증되는 계약이며, v0.15.x 검증 캠페인에서 12개 이상의 중단 지점 걷기로 확인됐다.

## 2. 전체 지도

```
<대상 저장소 루트>/
└─ devflow/
   ├─ project/                       ← Layer 0: 프로젝트의 "무엇·어떻게"의 정본 (느린 기억)
   │  ├─ product.md                  ← 정체성·능력·경계·성공 판정 (product 소유)
   │  ├─ glossary.md                 ← 용어 한 줄 정의 (product 소유, 전 스킬이 착지)
   │  ├─ arch.md                     ← 구성요소·stack·검증 창구·잠정값 (arch 소유)
   │  ├─ code-style.md               ← 스택 고유 선택·신뢰 경계, 1페이지 (arch 소유)
   │  ├─ design.md                   ← [선택] 디자인 여섯 결정 (design 소유; 구축은 카드가)
   │  ├─ decisions/ADR-NNN.md        ← 되돌리기 어려운 경계의 결정 기록 (arch 소유)
   │  └─ capabilities/NN-<이름>.md   ← 능력 지식 기준선: 설계 구역 + 검증 구역 (긴 기억)
   ├─ tree/                          ← Layer 1: 작업의 현재 (활성 기억 — 상태는 파일명)
   │  ├─ 01-foundation/              ← 골조 카드 (리포 셋업·검증 창구·공유 계약)
   │  ├─ NN-<능력이름>/              ← 능력 폴더 = product 능력 1:1, 그 안에 작업 카드
   │  │  ├─ NN.N-<작업>.md           ←   대기 / .wip-<id>.md 점유 / .done.md 완료 / .stale.md 묘비
   │  │  └─ verify.md                ←   능력층 검증 기록 (Record + 실패 이력 + 감리·회고)
   │  ├─ NN-<능력이름>.md            ← 아직 안 연 능력의 대기 파일 (제목 한 줄)
   │  └─ verify.md                   ← 제품층 검증 기록
   ├─ journal.md                     ← 전이 상태·교차 결정의 공유 게시판 (append 기본)
   └─ users/<id>/                    ← 세션 주체의 방 (개인 기억)
      ├─ owner.md                    ←   신원 두 줄 (id / git name,email)
      ├─ HANDOFF.md                  ←   다음 한 걸음 하나 (매번 전체 덮어쓰기)
      └─ digest.md                   ←   여기까지 소화했다는 commit hash
```

기억의 시간 축으로 보면: **journal·HANDOFF·digest**는 짧은 기억(전이 중 상태 — 소비되면
지워진다), **tree/**는 활성 기억(진행 중 작업 — 접미사로 늙는다), **project/**는 느린
기억(확인된 결정 — 재실행으로만 통째 갱신), **capabilities/·verify.md의 실패 이력**은 긴
기억(영구 축적 — 재검증이 덮어써도 이력은 보존)이다.

## 3. 계층별 상세 — 구조 · 소유 · 의도 · 기대

### 3.1 `devflow/project/` — Layer 0, 결정의 정본

| 파일 | 만드는 이 | 갱신 규칙 | 의도 |
|---|---|---|---|
| `product.md` | product 인터뷰(신설) / adopt 역산(기존) | product 소유. 정체성·능력·경계·성공 판정은 사용자 확인 후 커밋. 능력 목록은 append-only, 은퇴는 취소선 | 모든 카드가 복사해 갖는 "왜 만들었나"의 원천. 능력 행 순서가 트리 번호를 결정하므로 재배열 금지 |
| `glossary.md` | product와 동시 | `용어: 정의` 한 줄씩. 발견→갱신 표를 걷는 현재 스킬이 새 용어를 즉시 착지 | 1개념 1단어의 집행 장치 — 이름 충돌이 코드가 아니라 문서에서 잡힌다 |
| `arch.md` | arch / adopt 역산 | arch 소유(단 `기존 기록`은 adopt). 잠정값 행은 해소 카드 완료 때 실측으로 교체 | 되돌리기 어려운 선택의 거처. 검증 창구(`verify_channel`)가 여기 살아 verify가 "어떻게 실행하나"를 안다 |
| `code-style.md` | arch / adopt | 1페이지 상한 | 지식이 아니라 취향의 선언 — 모델이 아는 보편 원칙은 적지 않는다 |
| `design.md` | 선택한 design 실행 | **여섯 결정**(접근 방식·디자인 원천·토큰 전략·컴포넌트 전략·분해 축·검토 표면)만. 「안 함」도 유효한 값. 구축 사실은 정확한 한 줄 교체, 방향 변경은 기록-먼저 design 재실행 (DD-69) | design은 결정하고 split이 구축한다. 파일이 없어도 여섯 결정은 Layer 0 필드라, 방향 요청은 2a로 여기 온다 |
| `decisions/ADR-NNN.md` | 세 조건(되돌리기 어려움·비자명·실제 대안 검토) 충족 시 arch | 승계돼도 옛 ADR 보존 | "왜 그때 그랬나"가 뒤집을 때의 반박 대상이 된다 — 이 저장소 자신의 DD/DR 계보와 같은 원리 |

**핵심 계약**: 코어 문서는 소유 스킬의 전체 재실행으로만 통째 갱신된다. 예외는 발견→갱신
표가 지정한 정확한 한 줄뿐이며, 그 한 줄은 표를 걷는 현재 스킬이 수행한다. 사용자 확인
전의 문서는 **초안**이다 — 확인 전에는 어떤 코어 경로도 착지하지 않고, 중단으로 남은
미커밋 diff는 부분 진실로 쓰지 않고 HEAD에서 전체 재도출한다(0.15.1 G1).

**기대**: Layer 0를 매 카드가 다시 읽어도(불변식) 양이 통제된다 — 문서들이 결정만 담고
지식·진행을 담지 않기 때문. 잘못된 방향 전환이 조용히 스며들 수 없다 — 방향은 반드시
소유 스킬 재실행 + 사용자 확인이라는 좁은 문으로만 바뀐다.

### 3.2 `devflow/project/capabilities/` — 능력 지식 기준선 (긴 기억)

각 능력마다 한 파일. 정확히 하나의 `## Verified state` 헤딩이 두 구역을 가른다:

- **설계 구역** (파일 시작~경계, 약 45줄): H1+Purpose+Boundary+Trust 4줄 → Concept model
  (≤8행) → Invariants(≤8) → Non-goals(≤5) → Binding ADRs(≤5) → Design metadata(2필드).
  arch/adopt가 쓴다. "이 도메인은 어떻게 생겼어야 하는가"의 청사진.
- **검증 구역** (경계~EOF, 약 140줄): Main flow(mermaid ≤9노드) → Lifecycle(불법 전이가
  있을 때만) → Current behavior(≤10행) → Entrypoints(≤12행) → Consumed contracts(≤6행) →
  **Traps(≤10행: 증상/재현/원인/대신 할 것)** → Verify(≤8단계) → Verification metadata
  (5필드: Verified at·Covered cards·Scope paths·Consumed paths·Scope head).
  verify가 능력 폐쇄 때 **통째로 교체**한다(부분 갱신 금지 — 모순을 남기기 때문).

**신선도와 가설**: `Design head`(입력: product·arch·glossary 세 경로의 해시 — design.md는
의도적으로 제외, DD-43)와 `Scope head`가 스탬프다. 스탬프가 현재와 다르면 그 구역은
"참"이 아니라 **가설**로 강등된다 — 문서를 믿는 게 아니라 문서의 나이를 기계로 판정한다.

**의도와 기대**: 이것이 "지식이 쌓이는 곳"이다. 수리 카드가 잡은 함정은 폐쇄 때 Traps
행으로, 실제 행동은 Current behavior로 수확된다. 다음 세션이 이 능력을 다시 열면 카드
번호만으로 자동 도달한다(`읽을 것`에 적지 않아도). 185줄 캡은 "긴 기억은 요약된 기억"이라는
선언 — 원시 기록은 verify.md와 git에 있고, 여기는 다음 작업자가 읽을 정제본만 산다.

### 3.3 `devflow/tree/` — 작업의 현재 (활성 기억)

**번호는 정체성이다**: 골조 `01`, 능력은 product 능력 목록 순서로 `02`부터(은퇴 행도
셈에 포함 — 번호 재사용 금지). 자식은 `부모.한자리`(`02.3`→`02.3.1`), 중간 삽입은 소문자
접미사(`03.2b`). 끝난 번호는 다시 매기지 않는다 — 번호가 흔들리면 의존·계보·기준선이
전부 흔들리기 때문.

**카드의 4+α 필드**: 목적지(끝나면 무엇이 참인가) · 왜(없으면 사용자에게 무슨 일이) ·
금지(≤3줄) · 완료 신호(실행 가능한 확인) — 이 넷이 카드의 본질이고, 좌표·정체성(product
정체성 문단 복사)·의존·읽을 것·등급·승인·검토가 배선이다. **방법은 적지 않는다** — 방법은
모델의 것, 카드는 목적지의 것.

**상태 전이와 그 의미**:

```
<카드>.md ──(work claim 커밋)──> <카드>.wip-<id>.md ──(신호+검토+최종 커밋)──> <카드>.done.md
     │                                   │
     └──(상위 결정 변경/회수)──> <카드>.stale.md (묘비 — 역사, 삭제 금지)
```

점유가 커밋이므로 두 세션이 같은 카드를 잡으면 git이 먼저 착지한 쪽을 이기게 한다(패자는
진행 로그를 복사하고 물러난다). `.done.`은 내용 동결 — verify의 회귀 목록과 기준선
`Covered cards`의 입력이 된다. `.stale.`은 지우지 않는다 — 지우면 다음 세션이 같은 번호를
재발급하거나 같은 실수를 반복한다(묘비의 존재 이유).

**특수 카드**: 조사 카드(답이 산출물 — 좌표·정체성 주입 없음, 버리는 프로토타입은 완료
판정 전 삭제) · 해소 카드(arch 잠정값 행의 실측 담당 — 별도 문법 없이 번호만 잠정값 표에
기록) · 수정 카드(verify가 발급 — `왜`에 현재 non-pass와 직전 수리의 실패 결과, 완료
신호는 실패 재현의 실행 증명).

**기대**: 트리를 `ls` 한 번 스캔하면 프로젝트의 진행 전모가 나온다. 어떤 문서도 진행률을
주장하지 않으므로 낡은 진행 정보라는 것이 존재할 수 없다.

### 3.4 `devflow/journal.md` — 전이의 게시판 (짧은 기억)

append가 기본이고, 모든 예약 줄은 `timestamp + 종류 + 기계 필드` 형식이다. 핵심 줄들:

```text
<ts> 유지보수 라우팅 대기: 요청-json: <요청 전문 JSON>          ← 요청은 코드 읽기 전에 먼저 기록 (DD-50)
<ts> 층 열기: 부모: <경로>; 자식: <번호+번호>; 출처-json: <locator> ← 번호 발급의 구속 선언
<ts> 재분할 대기: 폴더: <경로>; 무효: <번호들>; 출처: <경로#절>    ← 상위 변경이 카드를 무효화했다는 표지
<ts> product 재실행 대기: 서술-json: <반증된 서술>
<ts> product 검증 요청 / 실행: ... / 결과: ...                  ← 제품 검증의 3단 마커
<ts> 능력 닫기: 폴더: ...; head: ...; <revision 3종>            ← 폐쇄 중단 복구의 닻
<ts> 증거 대기/마감: 카드-json: ...; checkpoint: ...; 점검-json: ... ← 원격(CI 등) 증거의 2단 마커
<ts> 감리 요청/회고 요청: <능력 번호|product>
```

각 줄은 **생산자→소비자→소거**의 생애가 고정돼 있다: 예컨대 유지보수 줄은 split이 쓰고,
split의 카드 계획 커밋이 소비하며 그 커밋에서 지워진다. 소비 전환이 아닌 방식으로 줄을
지우는 것은 금지 — 줄의 존재 자체가 "아직 안 끝난 전이"라는 상태이기 때문이다.

**기대**: 세션이 어디서 죽어도 journal에 남은 줄이 "무엇이 진행 중이었나"를 다음 세션에
알린다. resume은 이 줄들을 우선순위 표로 라우팅한다. 예약 밖 줄은 교차 과제 결정과 사람
미결 항목만 허용 — journal이 잡담장이 되는 것을 막는다.

### 3.5 `verify.md` — 판정의 기록 (긴 기억의 또 다른 절반)

능력 폴더마다 하나 + 트리 루트에 하나(제품층). Record 구조:

```markdown
# 검증 · <이름> · <날짜>
Product/Verification/Code/Capability revision: <4종 해시>   ← "무엇에 대한 판정인가"의 좌표
시나리오 / 실행 / 판정(통과|실패|미검증) / New entries
실패 이력:                                                  ← 영구 보존, 덮어쓰기 생존
- 출처 id: <id>; ts; 실패|미검증: …; 라우팅: 대기                      (1형식: label 없음)
- …; 신호 카드: <번호>; 라우팅: 대기                                   (2형식: 최초 재발 후보)
- …; 신호 카드: <번호>; 수리 계보: <root>; 재관측: <n>; 라우팅: 대기     (3형식: 계보 연결 재발)
회귀 / 표준 / 잠정값 / journal 정리
## 감리  ← 사건 상태
## 회고  ← 사건 상태
```

재검증은 Record를 덮어쓰지만 **실패 이력·감리·회고는 보존**된다(DD-30). 라우팅 값은
`대기 → (라우팅 준비: {base, result, operations}) → 수정 카드 NN.N(+NN.N)* | 문서 [...] |
product 재실행 <ts>`로만 전이한다.

**수리 계보(0.15.0의 핵심 추가)**: 완료된 수리의 신호가 다시 실패하면, verifier가 돌려준
신호 카드 label을 **저장된 카드 번호의 정확 일치**로 과거 route에 역색인해 같은
root(`<능력번호|product>@<최초 실패 id>`)에 연결한다. 새 수정 카드는 직전 수리 라운드의
카드들을 `읽을 것`으로 상속하고, 재관측 2부터는 자동 수리를 멈추고 사람에게 온다.
투영은 정확히 세 파일(현재 대상·트리 루트·label 소유 능력의 verify.md)만 읽는 유계 질의다.

**기대**: "한 번 만난 결함은 같은 문으로 두 번 나가지 못한다." 완료 신호는 회귀 목록에
영구 편입되고, 재발은 이전 시도의 증거를 들고 온 수리자가 맡으며, 반복 재발은 자동 루프가
아니라 사람의 결정이 된다.

### 3.6 `devflow/users/<id>/` — 세션 주체의 방 (개인 기억)

- `owner.md`: `id:`와 `git:` 두 줄 — 신원과 git 서명의 결속. 점유 접미사의 `<id>`가 여기서
  온다.
- `HANDOFF.md`: **다음 한 걸음 하나**(트리 경로 하나 또는 none)만 담고 매번 통째로
  덮어쓴다. 지식·함정·열린 결정을 담지 않는다 — 그것들은 정본 거처(능력 문서·journal·핵심
  문서)로 먼저 착지시킨 뒤에야 덮어쓸 수 있다. HANDOFF가 지식을 나르게 하면 덮어쓰기가
  곧 소실이기 때문이다.
- `digest.md`: "여기까지의 통합 역사를 소화했다"는 commit hash 하나. resume이 깨끗한
  경계에서만 전진시킨다 — 다중 세션 환경에서 "남이 한 일을 어디까지 알고 있나"의 눈금.

**기대**: 여러 사람·여러 터미널이 한 저장소에서 일해도, 각자의 "다음"과 "소화 지점"이
분리 보관되어 서로를 덮지 않는다. 방 이탈 시 열린 결정은 journal로 이관 후 방이 삭제된다
— 개인 기억은 개인과 함께 떠나되, 팀이 필요한 것은 공유 기억에 남긴다.

## 4. 커밋 아틀라스 — 기억의 원자 단위

제목이 곧 전이의 이름이다(전부 `<id> ` 접두). 주요 계열:

| 계열 | 제목 | 싣는 것 · 의미 |
|---|---|---|
| 합류 | `room — join` | 방 세 파일 — "내가 왔다" |
| Layer 0 | `product — product.md` / `arch — arch.md` / `arch — code-style.md` / `design — design.md` / `adopt — layer 0` | 확인된 핵심 문서만 — "방향이 정해졌다" |
| 능력 설계 | `arch\|adopt — capabilities` | 능력 문서 설계 구역 일괄 — "청사진이 갱신됐다" |
| 발급 | `split — begin <부모>` → `split — <연 층>` / `NN.N promote` | 마커 먼저, 카드·승인·마커 삭제가 한 계획 커밋 — "번호가 태어났다" |
| 요청 | `boundary — request recorded` | 유지보수 줄 하나 — "잊기 전에 적었다" |
| 작업 | `NN.N claim` → `NN.N wip: <내용>` → `NN.N <작업명>` | 점유 → 체크포인트(이 세션의 변경만) → 코드+카드+로그의 최종 — "한 걸음이 끝났다" |
| 경계 | `경계 정리 — <닫힌 것>` | 상태 rename·HANDOFF·journal 정리·verify.md — "닫힌 것을 닫았다고 기록했다" |
| 폐쇄 | `경계 정리 — begin <NN>` → 폐쇄 경계 | 통과 Record+닫기 마커+기준선 교체 → `.done` — "능력이 닫히고 지식이 수확됐다" |
| 경량 | `tweak <깊이1>: <무엇>` | 요청 산출물 경로만, devflow 경로 없음 — "기록이 곧 커밋인 작은 일" (DD-61) |

**기대**: `git log --oneline`만으로 "누가 언제 무엇을 결정·발급·점유·완료·폐쇄했는지"의
전 연대기가 복원된다. 커밋 규칙이 "자기 규칙이 명명한 경로만 싣는다"이므로, 커밋 하나가
곧 한 종류의 사건이다.

## 5. 기억의 흐름 — 시나리오별 서사

**새 프로젝트**: product 인터뷰(사실은 AI가 닫고 가치만 질문 — planning-evidence) →
`product — product.md` → arch(후보 생존 확인 → 창구 실행 가능성) → `arch — *` + 능력 문서
설계 구역 → [선택: design 여섯 결정] → split이 대기 파일 → 골조 → 첫 능력을 층층이 발급
→ work가 claim→구현→신호→clean reviewer→carry 줄→최종→경계 → 능력의 활성 카드가 전부
`.done`이면 verify가 시나리오+적대 입력+회귀를 실행 → 통과면 폐쇄: 기준선 검증 구역 통째
교체 + 감리·회고 사건 → 제품층 검증으로 MVP 판정.

**브라운필드**: adopt가 코드(현재)·고정 버전 문서(가능성)·소유자(미래)의 세 권위를 분리해
Layer 0를 역산 → 트리는 만들지 않고 대기 → 첫 변경 요청이 오면 journal에 먼저 기록 →
split 유지보수 라우팅이 기획 깊이 등급(0/1/2a/2b)으로 판정해 제 위치에 카드를 만든다.

**중단 복구**: 어느 지점에서 죽어도 — begin 커밋 뒤(마커가 출처에서 재구성), Record 쓰기 중
(완성성 판정으로 부분/완성 구분), 라우팅 준비 뒤(base+operations 접두 검증), evidence-wait
중(journal 2단 마커) — resume의 상태표 첫 일치 행이 정확히 한 가지 다음 행동을 지시한다.
공통 원칙: 재실행보다 "지정 커밋을 먼저 끝내라", 해석 불가면 정지·보고.

**다중 세션**: 점유는 rename 커밋 경쟁(패자 양보), 공유 진실은 통합 브랜치 tip 하나
(DD-51), journal은 3-way 병합에서 소비된 줄의 부활 금지, HANDOFF는 최신 헤더 승리,
봉쇄(네트워크 단절) 중에도 발급·점유·소비가 아닌 journal 덧붙임은 로컬로 즉시 기록.

## 6. 의도된 비용 — 왜 이 무게를 지불하는가

이 계층은 공짜가 아니다. 카드당 커밋 3+, 진입 고정비(규칙 텍스트 1,300~1,940줄), 승인
접점 7~9회(첫 코드까지), verify 한 번의 무게. 전부 **의도된 비용**이며 각각이 사는 이유:

- 커밋 밀도 → 죽는 순간을 모르므로, 기억의 원자를 잘게 — "나중에 커밋"이 곧 소실.
- 재읽기 → 압축 뒤 "읽었다"는 "가지고 있다"가 아니므로.
- 승인 접점 → 방향의 문을 좁게 — AI 개발의 고질인 조용한 범위 확장의 기계적 차단.
- clean 역할(reviewer/verifier/auditor/retrospector 각각 21~32줄 계약으로 격리) → 자기
  검증 통과라는 흔한 실패의 원천 차단.

**보장하지 않는 것**도 선언돼 있다(README 「보장하지 않는 것」 표가 정본): 같은 카드를 두
터미널이 동시에, force-push, 무공유 clone 둘, 하위 모델의 상태표 오일치 등.
