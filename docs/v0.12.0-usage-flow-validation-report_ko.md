## 0. 이 문서가 무엇을 판정하는가

이 검증은 기획서를 다시 구현하라는 검토가 아니다. 문서의 권위는 다음 순서로 두었다.

1. `docs/v0.12.0-usage-flow-report_ko.md` — 현재 구현에서 최종적으로 채택한 결정과 그 실행
   리포트
2. `skills/**`와 동반 정본·역할 계약 — AI가 실제로 문자 실행하는 현재 동작
3. `docs/design.md` — 그 동작을 선택한 이유와 기각 계보
4. `docs/plan-usage-flow_ko.md` — 구현 전 문제 정의와 비교 기준선

따라서 기획과 현재 리포트가 다르면 **현재 리포트의 결정이 이긴다.** 이 검증에서 결함으로 센
것은 “기획과 달라졌다”가 아니라 다음 네 종류뿐이다.

- 현재 리포트가 선언한 최종 동선과 실행 스킬이 서로 다른 경우
- 동일한 실행 정본 안에서 두 규칙을 함께 지킬 수 없는 경우
- 문서에 허용된 디스크 상태를 문자 그대로 걸었을 때 다음 행동이 정의되지 않거나 자료가
  소실되는 경우
- Claude 또는 Codex의 현재 전달 채널에서 설치된 규칙이 실제 세션에 도달하지 않는 경우

문구의 취향, 동의어 선택, 더 친절하게 쓸 수 있다는 의견은 결함에서 제외했다. 같은 문장을
다른 말로 고치는 반복을 피하기 위해 모든 확정 소견에는 **구체적인 시작 상태 → 문자 실행 →
잘못된 결과**를 붙였다. 그 경로가 없는 제안은 판단 항목 또는 관찰 항목으로 내렸다.

## 1. 결론부터

### 1.1 최종 판정

**0.12.0은 단일 흐름과 순차 실행에는 실제 사용 가능한 수준이지만, 릴리스의 핵심 주장인
동시 흐름까지 포함하면 아직 충분히 닫히지 않았다.**

가장 큰 이유는 문장의 미세한 모호성이 아니다. 현재 정본에는 공유 상태의 권위가 두 개 있다.

```
권위 A  공유 tree·journal·verify 상태 = 통합 브랜치 tip
권위 B  공유 tree 상태 = 통합 tip ∪ 살아 있는 모든 worktree HEAD
```

최초 점유는 반드시 통합 브랜치에 착지해야 한다. 그런데 완료 뒤에도 기능 워크트리 HEAD에
옛 `.wip-<id>.`가 남아 있을 수 있고, 권위 B는 그 옛 점유를 다시 현재 점유로 만든다. 정상적인
`claim → final task commit → boundary`를 끝낸 뒤 오히려 정합성 이상이 생긴다. 이것은
해석의 취향이 아니라 같은 카드 번호에 `.done.`과 `.wip-<id>.`를 동시에 만드는 재현 가능한
상태 충돌이다.

동시에 같은 작업 트리를 두 터미널이 쓰는 경로도 파일·인덱스·HANDOFF·journal 쓰기를
트랜잭션으로 만들지 않는다. 완료 신호를 능력 경로로 좁히는 것은 테스트 간섭을 줄이지만,
두 프로세스가 같은 파일을 읽고 서로 덮어쓰는 경쟁은 막지 못한다.

따라서 판정 범위는 다음처럼 나뉜다.

| 사용 범위 | 판정 | 근거 |
|---|---|---|
| 한 터미널, 한 작업 트리, 순차 카드 실행 | **조건부 사용 가능** | 점유·작업·검토·완료·복구의 주 동선이 닫혀 있음 |
| 한 터미널에서 여러 능력을 번갈아 수행 | **대체로 가능** | 능력 축 점유와 후보 순서는 작동. 같은 능력 파킹에는 결함 R-08 |
| 같은 작업 트리의 두 자율 세션 | **안전 보장 불가** | 공유 파일 lost update와 다른 세션의 미완성 변경 체크포인트 문제 |
| 여러 Git 워크트리의 자율 흐름 | **차단 결함 있음** | 원시 HEAD 합집합이 유령 점유·중복 번호를 만듦 |
| 중단 뒤 resume 복구 | **강함** | marker·최종 작업 커밋·경계 prefix 복구는 결정적. evidence 보고에는 결함 R-05 |
| Claude/Codex 의미 동형성 | **배포 경로는 통과** | Claude cache는 원본과 일치하고 Codex native plugin은 이 저장소를 직접 source로 등록 |
| Claude/Codex 세션 진입 보장 | **부분 실패** | 하위 디렉터리 SessionStart와 Codex 명시 프롬프트·신뢰 전환 문제 |
| 현장 검증 | **없음** | 현재 리포트도 0건이라고 명시함 |

### 1.2 릴리스 판단

- 현재 리포트의 **“GitHub에 아직 push하지 말 것”** 판단은 그대로 유지하는 편이 맞다.
- 0.12.0 전체를 폐기할 이유는 없다. 한 모드, 능력 축 점유, 후보 순서, `carry:`, 요청의
  기록/계획 분리 같은 중심 방향은 유효하다.
- 다만 **워크트리 HEAD 합집합과 같은 작업 트리 동시 쓰기 지원 범위**는 문장 보정 전에
  설계 결정을 다시 내려야 한다. 이 결정을 정하지 않고 세부 문구부터 고치면 규칙이 다시
  늘어나고 서로를 보정하는 루프로 돌아간다.
- 아래 확정 소견은 핵심 실행 결함 14건, 플랫폼 전달 결함 4건, 문서·증거 결함 3건이다.
  같은 원인의 증상은 가능한 한 하나로 묶었다.

## 2. 프로젝트에 대한 이해

### 2.1 프로젝트의 성격

devflow는 라이브러리 코드가 아니라 **AI 세션이 그대로 읽고 실행하는 개발 운영 체계**다.
프로젝트 상태는 대화 기억이 아니라 Git과 `devflow/` 아래 파일에 남는다. 따라서 일반 코드의
함수 호출 오류에 해당하는 것이 여기서는 다음 네 종류다.

- 상태 접미사와 커밋 순서가 서로 다른 현재를 가리킴
- 두 스킬이 동일한 상태에서 다른 다음 단계를 고름
- 한 문서의 생산자는 있지만 소비자 또는 종료 기점이 없음
- 설치 산출물이 있어도 세션 진입 시 AI에게 도달하지 않음

### 2.2 전체 흐름

새 프로젝트와 브라운필드는 Layer 0 진입만 다르고, 이후 같은 Layer 1을 사용한다.

```
새 프로젝트: product → arch → design(선택) → split → work ⇄ verify
브라운필드:  adopt ───────────────────────→ split → work ⇄ verify
새 세션:      resume ── 디스크 상태를 판정해 위 단계 중 정확히 하나로 라우팅
공통 정본:    principles + state/verification/baseline predicates
```

각 스킬의 책임은 다음과 같이 이해했다.

| 스킬 | 책임 |
|---|---|
| product | 문제·능력 구성·경계·성공 판정 확정 |
| arch | 구성 요소·스택·코드 구조·검증 창구와 능력 설계 구역 작성 |
| design | 선택적 UI 기반·토큰·디자인 시스템 전략 |
| adopt | 기존 코드에서 Layer 0과 능력 문서를 역산 |
| split | 트리를 한 층씩 열고 작업 카드·실행 제안·번호를 확정 |
| work | 작업 카드 하나를 점유하고 구현·완료 신호·검토·커밋·경계까지 수행 |
| verify | 능력/제품 수준을 실제 실행으로 검증하고 실패 라우팅·폐쇄 수행 |
| resume | 유계 디스크 읽기로 현재 상태를 복원하고 다음 단계 하나를 제안 |
| principles | 모든 스킬이 먼저 따르는 규칙 정본 |

`reviewer`, `verifier`, `auditor`, `retrospector`는 등록 에이전트가 아니라 매번 깨끗한 문맥에
그대로 전달되는 역할 계약이다. Codex 설치기는 평면 프롬프트가 상대 경로를 잃지 않도록 필요한
정본과 역할 계약을 각 프롬프트에 내장한다.

### 2.3 디스크 상태의 중심 축

- 작업 카드 접미사가 상태다: pending / `.wip-<id>.` / `.done.` / `.stale.`.
- 능력 폴더는 트리의 depth-1 단위이며 0.12.0의 동시 작업 단위다.
- `journal.md`는 예약 전이·다른 능력 관측·결정을 보존한다.
- 각 사람의 방은 `owner.md`, `HANDOFF.md`, `digest.md`를 가진다.
- 능력 문서는 설계 구역과 검증 구역을 한 고정 경계로 나누고, work는 작업 카드의 depth-1
  번호로 자동 진입한다.
- 구속 결정과 최초 점유는 통합 브랜치에 즉시 착지해야 한다.

### 2.4 0.12.0이 해결하려 한 문제

현재 리포트 기준의 목표는 다음 일곱 축으로 요약된다.

1. 사람 하나를 흐름 하나로 본 solo/multi 분기를 없애고 방을 항상 사용한다.
2. 점유를 `id × depth-1 능력` 축으로 옮겨 여러 능력의 동시 진행을 허용한다.
3. 사용자 지목 → 세션 단위 → 승계 단위 → 나머지라는 후보 순서를 하나로 정본화한다.
4. 같은 능력의 다음 카드에는 `carry:`, 다른 능력에는 `capability note`로 지식을 전달한다.
5. HANDOFF를 다음 한 단계와 열린 결정만 가진 작은 경계 문서로 줄인다.
6. 변경 요청은 즉시 보존하되 현재 점유가 끝난 뒤 계획한다.
7. Git을 필수로 하고 Git worktree 목록을 살아 있는 흐름의 등록부로 사용한다.

### 2.5 기획 뒤집기를 어떻게 다뤘는가

기획 뒤의 변경 자체는 결함으로 보지 않았다. 현재 리포트가 기록한 다음 반전은 합리적인
최종 결정으로 받아들였다.

- 대화 중 변경 요청의 **기록**은 점유보다 위, **계획**은 점유보다 아래로 분리
- 비-Git 축소 동작 삭제와 Git 필수화
- 원격 브랜치 필요 전제 폐기
- 완료 신호 범위화를 권고가 아니라 카드 생성 규칙으로 승격
- 지목 없는 여러 능력 후보에서는 추측하지 않고 사용자에게 질문

문제는 worktree를 흐름 **등록부**로 쓸 수 있다는 실측 사실에서, 각 worktree HEAD까지 현재
상태 **권위**로 격상한 부분이다. 객체가 다른 폴더에서 보인다는 사실은 그 객체가 현재 상태라는
뜻이 아니다. 이 한 단계가 현재 핵심 충돌을 만들었다.

### 3.2 사용한 렌즈

| 렌즈 | 질문 |
|---|---|
| 결정 계보 대조 | 새 결정이 앞선 결정의 이유를 실제로 반박했는가 |
| 독립 반박 | 이 설계를 깨뜨리는 최소 디스크 상태가 있는가 |
| 문자 실행 | 판단을 보태지 않는 AI가 각 문장을 순서대로 따르면 어디에 도달하는가 |
| 능숙한 사용자 동선 | 정상 사용에서 쓸데없는 정지·잘못된 제안·지식 소실이 있는가 |
| 좌표 스윕 | 카드 상태 × 라우팅 × 작업 공간 × 플랫폼의 안 걸어 본 칸이 있는가 |
| 과잉 하네스 감사 | 실패 경로 없이 규칙만 늘리는 제안인가 |
| 플랫폼 전달 감사 | 같은 의미 파일이 설치되는 것과 실제 세션에 도달하는 것이 모두 참인가 |

두 독립 렌즈에는 구현 맥락을 주지 않고 현재 파일만 주었다. 한 렌즈는 필수 사용 동선을
문자 실행했고, 다른 렌즈는 현재 설계를 반박했다. 소견 0건도 유효하다고 명시했다. 나온
소견은 다시 정본과 커밋 계보에서 재현되는 것만 이 문서에 채택했다.

### 3.3 심각도

| 등급 | 기준 |
|---|---|
| 차단 | 릴리스 핵심 동선에서 정상 상태가 모순·자료 소실·유령 상태로 끝남 |
| 높음 | 문서가 지원하는 상태에서 잘못된 라우팅, 지식 소실, 정의되지 않은 다음 행동이 재현됨 |
| 중간 | 조건부 업그레이드·복구·전환에서 멈춤 또는 잘못된 선택이 재현되며 우회가 있음 |
| 낮음 | 실행 정본은 보존되지만 문서·설치 안내·검증 증거가 현재 사실과 다름 |

실행하지 않기 때문에 아래 의미 결함을 반증하지는 않는다.

## 4. 잘 구성된 부분

결함만 나열하면 현재 구조를 잘못 평가하게 된다. 다음은 문자 실행에서 정상적으로 닫힌 부분이다.

### 4.1 한 모드와 능력 축 점유

- 방을 항상 사용해 solo/multi 분기 비용을 제거한 방향은 일관된다.
- 동일 id가 서로 다른 depth-1 능력에 점유를 하나씩 가질 수 있다는 규칙은 카드 후보 판정과
  정합성 항목에 대체로 같은 축으로 반영됐다.
- 사용자 지목이 있으면 그 능력이 먼저 오고, 지목 없이 여러 능력이 열려 있으면 resume은
  임의 선택하지 않고 질문한다.

### 4.2 요청 기록과 계획의 분리

대화 중 새 유지보수 요청은 journal 한 줄로 먼저 보존되고, 현재 점유가 있으면 계획은 그 카드의
경계 뒤로 미뤄진다. “잊지 않되 끊지 않는다”는 목표와 라우팅 표 순서가 맞는다. 이 순서는
판단 변경 없이 옮겨서는 안 된다.

### 4.3 정상적인 한 카드 수행

다음 순서는 한 작업 트리의 순차 실행에서 닫힌다.

```
준비 판정 → 통합 브랜치 최초 점유 → 카드/상위 문서/능력 문서 읽기
→ 구현과 진행 로그 → 완료 신호 → 깨끗한 검토
→ carry 판정 → 최종 작업 커밋 → 환류 → 완료 rename/HANDOFF 경계
```

완료 신호와 검토 뒤에만 `.done.`을 허용하고, 최종 작업 커밋과 경계를 분리해 중단 복구가
가능한 구조도 유지된다.

### 4.4 중단 복구

다음 복구 경로는 우선순위와 prefix가 구체적이며 재실행을 막는다.

- open rebase/merge 안전 정지
- `layer opening` marker의 같은 source·minted number 재사용
- 최종 작업 subject 뒤 두 번째 작업 커밋을 만들지 않는 경계 복구
- `capability closing` begin commit 뒤 step 8 suffix 복구
- 준비된 verify 라우팅 객체와 검증 상태 전이 복구
- malformed 예약 journal 줄의 쓰기 없는 정지

### 4.5 능력 지식 구조의 큰 방향

- work가 카드 번호로 능력 문서 하나를 자동 선택하는 구조는 카드마다 경로를 복제하지 않는다.
- 설계 구역과 검증 구역의 쓰기 소유권이 분리되어 있다.
- `carry:`는 카드 내부의 잔여 지식을 같은 능력의 다음 카드에 전달하고, 역할 계약에는 전달하지
  않아 독립 검토의 문맥 오염을 피한다.
- 다른 능력 관측을 직접 그 능력 문서에 쓰지 않고 journal 한 줄로 보내는 방향은 올바르다.

### 4.6 플랫폼 배포 동형성

- Claude와 Codex plugin manifest의 버전이 같다.
- 같은 `skills/`와 `hooks/hooks.json`을 배포한다.
- Codex 평면 프롬프트는 필요한 정본·판정 정본·역할 계약을 실제로 내장한다.
- Claude cache 사본의 확인 대상은 저장소 원본과 일치한다.
- Codex native plugin은 별도 복사본이 아니라 이 저장소를 local source로 직접 해석한다.

즉 플랫폼 문제는 “Claude용 문장과 Codex용 문장이 다르다”가 아니다. 공통 SessionStart 구현과
Codex의 보조 명시 호출 채널이 현재 플랫폼 계약을 완전히 따르지 않는 문제다.

## 6. 핵심 실행 결함 상세

### R-01 · 워크트리 HEAD 합집합이 완료된 점유를 되살린다

**등급: 차단**  
**근거:** `skills/principles/SKILL.md:73-83`, `skills/resume/SKILL.md:64-68`,
`skills/work/SKILL.md:101-107`, `docs/design.md:74,93`

서로 동시에 존재하는 규칙은 다음과 같다.

- 어느 worktree HEAD에든 점유가 있으면 점유된 것으로 본다.
- 다음 단계 라우팅과 정합성 점검의 공유 상태는 통합 tip에서 읽는다.
- 최초 점유는 통합 브랜치에 착지하고 현재 브랜치가 그 tip을 포함해야 한다.
- 최종 작업 커밋을 통합한 뒤 완료 rename은 통합 브랜치의 경계 커밋에 착지한다.

재현 상태:

1. 기능 워크트리의 HEAD `F`가 `04.6.wip-jmp.md`를 가진다.
2. 최종 작업 커밋을 통합한 뒤 통합 브랜치의 경계 `B`는 같은 카드를
   `04.6.done.md`로 바꾼다.
3. 기능 워크트리는 살아 있지만 HEAD가 `F`에 머문다. 이는 정상적인 Git 상태다.
4. 정본대로 `B ∪ F`를 읽으면 같은 번호의 `.done.`과 `.wip-jmp.`가 동시에 존재한다.
5. “어느 HEAD든 claim이면 claimed” 때문에 끝난 카드가 다시 점유가 된다.
6. 정합성 항목의 중복 번호 판정도 동시에 참이 된다.

잘못된 결과:

- resume이 완료된 카드를 work로 다시 보낼 수 있다.
- 또는 정합성 이상으로 모든 정상 라우팅을 멈춘다.
- 기능 워크트리 HEAD를 수동으로 전진시키거나 제거할 때까지 반복된다.
- 활성 카드에서도 통합의 옛 본문과 기능 HEAD의 새 진행 로그 중 어느 blob이 권위인지 없다.

계보 판정:

`git worktree list --porcelain`이 살아 있는 작업 공간을 열거한다는 측정은 맞다. 그러나
`docs/design.md:74`의 통합 직렬화 이유를 반박하지 않은 채 `docs/design.md:93`에서 모든 HEAD를
상태 권위로 올렸다. **등록부로서의 유효성은 상태 정본으로서의 유효성을 증명하지 않는다.**

개선 결정:

- 권장: 공유 tree 상태는 계속 통합 tip 하나에서 읽고, worktree 목록은 작업 공간·브랜치·통합
  보유자를 찾는 등록부로만 사용한다. 최초 점유가 통합에 있어야 하므로 다른 흐름도 점유 자체는
  이미 볼 수 있다.
- 대안: worktree HEAD를 상태 권위로 유지하려면 카드 번호별 ancestry, 동일 번호 blob 선택,
  stale HEAD 제외, 완료 후 feature HEAD 처리까지 완전한 투영 규칙이 필요하다. 이 방식은 새
  상태 기계를 만들며 정본 비용이 크다.

단순히 “최신 HEAD”라고 쓰면 안 된다. 서로 갈라진 두 HEAD에는 전역 최신이 없다.

### R-02 · 현재 리포트의 워크트리 대표 예제가 정본상 실행 불가다

**등급: 높음**

현재 리포트 §7.2는 다음 구조를 보여 준다.

```

~/proj-payment  feat-payment

~/proj-payment  work → 04.6 점유 커밋 (feat-payment에)
```

하지만 최초 점유는 구속 결정이므로 통합 브랜치에 착지해야 한다. 통합 브랜치가 `~/proj`에

- feature에서 main 갱신: “다른 worktree가 checkout한 통합 브랜치에는 쓰지 말고 정지” 위반

이 예제는 설명 문서의 오류지만 중요도가 높은 이유가 있다. 사용자가 0.12.0의 대표 워크트리
동선을 그대로 따라 할 때 첫 점유부터 실행 정본과 갈라진다. R-01을 고친 뒤 새 권위 모델에 맞춰
대표 예제를 실제 Git fixture로 실행해 다시 써야 한다.

### R-03 · 같은 작업 트리의 공유 상태 쓰기는 원자적이지 않다

**등급: 차단**  
**근거:** `skills/work/SKILL.md:93-94,369-390`,
`skills/principles/SKILL.md:636-639`, 현재 리포트 §7.1

현재 수리는 HANDOFF를 덮어쓰기 직전에 다시 읽고 열린 결정을 합집합으로 만든다. 이것은
순차적인 stale copy에는 유효하지만 두 세션이 같은 bytes를 동시에 읽는 경우에는 부족하다.

재현:

1. HANDOFF에 `D0`이 있다.
2. 능력 03의 세션 A와 능력 04의 세션 B가 같은 작업 트리에서 동시에 경계에 도달한다.
3. A가 HANDOFF를 다시 읽어 `D0`을 얻는다.
4. B도 A의 쓰기 전에 다시 읽어 `D0`을 얻는다.
5. A가 `D0 + D1`을 쓰고 커밋한다.
6. B가 미리 계산한 `D0 + D2`로 같은 파일을 덮고 새 HEAD 위에 커밋한다.
7. 같은 브랜치의 순차 커밋이므로 Git merge conflict는 없다. `D1`이 조용히 사라진다.

같은 위험은 journal, verify 경계, 상태 rename에도 있다. 또한 다른 능력 점유의 미커밋 변경을
발견한 세션이 그 카드의 `wip:` 체크포인트를 먼저 만들라는 규칙은, 그 변경을 작성 중인 다른
세션의 문맥과 파일 쓰기를 소유하지 않은 채 커밋하게 만든다. Git의 `index.lock`은 한 명령의
인덱스 갱신만 막지, “읽기 → 판단 → 파일 쓰기 → 커밋” 전체를 직렬화하지 않는다.

완료 신호 범위화는 이 문제의 해법이 아니다. 그것은 다른 능력의 미완성 코드가 테스트를 깨는
경우 일부를 줄일 뿐, 공유 파일의 lost update와 소스 파일 동시 편집은 막지 못한다.

권장 결정:

- **한 작업 트리에서 두 자율 세션의 동시 쓰기는 지원하지 않는다.** 여러 능력을 번갈아 수행할
  수는 있지만 한 시점의 writer는 하나로 직렬화한다.
- 실제 동시성은 작업 트리 격리를 제공하는 worktree로 한정한다.
- 정말 같은 작업 트리 동시 쓰기를 유지하려면 HANDOFF만이 아니라 모든 공유 상태에 lock 또는
  compare-and-retry를 정의해야 한다. stale lock 회수까지 새 상태 기계가 필요하므로 현재의
  “새 식별자·새 닫는 기점 없음” 방향과 맞지 않는다.

국소 문구 수리가 아니라 새 상태 기계다.

- [Codex hooks](https://learn.chatgpt.com/docs/hooks.md)

1. stdin의 `cwd`를 읽는다.
2. 그 위치에서 Git root까지만 위로 올라가 `devflow/`를 찾는다.
3. Claude의 환경 변수는 최적화로 사용할 수 있지만 공통 스크립트의 유일한 입력으로 만들지

  단계로 분리하거나, 신뢰 전까지 fallback AGENTS 안내를 유지한다.
- 현재 Codex CLI `0.146.0`에서 hooks는 stable·기본 활성이다. README의 `[features] hooks = true`
  필수 안내는 현재에는 불필요한 드리프트다. 구버전 최소 지원 정책이 있다면 버전 조건으로
  표현하고, 없으면 현재 native mechanism으로 갱신한다.

### 7.2 Codex 관리 worktree에 대한 제한

현재 Codex는 앱이 만든 worktree를 detached HEAD로 시작할 수 있다. devflow는 그런 worktree도
`git worktree list`에서 흐름으로 보지만 최초 점유는 통합 브랜치에 착지해야 한다. 통합 브랜치가
원래 checkout에 잡혀 있으면 관리 worktree의 세션은 안전하게 멈추는 것이 현재 정본상 맞다.

이것은 자료 손실 결함이라기보다 제품 결합 제한이다. 다만 “Codex worktree에서 자율 흐름을
바로 시작할 수 있다”는 기대와는 다르므로 다음 중 하나를 명시해야 한다.

- 통합 보유 checkout의 coordinator가 최초 점유·구속 결정을 대신 착지한다.
- Codex 관리 worktree에서는 점유 전 사용자가 통합 보유 위치에서 동기화한다.
- devflow가 해당 표면을 공식 지원하지 않는다.

worktree를 devflow가 만들거나 관리하지 않는다는 현재 결정을 유지한다면 첫 번째 또는 세 번째가
더 정직하다.

### 10.5 정의됨 / 해당 없음 / 자명 / gap 판정

- **정의됨:** 단일 흐름의 카드 생명주기, marker 복구, 사용자 지목/질문, 유지보수 기록 시점,
  능력 문서 번호 진입, Git 없음/identity 없음 안전 정지
- **해당 없음:** foundation은 능력 폐쇄를 갖지 않음, 역할 계약은 carry/note 소비자가 아님
- **자명:** worktree별 미커밋 파일과 index가 물리적으로 분리됨

  수명, malformed Covered cards, evidence 보고·room-upgrade path 보존, park 제외, recall tombstone, nested cwd hook,
  Codex fallback 호출/홈/신뢰

## 11. 판단 항목 — 소유자가 먼저 정해야 하는 것

다음은 결함 존재가 아니라 **개선 방식**에 판단이 필요한 항목이다. 여기서 결정을 내리지 않은 채
문장부터 고치면 서로 다른 해법이 동시에 정본에 들어간다.

### J-01 · worktree 목록은 등록부인가 상태 권위인가

권장 판정: **등록부다.**

- worktree의 존재, HEAD, branch, integration 보유 위치를 찾는 데 쓴다.
- 현행 공유 투영인 `devflow/project/`, `devflow/tree/`, journal, bounded verify는 통합 tip 하나가
  권위다. room 파일은 이 결정의 범위 밖이다.
- worktree-local 작업 commit은 그 흐름의 구현 증거이지, 아직 통합되지 않은 공유 상태가 아니다.

worktree HEAD도 권위로 유지하려면 R-01의 ancestry-aware projection을 별도 설계해야 한다.
현재 단순성·복구성·통합 직렬화 계보에는 권장안이 더 맞는다.

### J-02 · 같은 작업 트리의 “동시”가 무엇을 뜻하는가

권장 판정:

- 여러 능력을 **열어 두고 번갈아** 수행: 지원
- 같은 작업 트리에 두 AI 세션이 동시에 파일을 쓰고 커밋: 비지원
- 실제 병렬 실행: worktree 필요

완료 신호 범위화는 순차 전환과 일부 테스트 간섭을 줄이는 규칙으로 유지하되, 이를 파일 시스템
격리 보장으로 설명하지 않는다.

### J-03 · 통합 브랜치를 다른 worktree가 보유할 때의 자동성

현재 안전 정지는 옳다. 다만 사용자가 원하는 동시 흐름이 매 최초 점유마다 다른 폴더로 가서
착지시켜야 한다면 자동성은 낮다. devflow가 worktree를 관리하지 않는 결정을 유지할 때는
“통합 보유 세션/coordinator가 구속 결정을 착지한다”는 운영 경계를 README와 대표 예제에
정직하게 드러내야 한다.

### J-04 · 완료 신호를 능력 경로로 좁힐 수 없는 프로젝트

`whenever the means allows it`은 현실적으로 필요하다. 모든 빌드가 범위 실행을 지원하지 않는다.
그 경우의 정책을 정해야 한다.

- worktree 격리를 요구한다.
- 다른 흐름을 checkpoint하고 working tree를 깨끗이 만든 뒤 repo-wide 신호를 직렬 실행한다.
- 별도 verify channel을 만든다.

“가능한 경우 좁힌다”만으로는 가능하지 않은 경우의 실패 사다리 오진을 닫지 못한다.

### J-05 · deprecated Codex custom prompts를 계속 배포할 것인가

native plugin이 현재 정상이고 prompt 하나가 5만~12만 byte까지 커졌다. 명시 호출의 실제 사용자
가치와 하위 호환성을 측정한 뒤 유지 여부를 정한다. 유지하면 현재 `/prompts:` 이름과
`CODEX_HOME`을 지켜야 한다. 제거하면 native skill의 명시 호출 동선을 README에서 검증 가능한
형태로 제공해야 한다.

### J-06 · fresh HANDOFF의 exact path는 구속 포인터인가 단위 힌트인가

현재 리포트 §2.7은 `Next single step`을 “정본 후보 순서가 다음에 잡을 그 경로”라고 선언한다.
반면 현재 정본은 그 경로에서 depth-1 승계 단위만 뽑고 exact card는 버린다. 두 의미 중 하나를
선택해야 한다.

권장 판정: **fresh일 때는 exact card가 실제 포인터다.** 현재 리포트가 이미 사용자에게 약속한
의미를 보존하면서 HANDOFF를 단위 이름의 장황한 표기로 만들지 않는 선택이다. 다만 이것은
현행 후보 순서의 “기존 1순위”가 아니라 다음과 같은 **새 정본 규칙**이다.

1. 현재 대화에서 사용자가 exact card를 지목하면 그것이 항상 이긴다.
2. 사용자가 HANDOFF와 다른 session unit을 지목하면 그 session unit이 이긴다.
3. 그 둘이 없고 fresh HANDOFF exact path가 현재 ready 후보이면, 그 단위 안의 카드 번호 순서보다
   exact card가 먼저다. 사용자가 같은 단위만 지목한 경우도 여기에 포함한다.
4. exact path가 없거나 ready가 아니면 일반 후보 순서로 낮춘다.
5. stale HANDOFF는 지금처럼 carried unit만 제공한다.

대안은 exact path를 단위 힌트로만 유지하고, 현재 리포트와 resume의 “last handoff가 그 카드를
선택했다”는 표현을 약화하는 것이다. 어느 쪽이든 가능하지만 둘을 동시에 주장할 수는 없다.

### J-07 · claim의 실행 worktree를 자동 복원할 것인가

권장 판정: **0.12.0에서는 자동 cross-worktree 재개를 지원하지 않는다.** resume은 같은 id의
claim을 어느 worktree가 실행 중인지 추측하지 않고, 사용자가 `git worktree list`에 나온 현재
경로와 claim을 명시적으로 대응시킬 때까지 쓰지 않는다. 확인한 경로와 현재 경로가 다르면 그
worktree에서 다시 시작하라고 보고한다.

완전 자동 복원이 필요하면 새 mapping은 기술적으로 가능하다. 그러나 worktree absolute path는
move·clone·다른 기계에서 안정된 id가 아니며, 새 flow key는 “두 번째 식별자” 기각 계보를 다시
연다. 채택 전에는 다음을 하나의 설계로 닫아야 한다.

- portable identity와 저장 위치
- claim 생성·경계 종료 시점
- worktree move·prune·folder loss·repository clone 뒤의 상태
- byte-identical claim→done 경계와의 관계
- ownerless mapping 복구 및 정합성 항목

### J-08 · pre-v0.12 완료 신호를 어떻게 이주시킬 것인가

명령 문자열을 보고 “명백히 repository-wide”라고 추측하는 것은 정본이 될 수 없다. 권장 판정은
**room upgrade 안에 재시작 가능한 one-time migration을 넣고, 그 시점의 모든 ordinary
pending/claimed card를 사람이 각각 재승인**하는 것이다. 이 시점에는 아직 v0.12에서 새로 만든
카드가 없으므로 그 집합이 곧 legacy active set이다.

먼저 기존 정규 전이가 migration보다 이겨야 한다.

1. open Git operation을 먼저 끝낸다.
2. remote-evidence line이 bare `.wip.` exact path를 가리키면 R-14의 room-path transition으로
   confirmed owner suffix와 `card-json`을 원자적으로 함께 바꾼다. owner 불명은 여기서 정지한다.
3. 그 뒤 `evidence-finalizing`, 이미 끝난 final-task commit의 boundary를 현재 소비자가 끝낸다.
4. `evidence-wait`가 대기·접근 불가·판정 없음이면 card와 journal line을 건드리지 않고 migration
   차단 이유를 보고한다. 통과·실패가 정규 절차로 종결된 뒤 처음부터 다시 판정한다.
5. 미커밋 claim→done이나 다른 canonical transition도 먼저 끝낸다.
6. 따라서 migration 대상에는 remote-evidence record도, 완료된 작업의 미완 boundary도 없다.

그 뒤 `legacy signal migration` begin 상태를 새 정본 상태로 둔다.

```text
legacy signal migration:
  base: <full integration commit>
  cards: <release 뒤의 exact pending card path를 canonical path order로 담은 JSON array>
```

정확한 직렬화 형식은 `principles` 안에 한 번만 선언해야 한다. begin commit 전에는 모든 ordinary
claimed card의 diff와 progress log를 각 claim의 worktree에서 checkpoint한다. 하나라도
checkpoint되지 않았으면 begin을 쓰지 않는다. begin binding commit은 원자적으로 다음만 한다.

- resulting pending path의 exact list를 marker에 기록한다.
- 그 목록의 claimed suffix를 제거한다.
- 목록 전부의 `Approval`을 `pending`으로 바꾼다.

marker가 있는 동안 resume과 split은 work/claim보다 먼저 그 목록을 소비한다. 새 카드를 섞지
않고 canonical path order로 한 장씩 현재 signal을 보여 주며, 사용자는 `범위화해 교체` 또는
`J-04의 직렬/격리 전제로 재승인` 중 하나를 고른다. 각 planning commit 뒤 세션이 끝나도 marker의
고정 목록과 각 카드의 Approval이 남은 항목을 복원한다. exact path가 사라지거나 status가
예상 밖으로 바뀌면 추측하지 않고 정합성 이상으로 멈춘다.

목록 전부가 valid Approval과 승인된 completion signal을 가지면 final upgrade commit이 marker를
삭제한다. **그 삭제가 v0.12 동시 흐름 활성화의 유일한 완료 증거**다. marker의 producer,
resume/split consumer, work 차단 행, integrity shape check, final deletion을 한 묶음으로 추가해야
한다. 단순히 메모리에서 목록을 들고 순회하는 것은 중단 복구가 아니므로 금지한다.

대안은 정확한 legacy path 목록을 영속 상태로 남기고 그 카드가 닫힐 때까지 grandfather하는
것이다. 그러려면 목록의 형식·직렬 실행 token·소비자·삭제 기점을 똑같이 정의해야 한다. 지원
command whitelist도 기술적으로 가능하지만 runner별 유지비가 커서 기본안으로 권하지 않는다.

### J-09 · 은퇴 능력의 note를 누가 종결할 것인가

능력 은퇴를 실행하는 단계가 product·arch·glossary·다른 capability document를 임의로 함께 쓰면
기존 문서 소유권과 커밋 규율을 깬다. 권장 판정은 **note disposition을 은퇴보다 먼저 완결하고,
실제 target write는 그 문서의 owning skill이 수행**하는 것이다. note나 disposition state가
하나라도 남아 있으면 retirement commit을 금지한다.

- 다른 비은퇴 능력 지식: journal-only binding commit이 원 note를 그 능력의 canonical note로
  원자적으로 re-key한다.
- 더는 유효하지 않은 지식: exact prose를 보여 주고, 사용자 승인과 retirement evidence
  pointer가 가리킬 disposition commit을 남긴 뒤 원 note를 삭제한다.
- core 문서 또는 capability document: 아래 restartable disposition을 사용한다.

cross-owner 경로에는 최소한 다음 payload가 디스크에 있어야 한다.

```text
capability note disposition:
  id: <base commit + exact source line + duplicate occurrence로 만든 stable id>
  source: <exact whole capability-note locator>
  target: <exact owner skill + repository path + heading/zone>
  state: target-pending | target-prepared
  base: <full integration commit>
  operations: <target-prepared일 때만, exact final bytes와 source/marker cleanup>
```

이것은 예시 필드 이름을 그대로 채택하라는 뜻이 아니라, 다음 설계가 동등한 정보를 반드시
보존해야 한다는 최소 계약이다. `target-pending`은 resume을 exact owning stage로 보낸다. 대상
owner가 final bytes를 만들고 사용자 확인이 끝나면, routing-prepared의 기존 선례처럼
`target-prepared`에 exact operations를 먼저 쓴다. operations는 target owner의 문서 쓰기, 원 note
삭제, disposition 삭제 외의 경로를 담지 않는다.

그다음 **target owning skill**이 prepared operations를 한 번 적용하고 commit한다. 이 commit에
journal cleanup이 동승할 수 있도록 `principles`가 문서 소유권과 one-document commit discipline의
좁은 공인 예외를 선언해야 한다. uncommitted/committed prepared prefix의 base·operations 대조와
resume consumer도 routing-prepared와 같은 수준으로 정의한다. 그러면 세션이 target write 전,
operations 일부 적용 뒤, commit 직후 어디서 죽어도 같은 suffix만 끝내며 target을 두 번 쓰지
않는다. target bytes가 이미 같아 write가 no-op이면 사용자 확인과 현재 target commit을 증거로
삼은 journal-only disposition commit으로 source와 marker만 종결한다.

target commit 뒤 원 note와 disposition이 모두 사라진 것을 확인한 다음에만 product가 능력을
은퇴시킨다. 이 새 상태 기계를 원하지 않는 안전한 대안은 note가 하나라도 있는 능력의 은퇴를
계속 차단하고 사람이 먼저 각 note를 기존 owning stage에서 수동으로 정리하게 하는 것이다.

## 12. 권장 개선 순서

### 먼저: 기술적 해결 가능성 판정

아래에서 “불가능”은 devflow 전체를 고칠 수 없다는 뜻이 아니다. **현재 전제를 하나도 바꾸지
않고는 그 성질을 동시에 만족시킬 수 없다**는 뜻이다. 전제를 명시적으로 바꾸는 우회는 함께
적었다.

| 대상 | 기술 판정 | 이유 | 권장 해법 |
|---|---|---|---|
| R-01 HEAD 권위 충돌 | **해결 가능** | 통합 tip이라는 기존 단일 권위가 이미 있음 | worktree는 등록부, 통합 tip은 상태 권위로 분리 |
| R-02 실행 불가 예제 | **해결 가능** | R-01 결정 뒤 실제 Git 동선을 다시 쓰면 됨 | 통합 보유자가 claim을 착지하는 시나리오로 교체 |
| R-03 같은 tree lost update | **조건부 해결** | 직렬화·격리·원자 lock 중 하나가 필요 | 같은 tree 동시 writer 비지원, worktree 사용 권장 |
| R-04 note 폐쇄 race | **해결 가능** | marker에 기준 `head`가 이미 있음 | 그 head에 있던 exact note만 삭제 |
| R-05 evidence 보고 불일치 | **해결 가능** | work의 기계적 우선순위가 이미 있음 | 같은 우선순위를 resume 행에 투영 |
| R-06 stale Boundary 매핑 | **해결 가능** | freshness 판정이 이미 있음 | design refresh를 mapping보다 먼저 실행 |
| R-07 malformed Covered cards | **해결 가능** | 보수적 fallback을 하나 고르면 됨 | 모든 done을 미수확으로 보거나 명시 정지 |
| R-08 park 재점유 | **해결 가능** | 전환 한 번의 목적 카드만 보존하면 됨 | release 전에 목적 카드 고정 |
| R-09 HANDOFF exact path | **해결 가능·정본 결정 필요** | exact path가 이미 디스크에 있음 | J-06에서 구속 포인터 또는 단위 힌트 중 하나 선택 |
| R-10 recall 번호 재사용 | **해결 가능** | 현재 tree에 tombstone을 남길 수 있음 | 삭제 대신 `.stale.` 원본 유지 |
| R-11 은퇴 note orphan | **해결 가능·새 복구 상태 필요** | 은퇴 전에 disposition을 닫을 수 있음 | J-09의 restartable owner-target 전이 또는 note 존재 시 은퇴 차단 |
| R-12 이전 완료 신호 | **해결 가능·새 복구 상태 필요** | upgrade 시점의 ordinary 활성 카드 집합은 유계임 | special transition 선처리 + 영속 marker 아래 일회 재승인 |
| R-13 claim 실행 위치 | **조건부 해결** | 현재 상태에는 위치를 구분할 정보가 없음 | J-07의 사용자 확인 또는 새 portable mapping |
| R-14 bare evidence path | **owner 확인 시 해결 가능** | rename 전·후 exact path가 모두 기계적임 | room upgrade에서 card와 evidence line 원자 교체; owner 불명은 정지 |
| P-01 nested cwd hook | **해결 가능** | Git root와 stdin cwd가 있음 | root까지 유계 상향 탐색 |
| P-02 prompt 호출 이름 | **해결 가능** | 현재 공식 이름이 정해져 있음 | `/prompts:`로 갱신 또는 채널 은퇴 |
| P-03 CODEX_HOME | **해결 가능** | 계산된 홈 변수가 이미 있음 | prompt도 같은 home 아래 설치 |
| P-04 hook trust 전환 | **자동 완결은 불가능** | 플랫폼이 사람의 신뢰 승인을 의도적으로 요구 | `/hooks` 승인 단계를 설치 완료 조건으로 둠 |

#### 현재 전제 안에서 물리적·정보적으로 불가능한 네 가지

1. **한 작업 디렉터리에서 두 개의 서로 다른 미커밋 스냅숏을 동시에 제공하는 것**

   파일 시스템의 같은 경로는 한 시점에 bytes 한 벌만 가진다. 능력 03 세션은 `src/a.ts`의 A
   상태를, 능력 04 세션은 같은 경로의 B 상태를 동시에 보게 할 수 없다. 완료 신호를 경로로
   좁혀도 공유 설정·타입 검사·빌드 그래프가 전체 저장소를 읽으면 같은 한계가 돌아온다.

   가능한 해법은 세 가지뿐이다.

   - worktree/container처럼 working tree snapshot을 분리한다.
   - 한 세션을 checkpoint하고 다른 세션이 끝날 때까지 writer와 build를 직렬화한다.
   - 빌드 시스템 자체가 별도 snapshot/sandbox를 만들게 한다.

   프롬프트 문장을 더 정교하게 쓰는 것으로는 해결할 수 없다.

2. **같은 id와 별도 소유권 정보 없이 같은 작업 트리의 두 살아 있는 세션을 구분하는 것**

   두 세션이 모두 `jmp`이고 별도 session/flow id나 lock owner가 기록되지 않으면
   관찰 가능한 입력이 같다. 어떤 알고리즘도 동일한 입력에서 “이 변경은 A의 것, 저 변경은
   B의 것”을 복원할 수 없다.

   해결하려면 전제를 하나 바꿔야 한다.

   - session/flow 식별자를 새로 저장한다.
   - 동시에 writer 하나만 허용한다.
   - 서로 다른 worktree로 물리적으로 분리하고 아래 3번의 위치 정보를 사용한다.

   0.12.0의 “새 식별자 없음”을 유지하려면 writer 하나로 직렬화하거나 worktree로 분리한 뒤
   아래 3번의 위치 정책을 선택해야 한다.

3. **같은 id와 claim→worktree 대응 없이 여러 worktree의 실행 위치를 복원하는 것**

   worktree A와 B가 같은 integration claim을 포함하면 tracked Git 상태는 같다. A에만 미커밋
   구현이 있다는 사실은 다른 worktree B의 card 상태에 claim 소유 위치로 나타나지 않는다.
   worktree가 물리적으로 분리되어 있다는 사실만으로 어느 폴더가 그 claim의 실행 위치인지는
   복원되지 않는다.

   해결하려면 claim→portable worktree identity mapping을 새로 기록하거나, worktree마다 id를
   달리하거나, 사용자가 매 세션 exact listed path를 확인하는 조건으로 자동 cross-worktree
   재개를 지원하지 않아야 한다. absolute path만 저장하는 것은 move·clone 뒤의 durable 해법이
   아니다.

4. **Codex의 비관리 command hook 신뢰를 설치기가 사람 대신 승인하는 것**

   hook hash 신뢰는 보안 경계다. 설치 성공·plugin enabled만으로 우회할 수 없어야 정상이다.
   `--dangerously-bypass-hook-trust`를 일반 설치 동선에 넣는 것은 해결이 아니라 보안 장치
   제거다.

   기술적으로 올바른 해법은 자동 승인이 아니라 상태 전환을 정직하게 만드는 것이다.

   ```
   plugin installed
     → 자동 resume 아직 미활성이라고 표시
     → 사용자가 /hooks에서 exact hook 검토·신뢰
     → 새 세션 smoke test
     → 그 뒤 legacy hook 정리
   ```

#### Git이 다른 worktree의 integration checkout 갱신을 거부하는 문제

이 Git 제약도 문구로 우회할 수 없다. 강제로 ref를 움직이면 integration 보유 working tree의
index/HEAD와 branch ref가 어긋나며, devflow가 지키려는 복구성을 훼손한다. 해결 가능한 운영
구조는 다음 중 하나다.

- integration 보유 worktree의 coordinator가 최초 점유와 모든 구속 결정을 착지한다.
- integration branch를 어떤 작업 worktree도 checkout하지 않는 전용 통합 ref/서비스로 둔다.
- 원격 integration을 사용하고 보호된 직렬화 절차로 갱신한다.

현재 devflow가 worktree를 만들거나 관리하지 않는 결정을 유지한다면 첫 번째가 최소 변경이다.
리포트와 README는 이 수동/조정 단계를 “자동으로 feature에서 claim”처럼 보이지 않게 써야 한다.

### 소견별 구현 가이드

#### G-01 · R-01/R-02 권위 수리 패키지

권장 의미 규칙:

```
git worktree list --porcelain
  = 살아 있는 작업 공간과 integration 보유 위치를 찾는 등록부

integration tip의 devflow/project, tree, journal, bounded verify projection
  = 공유 상태의 유일한 현재 값

worktree-local HEAD
```

변경이 필요한 좌표:

- `skills/principles/SKILL_ko.md` ↔ `SKILL.md`: union 권위 제거·등록부 역할 한정
- `skills/resume/SKILL_ko.md` ↔ `SKILL.md`: union projection 제거, 통합 상태로 후보 판정
- `skills/work/SKILL_ko.md` ↔ `SKILL.md`: 최초 claim과 작업 worktree 동기화 절차 확인
- `README_ko.md` ↔ `README.md`: worktree 운영 설명
- `docs/design_ko.md` ↔ `docs/design.md`: v0.12 결정 이유를 보정하고 v0.9.21 이유와 화해
- 현재 실행 리포트 §7.2·§12
- repository invariant와 실제 Git fixture

주의: 이 수리는 R-01의 tree/card 권위와 현행 공유 상태 투영만 다룬다. `rooms`의 HANDOFF,
digest, identity는 현행 소비 규칙을 유지하며 이 결정에 몰래 포함하지 않는다. rooms까지
integration-tip 권위로 바꾸려면 생산자·소비자·현재 worktree와의 관계를 별도 좌표 스윕해야 한다.

단순히 union 문장을 지우기 전에 “worktree에서 진행 중인 claim이 어떻게 다른 흐름에
보이는가”를 확인해야 한다. 최초 claim이 통합에 먼저 착지한다는 기존 규칙이 그 가시성을 이미
제공하므로 별도 HEAD union이 필요 없어야 한다. 이 가정을 T-W02로 증명한다. 그러나 가시성과
실행 위치는 다르다. R-13을 닫으려면 다음 둘 중 하나를 별도로 결정한다.

- J-07 권장안처럼 다른 worktree의 claim을 자동으로 계속하지 않고, 사용자가 exact listed
  worktree와 claim을 확인한 뒤 그 위치에서 다시 시작한다.
- 자동 복원이 필수라면 portable worktree identity mapping을 새 상태 기계로 설계한다.

둘째 안은 move·clone·prune·중단 복구를 새 좌표로 추가하고 기각 계보를 먼저 반박해야 한다.
첫 안은 기능 범위를 줄이는 대신 새 영속 상태를 만들지 않는다.

#### G-02 · R-03 동시 writer 수리 패키지

권장안은 지원 범위를 줄이는 것이다.

```
같은 working tree:
  여러 능력의 claim 보유 가능
  세션 전환 가능
  동시에 쓰는 writer/build는 하나

실제 병렬 writer:
  능력마다 별도 worktree 필요
```

이 결정이면 HANDOFF compare-and-retry 규칙을 계속 늘릴 필요가 없다. resume은 현재 작업 트리에
다른 살아 있는 세션이 있는지 디스크만으로 알 수 없으므로 자동 감지까지 약속하지 않는다.
사용자 운영 계약과 “한 작업 트리 writer 하나”를 README와 current report에 분명히 둔다.

대안으로 같은 tree 동시성을 유지하려면 prompt-only 수정으로 충분하지 않다. 다음을 모두 가진
실제 atomic helper가 필요하다.

- 원자적 lock acquire
- owner/session 식별자
- PID가 아니라 재개 가능한 durable owner 판정
- crash 뒤 stale lock 회수에 대한 사용자 승인
- HANDOFF/journal/verify/tree rename을 포함한 잠금 범위
- Windows/macOS/Linux 동형 구현과 테스트

이 비용은 0.12.0이 피하려 한 새 흐름 식별자·닫는 기점을 다시 만든다. 따라서 권장하지 않는다.

#### G-03 · R-04 capability note 수확

새 marker 형식을 만들 필요가 없다.

1. marker의 `head`가 가리키는 journal blob을 읽는다.
2. 그 blob에 존재한 대상 능력의 canonical exact note line 집합을 `harvested`로 계산한다.
3. refresh는 그 집합을 입력으로 사용한다.
4. step 8은 현재 journal에서 `harvested`와 exact bytes가 같은 줄만 삭제한다.
5. marker head 뒤에 추가된 줄, 다른 능력 줄, baseline no-op 때의 모든 줄은 유지한다.
6. 동일 bytes 중복이 canonical format상 가능하면 timestamp 포함 whole line과 발생 횟수까지
   multiset으로 처리한다.

수용 조건은 T-K03/T-K04다. “현재 대상 능력 줄 전부 삭제”라는 구현은 금지한다.

#### G-04 · R-05 evidence 보고

resume의 table에 work의 precondition을 복제해서 두 번째 상태 기계를 만들지 말고, 정본화된
하나의 evidence projection을 인용하는 것이 좋다.

필요한 값:

- 상태 우선순위: `evidence-finalizing` 복구와 uncommitted transition을 포함한 work의 현재 순서
- 같은 상태 안 timestamp → journal line order
- 이번 호출이 실제로 먼저 처리할 exact card path
- 예상 행동: recheck / finalize boundary / fail checkpoint / pending retain

resume은 일반 “내 점유 카드” 행보다 위에서 이 projection의 첫 항목을 보고한다. work는 승인 뒤
동일 항목부터 처리한다. 한 호출에 여러 evidence 전이를 연속 처리할지 하나만 처리할지도
명시해야 한다. 보고-승인 일치를 가장 단순하게 하려면 한 번에 하나를 처리하고 재대조한다.

#### G-05 · R-06 maintenance mapping

권장 순서:

```
active claim 복구/경계
→ Layer 0 대비 capability-design freshness 확인
→ stale이면 arch/adopt design refresh
→ maintenance routing pending 매핑
```

이 순서는 “요청 기록은 점유보다 위, 계획은 점유보다 아래” 결정을 바꾸지 않는다. 이미 기록된
요청을 어떤 능력에 놓을지 결정하기 전에 매핑 권위를 최신으로 만드는 별도 준비 단계다.

#### G-06 · R-07 malformed Covered cards

두 해법 모두 기술적으로 가능하지만 하나만 정본으로 채택해야 한다.

- 권장 보수안: `Covered cards`가 없거나 비해석이면 현재 모든 비-`.stale.` done 카드를
  미수확으로 보고 마지막 `carry:`를 읽는다. 중복 전달 가능성은 있지만 지식 소실은 없다.
- 엄격안: carry를 쓰지 않고 integrity anomaly로 정지해 arch/adopt/verify 수리를 요구한다.

devflow가 손상된 검증 구역을 가설로 낮추고 active work를 계속하는 현재 철학에는 보수안이 더
맞는다. 이때 report token에 `Covered cards malformed — conservative complement: all`처럼
기계적인 한 줄을 두고 reviewer에는 carry 자체를 전달하지 않는 기존 경계를 유지한다.

#### G-07 · R-08/R-09 전환 포인터

- park: release 전에 목적 카드 exact path를 사용자 또는 명시 규칙으로 확정한다. release가
  끝난 같은 전환 invocation에서는 그 path를 **새 transition-local target 규칙**으로 보존한다.
  목적 카드가 ready가 아니면 release하지 말고 이유를 보고한다. 이것을 현재 대화의 사용자
  지목 카드와 같은 기존 입력이라고 부르지 않는다.
- fresh HANDOFF: J-06을 먼저 결정한다. 권장안을 택하면 사용자 exact card와 다른 session unit이
  먼저이고, 그 충돌이 없을 때 fresh exact path가 자기 단위의 카드 번호 순서보다 앞선다는 새
  정본 순서를 쓴다. path가 사라졌거나 ready가 아니면 일반 후보 순서로 낮추고, stale HANDOFF는
  처음부터 unit-only다.

park는 한 invocation 안의 전환 목적지이고 HANDOFF는 다음 세션의 디스크 입력이므로 같은
“기존 1순위”로 뭉치지 않는다. 생산·소비 수명과 사용자 지목 충돌 테스트도 따로 둔다.

#### G-08 · R-10 recall 번호

가장 작은 해법은 원본 pending card를 삭제하지 않고 같은 위치에서 `.stale.`로 바꾸는 것이다.

- 원본 번호·이름·body를 보존한다.
- progress log에 구현 역사를 꾸며 넣지 않는다.
- replacement는 올바른 폴더의 continuing number를 새로 받는다.
- planning commit 하나가 stale rename과 replacement를 함께 싣는다.
- 번호 탐색은 current tree만 읽어도 retired number를 보게 된다.

“never claimed and no task subject” 조건은 recall 자격으로 그대로 남는다. Git history 검색을 새로
추가하지 않는다.

#### G-09 · R-11 은퇴 note

능력 은퇴 확인 전에 그 번호의 note를 유계 열거한다.

1. note 0개: 기존 은퇴 절차
2. note 1개 이상: 사용자에게 exact prose를 보여 준다.
3. 아직 유효한 지식이면 J-09의 disposition 중 하나를 고른다.
   - 다른 비은퇴 능력: journal-only binding commit으로 exact line을 원자적으로 re-key한다.
   - product/arch/glossary/capability document: source·exact target·owner·state를 가진
     `target-pending` disposition을 먼저 디스크에 남긴다.
   - 무효 지식: 사용자가 exact line의 폐기를 승인하고 disposition commit을 retirement evidence로
     남긴다.
4. cross-owner이면 resume이 `target-pending`을 owning skill로 라우팅한다. owner는 user-confirmed
   final bytes를 `target-prepared` operations로 먼저 고정하고, prepared prefix consumer가 target
   write와 exact source/marker cleanup만 한 번 착지시킨다.
5. `principles`에 이 prepared 전이의 producer·consumer·base/operations 대조·좁은 commit 예외를
   선언한다. target owner 외의 단계는 core bytes를 쓰지 않는다.
6. 원 note와 disposition이 모두 없어진 뒤에만 retirement commit을 허용한다.

자동 폐기는 금지한다. 은퇴는 대상 능력의 다음 closure를 없애는 행위이므로 바로 그 결정이 note의
disposition 기점이어야 한다. 새 state를 만들지 않는 안은 “note가 있으면 은퇴 차단”이다. 단순히
“owning skill로 보낸다”는 대화 지시만 남기는 안은 중단 뒤 목적지가 사라지므로 해법이 아니다.

#### G-10 · R-12/R-14 room upgrade 패키지

업그레이드 때 모든 과거 `.done.`/`.stale.` 카드를 다시 읽는 것은 과잉 하네스다. J-08의
권장안은 room upgrade를 시작할 때 존재하는 **ordinary exact pending/claimed path**만 대상으로
삼는다. command 문자열을 분류하거나 runner 능력을 추측하지 않는다.

1. bare `.wip.`를 exact card path로 가진 evidence-wait/finalizing line이 있으면 owner를 먼저
   확인한다. 확인된 suffix rename과 matching line의 `card-json` rewrite를 room-upgrade binding
   commit 하나로 착지한다. 다른 field는 byte 그대로다. owner 불명 claim은 release하지 않는다.
2. 갱신된 evidence-wait/finalizing, final-task-complete claim, 미완 boundary·binding transition은
   기존 소비자가 먼저 종결한다. unresolved evidence-wait는 migration을 차단하며 release하지 않는다.
3. 남은 claimed card를 각 원 worktree에서 checkpoint한다. 전부 준비되기 전에는 begin marker를
   쓰지 않는다.
4. `legacy signal migration` begin binding commit이 resulting pending exact path 목록을
   canonical order로 고정하고, claim release와 목록 전부의 `Approval: pending`을 원자적으로
   착지시킨다.
5. marker consumer는 목록 한 장씩 현재 signal을 보여 주고 사용자가 `범위화해 교체` 또는
   `J-04의 직렬/격리 전제로 재승인` 중 하나를 고르게 한다. split planning commit마다 결과가
   card에 남는다.
6. 세션 재개는 marker의 고정 목록과 각 Approval을 비교해 남은 항목부터 계속한다. marker가 있는
   동안 work와 새 claim은 실행하지 않는다.
7. 목록 전부가 승인된 뒤 final upgrade commit이 marker를 삭제한다. 이 삭제 전에는 v0.12 동시
   흐름 지원을 활성이라고 보고하지 않는다.

대안인 grandfather 정책은 exact legacy path 목록·직렬 실행 token·삭제 기점을 정본화해야 한다.
지원 command whitelist를 택한다면 command grammar와 runner version별 목록을 유계 companion으로
정의해야 하며, `명백한`, `repository-wide처럼 보이는`, `기계적으로 확인` 같은 판정어만 두어서는
안 된다.

## 14. 현재 리포트의 결론을 어떻게 수정해 읽어야 하는가

현재 리포트의 장점은 분명하다.

- 기획과 구현을 구분했다.
- 왜 결정을 뒤집었는지 기록했다.
- 현장 검증 0, 정본 크기, `carry:` 품질, 완료 신호 범위, worktree 합집합 비용을 숨기지 않았다.
- Git 동작을 실측하지 않고 썼던 실패를 스스로 기록했다.
- push 보류를 권했다.

그러나 §12의 다음 두 판정은 범위를 좁혀야 한다.

| 현재 표현 | 이 검증의 판정 |
|---|---|
| 텍스트 정합성 ✅ | single-flow 중심 부분은 강함. worktree 권위 두 문장은 충돌 |
| 문자 실행 안전성 ✅ | marker/경계 복구는 강함. 동시성·evidence·note·maintenance 축은 미통과 |
| 기획 충실도 ✅ | 최종 리포트 기준 구현은 충실. 다만 owner-decision round가 새 결함을 도입 |
| 지금 쓸 수 있다 | **한 터미널 순차 사이클부터는 가능. 동시 흐름은 차단 결함 수리 전 보장 불가** |

이것은 0.12.0의 방향을 부정하는 판정이 아니다. 릴리스가 새로 연 축에서 좌표 스윕이 덜 된
것이다. 특히 최초 구현 `841455e` 뒤의 네 패스와, worktree 권위를 넣은 `234d19e` 뒤의 검증
증거를 분리해서 읽어야 한다.

## 15. 다른 설계 AI에게 보내는 작업 지시

### 15.1 먼저 할 일

1. 이 리포트의 R-01과 R-03을 각각 실제 Git/worktree와 동일 작업 트리 interleaving으로 재현한다.
2. `docs/design.md`의 v0.9.21 통합 직렬화 이유와 v0.12.0 worktree 이유를 나란히 놓는다.
3. 문장을 쓰기 전에 각 수리를 `시작 상태 · producer · durable token · consumer · 중단 prefix ·
   terminal state` 표로 고정한다. 이 언어 중립 골격을 한글 설계 원본으로 설명한 뒤에만 영문
   배포물로 번역한다. 영문 산문을 먼저 쓰고 한글을 사후 번역해 두 정본을 만들지 않는다.
4. J-01과 J-02에 대해 소유자 승인을 받는다.
5. 각 수리 묶음 전에는 J-06(HANDOFF), J-07(worktree 위치), J-08(legacy signal),
   J-09(은퇴 note writer)의 선택도 확정한다.
6. 승인 전에는 스킬 문구를 고치지 않는다.

### 15.2 피해야 할 일

- `shared`, `current`, `latest` 같은 판단어 하나를 더 넣어 R-01을 덮지 않는다.
- 모든 worktree의 전체 tree를 읽는 새 규칙으로 해결하지 않는다. 읽기 범위와 동일 번호 권위가
  더 커질 뿐이다.
- same-tree race마다 개별 “직전에 다시 읽기” 문장을 추가하지 않는다. 원자성 경계가 없으면
  마지막 재읽기도 동시에 일어날 수 있다.
- 불명확한 상태마다 새 marker를 만들기 전에 기존 commit/marker/head로 유계 판정 가능한지 본다.
- 73/73을 의미 안전성의 완료 증거로 사용하지 않는다.
- Claude와 Codex 문장을 따로 설계하지 않는다. 공통 의미 원본을 고치고 전달 채널만 플랫폼별로
  검증한다.

### 15.3 완료 조건

다음이 모두 참이어야 이번 개선이 닫힌다.

- 공유 tree 상태 권위가 정확히 하나다.
- 정상 worktree closure 뒤 stale worktree가 완료 카드를 점유로 되살리지 않는다.
- 같은 작업 트리의 동시 writer 지원 여부가 명시되고 그 범위 안에서 자료 소실이 없다.
- resume이 보고한 단계와 실제 첫 단계가 모든 evidence 상태에서 같다.
- `carry:`와 `capability note`의 생성·소비·폐쇄·은퇴·동시 추가 생명주기가 모두 닫힌다.
- maintenance mapping은 최신 능력 경계를 사용한다.
- park와 recall이 후보 순서·번호 불변식을 깨지 않는다.
- fresh HANDOFF exact path와 사용자 card/unit 지목의 우선순위가 한 곳에만 정의된다.
- pre-v0.12 active card의 완료 신호가 문자열 추측 없이 전부 disposition되고 migration 중단 뒤
  exact set과 남은 항목이 복원된다.
- claim 실행 worktree를 자동 복원하지 못할 때 AI가 추측하거나 다른 위치에 쓰지 않는다.
- 은퇴 note의 target write는 기존 문서 owning skill을 우회하지 않으며 pending/prepared 중단 뒤
  같은 target으로 복구되고 source와 disposition이 종결되기 전에는 은퇴하지 않는다.
- Claude와 Codex가 repo root와 nested cwd에서 같은 resume context를 받는다.
- Codex native skill, hook trust, 명시 호출, CODEX_HOME의 현재 공식 동선이 실제 설치로 확인된다.
- 상태 전이 fixture와 기존 repository invariant가 모두 통과한다.
- `_ko` 선행, 영문 동형, CHANGELOG, 버전 상승, 설치기 재생성·재설치가 완료된다.
