# DD-52 · 공유 전이는 기억해 둔 통합 id에 대고 게시한다

- 상태: 유효 · 일부 정정 → DD-62 (v0.14.0), DD-70 (v0.16.0)
- 주제: 동시성 · 점유 · 통합
- 도입: v0.13.0
- 결정일: 2026-08-13
- 최종 수정: 2026-08-15

아무도 쥐지 않은 통합에서도 두 흐름이 같은 지점에서 동시에 밀면 한쪽은 진다. 그것은 실패가 아니라 동시성 제어가 작동한 것이다. 둘을 가르지 않으면 정상 경쟁을 "통합 불가"로 오판해 막힌 경로로 보내고 점유가 이유 없이 흩어진다. 첫 실측은 id 자체가 판별자가 될 수 있다고 보였다 — 정상 경쟁에서는 바뀌고, 워크트리가 그 브랜치를 쥐면 그대로인 채 거부되기 때문이다. 실전 동시성 실행이 그것을 반증했다. 형제 흐름이 이미 게시한 *뒤에* 통합을 읽은 흐름은 그 뒤 바뀌지 않는 id를 기억하게 되는데, 그 거절은 평범한 non-fast-forward다. 그래서 기계적 검사는 통합 tip이 게시하려는 브랜치의 조상인가이다 — 조상이 아니면 정상 경쟁, 조상인데 거부되면 구조적 막힘 — 이며 두 실전 사례가 이 검사로 정확히 갈린다. 에러 문구는 locale과 Git 버전에 따라 달라지므로 판별자가 아니다. 재시도는 세 번으로 묶고, 지속 경합은 실패 사다리로 세지 않고 보고한다. 통합에 정말 쓸 수 없으면 이미 점유가 착지한 카드의 코드 편집과 진행 로그 체크포인트만 계속한다 - 조정점이 없으면 누가 무엇을 발급했는지에 전역 답이 없지만, 코드와 진행 로그는 나중에 합쳐도 안전하다(서로 다른 카드, 그리고 done 개명 대 로그 추가에서 실측). 이 경계가 오케스트레이터가 통합을 쥐는 환경도 살려 두며, 그때 오케스트레이터는 worker를 띄우기 전에 통합에서 카드와 점유를 먼저 만들어야 한다. **v0.14.0에서 정정**: 봉쇄 중 계속 목록이 넓어졌다 — 최종 작업 커밋과, 발급·점유·소비가 아닌 journal 덧붙임(정확 열거 4종)도 계속한다. "코드와 로그만"의 동결은 그 라운드의 유일한 조용한 소실 경로(봉쇄 중 요청 증발)로 판명됐다(봉쇄 덧붙임 행 참조)
