# DD-42 · 능력 지식 기준선 — 검증 폐쇄가 낳는 도메인 설계도 (v0.10.0, v0.11.0이 생애를 확장)

- 상태: 유효 · 일부 정정 → DD-76 (v0.18.1)
- 주제: 지식층과 능력 문서
- 도입: v0.10.0
- 최종 수정: 2026-08-18

근거는 실측 세 건이다: 중계노트의 기존 핸드오프 12편에서 연대기 절이 문서의 60~68%를 차지하고 수기 신선도 선언이 실패했다, ade의 G-T2가 이중 소유 사고를 냈다, rdsf의 지식 도달성 진단이 같은 공백을 가리켰다. v0.10.0은 마지막 검증 폐쇄에서 단일 작성자가 파일 하나를 전면 교체하는 옵션 D를 채택했다. 검증 캠페인(반증 16 → 연구 3패스 → Fable 반증 2패스 소견 15 → 재감사 13)이 그 후보 계약을 다듬었다. 제안서의 선택지 판정·기각 사유·소유자 선택·수용 한계는 아래 「제안서에서 옮긴 계보」에 원문 그대로 있고, 실행 계약은 기준선 판정 정본 한 곳에만 산다. 시간 감쇠·연속 갱신·append-only 승계·Assumptions와 Open Questions·인덱스·글롭 자동 첨부·스테이징 소비·심볼 바인딩 기각은 그대로 승계한다.

## 제안서에서 옮긴 계보

v0.10.0 제안서의 네 절을 원문 그대로 옮겼다(2026-09-11). 문장 속 경로는 그때의 경로다.

### 검토한 선택지

| 안 | 요약 | 판정 |
|---|---|---|
| A | 작업 트리와 Layer 0만 유지 | 소형 선형 작업에는 충분하지만 도메인 재진입 비용과 첫 카드 전 공백을 닫지 못함 |
| B | 기존 핸드오프를 정리해 계속 사용 | 연대기 비대·이중 소유·수기 신선도를 그대로 승계해 기각 |
| C | 카드나 컴포넌트마다 별도 기준선 | 독립 검증 경계가 없고 읽기 수가 작업 크기에 비례해 기각 |
| D | 능력 폐쇄에서 능력당 파일 하나를 전면 교체 | v0.10.0 채택. 현재 상태·기계 신선도·O(1) 읽기를 처음 확보 |
| E | 한 파일을 Layer 0 설계 구역과 폐쇄 검증 구역으로 분리 | v0.11.0 채택. D를 보존하면서 첫 폐쇄 전 공백과 카드 배선을 제거 |

E는 D의 파일 수·연대기 금지·현재 상태·기계 신선도를 버리지 않는다. 설계 진술과 코드 관측의
작성 시점이 다르다는 사실을 고정 byte 경계로 드러낸다. 설계는 arch(브라운필드는 adopt), 검증은
verify가 쓴다. 자세한 절·필드·명령은 이 문서가 아니라 판정 정본이 소유한다.

### 기각 계보

- **시간이 지나면 자동 폐기** — 시간은 드리프트의 원인이 아니라 대리 신호다. Git 경계와 카드
  집합은 실제 입력 변화를 측정한다.
- **연속·매 작업 갱신** — 카드마다 문서를 다시 쓰게 해 쓰기 충돌과 비용을 만든다. 설계 확정과
  능력 폐쇄라는 기존 직렬 경계만 쓴다.
- **append-only 승계** — ADR은 역사가 본문이지만 능력 문서는 현재 구조가 본문이다. 연대기 금지와
  충돌한다.
- **Assumptions·Open Questions 절** — 검증된 관측과 계획을 섞고 열린 일의 제2 거처를 만든다.
- **소비자 목록 저장** — 역방향 목록이 실제 경로와 따로 낡는다. 소비하는 쪽의 정확 경로에서
  필요할 때 투영한다.
- **전역 인덱스** — 능력 하나에 들어가기 위해 인덱스와 본문 두 파일을 읽게 하고 동기화 경로를
  연다.
- **자동 glob·폴더 전체 첨부** — 카드당 읽기 O(1)을 깨고 `관련` 판단을 무유계 검색으로 바꾼다.
- **심볼 바인딩·별도 hash 도구** — 경로 기반 정밀도 문제가 실제로 관측되기 전에는 하네스 비용을
  정당화하지 못한다.
- **프로젝트별 on/off 스위치** — 소형 프로젝트도 같은 생애가 필요하고 빈 절은 `None.` 한 줄이다.
  스위치는 모든 소비자에 분기와 이관 상태만 추가한다.
- **단일 7필드 기계 블록** — 두 구역의 소유 필드를 파일 끝에 모으면 설계 작성자와 verify가 같은
  byte를 고치게 된다. 메타데이터도 소유 구역 안에 물리 분리한다.
- **설계 구역에 planned flow·진입점 추가** — 첫 폐쇄 뒤 검증 구역과 같은 개념이 두 자리에 생긴다.
  계획된 진입점은 product.md·arch.md가 이미 소유한다.

### 확정된 소유자 선택

v0.11.0은 네 선택을 확정했다.

1. 능력 문서는 모든 프로젝트에서 항상 켠다.
2. 총 상한은 약 185줄이며 1,100~1,700줄짜리 수기 핸드오프보다 의도적으로 한 자릿수 작다.
3. 설계 구역은 목적·경계·개념·불변식·비범위·구속 ADR을 담고 planned flow·진입점은 담지 않는다.
4. `01-foundation.md`를 두되 검증 구역은 `None.`으로 유지한다. 실사용 가치가 없으면 첫 절단
   후보다.

이 선택을 바꾸려면 `docs/design_ko.md`의 기록된 근거를 먼저 반박한다.

### 수용 한계

아래는 의도적으로 남긴 한계다.

- 얕은 클론과 multi rebase에서 보수적인 거짓 가설이 생길 수 있다.
- 매우 긴 경로 집합은 셸 명령줄 한계에 닿을 수 있다.
- 미커밋 작업 트리는 Git head 비교에 보이지 않는다.
- 레지스트리·동적 디스패치를 거친 관계는 경로만으로 거짓 신선도가 남을 수 있다.
- 소비 관계는 현재 신선도를 보고하지만 다른 능력의 회귀를 자동 실행하지 않는다. 공유 변경이
  잦아지는 현장 신호가 생길 때만 승격한다.

### v0.9.21 보고에서 옮긴 것

v0.9.21 보고의 프론트엔드·백엔드 분리 기준선을 두지 않은 이유와 그 재개 조건.

프론트엔드·백엔드를 별도 기준선으로 나누지 않은 이유는 취향이 아니라 검증 경계다. 현재 devflow에는
`arch.md` 구성요소 단위의 독립 폐쇄가 없어 공유 구성요소를 어느 능력이 확정하는지 정할 수 없다.
공유 백엔드·플랫폼 지식은 `arch.md`·위임 ADR·코드가 소유하고, 수직 능력 기준선은 그 능력에 미치는
계약과 정확한 공유 경로만 보존한다. 독립 구성요소 검증 경계가 실제로 생기기 전에는 제2 기준선을
추가하지 않는다.

- 구성요소별 독립 검증 경계가 없으므로 공유 백엔드·플랫폼 지식을 별도 기준선으로 압축하지 않는다.
  그 지식은 arch·위임 ADR·기존 기록과 코드에 남아야 하며, 이것이 반복 비용으로 관측되면 먼저
  구성요소 검증 경계를 설계해야 한다.
