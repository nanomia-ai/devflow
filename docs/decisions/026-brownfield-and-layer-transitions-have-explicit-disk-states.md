도입이 끝난 저장소와 신규 프로젝트가 같은 문서 모양을 가져 resume이 기존 기능을 트리에 소급 생성했고, 대표 흐름 하나만으로 다도메인 서비스를 역산하면 능력 경계가 너무 거칠어졌다. adopt는 외부 진입점·최상위 모듈·기존 문서에서 후보를 열거한 뒤 후보마다 대표 흐름 하나를 추적한다. arch.md의 `브라운필드` 필드는 도입 전 구현 존재 여부만 기록해 기존 코드는 소급하지 않는다. 도입 후 추적 작업이 끝나도 전체 제품층으로 자동 확대하지 않고, 명시적인 `product 검증 요청`만 제품층을 연다. 요청은 실행·결과 상태로 원자적으로 바뀌며 각 상태가 전용 커밋에 착지하므로 요청 삭제 뒤에도 브라운필드 실행의 발동과 revision이 남는다. 도입과 첫 카드 계획 사이에서 세션이 끊겨도 변경 요청이 사라지지 않도록 원문 `유지보수 라우팅 대기` 줄은 계획 커밋까지 보존한다. 층을 열 때는 부모를 만들기 전에 정확한 부모 경로와 자식 번호를 journal 마커로 쓰고, 모든 자식과 작업 카드 승인이 계획 커밋에 착지할 때 지운다. 루트 대기 능력 파일은 작업 카드가 아니어서 승인·검토 필드가 없고, 새 프로젝트의 골조는 빈 폴더로 만들지 않고 다음 층에서 직계 카드와 함께 만든다. 일반 작업의 최종 커밋 뒤 경계는 Git의 rename label이 아니라 HEAD 점유 경로 부재·동일 부모의 번호와 이름이 같은 `.done.` 파일 하나·byte 동일성으로 판정하고, 능력 폐쇄는 통과 revision을 담은 시작 마커로 복구한다. 활성 직계 자식이 모두 `.done`인 비능력 폴더는 깊은 곳부터 닫고, 능력 폴더만 verify 통과 뒤 닫는다
