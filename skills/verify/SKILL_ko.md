# verify — 검증

먼저 규칙 정본(`../principles/SKILL.md`)와 `devflow/project/arch.md`의 `verify_channel`을 읽는다.

목적: 실제 실행으로 기준을 대조한다.

## 층

| 층 | 대조 대상 | 시점 | 담당 |
|---|---|---|---|
| 작업 | 완료 신호 실행 + 커밋 전 코드 검토 | work가 자동으로 | 구현 컨텍스트 + reviewer |
| **능력** | 사용자 시나리오 1개를 창구로 관통 | 능력 폴더가 전부 .done.일 때 | **verifier (깨끗한 컨텍스트)** |
| **제품** | product.md 성공 판정 전부 | MVP 도달 시 | verifier (깨끗한 컨텍스트) |

이 스킬의 본체는 능력·제품 층이다. 작업 층(신호 실행 + 검토)은 work에 흡수되어 있다.

역할의 이원화 — 서로 침범하지 않는다:
**reviewer는 읽되 실행하지 않고** (화이트박스 — 속이 맞는가),
**verifier는 실행하되 읽지 않는다** (블랙박스 — 겉이 맞는가).

## 절차

```
1. verify_channel을 읽는다. 검증은 반드시 작업 서버(작업 트리)에서 — 새 코드를 검증하는 것이다
2. 대상 층의 기준을 읽는다 (능력: 시나리오 / 제품: 성공 판정)
3. 창구로 실제 실행한다 — 브라우저 MCP 클릭, HTTP 호출, CLI 실행
4. 판정은 셋 중 하나로만: 통과 · 실패 · 미검증
5. 능력층 추가 확인 세 가지:
   - **회귀**: 같은 능력 폴더 내 `.done.` 카드들의 완료 신호 재실행
   - **경계**: 시나리오 중 경계 입력 하나는 악의적·비정상 입력으로 실행
     (code-style.md 신뢰 경계 절의 자세 등급을 강도 기준으로)
   - **표준**: code-style.md 위반이 눈에 띄는지 훑는다 — 스펙 부합과 별개의 축이다
6. 실패 → 같은 폴더에 수정 카드 생성 (예: 02.3b-fix-...) 후 트리에 반영
7. **능력층 통과 → 그 능력 폴더에 `.done`을 부여한다.** 검증 전에 붙이지 않는다 —
   검증 안 된 능력이 완료로 보이는 것이 트리의 거짓말 중 최악이다
```

**철칙: 실행하지 않은 것은 통과가 아니라 미검증이다.**
코드를 읽고 "맞는 것 같다"는 판정이 아니다. 창구 실행 결과(응답·화면·출력)를
판정 근거로 기록에 남긴다.

## 편향 제거

검증은 **구현 이력을 보지 않은 컨텍스트**에서 돈다.
- Claude: `verifier` 에이전트로 실행 (플러그인에 포함)
- 그 외: 새 세션/에이전트에 카드(또는 시나리오) + verify_channel만 준다.
  무슨 코드를 어떻게 고쳤는지는 주지 않는다.

권장 등급: T-상 + 낮은 사고량으로 짧게 (판정이지 탐구가 아니다).

## 실패 반복

같은 대상 3회 실패 → 멈추고 사람 호출. 4번째 시도는 없다 (규칙 정본의 실패 사다리).

## 기록 — devflow/tree/<능력폴더>/verify.md

```markdown
# 검증 · <능력이름> · <날짜>
시나리오: <한 줄>
실행: <창구 + 실제 실행 내용>
판정: 통과 | 실패 | 미검증
회귀: <재실행한 완료 신호 목록 + 결과>
표준: <code-style 위반 유무. 위반은 수정 카드로>
실패 시: <생성한 수정 카드>
```
