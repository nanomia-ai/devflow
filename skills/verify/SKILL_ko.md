# verify — 검증

먼저 규칙 정본(`../principles/SKILL.md`)와 `devflow/project/arch.md`의 `verify_channel`을 읽는다.

목적: 실제 실행으로 기준을 대조한다.

## 층

| 층 | 대조 대상 | 시점 | 담당 |
|---|---|---|---|
| 작업 | 완료 신호 실행 + 커밋 전 코드 검토 | work가 자동으로 | 구현 컨텍스트 + reviewer |
| **능력** | 사용자 시나리오 1개를 창구로 관통 | 능력 폴더가 전부 .done.일 때 | **verifier (깨끗한 컨텍스트)** |
| **제품** | product.md 성공 판정 전부 | MVP 도달 시 | verifier (깨끗한 컨텍스트) |

이 스킬의 본체는 능력·제품 층이다. 작업 층(신호 실행 + 검토)은 work에 흡수되어 있다.

역할의 분리 — 서로 침범하지 않는다:
**reviewer는 읽되 실행하지 않고** (화이트박스 — 속이 맞는가),
**verifier는 실행하되 읽지 않으며** (블랙박스 — 겉이 맞는가),
**auditor는 읽고 실행하되 구현 이력을 모른다** (감리 — 판정 없이 소견만. 아래 감리 절),
**retrospector는 devflow 산출물만 읽고 실행하지 않는다** (회고 — 설계 대안의 사후 평가. 아래 회고 절).

## 절차

```
1. verify_channel을 읽는다. 검증은 반드시 작업 서버(지금 체크아웃된 코드를 실행하는 곳)에서 — 새 코드를 검증하는 것이다
2. 대상 층의 기준을 잡는다 (능력: 시나리오 — 메인이 product.md의 능력 서술과 카드
   목적지에서 구성한다 / 제품: 성공 판정)
3. 창구로 실제 실행한다 — 브라우저 MCP 클릭, HTTP 호출, CLI 실행
4. 판정은 셋 중 하나로만: 통과 · 실패 · 미검증
5. 능력층 추가 확인 네 가지:
   - **회귀**: 같은 능력 폴더 내 `.done.` 카드들의 완료 신호 재실행,
     그리고 **이 폴더의 카드들이 `의존`으로 지목한 카드의 완료 신호도** (번호 접두사가
     폴더를 알려준다. 지목된 카드만, 1홉 — 아래층을 깨뜨리는 능력은 자기 폴더만
     봐서는 안 보인다). 이 환경에서 실행할 수 없는 신호(CI 등 원격 전용)는
     그 원격 증거의 최신 결과로 갈음한다. 조사 카드의 신호는 실행이 아니라
     기록이다 — 재실행 대신 메인이 카드 진행 로그의 답·근거 존재를 확인한다 (문서 축)
   - **경계**: 시나리오 중 경계 입력 하나는 악의적·비정상 입력으로 실행
     (code-style.md 신뢰 경계 절의 자세 등급을 강도 기준으로)
   - **표준**: code-style.md 위반이 눈에 띄는지 훑는다 — 스펙 부합과 별개의 축이다
   - **잠정값**: 이 폴더의 카드가 해소한 arch.md 잠정값 행이 실제로 교체됐는지 확인한다 —
     자기 카드가 이미 답한 질문을 계속 던지는 문서는 다음 능력을 오도한다
6. 실패 → 같은 폴더에 수정 카드 생성 (예: 02.3b-fix-...) 후 트리에 반영.
   verifier의 실패에서 태어난 수정 카드의 완료 신호는 그 재현 절차를 창구로
   재실행하는 것이다 — 빠져나간 결함이 신호가 되어, 회귀가 이후 내내 재실행한다.
   실패의 원인이 코드가 아니라 성공 판정의 내용 반증이면 (그대로 실행하면 틀린
   신호를 주는 기준) 수정 카드가 아니라 발견→갱신 표의 반증 행(정체성 문단·성공
   판정)으로 보고한다.
   다중: 수정 카드는 무기명(대기)으로 만든다 — 배정은 통상 경로(실행 제안·점유)로
7. **능력층 통과 → 그 능력 폴더에 `.done`을 부여한다.** 검증 전에 붙이지 않는다 —
   검증 안 된 능력이 완료로 보이는 것이 트리의 거짓말 중 최악이다
8. `.done` 부여와 함께 journal 전체를 정리한다 — 어느 능력에서 왔든 효력이 끝난 줄은
   지우고, 계속 효력이 있는 줄은 핵심 문서로 승격(발견→갱신 표)하거나 남긴다(교차 사안).
   정리 결과는 verify.md에 1줄 남긴다. journal은 항상 한 화면을 목표로 한다
```

재개봉된 능력의 재폐쇄는 시나리오를 바뀐 행동의 범위로 좁혀도 된다 —
**회귀는 언제나 폴더 전체의 신호를 재실행한다.**

역할 소유권: **시나리오·회귀의 실행과 판정은 verifier의 것이다.** 문서를 읽는 축(표준·잠정값)과
회귀 실행 목록 구성·journal 정리·수정 카드 생성은 verify를 진행하는 메인 세션의
것이다 — verifier는 구현도 문서도 읽지 않는다.

다중: 능력 폐쇄는 **통합 브랜치에서, fetch 후에만** 한다 — 낡은 브랜치 시야에서는
"폴더 전부 done"이 거짓 참일 수 있다. 폐쇄자의 플랫폼에서 실행 불가한 신호는
원격 증거 갈음(회귀 절 — 모드 공통) 또는 소유 구성원 위임으로 처리한다 —
배분을 verify.md에 기록한다. journal 정리는 폐쇄를 실행한 구성원이 한다.

판정 근거는 창구 실행 결과(응답·화면·출력)로 기록에 남긴다.

## 편향 제거

검증은 **구현 이력을 보지 않은 컨텍스트**에서 돈다: 깨끗한 서브에이전트/새 세션에 이
스킬 옆의 `verifier.md`를 **원문 그대로(요약 금지)** 브리핑으로 주고, 입력은 검증 대상(진행
로그 절을 뺀 카드, 또는 시나리오) + verify_channel만 준다. 무슨 코드를 어떻게 고쳤는지는
주지 않는다 — 진행 로그가 곧 그 이력이다.

권장 등급: T-상 + 낮은 사고량으로 짧게 (판정이지 탐구가 아니다).

## 실패 반복

같은 대상 3회 실패 → 멈추고 사람 호출. 4번째 시도는 없다 (규칙 정본의 실패 사다리).

## 감리 — 사건 발동

감리는 검증이 아니라 소견이다 — 판정을 내리지 않고, 통과와 `.done` 부여를 막지도
늦추지도 않는다. 세 사건에서만 돈다:

- 제품층 검증과 함께 — 1회
- 능력 폐쇄 verify를 시작할 때 그 폴더의 verify.md가 "판정: 실패"를 기록하고 있으면 —
  이번 통과와 `.done` 부여 뒤 1회. 재폐쇄는 감리를 재실행하지 않는다 — 새 유출이
  새 사건이다
- 사용자가 요청할 때 — 요청 범위가 지금까지의 전체면 제품층 형식으로

깨끗한 서브에이전트/새 세션에 이 스킬 옆의 `auditor.md`를 **원문 그대로(요약 금지)**
브리핑으로 주고, 입력은 product.md의 그 능력 서술(제품층은 product.md 전체)과
verify_channel만 준다. 구현 이력·진행 로그는 주지 않는다.
권장: T-중 + 높은 사고량 (판정이 아니라 탐구다).
소견은 사용자 보고에 싣는다 — 사용자가 채택한 소견만 유지보수 라우팅(split)으로
카드가 되고, 기각된 소견은 기록하지 않는다 (기각도 결정이다).

## 회고 — 사건 발동

회고는 검증이 아니라 소견이다 — 설계 대안의 사후 평가이며, 무엇도 막지도 늦추지도
않는다. 세 사건에서만 돈다:

- 1층 능력이 처음 폐쇄될 때 — 그 능력 범위로 1회. 입력을 좁힌다: product.md의
  그 능력 서술 · 그 폴더의 목록과 verify.md (arch.md·journal은 전체를 그대로 준다).
  재폐쇄는 재실행하지 않는다
- 제품층 판정이 처음 기록된 뒤 — 판정과 무관하게 1회. 실패를 고친 재검증은
  재실행하지 않는다 — 재기준선(product·arch 재실행)이 만든 새 MVP만 새 사건이다
- 사용자가 요청할 때 — 진행 중이면 지금까지의 전체가 범위다

깨끗한 서브에이전트/새 세션에 이 스킬 옆의 `retrospector.md`를 **원문 그대로(요약
금지)** 브리핑으로 주고, 입력은 devflow 산출물만 준다: product.md · arch.md(+
decisions/) · 트리 목록(파일명·상태만) · journal.md · 각 verify.md(트리 루트 포함).
코드는 주지 않는다. 권장: T-중 + 높은 사고량.
소견은 사용자 보고에 싣는다 — 채택된 소견만 유지보수 라우팅(split)의 카드 또는
재기준선으로 이어지고, 기각된 소견은 기록하지 않는다.

## 기록 — devflow/tree/<능력폴더>/verify.md

제품층 기록은 `devflow/tree/verify.md`(트리 루트)에 같은 형식으로 남긴다.
재검증은 같은 파일을 덮어쓴다 — 이력은 git이 기억한다.

```markdown
# 검증 · <능력이름> · <날짜>
시나리오: <한 줄>
실행: <창구 + 실제 실행 내용>
판정: 통과 | 실패 | 미검증
회귀: <재실행·갈음·확인한 완료 신호 목록 + 결과>
표준: <code-style 위반 유무. 위반은 수정 카드로>
잠정값: <교체 확인한 arch 행 또는 없음>
journal 정리: <승격·삭제한 줄 수 또는 없음>
실패 시: <생성한 수정 카드>
감리: <소견 n건 · 채택 m건 | 소견 없음 | 미실시>
회고: <소견 n건 · 채택 m건 | 소견 없음 | 미실시>
```
