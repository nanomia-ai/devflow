# design — 디자인 기획 (선택)

먼저 규칙 정본(`../principles/SKILL.md`)와 `devflow/project/product.md`,
`devflow/project/arch.md`를 통독한다. 존재하면 `devflow/project/design.md`·
`devflow/project/glossary.md`와 `devflow/journal.md`를 각각 통독한다.

**게이트:** `arch.md`의 `frontend: none`이면 실행하지 않는다 — 그렇게 답하고 끝낸다.
`needed`여도 사용자는 건너뛰거나 나중에 돌아올 수 있다. 명시적으로 design을 요청하지 않았다면
"디자인 기획을 할까요, 현재 또는 기본 스타일로 갈까요?"라고 묻는다. 건너뛰기는 상태가 아니며
파일·마커·커밋을 만들지 않고 split을 계속한다.

트리가 이미 있을 때 design 최초 실행이나 방향 변경을 요청받으면 기록이 먼저다. 그 요청에 대응하는
미해소 `유지보수 라우팅 대기` 줄이 없으면 design.md를 바꾸지 않고 split의 유지보수 라우팅으로
보내 줄과 `<id> boundary — request recorded` 커밋부터 남긴다. split이 2a로 돌려보냈거나 같은
미해소 줄이 있으면 진행한다. design은 그 줄을 지우지 않는다 — 확인·커밋 뒤 split이 같은 출처로
구축 카드를 계획할 때 소비한다.

목적: UI 구축의 방향과 경계를 결정해 `devflow/project/design.md`에 기록한다. 이 단계는
토큰·테마·컴포넌트·프리뷰 코드를 만들지 않는다. 실물은 이 문서를 읽고 split이 여는 카드가 소유한다.

## 절차

### 1. 여섯 결정

아직 유일하지 않은 결정만 추천과 함께 한 묶음씩 묻는다.

| 필드 | 결정할 것 |
|---|---|
| 접근 방식 | 어떤 디자인 방향을 핸드오프 이식·라이브러리+스타일·자체 개발·혼합 등의 방식으로 구현할지 |
| 디자인 원천 | 외부 산출물·라이브러리 기본값·저장소 자산 중 무엇이 어느 범위의 정본이며 충돌 때 어느 쪽을 갱신할지 |
| 토큰 전략 | 무엇을 토큰화하고 원천→코드 변환·동기화 방향과 예정 목적지를 어떻게 둘지 |
| 컴포넌트 전략 | 재사용·테마 커스터마이징·래퍼·자체 구현의 경계와 공유 범위 |
| 분해 축 | split이 작업 카드를 나눌 경계 한 문장 |
| 검토 표면 | 소유자가 구축 결과를 볼 대상과 예정 실행 방법 |

위 방식들은 열린 예시이지 닫힌 목록이 아니다. 여섯 필드는 자유 문장이며 **`안 함` 또는 `없음`과
그 이유도 유효한 값**이다. 이미 product·arch·기존 design·glossary나 사용자가 지목한 정확한
원천에 답이 있으면 되묻지 않는다. design은 저장소 전체를 조사하거나 기획 증거 규율의 새 소비자가
되지 않는다. 구현 사실이 더 필요하면 split의 유계 대조나 조사 카드가 답을 만든다.

분해 축을 적용해도 `목적지` 하나를 출처로 확정할 수 없으면 추측하지 않는다. split의 기존 매핑
질문으로 사용자에게 그 목적지만 묻는다.

### 2. 산출

확인받을 `devflow/project/design.md` 묶음을 메모리에서 다음 형식으로 만든다.

```markdown
# 디자인

접근 방식: <자유 문장>
디자인 원천: <정확한 외부 산출물·기존 경로·없음 + 범위별 권위 방향>
토큰 전략: <정본·변환/동기화 방향·예정 경로 또는 안 함 + 이유>
컴포넌트 전략: <재사용·테마/래퍼·자체 구현 경계 또는 안 함 + 이유>
분해 축: <카드 경계를 정하는 한 문장>
검토 표면: <볼 결과와 예정 실행 방법 또는 없음 + 이유>

## 구축 범위
| 항목 | 처분 | 원천 또는 예정 목적지 | 확인 방법 |
|---|---|---|---|
| <범위> | <재사용·테마·자체·이식·지연 등의 자유 문장> | <정확한 참조> | <검토 표면> |
```

`처분`은 진행 상태 토큰이 아니라 결정 문장이다. 카드 진행률은 design.md에 쓰지 않는다.

### 3. 확인·착지·구축

완료 조건은 여섯 필드와 구축 범위가 현재 범위에서 유일하고, 사용자가 문서 전체를 확인한 것이다.
확인 전에는 코어 경로를 바꾸지 않는다. 확인하면 design.md만 규칙 정본의 기존 Layer 0 커밋
`design — design.md`로 착지시킨다. 코드 산출물이나 프리뷰 실행은 이 단계의 완료 조건이 아니다.

다음은 split이다. split은 구축 범위와 분해 축을 기존 출처 매핑·한 층 열기·크기 판정에 적용해
카드를 만들고 실행 제안을 승인받는다. 여러 능력의 전제인 공유 구축은 골조 카드 후보이고 능력
하나의 구축은 그 능력 카드 후보이지만, 배치는 기존 규칙이 결정한다. 호환되는 기존 카드는
유지하고 새 방향과 함께 참일 수 없는 카드만 기존 `.stale.`·재분할 절차를 따른다.

구축 결과가 예정 경로·이름·명령을 확정하면 규칙 정본의 발견→갱신 행으로 design.md의 정확한
한 줄만 교체한다. 여섯 결정의 방향이 바뀌면 위 기록-먼저 경로로 design을 다시 실행한다.
소유자는 여기서 방향 문서를 확인하고, split의 실행 제안에서 실제 카드·순서·완료 신호를 승인한다.
