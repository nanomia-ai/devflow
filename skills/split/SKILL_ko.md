# split — 작업 분할

먼저 규칙 정본(`../principles/SKILL.md`)·상태 판정 정본
(`../principles/state-predicates.md`)·`devflow/project/product.md`(정체성 문단·능력 목록),
`devflow/project/arch.md`, 그리고 존재하면 `devflow/project/design.md`·
`devflow/project/code-style.md`·`devflow/project/glossary.md`와 **`devflow/journal.md`**를
각각 통독한다 — 앞선 카드들의 오래 남는 발견이 journal에 있고,
HANDOFF는 덮어써져 그것을 나르지 못한다.

기획 증거 규율(`../principles/planning-evidence.md`)은 아래 유지보수 기획 깊이를 판정할 때만
유계하게 읽는다. 먼저 `미지수 네 종류`·`차단 사실과 후속 사실`·`출처 소유권`·`정지 조건`·
`실제 제시 선택지 기준`·`구속 전 재검토` 절을 읽고, 사실 확인이 필요할 때만 `영속화`·
`격리 조사` 절을 더 읽는다.

목적: 작업 트리를 **한 번에 한 층만** 열고, 실행 제안을 승인받는다.

## 시작 조건

1. **product.md가 없으면 중단한다.** 코드가 없으면 product를, 기존 코드가 있으면
   adopt(브라운필드 = 이해 단계)를 먼저 안내한다. 프로젝트를 모른 채 쪼개지 않는다.
2. `devflow/tree/`를 훑어 현재 상태를 파악한다.
3. **무엇을 열지 선언한 뒤 진행한다:** "02-registration 아래 3층을 엽니다 (현재 02.3.2까지 done)."
   tree/가 아직 없으면 "트리를 새로 만듭니다"가 선언이다. 어긋난 인식은 이 한 줄에서 사람이 잡는다.

## 트리 구조

```
devflow/tree/
  01-foundation/            ← 필요한 리포 셋업·검증 창구·공유 계약 카드만 두는 골조
  02-<능력이름>/            ← product.md의 능력이 그대로 폴더가 된다. 이름도 그대로
    02.1-<작업>.md
    02.2-<작업>.wip.md
  03-<능력이름>.md          ← 아직 안 연 능력의 대기 파일. 본문은 `# 03 <능력이름>` 한 줄
```

- 폴더/파일 이름 = product.md·arch.md의 용어 그대로. 새 단어를 만들지 않는다.
- 상태 접미사·번호 규칙은 규칙 정본의 상태 표기 절을 따른다.
- 브라운필드: 기존 완성 코드를 소급해 `.done.` 카드로 채우지 않는다.
  arch.md가 `브라운필드: 예`이면 최초 트리에 골조·능력 대기 파일을 만들지 않는다.
  도입 뒤 사용자가 요청한 변경만 유지보수 라우팅으로 제 위치에 만든다. 요청한 변경이
  없으면 트리를 만들지 않고 새 요청을 기다린다.

## 한 번에 한 층만 연다

```
새 프로젝트 시작 → 능력 목록(대기 파일들)까지만. 빈 골조 폴더는 만들지 않음
첫 능력 착수 전  → 골조(01)의 작업들. 폴더와 직계 카드를 함께 만듦
능력 착수 직전   → 그 능력의 작업들
작업이 커 보이면 → 그 자리에서 폴더로 승격해 더 쪼갠다
```

전부 미리 쪼개지 않는다. 앞의 구현이 뒤의 분해를 바꾼다 — 모르는 것은 코드를
쳐봐야 알게 되고, 그때 쪼개는 게 정확하고 싸다.

`브라운필드: 아니오`에서 트리 루트를 처음 열 때는 product.md의 은퇴하지 않은 능력마다
그 능력에 배정된 트리 번호와 능력 이름으로 대기 파일 하나만 만든다. 이 파일은 작업 카드가
아니며 위 예시의 제목 한 줄 외에는 아무 필드도 갖지 않는다. 사용자에게 번호와 이름의 대응을 제시해 승인받은 뒤,
대기 파일들과 층 열기 마커 삭제를 계획 커밋 하나로 착지시킨다. 다음 split은 첫 능력을 열기
전에 `01-foundation/`과 리포 셋업·검증 창구에 필요한 직계 작업 카드를 함께 만든다.
`01-foundation/`은 직계 카드를 하나 이상 가져야 하며 빈 상태로 커밋하지 않는다.

**product.md와 트리의 대응 복원**(resume이 라우팅): 대응하는 폴더도 대기 파일도 없는
product.md의 은퇴하지 않은 능력마다 배정된 트리 번호로 대기 파일을 만들고,
`브라운필드: 아니오`에서는 `.stale` 폴더도 `.stale.md` 파일도 없는 은퇴 능력마다
`.stale.md` 파일을 만든다. 출처가 `core:devflow/project/product.md#능력`이고 `자식`이 그
번호들인 정본 층 열기 마커를 먼저 쓰고, 계획을 제시해 승인받은 뒤 파일들과 마커 삭제를 계획
커밋 하나로 착지시킨다.

기존 폴더에 직계 자식을 더하는 경우까지 포함해, 부모 폴더·자식·대기 파일을 처음 바꾸기 전에
이번에 만들 직계 자식 번호 전부와 그 층을 요구한 정확한 영속 출처를 정한다. 규칙 정본 형식의
층 열기 마커를 쓰고, 아직 커밋되지 않은 출처 기록이 있으면 함께 `split — begin <부모>`
커밋으로 먼저 착지시킨다. 그 전에는 트리 경로를 만들거나 rename하지 않는다. `자식`은 번호
전부를 정본 카드 번호 순서로 `+`로 이은 값이다. 새 프로젝트 루트와 능력 대기 파일 전환은 product.md의
능력 절, 골조는 arch.md의 문서 H1, 승격은 변환 전 카드가 있는 commit, 작업 중 추가한 선행·
조사 카드는 현재 카드의 checkpoint commit, 유지보수는 그 요청의 `유지보수 라우팅 대기` 줄,
검증에서 생긴 카드는 `라우팅: 대기`인 실패 이력의
`verify:<경로>#실패 이력@<출처 id>` 또는 감리·회고 채택 소견의
`verify:<경로>#<감리|회고>@<출처 id>/<소견 번호>`를 `출처-json`으로 쓴다. 출처 id와 소견 번호는
계획 커밋까지 같은 항목에 남아야 한다. `card:` 출처 commit이 통합 브랜치의 조상이
아니면 마커나 tree diff를 쓰기 전에 현재 브랜치를 그 commit까지 arch.md의 `merge` 방식으로
통합한다. rebase가 hash를 바꾸면 locator에는 Git이 출력한 바뀐 전체 commit object ID를 쓴다. 그 뒤 시작 커밋이 번호
발급의 구속 결정으로 통합 브랜치에 착지한다.

현재 체크아웃 또는 HEAD에 유효한 층 열기 마커가 있으면 새 층을 열지 않는다. timestamp가 가장 빠른 마커를 먼저 처리하고,
같으면 journal에서 먼저 나온 줄을 쓰되, 같은 `출처-json`을 가진 마커는 함께 가져온다 — 그
묶음은 실행 제안 한 번과 계획 커밋 하나를 받고 부모마다 따로 받지 않는다. 그 계획 커밋은
묶음의 마커 전부와, `출처-json`이 지목한 journal 원 요청 줄이 아직 남아 있으면 그 줄까지
함께 지운다. 정본 형식으로 `출처-json`을 복원해 그 출처를 열고,
이 스킬의 시작에서 읽은 상위 문서와 결합한다. 유지보수 또는 재분할 출처이면 아래 2단계가
열도록 정확히 열거한 현재 코드·기존 기록도 다시 대조한다. 출처가 없거나 정확히 하나로
해결되지 않으면 정합성 이상으로 보고한다. 현재 대화나 다른 문서로 출처를 대체하지 않는다.

이미 존재하는 직계 자식은 유지하고, 마커가 발급했지만 없는 번호만 같은 출처에서 다시
구성한다. 마커 밖의 번호를 더 만들지 않는다. 목적지 하나를 출처로 확정할 수 없으면 사용자에게
그 목적지만 묻고 답 전에는 자식을 만들지 않는다. 마커의 자식 번호 하나가 부모의 직계 자식
정확히 하나의 선두 번호와 일치할 때 그 자식이 존재한다. 둘 이상이면 정합성 이상이다. 모든
번호가 하나씩 존재하면 카드의 `승인`이 상태 판정 정본상 유효하지 않은 실행 제안을 다시
승인받고, 카드·승인·구조와 마커
삭제를 이 층의 계획 커밋으로 끝낸다. 시작 커밋 뒤 중단된 층은 새 번호를 발급하지 않는다.

journal에 `재분할 대기` 마커가 있으면 일반 층보다 먼저 timestamp가 가장 빠른 한 줄을
처리한다. 같으면 journal에서 먼저 나온 줄이다. 마커가 정확히 지목한 폴더와 `.stale.` 카드,
출처 절, 아래 유지보수 라우팅 2단계가 그 흐름에 대해 열도록 열거한 현재 코드·기존 기록을
읽는다. 이 목록 밖의 문서는 열지 않는다.
교체 카드 번호와 각 무효 번호를 대신할 교체 번호 묶음을 정한 뒤, 그 `재분할 대기` 줄 전체를 `journal:` 출처로 삼은 층 열기 마커를 시작
커밋으로 먼저 착지시킨다.

교체 대기 카드를 하나 이상 그 폴더에 만든다. 그 폴더와 1층 능력 또는 골조까지의 조상에
`.done`이 있으면 모두 벗긴다. 전체 트리의 `.stale.` 아닌 대기 카드와 점유 카드에서 `의존`
항목 하나가 무효 번호와 정확히 같으면 승인받은 교체 번호 묶음으로 바꾼다. 점유 카드는 변경
대상에 포함한 뒤 먼저 해제해야 하며, 남의 점유라면 규칙 정본의 재배정 승인을 먼저 받는다. 바뀐 대기 카드의
`승인`은 `대기`로 되돌린 뒤 새 실행 제안에서 다시 승인받는다. `.done.` 카드의 과거 의존은
바꾸지 않는다. 그 결과가 새 상위 결정과 함께 참일 수 없다면 그 카드도 애초 문서 계층
절차에서 `.stale.` 대상이어야 한다.

교체 카드·의존 교체·승인·조상 rename·층 열기 마커와 재분할 마커 삭제를 계획 커밋 하나로
착지시킨다. 교체 카드의 완료가 아니라 이 계획 커밋이 두 마커의 해소 조건이다. `.stale.`
카드는 역사로 남기고 지우지 않는다. 무효 번호 하나의 교체 묶음이 하나로 결정되지 않거나
마커의 폴더·카드·출처 중 하나라도 없으면 추측하지 않고 사용자 선택 또는 정합성 이상으로
보고한다.

arch.md 잠정값 표에 해소 카드가 '미발급'인 행이 있으면, 여는 층이 해소할 행의 카드를
이 층에 만들고 '미발급'을 그 번호로 교체한다 (발견→갱신 표).

`devflow/project/design.md`가 있으면 분해 축은 빌드 전략을 따른다:
A 목업 선행 → 화면 단위 / B 수직 슬라이스 → 기능을 프론트~백 관통 단위 / C 계약 선행 → 계약 카드 먼저, 그 아래 프론트·백 병렬.

## 크기 판정

```
카드 하나 = 완료 신호 하나 + 작업 커밋 하나
어느 한 부분이 미완인 채로 다른 부분의 완료 신호가 통과할 수 있다 → 별도 카드로 나눈다
형제 카드가 7개를 넘는다 → 중간 묶음 폴더를 하나 만든다
```

## 트리는 재귀다 — 깊어질 때

카드가 폴더로 승격되는 것은 실패가 아니라 정상이다. 몇 층이든 같은 규칙이 반복된다:

```
02.3-고객관리.md            ← 열어 보니 커밋 1개로 안 끝난다
  ↓ 승격
02.3-고객관리/
  02.3.1-목록.md
  02.3.2-필터.md
  02.3.3-모달.md            ← 이것도 크면 다시 02.3.3-모달/ 로 승격
```

승격 절차 (착수 전에 발급 선언부터 — 자식 번호는 발급이다, 실행 제안 절의 규칙 그대로):
1. 진행 로그가 비어 있지 않은 카드면, 바꾸기 전에 카드를 체크포인트로 커밋한다
   (`NN.N wip:` — 로그의 git 보증은 이 커밋이 만든다. 위 `card:` 출처 규칙에 따라
   마커 전에 checkpoint를 통합한다)
2. 자식 번호를 정한다. 변환 전 카드가 있는 현재 commit에서 Git이 출력한 전체 object ID와 카드 경로를
   `card:` 출처로 삼아 층 열기 마커를 쓰고 시작 커밋을 먼저 착지시킨다
3. 카드 파일을 **같은 번호·같은 이름의 폴더**로 바꾼다
4. 원래 카드의 목적지·왜·금지·의존과 이월된 인용은 자식 카드들에 분배한다 — 폴더
   자체는 카드를 갖지 않는다 (폴더의 의미는 이름과 자식들이 말한다. 능력 폴더와 같은 원리)
5. 자식 번호 = 부모 번호 + 한 자리 (`02.3` → `02.3.1`). 번호 불변 규칙은 그대로
6. 대기·점유 상태인 다른 트리 카드의 `의존`에서 쉼표로 나뉜 항목 하나가 부모 번호와 정확히
   같으면 그 항목을 이번 승격에서 태어난 자식 번호들로 교체하고 다른 항목의 순서는 유지한다.
   `읽을 것`이 사라질 부모 카드의 정확한 경로를 담으면 그 내용을 넘겨받은 자식 카드 경로로
   교체한다. 바꿀 카드가 점유 상태면 변경 묶음에 넣고 먼저 해제한다. 남의 점유는
   규칙 정본의 재배정 승인이 없으면 승격을 멈춘다. 바뀐 대기 카드의 승인은 `대기`로 되돌려
   10단계에서 다시 받는다. `.done.`·`.stale.` 카드는 고치지 않으며 다른 글은 찾거나 바꾸지 않는다
7. arch.md 잠정값 표의 `해소 카드` 값이 부모 번호와 정확히 같으면 그 행의 질문을 해소할
   자식 하나를 정해 그 번호로 교체한다. 어느 자식도 해소하지 않으면 승격 커밋 전에
   자식 구성을 고친다
8. 카드에 점유 접미사(`.wip-<내 id>.`)가 있었다면 접미사를 없애고,
   현재 구현이 속한 자식 하나를 실행 제안에서 이어갈 카드로 지목한다. 자식은 모두
   대기로 태어난다
9. 진행 로그가 있었다면 먼저 전역 결정을 발견→갱신 표로 착지시킨다. 남은 작업 한정
   금지는 해당 자식의 `금지`에, 실제 파일·문서 경로는 `읽을 것`에 넣는다. 완료한 내용과
   정확한 다음 구현 지점은 8단계에서 지목한 자식의 진행 로그로 옮긴다. 이어갈 자식이
   없으면 분해가 현재 진행분의 목적지를 잃은 것이므로 자식 구성을 고친다
10. 자식들의 실행 제안을 제시해 승인받고 카드별 승인 필드를 쓴다
11. 폴더 전환·자식·6~7단계의 교체·승인·층 열기 마커 삭제를 계획 커밋 하나로 즉시
     착지시킨다 (`NN.N promote` — 구속 결정이므로 통합에 착지). 그 뒤 이어갈 카드를 통상
     work 절차로 점유한다

- 능력 안의 분해 축은 **기능 단위가 기본**이다 (사용자가 하나로 인지하는 동작).
  프론트/백 같은 기술 축 분해는 빌드 전략 C(계약 선행)일 때만
- 시나리오 검증(verify 능력층)은 깊이와 무관하게 **1층 능력 폴더에서만** 연다.
  중간 폴더는 `.stale.` 아닌 직계 자식이 하나 이상이고 그 자식 전부 `.done`이면 `.done`을
  받을 뿐, 별도 검증 의식이 없다
- 4층을 넘게 쪼개지고 있다면 멈추고 사용자와 범위를 재검토한다 —
  트리가 깊은 게 아니라 능력 하나가 프로젝트만큼 큰 것일 수 있다

## 조사 카드 — 목적지가 추측이 될 때

미지수 하나가 카드의 목적지·완료 신호를 추측으로 만들면, 구현 카드 앞에
**답이 산출물인 카드**를 놓는다.

```markdown
# 04.1 조사: 토스 API 부분환불 지원 여부
목적지:   "지원하는가, 한도·제약은 무엇인가"에 답이 나온다
완료 신호: 진행 로그에 답 + 근거(문서 링크 또는 실제 호출 결과) 기록됨
의존:     없음
읽을 것: 없음
승인:     대기
검토:     해당 없음
```

- 조사 카드는 좌표·정체성을 갖지 않는다 (규칙 정본 정체성 반복 주입의 공인된 예외 —
  답이 나오면 로그가 동결되는 카드라 주입의 효용이 없다). 의존·읽을 것·승인은 작업 카드와
  같은 형식으로 반드시 쓰고, 등급을 생략하면 T-중이다. 검토는 `해당 없음`이다. 본 코드에
  diff가 생기면 work가 검토를 필수로 바꾼다.
- 실행 수단은 자유다: 문서 조사, 실제 호출, **버리는 프로토타입**.
  프로토타입은 버려질 것임을 이름·위치로 명시하고 본 코드에 섞지 않는다 — 결정만 남긴다.
- 답이 사실만이 아니라 다시 실행할 절차·도구이기도 하면 — 『부분환불 지원 여부』의 답은
  사실이고, 『기준 데이터와의 대조 절차』의 답은 도구다 — 버리는 프로토타입 규칙은 그
  도구에 적용되지 않는다. 뒤 카드가 그것을 본 코드로 들이거나 검증 창구의 확인 수단으로
  등재한다 (발견→갱신 표의 확인 수단 행).
- 뒤 구현 카드는 조사 답이 나오기 전에는 `승인: 대기`로 두고 점유하지 않는다. 답이 나오면
  답 때문에 달라진 목적지·금지·완료 신호·의존을 교체하고 실행 제안을 승인받아 계획 커밋으로
  착지시킨 뒤 진행한다. 이미 점유된 카드면 고치기 전에 해제한다. 30분의 조사가 며칠의
  갈아엎기를 대체한다.
- **답은 위로도 간다.** 조사가 해소한 상위 문서의 열린 서술(arch의 잠정값 행 등)을
  교체하지 않으면, 방금 반증한 값이 계층에서 계속 이긴다. work의 환류 단계가
  `.done.` 전에 이를 강제한다.
- 근거가 트리에 남아, 나중에 "왜 이렇게 설계했나"의 답이 된다.

## 수정·추가 요청 라우팅 — 유지보수 단계

"이 페이지의 필터를 고쳐줘" 같은 요청이 오면:

새 사용자 요청은 코드를 읽기 전에 규칙 정본 형식의 `유지보수 라우팅 대기` 줄로 쓴다. 요청
전체를 — 정본 경량 게이트를 통과한 항목이 있으면 그 항목들을 뺀 나머지를 — JSON 문자열
하나로 직렬화한다: 통과 항목은 어떤 journal 줄에도 적히지 않고 경량 차선이 그 대화에서
처리한다(규칙 정본). 뺀 뒤 남는 항목이 없으면 줄을 만들지 않는다 — 그 항목들은 차선의
몫이라고 말하고 끝낸다. 그 줄만 담는 기록 커밋의 메시지는
`<id> boundary — request recorded`다. 이 세션이 점유 카드를 갖고 있으면 그 커밋만 구속
결정으로 착지시키고 카드로 돌아간다 — 요청은 기다렸다가 그 카드가 닫힌 뒤에 계획된다. JSON을 복원한 요청이 같은 미해소 줄이 이미 있으면 다시
쓰지 않는다. 미해소 줄이 하나 이상이면 timestamp가 가장 빠른 줄을 요청으로 삼고, 같으면
journal에서 먼저 나온 줄을 쓴다. verify.md의 `라우팅: 대기` 또는 `사용자 결정 대기` 항목이
요청 원문을 이미 보존한 경우와 위 `재분할 대기` 처리에서는 이 줄을 만들지 않는다.

줄을 사용하기 전에 `요청-json`을 JSON 문자열로 복원한다. 정본 형식이 아니거나 복원되지 않으면
정합성 이상으로 보고하고, 규칙 정본의 12번 복구가 끝나기 전에는 코드를 읽거나 카드·폴더를
만들거나 그 줄을 지우지 않는다.

카드·승인·필요한 폴더 rename이 계획 커밋에 착지할 때 요청 줄과 그 요청의 층 열기 마커 전부를
같은 커밋에서 지운다. 여러 단위에 걸친 요청도 실행 제안을 한 번만 내고 승인도 한 번만 받는다 —
단위마다 따로 승인받으면 스무 개짜리 수정 목록에 승인이 여러 번 필요해진다.
사용자가 요청을 취소했을 때 줄이 아직 미커밋이면 그 줄과 그 줄로 발급한 미커밋
마커·초안 카드를 함께 지운다. 줄이 이미 커밋됐고 그 층
열기 마커가 HEAD 또는 현재 체크아웃에 있으면, 마커 전부와 줄을 함께 지우고 그 마커들로 발급한
미커밋 초안 카드를 버리는 구속 결정 커밋 하나를 착지시킨다. 마커가 없으면 줄 삭제만
구속 결정 커밋으로 착지시킨다. 매핑 질문이나 실행 제안 승인이 끝나지 않았으면 줄을 남긴다.
중단 뒤에는 그 원문이 현재 요청이다.

### 기획 깊이 등급
아래 1~2단계에서 유지보수 요청을 현재 코드와 정확한 기존 출처에 대조한 뒤, 카드를 쓰기 전에
카드의 `목적지`·`왜`·`금지`·`완료 신호` 네 필드가 각각 한 문장으로 유일한지를 다음 표로
판정한다. 페이지·목록·모달 같은 이름이나 크기는 등급 조건이 아니다.

| 등급 | 기계 조건 | 다음 행동 |
|---|---|---|
| 0 | 정확한 기존 출처에서 네 필드가 각각 한 문장으로 유일 | 질문 없이 카드 작성 |
| 1 | 한 질문 묶음의 실제 답으로 네 필드가 유일 | 추천을 붙인 묶음 하나 뒤 카드 작성 |
| 2a | 실제 선택지나 답이 Layer 0 필드를 바꾸거나 ADR 세 조건의 결정을 요구 | 카드를 만들지 않고 소유 단계로 환류. 2b보다 우선 |
| 2b | Layer 0는 보존되지만 한 묶음 뒤에도 어느 카드 필드에 유효 문장이 둘 이상 | 같은 유지보수 대화에서 다음 의존 프런티어를 계속 |

Layer 0 필드는 product의 정체성·능력·경계·성공 판정과 arch의 구성요소·stack·코드 구조·데이터·
검증 창구다. 2b의 답은 네 카드 필드 중 하나에 착지해야 하며, 어느 필드에도 착지하지 않으면
2a로 보낸다. 능력 설계 구역·새 기획 파일·새 상태는 만들지 않는다.

2b는 직전 답이 네 필드 중 하나의 유효 문장 수를 줄이거나 새 실제 의존을 열었을 때만 다음
프런티어를 만든다. 같은 미결 집합이면 표현만 바꾼 질문을 반복하지 않는다. 남은 필드와 추천
하나를 보여 사용자 결정을 기다리거나, 실행 사실이면 기존 조사 카드, Layer 0면 2a로 보낸다.
이 비교는 대화 안에서만 하고 상태로 저장하지 않는다.

새 용어가 확정되면 규칙 정본의 발견→갱신 표가 정한 `glossary.md` 한 줄 경로로 즉시 착지한다.
카드 네 필드가 처음 유일해진 뒤 카드 바이트를 쓰기 전 기획 증거 규율의 구속 전 재검토를 한
번 실행한다. Layer 0를 바꾸는 후보는 비교하지 않고 2a로 보낸다.

1. 요청의 범위를 **위치에 매핑**한다. 매핑 전에 후보 능력 문서의 `Design head` 메타데이터
   줄만 읽고 한 줄 명령
   `git log -1 --format=%H -- devflow/project/product.md devflow/project/arch.md devflow/project/glossary.md`
   를 실행한다. 후보의 문서가 없거나, 정본의 정확한 `legacy v0.10` 형태이거나, 고정 경계가 정확히 하나가
   아니면 저장된 값이 없는 것이므로 "다르다"와 같게 판정한다. 저장된 값이 하나라도 그 출력과
   다르면 매핑하지 않고 `브라운필드: 예`는 adopt,
   `아니오`는 arch로 보내 영향 설계 구역을 먼저 갱신한다. 낡은 경계로 매핑한 카드는 잘못된 능력에 들어간다. 여러 능력이 함께 쓰는
   기반·공유 계약·검증 창구면 `01-foundation`, 그 밖에는 product.md의 해당 능력 폴더다. 이
   매핑 단계에 한해 후보 능력 문서의 고정된 첫 4줄만 읽고 그 밖은 읽지 않는다 —
   `Boundary: owns …; does not own …`이 매핑 오라클이다. **한 요청이 여러 위치에 걸치면
   전부를 매핑한다** — 하나를 고르고 나머지를 버리지 않는다. 어느 위치도 결정되지 않는 부분이
   있거나 매핑된 능력이 product.md에서 은퇴했거나 트리 표현이 `.stale`이면, 시작 커밋 전에
   사용자에게 묻고 원 요청 줄은 그대로 둔다. 은퇴 단위는 product로 보내 재활성화 또는 새
   능력을 먼저 결정하며, 그 답 전에는 어느 단위의 카드도 만들지 않는다
2. 현재 코드에서 요청의 흐름을 추적한다. 대조할 기존 핸드오프·사양 문서는 사용자가 정확한
   경로로 지목한 파일, 그 흐름의 파일이 직접 정확한 경로로 한 번 링크한 파일, arch.md
   `기존 기록`에서 매핑한 능력과 `shared`에 적힌 파일로 한정한다. 링크된 문서 안의 링크는
   따라가지 않는다. 이 카드에 필요한 서술이 현재 코드와 맞는 문서만 정확한 경로로 `읽을
   것`에 넣는다. 다른 경로를 추측하거나 폴더 전체를 넣지 않는다
3. 만들 카드와 이어지는 번호를 정한다(01.7, 02.8…). 유지보수 줄이 있으면 그 줄 전체를
   `journal:` 출처로, verify.md가 요청을 보존했으면 위의 정확한 실패 또는 소견 `verify:` locator를 출처로 삼은 층 열기
   마커를 쓴다. 매핑이 부모 여럿에 걸치면 부모마다 마커를 하나씩 쓰되 전부 같은 `출처-json`을
   갖는다. 아직 미커밋인 유지보수 줄과 함께 마커 전부를 시작 커밋 하나로 먼저 착지시킨다.
   기존 폴더에 카드를 더할 때도 같다
4. 단위마다 매핑한 폴더에 그 카드를 추가한다. 매핑한 폴더가 없고 같은 번호·이름의 루트 대기
   능력 파일이 있으면 그 파일을 폴더로 바꾸고 카드를 만든다. 대기 파일도 없으면 폴더와 카드를
   함께 만든다. 다른 골조·능력 표현은 만들지 않는다
5. 매핑한 폴더마다 그 폴더와 1층 능력 또는 골조까지의 조상에 `.done`이 있으면 **모두 제거한다** — 활성 자식
   전부 done일 때만 `.done`이므로. 이 rename을 잊으면 트리가 거짓말을 한다
6. 제품층 실패도 같은 규칙을 쓴다. 트리 루트에는 작업 카드를 만들지 않는다

**verify-origin 수정 카드 상속.** `신호 카드`가 있는 실패 이력 출처이면 verify가 저장된 값으로
계산해 넘긴 `{현재 항목의 신호 카드} ∪ {같은 root의 직전 수리 라운드가 라우팅: 수정 카드에
기록한 카드 전부}`와 현재 non-pass 증거를 사용한다. 새 root는 신호 카드만, 재관측 1은 root
최초 route 전부, 그 뒤 사람이 추가 수리를 승인했으면 가장 최근 승인·완료 수리 라운드만 받는다.
번호 중복을 제거해 정본 카드 번호 순서로 정렬하며 임의 상한이나 계보 재귀 읽기를 두지 않는다.
route operations가 끝난 최종 트리에서 번호마다 정확한 카드 경로 하나를 계산해 새 카드의 `읽을
것`에 넣는다. 최종 경로가 없거나 둘 이상이면 추측하거나 `라우팅 준비`를 쓰지 않고 route를
만들지 않으며, 정확한 카드 번호와 찾은 경로를 정합성 이상으로 보고한 뒤 사람의 교정 후
같은 source의 유지보수 라우팅을 처음부터 다시 시작한다. 카드의 `왜`에는 현재 non-pass 증거를 쓰고, 직전 수리 라운드가 있으면 그것이 이
신호를 pass로 만들지 못한 결과도 쓴다. 직전 카드의 진행 로그와 현재 실행 증거가 동일 접근의 무변경 반복이 같은
결과를 낸다고 직접 뒷받침할 때만 `금지` 한 줄에 그 반복을 쓰고, 근거가 없으면 금지를 발명하지 않는다.
목적지는 신호 통과 자체가 아니라 그 신호가 지키던 능력 서술을 참으로 만드는 것이다.

**카드 회수.** 1단계에서 이 요청 범위의 기존 대기 카드가 잘못된 폴더에 있는 것이 드러나면,
매핑을 바로잡는 계획 커밋이 원 카드를 같은 경로·번호의 `.stale.` 묘비로 남기고 올바른 폴더에
새 번호로 교체 카드를 만든다 — 단 그 카드가 한 번도 점유된 적 없고 어떤 작업 커밋 제목도 그
번호를 부른 적이 없을 때만이다. 묘비가 그 번호를 트리에 남기므로 다음 발급이 그 번호를 다시
쓰지 않는다. 다른 대기·점유 카드의 `의존`에 그 번호와 정확히 같은 항목이 있으면 같은 계획
커밋에서 교체 카드 번호로 바꾸고, 점유 카드는 먼저 해제한다. 이 묘비는 상위 문서 변경이
아니므로 `재분할 대기` 마커를 만들지 않으며, 진행 로그에 구현 역사를 꾸며 넣지 않는다. 작업
커밋이 이미 그 번호를 담았으면 카드를 옮기지 않고 journal 1줄로 교정을 기록한다.

## 작업 카드 형식

```markdown
# 02.2 가입 API
좌표:   <서비스이름> ▸ ①등록 ▸ 02.2
정체성: <product.md 정체성 문단 그대로 복사>

목적지:    이게 끝나면 무엇이 참이 되는가 (1~2문장)
왜:        이게 없으면 사용자에게 무슨 일이 생기나 (1문장)
금지:      <3줄 이내>
완료 신호:  <실행 가능한 명령/확인 — 예: `pnpm test auth` 통과 + .http로 201 확인>
의존:      없음 | 02.1, 03.2
읽을 것:   <정확한 파일·문서 경로를 한 줄에 하나씩 | 없음>
등급:      T-중 | T-하   <!-- 생략 시 T-중. T-하면 읽을 것·금지·완료 신호를 완전하게 -->
승인:      대기 | YYYY-MM-DDTHH:MM:SSZ; 병렬: <번호+번호|없음>
검토:      필수 | 면제

## 진행 로그
<!-- work가 .wip. 동안 append -->
```

`의존`은 상태 판정 정본의 정규 형식과 구형 해석을 따른다. 새 카드는 정규값만 쓴다. split이
대기 구형 카드를 다음에 고칠 때 뒤의 설명을 지우고 정규값으로 교체한다. 해석되지 않는 항목은
사용자에게 대체값을 확인받으며 추측하지 않는다. 확인된 교정은 다른 필드와 상태를 바꾸지 않고
계획 커밋에 싣는다. 점유 카드면 먼저 해제한다.

split이 시작할 때 대기 카드의 `승인`이 `대기`가 아니면서 상태 판정 정본상 유효하지 않으면
정확한 이유를 보고하고
그 값을 `대기`로 바꾼다. 현재 카드 전체를 실행 제안에 다시 올린 뒤 새 승인값과 카드 변경을 계획
커밋으로 함께 착지시킨다.

**사용자가 진행 중인 카드의 목적지를 바꾸면** 기존 경로를 그대로 쓴다 — work가 체크포인트를
만들고 카드를 해제하면, split이 목적지·왜·금지·완료 신호를 고쳐 실행 제안을 다시 승인받아
계획 커밋에 싣고, 그 뒤 다시 점유한다. 상위 문서가 바뀐 것이 아니므로 `.stale.`도 `재분할 대기`
마커도 만들지 않는다.

목적지를 한두 문장으로 쓸 수 없으면 그럴듯한 것을 지어내지 않는다 — 무엇이 참이 되어야 하는지
사용자에게 묻고 답을 받기 전에는 그 카드를 만들지 않는다. 부실한 목적지는 다음 세션이 이 카드를
이어받을 때 무엇을 해야 하는지 모르게 만든다.

**작은 항목 묶기.** 기록된 요청 줄에 경량 게이트를 통과한 항목은 없다 — 통과 항목은 기록
시점에 경량 차선이 그 대화에서 처리했고 journal 줄에 적히지 않는다(규칙 정본). 그러므로
여기서 항목을 경량 차선으로 돌려보내지 않는다: 요청 줄은 계획 커밋이 한 번에 소비하므로,
차선으로 나간 항목은 중단 시 어느 기록에도 없다. 게이트를 통과하지 못하는 작은 항목 여럿(전이는
바뀌는데 각각 카드를 받기에는 작은 것들)은 카드 하나로 묶는다. 묶으려면 넷을 모두 충족한다:
① 같은 원 요청에서 나왔다 ② 같은 깊이 1 단위에 있다 ③ 하나의 목적지로 결과를 빠짐없이
말할 수 있다 ④ 한 revert로 함께 되돌려도 된다. 실행 제안에 묶인 항목을 하나씩 열거해 보여
주고 승인받는다. **기록을 건너뛰는 경로는 만들지 않는다** — 경량은 커밋이 기록이고, 카드는
문서가 기록이다.

완료 신호는 수단이 허락하는 한 그 능력이 소유한 경로로 좁힌다 — `pnpm test`가 아니라
`pnpm test src/payment`. 작업 트리 하나는 빌드 하나이므로, 저장소 전체를 도는 신호는 다른
흐름의 미완성 코드에 걸리고 실패 사다리가 그 책임을 이 카드에 씌운다.

**구현 방법은 적지 않는다.** 목적지·완료 신호·금지가 하네스의 전부다.
T-하 카드만 예외적으로 순서 힌트까지 준다 (규칙 정본의 하네스 다이얼).

## 실행 제안 — 이 스킬의 마지막 산출이자 관문

연 작업들에 대해 제안하고 **사용자 승인을 받는다**. 조사 답으로 필드를 확정해야 하는 뒤
구현 카드는 이 관문의 연 작업에서 제외하고 `승인: 대기`로 남긴다:

```
실행 제안
02.2~02.4  순차 · T-중 추천 (스키마가 얽혀 판단 필요)
03.1~03.3  병렬 가능 · T-하 + 완전한 카드 (기계적 CRUD, 파일 비겹침 확인함)
→ 현재 사용 가능한 모델 기준 매핑 예시를 제시하고 선택받는다
```

필수 순서는 승인 전에 뒤 카드의 `의존`에 넣고, 등급은 각 카드의 `등급`에 넣는다.
실행 제안의 순서·등급 문구는 설명이며 별도 상태 기록이 아니다.

병렬 허용 조건: 파일이 안 겹치고 + 공유 개발 서버를 건드리지 않는 작업만. **개발 서버를
공유하는 프론트엔드는 순차** (한 에이전트의 컴파일 에러가 전체 화면을 깨뜨린다).
사용자가 승인하면 각 카드의 `승인`을 `YYYY-MM-DDTHH:MM:SSZ; 병렬: <번호+번호|없음>`으로
교체한다. `병렬`은 함께 실행하도록 승인된 카드 번호 전부를 정본 카드 번호 순서로 `+`로 잇고,
묶음의 모든 카드에 같은 값을 반복한다. 병렬이 아니면 `없음`이다. 병렬 묶음을 바꾸면 이전
묶음이나 새 묶음의 대기 카드 `승인`을 계획 커밋 하나에서 모두 고친다. 점유 카드는 승인값을
바꾸지 않으며, 새 묶음에 넣으려면 먼저 해제한다. `.done`·`.stale` 카드의 과거 승인값도
바꾸지 않는다. `병렬:` 값은 계획의 판정 기록이다 — 점유를 허가하거나 막지 않으며(상태 판정
정본), work가 같은 단위의 점유를 알릴 때 정보로 읽는다.

구현 카드의 `검토` 기본값은 `필수`다. 메인 세션은 면제를 선택할 수 없고, 사용자가 해당
카드의 면제를 명시적으로 승인했을 때만 `면제`로 바꾼다. 조사 카드는 `해당 없음`이며, 본
코드에 diff가 생기면 `필수`로 바꾼다. 배정은 기록하지 않는다. 점유 접미사가 현재 소유자를
단독으로 나타낸다.

작업 카드 층은 카드·`승인`·`검토`·층 열기 마커 삭제를 규칙 정본의 계획 커밋으로 함께
착지시킨다. 상태 판정 정본의 승인 판정을 충족하기 전에는 점유하지 않는다.

루트 대기 능력 파일 층을 닫았으면 "다음은 split"이라고 안내해 골조 층을 연다. 그 밖의
작업 카드 층을 승인했으면 "다음은 work"라고 안내한다.
