# Work

## why: purpose

Carry one approved card through implementation, current execution evidence, clean review,
integration, durable feedback, and its observed boundary without replacing principles,
split, verify, or a semantic owner.

## guard: state-kernel-unavailable

Stop when the sibling principles package does not return the structured
`devflow/project-state/2` result. Compatibility rendering, a stale migration wrapper, or a
locally reconstructed journal/card model is not shared state.

## guard: premature-knowledge-marker

A knowledge marker already sourced from this research card is invalid until the durable
conclusion and evidence are present in the card at a committed checkpoint. Preserve the
card and report the marker; do not legitimize it after the fact.

## guard: knowledge-landing-before-closure

Route the exact current-source marker to its named arch or adopt writer. One consumed owner
does not clear another owner’s marker, so a crosscut source remains open until no marker
from that source remains.

## guard: invalid-card

Split owns a missing, stale, noncanonical, or undecidable card contract. Preserve current
progress in the card before release; work does not repair planning authority by inference.

## guard: missing-bounded-basis

An exact `Read first` path that is absent, escapes the repository, or names legacy baseline
wiring has no substitute. Stop with that path instead of searching for a plausible basis.

## guard: closed-history-refusal

An allowed descent has one exact reason and target: the card named now, the prior non-pass
repair lineage being continued, or the exact Source named by the current K or Trap. A unit,
folder, old-card set, or “relevant history” request is broad and remains closed.

## guard: invalid-progress-evidence

Malformed signal, review, carry, or remote-evidence lines are neither prose nor evidence.
Repair the canonical line shape in the card before any completion decision.

## guard: boundary-incomplete

The structured finish-boundary fact names the missing signal, review, carry, or handoff
passenger. Report that exact omission; never invent the lost result or close around it.

## guard: non-work-route

Another canonical route outranks ordinary implementation. Return it to resume without
turning the route into a work-local state or interpreting its rendered text.

## stage: claim-or-reenter

Judgment: Claim only the selected ready card after the contract preflight; otherwise re-enter
the exact current claim. A T-low basis must be concrete enough for its consumer, and the
completion signal must state the expected observation and what it proves.

Why: split owns readiness and the card contract; the binding claim makes concurrent ownership
durable before code changes begin.

## stage: remote-evidence

Judgment: Trust only the current recorded pointer and its fresh result. Pending or inaccessible
evidence waits; fail returns to the anchored failure loop; pass advances to the existing
reviewed finalization; finalizing means the task commit already exists.

Why: remote evidence separates a durable checkpoint from later execution without rerunning
the local signal or manufacturing a second task commit.

## stage: implement-and-signal

Judgment: implementation.action continue signal-ready repair scope-escape park handoff; history.basis none named-card nonpass-repair current-k-source current-trap-source broad invalid. `implementation.action` is exactly `continue`, `signal-ready`, `repair`,
`scope-escape`, `park`, or `handoff`; `history.basis` is exactly `none`, `named-card`,
`nonpass-repair`, `current-k-source`, `current-trap-source`, `broad`, or `invalid`. Work only
inside the card destination and exact bounded inputs. `continue` means the
next named implementation point is not yet signal-ready; `repair` answers anchored non-pass
evidence; scope escape belongs to split; parking requires an explicit request; a mid-task
handoff waits at the next boundary. For closed history, choose only one allowed exact basis.

Why: current progress survives interruption, while scope and historical context stay bounded
to authority the card or present evidence actually names.

## stage: review-reduction

Judgment: `review.action` is exactly `dispatch`, `repair`, `contract-route`, `ask-disposition`, `apply-disposition`, or `block-nonpass`. Current means both fresh and a verdict: its completion inputs and this card's task diff are unchanged since it ran, and the line carries one of the three verdicts. No clean review starts unless the current local completion result is `pass`.

The review boundary is the canonical planning commit carrying the current Approval. Count anchored code-objection results after that boundary in commit order; `pass`, `unverified`, and a card-contract objection do not increase the objection count. A person's disposition is valid only in the same checkpoint as the third code objection and immediately after that result line; a disposition written anywhere else is not one.

Reduce the settled review events with these non-overlapping conditions:

- A valid disposition with no settled `review result` after it selects `apply-disposition`: carry out the disposition, establish a current pass, then take exactly one clean review.
- A valid disposition with exactly one settled `review result` after it, and it is `pass`, completes review and proceeds to finalization.
- A valid disposition with exactly one settled `review result` after it that is not `pass` selects `block-nonpass`; the disposition is spent and later evidence does not revive it.
- A valid disposition with two or more settled `review result` lines after it selects `block-nonpass` because the record is broken.
- With no valid disposition and no settled review result, select `dispatch` after establishing a current pass. A latest pass completes review; a card-contract objection selects `contract-route`; a first or second code objection selects `repair`; and `unverified` selects `repair` of its missing evidence without increasing the objection count.
- With no valid disposition, and the latest result objects to the code and is the third or later, select `block-nonpass` and report to the person: a disposition written in any other checkpoint authorizes nothing. Only a fresh execution-proposal approval from split starts a new boundary.
- A fresh unanchored third code objection selects `ask-disposition`; once the adjacent disposition is present, anchor the result and disposition together before selecting `apply-disposition`.

Why: clean review challenges intent, logic, and scope without implementation-history bias, and the anchored lineage makes interruption recovery deterministic.

## stage: research-checkpoint

Judgment: A research conclusion is durable only when the card contains the current synthesis,
its evidence, and the passing result at the committed checkpoint. Draft notes remain card
evidence and do not qualify.

Why: promotion must survive interruption before it can ask another owner to rewrite current
knowledge.

## stage: knowledge-marker

Judgment: `knowledge.action` is exactly `none`, `emit-arch`, or `emit-adopt`. Promote only a
reusable current conclusion with one named long-lived owner. Choose
arch for a new-project writer and adopt for a brownfield writer. Emit one owner marker now;
if the same source has another owner, re-evaluate after the first marker is consumed.

Why: independent markers preserve partial multi-owner landing without a batch or shared set,
or semantic-owner inference.

## stage: task-finalization

Judgment: `feedback.action` is exactly `none`, `compatible`, `staling`, or `design-note`.
Before the task commit, decide whether upper feedback is absent, compatible,
staling, or a confirmed design note. Staling leaves through the document hierarchy; a design
note routes its canonical writer. Otherwise record compatible replacement coordinates, add
the one final carry fact (or `none`), and commit the exact card H1. On remote pass, replace
the wait record with finalizing inside that same commit.

Why: the task commit is the durable evidence boundary; carry and feedback cannot be repaired
after closure by guessing.

## stage: integration

Judgment: Apply arch’s configured merge method and prove the task commit is on integration.
An integration blockade waits with its exact cause rather than allowing boundary passengers
to move early.

Why: shared truth must contain the code and progress evidence before status, handoff, journal,
or feedback changes can close the task.

## stage: handoff

Judgment: Refresh only the room’s exact next actionable path from structured state, unless a
fresher user preference names another path. Durable facts belong to their owners, not HANDOFF.

Why: the boundary tool requires current handoff bytes, and volatile continuity should remain
small enough to overwrite safely.

## stage: boundary

Judgment: `feedback.action` is exactly `none`, `compatible`, `staling`, or `design-note`.
Close only when the structured finish-boundary passenger set is empty, the task
commit is integrated, and no marker sourced from this card remains. Transport compatible owner
feedback to resume so its named product, arch, design, or adopt writer lands it before this
boundary resumes; work never writes that owner document. A done card plus a complete boundary
is observed completion; no completion judgment substitutes for it.

Why: one ordered boundary prevents an ownerless rename, feedback fragment, or handoff; an
owner handoff preserves the semantic-writer boundary before verify becomes the next consumer.

## role: reviewer

You are the reviewer. Not knowing the implementation process is your asset—the code must
explain itself.

Input is only the progress-excluded card, the diff limited to that card’s paths, code-style,
glossary, journal, the capability design zone and existing Binding ADR paths when present,
one design freshness/reconfirmation/baseline-missing projection, and every currently existing
exact non-capsule `Read first` path. Receive no conversation, excuses, implementation
backstory, earlier objections, or capsule body.

Judge exactly intent (the Destination by meaning), logic (uncovered edges and error paths),
and scope (Forbidden or unrequested changes). Never execute or fix code, critique undeclared
taste, override a Binding ADR with a baseline, infer a missing contract basis, or open more
files. A needed unreconfirmed hypothesis is an intent objection; a missing baseline alone is
not. Mark uncertainty as speculative.

Return exactly `pass` when passing. With objections, return four lines: `objections`; the
where/what/why list; evidence; and `speculative` or `not speculative`.
