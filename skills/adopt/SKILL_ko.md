# adopt — 기존 프로젝트 도입

먼저 규칙 정본(`../principles/SKILL.md`)를 읽는다.

목적: **브라운필드(이미 코드가 있는 프로젝트에 중간 참여)**에 Layer 0 문서
(product.md·arch.md·code-style.md·glossary.md)를 역산으로 만들어 상속시킨다.
인터뷰하지 않는다. 역산한다. 이 절차가 곧 "이해 단계"다 — split은 이것 없이 돌지 않는다.

적용 조건:

- 코드가 없으면 이 스킬이 아니라 product다.
- `devflow/project/`가 이미 완비된 프로젝트면 일이 없다 — 이어하기는 resume이고,
  대청소가 필요하면 product·arch를 재실행한다.
- 일부 문서만 있으면 있는 것을 상위 문서로 존중하고 없는 것만 역산한다.

증거 서열: **문서보다 코드가 진실이다.** 저장소의 기존 문서(README·docs·기획 문서)는
주장으로 취급해 코드와 대조한 뒤 채택한다. 커밋 이력은 보조 증거다.

## 절차 — 이 순서 그대로

1. **흐름 추적.** 진입점에서 대표 요청 하나를 끝까지 따라가며 능력 경계를 눈으로 확인한다.
2. 코드·기존 문서·커밋 이력에서 `product.md`를 **product 스킬의 산출 형식 그대로** 역산한다.
   코드가 답할 수 있는 것(정체성 문단, 한 줄 설명이 붙은 능력 목록, 경계의 MVP
   범위 — 이미 만들어진 것이 그 답이다, 화면·창구, interface)은 역산으로 채우고, 코드가 답할 수 없는 것(경계의 "안 만들 것" ·
   성공 판정 · 역산된 정체성 문단이 놓친 문제와 해결 방식)은 소유자에게 묻는다.
   전체 인터뷰는 하지 않는다 — 확인 질문 한 묶음이 틀리게 역산한 것의 교정과 이
   보완을 겸한다. 답을 받지 못한 항목은 지어내지 말고 '열린 질문'에 남긴다.
   `glossary.md`도 코드가 실제로 쓰는 용어로 시작한다 — 코드의 단어가 정본이다.
3. `arch.md`를 **arch 스킬의 산출 형식 그대로** 역산해 초안으로 제시하고 사용자 확인을
   받는다. 이후 영원히 상속. 검증 창구는 arch의 "검증 창구 결정" 절을 게이트째 그대로
   적용한다 — 정해지기 전에는 이 스킬이 끝나지 않는다. git 확인(리포가 아니면
   `git init` 제안)도 같은 절의 것이다.
4. **code-style.md도 arch 스킬의 "산출 2" 형식 그대로 역산한다.** 코드가 이미 하고
   있는 방식이 정본이다 — 형식의 기본 지향을 강요해 스타일을 두 쪽 내지 않는다.
5. **기존 완성 코드를 트리에 소급 기록하지 않는다.** `devflow/tree/`는 도입 이후의
   작업부터 시작한다 — 이미 있는 기능을 `.done.` 카드로 채우는 것은 낭비다.
   트리를 여는 것은 split이다 — 능력 폴더 이름이 역산된 능력 목록과 같은 단어가
   되게 하여, 새 작업이 제자리에 쌓이게 한다.

완료 후: "다음은 split" 한 줄 안내. frontend가 있어도 기존 화면이 사실상의 디자인
정본이다 — design(선택)은 화면 체계를 새로 세울 때만 권한다.
