# Brownfield reconstruction workflow

1. Use the current state snapshot as route authority and its current tracked-plus-untracked, non-ignored path observation as the bounded material-presence fact. Proceed only for explicit Adopt with `setup.unmanaged` and at least one maintained non-devflow source; documentation, code, or both are sufficient. Only no such material belongs to Product. A non-ignored repository-support file is enough to enter evidence inspection but is not itself proof of a product capability; fully ignored material is outside this maintained-source observation.
2. Inventory every maintained implementation, test, API, schema, configuration, document, specification, and operational source with project-relative coordinates. Inspect maintained meaningful human prose in documentation, code comments, specifications, and operational records to infer a proposed Working language under the shared policy; an explicit owner language wins, code and API identifiers or other machine tokens do not vote, and tied, materially multilingual, sparse, or absent evidence remains visible uncertainty for the owner. Preserve each knowledge unit that its readers need together and would revise for the same reason; one whole source may be one knowledge unit, while a mixed source may need several knowledge units. Related supporting sources may be grouped. Every knowledge unit or group receives one visible disposition and exact destination: an owner document or planned K path for a current landing, otherwise the evidence or reason that makes it supporting, superseded, contradicted, excluded, or unresolved. Project those coordinates, authority status, disposition, and destination into Architecture's `Existing records` section so later maintenance can recover why each retained source matters without a second ledger.
3. Classify each source as implemented/current material, binding plan, exploratory research, superseded record, or unresolved conflict. Use document-internal status and actual code, test, and operational evidence to judge authority; use path/name context, Git history when available, and last-modified time only as corroborating clues, never as sole authority. Resolve evidence-supported discrepancies autonomously with exact provenance. If competing sources still leave current product intent genuinely undecidable, ask with the conflicting coordinates and exact decision needed. Apply the planning-evidence row selected through the shared policy index before separating observations, interpretations, and owner decisions.
4. Identify capability candidates from entrypoints, top-level modules, service boundaries, and maintained domain documents. Trace one representative executable flow per code-backed candidate. When a candidate is derived only from maintained documents and no executable path exists, cite the exact documentary basis and mark the executable flow not applicable rather than inventing one.
5. Before authoring, use the capability baseline or knowledge capsule row selected through the shared policy index to open only `## Identity and expected set`, `## Document contract and zone boundary`, `### Opening budget — a hard cap`, `## Metadata and freshness`, and `## Domain knowledge capsules` from their named policy owners. From `<skill-root>/../arch/references/workflow.md`, open only the Surface and Required channel columns of the verification-channel table and the first proposal paragraph with its ADR conditions; do not import the Missing-channel action column or other Arch execution, verification-run, approval, write, or commit instructions. Reverse-derive product scope, architecture, applicable design strategy, code style, glossary, and capability design zones in those canonical forms. `Concepts:` is `none` or a JSON array of exact glossary terms; K has an exact nonempty `Source basis` and must pass the canonical capsule validator after its owner document is written; capability `Design head` is the canonical command output after the first adoption commit. Write `Brownfield: yes` only when executable implementation existed before adoption; a documentation-only project writes `no`. Preserve uncertainty instead of filling gaps with defaults.
6. Land each knowledge unit whole at its nearest owner document — Product, Architecture, Design, or a capability — or as one K beneath it, using the shared capsule contract to choose its boundary. Keep only concise always-needed direction in the owner document. Propose zero K only after showing that every maintained domain source has a complete exact landing elsewhere; create no central index.
7. Ask only irreducible missing decisions and contradictions, then assemble one complete draft covering every source disposition, Layer 0, applicable Design, capability zone, and K-node landing. Before presenting it for binding, run one bounded clean-context semantic refutation. Give that context only the full draft; knowledge unit inventory, dispositions, and exact landing targets; load-bearing current and proposed source/code coordinates; the same shared baseline and knowledge sections opened in step 5; the Surface and Required channel columns of Arch's verification-channel table; and its first proposal paragraph with ADR conditions. Exclude the producer transcript, earlier audit conclusions, the Missing-channel action column, and all other Arch execution, verification-run, approval, write, or commit instructions. A departure from those opened sections, or a supported contradiction or omission that would cause a wrong action, lose a required decision or rejected direction, assign the wrong owner document, omit a knowledge unit's landing, scatter or duplicate that knowledge unit across current targets, or omit verification means, blocks. Select revise only when the current draft and returned evidence exist and every current blocker has a concrete correction grounded in current authority. Correct the draft, then independently recheck the returned coordinates, changed targets, and directly affected inventory landing, reference, owner, and source relationships without starting another full pass; the independent context may be reused but receives no producer transcript or verdict. Record initial coverage, current causal scope, observed progress or remaining failure, and the result under Evidence verification. Continue only while every attempted root is removed or strictly narrowed without introducing or reopening a blocker; an unchanged attempted root, regression, recurrence of a closed failure, or change only in finding labels, coordinates, or total count blocks. Also block for a required owner answer or authority contradiction, or unavailable required draft, source, prior evidence, or clean context, and explain the current failure and exact input needed. A future choice falsely presented as confirmed may instead be retracted when current binding does not depend on resolving it; moving an unresolved binding fact to Questions does not make the draft clear. Clear requires preserved initial coverage, current independent verification, and no supported blocker or unanswered binding dependency. Recheck any load-bearing change from an owner answer before binding.
8. Show the proposed Working language in the complete proposal, then request one binding confirmation. A language correction supplies no approval value: incorporate it while preserving fixed tokens and exact terms, then run a fresh independent semantic refutation of the complete revised proposal before using the same write-free proposal fallback to show it again. Refusal, correction, or interruption before approval writes nothing.
9. After approval, if follow-on work was part of the request, open only `FORMATS.maintenanceRoutingPending` in `<skill-root>/../principles/spec.mjs` and append the whole request idempotently once in that canonical format; do not copy its grammar here. Write Layer 0 except `product.md` and that optional record, then write `product.md` last among the owner documents, write and validate those documents' K nodes, stage only those paths, and commit them immediately as `adopt — layer 0`. Run the canonical Design head command against that landed commit, write every capability design with that exact output, then write and validate its K nodes beside it. Stage only those capability documents and nodes and commit them as `adopt — capabilities`. Report and stop. An interruption remains unmanaged and explicit Adopt rederives only while no current `.devflow` root or indexed path exists; once current evidence exists, canonical state owns recovery. Between that write and the first commit, report the exact dirty paths for owner-directed commit or discard; no stage claims them. After the first commit and before second-boundary writes, the existing managed baseline-missing state routes through Resume to Arch without reopening Adopt. Treat any uncommitted boundary as unverified.
