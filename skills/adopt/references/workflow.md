# Brownfield reconstruction workflow

1. Use the current state snapshot as route authority and its current tracked-plus-untracked, non-ignored path observation as the bounded material-presence fact. Proceed only for explicit Adopt with `setup.unmanaged` and at least one maintained non-devflow source; documentation, code, or both are sufficient. Only no such material belongs to Product. A non-ignored repository-support file is enough to enter evidence inspection but is not itself proof of a product capability; fully ignored material is outside this maintained-source observation.
2. Inventory every maintained implementation, test, API, schema, configuration, document, specification, and operational source with project-relative coordinates. Inspect maintained meaningful human prose in documentation, code comments, specifications, and operational records to infer a proposed Working language under the shared policy; an explicit owner language wins, code and API identifiers or other machine tokens do not vote, and tied, materially multilingual, sparse, or absent evidence remains visible uncertainty for the owner. Preserve each knowledge unit that its readers need together and would revise for the same reason; one whole source may be one knowledge unit, while a mixed source may need several knowledge units. Related supporting sources may be grouped. Every knowledge unit or group receives one visible disposition and exact destination: an owner document or planned K path for a current landing; `owner-kept live input` with an Architecture `Existing records` row and only the K footers it supports; otherwise the evidence or reason that makes it supporting, superseded, contradicted, excluded, or unresolved. Keep this coordinate, authority, disposition, and destination inventory on the proposal surface through refutation and approval only. Do not project absorbed-input coordinates into final owners, K nodes, or Architecture `Existing records`.
3. Classify each source as implemented/current material, binding plan, exploratory research, superseded record, or unresolved conflict. Use document-internal status and actual code, test, and operational evidence to judge authority; use path/name context, Git history when available, and last-modified time only as corroborating clues, never as sole authority. Resolve evidence-supported discrepancies autonomously with exact provenance. If competing sources still leave current product intent genuinely undecidable, ask with the conflicting coordinates and exact decision needed. Apply the planning-evidence row selected through the shared policy index before separating observations, interpretations, and owner decisions.
4. Identify capability candidates from entrypoints, top-level modules, service boundaries, and maintained domain documents. Trace one representative executable flow per code-backed candidate. When a candidate is derived only from maintained documents and no executable path exists, cite the exact documentary basis and mark the executable flow not applicable rather than inventing one.
5. Before authoring, use the capability baseline or knowledge capsule row selected through the shared policy index to open only `## Identity and expected set`, `## Document contract and zone boundary`, `### Opening budget — a hard cap`, `## Metadata and freshness`, and `## Domain knowledge capsules` from their named policy owners. From `<skill-root>/../arch/references/workflow.md`, open only the Surface and Required channel columns of the verification-channel table and the first proposal paragraph with its ADR conditions; do not import the Missing-channel action column or other Arch execution, verification-run, approval, write, or commit instructions. Screen every ADR-qualified decision and every decision with missing ground into the proposal as its current direction, ground, dropped alternatives, and exact owner landing. Adopt creates no ADR artifact: current direction, ground, and dropped alternatives land self-contained in Architecture or capability Intent, on-demand K holds only additional depth, `Binding ADRs` names only exact existing decision paths, and Arch remains the formal ADR writer. Reverse-derive product scope, architecture, applicable design strategy, code style, glossary, and capability design zones in those canonical forms. `Concepts:` is `none` or a JSON array of exact glossary terms. K is self-contained current knowledge and omits `Source basis` for absorbed migration inputs; only an owner-designated live input or managed card evidence supplies a nonempty exact footer, and any supplied footer must pass the canonical validator. Capability drafts use `Design head: none` until the first adoption commit supplies the canonical output. Write `Brownfield: yes` only when executable implementation existed before adoption; a documentation-only project writes `no`. Preserve uncertainty instead of filling gaps with defaults.
6. Land each knowledge unit whole at its nearest owner document — Product, Architecture, Design, or a capability — or as one K beneath it, using the shared capsule contract to choose its boundary. Keep only concise always-needed direction in the owner document. Preserve purpose, domain meaning, constraints, decisions and rejected directions, modality, uncertainty, and canonical terminology in that owner/K surface so deleting an absorbed input does not reduce comprehension. Propose zero K only after showing that every maintained domain source has a complete exact landing elsewhere; create no central index.
7. Ask only irreducible missing decisions and contradictions, then assemble one complete draft covering every source disposition, Layer 0, applicable Design, capability zone, and K-node landing. Before presenting it for binding, open the refuter contract and dispatch that role for one bounded clean-context semantic refutation; the role declaration fixes its inputs, exclusions, and return. The role contract owns the blocking threshold and the bounded recheck; the stage judgment owns what pending, revise, clear, and blocked mean. Select revise only when the current draft and returned evidence exist and every current blocker has a concrete correction grounded in current authority; correct the draft, then dispatch the same role again. Record its returned coverage, causal scope, progress or remaining failure, and result under Evidence verification. A future choice falsely presented as confirmed may instead be retracted when current binding does not depend on resolving it; moving an unresolved binding fact to Questions does not make the draft clear. A load-bearing change from an owner answer returns to the same role before binding.
8. Show the proposed Working language in the complete proposal, then request one binding confirmation. A language correction supplies no approval value: incorporate it while preserving fixed tokens and exact terms, then run a fresh independent semantic refutation of the complete revised proposal before using the same write-free proposal fallback to show it again. Refusal, correction, or interruption before approval writes nothing.
9. After approval, the selected `maintenanceRoutingPending` FORMAT effect appends the whole follow-on request idempotently once when follow-on work exists; adoption-only requests omit it. Write the complete approved Layer 0, capability, and K set, using `Design head: none` in every capability document, write `product.md` last among Layer 0 owners, and validate every K. The selected effect creates the absent resolved-actor room under the shared contract. Stage all approved owner documents, same-owner K nodes, the optional record, and that newly created room triple, then commit them as `adopt — layer 0`; preserve and do not stage an existing room. Run the canonical Design head command, replace only each capability Design head line with that exact output, stage only those changed capability documents, and commit them as `adopt — capabilities`. Report and stop. An interruption remains unmanaged and explicit Adopt rederives only while no current `.devflow` root or indexed path exists; once current evidence exists, canonical state owns recovery. After the first commit, all approved meaning is committed and the `none` heads make the baseline stale, so Resume routes recovery to Arch without treating uncommitted bytes as input. Treat any uncommitted boundary as unverified; create no recovery state, marker, predicate, ledger, or commit-body mapping.
