# Brownfield reconstruction workflow

1. Use the current state snapshot as route authority and its current tracked-plus-untracked, non-ignored path observation as the bounded material-presence fact. Proceed only for explicit Adopt with `setup.unmanaged` and at least one maintained non-devflow source; documentation, code, or both are sufficient. Only no such material belongs to Product. A non-ignored repository-support file is enough to enter evidence inspection but is not itself proof of a product capability; fully ignored material is outside this maintained-source observation.
2. Inventory every maintained implementation, test, API, schema, configuration, document, specification, and operational source with project-relative coordinates. Related sources may be grouped, but every source receives one visible disposition: named knowledge owner, supporting evidence, superseded or contradicted evidence, reasoned non-domain exclusion, or unresolved. Project the confirmed source/group coordinates, authority status, disposition, and landing owner into Architecture's `Existing records` section so later maintenance can recover why each retained source matters without a second ledger.
3. Classify each source as implemented/current material, binding plan, exploratory research, superseded record, or unresolved conflict. Use document-internal status and actual code, test, and operational evidence to judge authority; use path/name context, Git history when available, and last-modified time only as corroborating clues, never as sole authority. Resolve evidence-supported discrepancies autonomously with exact provenance. If competing sources still leave current product intent genuinely undecidable, ask with the conflicting coordinates and exact decision needed. Apply the planning-evidence row selected through the shared policy index before separating observations, interpretations, and owner decisions.
4. Identify capability candidates from entrypoints, top-level modules, service boundaries, and maintained domain documents. Trace one representative executable flow per code-backed candidate. When a candidate is derived only from maintained documents and no executable path exists, cite the exact documentary basis and mark the executable flow not applicable rather than inventing one.
5. Before authoring, use the capability baseline or knowledge capsule row selected through the shared policy index to open only `## Identity and expected set`, `## Document contract and zone boundary`, `### Opening budget — a hard cap`, `## Metadata and freshness`, and `## Domain knowledge capsules` from their named policy owners. From `<skill-root>/../arch/references/workflow.md`, open only the Surface and Required channel columns of the verification-channel table and the first proposal paragraph with its ADR conditions; do not import the Missing-channel action column or other Arch execution, verification-run, approval, write, or commit instructions. Reverse-derive product scope, architecture, applicable design strategy, code style, glossary, and capability design zones in those canonical forms. `Concepts:` is `none` or a JSON array of exact glossary terms; K has an exact nonempty `Source basis` and must pass the canonical capsule validator after its owner document is written; capability `Design head` is the canonical command output after the first adoption commit. Write `Brownfield: yes` only when executable implementation existed before adoption; a documentation-only project writes `no`. Preserve uncertainty instead of filling gaps with defaults.
6. Keep concise always-needed domain knowledge in each capability document. Create as many same-stem owner-adjacent K nodes as deeper reusable evidence requires, with exact provenance and no central index; propose zero only after showing that every maintained domain source lands completely elsewhere.
7. Ask only irreducible missing decisions and contradictions, then assemble one complete draft covering every source disposition, Layer 0, applicable Design, capability zone, and K-node landing. Before presenting it for binding, run one bounded clean-context semantic refutation. Give that context only the full draft; inventory and dispositions; load-bearing current and proposed source/code coordinates; the selected shared capability/capsule contract; the Surface and Required channel columns of Arch's verification-channel table; and its first proposal paragraph with ADR conditions. Exclude the producer transcript, earlier audit conclusions, the Missing-channel action column, and all other Arch execution, verification-run, approval, write, or commit instructions. Accept only supported contradictions or omissions that would cause a wrong action, lose a required decision or rejected direction, assign the wrong owner, or omit verification means. Revise at most once and recheck only the returned coordinates; do not start another full pass. Record the refutation scope, findings, and result under Evidence verification. An unresolved blocking finding or unavailable clean context prevents binding.
8. Request one binding confirmation. Refusal or interruption before approval writes nothing.
9. After approval, if follow-on work was part of the request, open only `FORMATS.maintenanceRoutingPending` in `<skill-root>/../principles/spec.mjs` and append the whole request idempotently once in that canonical format; do not copy its grammar here. Write Layer 0 except `product.md` and that optional record, then write `product.md` last, stage only those paths, and commit them immediately as `adopt — layer 0`. Run the canonical Design head command against that landed commit, write every capability design with that exact output, then write every approved K node beside its owner and run the canonical capsule validator. Stage only those capability documents and capsules and commit them as `adopt — capabilities`. Report and stop. An interruption remains unmanaged and explicit Adopt rederives only while no current `.devflow` root or indexed path exists; once current evidence exists, canonical state owns recovery. Between that write and the first commit, report the exact dirty paths for owner-directed commit or discard; no stage claims them. After the first commit and before second-boundary writes, the existing managed baseline-missing state routes through Resume to Arch without reopening Adopt. Treat any uncommitted boundary as unverified.
