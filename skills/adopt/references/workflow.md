# Brownfield adoption workflow

Start at the explicit project root. Inspect executable entrypoints and top-level modules first; each proposed capability needs one traced path from an external entry to an observable outcome. A document may supply a candidate only after its filename/path connects to that code flow; retain unmatched statements as owner questions, not facts.

For every traced candidate record the entry coordinate, ordered code path, observed responsibility, outcome, and conflicting document claim. Merge candidates only when both external responsibility and code flow are the same. The architecture document's record section contains one exact path per line and names a single candidate or `shared`; it copies no document body.

Reverse-derive product, architecture, glossary, and code style from the trace and existing code. Derive current behavior and code style; ask the owner for future exclusions, success criteria, and unresolved interpretation. Report observation, interpretation, and decision preview separately. Present the complete Layer 0 and verification-channel evidence before approval; refusal or interruption writes no current document.

After the confirmed Layer 0 boundary commit, derive the expected capability design zones and baseline shapes in one `adopt — capabilities` commit. Preserve verified zones, do not backfill done cards, and route to split for a requested change, design only for a new screen system, otherwise resume.
