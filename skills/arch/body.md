# Architecture

## why: purpose

Arch turns an approved product definition into current technical Layer 0 and greenfield capability design zones. It preserves reasons and rejected alternatives, keeps uncertain optimization values visibly provisional, and leaves implementation method to later work.

## why: workflow

The ordered workflow is stateful because entry repair, research interruption, approval, capability generation, and marker consumption have different safe effects. The specification owns those branches; the workflow reference explains what a cold consumer must decide within them.

## why: schemas

Canonical output shape is template-owned. A proposal is not current truth, and a generated capability document separates design knowledge from an initially empty verified zone.

## why: knowledge-landing

A valid marker identifies its authorized owner and committed source. Arch decides whether the conclusion belongs compactly in that owner or warrants recursive K, while the selected owner update and marker consumption remain one boundary.

## why: legacy

The immutable English and Korean sources are migration provenance. Runtime behavior lives in the specification, selected references, and templates, with executable fixtures as evidence.

## guard: state-kernel-unavailable

Stop when the sibling structured state calculation cannot be obtained for the supplied project.

## guard: compatible-feedback-shape

Block unless canonical state exposes an Arch-owned marker for exactly the architecture owner or one exact capability design document, with a valid pending or satisfied landing state. Never broaden a capability target to the whole capabilities folder or infer ownership from prose.

## guard: layer0-state-unknown

Stop because the sibling state contract could not establish whether Layer 0 is current. A write boundary is unsafe until that canonical fact is available.

## guard: worktree-state-unknown

Ask the owner to establish the repository/worktree context because integration-branch judgment depends on whether one or several worktrees exist.

## guard: canonical-integrity-block

Stop on the canonical integrity route, including malformed or unauthorized knowledge markers. Do not reconstruct their meaning locally.

## guard: open-git-operation

Ask the owner how the existing merge or rebase should proceed before architecture effects begin.

## guard: product-required

A new project needs approved product intent before technical planning.

## guard: adoption-required

Existing implementation without a product definition belongs to adoption and reverse derivation.

## guard: brownfield-capability-writer

Adopt, not arch, owns brownfield capability design writing.

## guard: state-owned-elsewhere

Return unrelated canonical routes to resume so arch never steals another stage's transition.

## stage: compatible-feedback

Judgment: For a pending marker, edit only its exact owner and preserve the source provenance plus Background, Why/evidence, Conclusion, and implication; then wait for canonical replay. Delete only the byte-identical marker after state proves those values are present in that owner, and commit the exact owner diff with the journal deletion atomically before routing to Resume.

Why: A superficial owner-file diff is insufficient, and every other owner's marker remains pending.

## stage: glossary-term

Judgment: glossary.phase is definition or align-capabilities.

Why: The definition must land while its marker remains before capability discovery headers and design heads can be aligned safely.

## stage: design-marker

Judgment: Use the exact structured note or open-item payload and its named capability; make no broader architecture inference.

Why: A confirmed localized statement should refresh one design zone without reopening Layer 0.

## stage: knowledge-landing

Judgment: landing.mode is compact, recursive, partial-compact, partial-recursive, or multi-mixed. Choose compact when the conclusion stays understandable in its named owner; choose recursive only for depth or reuse, and select only owners that can be completed in this boundary.

Why: Recursive structure is optional, while every consumed marker must have a concrete owner or K write in the same commit.

## stage: repair-layer0-fields

Judgment: repair.action is ask or commit. When repairing integration configuration, write a bare Git branch name; with one worktree, write the current branch name.

Why: A missing brownfield field or missing or malformed integration field is a bounded repair, not permission to rerun architecture planning.

## stage: read-inputs

Judgment: inputs.status is needed or read.

Why: Current product language, prior technical choices, attributed decisions, and existing outputs are the minimum basis for a coherent proposal.

## stage: refresh-check

Judgment: refresh.result is compatible, product-contradiction, or capability-only.

Why: A lower technical plan cannot silently reinterpret a changed product boundary, while a pure design-zone refresh need not repeat the interview.

## stage: component-derivation

Judgment: components.status is derive, proposed, or confirmed. Prefer the smallest component set that explains every capability and state the reason for including or excluding each component.

Why: Components are derived from product outcomes before technology candidates can be compared responsibly.

## stage: candidate-research

Judgment: research.state is none, needed, active, blocked, settled, conflicted, or unavailable. Research only facts that can remove a candidate, alter a default, or change verifiability.

Why: A blocking uncertainty cannot become a provisional optimization guess, and durable research must survive interruption outside the interview.

## stage: stack-and-derived

Judgment: stack.status is propose, needs-choice, or confirmed. Present viable candidates with one recommendation and reason, then surface only decisions created by the selected stack.

Why: Derived choices do not exist before the stack, and hard-to-reverse tradeoffs deserve a genuinely distinct counter-design only when evidence distinguishes it.

## stage: code-structure

Judgment: project.shape is screen-heavy, under-twenty-files, three-plus-capabilities, or confirmed. Treat searchable names, explicit wiring, shallow folders, bounded files, and centralized boundary contracts as decision criteria.

Why: The project structure should remain legible to later AI sessions while matching actual scale.

## stage: verify-channel

Judgment: verification.state is select, probe, confirmed, or unavailable. A confirmed channel has clean-context execution evidence from the exact command that will be recorded; a frontend also has a rendered-value read and a real interaction.

Why: Installation, help output, attachment, or success in the planning context does not prove that the independent verifier can drive the channel.

## stage: proposal

Judgment: proposal.state is draft, interrupted, or ready. A ready proposal includes grounds, discarded alternatives, provisional values, verification evidence, and the complete ADR review.

Why: Interruption cannot promote a partial report into current architecture.

## stage: approval

Judgment: approval.action is ask, approve, or refuse; request.kind is initial, refresh, capability-only, or none.

Why: Reporting precedes explicit approval. Refusal writes nothing, while approval makes the complete Layer 0 pair current at the appropriate boundary.

## stage: capability-capacity

Judgment: capacity.state is enough or warned.

Why: A context warning ends the run at the confirmed Layer 0 boundary so a fresh resume can generate the full expected set without partial output.

## stage: capability-design

Judgment: capability.action is ask or approve; route.after is design, split, or resume. Confirm the full expected design batch, preserve existing verified zones, and choose the next stage from the confirmed frontend need and owner preference.

Why: Capability documents are arch's final greenfield output and must exist before the first tree opening.

## role: channel-verifier

Run in a clean context with only the proposed channel, its exact command, and the smallest representative target. Return the command verbatim, exit code, clean-context identity, and observed probes; do not modify project state.
