# product — 서비스 기획

먼저 규칙 정본(`../principles/SKILL.md`)를 읽는다. `devflow/journal.md`와
`devflow/project/product.md`·`devflow/project/glossary.md`가 있으면 각각 통독한다. 재실행 뒤
다음 단계를 판정할 때만 기존 `devflow/project/arch.md`를 읽는다.

`product 재실행 대기` 줄이 있으면 timestamp 오름차순, 같으면 journal 줄 순서로 각
`서술-json`을 JSON 문자열로 복원해 이번 인터뷰에서 반증된 원문으로 제시한다. 그 접두로
시작하지만 정확한 형식이 아니거나 JSON 문자열로 복원되지 않는 줄은 정합성 이상으로
보고한다. 그 줄을 근거로 추측하거나 지우지 않으며, 사용자가 원문을 다시 확인하기 전에는
재실행을 시작하지 않는다. 교정은 규칙 정본의 정합성 점검 12번 복구를 따른다.

목적: 사용자와의 인터뷰로 서비스 기획을 완성해 `devflow/project/product.md`를 만든다.
이 단계는 **서비스** 기획이다 — 개발 얘기(스택·DB·프레임워크·아키텍처)는 꺼내지도, 받아주지도 않는다.
사용자가 개발 얘기를 시작하면 "그건 arch에서"라고 한 줄로 미루고 돌아온다.

## 판단할 것 여섯 가지 (= product.md의 목차)

| 판단 | 질문 |
|---|---|
| 문제 | 누가, 무엇 때문에, 얼마나 불편한가 |
| 해결 방식 | 왜 이 방식인가. 버린 방식은 무엇인가 |
| 능력 구성 | 이 문제를 풀려면 어떤 덩어리(능력)가 필요한가 |
| 경계 | MVP는 어디까지. **안 만들 것**은 무엇인가 |
| 성공 판정 | 무엇이 되면 성공인가 — 반드시 검증 가능한 서술로 |
| 화면·창구 | 사용자가 어디로 접근하나 |

**능력 구성이 심장이다.** 여기서 정한 능력 이름이 이후 아키텍처의 모듈 이름,
작업 트리의 폴더 이름이 되어 끝까지 같은 단어로 따라간다.

## 인터뷰 규칙

- **질문은 반드시 묶음으로.** 단건 왕복 금지. 한 묶음은 축이 하나(대상·가치 / 경계 / 미결), 3~5개.
- **모든 질문에 내 기본값(추천안)을 붙인다.** "답 없는 항목은 기본값으로 진행합니다"를 명시.
- 라운드는 범위에 비례해 능동적으로:
  - 능력 1~3개 → 1~2라운드. 얕게. 과한 질문 자체가 낭비다
  - 능력 4~7개 → 3라운드. 능력별로 파고든다
  - 능력 8개 이상 → 멈추고 "한 프로젝트가 아니다"라고 말한 뒤 분할을 제안한다
- 능력마다 딱 하나는 반드시 묻는다: **"이 능력을 MVP에서 빼도 성공 판정을 모두 충족할 수 있는가?"** 예 → MVP 제외 후보.

## 산출 — devflow/project/product.md

```markdown
# <서비스 이름>

<정체성 문단 — 아래 형식 그대로. 모든 작업 카드에 복사될 문단이다>
이 서비스는 <누구>가 <무엇> 때문에 겪는 <문제>를, <방식>으로 해결한다.
성공하면 <무엇>이 가능해진다.

## 문제
## 해결 방식        <!-- 버린 방식 각 1줄 포함 -->
## 능력             <!-- ① ② ③ 번호 + 이름 + 한 줄 설명. 이 이름이 끝까지 간다 -->
## 경계             <!-- MVP 범위 / 안 만들 것 (명시) -->
## 성공 판정        <!-- 검증 가능한 수용 기준 3~7개 -->
## 화면·창구        <!-- 화면 또는 인터페이스 목록 -->
## 열린 질문

interface: web | desktop | cli | server-only | tui | mixed
```

같이 만든다: `devflow/project/glossary.md` — 인터뷰 중 확정된 프로젝트 용어를 `용어: 정의` 한 줄씩.

확정된 product.md가 있고 glossary.md만 없어서 재진입했다면 인터뷰와 product.md 수정을
다시 하지 않는다. product.md에서 뜻이 확정된 용어를 옮기고, 정의가 없는 용어만 질문 한
묶음으로 확인해 glossary.md만 만든다.

능력 목록은 append-only다 — 은퇴 행은 자리를 유지하고, 행은 삭제·재배열하지 않으며, 추가는
목록 끝에 붙인다. 아직 디스크에 번호가 없는 능력의 번호를 이 위치에서 유도한다 (규칙 정본
상태 표기).

유지보수 중 능력이 은퇴하면 목록에서 지우지 않는다 — `④ ~~이름~~ — 은퇴(날짜, 근거 포인터)`
1줄로 남긴다 (번호는 불변 식별자다). 트리에 해당 열린 폴더가 있으면 `.stale`, 아직 안 연
대기 파일이 있으면 `.stale.md`로 바꾼다. `브라운필드: 아니오`에서 은퇴한 능력에 트리 표현이
없으면 같은 은퇴 커밋에서 그 능력의 `.stale.md` 대기 파일을 만든다. 브라운필드라서 트리
표현이 없으면 새 표현을 만들지 않는다 (규칙 정본 상태 표기).

## 게이트

- 성공 판정이 검증 불가능한 서술이면 통과 못 한다. 되묻는다.
- 사용자가 product.md 또는 함께 만든 glossary.md를 확인한 즉시 규칙 정본의 Layer 0 커밋으로
  착지시킨다. 단, `product 재실행 대기` 줄을 근거로 한 재실행은 아래 구속 결정 커밋을 쓴다.
- journal의 `product 재실행 대기` 줄을 근거로 재실행했다면, 정체성 문단·능력·경계·성공
  판정을 사용자가 확인한 뒤 규칙 정본의 발견→갱신 표에서 이번 변경과 일치하는 행의 동작을
  전부 수행한다. product.md 변경·그 행이 요구하는 상태 rename과 마커·이번 실행이 다룬 대기
  줄 삭제는 구속 결정 커밋 하나에 둔다. 커밋 전에 중단되면 대기 줄을 지우지 않는다. 이번
  실행에서 다루지 않은 대기 줄은 남긴다.
- 최초 작성 완료 후에는 "다음은 arch" 한 줄 안내. 재실행이면 확인된 변경이 기존 arch의
  구성요소·스택·코드 구조·데이터·검증 창구의 현재 서술과 모순되는지 대조한다. 하나라도
  모순되면 "다음은 arch"라고 안내한다. 모순이 없고 트리가 있으면 "다음은 resume", 트리가
  없으면 "다음은 split"이라고 안내한다.
