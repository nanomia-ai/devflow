# resume — 재개

먼저 규칙 정본(`../principles/SKILL.md`)·상태 판정 정본
(`../principles/state-predicates.md`)·검증 판정 정본
(`../principles/verification-predicates.md`)·능력 지식 기준선 판정 정본
(`../principles/baseline-predicates.md`)을 읽는다.

목적: 새 세션이 트리가 있으면 아래의 유계 읽기로 상태를 복원하고, 없으면 Layer 0 문서에서
다음 단계를 판정해 이어간다.

## 도메인 진입 질문

사용자 요청이 상태 재개가 아니라 능력·도메인을 설명하거나 그 안에 들어가기 위한 것이면 정상
라우팅보다 이 절을 먼저 실행한다.

1. product.md·arch.md·glossary.md 중 하나라도 없거나 arch.md에 `Brownfield` 필드가 없으면 없는
   정확 경로나 필드와 `도메인 지식 미초기화`만 보고하고 능력 본문을 열지 않는다. 사용자가 초기화를 요청하면 이 절을 끝내고 정상 resume
   라우팅을 쓴다. 세 파일이 있으면 product.md의 정체성 문단·능력 목록과
   `devflow/project/capabilities/`의 파일 이름·형태 투영을 읽는다. 대상은 규칙 정본의 정본
   인식으로 해결하고, 고른 단위의 번호가 같은 번호의 능력 문서를 지목한다. 해결 집합이 비면
   골조와 비은퇴 능력의 번호·이름만, 둘 이상이면 해결된 후보만 제시해 묻고 답을 받기 전에는
   본문을 열지 않는다.
   골조를 포함해 고른 번호의 파일이 없으면 기대 경로와 `브라운필드: 예`는 adopt, `아니오`는 arch의
   복구 경로만 보고하고 설명을 발명하지 않는다. 사용자가 기대 집합 전부를 명시적으로 요청했을
   때만 골조와 모든 비은퇴 능력 문서를 대상으로 삼는다. 일반적인 도메인 질문은 전부 요청이
   아니다. 같은 번호의 유일한 파일이 정본의 정확한 `legacy v0.10`이면 본문을 열지 않고 그 경로와
   arch·adopt 기계 이관 경로만 보고한다. 본문을 열기 전에 같은 번호 파일이 정확히 하나이고 고정 경계·절·메타데이터 형태가
   유효해야 한다. 단일 요청의 중복·형태 이상은 유계 형태 정보와 복구 경로만 보고하고 끝낸다.
   중복은 사용자가 번호·경로 이상을 해소한다. 경계 0개·2개 이상은 정본의 복구 절차, 경계 하나의
   설계 형태는 arch·adopt, 검증 형태만의 이상은 다음 능력 폐쇄의 verify로 라우팅한다.
   전부 요청에서는 유효한 파일만 열고 이상인 번호를 같은 방식으로 보고한 뒤 나머지를 계속한다.
2. 선택한 파일의 설계·검증 구역과 구속 ADR 절이 지목한 정확 경로를 읽고, 기준선 판정 정본의
   Design head·Scope head·Covered cards 비교를 실행한다. 가설을 현재 사실로 바꾸어 말하지 않는다.
   구속 ADR 경로가 없으면 정확 경로를 보고하고 설계 구역을 가설로 두며 대체 경로를 찾지 않는다.
3. 경로 · 목적과 경계 · 개념과 불변식 · 검증된 현재 행위와 진입점 · 소비 계약과 함정 · 두
   구역의 신선도와 기준선 뒤 완료 카드 집합의 대칭 차이를 이 순서로 답한다. 근거가 `None.`이면 그대로 말한다.

이 답은 파일이나 상태를 바꾸지 않고 정상 재개의 승인 질문도 하지 않는다. 사용자가 이어서
구현을 요청하면 정상 절차로 돌아가 상태 보고 승인을 받은 뒤 work이 같은 번호 문서를 자동으로
읽는다.

## 경량 진입

현재 대화의 요청이 — 항목이 여럿이면 모든 항목이 — 규칙 정본의 경량 변경 세 질문을
통과하면 아래 절차(상태 복원)를 돌지 않는다 — 이 경로는 기존 기록을 소비하지도 공유 상태를 바꾸지도 않으므로 복원이 지킬 것이
없다. 정본의 열린 Git 작업 관문만 적용하고 정본의 경량 변경 절차를 따른 뒤 끝낸다. 세 질문을
통과하지 못하는 항목이 하나라도 있거나 진행 중 판정이 뒤집히면 정상 절차로 돌아온다(요청
기록 행이 받는다).

## 절차 — 트리가 있을 때, 이 순서 그대로

```
1. product.md의 정체성 문단·능력 목록과 arch.md의 브라운필드·integration 필드.
   `devflow/project/capabilities/` 바로 아래 파일 이름과 기준선 판정 정본의 형태 투영까지
   (기계 질의 결과만 — 본문은 읽지 않는다)
2. 통합 tip의 devflow/tree/ 목록. `.done` 깊이 1 폴더는 규칙 정본의 닫힌 폴더 투영을
   쓴다                                     ← 어디까지 왔는지 (.done. / .wip. / 대기)
3. 내 점유는 전부 경로와 상태를 읽고, 통독은 이번 호출이 이어갈 하나만 — 정본 후보 순서의
   첫 점유다. 사용자의 지목이나 일치한 행이 점유가 아닌 작업을 잇는다면 이번 호출이 잇는
   점유는 없다 — 그때는 통독과 그 점유에 대한 미커밋 대조·워크트리 질문을 건너뛴다. 내 점유가 둘 이상인데 이번 대화가 카드도 깊이 1 단위도 지목하지 않았으면,
   첫 점유를 추측해 잇지 않는다 — 다른 터미널이 지금 그 카드를 돌리는 중일 수 있다. 점유
   목록(경로)을 보여 주고 어느 것을 이어갈지 묻는다. 남의 점유는 경로와 점유자만. 모든
   대기 카드에서는
   `의존`·`승인`·`검토` 필드만 읽는다. `git worktree list`가 워크트리를 둘 이상 보고하고
   이번 호출이 이어갈 그 점유 카드에 대해 이 폴더에 미커밋 변경도, 제목의 토큰 하나가 그
   카드 번호와 정확히 같은 통합 밖 커밋도
   없으면, 어느 폴더가 그 카드를 돌리는지 추측하지 않는다 — 그 목록의 경로와 브랜치를 보여
   주고 여기서 이어갈지 그 폴더에서 열지 묻는다
4. **유계 verify 투영** — 모든 verify.md를 모델 입력으로 열지 않는 기계 질의를 실행한다. 질의는 파일마다 네 revision·
   `판정`, 절별 최대 출처 id, 출처 id 없는 항목의 존재 여부, `라우팅 준비`·`라우팅: 대기`·
   `사용자 결정 대기`·사건 `라우팅`·사건 `대기` 상태인 항목의 경로·상태·출처 id·사건 key,
   검증 판정 정본에서 지금 발동한 유한한 사건 key마다 기존 기록 존재 여부만 출력한다. 완료된
   설명·소견과 지금 발동하지 않은 사건 key는 출력하지 않는다. 그 결과가 고른 활성 항목 또는
   출처 id 없는 항목 하나만 끝까지 읽는다. 상태표가 정확한 파일과 상태를 골라 verify를 부르기
   전에는 `시나리오`·`실행`·`회귀`·`표준`·`잠정값`·`journal 정리`를 읽지 않는다
5. 내 방의 HANDOFF.md ← 다음 한 걸음
6. devflow/journal.md 전체 (있으면 — 정리 규율로 항상 짧다) ← 작업을 가로지르는 결정들
7. git status 전체. 미커밋 변경은 이번 호출이 이어갈 점유 카드의 진행 로그 마지막 항목과만
   대조하고, 나머지 미커밋 경로는 어느 카드에도 귀속하지 않은 채 보고한다.
   대기 카드는 authority에 같은 경로가 있는지 확인하고, 상태 판정 정본의 두 트리 전체 Git
   diff는 한 번만 실행해 모든 대기 카드를 함께 판정한다. 통합 tip을 authority로 쓴다
```

**HANDOFF는 신선도를 확인한 뒤에 믿는다.** 날짜를 최신 작업 커밋(`NN.N` 형식, wip 포함.
내 id 접두 커밋 또는 내 점유 카드 경로를 건드린 커밋)과 대조한다. 인계는 경계에서만 쓰이므로, 중간에 죽은 세션은 이전 경계의 파일을 남긴다 —
이미 밟은 다음 걸음을 지시하는 파일이다. HANDOFF 날짜 이후의 작업 커밋이 있으면 낡은
것으로 보고하고, 트리와 내 점유 카드가 결정한다. 헤더가
`# HANDOFF · YYYY-MM-DDTHH:MM:SSZ` 형식이 아니어도 낡은 것으로 취급한다.
**HANDOFF와 트리가 충돌하면 트리가 이긴다.** 사람이 결정해야 하는 열린 journal 항목과, 구형
HANDOFF에 남은 `Open decisions` 절의 내용은 보고에 포함한다.

## 보고 후 승인

읽은 것을 **한 문단**으로 보고한다:

```
"<서비스>는 지금 <능력>까지 완료됐고, <작업>이 진행 중이었습니다.
진행 로그상 <마지막 지점>까지 됐고, 능력 문서는 <비은퇴 파일 이름 목록|없음>입니다.
다음은 <한 걸음>이고 <요청하신 것|지난 인계|정본 순서>으로 골랐습니다.
같이 열려 있는 것: <같은 행에 후보가 있는 다른 단위 목록|없음>, 귀속되지 않은 미커밋 경로:
<그 경로들|없음>, 아직 통합에 안 올라간 것: <경로 N건|없음>. 진행할까요?"
```

`아직 통합에 안 올라간 것`은 통합 tip이 현재 브랜치의 조상이면 `없음`이고, 아니면 통합 tip에
없는 커밋이 바꾼 `devflow/tree/` 아래 작업 카드 경로에 `devflow/journal.md` 변경을 더한
수다 — 봉쇄 중 덧붙인 journal 줄도 이 수가 비춘다. 규칙 정본이 통합에 게시할 수
없다고 판정한 세션에서는 이 수가 계속 늘어난다 — 그것이 흩어진 상태로 일하고 있다는 신호다.

고른 사유는 정본 후보 순서에서 그대로 나온다 — 사용자가 지목한 카드나 세션 지목 단위에서
나왔으면 `요청하신 것`, 승계 단위에서 나왔으면 `지난 인계`, 그 밖에는 `정본 순서`다. 세션 지목
단위에 후보가 없으면 그 사실을 그 절에 적는다. 일치한 행이 work이면 보고하는 걸음은 work의
선택이 잡을 그 카드다 — work의 전제조건 2가 원격 증거 전이를 먼저 고르고, 남는 것이 없을 때만
내 점유와 준비된 대기 카드 전체에 대한 정본 후보 순서가 고른다 — 이므로 보고와 단계가 서로
다른 카드를 말할 수 없다. 원격 증거 전이가 골라졌으면 그 카드 경로와 그 분기가 지시하는 다음
행동을 그대로 적는다.
대화가 깊이 1 단위를 지목하지 않았고 일치한 행에 후보를 가진 단위가 둘 이상이면, 하나를
제안하는 대신 어느 단위를 이어갈지 묻는다. 후보를 가진 단위가 하나뿐이면 물을 것이 없으므로
그대로 제안한다.

은퇴 능력의 문서는 목록에서 빼고, 다음 단계가 능력이나 골조를 지목하면 그 번호 문서의 정확한
경로도 적는다. 형태 투영의 이상은 해당 경로와 구역을 한 줄로 덧붙인다.

승인받으면 보고서가 지목한 단계로 이어간다. 승인 전에 코드를 고치지 않는다.

다음 단계 판정은 아래 표를 위에서 아래로 대조해 처음 맞는 행으로 한다. 표의 journal·verify
행은 절차가 읽어 둔 그 읽기(절차 6의 journal, 절차 4의 투영)로 판정한다 — 봉쇄 중 로컬로
덧붙인 줄도 그래서 보인다:

| 디스크 상태 | 다음 단계 |
|---|---|
| `git status`가 열린 rebase 또는 merge를 보고함 | resume — 정상 라우팅을 멈추고 규칙 정본의 열린 Git 작업 관문으로 사용자 결정을 받음 |
| HEAD의 어느 verify.md든 유효한 `라우팅 준비` 객체가 있음 | verify — payload를 대조·적용하고 준비 객체를 다시 커밋하지 않은 채 완료 상태와 지정 라우팅 커밋을 끝냄 |
| 현재 체크아웃에서 journal 또는 verify.md 중 하나 이상이 HEAD와 다르고 전체 working-tree diff가 정규 검증 상태 전환·제품 결과 작성 접두 상태·미커밋 라우팅과 그 결과물·라우팅 준비 접두 상태 중 하나임 | verify — 실행을 반복하지 않고 빠진 출력과 해당 상태 또는 라우팅 커밋을 먼저 마침 |
| 어느 verify.md에 출처 id 없는 구형 실패 이력·감리·회고 항목이 있음 | verify — 규칙 정본의 출처 id 이관 커밋을 먼저 마침 |
| 현재 체크아웃 또는 HEAD에 유효한 층 열기 마커가 있음 | split — 가장 빠른 마커와 같은 `출처-json`을 가진 마커 전부를 한 묶음으로, 그 영속 출처와 발급 번호로 중단된 계획 커밋을 마침 |
| journal에 `product 검증 실행` 줄이 있음 | verify — 기록된 실행을 다시 수행함 |
| journal에 `product 검증 결과` 줄이 있음 | verify — 저장된 결과의 실패 라우팅·사건·보고를 마침 |
| journal의 `증거 대기` 또는 `증거 마감` 줄이 내 점유 카드를 지목함 | work — 그 원격 증거 전이를 먼저 처리함. 보고에는 work의 전제조건 2가 고르는 정확한 카드 경로와 그 분기의 다음 행동을 적음 |
| 규칙 정본의 정본 점유→완료 이동이 미커밋이거나, 증거 기록이 지목하지 않는 내 점유 카드의 마지막 변경 commit 제목이 규칙 정본의 최종 작업 제목과 같음 | work — 최종 작업 커밋을 다시 만들지 않고 환류와 경계 정리만 마침 |

| journal에 정확한 `product 검증 요청` 줄이 있음 | verify — 제품층 |
| 회고 절에 `대기 · 출처 id:` 상태가 있거나, 감리 절의 `대기 · 출처 id:` 상태가 감리 실행 경계를 충족함 | verify — 실행 가능한 대기 사건 하나를 실행하고 기록 |
| 검증 판정 정본상 자동 회고가 미실행이거나, 자동 감리가 감리 실행 경계를 충족한 채 미실행이거나, journal의 사용자 요청 회고가 대상 기록을 가지거나, 사용자 요청 감리가 대상 기록과 감리 실행 경계를 모두 충족함 | verify — 새 사건 하나를 실행하고 기록 |

| `브라운필드: 아니오`인데 product.md의 은퇴하지 않은 능력이 대응하는 1층 폴더나 대기 파일을 갖지 않거나, 은퇴한 능력이 대응하는 `.stale` 폴더·`.stale.md` 대기 파일을 갖지 않음 | split — product.md와 트리의 대응을 복구 |
| `브라운필드: 아니오`인데 트리 루트에 `01-foundation/`과 `01-foundation.done/`이 모두 없음 | split — `01-foundation/`과 직계 작업 카드 하나 이상을 같은 층에서 만듦 |
| 대기 작업 카드가 `승인`·`검토` 필드를 빠뜨렸거나 `의존`이 정규 형식이 아님 | split — 구형 `의존`을 상태 판정 정본대로 정규화하고 해석 불가능한 항목은 사용자에게 물은 뒤, 빠진 필드는 `대기`와 `필수`로 추가하되 조사 카드의 검토는 `해당 없음`으로 두고 실행 제안을 제시 |

`사용자 결정 대기` 소견 행은 통과·`.done`·다른 작업을 막지 않는다. 사용자가 지금 결정하면
기록한다. 결정을 미루거나 소견 결정 없이 계속하라고 하면 원문은 그대로 두고, 같은 세션의
나머지 표 대조에서는 그 행만 일치하지 않는 것으로 취급한다.

막힌 감리 보고 행은 판정·`.done`·제품 결과 보고·다른 작업을 막지 않는다. 현재 후보를 보고한
뒤에는 디스크를 바꾸지 않고, 같은 세션의 나머지 표 대조에서 그 후보들만 사건 행과 `미실행 사건`
조건에 일치하지 않는 것으로 취급한다. 다음 세션에는 실행 경계가 달라질 수 있으므로 다시 판정한다.

앞선 행이 없고 `브라운필드: 예`이면 추적한 도입 후 작업이 끝났다고 보고하고 새 요청을
기다린다. 제품층은 사용자가 명시적으로 요청해 journal에 product 검증 활성 상태가 있을 때만
실행한다.

검증 구역 절·검증 메타데이터 형태만 다른 파일은 보고하되 별도 단계를 열지 않는다. 다음 능력
폐쇄의 verify가 그 구역을 전면 교체해 치유한다. 기준선 수리를 미루겠다는 사용자 답은 이
세션의 나머지 표 대조에서 세 기준선 행(정확한 `legacy v0.10` · 기대 파일 부재나 설계 형태
불일치 · 경계 0개나 2개 이상)만 건너뛰게 하며 실행축을 막지 않는다. split의 유지보수 매핑
게이트는 그 미룸으로 열리지 않는다 — 낡은 경계로 만든 카드는 잘못된 능력에 들어간다.

아래 네 행은 `브라운필드: 아니오`이고, 앞선 행이 없고, 골조가 없거나 `.done`이며,
product.md의 모든 비은퇴 능력에 `.done` 폴더가 있고 모든 은퇴 능력에 `.stale` 폴더 또는
`.stale.md` 대기 파일이 있으며, 대기·점유 카드와 대기 능력 파일이 하나도 없을
때만 본다. product 검증 활성 상태로 진입한 `브라운필드: 예`도 능력 표현 완전성 조건만 빼고
같은 네 행을 본다.

| 디스크 상태 | 다음 단계 |
|---|---|
| 트리 루트 verify.md가 없거나, 그 `Product revision`·`Verification revision`·`Code revision` 중 하나가 검증 판정 정본의 현재 값과 다르거나, devflow 밖 미커밋 경로가 있거나, 판정이 없음 | verify — 제품층 |
| 현재 Product revision·Verification revision·Code revision의 제품층 판정이 실패임 | verify — 기록된 실패의 라우팅을 마치거나 수정 카드가 모두 닫혔으면 제품층 재실행 |
| 현재 Product revision·Verification revision·Code revision의 제품층 판정이 미검증임 | verify — 제품층 재실행 |
| 현재 Product revision·Verification revision·Code revision의 제품층 판정이 통과이고 미실행 사건이 없음 | 완료와 남아 있는 사용자 결정 대기 소견 수를 보고하고 새 요청을 기다림 |

위의 능력 폴더 아닌 폴더 경계 정리 행은 승인 뒤 코드를 고치지 않고 폴더를 가장 깊은 곳부터 개명한 뒤
경계 정리 커밋 하나를 만들고 표를 처음부터 다시 대조한다.

## 소화 — 내 세션 밖 작업 따라잡기

소화는 깨끗한 경계에서만 한다 — 카드가 닫힌 뒤, 또는 새 점유 직전이다. 진행 중인 점유를
소화하려고 중단하지 않는다.

```
1. 통합 브랜치를 당겨온다 (arch 설정)
2. 내 방 digest.md의 마커 이후 커밋 중 소화 대상을 고른다:
   작성자가 내가 아닌 것 전부 + 내가 작성했지만 `<내 id>` 접두가 없는 것
3. 대상 커밋마다 제목과 변경 경로를 읽는다. 공유 문서, 다음 점유 후보의 능력 폴더, 또는 그
   후보 카드의 `읽을 것` 경로를 건드린 커밋만 diff를 읽는다. 제목이 정본 tweak 형식(id 접두 뒤 `tweak `로 시작)인 커밋은 형식상
   `devflow/`를 건드리지 않으므로 제목과 경로만으로 분류가 끝난다. 그 diff가 공유 문서와
   모순되면
   발견→갱신 표로 착지시킨다. 공유 문서를 고치게 되면 구속 결정이다 (규칙 정본 커밋 규율)
4. 잔량이 30건을 넘으면 개별 diff를 열지 않는다. 경로·능력별 `git log --stat` 롤업을 읽고,
   그 결과로도 3단계의 diff 대상을 정할 수 없으면 사용자에게 digest 마커로 삼을 커밋을
   확인받고 건너뛸 정확한 커밋 범위를 journal에 남긴다
5. 마커를 전진시키고 다음 경계 정리 커밋에 동승시킨다 — 점유 직전의 소화면 이번 점유
   커밋에 동승시킨다(work의 점유 커밋 규칙)
```

마커가 해석 불능이면(강제 push 등) 보고하고 사용자 확인으로 재정박한다 — 기본 후보는
내 마지막 커밋. 조용한 전량 재소화는 금지다. 마커 병합 충돌(내 두 머신)은 자손 해시를
남기고, 무관한 해시면 재정박 절차를 밟는다.

## 예외

  보고에 남의 점유 요약(누가 무엇을)을 한 줄 포함한다.
- HANDOFF가 없거나 비어 있으면: 정상이다. 트리만으로 재개한다.
- 트리 자체가 없으면: Layer 0 파일 목록과 존재하면 journal 전체를 읽고 규칙 정본의 적용 가능한
  정합성 점검을 먼저 실행한 뒤 아래 순서로 판정한다. 판정 결과를 한 문단으로 보고한 뒤 승인받는다.
  1. `devflow/project/product.md`가 없으면 "이번 작업이 저장소에 이미 있는 구현 동작을
     보존해야 합니까?"를 묻는다. 예면 adopt, 아니면 product.
  2. journal에 정확한 `product 재실행 대기` 줄이 있으면 product.
  3. product.md는 있으나 glossary.md가 없으면 같은 질문을 묻는다. 예면 adopt가 없는 Layer 0
     문서를 모두 역산하고, 아니면 product가 product.md를 바꾸지 않고 glossary.md만 만든다.
  4. product.md는 있으나 arch.md 또는 code-style.md가 없으면 같은 질문을 묻는다. 예면
     adopt가 없는 문서만 역산하고, 아니면 arch.
  5. product.md·arch.md·code-style.md·glossary.md가 모두 있으나 arch.md에 브라운필드 필드가 없으면
     "devflow 도입 전에 구현 코드가 있었습니까?"를 묻는다. 예면 adopt가 그 필드만 `예`로,
     아니면 arch가 그 필드만 `아니오`로 쓴다.
  6. Layer 0는 완성됐지만 기준선 판정 정본의 기대 파일이 정확한 `legacy v0.10`이면
     `브라운필드: 예`는 adopt, `아니오`는 arch가 기계 이관한다. 그 밖에 기대 파일이 없거나, 고정
     경계가 정확히 하나인 기대 파일의 설계 절·설계 메타데이터·현재 Design head가 계약과 다르면
     같은 분기로 능력 문서만 만들거나 갱신한다. 다른 고정 경계 이상은 위 사용자 확인 경로를 따른다.
  7. 현재 체크아웃 또는 HEAD에 유효한 층 열기 마커가 있으면 split이 timestamp가 가장 빠른 마커
     하나를 골라 영속 출처와 발급 번호로 계획 커밋을 마친다.
  8. journal에 정확한 `재분할 대기` 줄이 있으면 split.
  9. journal에 정확한 `유지보수 라우팅 대기` 줄이 있으면 split의 유지보수 라우팅.
  10. journal에 정확한 `product 검증 요청` 줄이 있으면 verify 제품층.
  11. `브라운필드: 예`이면 현재 대화에 도입 뒤 변경 요청이 있을 때만 split의 유지보수
     라우팅으로 간다. 요청이 없으면 도입 완료와 활성 작업 없음으로 보고하고 기다린다.
  12. `브라운필드: 아니오`이면 split. design은 사용자가 명시적으로 선택했을 때만 실행한다.
