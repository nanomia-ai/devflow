# resume — 재개

먼저 규칙 정본(`../principles/SKILL.md`)·상태 판정 정본
(`../principles/state-predicates.md`)·검증 판정 정본
(`../principles/verification-predicates.md`)·능력 지식 기준선 판정 정본
(`../principles/baseline-predicates.md`)을 읽는다.

목적: 새 세션이 트리가 있으면 아래의 유계 읽기로 상태를 복원하고, 없으면 Layer 0 문서에서
다음 단계를 판정해 이어간다.

## 절차 — 트리가 있을 때, 이 순서 그대로

```
1. product.md의 정체성 문단·능력 목록과 arch.md의 브라운필드·integration·`capability_baseline`
   필드. arch.md `capability_baseline`이 `yes`이면 `devflow/project/capabilities/` 바로 아래
   파일 이름 목록까지 (이름만 — 내용은 절대 읽지 않는다)
2. devflow/tree/ 전체 목록                  ← 어디까지 왔는지 (.done. / .wip. / 대기)
3. 내 점유 카드는 통독. 남의 점유는 경로와 점유자만. 모든 대기 카드에서는
   `의존`·`승인`·`검토` 필드만 읽는다
4. **유계 verify 투영** — 모든 verify.md를 모델 입력으로 열지 않는 기계 질의를 실행한다. 질의는 파일마다 네 revision·
   `판정`, 절별 최대 출처 id, 출처 id 없는 항목의 존재 여부, `라우팅 준비`·`라우팅: 대기`·
   `사용자 결정 대기`·사건 `라우팅`·사건 `대기` 상태인 항목의 경로·상태·출처 id·사건 key,
   검증 판정 정본에서 지금 발동한 유한한 사건 key마다 기존 기록 존재 여부만 출력한다. 완료된
   설명·소견과 지금 발동하지 않은 사건 key는 출력하지 않는다. 그 결과가 고른 활성 항목 또는
   출처 id 없는 항목 하나만 끝까지 읽는다. 상태표가 정확한 파일과 상태를 골라 verify를 부르기
   전에는 `시나리오`·`실행`·`회귀`·`표준`·`잠정값`·`journal 정리`를 읽지 않는다
5. devflow/HANDOFF.md (다중: 내 방의 HANDOFF.md) ← 함정·배운 것·열린 결정
6. devflow/journal.md 전체 (있으면 — 정리 규율로 항상 짧다) ← 작업을 가로지르는 결정들
7. git status 전체. 내 점유 카드가 있으면 미커밋 변경을 진행 로그 마지막 항목과 대조한다.
   대기 카드는 authority에 같은 경로가 있는지와 상태 판정 정본의 두 Git diff를 확인한다.
   다중에서는 fetch한 통합 브랜치를 authority로 쓴다
```

**HANDOFF는 신선도를 확인한 뒤에 믿는다.** 날짜를 최신 작업 커밋(`NN.N` 형식, wip 포함.
다중: 내 id 접두 커밋 또는 내 점유 카드 경로를 건드린 커밋)과 대조한다. 인계는 경계에서만 쓰이므로, 중간에 죽은 세션은 이전 경계의 파일을 남긴다 —
이미 밟은 다음 걸음을 지시하는 파일이다. HANDOFF 날짜 이후의 작업 커밋이 있으면 낡은
것으로 보고하고, 트리와 내 점유 카드가 결정한다. 헤더가
`# HANDOFF · YYYY-MM-DDTHH:MM:SSZ` 형식이 아니어도 낡은 것으로 취급한다.
**HANDOFF와 트리가 충돌하면 트리가 이긴다.** 낡은 HANDOFF라도 '열린 결정'은 보고에 포함한다.

## 보고 후 승인

읽은 것을 **한 문단**으로 보고한다:

```
"<서비스>는 지금 <능력>까지 완료됐고, <작업>이 진행 중이었습니다.
진행 로그상 <마지막 지점>까지 됐고, 다음은 <한 걸음>입니다. 진행할까요?"
```

arch.md `capability_baseline`이 `yes`이고 다음 단계가 기준선 파일이 있는 능력을 지목하면,
사람이 열어볼 수 있도록 그 파일의 정확한 경로를 보고에 적되 내용은 읽지 않는다.

승인받으면 보고서가 지목한 단계로 이어간다. 승인 전에 코드를 고치지 않는다.

다음 단계 판정은 아래 표를 위에서 아래로 대조해 처음 맞는 행으로 한다:

| 디스크 상태 | 다음 단계 |
|---|---|
| `git status`가 열린 rebase 또는 merge를 보고함 | resume — 정상 라우팅을 멈추고 규칙 정본의 열린 Git 작업 관문으로 사용자 결정을 받음 |
| HEAD의 어느 verify.md든 유효한 `라우팅 준비` 객체가 있음 | verify — payload를 대조·적용하고 준비 객체를 다시 커밋하지 않은 채 완료 상태와 지정 라우팅 커밋을 끝냄 |
| 현재 체크아웃에서 journal 또는 verify.md 중 하나 이상이 HEAD와 다르고 전체 working-tree diff가 정규 검증 상태 전환·제품 결과 작성 접두 상태·미커밋 라우팅과 그 결과물·라우팅 준비 접두 상태 중 하나임 | verify — 실행을 반복하지 않고 빠진 출력과 해당 상태 또는 라우팅 커밋을 먼저 마침 |
| 어느 verify.md에 출처 id 없는 구형 실패 이력·감리·회고 항목이 있음 | verify — 규칙 정본의 출처 id 이관 커밋을 먼저 마침 |
| 현재 체크아웃 또는 HEAD에 유효한 층 열기 마커가 있음 | split — 가장 빠른 마커의 영속 출처와 발급 번호로 중단된 계획 커밋을 마침 |
| journal에 `product 검증 실행` 줄이 있음 | verify — 기록된 실행을 다시 수행함 |
| journal에 `product 검증 결과` 줄이 있음 | verify — 저장된 결과의 실패 라우팅·사건·보고를 마침 |
| 규칙 정본의 정본 점유→완료 이동이 미커밋이거나, 증거 기록이 지목하지 않는 내 점유 카드의 마지막 변경 commit 제목이 규칙 정본의 최종 작업 제목과 같음 | work — 최종 작업 커밋을 다시 만들지 않고 환류와 경계 정리만 마침 |
| 감리·회고 절에 `라우팅 · 출처 id:` 상태가 있음 | verify — 대기 소견 라우팅을 번호순으로 한 번에 하나씩 착지시킴 |
| 감리·회고 절에 `사용자 결정 대기` 소견이 있음 | verify — 기록된 소견을 그대로 제시하고 결정을 기록 |
| 어느 verify.md든 실패 이력에 `라우팅: 대기`가 있음 | verify — verify.md 정본 경로 순서에서 첫 파일의 출처 id가 가장 작은 항목 하나를 실행 없이 라우팅 |
| journal에 정확한 `product 재실행 대기` 줄이 있음 | product |
| HEAD에 유효한 능력 닫기 마커가 있음 | verify — 중단된 능력 폐쇄를 마침 |
| journal에 정확한 `재분할 대기` 줄이 있음 | split — timestamp가 가장 빠른 마커 하나의 교체 카드 계획을 마침 |
| journal에 정확한 `유지보수 라우팅 대기` 줄이 있음 | split — timestamp가 가장 빠른 줄의 요청을 유지보수 라우팅으로 계획함 |
| arch.md에 브라운필드 필드가 없음 | "devflow 도입 전에 구현 코드가 있었습니까?"를 한 번 묻고, 예면 adopt가 필드만 추가하며 아니면 arch가 필드만 추가 |
| `devflow/project/glossary.md`가 없음 | `브라운필드: 예`면 adopt가 glossary.md만 역산하고, `아니오`면 product가 확정된 product.md를 바꾸지 않고 glossary.md만 만듦 |
| 작업 카드의 `의존`이 상태 판정 정본으로 해석되지 않거나 의존 번호가 정확히 하나의 카드를 가리키지 않음 | split — 사용자가 확인한 정규 의존값으로 교정하고 계획 커밋을 마침 |
| 내 점유 카드가 `승인`·`검토` 필드를 빠뜨렸거나 `승인: 대기`이거나 `의존`이 정규 형식이 아님 | split — 현재 diff·진행 로그가 있으면 wip 체크포인트를 만들고 카드를 해제한 뒤, 구형 의존 정규화·실행 제안 승인·계획 커밋을 마치고 다시 점유 |
| 내 점유 카드의 `의존` 중 `.done.` 아닌 카드가 있음 | split — 원 카드를 해제하고 선행 작업을 마침 |
| 내 점유 카드가 있음 | work |
| journal에 정확한 `product 검증 요청` 줄이 있음 | verify — 제품층 |
| 회고 절에 `대기 · 출처 id:` 상태가 있거나, 감리 절의 `대기 · 출처 id:` 상태가 감리 실행 경계를 충족함 | verify — 실행 가능한 대기 사건 하나를 실행하고 기록 |
| 검증 판정 정본상 자동 회고가 미실행이거나, 자동 감리가 감리 실행 경계를 충족한 채 미실행이거나, journal의 사용자 요청 회고가 대상 기록을 가지거나, 사용자 요청 감리가 대상 기록과 감리 실행 경계를 모두 충족함 | verify — 새 사건 하나를 실행하고 기록 |
| `.done`·`.stale`이 아닌 골조·능력·중간 폴더가 비어 있음 | split — 그 폴더의 한 층 열기를 완료 |
| 능력 폴더 아닌 폴더가 `.stale.` 아닌 직계 자식을 하나 이상 갖고 그 자식이 모두 `.done` 상태인데 폴더는 `.done`이 아님 | resume — 가장 깊은 해당 폴더부터 `.done`을 붙여 중단된 경계 정리를 마침 |
| `.done`·`.stale`이 아닌 1층 능력 폴더가 `.stale.` 아닌 직계 자식을 하나 이상 갖고 그 자식이 모두 `.done` 상태임 | verify — 능력층 |
| `브라운필드: 아니오`인데 product.md의 은퇴하지 않은 능력이 대응하는 1층 폴더나 대기 파일을 갖지 않거나, 은퇴한 능력이 대응하는 `.stale` 폴더·`.stale.md` 대기 파일을 갖지 않음 | split — product.md와 트리의 대응을 복구 |
| `브라운필드: 아니오`인데 트리 루트에 `01-foundation/`과 `01-foundation.done/`이 모두 없음 | split — `01-foundation/`과 직계 작업 카드 하나 이상을 같은 층에서 만듦 |
| 대기 작업 카드가 `승인`·`검토` 필드를 빠뜨렸거나 `의존`이 정규 형식이 아님 | split — 구형 `의존`을 상태 판정 정본대로 정규화하고 해석 불가능한 항목은 사용자에게 물은 뒤, 빠진 필드는 `대기`와 `필수`로 추가하되 조사 카드의 검토는 `해당 없음`으로 두고 실행 제안을 제시 |
| 대기 작업 카드의 `승인`이 `대기`가 아니며 상태 판정 정본상 유효하지 않음 | split — 정확한 무효 이유를 보고하고 `승인`을 `대기`로 되돌린 뒤 실행 제안을 다시 승인받아 계획 커밋을 완료 |
| 대기 작업 카드의 `승인`이 `대기`임 | split — 실행 제안을 제시하고 승인받음 |
| 상태 판정 정본상 준비된 대기 작업 카드가 있음 | work |
| 대기 능력 파일이 있음 | split — 그 능력의 한 층을 엶 |
| 앞선 실행 행이 없고, 감리 절의 대기 사건·대상 기록이 있는 사용자 요청 감리·발동 조건을 충족한 자동 감리 중 하나 이상이 감리 실행 경계만 충족하지 못함 | verify — 사건을 실행하거나 상태를 쓰지 않고 해당 후보를 사건 우선순위대로 나열해 각각의 정확한 막힌 경로 또는 브랜치 상태와 이유를 보고 |
| 대기 작업 카드는 있으나 유효하게 승인된 카드마다 하나 이상의 `의존`이 `.done.`이 아님 | 막은 카드 번호와 점유자를 보고하고, 의존이 닫힐 때까지 코드를 고치지 않음 |
| 다중에서 앞선 행이 없고 끝나지 않은 작업이 남의 점유뿐임 | 점유자와 카드를 보고하고 그 점유가 해제되거나 닫힐 때까지 기다림 |

`사용자 결정 대기` 소견 행은 통과·`.done`·다른 작업을 막지 않는다. 사용자가 지금 결정하면
기록한다. 결정을 미루거나 소견 결정 없이 계속하라고 하면 원문은 그대로 두고, 같은 세션의
나머지 표 대조에서는 그 행만 일치하지 않는 것으로 취급한다.

막힌 감리 보고 행은 판정·`.done`·제품 결과 보고·다른 작업을 막지 않는다. 현재 후보를 보고한
뒤에는 디스크를 바꾸지 않고, 같은 세션의 나머지 표 대조에서 그 후보들만 사건 행과 `미실행 사건`
조건에 일치하지 않는 것으로 취급한다. 다음 세션에는 실행 경계가 달라질 수 있으므로 다시 판정한다.

앞선 행이 없고 `브라운필드: 예`이면 추적한 도입 후 작업이 끝났다고 보고하고 새 요청을
기다린다. 제품층은 사용자가 명시적으로 요청해 journal에 product 검증 활성 상태가 있을 때만
실행한다.

아래 네 행은 `브라운필드: 아니오`이고, 앞선 행이 없고, 골조가 없거나 `.done`이며,
product.md의 모든 비은퇴 능력에 `.done` 폴더가 있고 모든 은퇴 능력에 `.stale` 폴더 또는
`.stale.md` 대기 파일이 있으며, 대기·점유 카드와 대기 능력 파일이 하나도 없을
때만 본다. product 검증 활성 상태로 진입한 `브라운필드: 예`도 능력 표현 완전성 조건만 빼고
같은 네 행을 본다.

| 디스크 상태 | 다음 단계 |
|---|---|
| 트리 루트 verify.md가 없거나, 그 `Product revision`·`Verification revision`·`Code revision` 중 하나가 검증 판정 정본의 현재 값과 다르거나, devflow 밖 미커밋 경로가 있거나, 판정이 없음 | verify — 제품층 |
| 현재 Product revision·Verification revision·Code revision의 제품층 판정이 실패임 | verify — 기록된 실패의 라우팅을 마치거나 수정 카드가 모두 닫혔으면 제품층 재실행 |
| 현재 Product revision·Verification revision·Code revision의 제품층 판정이 미검증임 | verify — 제품층 재실행 |
| 현재 Product revision·Verification revision·Code revision의 제품층 판정이 통과이고 미실행 사건이 없음 | 완료와 남아 있는 사용자 결정 대기 소견 수를 보고하고 새 요청을 기다림 |

위의 능력 폴더 아닌 폴더 경계 정리 행은 승인 뒤 코드를 고치지 않고 폴더를 가장 깊은 곳부터 개명한 뒤
경계 정리 커밋 하나를 만들고 표를 처음부터 다시 대조한다.

## 소화 — 다중 모드에서 남들의 작업 따라잡기

소화는 깨끗한 경계에서만 한다 — **내 점유 카드가 있으면 재개가 먼저다.** 소화는 그 카드가
닫힌 뒤, 또는 새 점유 직전에 한다.

```
1. 통합 브랜치를 당겨온다 (arch 설정)
2. 내 방 digest.md의 마커 이후 커밋 중 소화 대상을 고른다:
   작성자가 내가 아닌 것 전부 + 내가 작성했지만 `<내 id>` 접두가 없는 것
   (= 내 세션 밖 작업. 접두가 있는 커밋 — 작업·wip·claim·promote·경계 정리 — 은 이미 내 것이다)
3. 대상 커밋마다 제목과 변경 경로를 읽는다. 공유 문서, 다음 점유 후보의 능력 폴더, 또는 그
   후보 카드의 `읽을 것` 경로를 건드린 커밋만 diff를 읽는다. 그 diff가 공유 문서와 모순되면
   발견→갱신 표로 착지시킨다. 공유 문서를 고치게 되면 구속 결정이다 (규칙 정본 커밋 규율)
4. 잔량이 30건을 넘으면 개별 diff를 열지 않는다. 경로·능력별 `git log --stat` 롤업을 읽고,
   그 결과로도 3단계의 diff 대상을 정할 수 없으면 사용자에게 digest 마커로 삼을 커밋을
   확인받고 건너뛸 정확한 커밋 범위를 journal에 남긴다
5. 마커를 전진시키고 경계 정리 커밋에 동승시킨다
```

마커가 해석 불능이면(강제 push 등) 보고하고 사용자 확인으로 재정박한다 — 기본 후보는
내 마지막 커밋. 조용한 전량 재소화는 금지다. 마커 병합 충돌(내 두 머신)은 자손 해시를
남기고, 무관한 해시면 재정박 절차를 밟는다.

## 예외

- 내 점유가 없으면: 위 표에서 다음 단계를 판정한다.
  다중: 보고에 남의 점유 요약(누가 무엇을)을 한 줄 포함한다.
- HANDOFF가 없거나 비어 있으면: 정상이다. 트리만으로 재개한다.
- 트리 자체가 없으면: Layer 0 파일 목록과 존재하면 journal 전체를 읽고 규칙 정본의 적용 가능한
  정합성 점검을 먼저 실행한 뒤 아래 순서로 판정한다. 판정 결과를 한 문단으로 보고한 뒤 승인받는다.
  1. `devflow/project/product.md`가 없으면 "이번 작업이 저장소에 이미 있는 구현 동작을
     보존해야 합니까?"를 묻는다. 예면 adopt, 아니면 product.
  2. journal에 정확한 `product 재실행 대기` 줄이 있으면 product.
  3. product.md는 있으나 glossary.md가 없으면 같은 질문을 묻는다. 예면 adopt가 없는 Layer 0
     문서를 모두 역산하고, 아니면 product가 product.md를 바꾸지 않고 glossary.md만 만든다.
  4. product.md는 있으나 arch.md 또는 code-style.md가 없으면 같은 질문을 묻는다. 예면
     adopt가 없는 문서만 역산하고, 아니면 arch.
  5. product.md·arch.md·code-style.md·glossary.md가 모두 있으나 arch.md에 브라운필드 필드가 없으면
     "devflow 도입 전에 구현 코드가 있었습니까?"를 묻는다. 예면 adopt가 그 필드만 `예`로,
     아니면 arch가 그 필드만 `아니오`로 쓴다.
  6. 현재 체크아웃 또는 HEAD에 유효한 층 열기 마커가 있으면 split이 timestamp가 가장 빠른 마커
     하나를 골라 영속 출처와 발급 번호로 계획 커밋을 마친다.
  7. journal에 정확한 `재분할 대기` 줄이 있으면 split.
  8. journal에 정확한 `유지보수 라우팅 대기` 줄이 있으면 split의 유지보수 라우팅.
  9. journal에 정확한 `product 검증 요청` 줄이 있으면 verify 제품층.
  10. `브라운필드: 예`이면 현재 대화에 도입 뒤 변경 요청이 있을 때만 split의 유지보수
     라우팅으로 간다. 요청이 없으면 도입 완료와 활성 작업 없음으로 보고하고 기다린다.
  11. `브라운필드: 아니오`이면 split. design은 사용자가 명시적으로 선택했을 때만 실행한다.
