# devflow 원칙 (규칙 정본)

모든 devflow 스킬·카드·프롬프트는 이 문서를 따른다. 다른 문서와 충돌하면 이 문서가 이긴다.

## 프롬프트 7원칙

1. **1개념 1단어.** 동의어 금지. 프로젝트 고유 용어는 `devflow/project/glossary.md`에 등재하고 끝까지 같은 단어를 쓴다.
2. **목적지 > 지시.** "무엇을 하라"가 아니라 "무엇이 참이 되어야 하는가"를 적는다.
3. **방향은 풍부하게, 금지는 짧게.** 맥락·의도·왜는 넉넉히 준다. 하네스(금지)는 3줄 이내.
4. **방법을 지시하지 않는다.** 구현 방법은 실행하는 모델이 결정한다.
5. **예시 1개 > 규칙 5개.**
6. **기성 방법론 용어 회피.** spec-driven, TDD, DDD 같은 단어는 원치 않는 짐을 끌고 온다.
7. **정체성 반복 주입.** `product.md`의 정체성 문단은 모든 작업 카드에 그대로 복사한다
   (예외: 조사 카드 — split의 조사 카드 절).
   이것이 유일하게 허용된 중복이다 — 비용은 한 문단, 효과는 "길 잃지 않음".

## 신원과 방

devflow의 모드는 하나다. 혼자 쓰든 여럿이 한 저장소를 쓰든 모든 세션은 자기 방에서 일한다.

트리·journal·코어 문서(`devflow/project/*`)에 쓰기 전에, 그리고 tweak 커밋을 만들기 전에
자기 id를 해결한다 —
`git config user.name`과 `git config user.email`을 읽고 두 값 중 하나를 각
`devflow/users/*/owner.md`의 `git:` 줄과 대조하되 빈 값은 아무것과도 일치시키지 않고, 한 값이
어떤 방의 `git:` 줄과 맞아도 다른 값이 그 줄과 어긋나면 일치가 아니다.
정확히 하나가 일치하면 그것이 내 방이다.
디스크에 방이 하나도 없으면 그 신원에서 만든 id 후보를 제안하고(두 git 값이 모두 비었으면 id를
사용자에게 묻는다) 아래 합류 절차로 방을 만든다. 방이 있는데
일치가 없으면 기존 id를 전부 보여주고 새 사람인지 신원이 바뀐 것인지 묻는다 — 새 사람이면 같은
합류 절차로 방을 만들고, 신원이 바뀐 것이면 사용자가 지목한 방의 `git:` 줄을 교체하며 방을 새로
만들지 않는다. 트리·journal·코어 문서에 처음 쓰는 스킬이 이것을 한다.
신원을 해결할 수 없거나 사용자에게 물을 수 없는 세션(CI·봇)은 읽기만 한다.
id는 소문자 `[a-z0-9]{2,8}`. devflow가 쓰는 이름(project·tree·users·decisions) 금지, 재사용 금지.

방 = `devflow/users/<id>/` = owner.md + HANDOFF.md + digest.md. owner.md는 두 줄이다 —
`id: <id>`와 `git: <git user.name>, <git user.email>`. digest.md는 소화 마커 한 줄이며 값은
commit hash 또는 `none`이다. 자기 방에만 쓴다. 방은 팀 전체가 읽는다 — 그 전제로 쓴다.

devflow는 Git 작업 트리에서만 돈다 — 점유·승인 신선도·통합·모든 되돌리기가 Git 위에 있다.
작업 트리가 아닌 폴더에서 처음 도는 스킬은 `git init`을 제안하고, 사용자가 거부하면 멈춘다.
`user.name`이나 `user.email`이 없으면 정확한 `git config` 줄을 제안하고 확인받기 전까지
멈춘다 — Git 자체가 그 값 없이는 커밋을 거부한다. 모든 devflow 경로는 저장소 루트 기준이다 —
진입 시 `git rev-parse --show-toplevel`로 루트를 해석한다. cwd가 하위 폴더여도 거기에 둘째
devflow를 만들지 않는다.

**`.wip-<내 id>.`만이 내 작업이다.** 전제조건·통독·이어하기 규칙은 전부 내 점유에만
적용된다. 남의 점유 카드는 읽기 전용 참고다 — 점유하지 않은 카드에 쓰지 않는다.
멈춘 점유의 재배정 = 해제 후 재점유. 사용자의 명시적 지시로만 하며 journal 1줄을
남긴다 (점유 불가침의 공인된 예외).

**통합 브랜치.** arch.md의 `integration`은 발급·폐쇄·구속 결정이 착지하는 브랜치를 지목한다.
그 값이 현재 브랜치를 지목하거나 arch.md가 없거나 `integration` 줄이 없으면 **통합 tip은
HEAD**이고, devflow의 모든 규칙에서 통합을 fetch·통합·push·대조하라는 지시는 현재 브랜치를
읽으며 네트워크 명령을 실행하지 않는다. 다른 브랜치를 지목하면 그 브랜치의 tip을 읽되, 그
브랜치가 원격을 추적할 때만 fetch·push한다 — 로컬만 있는 통합 브랜치에는 네트워크 명령이
필요 없다. 여기의 모든 조상 판정에서 커밋은 자기 자신의 조상이다.

**공유 진실은 통합 브랜치 하나다.** 카드 상태·트리 번호·verify 출처 id·`devflow/journal.md`·
능력 문서·구속 결정은 통합 tip에서 판정한다. 내 작업 트리와 HEAD에는 아직 진행 중인 전이가
있고, 그것을 언제 읽는지는 아래 규칙들이 정확히 지목한다. 이 저장소의 모든 워크트리는 `.git`
하나를 공유하므로 한쪽의 커밋이 fetch도 원격도 없이 다른 쪽에서 보이지만, 다른 워크트리의
HEAD는 아직 통합되지 않은 증거이지 권위가 아니다 — 그 흐름의 코드와 진행 로그는 통합될 때
들어오고, 공유 상태 판정은 그것을 읽지 않는다. `git worktree list --porcelain`이 이 저장소의 워크트리 목록이고,
폴더가 사라진 워크트리는 `git worktree prune`이 지운다.

**공유 전이의 게시.** 게시는 전이를 통합에 착지시키는 행위이고 착지는 그 결과다 — 두 말이
가리키는 동작은 하나다. 게시 전에 통합 tip의 축약하지 않은 전체 commit object ID를 기억한다.
게시가 거절되면 통합을 다시 읽는다. id가 바뀌었으면 판정의 근거가 낡은 것이므로 최신 상태에서
다시 판정한다. 거절의 분류는 기계적 검사 하나로만 하고 에러 문구로는 하지 않는다 — 문구는
locale과 Git 버전에 따라 달라진다. 통합 tip이 게시하려던 브랜치의 조상이 아니면 정상 경쟁이므로
그 tip을 통합하고 재시도한다 — 세 번까지다. tip이 조상인데도 거절되면 구조적 막힘이므로 정확한
원인과 함께 보고한다. 세 번을 시도해도 tip이 계속 앞서 있으면 지속 경합으로 보고하며 실패
사다리로 세지 않는다. 같은 카드의 점유를 남이 먼저 착지시켰으면 재시도하지 않고 아래 진 점유
규칙을 따른다. 같은 번호가 서로 다른 카드로 발급됐으면 점유 경쟁이 아니다 — 아래 발급 규칙의
중간 삽입(`03.2b`)이 처리한다. 통합에 게시할 수 없으면 — 다른 워크트리가 통합을
체크아웃했거나, 권한·보호·네트워크가 막거나 — 다음은 계속한다: 최초 점유가 이미 통합에 착지한
카드의 코드 편집·진행 로그 체크포인트·최종 작업 커밋(자기 브랜치 소관이다), 경량 변경
커밋(구속 결정이 아니다), 그리고 번호를
발급하지 않고 점유를 만들지 않는 journal 덧붙임 — `유지보수 라우팅 대기`·`능력 관측`·기명
미결/결정 줄·`product 재실행 대기` — 과 그 로컬 커밋. 다음은 통합이 열릴 때까지 기다린다:
새 점유·새 트리 번호·새 verify 출처 id·카드의 `.done.` 개명과 그 경계 정리 커밋·층 열기
마커(번호를 발급한다)·새 증거 기록(record 커밋과 push가 필요하다)·`audit requested`와
`retrospective requested` 줄·검증 상태 줄·정본 journal 줄의 소비(삭제)·
Layer 0와 능력 문서 변경. 예외 하나: 이미 게시된 `증거 대기`의 통과가 봉쇄 중에 오면, 최종
작업 커밋이 그 줄을 `증거 마감`으로 교체하는 것은 소비가 아니라 그 커밋의 일부인 상태
교체이므로 자기 브랜치에서 계속한다. 처음 막힐 때 정확한 원인과 여는 방법을 알리고, 그 뒤로는 지금
기다리게 된 전이를 한
줄로 이름만 적는다. 원인은 되풀이하지 않되 이름 없이 기다리는 것은 없다 — resume 보고의 상시
한 줄이 개수를 나른다.

**한 작업 폴더에 손이 여럿일 때.** 여러 세션이 서로 다른 카드를 동시에 진행할 수 있다.
`devflow/journal.md`는 덧붙여서 고친다 — 읽어서 통째로 다시 쓰면 그사이 붙은 남의 줄이 사라진다.
HANDOFF에는 트리에서 다시 계산되는 값만 둔다 — 사람이 필요한 열린 결정은 기명 journal 줄로
착지시킨다. 그 해소는 발견→갱신 표의 미결 항목 행이 정한다. 다른 흐름이
살아 있는 동안에는 파일을 통째로 다시 쓰지 않고 바꿀 부분만 고친다 — 통째 쓰기만이 남의 변경을
조용히 덮는다. 완료 신호나 빌드가 실패했는데 이 작업 트리에 내 카드 밖의 미커밋 경로가 있으면
그 정확한 경로를 실패 사다리를 세기 전에 먼저 보고한다. 워크트리는 안전 장치가 아니라 빌드를 완전히 격리하고 싶을 때의 선택이다.

라우팅 전에 통합 브랜치를 fetch하고 그 tip에서 이 공유 상태를 읽는다 —
`devflow/project/`·`devflow/tree/`·`devflow/journal.md`와 resume의 유계
verify 투영이다. 통합 tip이 현재 브랜치 조상이
아니고 그 tip에서 journal 또는 어느 verify.md에 활성 마커, 활성 요청 또는 product 검증 줄,
사건 `대기` 또는 `라우팅` 상태가 있으면 로컬 점유보다 먼저 통합 tip을 현재 브랜치에
포함시킨다. 관련 없는
미커밋 변경은 먼저 checkpoint한다. 이것은 상태 동기화이며 점유 중에도 실행한다. 소화의 diff
읽기와 digest 마커 갱신은 계속 깨끗한 경계에서만 한다.

`git rev-parse --is-inside-work-tree`가 `true`인 Git 작업 트리에서만 아래
관문(**열린 Git 작업 관문**)을 적용한다. 그렇지 않으면 관문을 적용하지 않고 Git을 초기화하지 않는다. product·arch·design·
adopt·split·work·verify·resume은 진입 직후 정상 라우팅·실행·경로 변경 전과 통합 rebase·merge
명령 직후에 `git status`가 열린 rebase 또는 merge를 보고하는지 확인한다. 하나라도 열려 있으면
정상 라우팅을 멈추고 작업 종류·현재 branch 또는 detached HEAD·충돌 미해소 경로 전체를 보고한다.
사용자가 결정하기 전에는 경로를 바꾸거나 commit하지 말고, 충돌 경로가 없어도 기존 Git 작업을
계속할지 중단할지 묻는다. 자동 중단은 금지다. 계속하려면 의미 선택이 필요한 각 충돌의 정확한
해소안을 먼저 제시해 확인받는다. 그 확인된 충돌 해소 경로와 기존 작업을 계속하며 Git이 만드는
commit만 허용하고 별도 devflow 상태를 쓰지 않는다. 열린 작업이 사라진 뒤 `git status`를 다시
읽고 정합성 점검 1번부터 재시작한다.

방 전환 — 합류와 이탈은 각각 커밋 하나이고, 올리기는 셋으로 나뉜다:

- 합류: 방을 만들고(owner.md + 빈 HANDOFF.md + 마커 = 현재 HEAD인 digest.md) 그 세 경로만
  `<id> room — join`으로 착지시킨다. 구속 결정이다. 커밋이 아직 하나도 없는 저장소에서는
  마커가 `none`이고 첫 소화는 저장소의 첫 커밋부터 본다. 과거의 이해는 커밋 고고학이 아니라
  공유 문서에서 온다.
- 방 이전 버전에서 올라오기: 기존 소유권대로 나눈다 — arch가 arch.md에 `integration`·`merge`를 더하고, 위 신원 해결이 방을 만들고, work가 자기
  무기명 `.wip.`를 `.wip-<id>.`로 바꾸며 `devflow/HANDOFF.md`를 방으로 옮긴다. 그 개명이
  바꾼 정확한 경로를 `카드-json`으로 가진 `증거 대기`·`증거 마감` 줄은 같은 커밋에서 새 경로로
  교체한다 — timestamp·checkpoint·점검-json은 바이트 그대로 보존한다. 무기명
  `.wip.`나 루트 `devflow/HANDOFF.md`가 보이면 올리기 미완이다 — 보고하고 소유자를
  사용자에게 확인해 마저 올린다. 추측 금지.
- 이탈: 사용자가 선언한다. 남은 구성원 아무나 — 떠난 방의 HANDOFF에 구형 `Open decisions`
  절이 남아 있으면 그 내용을 기명 journal 줄로 옮기고, 그의 점유를 해제, 방 삭제, journal 1줄.
  "자기 방에만 쓴다"와 점유 불가침 둘 다의 공인된 예외다.

## 문서 계층 (계약)

정규 절차가 journal 줄을 쓰거나 append하라고 할 때 `devflow/journal.md`가 없으면 먼저 만든다.

### journal 정확한 형식

아래 형식이 예약된 journal 기록의 유일한 정본이다. 다른 스킬은 값을 채울 뿐 형식을 다시
정의하지 않는다. 예약 형식 밖에서 journal에 허용되는 줄은 교차 과제 결정과 사람이 결정할
미결 항목뿐이며, 그 줄은 정본 timestamp로 시작하고, 존재하는 방의 id와 정확히 같은 토큰 하나를 담아야
한다(부분 문자열은 아니다) — 그 두 검사가 기명(attributed)의 판정이다. `출처-json`은 아래 형식 중 하나인 locator 전체를 JSON 문자열로 담는다.
경로는 저장소 상대 경로, hash는 Git이 출력한 축약하지 않은 전체 commit object ID, 제목은 문서에
있는 제목 원문이다.
verify `출처 id`는 해당 verify.md 절에서 양의 정수이며, 새 항목은 기존 최댓값+1을 받고
재사용되지 않는다. 출처 id가 없는 구형 실패 이력·감리·회고 항목을 처음 쓰기 전에, 각 절에서
기존 id의 최댓값+1부터 파일 순서대로 빠짐없이 부여하고 원문 timestamp·내용을 보존한 뒤
`경계 정리 — verify 출처 id` 커밋으로 먼저 착지시킨다.

정본 정렬에는 두 순서만 있다. **정본 경로 순서**는 저장소 상대 `/` 경로 문자열의 UTF-8 byte
순이다. **정본 카드 번호 순서**는 `.`으로 나눈 각 구성요소의 숫자 앞부분을 정수로 비교하고, 같은 정수에서는 접미사가
없는 구성요소가 먼저이며 영문 소문자 접미사는 ASCII byte 순이다. 공통 구성요소가 모두 같으면
구성요소가 적은 번호가 먼저이고, 그래도 같으면 전체 번호의 UTF-8 byte 순으로 결정한다.

**정본 후보 순서**는 후보들 사이의 선택 순서이며, 경로나 카드 번호의 비교 순서가 아니다.

후보의 **깊이 1 단위**는 `devflow/tree/` 바로 아래 첫 경로 구성요소이거나, 아직 열지 않은
능력의 대기 파일에 적힌 번호다.

**세션 지목 단위**는 현재 대화에서 사용자가 지목한 깊이 1 단위이고, **승계 단위**는 내 방
HANDOFF의 `## Next single step` 경로 맨 앞 번호를 가진 깊이 1 단위다(그런 단위가 실존할 때만).

**정본 인식**은 현재 대화의 글을 단위 집합으로 해결한다. product.md의 완전한 능력 이름, 단위
번호와 정수로 비교되는 독립 번호 토큰, 골조를 지목하는 글이나 독립 `01`은 각각 그 깊이 1
단위로 해결된다. 정확히 하나의 카드로 해결되는 독립 작업 카드 번호는 그 카드와 그 단위로 해결된다.
해결 집합의 원소가 정확히 하나면 그것을 고른다. 후보 순서에서는 원소가 둘 이상이면 대화에서
가장 나중에 언급된 것을 고르고, 그 밖의 소비자는 둘 이상을 아무것도 고르지 않은 것으로 본다.

순서: 사용자가 지목한 카드 → 세션 지목 단위의 후보 → 승계 단위의 후보 → 나머지. 한 깊이 1
단위 안과 나머지 안에서는 정본 카드 번호 순서다.

일치한 라우팅 행을 둘 이상의 단위가 충족할 수 있고 그 행이 선택 순서를 정하지 않았으면 이
순서로 후보를 고른다. 이 순서는 어느 행이 일치하는지를 바꾸지 않고 준비되지 않은 카드를
준비시키지도 않는다. 신선도는 HANDOFF 진술을 믿을지를 지배하고, 승계 단위는 순서 열쇠일 뿐이므로 HANDOFF가
낡았어도 쓴다.

- `core:<경로>#<제목>` — 그 코어 문서의 정확한 절
- `card:<경로>@<hash>` — 그 커밋에서의 정확한 작업 카드
- `journal:<예약된 journal 줄 전체>` — 디스크에 있는 timestamp 포함 정본 줄
- `verify:<경로>#실패 이력@<출처 id>` — 그 id 필드를 가진 실패 이력 항목
- `verify:<경로>#<감리|회고>@<출처 id>/<소견 번호>` — 그 id의 사건 안에 있는 해당 채택 소견

대화의 요청은 먼저 `유지보수 라우팅 대기`에 써서 `journal:` 출처로 만든다. locator는 현재
체크아웃의 정확한 출처로 해결한다. 유효한 `라우팅 준비` 객체가 참조한 verify 출처의
`라우팅: 대기`를 교체했다면, 그 객체의 `base` commit에서 같은 출처 id와 소견 번호의 locator를
해결한다. 그 밖에 같은 미커밋 출력 전환이 출처를 바꾸거나 지워 현재 체크아웃에서 정확한 값이
사라졌으면 HEAD의 정확한 출처를 쓴다. journal 출처 줄과 층 열기 마커를 함께 지운 상태, verify
출처를 최종 결과로 바꾼 상태도 이 규칙에 포함된다.
폴더 경로 placeholder는 각 경로 구성요소에서 `.done`·`.stale` 상태 접미사를 제거한 값이다.
층 열기 마커의 `부모`만 생성 전에는 일치하는 실제 폴더가 0개여도 유효하고, 생성 뒤에는 정확히
하나여야 한다. 그 밖의 폴더 placeholder는 항상 정확히 하나의 실제 폴더와 일치해야 한다. 어느
경우든 둘 이상이면 정합성 이상이다.

```text
YYYY-MM-DDTHH:MM:SSZ 층 열기: 부모: <상태 접미사를 제거한 devflow/tree 또는 폴더 경로>; 자식: <번호+번호>; 출처-json: <정확한 영속 출처 locator를 담은 JSON 문자열>
YYYY-MM-DDTHH:MM:SSZ 재분할 대기: 폴더: <상태 접미사를 제거한 직계 부모 폴더 경로>; 무효: <번호+번호>; 출처: <devflow/project 파일 경로>#<절 제목>
YYYY-MM-DDTHH:MM:SSZ 유지보수 라우팅 대기: 요청-json: <사용자 요청 전체를 담은 JSON 문자열>
YYYY-MM-DDTHH:MM:SSZ product 재실행 대기: 서술-json: <반증된 정체성 또는 성공 판정 전체를 담은 JSON 문자열>
YYYY-MM-DDTHH:MM:SSZ product 검증 요청
YYYY-MM-DDTHH:MM:SSZ product 검증 실행: 발동: 요청 | 자동; product: <Product revision>; verification: <Verification revision>; code: <Code revision>
YYYY-MM-DDTHH:MM:SSZ product 검증 결과: 발동: 요청 | 자동; product: <Product revision>; verification: <Verification revision>; code: <Code revision>; 판정: 통과 | 실패 | 미검증
YYYY-MM-DDTHH:MM:SSZ 능력 닫기: 폴더: <상태 접미사를 제거한 devflow/tree/능력 폴더 경로>; head: <git rev-parse HEAD>; product: <Product revision>; verification: <Verification revision>; capability: <Capability revision>
YYYY-MM-DDTHH:MM:SSZ 능력 관측: 능력: <NN>; 관측-json: <관측 전체를 담은 JSON 문자열>
YYYY-MM-DDTHH:MM:SSZ 감리 요청: <능력 번호|product>
YYYY-MM-DDTHH:MM:SSZ 회고 요청: <능력 번호|product>
YYYY-MM-DDTHH:MM:SSZ 증거 대기: 카드-json: <작업 카드 전체 경로를 담은 JSON 문자열>; checkpoint: <NN.N wip: evidence-wait 커밋 hash>; 점검-json: <정확한 원격 결과 명령 또는 URL을 담은 JSON 문자열>
YYYY-MM-DDTHH:MM:SSZ 증거 마감: 카드-json: <작업 카드 전체 경로를 담은 JSON 문자열>; checkpoint: <NN.N wip: evidence-wait 커밋 hash>; 점검-json: <정확한 원격 결과 명령 또는 URL을 담은 JSON 문자열>
```

층 열기 기록은 첫 자식이나 폴더를 만들기 전에 출처 기록과 함께 `split — begin <부모>`
커밋으로 착지시킨다. 한 출처가 여러 깊이 1 단위에 걸치면 영향받는 부모마다 층 열기 마커를
하나씩 쓰되 전부 같은 `출처-json` 값을 갖고 한 begin 커밋에 함께 착지한다 — 그 locator가
묶음의 정체성이므로 별도 묶음 식별자를 만들지 않는다. 그때 메시지의 `<부모>`는 그 부모
경로들을 정본 경로 순서로 `+`로 이은 값이다. 능력 닫기 기록은 통과 verify.md 기록과 함께, 기준선 판정 정본의 검증
구역 갱신이 성공하면 폐쇄 능력의 기준선 파일까지, 폴더 rename이나 그 밖의 journal 변경 전에
`경계 정리 — begin <능력 번호>` 커밋으로 착지시킨다. 갱신 무연산은 기준선 판정 정본이
지배한다. 둘 다 그 기록을 삭제하는 다음 커밋이
착지할 때까지 유효하다. 현재 체크아웃에서 줄을 지웠어도 HEAD에 있고 삭제가 아직 커밋되지 않았으면
소비자는 그 줄을 유효한 것으로 읽고 중단된 커밋을 먼저 끝낸다. 이 시작 커밋들은 작업
커밋이 아니다.

`product ⊃ arch ⊃ design·code-style ⊃ tree(카드)`. **하위는 상위를 어길 수 없다.**
어겨야 한다면 그것은 상위의 결정이다:

1. 멈추고 진행 로그에 "왜" 2줄
2. 상위 문서를 고친다 (ADR 세 조건을 충족하면 ADR 동반 — arch 참조)
3. 교체 작업이 필요한 카드에 `.stale.` 표시. 그 카드들의 직계 부모 폴더마다 정본
   `재분할 대기` 마커 1줄을 journal.md에 쓴다. 그 카드 경로를 담은 `증거 대기`·`증거 마감`
   줄은 같은 구속 결정 커밋에서 삭제한다
4. split로 영향 구간을 재분할하고 재개

`무효`는 그 폴더의 직계 자식 중 이번 결정으로 `.stale.`이 된 작업 카드 번호를 정본 카드 번호 순서로 `+`로
이은 값이다. 상위 문서 수정·`.stale.` rename·마커를 한 구속 결정 커밋으로 먼저 착지시킨다.
능력 은퇴는 product의 `.stale` 폴더·`.stale.md` 규칙을 따르며 교체 작업과 이 마커를 만들지
않는다. 은퇴한 열린 폴더 안의 카드를 가리키는 증거 기록은 같은 은퇴 커밋에서 삭제한다.
은퇴를 확인하기 전에 **은퇴 관측 게이트**를 돈다: 이미 전문을 읽어 둔 현재 journal 안에서 그
능력 번호를 담은 `능력 관측` 줄을 열거한다 — 그 관측의 유일한
소비자는 그 능력의 다음 폐쇄인데 은퇴한 능력에는 다음 폐쇄가 없어 줄이 영구히 남는다. 0건이면
그대로 은퇴한다. 1건 이상이면 사용자가 고른 폐기 또는 골조·정확한 비은퇴 능력 번호로의 재지정을
같은 은퇴 커밋에 담고, 사용자가 미루면 은퇴도 미룬다. product가 그 줄들을 고치는 것이
journal 쓰기의 공인된 예외이며, 자동 폐기는 금지다.
split은 교체 카드의 계획 커밋이 착지할 때 마커를 지운다.

`교체 작업이 필요하다`의 판정은 하나다. 상위 문서의 바뀐 서술과 카드의 목적지·금지·완료
신호 또는 그 카드가 만든 구현을 함께 참으로 둘 수 없으면 필요하고, 모두 함께 참이면 필요하지
않다. 카드 문구와 구현을 바꾸지 않은 채 모두 참이라고 가정하지 못하면 `.stale.`로 바꾼다.

**문서 간 모순을 발견하면 그것은 우선순위 문제가 아니라 결함이다.** 어느 쪽도 조용히
채택하지 말고, 멈춰서 이 절차로 합친 뒤 진행한다. 위임받은 구현자라면 멈추고 보고만
한다 — 합치는 것은 메인 세션의 일이다.

무엇을 발견했을 때 어디를 고치는가:

| 발견한 것 | 갱신할 곳 |
|---|---|
| 기능·화면·범위가 바뀜 | product.md (+교체 작업이 필요한 영향 카드 `.stale.` + 위 재분할 대기 마커) |
| 능력의 이름이 바뀜 | 먼저 product.md의 그 능력 행 + 같은 번호의 트리 폴더 또는 대기 파일(대기 파일은 본문 줄도 새 이름을 받는다) + arch.md `기존 기록`에서 그 능력을 지목하는 줄 전부를 한 구속 결정으로 갱신한다 (+그 폴더 안의 경로를 지목하는 HANDOFF 교체). 그 뒤 arch(브라운필드는 adopt)의 능력 설계 커밋이 같은 번호의 기준선 경로와 설계 구역을 함께 갱신한다. 두 커밋 사이의 복구는 기준선 판정 정본이 소유한다. 코드 경로와 arch.md 코드 구조는 디스크에 실재하는 것을 계속 가리키고, 그 스케치 항목은 여전히 이 능력에 대응한다. 코드를 옮기는 것은 별도 카드다. 번호는 바뀌지 않고 카드는 이동하지 않는다. 그 폴더나 그 안의 경로를 지목하는 정본 journal 마커나 증거 기록이 없을 때만 첫 커밋을 착지시킨다 |
| 능력이 둘로 드러남 | product.md(기존 행을 좁히고 새 능력을 끝에 추가)와 경로 분리를 위한 arch.md 코드 구조. 기존 폴더는 번호·카드·이력을 그대로 유지하고, 새 능력은 지금 폴더도 카드도 갖지 않는다. 카드는 소급 생성하지도 이동하지도 않는다. arch(브라운필드는 adopt)가 영향받은 설계 구역과 새 능력 문서를 재도출하고 기준선 판정 정본의 등록된 소비자를 보고한다. 좁히면서 기존 능력의 이름도 바뀌면 위 개명 행을 함께 거친다 |
| 스택·모듈 경계·데이터가 안 맞음 | arch.md (+ADR 검토) |
| 상위 문서의 잠정값이 실측됨 | arch.md 잠정값 표의 그 행 — 옆에 더하지 말고 **교체**. 그 값을 전제한 ADR에는 날짜 딸린 갱신 주석 |
| 잠정값 행의 해소 카드가 '미발급'인데 트리가 그 층에 도달함 | 해소 카드를 만들고 arch.md 그 행의 '미발급'을 그 번호로 교체 |
| 성공 판정이 적힌 대로는 실행 불가 | product.md (+그 판정을 인용하는 카드들) |
| 실측이 확정된 정체성 문단·성공 판정의 내용을 반증함 (실행 불가가 아니라, 그대로 실행하면 틀린 신호를 줌) | 사용자 확인 후 — 교체할 서술이 확정돼 있으면 그 서술만 교체하고, 무엇으로 바꿀지가 다시 기획 질문이면 아래 줄로 product를 재실행한다(파급되면 arch도). 어느 경우든 교체 작업이 필요한 영향 카드는 `.stale.`과 위 재분할 대기 마커를 받는다. 재실행은 그 줄을 근거로 다음 세션이 맡아도 된다 |
| `.done.` 카드의 완료 신호가 실행 불가로 판명 | 그 카드의 신호 문구도 고친다 — 회귀는 항상 돌 수 있어야 한다 |
| 코딩 방식 결정이 새로 필요 | code-style.md 선택 절에 1줄 |
| 확인 수단이 새로 생기거나 바뀜 | arch.md verify_channel의 확인 수단 줄 |
| arch.md `기존 기록`의 파일이 이동했거나 현재 코드와 더는 맞지 않음 | 그 정확한 경로를 교체 또는 삭제 (+그 경로를 가진 대기·점유 카드의 `읽을 것`) |
| ADR에 기록된 결정이 뒤집히거나 더는 적용되지 않음 | 승계 ADR을 쓰고, 승계된 ADR에 그 승계 경로를 지목하는 날짜 딸린 갱신 주석을 더한다. arch는 옛 경로를 열거한 모든 기준선 설계 구역의 구속 ADR 경로를 같은 구속 결정에서 교체하고, 옛 경로를 직접 가진 대기·점유 카드의 `읽을 것`도 교체한다 |
| 새 용어가 필요해짐 | glossary.md 1줄 |
| 작업이 예상보다 클 뿐 | 문서 변경 없음 — 카드를 폴더로 승격 (split의 승격 절차) |
| 지금 작업 중이 아닌 다른 능력에 대해 코드에서 확인된 관측을 얻음 | 그 능력 번호를 담은 정본 `능력 관측` 줄 1줄을 journal.md에. 상대 능력의 문서를 직접 고치지 않는다 — 그 능력의 다음 폐쇄가 수확한다 |
| 공용 계약이나 골조에 대해 코드에서 확인된 것 | 되돌리기 어려운 결정을 낳았으면 ADR (arch의 세 조건). 먼저 깨질 것이면 arch.md의 `위험`. 그 밖이면 어디에 착지할지(또는 폐기할지) 사람이 결정할 기명 미결 항목 1줄 — 아래 미결 항목 행의 의미론(해소되면 다른 행으로 착지 후 삭제)이 그 줄의 소비자다. 골조의 검증 구역에는 쓰지 않는다 — 검증하지 않은 것은 검증된 상태가 아니다 |
| 작업 간 결정, 또는 사람이 결정해야 하는 열린 항목 | journal.md 1줄(기명). 열린 항목은 해소될 때 그 줄을 결정으로 바꾸거나 이 표의 다른 행으로 착지시킨 뒤 지운다 |

product 재실행에는 위 정본 `product 재실행 대기` 줄을 쓴다. 반증된 서술 전체를 JSON
문자열 하나로 직렬화해 줄바꿈·따옴표도 복원할 수 있게 한다.

위 표에 따른 갱신(잠정값 교체, 신호 문구 수정 등)은 그 자체로 공인된 수정 경로다.
1~4단계 절차는 하위가 상위를 **위반**해야 할 때만 밟는다.

발견의 출처는 카드 작업만이 아니다 — 대화에서 확정된 결정도 이 표로 즉시 착지한다.
확정된 product.md의 정체성 문단·능력·경계·성공 판정은 어느 경로로 오든 사용자 확인
후에만 고친다 — 사용자가 그 수정을 확정한 대화가 곧 확인이다. 기획은 product.md·
arch.md·design.md와 ADR의 수정으로 남긴다 — 그 밖에 기획 문서를 새로 만들지 않는다.

코어 문서(`devflow/project/*`)는 **이 절차 또는 해당 스킬의 재실행으로만** 수정한다 —
작업 중에 지나가며 고치지 않는다. 그리고 수정은 **대체가 기본**이다:
새 줄을 더했으면 낡은 줄을 지웠는지 본다. 자라기만 하는 문서는 죽은 문서다.
대상 소유 스킬은 고정이다: product.md·glossary.md는 product, arch.md·code-style.md·decisions/는
arch, design.md는 design, arch.md의 `기존 기록`은 adopt이며 adopt는 기존 arch.md에 빠진
`브라운필드` 필드만 더할 수 있고, tree와 작업 카드는 split, verify.md는 verify다.
`devflow/project/capabilities/`의 설계 구역은 arch(브라운필드는 adopt), 생성 뒤 검증 구역은
verify가 소유한다. 최초 빈 검증 골격, ADR 승계의 기계적 경로 교체, 정확한 바이트 경계, 정확한
v0.10 기계 이관과 사람의 삭제 예외는 기준선 판정 정본이 지배한다.

product·arch·design·adopt가 실행 중에 만들고 있는 문서는 사용자 확인 전까지 초안이다 —
초안의 모순은 위 절차가 아니라 그 자리의 초안 수정으로 합치고, 이미 상속된 상위
문서를 고쳐야 하면 그 수정을 같은 확인 묶음에 올린다.

devflow 밖의 기록 — 실행 환경이 세션에 주입하는 기억·작업 목록, 저장소의 devflow 아닌
문서 — 은 주장이지 정본이 아니다. 그런 기록을 찾아 읽으라는 지시가 아니다 — 이미
컨텍스트에 있는 것에만 적용된다. 확정된 devflow 문서와 어긋나면 조용히 넘기지 말고
보고한다. 확인 전에는 devflow 문서를 따르고, 확인 후 어긋난 쪽을 고친다 — devflow 문서
쪽이면 발견→갱신 표의 경로로, 밖의 기록 쪽인데 고칠 수단이 없으면 보고가 끝이다.

## 정합성 점검

트리를 여는 관문(split·resume 시작 시)에서 훑는다. 경량 진입은 트리를 열지 않으므로 그
관문이 아니다 — 디스크 이상은 다음 정식 세션의 점검이 잡는다.
이상은 **고치지 말고 보고한다** — 자동 교정이 오판하면 오염이 가속된다. 사용자 승인 후 교정.

**닫힌 폴더 투영.** `.done` 깊이 1 폴더 안에서는 경로 이름과 상태 접미사만 기계 질의로 읽고
본문을 열지 않는다 — 그 폴더의 지식은 이미 그 능력 문서에 접혀 있다. 그래서 4번은 그런 폴더
밖의 작업 카드만 판정한다(재폐쇄가 폴더의 `.done`을 먼저 떼므로 그 카드들은 그때 다시 들어온다).
1·8·9·13번은 점유·대기 카드에 대한 것이고, 그런 카드가 그 안에 있으면 3번이 투영만으로 이미
보고하므로 더 보태는 것이 없다. 예외 하나: 증거 줄이 닫힌 폴더 안 경로를 지목하면 13번이
그 줄로 판정한다 — journal을 읽는 판정이라 폴더 본문은 여전히 열지 않는다. 나머지 항목은 투영된 이름과 상태로 판정하고, 어느 항목이 그 안의 정확한 경로에서
이상을 보고할 때만 본문 하나를 연다. 이 투영은 다음 번호 산출·번호 재사용 금지·locator 해석·
`Covered cards` 비교에도 같은 이름 집합을 준다.

1. 점유 카드의 `<id>`가 어느 `devflow/users/*/owner.md` 방과도 일치하지 않는가
   (고아 점유 — 떠난 팀원이나 오타의 잔재. 무기명 `.wip.`은 6번 소관이라 여기서 세지 않는다)
2. 같은 번호가 중복되는가
3. `.done` 폴더 안에 `.done.`도 `.stale.`도 아닌 작업 카드가 있는가
4. 각 작업 카드의 `의존`이 상태 판정 정본의 정규·구형 형식 중 하나로 해석되고, 그 의존 번호마다
   정확히 하나의 카드가 실존하는가
5. HANDOFF가 가리키는 경로가, 양쪽 경로의 각 구성요소에서 상태 접미사를 제거하고 비교했을 때
   정확히 하나의 실존 경로와 일치하지 않는가
6. 무기명 `.wip.` 또는 루트 `devflow/HANDOFF.md`가 있는가 (무주 점유 또는 올리기 미완)
7. 같은 git 신원을 주장하는 owner.md가 둘 이상인가
8. 무기명 `.wip.`은 점유자가 없으므로 6번이 맡고 이 항목은 건너뛴다. 그 밖의 현재 점유 카드마다
   그 접미사를 만든 현재 점유 커밋부터 통합 tip까지, 그 카드의 같은
   번호 상태 경로를 바꾼 commit 작성자가 점유자의 owner.md git identity와 다른가. 사용자가 승인한
   재배정·이탈·계획 전환에서 그 점유를 해제하는 정규 commit은 예외다. 점유 전 commit과 이전
   점유 구간은 검사하지 않는다
9. 대기 작업 카드가 split이 정의한 `승인`·`검토` 필드를 빠뜨렸거나 허용하지 않은 값을 갖는가
10. 비어 있는데 유효한 층 열기 마커가 없는 골조·능력·중간 폴더가 있는가
11. 능력 폴더 아닌 폴더가 `.stale.` 아닌 직계 자식을 하나 이상 갖고 그 자식이 모두 `.done`
    상태인데 폴더에는 `.done`이 없는가
12. timestamp 뒤에 `층 열기:`·`재분할 대기:`·`유지보수 라우팅 대기:`·`product 재실행 대기:`·
    `product 검증 요청`·`product 검증 실행:`·`product 검증 결과:`·`능력 닫기:`·`능력 관측:`·`감리 요청:`·`회고 요청:`·`증거 대기:`·`증거 마감:` 중 하나로 시작하는
    journal 줄이 위 정본 형식과 다르거나, `-json` 값이 JSON 문자열로 해석되지 않거나, 층
    열기 `출처-json`의 decoded 값이 위 locator 형식 중 하나가 아니거나 정확히 하나의 출처로
    해결되지 않는가
13. `증거 대기`·`증거 마감` 줄의 decoded 카드 경로가 정확히 하나의 점유 카드를 가리키지
    않거나, checkpoint hash가 현재 저장소에 없거나 그 커밋의 메시지와 카드 경로가 일치하지
    않거나, 그 commit의 카드 진행 로그에서 마지막 `원격 증거 점검` 줄의 JSON 값이 journal의
    `점검-json`과 다른가. 다만 커밋된 `증거 마감`의 카드 경로가 사라지고 같은 부모에 번호·이름·
    byte가 같은 `.done.` 카드가 정확히 하나 있으면 정본 점유→완료 이동 중단이므로 work가 경계
    정리를 끝낸다. 그 밖에는 같은 미커밋 구속 결정 diff가 줄을 지우고 카드를 `.stale.`로 바꾸는
    중일 때 그 커밋을 먼저 끝낸 뒤 다시 판정한다
14. verify.md 한 절의 기존 `출처 id` 중 양수가 아닌 값이나 중복이 있거나, 감리·회고 라우팅
    항목에서 채택 소견 번호가 양수가 아니거나 중복되거나 `라우팅: 대기` 소견에 번호가 없는가.
    `라우팅 준비:` 뒤가 JSON 객체로 해석되지 않거나 아래 라우팅 쓰기 순서의 정확한 key·값
    형식, base 관계, operation 항목 형식·적용 가능성·접두 구간·범위 조건을 충족하지 않는가
15. journal에 product 검증 활성 상태 종류가 둘 이상 함께 있거나, `product 검증 실행` 또는
    `product 검증 결과` 줄이 둘 이상이거나, 결과 줄의 product·verification·code·판정이 트리
    루트 verify.md의 같은 필드와 다른가
12번·13번·14번·15번 이상은 뒤의 라우팅과 트리 쓰기를 막는다. 원본 줄·기대 형식·교체안 전체를 사용자에게
제시한다. 교체안에는 원본에서 정상 해석된 값과 디스크에서 정확히 하나로 결정되는 값만 쓰며,
나머지는 묻는다. 사용자가 교체안 전체를 확인하면 그 줄 교체만 구속 결정 커밋으로 착지시키고
정합성 점검을 처음부터 다시 실행한다. `라우팅 준비` 이상만 예외다. 확인된 교정 객체를 단독
커밋하지 않는다. 현재 체크아웃에서 교체한 뒤 이미 적용된 operations 접두 구간을 객체와 대조하고,
나머지를 적용하며, verify.md를 `result`의 완료 상태로 바꿔 지정 라우팅 커밋 하나로 끝낸다.
객체의 유실값을 사용자 확인으로도 복원하지 못하면 출력이나 rollback을 추측하지 않고 멈춘다.

## 모델 등급

**파일에 모델명을 적지 않는다.** 등급만 쓴다. 실제 모델·사고량은 split의
실행 제안에서 사용자가 그 세션에 한해 결정한다.

| 등급 | 역할 | 용도 |
|---|---|---|
| T-상 | 최상위 사고 | 판정·리뷰. 짧게만 — 길게 돌리면 비용이 정당화되지 않는다 |
| T-중 | 표준 사고 | 기본값. 기획, 분할, 모호하거나 얽힌 작업 |
| T-하 | 구현 특화 | 카드가 완전한 구현, 기계적 변환, 수집·정리 |
| 그 이하 | — | 코딩 금지 |

사고량(effort) 규칙: **판정은 상위 등급 + 낮은 사고량으로 짧게. 설계는 표준 등급 + 높은 사고량으로 깊게.**

하네스 다이얼 — 등급에 반비례한다:

- T-중 이상: 목적지 + 금지 3줄. 경로 지시 없음. 방법을 지시하면 오히려 성능이 깎인다.
- T-하: `읽을 것` 완전 열거 + 진행 순서 힌트 + 금지 확대 + 완료 신호 명령어 그대로.
- **T-하 수준의 카드를 쓸 시간이 없으면 그 작업을 T-하에게 주지 않는다.**

## 실패 사다리 (모든 재시도에 공통)

```
1차 실패 → 카드를 보강해 재투입 (같은 프롬프트 재투입 금지 — 실패는 카드 결함의 신호다)
          보강의 핵심은 지시 추가가 아니라 실패의 인과다 — 무엇이 왜 실패했고
          그 결과 무엇이 일어나는지 1~2문장을 카드에 싣는다
2차 실패 → 등급을 올리거나 메인이 직접
3차 실패 → 사람 호출. 4번째 시도는 없다
```

구현 중 같은 가설의 수정 시도 반복은 사다리로 세지 않는다 — 그것은 work의 고착 탈출이 맡는다.

## 상태 표기

**파일명의 상태 접미사가 작업 상태의 정본이고, 점유 카드의 진행 로그가 그 작업 내부 진행의
유일한 기록이다.** product·arch·design·code-style·glossary에는 작업 진행을 적지 않는다.
journal은 카드 간 결정, 사람이 결정해야 하는 열린 항목, 규칙 정본이 정확한 형식을 정한 줄만
기록할 수 있으며, 작업 진행·승인은 기록하지 않는다. verify.md는 판정·실패
라우팅·감리와 회고의 사건 상태·소견·사용자 결정을 기록할 수 있다. 이 기록들은 카드나 폴더의
상태를 직접 바꾸지 않는다. 작업 카드의 `.done.` 근거는 완료 신호와 적용되는 검토이고, 능력
폴더의 `.done` 근거는 verify의 능력층 통과 판정이다.

- 접미사 없음 = 대기 / `.wip.` = 진행 중 / `.done.` = 완료 / `.stale.` = 상위 결정 변경으로
  무효, 또는 정본 절차가 남긴 묘비(회수)
- 점유는 `.wip-<id>.`로 표기한다. 무기명 `.wip.`은 무주 점유 = 정합성 이상.
  해제는 접미사 전체를 벗겨 대기로 되돌린다(진행 로그는 카드에 남는다).
  `.done.`·`.stale.`은 무기명 그대로 — 완료의 소유는 git이 기억한다
- 한 사람이 점유를 여럿 가질 수 있다. 한 카드는 한 번에 한 세션이 다룬다 — 디스크는 터미널을 구분하지 못하므로, 같은 카드를
  두 터미널에 시키지 않는 것은 사용자 몫이다(README 지침)
- `.done.`은 **완료 신호 통과 + 카드에 적용되는 검토 통과 + 커밋 착지 이후에만**.
  이 문서에서 "검증"은 verify의 능력·제품층 전용어다
- 능력 폴더가 아닌 폴더는 `.stale.`이 아닌 직계 자식이 하나 이상이고 그 자식들이 모두
  `.done` 상태이면 `.done`을 받는다. `.stale.` 작업 카드는 역사로 남지만 활성 자식 수와
  폐쇄 판정에서 제외한다.
  **1층 능력 폴더는 능력층 검증 통과 후에만** verify가 부여한다.
  골조 폴더(01)는 능력이 아니므로 시나리오 검증 없이 같은 조건으로 닫힌다
- 트리 번호는 한 번 배정한다. 골조는 `01`이고, 능력은 루트를 처음 열 때 product.md 능력
  목록 순서대로 `02`·`03`…을 받는다.
  아직 디스크에 번호가 없는 능력의 번호는 product.md 능력 목록의 위치에서 유도한다 — 첫
  능력이 02이고 은퇴 행도 자리를 유지하며 셈에 포함된다. 폴더·대기 파일·기준선이 번호를
  보유하면 디스크가 유일한 권위다.
  트리 루트의 `.md`는 이름이 product.md의 은퇴하지 않은 능력 이름과 같고 번호가 그 능력에
  배정된 트리 번호일 때 대기 능력 파일이며 작업 카드가 아니다. 본문은 `# <번호> <능력이름>`
  한 줄이고 `승인`·
  `검토`·완료 신호를 갖지 않는다. split은 능력을 열 때 이 파일을 같은 번호·이름의 폴더로
  바꾸고 직계 작업 카드를 만든다
- 은퇴한 능력은 이미 열린 폴더면 `.stale`, 아직 안 연 대기 파일이면 `.stale.md`를 받는다.
  열린 은퇴 폴더의 내부 카드 상태는 전부 무효다.
  훅과 정합성 점검은 `.stale` 폴더 내부를 세지 않는다
- 파일명 본체와 번호는 불변 식별자. 재정렬·재사용 금지. 능력의 번호도 마찬가지로 불변이며,
  바뀌는 것은 product.md 그 행의 이름 부분·트리 폴더 또는 대기 파일·기준선 파일뿐이고 위
  발견→갱신 행을 거쳐 함께만 바뀐다. 중간 삽입은 `02.2b` 형식
- 카드가 아닌 기록 파일(`verify.md` 등)은 상태 접미사를 갖지 않으며 상태 판정에서 제외한다

## 경량 변경 (tweak)

판정 단위는 항목이다 — 여러 항목을 담은 요청은 항목마다 세 질문을 따로 판정한다. 세 질문은
저장소 산출물의 변경을 요구하는 항목에만 적용된다 — 아무것도 바꾸지 않는 항목(질문·설명·
상태 확인)은 셋 다 "아니오"로 나와도 경량 항목이 아니라 정상 절차의 몫이다: 바꿀 것이 없는
세션은 이 차선에서 만들 수정도, 실행할 확인도, 착지시킬 커밋도 찾지 못한다. 항목이
세 질문에 전부 "아니오"일 때만 경량 변경이다 — 하나라도 불확실하면 경량이 아니다:
① 사용자가 보는 동작의 전제→결과 전이가 바뀌는가. ② 설계 결정을 낳거나 기존 결정·디자인
토큰·ADR과 충돌하는가. ③ 다음 작업자가 몰라서 틀릴 수 있는 함정을 남기는가.
세 질문은 요청 자체와 이 차선이 읽는 문서에서 판정한다 — 그 밖을 뒤져 불확실성을 만들지
않는다. 다만 이 세션의 컨텍스트에 이미 보이는 충돌은 뒤진 것이 아니다 — 보이는 충돌은 ②를
"예"로 답한다. 거기서 보이는 전이 변화·충돌·함정이 없으면 "아니오"다.
게이트를 통과한 항목은 어떤 journal 줄에도 적히지 않는다 — 이 차선이 그 대화 안에서
처리하고, 유지보수 기록 줄은 게이트를 통과하지 못한 항목만 담는다. 기록된 요청 줄은 카드
계획 커밋이 한 번에 소비하므로, 통과 항목이 그 줄에 섞이면 카드도 기록도 얻지 못한 항목이
소비만 되어 중단 시 흔적 없이 사라진다.
경량 변경의 diff는 그 자체로 완전한 기록이다. 그래서 카드·journal 줄·검토 없이 진행한다.
이 차선은 devflow가 들어온 저장소를 전제한다 — 저장소 루트에 `devflow/`가 없으면 tweak하지
않는다: 도입을 결정한 적 없는 저장소에 방부터 심게 되므로, 무트리 예외의 도입 질문이 먼저다.
먼저 이 차선의 커밋이 안전하게 착지할 자리를 기계로 확인한다:

- `git symbolic-ref -q HEAD`가 비면(이름 없는 HEAD) 진행하지 않고 그 사실과 브랜치
  선택·생성 선택지를 보고한다 — 경량 커밋은 통합 경계를 타지 않으므로, 이름 없는 HEAD 위의
  커밋은 어느 브랜치에도 담기지 않고 reflog에만 남는다.
- 작업 트리의 어느 verify.md든 `라우팅 준비`를 담고 있으면 진행하지 않는다 — 이 차선이 쥔
  항목 전부를 통과로 판정하지 않고 그 항목들을 정상 경로로 넘긴다(그 전이가 먼저 끝나고,
  요청 기록 행이 그 항목들을 받는다) — 그 전이는 base 커밋 id에 고정돼 있어, 경량 커밋
  하나가 HEAD를 전진시키는 것만으로
  재개 가능하던 상태가 정합성 이상으로 바뀐다.
- 읽을 수 있는 통합 tip이 HEAD의 조상이 아니면 같은 처분이다 — 이 차선이 쥔 항목 전부를
  통과로 판정하지 않고 그 항목들을 정상 경로로 넘긴다. 읽을 수 있는 통합 tip이란 위 통합
  규칙이 네트워크 명령 없이 읽는 그 tip이다 — 원격 추적 브랜치면 마지막으로 fetch된 로컬
  ref이고, 읽을 tip이 아예 없으면 같은 처분으로 넘긴다. 낡은 checkout의 문서로 내린
  "아니오"는 통합에 이미 착지한
  결정과 충돌하는 커밋을 만든다.

확인이 통과하면 "경량으로 처리합니다 — <항목>"을 한 줄 선언하고(대화의 요청이 곧 승인),
존재하는 product.md·arch.md·design.md·code-style.md를 읽고 — 항목이 이름이나 용어에 닿을
수 있으면(사용자가 보는 문구·식별자·메시지처럼 이름이 붙는 모든 것) 존재하는 glossary.md도
함께: 용어 결정은 거기에만 살고, 인근 코드는 현재 표기를 보여줄 뿐 그것이 결정이라는 표시가
없다; 닿는지 불확실하면 읽는다(한 용어 한 줄짜리 작은 문서다) —, 수정한다. 편집 직전, 대상
경로의 미커밋 변경을 본다: 이 세션이 점유 카드 작업으로 만든 변경이면 그 카드의 wip
체크포인트로 먼저 착지시킨다. 판정이
뒤집힌 항목이 작업 트리에 남긴 이 세션의 수정은 그 요청의 카드 몫이다: 이 차선의 커밋 전에 잠시
되물리고 커밋 뒤 작업 트리에 다시 적용한다(커밋은 파일의 전체 내용을 담는다 — 같은 묶음의
형제 경량 항목이 만든 수정은 이에 해당하지 않고 이 커밋에 함께 탄다). 이 세션이
만들지 않은 변경이면 소유를 추측하지 않는다 — 그
경로와 변경을 보고하고 사용자의 처분을 따른다. Git 커밋은 경로의 최종 내용을 담지 변경분의
주인을 구분하지
못하므로, 같은 파일에 남은 다른 흐름의 변경은 경량 커밋에 그대로 동승한다. 수정 뒤, 변경
파일을 포함하는 가장
좁은 실행 확인 하나 — 그 파일들의 테스트가 있으면 그것, 없으면 린트나 빌드 — 를 실행한다.
확인이 실패하면 그 항목 안에서 고쳐 통과시키고, 실패가 드러낸 것이 세 질문을 뒤집으면 아래
전환 규칙을 따른다. 그리고
커밋 직전 대상 경로의 diff를 이 커밋이 묶는 항목들을 위해 만든 변경과 대조한다 — 그 밖의 내용이 보이면
커밋하지 않고 내 수정을 되물린 뒤 상대 흐름이 커밋하고 나서 다시 적용하며, 물러났다는
사실을 그 자리에서 말한다. 사용자가 그 변경을 산 흐름이 없는 죽은 잔여로 확인하면 사용자의
결정대로 넘겨받거나 버리고 진행한다. 물러나는 쪽이
경량으로 고정돼 있어 서로 기다리는 교착은 생기지 않는다. 그리고
`<id> tweak <단위 번호>: <무엇>` 커밋 하나로 끝낸다. `<id>`는 신원과 방 규칙으로
해결한다 — 방이 없으면 합류 전이가 방을 만들며, 그 방 생성 커밋은 이 차선의 devflow 무접촉
규칙의 공인된 예외다(요청의 산출물이 아니라 신원의 산출물이다). 방 생성은 구속 결정이므로
봉쇄 중에는 착지할 수 없다 — 방 없는 세션의 tweak는 그때 진행하지 않고 정확한 원인을
보고한다. 단위 번호는 정본 인식을 그 항목의 문장에 적용해
해석한 깊이 1 단위의 번호이고 — 대화 전체가 아니다: 두 항목이 각자 다른 단위를 지목한 대화
전체는 해석 집합이 둘이라 아무 단위도 고르지 못한다 —, 해석되지 않으면 `01`이다.
한 요청의 여러 경량 항목은 깊이 1 단위마다 커밋 하나로 묶는다. 그 밖에는 `devflow/` 경로를
건드리지 않는다 — 건드릴 필요가 생기는 순간 그 항목은 경량이 아니다. 이 차선은 라우팅이
아니다 — 라우팅 전 통합 읽기와 상태 복원은 여기 적용되지 않는다(위의 기계 확인은 복원이
아니라 이 커밋의 착지 전제다). 선언 뒤 — 읽기·수정·확인 어느 국면에서든 — 세 질문 중 하나가
"예"로 뒤집히면 멈추고 보고한 뒤 정식 경로(요청의 journal 기록부터)로 전환한다 — 이미 만든
수정은 작업 트리에 남고, 그 요청의 카드를 잡은 세션이 사용자 확인을 받아 자기 것으로
넘겨받는다(resume 보고의 미커밋 경로가 그것을 비춘다). 경량 작업 중의 발견은
발견→갱신 표를 변경 크기와 무관하게 따른다. 이 커밋은 구속 결정이 아니다 — 봉쇄가 이
차선을 막지 않는다.

## 커밋 규율

- **모든 devflow 커밋은 자기 경로만 담는다.** 이 working tree에 무엇이 stage돼 있든 커밋에는
  그 커밋의 규칙이 열거한 정확한 경로만 담긴다 — 같은 폴더에서 도는 다른 흐름이 미리 stage해
  둔 파일이 동승하면 안 된다.
- **Layer 0 커밋**: product·arch·design·adopt는 사용자가 확인한 즉시 각 코어 문서를 커밋
  하나로 착지시킨다 — 메시지는 `<스킬> — <문서 파일명>`이다(adopt는 도입 문서 전체를
  `adopt — layer 0`으로 함께 착지시킨다). 다른 문서와 함께 만든 문서(product.md와 함께 만든
  glossary.md)는 같은 커밋에 동승한다. 기존 문서의 단일 필드 완성도 같은 메시지 형식을 쓴다.
  이 커밋은 구속 결정이다.
- **능력 설계 커밋**: arch·adopt는 확정된 Layer 0 커밋이 전부 착지한 뒤 기준선 판정 정본대로
  골조와 모든 비은퇴 능력의 설계 구역을 쓴다. 그 실행의 마지막 커밋에는 능력 문서만 담고
  메시지를 각각 `arch — capabilities`·`adopt — capabilities`로 쓴다. 바뀐 byte가 없으면
  커밋하지 않는다. 통합 브랜치의 구속 결정이다.
- **계획 커밋**: split이 새로 만들거나 고친 대기 카드·사용자가 확인한 카드 의존 형식 교정·트리 구조·카드의 승인과 검토·
  arch.md `해소 카드` 교체·verify.md 실패 또는 채택 소견 라우팅·이 커밋이 해소하는 층 열기
  마커 전부의 삭제를 한 커밋에 묶는다. 구현 결과가 아니므로
  완료 신호를 요구하지 않는다. 메시지: `split — <연 층>`. 승격의 `NN.N promote`는 같은
  계획 커밋의 전용 메시지다. 구속 결정으로 통합 브랜치에 착지한다.
- **라우팅 쓰기 순서**: 실패 이력이나 채택 소견의 정확한 결과가 결정되고 필요한 사용자 승인이
  끝나면, 출력 전에 verify.md의 `라우팅: 대기`를 `라우팅 준비: <JSON 객체>`로 바꾼다. 객체는
  `base`·`result`·`operations` key만 정확히 한 번씩 가진다. `base`는 이 교체 직전 HEAD에서 Git이
  출력한 축약하지 않은 전체 commit object ID다. `result`는 `라우팅: 수정 카드 <카드 번호>(+<카드 번호>)*`·`라우팅: 문서
  <devflow/project 정확한 경로의 JSON 배열>`·`라우팅: product 재실행 <journal timestamp>` 중 한
  줄이다. 첫 형식의 `*`는 기록 문자가 아니라, 정확한 카드 번호를 하나 이상 쓰고 둘째 번호부터
  앞에 `+`를 붙인다는 표기다.

  `operations`는 적용 순서의 JSON 배열이다. 각 항목은 `{"op":"write","path":<경로>,
  "content":<최종 UTF-8 문자열>}`·`{"op":"move","from":<경로>,"to":<경로>}`·
  `{"op":"delete","path":<경로>}` 중 하나이며 표시된 key만 가진다. 경로는 저장소 상대 `/`
  형식이고 `devflow/`로 시작하며 절대 경로나 `..`를 포함하지 않는다. write·delete는 현재
  verify.md를 대상으로 삼지 않는다. move는 그 파일의 조상 상태 경로를 개명할 수 있으며, 이때
  현재 verify.md 경로도 새 조상 아래로 따라간다. write는 필요한 부모 폴더를 만들고 일반 파일을
  생성·교체한다. move는 존재하는 상태 경로를 존재하지 않는 경로로 개명한다. delete는 존재하는
  일반 파일을 지운다. 각 항목은
  직전 tree를 실제로 바꿔야 하며, 배열 전체가 오류 없이 적용돼 선택한 정본 라우팅이 요구한 출력만
  만들어야 한다.

  실행 제안을 위해 먼저 쓴 카드 초안은 커밋된 층 열기 마커가 지키고 `operations`의 첫 write
  항목들로 정확히 표현돼야 한다. 준비 객체가 미커밋이면 HEAD가 `base`와 같아야 한다. 규칙을 어겨
  객체가 HEAD에 착지했다면 그 commit의 첫 부모가 `base`이고 현재 verify.md에 같은 객체가 있어야
  한다. 그 두 경우 외에는 정합성 이상이다. `base` tree에서 operations를 순서대로 적용할 때 조상
  move마다 현재 verify.md 경로를 추적한다. 대조용 tree에서는 그 파일의 정확히 한 `라우팅 준비`
  필드만 `base`의 같은 출처가 가진 `라우팅: 대기`로 되돌린다. 다른 byte는 하나도 제외하지 않는다.
  staged·unstaged·미추적 경로를 포함한 이 정규화 checkout tree와 `base`의 전체 차이는 정확히 한
  접두 구간의 결과와 같아야 하며, 경로 이동 자체도 포함한다. 다르면 payload 밖
  변경이므로 정합성 이상이다. 준비 객체를 다시 커밋하지 않은 채 남은 접미 구간만 순서대로 적용하고
  추적한 verify.md의 준비 객체를 `result`가 지정한 완료 상태로 바꾼 뒤 지정 커밋 하나로 함께
  착지시킨다. 새 라우팅을 고르거나 출력을 두 번 만들지 않는다.
- **승계 줄.** 환류 판정 뒤 최종 작업 커밋 직전에, work은 점유 카드의 진행 로그에 아래 줄을
  정확히 하나 붙인다.

  ```text
  YYYY-MM-DDTHH:MM:SSZ carry: <이 깊이 1 단위의 다음 카드를 틀리게 만들 수 있는 사실 | none>
  ```

  담는 것은 착지할 곳이 없는 잔여뿐이다 — 이 단위에만 있는 함정, 이 카드가 반증한 접근,
  어느 문서도 기록하지 않은 측정값. 발견→갱신 표·journal·능력 문서·코드가 이미 받은 것은 여기
  적지 않는다. 이 줄은 최종 작업 커밋에 실리므로 정본 점유→완료 이동의 byte 동일성은 그대로다.
- **1 작업 = 1 커밋.** 완료 신호 통과 후에만 커밋한다 (원격 증거만 남았을 때는 아래 예외).
  메시지는 `02.2 가입 API` 형식이며 카드 H1에서 `# `만 제거한 값과 정확히 같다.
  최종 작업 커밋 뒤에도 경계 정리 전까지 카드는 점유
  상태다. 그 카드를 마지막으로 바꾼 commit 제목이 이 형식과 정확히 같으면 최종 작업 커밋은
  끝난 것이다. 최종 작업 커밋은 점유 카드와 그 시점의 진행 로그를 포함한다. work는 다시
  만들지 않고 환류 착지와 경계 정리만 끝낸다.
- **정본 점유→완료 이동**: HEAD의 점유 카드 경로가 현재 체크아웃에서 사라지고, 같은 부모에서
  번호와 이름이 같은 `.done.` 카드가 정확히 하나 있으며, 두 파일의 byte가 같으면 성립한다.
  git이 이를 rename으로 표시하는지 삭제+미추적으로 표시하는지는 판정에 쓰지 않는다. 이 이동이
  미커밋이면 미완 경계다.
- 긴 작업의 중간 체크포인트는 `02.2 wip: <내용>` 커밋 허용. 체크포인트류 커밋이 담는
  "현재 diff"는 언제나 이 세션이 그 카드에 만든 변경을 뜻한다 — 자기 경로만 담는다는
  첫 항목의 세션판이다.
- 완료 신호에 원격 증거(CI 등)만 남았다면: 검토를 먼저 받고 코드·진행 로그를
  `NN.N wip: evidence-wait` 체크포인트로 커밋한다. 커밋 직전에 진행 로그에 아래 줄을 쓰며,
  `점검-json`은 원격 결과 하나를 돌려주는 정확한 명령 또는 URL의 JSON 문자열이다.

  ```text
  YYYY-MM-DDTHH:MM:SSZ 원격 증거 점검: 점검-json: <정확한 원격 결과 명령 또는 URL을 담은 JSON 문자열>; 판정: 미실행 | 통과 | 실패 | 대기 | 접근 불가 | 판정 없음; 상세-json: <결과 상세를 담은 JSON 문자열>
  ```

  journal이나 다른 경계 변경을 쓰기 전에 현재 브랜치를 그 checkpoint까지 arch.md의
  `merge` 방식으로 통합한다. rebase가 hash를 바꾸면 바뀐 hash를 쓴다. 그 hash를 넣은 정본 `증거 대기` 줄을
  journal에 쓰고 `경계 정리 — evidence-wait <번호>` 커밋으로 착지시킨 뒤 두 커밋을 push한다.
  카드는 `.wip.`로 남는다. checkpoint 커밋 뒤 기록 커밋 전에 중단되면 work가 정확한
  checkpoint를 찾아 줄·기록 커밋·push만 끝낸다. `카드-json`과 `점검-json`은 JSON 문법으로
  읽으며 구분자 문자열로 쪼개지 않는다.
  checkpoint의 정확한 메시지는 `<id> NN.N wip: evidence-wait`다.

  checkpoint 직전 줄의 판정은 `미실행`, 상세-json은 빈 문자열이다. 증거를 처리할 때 그 명령을
  실행하거나 URL을 열고 같은 형식의 새 줄에 현재 판정과 상세를 기록한다. 대기면 journal 줄과 카드를
  유지한다. 통과면 `증거 대기`를 같은 필드의 `증거 마감`으로
  교체한 최종 작업 커밋을 만든다. 커밋된 `증거 마감`은 작업 커밋이 끝났고 환류와 경계 정리만
  남았다는 뜻이다. work는 완료 신호를 다시 실행하지 않고 카드를 `.done.`으로 바꾸고 그 줄을 지우는 경계 정리 커밋만 수행하며 최종 작업
  커밋을 다시 만들지 않는다. 실패면 결과를 진행 로그에 기록하고 줄을 지운
  `NN.N wip: remote evidence failed` 체크포인트를 만든 뒤 실패 사다리로 돌아간다. 열 수 없거나
  판정 결과가 없으면 미검증으로 보고 줄을 유지한다.
- **경계 정리 커밋**: 상태 개명·HANDOFF·journal·verify.md·환류로 고친 문서(work 참조)를 하나로 묶는다.
  메시지는 `경계 정리 — <닫힌 것>`. HANDOFF는 전용 커밋을 만들지 않고 여기 동승만 한다.
  작업 경계가 기록하는 최종 작업 commit이나 checkpoint가 아직 통합 브랜치에 없으면,
  상태 개명·HANDOFF·journal·verify.md·환류 문서 중 어느 것도 working tree에 쓰기 전에 먼저
  arch.md의 `merge` 방식으로 그 commit까지 통합한다. 구속 결정으로 이미 통합에 착지한 문서는
  다시 싣지 않는다 — 경계 정리 커밋에는 개명·HANDOFF·journal·verify.md·마커만 싣는다.
  `merge-commit`은 통합 브랜치에 squash 없는 merge commit을 만들고, `rebase`는 fetch한 통합 tip
  위로 현재 브랜치를 rebase한 뒤 통합 브랜치를 fast-forward한다. rebase가 checkpoint hash를
  바꾸면 journal에는 바뀐 hash를 쓴다. 경계가 기록하는 commit이 통합 tip의 조상인 것을 확인한
  뒤에만 그 통합 브랜치에서 경계 정리 커밋을 만든다. 기록할 작업 commit이 없는 경계는 통합
  브랜치에서 바로 만들며, 그 뒤 다음 단계를 라우팅한다.
- **검증 상태 커밋**: product 검증의 실행·결과·보고 상태는 각각
  `경계 정리 — product 검증 실행`, `경계 정리 — product 검증 결과`,
  `경계 정리 — product 검증 보고`로 착지한다. 능력 검증의 실패·미검증 결과와 폐쇄 게이트 실패가
  붙은 통과 결과는 `경계 정리 — 능력 검증 결과 <능력 번호>`로 착지한다. 감리·회고 사건의 대기·결과·결정 상태는 각각
  `경계 정리 — verify 사건 <감리|회고> <출처 id> <대기|결과|결정>`으로 착지한다.
  `경계 정리 — verify 출처 id`를 포함한 모든 검증 상태 커밋이 공유 상태이므로 통합 브랜치에
  착지한다. 이 커밋들 중 하나 또는 `경계 정리 — begin <능력 번호>` 커밋이 착지하기 전에 그
  커밋이 지정하는 현재 체크아웃 상태가 **정규 검증 상태 전환**이며, 소비자는 실행을 반복하지
  않고 지정된 커밋을 먼저 마친다. `경계 정리 — begin <능력 번호>` 커밋이 지정하는 상태는 통과
  verify.md 기록, 폐쇄 능력의 정확한 기준선 경로 한 개(부재·부분·임의 바이트 모두 허용),
  그리고 이미 만들었다면 능력 닫기 기록이다 — 그 커밋이 착지하기 전 그 기준선 파일의 재생성은
  기준선 판정 정본이 지배한다. 정규 능력 설계 커밋·ADR 승계의 기계적 정확 경로 교체·정본의
  사람 삭제 예외·사용자가 지목한 Git revision에서 경계 하나인 완전한 파일 하나를 현재 기대 경로로 복구한 경우·
  이 begin 전환 밖의 `devflow/project/capabilities/` 경로 diff는 정합성 이상이다.
- **git은 메인 세션의 것이다.** 서브에이전트는 구현하고 진행 로그를 남길 뿐,
  커밋·개명·push를 하지 않는다.
- 커밋 메시지에 id를 접두한다 — `<id> 02.2 가입 API`, `<id> 02.2 wip: ...`,
  `<id> 경계 정리 — ...`. 이 문서의 모든 메시지 형식은 id 뒤 부분만 적은 것이다. 전부 앞에
  `<id> `를 붙이고, 기록된 제목을 읽을 때도 같게 읽는다.
- **구속 결정** — 공유 문서·트리 구조나 번호(폴더·발급)·남의 점유 카드에 영향을 주는
  결정, 최초 `.wip-<내 id>.` 점유 개명, 그리고 내 점유 카드를 대기로 되돌리는 해제.
  이미 통합에 보이는 내 점유 카드의 그 밖의 상태 개명은 구속 결정이 아니다.
  그 결정을 구성하는 파일만 담은 커밋을 지금 통합 브랜치(arch 설정)에 착지시킨다 — 통합에
  쓸 수 없으면 게시 문단의 봉쇄 규칙이 이 "지금"보다 우선한다.
  계획 커밋이면 위에 열거된 파일 묶음 전체가 그 결정이다. 관계없는 변경은 동승시키지 않는다.
  최초 점유 커밋은 통합에 착지하고 현재 브랜치가 그 통합 tip을 포함하기 전까지 구현을 시작하지
  않는다. 나머지 변경은 내 브랜치에 실린다.
- 통합을 당겨왔을 때 같은 번호에 남의 점유가 이미 착지해 있으면 내가 진 것이다 —
  내 진행 로그를 살아남은 카드로 옮기고 물러난다.
- 번호는 통합에서만 발급되므로 중복은 대기·미점유 단계에서만 생긴다. 그 단계에서는 나중에
  병합된 쪽이 중간 삽입 형식으로 옮기고(`03.2` → `03.2b`) journal 1줄을 남긴다. 이미
  점유되었거나 끝난 카드의 번호는 바꾸지 않고 정합성 이상으로 보고한다 — 그 번호는 커밋
  제목·외부 이슈·사람의 링크에도 남아 있어 파일과 의존만 고쳐도 그것들은 따라오지 않는다.
  verify 출처 id도 같은 원리다.
- HANDOFF 병합 충돌은 `# HANDOFF · <timestamp>` 헤더가 더 최신인 쪽을 쓴다. digest 마커는
  자손 hash를 남긴다 (resume의 마커 규칙).
- journal 병합 충돌은 3-way로 푼다. 충돌의 공통 조상 journal blob — merge면
  `git merge-base`가 준 커밋, rebase면 재생 중인 커밋의 부모 — 과 충돌 구간을 대조한다:
  조상에 있던 줄이 한쪽에 없으면 소비된 것이다 — 되살리지 않는다.
  조상에 없던 줄은 추가다 — 양쪽 것을 모두 timestamp 순서로 남기고, 같으면 내 쪽을 먼저
  둔다. 합집합으로 풀면 이미 소비된
  요청이 부활해 같은 수정이 새 번호로 두 번 계획된다.
  squash 병합은 금지다(`NN.N` 이력 위의 규칙들이 침식된다) — 정책은 arch 설정에 선언한다.
- 되돌릴 때는 revert 커밋 — 히스토리를 지우지 않는다.

## 검증 철칙

**실행하지 않은 것은 통과가 아니라 미검증이다.**
코드를 읽고 "맞는 것 같다"는 판정이 아니다.
