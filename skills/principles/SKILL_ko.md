# devflow 원칙 (규칙 정본)

모든 devflow 스킬·카드·프롬프트는 이 문서를 따른다. 다른 문서와 충돌하면 이 문서가 이긴다.

## 프롬프트 7원칙

1. **1개념 1단어.** 동의어 금지. 프로젝트 고유 용어는 `devflow/project/glossary.md`에 등재하고 끝까지 같은 단어를 쓴다.
2. **목적지 > 지시.** "무엇을 하라"가 아니라 "무엇이 참이 되어야 하는가"를 적는다.
3. **방향은 풍부하게, 금지는 짧게.** 맥락·의도·왜는 넉넉히 준다. 하네스(금지)는 3줄 이내.
4. **방법을 지시하지 않는다.** 구현 방법은 실행하는 모델이 결정한다.
5. **예시 1개 > 규칙 5개.**
6. **기성 방법론 용어 회피.** spec-driven, TDD, DDD 같은 단어는 원치 않는 짐을 끌고 온다.
7. **정체성 반복 주입.** `product.md`의 정체성 문단은 모든 작업 카드에 그대로 복사한다
   (예외: 조사 카드 — split의 조사 카드 절).
   이것이 유일하게 허용된 중복이다 — 비용은 한 문단, 효과는 "길 잃지 않음".

## 모드와 신원

devflow는 두 모드로 동작한다. 판별 기준은 파일 하나다:

- `devflow/users/*/owner.md`가 하나라도 있으면 **다중 모드** — 여러 사람이 한 저장소에서
  각자의 세션을 돌린다.
- 하나도 없으면 **솔로 모드** — 이 문서 전체에서 "다중:"이 붙은 규칙은 전부 무시한다.
  솔로의 동작은 그 규칙들이 없던 버전과 동일하다.

다중: 트리·journal·공유 문서에 쓰기 전에 자기 id를 해결한다 — git 신원(이름 또는 이메일)을
`devflow/users/*/owner.md`와 대조한다. 일치가 없으면 사용자에게 1회 묻고 방을 만든다.
해결 불능인 세션(CI·봇)은 읽기만 한다.
id는 소문자 `[a-z0-9]{2,8}`. devflow가 쓰는 이름(project·tree·users·decisions) 금지, 재사용 금지.

방 = `devflow/users/<id>/` = owner.md(신원 선언) + HANDOFF.md + digest.md(소화 마커).
자기 방에만 쓴다. 방은 팀 전체가 읽는다 — 그 전제로 쓴다.

다중: **`.wip-<내 id>.`만이 내 작업이다.** 전제조건·통독·이어하기 규칙은 전부 내 점유에만
적용된다. 남의 점유 카드는 읽기 전용 참고다 — 점유하지 않은 카드에 쓰지 않는다.
멈춘 점유의 재배정 = 해제 후 재점유. 사용자의 명시적 지시로만 하며 journal 1줄을
남긴다 (점유 불가침의 공인된 예외).

모드 전환 — 전부 커밋 1개짜리 절차다:

- 합류: 방 생성(owner.md) + 마커 = 현재 HEAD. 과거의 이해는 커밋 고고학이 아니라
  공유 문서에서 온다.
- 솔로→다중: 방 생성 + `devflow/HANDOFF.md`를 방으로 이동 + `.wip.` → `.wip-<id>.` +
  마커 = HEAD. 다중 모드에서 솔로 흔적(무기명 `.wip.`, `devflow/HANDOFF.md`)이 보이면
  전환 미완이다 — 보고하고 소유자를 사용자에게 확인해 마저 전환한다. 추측 금지.
- 이탈: 사용자가 선언한다. 남은 구성원 아무나 — 떠난 방의 열린 결정을 journal로 승격(기명),
  그의 점유를 해제, 방 삭제, journal 1줄. "자기 방에만 쓴다"와 점유 불가침 둘 다의
  공인된 예외다.
- 다중→솔로(마지막 1인): HANDOFF를 devflow/로 복귀, users/ 삭제, 접미사를 `.wip.`으로,
  arch의 다중 전용 설정 줄(integration·merge)을 지운다.

## 문서 계층 (계약)

`product ⊃ arch ⊃ design·code-style ⊃ tree(카드)`. **하위는 상위를 어길 수 없다.**
어겨야 한다면 그것은 상위의 결정이다:

1. 멈추고 진행 로그에 "왜" 2줄
2. 상위 문서를 고친다 (ADR 세 조건을 충족하면 ADR 동반 — arch 참조)
3. 낡아진 카드에 `.stale.` 표시, journal.md에 1줄
4. split로 영향 구간을 재분할하고 재개

**문서 간 모순을 발견하면 그것은 우선순위 문제가 아니라 결함이다.** 어느 쪽도 조용히
채택하지 말고, 멈춰서 이 절차로 합친 뒤 진행한다. 위임받은 구현자라면 멈추고 보고만
한다 — 합치는 것은 메인 세션의 일이다.

무엇을 발견했을 때 어디를 고치는가:

| 발견한 것 | 갱신할 곳 |
|---|---|
| 기능·화면·범위가 바뀜 | product.md (+영향 카드 `.stale.`) |
| 스택·모듈 경계·데이터가 안 맞음 | arch.md (+ADR 검토) |
| 상위 문서의 잠정값이 실측됨 | arch.md 잠정값 표의 그 행 — 옆에 더하지 말고 **교체**. 그 값을 전제한 ADR에는 날짜 딸린 갱신 주석 |
| 성공 판정이 적힌 대로는 실행 불가 | product.md (+그 판정을 인용하는 카드들) |
| `.done.` 카드의 완료 신호가 실행 불가로 판명 | 그 카드의 신호 문구도 고친다 — 회귀는 항상 돌 수 있어야 한다 |
| 코딩 방식 결정이 새로 필요 | code-style.md 선택 절에 1줄 |
| 새 용어가 필요해짐 | glossary.md 1줄 |
| 작업이 예상보다 클 뿐 | 문서 변경 없음 — 카드를 폴더로 승격 (split의 승격 절차) |
| 작업 간 결정 | journal.md 1줄 |

위 표에 따른 갱신(잠정값 교체, 신호 문구 수정 등)은 그 자체로 공인된 수정 경로다.
1~4단계 절차는 하위가 상위를 **위반**해야 할 때만 밟는다.

코어 문서(`devflow/project/*`)는 **이 절차 또는 해당 스킬의 재실행으로만** 수정한다 —
작업 중에 지나가며 고치지 않는다. 그리고 수정은 **대체가 기본**이다:
새 줄을 더했으면 낡은 줄을 지웠는지 본다. 자라기만 하는 문서는 죽은 문서다.

## 정합성 점검

트리를 여는 관문(split·resume 시작 시)에서 훑는다.
이상은 **고치지 말고 보고한다** — 자동 교정이 오판하면 오염이 가속된다. 사용자 승인 후 교정.

1. `.wip.`가 2개 이상인가 (journal에 병렬 승인·증거 대기 기록이 없는데. 다중: 같은 id 기준)
2. 같은 번호가 중복되는가
3. `.done` 폴더 안에 done 아닌 카드가 있는가
4. 카드의 `의존`이 가리키는 번호가 실존하는가
5. HANDOFF가 가리키는 경로가 실존하는가
6. 다중: 무기명 `.wip.`이 있는가 (무주 점유 또는 전환 미완)
7. 다중: 같은 git 신원을 주장하는 owner.md가 둘 이상인가
8. 다중: 점유자가 아닌 작성자가 그 점유 카드를 건드린 커밋이 있는가

## 모델 등급

**파일에 모델명을 적지 않는다.** 등급만 쓴다. 실제 모델·사고량은 split의
실행 제안에서 사용자가 그 세션에 한해 결정한다.

| 등급 | 역할 | 용도 |
|---|---|---|
| T-상 | 최상위 사고 | 판정·리뷰. 짧게만 — 길게 돌리면 비용이 정당화되지 않는다 |
| T-중 | 표준 사고 | 기본값. 기획, 분할, 모호하거나 얽힌 작업 |
| T-하 | 구현 특화 | 카드가 완전한 구현, 기계적 변환, 수집·정리 |
| 그 이하 | — | 코딩 금지 |

사고량(effort) 규칙: **판정은 상위 등급 + 낮은 사고량으로 짧게. 설계는 표준 등급 + 높은 사고량으로 깊게.**

하네스 다이얼 — 등급에 반비례한다:

- T-중 이상: 목적지 + 금지 3줄. 경로 지시 없음. 방법을 지시하면 오히려 성능이 깎인다.
- T-하: `읽을 것` 완전 열거 + 진행 순서 힌트 + 금지 확대 + 완료 신호 명령어 그대로.
- **T-하 수준의 카드를 쓸 시간이 없으면 그 작업을 T-하에게 주지 않는다.**

## 실패 사다리 (모든 재시도에 공통)

```
1차 실패 → 카드를 보강해 재투입 (같은 프롬프트 재투입 금지 — 실패는 카드 결함의 신호다)
2차 실패 → 등급을 올리거나 메인이 직접
3차 실패 → 사람 호출. 4번째 시도는 없다
```

## 상태 표기

**파일 트리가 진행 상태의 정본이다. 문서에 진행률을 적지 않는다.**

- 접미사 없음 = 대기 / `.wip.` = 진행 중 / `.done.` = 완료 / `.stale.` = 상위 결정 변경으로 무효
- 다중: 점유는 `.wip-<id>.`로 표기한다. 무기명 `.wip.`은 무주 점유 = 정합성 이상.
  해제는 접미사 전체를 벗겨 대기로 되돌린다(진행 로그는 카드에 남는다).
  `.done.`·`.stale.`은 무기명 그대로 — 완료의 소유는 git이 기억한다
- `.wip.`는 동시에 하나만 (다중: 1인당 하나. 예외: 승인된 병렬, 증거 대기 — 둘 다 journal 기록이 근거)
- `.done.`은 **완료 신호 통과 + 카드에 적용되는 검토 통과 + 커밋 착지 이후에만**.
  이 문서에서 "검증"은 verify의 능력·제품층 전용어다
- 하위가 전부 `.done.`이면 폴더도 `.done`을 받는다.
  단, **1층 능력 폴더는 능력층 검증 통과 후에** — 부여는 verify가 한다.
  골조 폴더(01)는 능력이 아니므로 시나리오 검증 없이 자식 전부 `.done.`이면 닫힌다
- 은퇴한 능력 폴더는 `.stale` — 내부 카드 상태는 전부 무효다.
  훅과 정합성 점검은 `.stale` 폴더 내부를 세지 않는다
- 파일명 본체와 번호는 불변 식별자. 재정렬·재사용 금지. 중간 삽입은 `02.2b` 형식
- 카드가 아닌 기록 파일(`verify.md` 등)은 상태 접미사를 갖지 않으며 상태 판정에서 제외한다

## 커밋 규율

- **1 작업 = 1 커밋.** 완료 신호 통과 후에만 커밋한다 (원격 증거만 남았을 때는 아래 예외).
  메시지는 `02.2 가입 API` 형식(트리 번호 + 제목).
- 긴 작업의 중간 체크포인트는 `02.2 wip: <내용>` 커밋 허용.
- 완료 신호에 원격 증거(CI 등)만 남았다면: 검토를 먼저 받고 본 커밋으로 push한다.
  카드는 증거 도착까지 `.wip.`(증거 대기)로 남고 journal에 1줄 남긴다.
  증거가 도착하면 개명과 journal 대기 줄 삭제를 경계 정리 커밋에 담는다.
- **경계 정리 커밋**: 상태 개명·HANDOFF·journal·환류로 고친 문서(work 참조)를 하나로 묶는다.
  메시지는 `경계 정리 — <닫힌 것>`. HANDOFF는 전용 커밋을 만들지 않고 여기 동승만 한다.
  다중: 구속 결정으로 이미 통합에 착지한 문서는 다시 싣지 않는다 — 경계 정리 커밋에는
  개명·HANDOFF·journal·마커만 싣는다.
- **git은 메인 세션의 것이다.** 서브에이전트는 구현하고 진행 로그를 남길 뿐,
  커밋·개명·push를 하지 않는다.
- 다중: 커밋 메시지에 id를 접두한다 — `<id> 02.2 가입 API`, `<id> 02.2 wip: ...`,
  `<id> 경계 정리 — ...`. 솔로 형식은 그대로다.
- 다중: **구속 결정** — 공유 문서·트리 구조나 번호(폴더·발급 — 내가 점유한 카드의
  상태 개명은 아니다)·남의 점유 카드에 영향을 주는 결정.
  그 수정(문서 + journal 줄)만 담은 커밋을 지금 통합 브랜치(arch 설정)에 착지시킨다 —
  다른 변경을 동승시키지 않는다 (공인된 예외: split의 승격 커밋은 점유 접미사 상속을
  동승시킨다). 나머지 변경은 내 브랜치에 실린다.
- 다중: 통합을 당겨왔을 때 같은 번호에 남의 점유가 이미 착지해 있으면 내가 진 것이다 —
  내 진행 로그를 살아남은 카드로 옮기고 물러난다.
- 다중: 동시 발급으로 번호가 중복되면 나중에 병합된 쪽이 중간 삽입 형식으로 옮긴다
  (`03.2` → `03.2b`). `.done.` 전에만 허용, journal 1줄.
- 다중: journal 병합 충돌은 합집합이다 — 양쪽 줄을 날짜순으로 다 남긴다.
  squash 병합은 금지다(`NN.N` 이력 위의 규칙들이 침식된다) — 정책은 arch 설정에 선언한다.
- 되돌릴 때는 revert 커밋 — 히스토리를 지우지 않는다.

## 검증 철칙

**실행하지 않은 것은 통과가 아니라 미검증이다.**
코드를 읽고 "맞는 것 같다"는 판정이 아니다.
