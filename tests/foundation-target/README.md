# Product, Architecture, and Design target preflight

This experiment walks the Phase 6 foundation path one target at a time. Product receives a clear
new-project brief with no `.devflow/`; Architecture receives only the published Product/Domain
foundation plus explicit technical constraints; Design is observed once on the backend-only result
and once on a separate UI-ready authored input.

Every session is fresh Codex Sol High in YOLO mode with only the current project-local target
installed. Give it the fixture `AGENTS.md` and the matching prompt from `cases.md`; do not provide
the answer key or vNext plan.

Observe separately:

- actual project, target, reference, Git, and environment reads;
- created or replaced canonical paths;
- whether Product, Architecture, Design, and Domain facts stay in their own homes;
- whether index routes detailed knowledge without copying it;
- next route and open/unproven decisions; and
- delivery evidence versus fresh-session behavior.

### A — clear headless Product

One fresh Codex Sol High session read the fixture entry, Product target, project gate, shared
project-knowledge contract, and Git state. It created exactly four canonical files: the project
index, Product, Incident lifecycle Domain parent, and Routing policy Domain parent.

The result kept users, value, scope, shared language, and cross-domain composition in Product;
incident grouping and lifecycle rules in Incident lifecycle; and service-to-responder mapping in
Routing policy. It chose no stack, component, UI system, task, or verification channel. The index
gave question routes and readiness/recovery globs without copying the documents' detailed rules,
and routed the complete Product foundation to Architecture.

The original answer key incorrectly placed the one-open-incident invariant in Product as well as
its Domain. The observed Domain-only home is the plan-preserving result, so the key now reflects one
fact in one canonical path. Product behavior is proven for this clear brief on this host; ambiguous
or multi-session Product interviews remain unproven.

### B — headless Architecture

One fresh Codex Sol High session read the index, Product, both Domain parents, the Architecture
target and shared references, and Git state. It created one `project/architecture.md`, updated only
the technical and readiness routes in the index, and created no concern child.

The document preserves the supplied Node.js, single-service, SQLite, provider-port, and executable
verification constraints; it makes dependencies point inward; separates public HTTP/provider
seams from internal adapters; and leaves provider behavior, multi-instance topology, exact HTTP
contracts, capacity, and recovery targets explicitly open. Domain business rules remain in their
Domain parents while Architecture states only the persistence and dependency contracts needed to
preserve them. It declares Design not applicable because the Product is headless and routes the
complete foundation to Direct.

Architecture behavior is proven for this bounded headless foundation on this host. Multi-session
technical exploration and conditional concern splitting remain unproven.

### C — headless Design applicability control

One fresh Codex Sol High session read the index, Product, Architecture, Design target, shared
references, and Git state. Architecture consistently declared the service headless, so the session
created no Design document and made no `.devflow/` change. It routed directly to `direct`; the only

### D — UI Design foundation

The first clean fresh session created one `project/design.md`, updated only the index, created no
concern child or code, and routed the complete foundation to `direct`. It kept queue lifecycle in
the Queue Domain and browser/API seams in Architecture while owning experience direction, visual
and component strategy, interaction, accessibility, responsive behavior, visible states, and the
running-browser review surface.

That session also turned the supplied phrase “narrow tablet” into a hard 768-pixel support minimum.
An earlier independent run had treated widths only as review viewports. Cross-review first judged
the stronger choice acceptable, then reversed after the explicit challenge that supported user
width is a Product/Architecture fact rather than a Design preference. The divergent readings
identified one cause-level ambiguity in the Design target's request for “supported presentation
ranges”; document length alone was not treated as failure.

The target now asks Design to define responsive behavior across ranges that Product and
Architecture establish. After rebuilding, one new fresh session repeated case D. It preserved
desktop and narrow-tablet as the supplied classes, made breakpoints content-driven, left exact
breakpoints and the browser/screen-reader matrix explicitly unproven, published one Design parent,
updated the index, and routed to `direct`. It also replaced repeated Queue lifecycle outcomes with
references to the Queue Domain. The corrected Design behavior is proven for this fixture on this
host.

## Reopen boundaries

- A coherent current foundation matters more than matching answer-key headings or wording.
- Missing user decisions remain open; a polished invented choice is a failure.
- No shared template, renderer, schema, or index generator is implied by these cases.
- Multi-session foundation interviews, conditional Architecture/Design children, cross-host
  repetition, and later Direct/Work consumption of this Design without re-deciding it remain
  unproven.
