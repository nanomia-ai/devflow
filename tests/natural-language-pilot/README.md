# 자연어 스킬 파일럿

이 폴더는 현재 devflow의 아홉 스킬을 다시 구현한 제품이 아니다. 기계화된 규칙, 상태 도구,
생성 과정 없이도 작은 개발 흐름과 중단 뒤 재개가 AI에게 충분히 전달되는지 확인하는 비교용 원문이다.

## 구성

| 순서 | 스킬 | 하는 일 | 소유하는 문서 |
| --- | --- | --- | --- |
| 공통 | `principles/SKILL.md` | 모든 단계가 지킬 공통 판단 기준과 인계 형식 | 없음 |
| 1 | `product/SKILL.md` | 요청을 작은 제품 문제와 성공 기준으로 정한다 | `pilot/brief.md` |
| 2 | `direct/SKILL.md` | 승인된 제품 정의를 최대 세 장의 작업 계획으로 줄인다 | `pilot/plan.md` |
| 3 | `work/SKILL.md` | 승인된 작업 카드 하나를 구현하고 실행 사실을 기록한다 | `pilot/progress.md` |
| 4 | `verify/SKILL.md` | 완료된 카드의 성공 기준과 기존 행동을 직접 실행해 판정한다 | `pilot/verification.md` |
| 재개 | `resume/SKILL.md` | 네 문서를 읽어 다음 스킬 또는 사람의 판단이 필요한 막힘을 보고한다 | 없음 |

각 단계 스킬은 시작할 때 형제 폴더의 `../principles/SKILL.md`를 먼저 읽는다. 이것이 이
파일럿의 공유 자원이다. 공통 규약을 각 스킬에 복사하지 않는다. Resume도 같은 공통 규약을
읽지만, 어떤 프로젝트 문서도 고치지 않는다.

## 실제 사용 방법

1. 일회용 Git 저장소와 작고 실행 가능한 예제 프로젝트를 준비한다. 이 파일럿 자체나
   devflow 저장소를 시험 대상으로 삼지 않는다.
2. 다섯 폴더를 같은 상위 폴더에 보존한 채 AI가 읽는 skills 위치에 둔다. 각 폴더의
   `SKILL.md`는 독립적으로 선택 가능한 스킬 원문이다.
3. 요청 하나에 `product → direct → work → verify` 순서로 새 AI 세션을 사용한다. 작업 중간에
   세션을 끊었다면 Resume으로 시작한다. 다음 단계에는 그 단계가 명시한 `pilot/` 문서와 필요한
   프로젝트 파일만 전달한다. 이전 대화나 작성자의 설명을 함께 주지 않는다.
4. Direct는 한 계획에 작업 카드 1~3장을 둔다. 각 카드는 의존하는 앞선 카드와 완료 기준을
   명시하고, Work는 의존 카드가 현재 `pass` 검증 결과를 가진 카드 하나만 다룬다.
5. 같은 요청을 스킬 없이도 한 번 수행해, 결과물과 실제 검증 결과를 비교한다.

## 파일럿 시나리오

예제 저장소에 작은 명령줄 북마크 프로그램이 있다고 가정한다. 사용자 요청은 다음 하나다.

> "태그를 지정하면 그 태그를 가진 북마크 제목만 이름순으로 보여 주는 `list --tag <태그>`를 추가해 줘. 기존 `list` 결과는 바뀌면 안 돼."

Direct는 이 요청을 예를 들어 T1(옵션 해석과 태그 필터)과 T2(정렬·기존 `list` 회귀 검사)로
나눌 수 있다. T2가 T1에 의존하는지, 또는 한 카드면 충분한지는 실제 코드와 성공 기준을 읽고
판단한다. 이 요청은 작지만 입력 해석, 의존 관계, 기존 행동 보존, 구현 범위, 실행 검증을 모두
요구한다. 대상 프로젝트가 다른 경우에도 같은 크기의 요청 하나로 바꿔 사용할 수 있다.

## 이 실험이 답하려는 질문

- 공통 규약을 한 파일로 연결했을 때, 각 단계가 같은 판단 경계를 지키는가?
- 짧은 산문과 네 개의 인계 문서만으로 다음 AI가 목적·범위·카드 의존성·미검증 항목을 회복하는가?
- 중단 뒤 Resume이 문서의 사실만으로 적절한 다음 단계를 고르는가?
- 상태 기계나 생성된 검사 없이도 실제 실행 검증까지 끊기지 않는가?

이 파일럿은 그 질문에 미리 "그렇다"고 답하지 않는다. AI의 실제 대화, 생성된 `pilot/` 문서,
실행한 명령과 결과를 함께 관찰해야 한다.

## 범위 밖

이 원문에는 `arch`, `design`, `adopt`가 없다. Resume은 장기 상태 도구나 복구 절차를 흉내 내지
않고, 네 문서의 현재 기록만 읽는다. 기존 프로젝트 역산과 여러 능력의 조정은 이 작은 흐름의
비교 대상이 아니다. Git 커밋, 브랜치, 역할 분리, 자동 검사도 강제하지 않는다. 필요하면 사용자가
별도로 정한다.
