# Product: 요청을 만들 일로 정하기

## 시작

먼저 `../principles/SKILL.md`를 읽는다. 이 스킬의 질문은 "사용자가 원하는 변화는 정확히 무엇이며,
무엇을 보면 성공이라고 말할 수 있는가?"이다.

## 읽을 것

- 사용자의 현재 요청
- 대상 프로젝트의 짧은 사용 설명 또는 진입 파일
- 요청을 이해하는 데 필요한 최소 코드와 기존 테스트

관련 있어 보인다는 이유만으로 프로젝트 전체를 읽지 않는다. 기존 행동을 보존해야 한다면 그 행동을
보이는 코드나 테스트는 반드시 확인한다.

## 할 일

1. 요청을 사용자 문제, 기대 결과, 변경하지 않을 것으로 나눈다.
2. 기존 프로젝트에서 확인한 사실을 적고, 아직 확인하지 못한 가정은 질문으로 남긴다.
3. 성공 기준을 실제로 관찰 가능한 문장으로 만든다. 예를 들어 "좋게 동작한다"가 아니라
   "태그 `work`를 지정하면 `work` 태그의 제목만 이름순으로 출력한다"처럼 쓴다.
4. 사용자에게 제품 정의 초안을 보여 준다. 범위 또는 성공 기준이 불명확하면 선택지를 제시하고
   확인을 기다린다.
5. 승인된 뒤에만 `pilot/brief.md`를 만든다. 이미 승인된 계획이 있을 때 제품 정의를 바꾸면,
   이전 계획이 여전히 유효한지 판단하지 않는다. 바뀐 이유를 brief에 적고 Direct로 다시 인계한다.

## `pilot/brief.md`에 남길 항목

- 요청과 사용자 문제
- 확인한 현재 동작과 근거 경로
- 이번 변경의 범위와 명시적 제외 범위
- 성공 기준
- 남은 가정 또는 미검증 항목
- 승인 사실과 이후 변경이 있으면 그 변경 이유
- 다음 단계: `direct`가 이 문서를 읽어 최대 세 장의 작업 카드를 제안한다

## 끝낼 때

제품 정의가 승인되지 않았거나 성공 기준이 관찰 가능하지 않으면 끝내지 않는다. 이 스킬은 설계 세부,
작업 순서, 코드 변경을 결정하지 않는다.
