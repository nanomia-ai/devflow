# 개인 워크플로우 편집 스킬

## 1. 출발점과 결정

현재 [기존 기획과 구현 기록](README.md)의 §13, 커밋 `7af7667`에는 Work·Verify의 개인 설정
소비가 구현되어 있다. 사용자가 저장한 선호를 실행에서 적용하는 경로는 있지만, 자연어 설정 요청을
받아 해당 파일을 만들고 보존하며 수정하는 공개 진입은 없다. 일반 AI가 우연히 경로와 계약을 아는
것을 사용자 경험의 전제로 삼을 수 없다.

**추천은 전용 편집 스킬을 개인화의 기본 제공 범위로 추가하는 것이다.** Work·Verify 앞에서 매번
실행하는 단계가 아니라 사용자가 자신의 지속적인 작업 방식을 설정할 때 호출하는 별도 기능이다.
기존 직접 편집도 허용하고 작성기를 거쳤다는 이유로 소비 시 보호 검토를 생략하지 않는다.

이 문서는 처음에는 그 후속 기획으로 작성되었고, 사용자의 구현 요청 뒤 적용한 결과를 §9에 이어
기록한다. 기본 소비 기능을 다시 구현하거나 기존 입증을 다시 미입증으로 돌리지 않는다. 기존 자연어
보호의 기술적 한계도 그대로이며 작성 스킬을 강제 쓰기 차단 장치라고 주장하지 않는다.

| 대안 | 판단 |
|---|---|
| 경로를 알려 주고 일반 AI에게 편집을 맡김 | 작성 책임과 발견 경로가 없다. 수동 편집의 보조 경로로 남긴다. |
| Work·Direct에 편집 분기와 작성 설명 추가 | 보통 작업도 편집 지침을 읽고, 작업 수행과 지속 선호 편집의 책임이 섞인다. |
| 새 편집 라우터·공통 작성 모듈·별도 매뉴얼 | 현재는 작성자가 하나뿐이다. 추가 연결과 반복 읽기를 정당화하지 못한다. |
| 공개 편집 스킬 하나 + 기존 공통 계약 재사용 | 편집 요청에만 본문을 읽으며 생성·수정 책임을 한 곳에 둔다. 채택을 추천한다. |

## 2. 이름과 발견

추천 ID는 **`workflow-customize`**, 사용자 표시명은 **개인 워크플로우 설정**이다.
사용자가 말한 행동을 직접 드러내되 설명에서 Work·Verify 실행 방법으로 범위를 한정한다.

| 후보 | 판단 |
|---|---|
| `personalize` | 무엇을 개인화하는지 드러나지 않는다. |
| `workflow-preferences` | 선호 범위는 잘 드러나지만 사용자가 수행할 편집 행동은 덜 직접적이다. 독립 검토자가 선호한 대안이다. |
| `customize-workflow` | 의미는 유사하다. 두 이름을 함께 제공하거나 별칭을 추가할 이유는 없다. |
| `workflow-customize` | 워크플로우를 조정하려는 사용자 표현과 가깝다. 전체 단계 변경으로 오해할 여지는 설명에서 제한한다. |

스킬 설명의 제안 문안:

> 현재 팀원의 Work 구현·자체 점검과 Verify 독립 검증 방법을 개인 설정으로 생성·수정·초기화한다.
> 개인 워크플로우에서 설정할 수 있는 범위를 묻거나 앞으로 사용할 작업 방식의 설정을 요청할 때 사용한다.
> 작업 실행, 일회성 지시,
> 공유 계약·단계·관리권·검증 의무 변경에는 사용하지 않는다.

호스트가 제공하는 스킬 목록의 이름·설명으로 자연어 요청을 연결한다. 각 Work·Verify 진입문이나
프로젝트 index에 편집 안내를 복제하지 않는다. 자동 선택은 호스트의 기능과 관찰에 달려 있으므로
보장하지 않는다. 명시적으로 스킬을 선택하는 경로도 제공하고, 설치 안내에 이름과 요청 예시를 둔다.
특정 호스트의 호출 문법을 공통 계약으로 만들거나 자동 호출 장치를 추가하지 않는다.

“이번에는 경계값부터 봐줘”는 현재 실행의 지시다. “앞으로 내 검증은 경계값부터 확인하도록 설정해줘”는
지속 편집 요청이다. 설정 의도가 없는데 작업 중 개인 파일을 생성하지 않는다. 지속 여부가 실제로
불명확할 때만 묻는다. 명시적인 생성·수정 요청을 받은 뒤 같은 승인을 반복해서 받지 않는다.

## 3. 사용자 경험과 범위

사용자는 파일 경로나 양식을 외울 필요가 없다. “내 Work는 재현부터, Verify는 경계 입력부터 보도록
설정해줘”라고 요청하면 현재 팀원과 기존 선호를 확인하고 필요한 파일만 만든다. 이후 “단순 문구
수정에는 재현 절차를 적용하지 않도록 바꿔줘”라고 요청하면 관련 조건만 바꾸고 다른 선호를 보존한다.

| 요청 | 파일 행동 |
|---|---|
| 첫 Work 선호 설정 | 본인의 `preferences/work.md`와 필요한 부모 폴더만 생성 |
| Work·Verify를 함께 조정 | 두 파일을 읽고 역할별 방법으로 나누어 작성 |
| 특정 선호 수정·해제 | 해당 부분만 변경하고 기존의 다른 선호 보존 |
| 명시한 스킬 설정 전체 초기화 | 해당 개인 파일만 삭제하여 기본 방법으로 복귀 |
| 이미 반영된 요청·설명만 요청 | 불필요한 쓰기 없이 현재 내용과 적용 범위를 설명 |

파일명만 안내하는 것으로 끝내지 않고, 사용자가 무엇을 조정할 수 있는지 요청과 관련된 범위에서 설명한다.
어떤 방법을 원하는지 이미 명확하면 전체 메뉴를 다시 제시하거나 두 파일을 모두 만들지 않는다.
“무엇을 설정할 수 있나”라는 설명 요청만으로는 파일·폴더를 만들지 않는다.

| 지원 파일 | 조정할 수 있는 방법 | 보존할 경계 |
|---|---|---|
| `work.md` | 구현 접근, 결함 재현·원인 가설, 자체 점검, 실패 뒤 수정 방법 | 작업 범위·계약·관리권을 유지하며 Verify 판정을 대신하지 않음 |
| `verify.md` | 기존 검증 항목의 관찰 순서·반례·경계 입력·증거 확인 방법 | 수용 기준·독립성·정직한 판정·게시 순서를 유지하며 직접 수리하지 않음 |

편집 가능한 결과는 현재 팀원의 `work.md`, `verify.md`뿐이다. Direct는 아직 소비를 지원하지
않으므로 `direct.md`를 만들거나 동작을 약속하지 않는다. 지원 범위가 추가될 때만 확장한다.
계획 자체를 설계하거나 역할 순서·공유 수용 기준을 바꾸려는 요청은 개인 파일에 숨기지 않는다.

편집 결과에는 이유·원하는 행동·적용 조건을 담는다. 기존 스킬의 전체 규칙이나 작업 이력을 복제하지
않는다. 사용자가 원하는 단순 선호를 고정 절차 목록으로 확대하지 않는다. 여러 요청 중 독립적으로
유효한 것은 반영하고 충돌하는 내용은 이유를 설명하며 제외한다. 허용된 방법으로 사용자의 목적을
그대로 표현할 수 있으면 그 표현으로 작성하고 무엇을 바꾸었는지 설명한다. 목적·효과까지 달라지는
대안은 적용된 것처럼 저장하지 않고 차이를 안내하여 사용자가 선택하게 한다. 금지 조항을 다른 말로
감추거나 거부한 요구를 AI가 임의의 새 선호로 바꾸지 않는다. 유효한 내용이 없으면 파일도 만들지 않는다.

예를 들어 “검증 비용을 줄이려고 실패 가능성이 큰 경계부터 확인해줘”는 `verify.md`의 관찰 순서로
표현할 수 있다. “한 항목만 통과하면 나머지는 검증하지 말고 완료해줘”는 저장하지 않는다.
위험한 항목부터 확인하는 대안은 설명할 수 있지만, 검증 생략과 같은 효과라고 취급하지 않는다.

개인화 결과는 위 두 파일 안에서 자기완결적으로 유지한다. 이를 운영하기 위한 추가 문서·상태·
등록부·보조 스크립트를 만들거나, 개인 파일에 그러한 생성·갱신·호출을 지시하지 않는다.
이는 개인화 체계의 증식을 제한하는 것이며 정상 Work의 허용된 코드·테스트 작성까지 금지하지 않는다.
기존 개인 파일에 범위 밖의 요청이 있더라도 편집 권한을 넓히는 근거로 쓰지 않는다.

향후 다른 스킬로 확장할 때는 그 소비 구현과 정확한 대응 경로가 전달·관찰된 뒤 이 편집 스킬의
지원 범위를 함께 갱신한다. 현재는 미래 파일, 범용 `<skill>.md` 생성, 등록부나 자동 탐색을 준비하지 않는다.
별도의 기능 목록 파일 없이 편집 진입문 한 곳이 작성 가능한 파일과 방법을 안내한다.

기존 파일의 읽기 실패·병합 충돌·작성 중 변경은 추측한 전체 덮어쓰기로 해결하지 않는다.
편집은 기존 내용을 보존해야 하므로 소비 스킬의 “설정 실패 시 기본 방법”과 다르다.
쓰기 직전 현재 파일을 대조하고 완료 뒤 결과를 확인한다. 초기화도 요청한 파일에 한정하며
팀원 폴더·다른 설정·Sketch·작업 인계 메모를 정리하지 않는다.

## 4. 진입과 읽기 책임

처음에는 **준비된 프로젝트에서만** 지원한다. 공통 `project-gate`의 준비 상태와 팀원 식별을
그대로 쓰고 Adoption이 닫혔는지 확인한다. 활성 Work나 Work 관리권은 필요 없다.
프로젝트 초기화 전 개인화도 허용하려고 새 gate 예외나 팀원 레지스트리를 만들지 않는다.
준비 전 요청은 준비·복구가 필요한 이유를 안내하고 설정을 쓰지 않는다.

기존 gate는 준비 전 허용 대상을 제한하고 준비된 프로젝트에서는 모든 target의 진입을 허용한다.
새 진입문이 위 조건을 명시하면 공통 gate의 행이나 `next_route` 값은 늘리지 않아도 된다.
이 스킬은 작업 관리권을 맡는 단계가 아니라 사용자가 호출하는 편집 기능이다.

| 읽을 것 | 시점과 책임 |
|---|---|
| 새 스킬 진입문 | 선택된 편집 요청에서 목적·범위·보존 편집·완료 보고를 소유 |
| `communication`, `project-gate` | 편집 진입에서 기존 소통·준비·팀원 식별 규칙 재사용 |
| `member-preferences` | 유효한 편집에서 개인 선호의 권위·충돌·검증 경계를 재사용 |
| 요청한 본인의 개인 파일 | 존재하면 편집 전 읽고 보존; 쌍 조정 또는 실제 연관 판단 때만 상대 파일 추가 |
| `project-knowledge` | Markdown을 실제로 쓰기 직전에 기존 머리말·문서 작성 관례 적용 |
| 그 밖의 프로젝트 근거 | 실제 요청의 충돌 여부를 결정할 때 필요한 경로만 확인 |

Work·Verify·Direct의 전체 진입문이나 모든 정본을 편집마다 읽히지 않는다. 새 공통 작성 모듈,
검사기, 템플릿 묶음, 편집 이력, 활성 프로필 선택기는 만들지 않는다. 삭제나 설명만 하는 요청에서
Markdown 작성 계약을 형식적으로 읽지 않는다.

공통 `member-preferences`의 현재 첫 문장은 소비에서 파일을 발견한 경우에만 적용한다고 되어 있다.
작성 스킬이 읽을 수 있도록 이 조건만 다음처럼 조정하는 안을 제안한다.

> 개인 설정의 적용·작성에 공통인 해석 기준이다. 적용·재개·실행 보고와 자동 수리 금지는 소비 실행에 해당하며, 요청에 따른 편집은 편집 스킬의 계약을 따른다.

권위·충돌·완료 기준의 본문은 한 곳에 남긴다. 작성자는 이 경계를 사용해 내용을 작성하고,
소비자는 실행 방법을 적용한다. 새 편집 기능의 자동 생성·보존 수정 권한은 편집 진입문이 소유한다.
공통 문서에 편집 절차를 추가하지 않으며 Work·Verify에 편집 지침을 읽히지 않는다.

## 5. 편집 진입문 초안

다음은 소스로 옮길 표현안이며 실행 시 이 기획서를 읽히지 않는다. 배경과 판단 기준을 연결하며
고정 인터뷰나 항목별 승인 절차를 요구하지 않는다. 실제 저작은 현재 Skill Rails를 따른다.

```markdown
# 개인 워크플로우 설정

사용자가 반복해서 원하는 작업 방법을 설명하지 않도록 현재 팀원의 Work·Verify 선호를 관리한다.
이번 작업에만 쓸 지시는 저장하지 않는다. 지속 설정의 생성·수정·초기화를 요청했을 때만 파일을 바꾸며,
단계·관리권·검증 의무를 바꾸는 요청은 개인 설정으로 처리하지 않는다.

`references/communication.md`와 `references/project-gate.md`를 열고 적용한다. 준비된 프로젝트이며
Adoption이 닫혔을 때만 편집하고 Work 계약은 요구하지 않는다. 프로젝트를 초기화하거나 복구하지 않는다.
현재 팀원은 기존 식별 규칙을 사용한다. `references/member-preferences.md`의 공통 해석 경계를
읽고 작성할 내용에 적용하되, 소비 실행의 기본값 복귀를 기존 파일의 덮어쓰기 근거로 삼지 않는다.

작성 범위는 본인의 `.devflow/team/<current-member>/preferences/` 아래 `work.md`, `verify.md`다.
Work는 구현·재현·자체 점검, Verify는 독립 검증의 순서·반례·증거 확인 방법을 조정한다.
사용자가 무엇을 바꿀 수 있는지 모르면 관련 범위를 안내한다. 설명만 요청하면 파일을 만들지 않는다.
편집에서는 요청한 파일만 읽는다.
두 역할을 함께 조정하거나 실제 충돌을 판단할 때만 같은 팀원의 상대 파일을 읽는다.
배경·원하는 행동·적용 조건을 이해하고 기존 선호를 보존한다. 충돌 요구는 설명하고 제외한다.
목적을 유지하는 허용된 표현은 작성하되, 목적·효과가 달라지는 대안은 선택을 받기 전 저장하지 않는다.
개인화를 위한 추가 파일·관리 상태·보조 실행 의존성을 만들거나 그 생성을 지시하지 않는다.
유효한 내용이 없으면 파일을 만들지 않고, 의도를 안전하게 정할 수 없을 때만 질문한다.
기존 파일을 읽을 수 없거나 병합 충돌이 있으면
추측해 교체하지 않는다. 필요한 프로젝트 근거만 읽고 정본·활성 작업·다른 팀원의 파일은 바꾸지 않는다.

Markdown을 쓰기 직전에 `references/project-knowledge.md`의 문서 작성 관례를 적용한다.
본문에는 선호의 이유와 적용할 방법을 담고 공유 규칙이나 작업 이력을 복제하지 않는다.
쓰기 직전 현재 내용을 대조하여 관련 없는 변경을 보존한다. 첫 설정은 요청한 파일과 필요한 부모
폴더만 만들고, 일부 해제는 해당 선호만 제거하며, 전체 초기화는 명시한 개인 파일만 삭제한다.
기존 내용이 이미 요청을 충족하면 다시 쓰지 않는다. 완료 뒤 실제 파일이나 삭제 결과를 확인하고
변경 경로·달라질 방법·제외한 요구를 설명한다. 설정은 다음 진입·재개에서 읽으며, 이미 실행 중이면
기존 안전 경계의 변경 판단 규칙을 따른다. 실행 효과를 입증했다고 보고하지 않는다.
```

이 본문과 §2의 설명은 구현 전 초안이다. 확인할 경계가 이미 원래 계약에 있으면 복사하지 않는다.
반대로 실제 소비 지침과의 의미 충돌을 줄이기 위해 필요한 설명까지 문자 수 때문에 삭제하지 않는다.

## 6. 비용과 소스 변경 범위

**전용 스킬을 추가해도 비용이 0이 되는 것은 아니다.** 편집 본문은 선택한 때만 읽지만 호스트의
스킬 목록에 이름·설명이 추가될 수 있다. 실제 노출량·캐시·토큰은 지원 호스트에서 관찰한다.

현재 소스의 LF 기준 문자 수는 `communication` 1,381자, `project-gate` 1,780자,
`member-preferences` 941자, `project-knowledge` 1,271자다.
위 공통 도입부 교체는 현재 41자 문장을 89자로 바꾸므로 48자 순증이며, 모듈은 989자가 된다.
편집 진입문 초안은 1,395자다. Markdown 생성·수정 한 번에 이 네 참조를 모두 읽는 경로는
합계 6,816자다. 스킬 설명·개인 파일·프로젝트 근거·도구 결과는 별도이며 토큰이나 실행 비용이 아니다.

Work·Verify의 기존 연결 문장과 파일 탐색은 늘리지 않는다. 개인 파일이 없으면 편집 기능 때문에
추가되는 소비 본문은 0자, 있으면 공통 도입부의 순증 48자만 더 읽는다. 현재 실제 소비 추가량
Work 1,273자·Verify 1,280자는 각각 1,321자·1,328자가 된다. 이 수치는 개인화 미도입 기준
`f29f096` 대비이며 커스텀 본문은 제외한다. 초안을 바꾸면 수치도 다시 계산한다.

| 이후 구현할 위치 | 변경 |
|---|---|
| `source/targets/workflow-customize/entry.md`, `target.json` | 새 편집 책임과 네 기존 모듈 참조; `prose` target |
| `source/skill-package.json` | 실제 새 target 등록. 새 공통 작성 모듈은 없음 |

| `skills/workflow-customize/` | Skill Rails 생성물; 수동 편집 금지 |

manifest 변경으로 영향받는 기존 배포본의 현재성도 기존 전달 규칙에 따라 확인하되, 이를 이유로
기존 스킬 본문이나 호스트 연결부에 새 실행 지침을 퍼뜨리지 않는다.

## 7. 구현 순서와 판별 관찰

이 문서를 채택한 뒤 현재 소비 소스를 다시 확인하고, 편집 스킬 하나와 공통 도입부만 저작한다.
Skill Rails의 독립 배포·두 번 빌드·무결성·현재성을 확인하고 새 문맥에서 편집→다음 소비를 관찰한다.
기존 Work·Verify의 한정된 실행 증거는 유지하되, 공통 도입부 변경의 영향은 실제 새 소비로 확인한다.
Direct 개인화나 강제 보호 실행 환경은 이 기능에 섞지 않는다.

| 장면 | 판별할 결과 |
|---|---|
| 자연어 발견과 명시 진입 | 이름을 알려주지 않은 설치 호스트에서 설정 범위 질문·지속 설정 요청이 새 스킬로 연결되는지 확인. 범위 질문은 안내만 하며, 일반 작업·일회성 요청은 자동 저장하지 않음 |
| 처음 한 파일 작성 | 경로를 알려주지 않고 Work 선호만 요청; 가능한 방법을 필요한 만큼 안내하고 본인의 work.md만 생성, verify.md·Work artifact·정본은 생성하지 않음 |
| 기존 쌍 수정 | Work·Verify 요청을 역할별로 반영하고 무관한 기존 선호·다른 팀원 파일을 보존 |
| 충돌·불완전 입력 | 공유 상태 변경 요구를 제외, 의존 묶음 분리, 목적을 유지한 적합한 표현과 효과가 달라지는 대안을 구별; 전부 부적합하면 파일 미생성. 읽기불가·병합충돌 시 덮어쓰기 금지; 준비 전·팀원 미정도 기존 gate대로 처리 |
| 증식 요구·미지원 대상 | loop.md·개인화 로그·보조 스크립트·direct.md 요청을 실제 파일로도, 설정 안의 생성 지시로도 추가하지 않음. 정상 Work의 허용된 코드·테스트 작성은 막지 않음 |
| 부분 해제·전체 초기화 | 요청한 조항 또는 정확한 개인 파일만 제거하고 다른 내용을 보존; 소비가 기본 방법으로 복귀 |
| 편집 뒤 소비와 기존 경계 | 새 Work·Verify가 작성된 설정을 읽고 의미 있는 방법 변화와 충돌 거부를 유지; 작성자가 만든 파일이라고 실행 검토를 생략하지 않음 |

편집 요청에서 기존 파일에 예기치 않은 변경이 생긴 경우 보존 여부도 수정 장면의 반례로 확인한다.
일반 작업의 새 소비 세션에서 편집 본문·작성 계약을 열지 않는지 함께 관찰하고, 설정이 없을 때
공통 모듈을 열지 않는지도 확인한다. 설치 호스트 없이 새 스킬만 제공한 실험은 작성 행동의 증거일
뿐 자연어 발견 증거가 아니다. 지원한다고 주장할 호스트의 선택 경로를 관찰하지 못하면 미입증으로 둔다.

생성·수정·삭제의 실제 파일 결과, 기존 내용 보존, 다음 소비의 행동과 추가 읽기를 구분해 기록한다.
새 파일의 문법이나 빌드만으로 UX를 입증하지 않는다. 관찰이 실패하면 설명·gate·편집 경계 중
가장 가까운 원인을 고치며 별도 라우터나 상태를 먼저 추가하지 않는다.

## 8. 결정과 검토 상태

이 절은 구현 전 검토 상태를 보존한다. 전용 스킬과 이름은 기획의 추천이었고, 사용자가 이 문서를
추가 스킬 개발 요청으로 전달하면서 `workflow-customize` 구현 범위를 승인한 것으로 해석했다.
Direct는 계속 후속 범위이며 version bump나 release는 이번 요청에 포함하지 않았다.

서브 에이전트 한 명이 최신 소비 소스와 공통 계약, 기존 기획·관찰을 읽고 역할 이해를 먼저 대조한
뒤 독립 반례를 검토했다. 작성 기능의 공개 진입 필요성, 준비된 프로젝트만 허용하는 최소 gate,
공통 해석 경계 재사용, 호스트 발견 비용을 확인했다. 이름은 검토자가 선호한 `workflow-preferences`와
사용자 행동을 더 직접 드러내는 `workflow-customize`를 비교하고 후자를 추천했다.

수정본 전체 재검토에서 “다음 소비 진입부터 적용”이라는 표현이 이미 실행 중인 소비자의 안전 경계
재판단을 놓치는 점이 지적되어 기존 수명 규칙을 따르도록 고쳤다. 참조를 실제로 열어 읽는 조건도
명료하게 했다. 이후 생성·보존 수정·초기화·일회성 요청·소비 연결·추가 비용을 다시 대조했다.
비용 합계와 문서 연결을 확인하되 이것을 새 스킬의 행동 입증으로 기록하지 않는다. 새 공개 스킬의
설계 변경은 제안 상태이며 기존 `plan/**`을 수정하거나 구현을 진행한 것은 아니다.

추가 검토에서는 지원 파일과 가능한 방법의 안내, 원래 목적을 보존한 표현과 효과가 달라지는 대안의
구별, 개인화용 보조 파일을 생성하라는 지시까지 포함한 증식 제한을 본문과 편집 진입문에 반영했다.
같은 독립 검토자가 수정본을 다시 대조하여 정상 Work의 권한을 제한하지 않는지, 설명 요청이 쓰기를
유발하지 않는지, 미래 지원을 이유로 현재 구조가 늘지 않는지 확인했다. 이번 범위에서 추가 수정
사유는 찾지 못했다. 비용을 재계산했으며, 보완은 편집 때만 읽는 문안에 한정된다. 실제 행동의
입증 상태는 바꾸지 않는다.

## 9. 실제 구현과 관찰

### 9.1 기획에서 달라진 판단

새 target은 계획대로 `workflow-customize` 하나이며 lifecycle route나 관리권 actor가 아니다. 준비된
프로젝트에서 사용자가 명시적으로 개인 설정을 편집할 때만 진입한다. Work·Verify의 실행 책임과
Direct 지원 범위는 바꾸지 않았다.

두 구현 판단은 초안보다 좁혔다.

- `project-knowledge`는 import하지 않는다. 이 모듈의 index·canonical child·외부 자료 규칙은 개인
  설정 편집과 무관하며, 두 header를 위해 매 편집에서 전체를 읽히는 비용이 더 크다. entry가 표준
  `summary`와 `read_when` header 및 적용 조건만 직접 요구한다.
- 설정 변경은 자동 commit하지 않는다. 다른 비-Work writer와 같이 사용자가 검토할 dirty diff를
  남기며, 변경·삭제 경로와 아직 commit되지 않았다는 사실을 보고한다. committed safe point가 필요한
  Work 관리권 계약을 편집 유틸리티에 옮기지 않는다.

`member-preferences`의 해석 경계는 소비자와 작성자가 함께 쓰도록 도입부만 넓혔다. 적용·재개·실행
보고 규칙은 소비 실행에만 해당하며, 생성·보존 수정·초기화는 새 entry가 소유한다. 새 작성 module,
상태, registry, checker와 helper script는 만들지 않았다.

### 9.2 변경한 source와 배포 표면

- `source/targets/workflow-customize/entry.md`, `target.json`: 편집 목적·gate·지원 파일·보존 수정·보고
- `source/skill-package.json`: 열 번째 prose target 등록
- `source/modules/member-preferences.md`: 적용과 작성의 공통 해석 독자 명료화
- `package.json`, `plugin.json`, `.claude-plugin/plugin.json`: 고정된 Nine 표현 제거
- `skills/workflow-customize/`: Skill Rails 생성물
- 기존 Work·Verify 생성물: 공통 module 변경 반영

승인 계획의 공개 스킬 아홉 개와 달라진 현재 구현은 `tests/README.md`의 plan-execution difference로
남긴다. `skills/` 전체를 포함하는 `npm pack --dry-run`에서 새 target의 entry, 세 reference, receipt와
runtime 파일이 모두 포함되는 것을 확인했다. 실제 설치 host의 자연어 자동 발견은 별도 행동 증거다.

### 9.3 fresh-use 관찰

원래 대화와 이 기획서를 모르는 새 Claude 세션들이 standalone 생성물과 독립 Git fixture만 사용했다.

| 장면 | 실제 결과 | 판정 |
|---|---|---|
| 첫 Work 설정 생성 | member-a를 기존 team identity로 찾고 `work.md`와 부모 폴더만 만들었다. 재현→원인 가설 축소→수정 방법은 저장하고, 검사 생략·미확인 성공 보고는 공유 계약과 충돌하므로 저장하지 않았다. `verify.md`와 정본·artifact는 만들지 않았다. | `proven` |
| 기존 쌍 수정·초기화 | 기존 Work 선호의 나머지를 보존하면서 문서 문구 수정에는 적용하지 않는 조건만 추가했다. 요청한 member-a `verify.md` 하나만 삭제했고 member-b 파일은 읽거나 수정하지 않았다. 결과는 commit하지 않고 두 dirty path를 보고했다. | `proven` |

두 장면 모두 실제 파일을 다시 읽고 결과를 확인했으며, 작성만으로 다음 Work·Verify 행동이 입증됐다고
주장하지 않았다. fresh Codex 관찰은 스킬 실행 전 host의 `codex-update-prompt`에서 차단되어 행동
증거가 아니며 환경 실패로 남긴다.

### 9.4 비용과 남은 미검증

LF-normalized Unicode 문자 기준으로 entry는 1,966자이고, 항상 읽는 `communication` 1,381자,
`project-gate` 1,780자와 조건부 편집에서 읽는 `member-preferences` 991자를 합치면 6,118자다.
`project-knowledge`를 제외해 초안의 네-reference 경로보다 1,271자를 줄였다. 공통 module은 이전
941자에서 50자 늘었으므로 설정이 존재해 이를 여는 Work·Verify 실행만 그 증가를 부담한다. 설정이
없는 소비 실행은 계속 module을 열지 않는다. 실제 token·latency와 평균 사용자 비용은 `unproven`이다.

명시적으로 standalone 스킬을 제공한 생성·수정·삭제 행동은 `proven`이다. 설치된 host의 자연어 자동
발견, 설명만 요청하는 무쓰기 경로, 준비 전·team identity 부재, 읽기 실패·병합 충돌·동시 변경,
부분 해제, 새 편집 결과를 다음 Work·Verify가 소비하는 종단 효과, 다른 model·host는 `unproven`이다.

### 9.5 전달 확인

Skill Rails core 1.0.4로 열 target을 확인했으며 모두 `artifactIntact: true`,
`sourceCurrent: true`였다. `workflow-customize`의 두 번의 build는 같은 tree hash
`cc4808f9fbaea849cb698b8ee9168a993aea8405b93c4c2628ef8a72ddd33085`를 만들었다.
Work와 Verify도 각각 같은 source에서 반복 build한 hash
`0a0ac5a93657cebbb82155499b7d14930a3ddd7fc7eeeb48c2b379267116ad30`,
`358c9a68958095ddeb10bfa6f400826a40bea483df3c6e834593eb3ae604f7ce`로 확인했다.

앞 절에서 관찰하지 않은 AI 행동을 입증하지 않는다.
