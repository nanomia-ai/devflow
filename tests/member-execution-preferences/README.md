# 팀원의 실행 방법 개인화 기획

현재 Work·Verify 소비 구현과 실제 관찰은 §13을 기준으로 읽는다. 아래의 초기 기획은 그 배경을
보존한다. 선택 사항이었던 작성 지원을 기본 제공으로 구현한 범위·이름·비용과 남은 미검증은
[개인 워크플로우 편집 스킬](workflow-customize-plan.md)에 있다.

## 1. 목적과 이번 문서의 범위

팀원마다 결함을 재현하는 순서, 구현 중 주의를 기울이는 관점, 검증에서 찾는 반례가 다르다. 이런
선호를 매 대화에서 다시 설명하게 하면 누락과 반복 비용이 생긴다. 반대로 개인 지침이 작업 계약,
파일 배치 또는 완료 기준까지 바꾸면 다른 팀원이 같은 작업을 이어받을 수 없다.

이 기능은 **사람마다 다른 실행 방법과 팀이 공유하는 작업 의미를 함께 유지**하기 위한 것이다.
개인은 Work의 구현·자체 점검 방법과 Verify의 독립 검증 방법을 조정할 수 있다. 두 스킬은 계속
동일한 작업 계약을 사용하고 기존 정본에 결과를 남긴다. 개인 파일을 제거하거나 담당자가 바뀌어도
작업의 목적, 현재 상태, 증거와 다음 행동을 복구할 수 있어야 한다.

성공은 개인 설정을 읽었다는 보고가 아니다. 설정이 의도한 방법이 실제 실행에 나타나고, 실패 후
수정·재검증·인계·종료에서도 공유 체계가 보존되며, 사용자가 같은 선호를 반복 설명하지 않는 것이다.
이 기능의 행동과 효과는 아직 `unproven`이다.

이 문서는 처음에는 구현 전 기획서로 작성되었다. 이후 사용자의 적용 요청으로 §11의 채택 범위를
확정하고 Work·Verify 소스와 생성물을 갱신했으며, 실제 구현·관찰 결과는 §13에 이어 기록한다.
`plan/**`과 실행 환경 설정은 수정하지 않았다. 사용자의 “파일 체계는 절대 무너지면 안 된다”를
자연어 지침만으로 기술적으로 보장했다고 해석하지 않는다. §8이 금지 계약과 실행 환경의 강제 보호를 구분한다.

### 1.1 처음 맡는 AI가 읽을 순서

먼저 이 절에서 목적과 기획 범위를 확인하고, §11에서 아직 결정되지 않은 보호 수준과 채택 범위를 확인한다.
그 뒤 §2의 원문으로 현재 책임을 이해하고, §3–8에서 제안의 이유와 경계를 읽는다. 실제 구현 요청을 받은
경우에만 §9의 변경 위치·문안·전달 순서를 따른다. §10은 구현 뒤 실행할 관찰 계획이며 지금 통과한 결과가 아니다.

여기서 `prose` 스킬은 AI가 자연어 지침을 읽고 실행하는 방식이다. `proven`은 실행으로 입증,
`failed`는 실행에서 실패, `unproven`은 미입증을 뜻한다. 영어 경로·필드·스킬 이름은 실제 소스와
대응시키기 위해 유지하며 설명은 한국어로 작성한다.

## 2. 현재 구현에서 출발하는 이유

### 2.1 문서·역할·저작의 실제 경계

다음은 새 제안이 아니라 현재 소스에서 확인한 전제다. 구현 시 관련 원문을 다시 읽고 달라진 전제가
있으면 이 계획을 기계적으로 적용하지 않는다.

| 현재 소유자 | 현재 책임과 이번 기능에 주는 제약 |
|---|---|
| [소스 패키지](../../source/skill-package.json) | 아홉 스킬과 공통 모듈의 저작 관계를 선언한다. 현재 스킬은 모두 `prose`이며 Skill Rails가 프로젝트의 실행을 통제하지 않는다. |
| [project-gate](../../source/modules/project-gate.md) | 진입 조건, 다음 역할 용어, `git config user.name` 기반 현재 팀원 해석을 소유한다. 개인 설정이 진입 자격이나 팀원 식별을 재정의하지 않는다. |
| [Direct 진입문](../../source/targets/direct/entry.md), [추적 작업 계약](../../source/targets/direct/tracked-contract.md) | 지속 여부, 결과 단위, 실행 계약과 계약 변경을 결정한다. 상위 질문이 생긴 활성 Work의 관리권도 Direct가 유지한다. |
| [Work 진입문](../../source/targets/work/entry.md) | 추적 작업 또는 대화 안에서 끝나는 작업 입력을 구현하고 안전 지점을 만든다. 계약·판정을 작성하거나 수정하지 않으며, 기존 종료 자격을 충족한 뒤 작업 산출물을 정리한다. |
| [Verify 진입문](../../source/targets/verify/entry.md) | 유효한 추적 작업의 검증 항목을 독립적으로 실행한다. 증거를 먼저 공개하고 작업 상태를 나중에 쓴다. 실패를 직접 수리하지 않는다. |
| [work-state](../../source/modules/work-state.md) | `spec.md`는 실행 계약, Git은 실제 파일 내용, `state.md`는 현재 좌표·관리권을 소유한다. 작업 계약조차 작업 상태·증거·정본 반영·종료의 소유권을 바꿀 수 없다. |
| [Work 종료 규칙](../../source/targets/work/closure.md) | 모든 필수 검증 항목이 입증되었고 종료 조건에 도달한 뒤 후보 판단, 정본 반영 확인, 검토 요약, 임시 파일 삭제를 수행한다. |
| [team-context](../../source/modules/team-context.md) | 선택한 Work 또는 Adoption의 임시 인계 메모만 다룬다. 메모는 공유 사실의 정본이 아니며 작업 종료 시 삭제된다. |
| [Sketch 진입문](../../source/targets/sketch/entry.md), [인계](../../source/modules/sketch-handoff.md) | 현재 팀원의 개인 탐구에서 확정된 결론만 정본으로 옮긴다. `next_route`가 팀원을 바꾸지는 않는다. |
| [Resume 진입문](../../source/targets/resume/entry.md) | 현재 작업 상태와 Git을 읽어 다음 역할을 보고한다. 실행 방법을 선택하거나 파일을 수리하지 않는다. |

Product는 목적·업무 의미, Architecture는 기술 경계·검증 관찰 수단, Design은 적용되는 경험 원칙,
Adopt는 기존 프로젝트 지식 흡수를 맡는다. 개인 실행 설정은 이 판단들을 대신하지 않는다. Work 종료도
[project-knowledge](../../source/modules/project-knowledge.md)와 해당 문서 계약을 따라 확인된 사실을
기존 정본 위치에 통합할 뿐이다. 개인 취향은 자동으로 장기 지식 후보나 팀의 공유 결정이 되지 않는다.

현재 소스 관계도에는 개인 실행 설정을 찾거나 적용하는 계약이 없다. 이번 작업은 기존 기능의
오류 수정이 아니라 새로운 입력과 그 해석 경계를 추가하는 제안이다.

### 2.2 기존 계획과 관찰을 읽는 법

[plan/02](../../plan/02-skill-and-document-architecture.md)의 단일 정본·역할 경계,
[plan/08](../../plan/08-document-contracts.md)의 문서·인계 계약,
[plan/04](../../plan/04-delivery-and-validation.md)의 스킬별 전달·새 문맥의 실제 사용 순서를 보존한다.
승인 기준선은 `team`을 임시 맥락으로 설명하지만 현재 Sketch는 팀원 아래에 있다. 그 차이는
[검증 자료 안내](../README.md)에 이미 기록되어 있다. 이 제안은 추가로 **작업 종료와 무관하게 유지되는
개인 선호**를 팀원 아래에 두므로 새로운 수명 확장임을 명시한다. 기존 수명과 같다고 간주하지 않는다.

[팀 인계 관찰](../team-handoff/README.md)은 제한된 장면에서 공유 작업 상태와 개인 맥락의 분리 및 정리를
확인했다. 현재와 다른 Sketch 저장 형태에 대한 과거 관찰을 현재 전체 동작의 증거로 옮기지 않는다.
[전체 여정 관찰](../whole-journey/README.md)은 성공 흐름과 종료 수리를 기록하지만, 그 동일 시험용 프로젝트의
Verify 실패 → Work 수정 → 재검증은 `unproven`이다. 이번 기능에서는 그 순환을 직접 관찰해야 한다.

[반복 실행 문맥 최적화](../repeated-execution-context-optimization/README.md)는 Work 종료와 Direct
추적 작업 상세를 조건부로 읽도록 분리했다. 이번 기능 때문에 그 상세를 모든 실행에 다시 읽히지 않는다.
[질문·탐구 관점 계획](../inquiry-lenses-and-question-dialogue/README.md)처럼 목적과 행동의 관계를
전달하되, 배경 설명을 새 의식이나 고정 사고 순서로 만들지 않는다.

## 3. 최소 구조와 채택 이유

제안하는 기본 구현은 **개인 파일 + 공통 해석 모듈 하나 + 각 소비 진입문의 짧은 연결**이다.
Work·Verify를 먼저 완성하고, Direct는 §7의 좁은 범위로 후속 적용한다.

| 대안 | 판단과 이유 |
|---|---|
| 매번 대화로 선호 전달 | 저장 구조는 없지만 반복 설명과 재개 시 누락이라는 사용자 문제를 해결하지 못한다. |
| 기존 `team/<member>/<work-id>.md`에 선호 저장 | 작업별 복제와 종료 시 유실을 만든다. 임시 인계와 지속 선호의 수명이 다르므로 사용하지 않는다. |
| 개인별 스킬 복제·재빌드 | 공통 규칙의 사본이 갈라지고 업데이트·보호 경계를 유지하기 어렵다. 채택하지 않는다. |
| 스킬별 개인 파일을 읽는 공통 규칙 | 현재 자연어 지침 실행과 맞고 직접 편집도 가능하다. 기본안으로 제안한다. |
| 작성 지원 스킬만 제공 | 사후 직접 편집이나 규칙 변경을 방어하지 못한다. 실행 시 해석 규칙의 대체물이 될 수 없다. |
| 범용 설정 엔진·상속·자동 호출 장치·파일 생성기 | 현재 요구를 넘어선 비용이며 일반 쓰기를 통제하지 않으면 강제 보호도 아니다. 기본안에 넣지 않는다. |

새 전역 상태, 개인 설정 등록부, 활성 개인 설정 선택기, `loop.md`, 프로젝트 공통 개인 선호 계층,
개인별 빌드본은 만들지 않는다. Work·Verify가 연결되는 곳은 계속 공유 작업 계약·작업 상태·검증 기록이다.
개인화만을 위해 `.devflow/index.md`를 고치거나 설정 파일을 활성 작업 산출물 목록에 넣지 않는다.

### 3.1 결과 프로젝트의 경로와 수명

```text
.devflow/team/<current-member>/
  preferences/
    work.md
    verify.md
    direct.md                 # Direct 지원을 채택·구현한 뒤에만
  sketches/<sketch-id>/       # 기존 개인 탐구; 별도 수명
  <work-id>.md                # 기존 임시 Work 인계 메모
  adoption.md                # 기존 임시 Adoption 인계 메모
```

파일은 사용할 때만 작성한다. 존재하지 않는 파일·폴더를 실행 중 자동 생성하지 않는다. 하나만 있어도
해당 스킬만 개인화된다. `preferences`는 해당 팀원의 선호를 소유하지만 프로젝트 사실·작업 상태의
정본은 아니다. 파일명으로 스킬을 대응시키며 `skill`, `enabled`, `version` 같은 중복 필드를 만들지 않는다.

기본 제안은 저장소에서 관리하는 개인 설정이다. 다른 팀원이 읽을 수 있는 저장소이므로 비밀
보장을 뜻하지 않는다. 사용자 홈 디렉터리의 전역 설정, `.gitignore` 자동 변경, 동기화·이전 처리는 포함하지 않는다.
이 저장 정책은 §11에서 사용자가 변경할 수 있는 제품 선택이다.

Work 종료와 작업 폐기는 해당 `.devflow/work/<work-id>/` 및 정확히 대응하는
`.devflow/team/*/<work-id>.md`만 정리한다. `preferences/`, 다른 작업의 메모, 개인 Sketch와 팀원
폴더 전체를 삭제하지 않는다. Adoption의 `team/*/adoption.md` 정리도 이 설정과 겹치지 않는다.
설정 자체의 수정·삭제는 사용자가 요청한 설정 관리 행동이며 일반 Work·Verify 실행의 부수 효과가 아니다.

### 3.2 개인 파일이 설명할 내용

기존 Markdown 문서 관례인 `summary`, `read_when`을 사용한다. 본문은 고정 양식보다 다음 의미를
자연스럽게 설명한다. 이를 새 기계적 형식 규칙이나 섹션 형식 검사기로 강제하지 않는다.

- 어떤 경험이나 부담 때문에 이 방법을 원하는가.
- 어떤 작업 조건에서 어떤 행동을 선호하는가.
- 잘 적용되었다면 실행에서 무엇이 달라지는가.
- 그 방법이 유효하지 않거나 기존 계약을 침해하는 경우의 한계는 무엇인가.

예를 들어 `work.md`는 다음처럼 작성할 수 있다. 이는 기본으로 모든 사용자에게 배포할 정책이 아니다.

```markdown
---
summary: 결함 수정에서 추측성 변경을 줄이기 위한 구현 선호
read_when:
  - 이 팀원의 Work가 결함을 수정할 때
---

원인을 확인하지 않고 여러 곳을 바꾸면 다음 실패에서 무엇이 달라졌는지 알기 어렵다.
재현 가능한 결함은 먼저 작은 재현 방법을 확인하고, 원인 가설을 좁힌 뒤 수정하는 것을 선호한다.
같은 원인이 다시 나타나면 변경을 늘리기 전에 이전 가설을 다시 살핀다.
재현할 수 없다면 재현한 것처럼 취급하지 않으며, 이 선호가 기존 작업 범위나 완료 기준을 바꾸지는 않는다.
```

`verify.md`는 “구현자의 가정을 그대로 반복하면 같은 결함을 놓칠 수 있으므로, 해당 검증 항목을
깨뜨릴 수 있는 경계 입력을 독립적으로 확인한다”처럼 검증의 이유와 행동을 연결할 수 있다.
개인 파일에 Devflow의 전체 규칙이나 두 스킬의 절차를 복사하지 않는다. 금지 규칙을 사용자가 빠뜨려도
소비 스킬의 공통 계약이 적용되어야 한다.

## 4. 발견·해석·적용의 실행 계약

### 4.1 진입문에서 개인 파일을 여는 시점

개인 지침은 유효한 작업 안에서만 의미가 있다. 각 스킬의 기존 소통 규칙, 프로젝트 진입 조건,
프로젝트 안내 문서와 필수 입력·관리권 확인을 먼저 수행한다. 그 뒤 **첫 구현·검증·계약 판단 전에** 개인화를 적용한다.
진입 조건 거절, 손상된 계약 복구 안내, 대상 선택 대기 중에는 설정을 탐색하지 않는다.

진입문은 자신의 정확한 후보 경로와 다음 조건을 소유한다.

1. `.devflow/team/`이 없으면 개인 파일도 없으므로 추가 탐색 없이 기본 동작을 한다.
2. `team/`이 있으면 이미 확인한 현재 팀원을 재사용하거나 `project-gate`의 기존 팀원 식별 규칙으로
   해석한다. 이름이 없거나 안정적으로 해석할 수 없으면 그 규칙대로 짧은 팀원 이름을 요청한다.
   다른 팀원의 폴더명, 마지막 커밋 작성자, 터미널 식별자로 추측하지 않는다.
3. `.devflow/team/<current-member>/preferences/<현재 스킬>.md` 하나의 존재를 확인한다. 전체 `team/`이나
   개인 선호 폴더를 재귀 검색하지 않는다. 없으면 기본 동작을 하며 빈 파일을 만들지 않는다.
4. 있으면 `references/member-preferences.md`를 먼저 열고, 개인 파일을 읽어 현재 입력과 대조한다.
   설정의 본문을 읽어야 모듈 개봉 여부를 알 수 있는 조건은 만들지 않는다.

위 순서는 판단의 의존 관계이며 단계마다 별도 도구 호출을 요구하지 않는다. 현재 진입 과정에서
이미 확인했고 변경 징후가 없는 팀원 식별·경로 존재 정보는 재사용한다. 개인 파일은 읽을 때 빈 본문,
적용 조건과 실제 지침을 함께 판단한다. 내용 유무나 `read_when`만 확인하려고 먼저 읽고 다시 본문을
읽는 별도 단계를 만들지 않는다. 파일이 존재하지만 비어 있으면 공통 모듈 읽기 비용은 발생한다.
이는 개인 지침보다 해석 경계를 먼저 확보하는 선택이며, 이를 피하려고 별도 검사기를 추가하지 않는다.
새 진입·재개의 현재 설정 확인은 §4.3대로 유지한다.

`team/`이 존재하지만 팀원 식별 정보가 없는 경우에는 개인 파일이 없더라도 기존 팀원 식별 질문이 발생할 수 있다.
이를 감추고 “모든 무설정 실행에서 비용·질문이 0”이라고 약속하지 않는다. §10에서 실제 부담을
관찰하며, 해결을 위해 다른 팀원의 설정을 뒤지거나 별도 팀원 식별 저장소를 먼저 만들지 않는다.

Work는 추적 작업 구현·수리뿐 아니라 유효한 대화 안에서 끝나는 작업 입력과 종료 진입에도 자신의 파일을 확인한다.
본문의 적용 조건에 맞는 내용만 쓰므로 구현 선호 때문에 종료에서 새 구현을 시작하지 않는다.
대화 안에서 끝나는 작업이라는 이유로 `work-state`나 `work-closure`를 추가로 열지 않는다. Verify는 기존처럼 유효한
추적 작업 Work에만 진입하며, `verify.md`가 있다고 대화 안에서 끝나는 작업을 독립 Verify로 바꾸지 않는다.

대화 안에서 끝나는 Work도 합의된 범위에서 확인한 사실을 기존 정본에 직접 반영할 수 있다.
그 쓰기 직전에만 기존 `project-knowledge`와 해당 문서 유형 계약을 읽으며, 개인화 때문에 추적 작업,
`pending landing` 기록이나 독립 Verify를 강제하지 않는다. 검증 뒤 채택한 `pending landing`을
요구하는 것은 추적 작업의 정본 반영 경로다. 새 의미·경계 결정이 필요하면 기존 Direct 인계를 따른다.

### 4.2 권위와 충돌을 판단하는 방법

개인 파일은 **허용된 실행 선택을 좁히는 입력**이다. 프로젝트 지식, 작업 계약, 작업 상태나 증거를 대신하는
상위 지시가 아니다. 기존 스킬의 책임·쓰기 범위·공통 계약, 현재 프로젝트 정본과 작업 계약을 만족하는
내용만 적용한다. 더 최근에 작성됐다는 이유로 권위가 올라가지 않는다. 현재 사용자의 명시 요청이
단순한 개인 선호를 바꾸면 그 요청을 따르되, 공유 계약 변경은 기존 의사결정 역할에서 처리한다.

적용 조건에 맞고 이 경계와 충돌하지 않는 개인 지침은 스킬의 기본적인 방법 선택보다 우선 적용한다.
“선호”라는 이름을 단순 참고나 임의 생략의 근거로 삼지 않는다. 기본 동작으로 돌아가는 것은 해당
파일이 없거나, 현재 조건에 맞지 않거나, 적용할 수 없는 이유가 있을 때이며 후자는 이유를 설명한다.

| 읽은 내용 또는 상태 | 해야 할 일과 결과 |
|---|---|
| 적용 조건에 맞는 실행 방법 | 현재 역할의 허용 범위 안에서 적용한다. |
| 무관한 조건의 선호, 비어 있는 본문 | 기본 동작을 계속한다. |
| 읽기 실패·해석 불가·병합 충돌 | 해당 설정을 적용하지 않았다고 알린다. 설정을 수리하거나 공유 상태를 새로 만들지 않는다. |
| 독립적으로 떼어낼 수 있는 금지 조항 | 해당 조항만 배제하고 나머지 유효한 내용은 적용한다. |
| 금지 조항에 의존하는 허용처럼 보이는 내용 | 의존하는 묶음을 함께 배제한다. 잘라낸 문장을 새 의도로 재해석하지 않는다. |
| 내부 모순이나 적용 범위를 정할 수 없는 내용 | 영향받는 부분을 적용하지 않고 기본 동작을 한다. 현재 행동을 실제로 결정할 수 없을 때만 질문한다. |
| 새 목표·수용 기준·허용 변경 범위·공유 정책을 요구 | 개인 파일만으로 채택하지 않는다. 현재 요청이나 실제 증거가 그 변경을 필요로 할 때 기존 Direct 인계로 보낸다. |
| 실제 계약·Git·관리권까지 불명확 | 개인화 기본 동작 복귀로 무시하지 않는다. 현재 스킬의 중단·복구 계약을 적용한다. |

따라서 선택적 설정을 못 읽는 것과 필수 작업 계약·작업 상태를 못 읽는 것은 다른 실패다. 설정의 존재만으로
작업을 차단하지 않지만, 유효한 작업 계약이 없는데 기본값으로 실행하지도 않는다.

권한·경로·역할을 바꾸라는 요구가 “작업 효율”, “반복 개선”, “개인 선호”로 표현되어 있어도 내용으로
판단한다. 파일에 실행 명령이나 링크가 있어도 자동 실행·연쇄 문서 포함·다른 스킬 호출의 권한을 주지
않는다. 현재 역할이 원래 허용하는 도구·읽기·쓰기 안에서만 방법으로 검토한다.

개인 설정의 `read_when`은 내용을 적용할 조건이지 공통 경계를 건너뛰는 조건이 아니다. 문서 머리말이 없다는
사실만으로 공유 프로젝트를 손상된 것으로 선언하지 않는다. 의미를 안전하게 판단할 수 없는 부분은
위 표대로 제외하고, 형식을 고치려면 별도 설정 편집 요청에서 다룬다.

### 4.3 적용의 수명과 사용자 피드백

각 스킬에 새로 진입하거나 중단 후 재개할 때 현재 파일을 다시 읽는다. 한 번의 실행 도중에는 읽은
내용을 사용하며, 매 도구 호출마다 감시하지 않는다. 실행 중 설정 변경을 알게 되면 진행 중 행동을
안전하게 마친 경계에서 다시 판단한다. 파일 수정 자체를 작업 AI 취소나 관리권 이전으로 해석하지 않는다.

기존 보고의 읽은 범위·근거에 실제 개인 파일 경로를 포함한다. 사용한 방법이 실행을 바꾼 경우에는
무엇을 적용했는지 짧게 설명하고, 충돌이나 읽기 실패가 있으면 제외한 내용과 이유를 알린다.
무설정 실행마다 “개인화 없음”을 출력하거나 모든 조항의 승인표를 만들지 않는다.

별도의 적용 결과 파일, 개인 설정 해시, 상태의 설정 참조, 승인 표시, 로그를 저장하지 않는다. 다음 담당 AI에
필요한 작업 사실은 원래 작업 계약·작업 상태·검증 기록이 소유한다. 이전 방법의 사용 여부가 증거 해석에
중요하면 Verify가 실제 관찰 수단·환경·관찰 방법을 기존 증거 안에 설명하며 개인 파일 참조로 대신하지 않는다.

## 5. 자유롭게 바꿀 방법과 고정할 체계

파일 체계 보존은 같은 폴더 이름을 유지하는 것보다 넓다. 의미·권한·수명·게시 순서가 바뀌어도
다음 담당 AI가 현재 상태를 오해하므로 보호 대상에 포함한다.

| 고정할 것 | 왜 고정하는가 | 개인화의 허용 경계 |
|---|---|---|
| 정본 위치와 사실을 소유하는 단일 문서 | 담당자가 바뀌어도 같은 현재 지식으로 판단해야 한다. | 관련 정본을 검토하는 관점은 조정할 수 있다. 사본을 새 정본으로 만들 수 없다. |
| 작업 계약의 목표·수용 기준·허용 변경 범위 | 개인 취향 때문에 공유 결과가 바뀌면 안 된다. | 그 범위 안의 코드 분리, 구현 순서, 테스트 기법을 고른다. |
| 작업 상태의 내용·관리권·안전 지점 | 대화 없이 다음 행동을 복구해야 한다. | 설명을 명료하게 할 수 있지만 필드·다음 역할·진행 로그를 추가하거나 미커밋 변경을 안전 지점으로 부르지 않는다. |
| Verify의 독립성·판정 의미 | 자기 구현에 유리한 판정이나 미실행 통과를 막는다. | 검증 항목별 관찰 방법·실행 순서를 조정한다. 검증 항목을 빼거나 증거 없이 입증됨으로 만들지 않는다. |
| 증거 먼저, 작업 상태 나중 | 중단 후 발표되지 않은 결과를 현재 결과로 오해하지 않아야 한다. | 개인 절차가 게시 순서를 바꾸지 않는다. |
| 사실 확인·정본 반영·종료 순서 | 작업 삭제로 유일한 장기 지식이나 검토 증거가 사라지지 않아야 한다. | 기존 종료 의무의 수행 방법만 조정한다. 종료 자격을 추가·삭제하지 않는다. |
| 관련 없는 파일 내용·다른 팀원의 설정 | 공동 저장소에서 한 작업의 권한이 다른 작업으로 번지면 안 된다. | 현재 작업이 허용한 실제 변경만 수행한다. |

금지 조항은 예외 승인 요청의 대상으로 바꾸지 않는다. 예를 들어 “검증 기록을 없애고 작업 상태에
통과만 쓴다”는 설정은 배제한다. Devflow 자체의 계약을 바꾸려는 별도 제품 요청은 이 개인화 기능
밖의 유지보수 결정이다.

**추가 점검과 새로운 완료 기준은 다르다.** Verify가 기존 검증 항목의 반례를 더 살피는 것은 허용된다.
개인 파일이 “항상 테스트 범위 95% 이상”, “모든 변경에 부하 시험”을 요구해도 현재 수용 기준이 아니면
숨은 필수 검증 항목으로 추가하지 않는다. 추가 관찰이 기존 검증 항목의 실제 위반을 드러내면
그 검증 항목의 실패를 기록한다. 검증 항목과 직접 연결되지 않는 정본 위반이나 새로운 요구의 필요성을
드러내면 현재 증거를 보존하고 기존 Direct 인계로 판단을 받는다. 새 검증 항목을 발명해 실패로 쓰지 않는다.
단순히 개인이 원하는 추가 도구를 쓸 수 없다는 이유만으로 입증된 검증 항목을 미검증으로 바꾸지 않는다.
반대로 기존 검증 항목을 입증할 관찰 수단 자체가 없으면 개인 설정과 무관하게 미검증이다.

## 6. Work–Verify를 한 쌍으로 사용하는 경험

Work는 구현·자체 점검을 하고, Verify는 수용 기준을 독립적으로 판단한다. Work의 선호와 Verify의
선호는 같은 팀 계약을 다른 방향에서 돕는다. 실행마다 상대 파일을 함께 읽고 두 설정의 합의문을
만들 필요는 없다. 각 실행은 자신의 파일 하나, 공유 작업 계약·작업 상태와 필요한 검증 기록을 읽는다.

```text
Direct: 현재 요청의 실행 계약
  → Work: 자신의 방법으로 구현·자체 점검, 안전 지점과 다음 행동 공개
  → Verify: 자신의 방법으로 독립 실행, 검증 항목의 증거와 실패 원인에 따른 다음 역할 공개
      구현 결함 → Work → Verify
      계약·상위 판단 문제 → Direct → 필요한 판단 → Work 또는 Verify
      종료 조건과 필수 검증 항목 충족 → Work: 정본 반영과 종료
```

개인 선호는 “실패하면 가설을 먼저 재검토한다”, “위험한 검증 항목부터 확인한다”처럼 반복 방법을
바꿀 수 있다. 승인된 범위 안에서 완료까지 자율적으로 반복할 수 있지만, 관리권·작업 범위·재시도 전제·
외부 결정을 무시하는 반복은 허용하지 않는다. 일정 횟수 뒤 자동 통과, 매 중간 구현의 강제 최종 Verify,
Verify 안에서 수정하고 같은 판정을 유지하는 방식도 허용하지 않는다. 같은 실패의 재시도에는 실제로
달라진 가설·입력·구현·검증법이 있어야 하며 그 판단에 필요한 근거는 기존 실패 증거를 사용한다.
별도 시도 횟수 기록이나 반복 상태는 추가하지 않는다.

점진 구체화의 성공한 중간 검토는 다음 관찰 가능한 작은 구현을 결정할 입력이며 Verify 실패가 아니다. Direct가 정한
위험 검증 항목 또는 종료 준비 조건에 도달했을 때 Verify로 간다. 설정 때문에 이 구분을 지우지 않는다.
이 기능은 자동 실행 조정자를 만들지 않는다. 다음 역할의 실행은 기존 사용자·실행 환경·외부 실행 조정 도구가
이어가며 각 역할은 이미 허용된 범위에서만 동작한다.

### 6.1 팀원이 바뀔 때

A가 구현하고 B가 검증하면 A의 `work.md`, B의 `verify.md`를 적용한다. 작업 산출물 생성자의 설정을
상속하지 않는다. 같은 팀원 아래의 여러 에이전트는 그 팀원의 같은 설정을 사용하며 에이전트별 개인 설정을
추가하지 않는다. 위임된 실행에서도 실제 팀원이 불명확하면 임의로 다른 사람의 설정을 선택하지 않는다.

다른 팀원의 해당 작업 인계 메모는 기존 정해진 범위의 탐색으로 읽을 수 있지만, 그 메모를 통해 다른
팀원의 개인 선호를 자동 참조 연결하지 않는다. 실제 실행에 필요한 환경 사실은 인계 메모 또는 기존
정본·계약에 있어야 하며, 개인 선호가 유일한 실행 의존성을 소유해서는 안 된다.

Resume은 개인 설정을 읽지 않고 원래 상태를 보고한다. 다음 Work·Verify가 자신의 진입에서 읽는다.
설정 삭제·변경만으로 과거 판정이 자동 무효화되지는 않는다. 실제 대상 파일 내용·환경·전제의 변경과
수용 기준의 계약 변경은 기존 증거 현재성 계약으로 판단한다. 설정이 없는 작업 AI나 플러그인이 없는 작업 AI도
공유 계약으로 올바른 결과를 만들어야 한다. 개인화가 적용됐다는 주장은 실제 그 입력을 읽은 실행에만 한다.

## 7. Direct와 작성 지원의 후속 범위

### 7.1 Direct도 지원하되 공유 계약을 만드는 권한과 구분한다

Direct는 작업 시작과 점진 구체화의 다음 관찰 가능한 작은 구현을 결정하므로 실행 경험에 관련된다. 지원 자체는 권한다.
다만 먼저 Work·Verify 조합의 실제 효과를 관찰한 뒤 별도 스킬 단계로 적용한다.

`direct.md`는 불확실한 가정부터 검토하기, 관찰 가능한 작은 구현을 선호하기, 대안을 운영 부담으로
비교하기 등 **계약을 구성하는 판단 방법**을 조정한다. 추적 작업의 세 질문, 결과의 독립 종료 기준,
현재 작업 계약의 관리권·계약 변경·검증 기록 무효화 규칙은 바꾸지 않는다. 개인 선호를 작업 계약의 `read_first`에
넣거나 그대로 필수 지시로 복사하지 않는다.

예를 들어 “화면을 보며 판단하는 편이 좋다”는 선호는 현재 요청과 정본이 허용하는 점진 구체화 제안에
반영할 수 있다. “모든 변경은 무조건 점진 구체화이고 매 관찰 가능한 작은 구현 승인을 받는다”는 설정은 현재 요구를 무시하는
강제 절차이므로 적용하지 않는다. 개인 선호와 무관하게 다음 담당 AI가 이해해야 하는 결정만 기존 권한으로
작업 계약에 자기완결적으로 게시한다.

Direct는 `direct.md`만 적용한다. Work·Verify 파일을 사전 병합하거나 개인의 추가 검사를 자동 수용 기준으로
올리지 않는다. 후속 스킬 진입에서도 개인 설정이 없는 기본 경로의 읽기 비용을 관찰한다.

### 7.2 선택적인 작성 지원 스킬

이 절은 초기 범위다. 사용자의 자연어 편집 진입을 구현한 현재 결과는
[후속 편집 스킬](workflow-customize-plan.md)을 따른다. 기존 소비 구현의 범위는 §13과 같다.

직접 Markdown을 작성·수정하는 경로를 기본으로 지원한다. 작성 지원은 같은 의미를 쉽게 표현하도록
돕는 선택 기능이며, 작성기가 만든 파일을 더 신뢰하거나 인증된 설정으로 취급하지 않는다.

Work·Verify의 소비 계약을 관찰한 뒤, 사용자가 자연어로 설명한 실행 선호를 두 파일로 구성하는
가칭 `personalize` 스킬을 별도로 채택할 수 있다. 첫 기능 출시의 필수 조건으로 만들지 않는다.

채택할 경우 한 책임은 “현재 팀원의 지원되는 실행 선호를 작성·검토·수정한다”이다.

- 배경과 원하는 행동을 먼저 파악하고 공통 해석 계약으로 분류한다. 공유 요구 변경을 개인 설정으로 숨기지 않는다.
- 요청한 스킬 파일과 쌍의 일관성을 검토할 때 필요한 같은 팀원의 상대 파일만 읽는다.
- 작성 직전 기존 내용을 다시 확인하고, 유지할 선호를 보존해 요청된 현재 파일만 교체한다.
- 해당 팀원의 개인 선호만 쓴다. 프로젝트의 기초 정본, 활성 Work, 다른 팀원 파일을 쓰거나 프로젝트를 초기화하지 않는다.
- 결과에는 작성 경로, 달라질 행동과 충돌로 제외한 요구를 설명한다. 실행 안전성이 인증됐다고 주장하지 않는다.
- 부족한 사용자 의도만 묻고, 잘못된 설정을 적용한 뒤 관찰하는 방식으로 작성 검증을 하지 않는다.

공개 스킬을 추가하려면 이 책임·진입 조건과 이름을 먼저 결정한다. 기존 아홉 스킬의 책임이나
`next_route` 허용값 목록을 늘리지 않는다. 새 스킬의 저작·배포는 Skill Rails를 사용하지만 개인 설정 파일은
생성된 스킬이 아니며 사용자가 편집할 때 재빌드하지 않는다.

## 8. “절대 보호”의 의미와 미결정 경계

개인화가 Devflow 파일 체계와 충돌하면 실행해서는 안 된다는 **금지 요구는 고정**이다. 아직 정해지지
않은 것은 AI가 이를 잘못 해석했을 때까지 차단할 실행 수단을 제품 범위에 넣는가이다. 이전 대화의
질문에는 아직 답이 없으며, 기획서 작성 요청을 그 답으로 취급하지 않는다.

| 선택 | 보장 범위 | 이 계획을 실행하는 조건 |
|---|---|---|
| A. 현재 자연어 지침 스킬 안에서 개인 지침의 권한을 제한 | 모든 충돌은 금지하고 새 문맥의 실제 사용 반례로 실제 거부 행동을 확인한다. AI의 모든 오해·우회 쓰기에 대한 기술적 불가능성은 보장하지 못한다. | 이 한계를 사용자가 수용하면 §9–10의 최소 구현을 채택할 수 있다. |
| B. 보호 파일에 대한 잘못된 쓰기를 적용 전에 강제 차단 | 지정한 환경에서 모든 쓰기 경로를 통제하고 기계적으로 판정 가능한 불변식 위반을 거부해야 한다. 자연어 지식의 진실성까지 자동 보장하지는 못한다. | 보호 범위·지원 실행 환경·우회 경로·쓰기 주체를 별도 아키텍처로 결정하고 관찰한 뒤 구현 범위를 다시 확정한다. |

현재 구조에는 A가 가장 작고 자연스럽다. 그러나 사용자가 B를 요구한다면 A를 대신 구현하고 요구를
충족했다고 하지 않는다. 사후 검사, Git 복구, 작성 지원 스킬, Skill Rails 빌드 결과 기록은
쓰기 전 강제 보호가 아니다. 일반 셸·편집기로 같은 경로에 쓸 수 있으면 전용 파일 작성 주체도 우회가 남는다.

B의 가장 작은 다음 관찰은 선택한 실행 환경의 폐기 가능한 시험용 프로젝트에서 보호 경로에 대해 허용 쓰기는 되고
직접 셸·편집기·별도 에이전트의 우회 쓰기는 거절되는지 확인하는 것이다. 지원 환경이나 보호할 불변식이
정해지기 전에 검사기·자동 호출 장치를 만들지 않는다. 이 문서는 B의 실현 가능성이나 모든 실행 환경의 차단을 입증하지 않는다.

## 9. 승인 뒤 바꿀 정확한 소스와 저작 방식

아래는 A를 채택할 때의 변경 계획이다. 지금 파일이 존재한다고 주장하는 것은 아니며, 새 모듈은
현재 소스 관계도에 아직 없다. `plan/**`이나 생성된 스킬을 직접 수정하지 않는다.

| 위치 | 담을 내용 | 늘리지 않을 책임 |
|---|---|---|
| `source/modules/member-preferences.md` 신설 | 개인 선호를 따로 두는 이유, 현재 역할의 권한 안에서 해석하는 규칙, 충돌 처리, 적용 수명·보고 경계 | 실행 스킬의 본래 절차, 작업 상태 기계적 형식 규칙, 전역 다음 역할·팀원 식별, 새 기록 체계 |
| `source/skill-package.json` | 실제 모듈 경로를 한 번 등록 | 사용하지 않는 스킬이나 자동 처리 장치 선언 |
| `source/targets/work/entry.md` | §4.1의 Work 후보 발견 조건과 공통 모듈 연결을 입력 확인 뒤·실행 전에 둠. 기존 결과 보고의 읽은 범위에 실제 개인 파일도 포함 | 기존 진입·대화 안에서 끝나는 작업·종료 계약의 재작성 |
| `source/targets/work/target.json` | `member-preferences` 참조 연결 | 관찰 도구·파일 생성기 도입 |
| `source/targets/work/closure.md` | 기존 마지막 정리 문장을 정확한 Work ID의 팀원 메모 삭제로 좁혀 개인 설정이 보존되게 명료화 | 새 정리 서비스, 팀 전체 탐색·삭제 |
| `source/targets/verify/entry.md`, `target.json` | 계약 확인 뒤·검증 항목 실행 전 Verify 후보 발견과 같은 모듈 참조 연결. 기존 보고에 실제 개인 입력·미적용 이유를 설명 | `team-context` 강제 참조 연결, 구현 수리, 추가 검증 항목 양식 |
| `source/targets/direct/entry.md`, `target.json` — 후속 | 기존 입력·인계 맥락 확인 뒤 첫 계약 판단 전 같은 연결 추가 | Work·Verify 설정 병합, 추적 작업 상세의 무조건 개봉 |
| `skills/<affected-target>/` | 해당 소스에서 Skill Rails로 생성 | 수동 편집, 개인별 배포본 |
| 이 검증 기록 위치와 `tests/README.md` | 실제 관찰과 필요한 계획과 구현의 차이 | 실행 전 성공 기록이나 승인 기준선 개정 |

`project-gate`, `work-state`, `team-context`, `project-knowledge`, 공통 소통 규칙과 문서 유형 계약에는
이번 기능의 절차를 넣지 않는다. 기존 담당 경계를 참조하고 개인화가 이를 바꿀 수 없다고 말하면 된다.
Resume·Sketch·Product·Architecture·Design·Adopt에 개인화 참조 연결을 추가하지 않는다. 소비자와 관계없는
스킬에 새 항상 읽는 본문을 퍼뜨리지 않는 것이 변경량보다 중요한 최소화 기준이다.

### 9.1 실제 지침으로 옮길 문안

§4–6은 구현할 의미와 근거이고, 아래는 그 의미를 소스에 전달할 **검토용 문안**이다. 실행 시에는
독립 배포된 스킬과 참조 문서가 규칙을 소유한다. 이 기획서를 추가 실행 지침으로 읽히거나
소스와 동기화할 두 번째 정본으로 만들지 않는다. 기존 소스의 문체에 맞춰 표현을 줄일 수 있으나
유효한 선호 적용, 금지 조항 배제, 필수 계약 실패 처리, 증거·완료의 불변성을 생략하지 않는다.

**진입문에 넣을 연결 문안.** Work는 유효한 입력을 확인한 뒤 첫 구현·종료 행동 전에,
Verify는 작업 계약·관리권을 확인한 뒤 첫 검증 항목 실행 전에 둔다. 아래 `<skill>`은 각각
`work`, `verify`로 바꾼다. 후속 Direct를 채택하면 입력 확인 뒤 첫 계약 판단 전에 `direct`로 사용한다.

> 개인 설정은 공유 계약을 유지하며 팀원마다 실행 방법을 조정하기 위한 입력이다.
> 유효한 입력 확인 뒤 첫 실행 판단 전에, `.devflow/team/`이 있으면 기존 팀원 식별 규칙으로
> 현재 팀원의 `.devflow/team/<current-member>/preferences/<skill>.md`만 확인한다.
> 이미 확인한 팀원 정보는 재사용한다. 파일이 있으면 `references/member-preferences.md`를 먼저
> 읽고 개인 파일을 적용하며, 없으면 파일을 만들지 않고 기본 방식으로 진행한다.

**공통 해석 모듈의 본문 문안.** 발견·팀원 식별 절차는 진입문과 기존 담당 모듈에 남기고 여기서 복제하지 않는다.
새 모듈의 머리말은 이 목적과 “소비 진입문에서 현재 스킬의 개인 파일을 발견했을 때”라는 읽기 조건을 담는다.

> 개인 선호는 반복 설명을 줄이되 다른 팀원도 같은 계약으로 이어갈 수 있게 해야 한다.
> 현재 조건에 맞는 방법은 기본 방법보다 우선 적용하고, 현재 사용자의 명시 요청이 선호를 바꾸면
> 그 요청을 따른다. 개인 설정은 프로젝트 정본·작업 계약이나 역할별 권한을 바꾸지 않는다.
> 파일 위치·상태·관리권·증거·정본 반영·종료는 기존 계약을 따르며, 명령이나 링크도 권한을 추가하지 않는다.
>
> 충돌하는 조항과 그에 의존하는 내용은 함께 제외하고 독립적으로 유효한 부분만 적용한다.
> 제외한 내용을 새 의도로 재해석하지 않는다. 빈 본문이나 무관한 조건은 기본 방식으로 진행한다.
> 읽기 실패·병합 충돌·해석 불가·내부 모순은 영향받는 부분을 적용하지 않고 이유를 알린다.
> 머리말 누락만으로 공유 작업을 손상으로 판단하거나 설정을 자동 수리하지 않는다.
> 실제 행동을 결정할 수 없을 때만 질문한다. 설정을 못 쓰는 것과 필수 계약·Git·관리권의 결함은
> 구별하며, 후자는 기존 중단·복구 규칙을 따른다.
>
> 개인 품질 문턱을 새 완료 기준으로 만들지 않는다. 추가 관찰에서 기존 검증 항목의 위반이 드러나면
> 그 항목의 증거로, 실제 계약·상위 판단 문제는 기존 인계로 다룬다. 선호 도구가 없다는 이유만으로
> 입증된 항목을 미입증으로 바꾸지 않되, 필수 관찰 수단이 없으면 `unproven`으로 남긴다.
>
> 새 진입·재개에서는 현재 설정을 읽고 같은 실행에서는 반복해서 읽지 않는다. 도중에 변경을 알게 되면
> 진행 중 행동을 안전하게 마친 경계에서 다시 판단한다. 실제 읽은 경로, 적용해 달라진 방법과
> 제외 이유를 기존 보고에 짧게 설명한다. 무설정 보고나 별도 설정 상태·로그는 만들지 않으며,
> 인계할 작업 사실과 증거는 기존 작업 문서에 남긴다.

**Work 종료 문장의 수정안.** 기존 종료 자격·지식 반영·검토 요약 순서는 그대로 두고 마지막
삭제 대상만 명료하게 한다.

> 기존 종료 조건과 검토 요약을 충족한 뒤 해당 `.devflow/work/<work-id>/`와
> 정확히 같은 작업 ID의 `.devflow/team/*/<work-id>.md`만 정리한다.
> 개인 설정 `preferences/`, 다른 작업의 메모, 개인 Sketch, 팀원 폴더 전체는 삭제하지 않는다.

개인 파일의 작성 관례는 기존 `project-knowledge`를 따른다. 소비 단계에서 머리말을 검사하려고
작성 담당 모듈을 항상 읽히지 않는다. 선택적인 작성 지원 스킬을 채택하면 그 스킬이 작성 전에 읽는다.

### 9.2 전달 순서

1. §11의 보호 수준과 채택 범위를 결정한다. 기존 미커밋 변경을 분리해 보존하고 현재 소스를 재확인한다.
2. Work만 저작한다. 공유 모듈의 최소 내용, 패키지 선언 등록, Work 연결과 종료 정리를 구현한다.
   해당 스킬을 두 번 빌드하여 빌드 결과 기록·변경 차이·결정성·배포본 무결성·소스 원본과 배포본의 일치를 확인한다.
   독립 배포본을 사용한 Work 새 문맥의 실제 사용에서 무설정·정상 설정·충돌·종료를 관찰한다.
   이때 종료의 선행 `proven` 검증 기록을 시험 입력으로 준비했다면 Work의 종료 행동만 관찰한 것이며
   Verify 실행을 증명한 것으로 기록하지 않는다.
3. Work의 전달과 해당 행동을 확인한 뒤 Verify만 저작·빌드한다. 독립 검증, 충돌 배제, 실제 실패·수리·
   재검증·인계 장면을 관찰한다. 공유 모듈을 고치면 이미 구현한 소비 스킬도 재빌드하고 영향받은
   행동만 다시 확인한다.
4. 기본 쌍이 유효하면 채택한 범위에 따라 Direct를 같은 방식으로 한 스킬씩 전달·관찰한다.
5. 작성 지원을 채택하면 소비 계약을 재사용하는 별도 스킬 하나로 저작·관찰한다. 기존 스킬의
   실행 전에 호출되는 필수 단계로 만들지 않는다.

저작 시 설치된 Skill Rails CLI의 현재 `help`, `inspect --id <target/module>`, `overview`를 사용한다.
현재 소스 관계도 조회 도구의 첫 버전은 요구사항·검사·외부 경계 의미 관계를 선언하지 않는다고
명시한다. 그 공백을 자동 증명으로 해석하거나 개인화 도입을 이유로 새 관계 체계를 만들지 않는다.

### 9.3 구현을 인계할 때 전달할 요청

아래 요청은 **보호 수준과 범위를 실제로 결정한 뒤** 사용할 예시다. 빈 결정을 AI가 승인된 것으로
채우지 않는다. 별도 승인 파일이나 새 상태 필드는 필요 없으며 실제 사용자 결정이 근거다.

> 승인된 보호 수준과 채택 범위를 먼저 확인하고 이 기획서 §2의 현재 소스 전제를 재확인한다.
> §9.2 순서대로 한 스킬의 저작·전달·새 문맥 사용을 완결한 뒤 다음 스킬을 진행한다.
> 첫 작업은 공통 해석 모듈과 Work의 연결·종료 대상 명료화다. 생성된 스킬은 수동 편집하지 않는다.
> §9.1의 이유와 필수 의미를 소스에 남기되 기획서의 모든 표를 실행 문서에 복제하지 않는다.
> 기존 미커밋 변경과 불변 계획을 보존하고, 승인 범위에 없는 Direct·작성 지원·강제 보호 장치를
> 덧붙이지 않는다. §10의 관찰로 전달·행동·효과를 각각 기록한다.
> 승인 범위 안에서는 단계의 관찰이 충족되면 다음 단계로 이어간다. 책임·수명·사용자 동작을
> 새로 바꿔야 하거나 선택한 보호 수준으로 요구를 충족할 수 없으면 그 결정만 사용자에게 돌려준다.

### 9.4 커스텀 본문을 제외한 추가 실행 지침 비용

기준 소스는 `f29f096`이다. 수치는 UTF-8 문서를 읽고 줄바꿈을 LF로 통일한 Unicode 문자 수다.
§9.1 인용문의 `> ` 표시와 마지막 줄바꿈을 제외한 본문을 센다. 개인 파일, 프로젝트 문서, 코드,
대화 이력, 도구 결과, 새 모듈 제목·머리말과 최종 연결 문장의 차이는 포함하지 않는다.
따라서 구현 전 문안 규모의 비교이며 모델 토큰·과금·지연 또는 완성 배포본의 정확한 증가량이 아니다.

현재 연결 문안은 287자·5줄, 조건부 공통 해석 본문은 859자·20줄(빈 줄 포함)이다.
직전 문안의 419자·1,174자와 비교해 중복·도구 운용 세부 설명을 줄이고, 함께 판단할 의미를
문단으로 묶었다. 보호·충돌·완료 기준의 구분은 유지했다. 줄 수는 원문 줄바꿈 기준이며 화면 너비에
따라 달라진다. 설정이 없는 실행도 진입문을 읽으므로 287자의 비용은 발생한다. 진입 거절 시 추가 탐색은 없지만 이미 읽은 진입문 비용까지 없어지지는 않는다.

| 실행 경로 | 현재 기본 지침량 | 개인 파일 없음: 추가 본문 | 개인 파일 있음: 추가 본문 |
|---|---:|---:|---:|
| Work: 대화 안에서 끝나는 구현, 정본 쓰기 없음 | 7,725자 | 287자 / 약 3.7% | 1,146자 / 약 14.8% |
| Work: 일반 추적 구현, 인계 메모 없음 | 9,674자 | 287자 / 약 3.0% | 1,146자 / 약 11.8% |
| Verify: 유효한 추적 작업 | 9,693자 | 287자 / 약 3.0% | 1,146자 / 약 11.8% |

기본 지침량은 각 진입문과 `communication`, `project-gate`를 합산하고, 추적 Work·Verify에만
`work-state`를 더한 값이다. 다른 조건부 참조가 필요한 실행은 그만큼 기준량이 달라진다.
Work 종료 문안은 기존 정리 문장을 대체하므로 169자 전체를 순증으로 더하지 않는다.
종료에서의 최종 순증과 모듈 머리말 등은 구현 뒤 실제 차이로 측정한다.

새 지침 파일 읽기는 개인 파일이 없을 때 0개, 있을 때 공통 모듈 1개다. 기존 진입문 자체는 이미
읽으므로 새 파일 읽기가 아니다. Resume 등 비소비 스킬은 추가 비용이 없다. 경로 존재 확인과
필요한 팀원 식별은 별도 부담이며, 명령을 묶거나 기존 정보를 재사용할 수 있으므로 이를 고정된
도구 호출 수로 환산하지 않는다. 빈 개인 파일도 현재 설계에서는 공통 모듈 읽기 비용을 부담한다.

Work와 Verify를 새 문맥에서 각각 한 번 실행하면 개인 설정이 둘 다 없을 때 총 574자,
둘 다 있을 때 총 2,292자의 추가 지침 본문을 읽는다. 같은 실행 내부의 테스트 반복에는
이 문안을 다시 읽지 않는다. 실제 과금 캐시 효과나 재진입 빈도는 이 합산으로 입증하지 않는다.

모든 규칙을 진입문에 합치면 설정이 없는 실행에도 859자를 추가로 부과한다. 반대로 공통 모듈을
더 나누면 같은 개인 파일을 판단하는 데 필요한 규칙이 흩어지고 읽기 횟수가 늘어난다. 따라서
현재는 짧은 진입 연결과 조건부 공통 모듈 하나를 유지한다. 설정 사용률이 매우 높고 실제 실행에서
추가 참조 지연이 절약하는 읽기보다 크다면 통합을 재검토한다. 현재 자료로 평균 절감은 주장하지 않는다.

구현 관찰에서는 무설정·설정 실행의 실제 열린 지침, 경로 확인·식별 호출, 추가 질문, 최종 배포본
문자량과 가능하면 모델 입력 토큰을 함께 기록한다. 조항 누락·잘못된 적용·재작업이 생기면 그것도
비용에 포함한다. 글자 수 감소만으로 운용 개선을 선언하거나 측정용 제품 로그를 신설하지 않는다.

## 10. 결정에 필요한 관찰과 종료 기준

다음 장면들은 구현 전에 작성한 판별 계획이다. 실제로 실행한 장면과 결과는 §13에 구분해 기록한다.
기존의 작은 기본 준비가 끝난 시험용 프로젝트를 폐기 가능한 Git 사본으로 사용하고, 이전 대화 없는
실행 AI에는 정확한 독립 배포본 스킬·프로젝트 입력·요청만 준다. 이 기획서나 정답표, 기존 대화,
전역에 설치된 구버전 스킬을 실행 근거로 제공하지 않는다.

기본 출발점은 [Queue Relay 시험용 프로젝트](../work-target/fixture/)의 별도 사본이다. 현재 `src/retry-policy.js`는
`shouldRetry(attempt) = attempt < config.retryLimit`이고 기본 한계값은 3이다. 기존 설정 테스트는 한계값의
값만 확인하므로 경계 입력을 별도로 관찰할 이유가 있다. 다만 원본 Architecture는 재시도 주장에 사전 운영 환경
증거도 요구하고 프로젝트 안내 문서는 과거의 공유 Sketch 검색 패턴을 사용한다. 그대로 복사해 로컬 테스트만으로 종료하면
잘못된 시험이다. **실험 전 입력을 준비하는 담당 AI**가 폐기 가능한 사본에서 다음 두 사항을 명시한다.

- Architecture의 검증 계약은 이 실험의 순수한 로컬 판정 함수는 Node 실행으로 관찰하고,
  시간 초과·실제 전달 재시도·외부 전송 주장은 여전히 사전 운영 환경 또는 외부 제공자 증거가 필요하다고
  구분한다. 작업 계약의 범위도 로컬 판정 함수로 한정한다. 실제 외부 재시도를 검증했다고 주장하지 않는다.
- 프로젝트 안내 문서의 Sketch 발견 경로는 현재 소스의 `team/<current-member>/sketches/*/state.md`로 맞춘다.
  활성 Work의 작업 계약·작업 상태·Git 기준을 완결하고 커밋한다. 원본 시험용 프로젝트와 Devflow 소스는 고치지 않는다.

이는 대상 제품의 검증 기준을 실행 중 낮추는 것이 아니라 범위를 명시한 **새 시험 입력**이다. 무설정
대조군에도 같은 입력을 사용한다. 이 준비가 빠지면 그 실행은 시험용 프로젝트 오류로 분리하고, 실행 담당 AI가
사전 운영 환경 의무를 무시하도록 지시하지 않는다. 실패 순환의 정답은 다음과 같이 사전에 고정한다.

- 선택한 작업 계약은 한계값보다 작은 마지막 시도 번호에서 `true`, 한계값과 같은 번호 및 그보다 큰 번호에서
  `false`라는 수용 기준을 갖는다. 현재 한계값 3에서는 입력 `2/3/4`와 결과 `true/false/false`다.
- 구현 수리의 허용 변경 범위는 `retry-policy`와 직접 관련된 해당 기능의 테스트로 제한하고 설정 등 무관한
  파일 내용은 보존한다. 작업 상태·검증 기록·종료 쓰기는 각 역할의 기존 작업 산출물 계약을 따른다.
- B와 D는 모두 원래 올바른 함수에 `<=` 경계값 결함을 주입하고 커밋한 사본을 사용한다.
  B의 무설정·설정 실행은 같은 결함·계약에서 Work 관리권으로 시작한다. D는 같은 결함을 가리키는
  유효한 Verify 관리권·안전 지점에서 시작한다. 검증 담당 AI에게 실패 답을 알려 주거나 실패 판정을 미리 넣지 않는다.
- 새 문맥의 Verify가 입력 3의 실제 실패를 찾고 Work로 보낸 뒤, 새 문맥의 Work가 수리·안전 지점을 게시하고
  새 문맥의 Verify가 다시 실행한다. 시험용 결함 주입은 **작성한 시험 입력**이지 앞선 Work가 실제로 저지른 오류의 증거가 아니다.
- D의 팀원 A/B 전환은 시험 준비 담당자가 각 순차 실행 전에 해당 사본의 저장소 로컬
  `git config user.name`을 실제로 전환·확인하여 수행한다. 전역 설정은 바꾸지 않는다.
  실행 AI에게 어느 개인 파일을 선택하라는 정답을 주지 않고 기존 식별 규칙으로 찾게 한다.
  동시에 같은 사본의 팀원 식별을 바꾸지 않는다.
- F는 후보와 미반영 지식이 없는 종료를 기본으로 한다. 개인 취향이나 단순 테스트 결과를
  장기 지식으로 만들지 않는다. 실제로 새 지속 사실이 드러난 경우에만 기존 정본 반영 계약을 적용하며,
  그 경로를 수행하지 않았다면 이번 관찰의 정본 반영 효과를 입증됨이라고 쓰지 않는다.

이 시험용 프로젝트의 과거 시험 장면 문구나 기대하는 다음 역할이 현재 소스와 다르면 현재 소스를 기준으로 새 시험 장면의
기대를 고정한다. 예를 들어 Verify의 외부 증거 부족은 증거에 실제 실패 원인의 담당 역할을 적되 활성 Work
작업 상태는 현재 `work-state`의 Direct 인계를 따른다. 과거 `user` 직행 기대를 그대로 복제하지 않는다.

| 장면 | 최소 입력·행동 | 확인할 결과와 반례 |
|---|---|---|
| A. 기본 경로와 팀원 식별 | 설정 없는 대화 안에서 끝나는 작업·추적 작업 입력, 팀원 폴더 유무와 팀원 식별 부재, 진입 조건 거절 입력을 구분 | 없는 설정을 만들지 않고 기본 의미를 유지한다. 필요한 경우 기존 팀원 이름 질문을 사용하며 다른 팀원을 추측하지 않는다. 진입 조건 거절 시 설정을 탐색하지 않는다. 추가 읽기·질문의 실제 비용을 기록한다. |
| B. 방법의 실제 차이 | 같은 `<=` 결함·계약·Work 관리권에서 무설정과 재현 우선 설정으로 별도 실행 | 설정이 요구한 재현·가설 검토가 실제 행동에 나타나며 작업 계약·허용 변경 범위·판정 소유권은 동일하다. 보고만 바뀌면 효과 근거가 아니다. |
| C. 유효·금지 조항 혼합 | 재현 우선 + 작업 상태에 판정 복사 + 의존된 검증 생략, 읽기 불가 설정은 별도 변형 | 독립된 선호만 적용하고 금지·의존 묶음을 배제한다. 설정 실패로 필수 계약을 무시하거나 공유 작업의 차단 사유를 발명하지 않는다. |
| D. 실제 실패 순환과 담당자 변경 | 위에서 결함을 주입한 안전 지점·Verify 관리권, 팀원 B의 반례 중심 Verify, 팀원 A의 수정, 팀원 B의 재검증 | Verify가 실패 증거를 먼저 쓰고 Work로 인계한다. Work가 수리·안전 지점을 만들고 재검증한다. B는 A의 설정을 상속하지 않는다. 실행 없는 통과나 Verify의 직접 수리는 실패다. |
| E. 추가 점검과 상위 판단 | 작업 계약에 없는 개인 품질 문턱, 기존 검증 항목의 관찰 수단 부재, 실제 계약 결함을 구별 | 숨은 검증 항목을 만들지 않는다. 필수 증거 부재는 미검증, 실제 상위 문제는 증거의 담당 경계와 작업 상태의 Direct 인계를 구분한다. 후속 Direct가 개인 선호를 공유 의무로 바꾸지 않고 질문을 이해해야 한다. |
| F. 재개·설정 변경·종료 | D의 안전한 인계 지점에서 중단, 설정 변경 또는 삭제 후 Resume→실행. 정확한 작업 메모·무관한 설정과 팀원 폴더 전체 삭제를 요구하는 금지 조항을 배치 | Resume은 개인화 없이 다음 역할을 복구한다. 재진입은 현재 설정을 사용한다. 후보 없는 종료에서 검토 요약 뒤 정확한 작업 산출물·메모만 삭제하고 개인 선호와 무관한 파일 내용을 보존한다. |
| G. Direct — 후속 채택 시 | 관찰 가능한 작은 구현 선호, 모든 작업을 추적 대상으로 만드는 강제 조항, 실제 점진 구체화 계약의 다음 관찰 가능한 작은 구현 판단 | 유효한 판단 방법만 반영하고 지속성 진입 조건·계약 변경·공유 수용 기준을 보존한다. 성공한 중간 검토를 Verify 실패로 보내지 않는다. |
| H. 작성 지원 — 후속 채택 시 | 정상 선호와 충돌 요구를 섞은 자연어 요청, 기존 선호 파일 | 이유와 적용 조건을 가진 개인 파일만 작성하고 유지할 내용을 보존한다. 다음 소비 담당 AI가 파일을 실제로 사용하며 작성기를 거쳤다는 이유로 검사를 생략하지 않는다. |

D와 F는 동일한 시험용 프로젝트에서 이어 관찰할 수 있다. 서로 다른 실패 원인을 가리기 어려워지면
해당 분기만 독립 사본으로 나눈다. 모델·실행 환경·시험 장면 수 자체를 목표로 행렬을 늘리지 않는다. 지원한다고
주장할 환경에서 실행하지 못한 경로는 해당 범위를 명시해 `unproven`으로 둔다.

B의 무설정 실행도 같은 좋은 방법을 자연스럽게 사용했다면, 개인 파일의 읽기·적용 가능성과 추가
효과를 구분한다. 차이가 없는데 개인화 덕분에 개선됐다고 주장하지 않는다. 방법 차이가 필요한 다른
실제 요구가 있는지 확인하거나 추가 효과를 미검증으로 남기며, 차이를 만들려고 기본 동작을 약화하지 않는다.

관찰에는 실제 열린 파일, 실행한 명령·관찰, 전후 변경 차이, 검증 증거와 작업 상태의 게시 순서, 정리 후 남은 파일을
남긴다. 관찰 기록은 이 저장소의 `tests/` 증거에 두고 결과 프로젝트에 별도 로그를 추가하지 않는다.
개인 설정의 말과 실제 행동이 일치했는지, 금지 조항의 효과가 없었는지, 다음 담당 AI가 원래 대화 없이
이어갔는지를 함께 본다. Work 출력을 구현 사실로 사용하되 Verify의 독립 판정을 대신하지 않는다.

전달 증거와 행동·효과를 따로 `proven`, `failed`, `unproven`으로 기록한다. 소스 검토나 빌드만으로
안전성·사용성·강제 보호를 입증됨이라고 쓰지 않는다. Work 단독 관찰만으로 Work–Verify 쌍을 완료로
보고하지 않는다. 적용 스킬별 연결·보호 경계·실제 순환·설정 보존이 확인되면 채택한 범위의 관찰을 닫는다.

실패하면 가장 가까운 원인으로 돌아간다. 읽기 누락은 진입문의 발견 조건, 의미 오해는 공통 해석 문장,
잘못된 정리는 Work 종료, 공유 의무 누수는 Direct 또는 개인화 범위의 결정을 고친다. 기존 계약
결함과 시험용 프로젝트 오류는 개인화 규칙을 늘려 가리지 않는다. 더 짧은 문장으로 같은 원인을 해결할 수
없거나 보호 수준 자체가 틀린 경우에만 구조를 다시 검토한다. 선택한 A가 B를 충족하지 못하는 것은
문구를 늘려 수리할 결함이 아니다.

## 11. 결정 상태와 구현 시작 조건

다음 표의 추천으로 시작했으며, 2026-09-23 적용 요청과 후속 검토에서 첫 구현 범위를 확정했다.

| 결정 | 추천 또는 현재 상태 | 구현에 미치는 영향 |
|---|---|---|
| 보호 보장 | A: 자연어 계약 채택 | 역할·경로·증거·종료 경계를 지침으로 보존한다. 일반 파일 쓰기를 막는 B의 기계적 강제는 제공하지 않는다. |
| 첫 소비 범위 | Work·Verify 채택 | 두 스킬만 소비자로 연결하고 실제 실패·수정·재검증 순환을 관찰한다. |
| Direct | 보류 | 첫 구현에 import나 개인 파일 경로를 추가하지 않는다. |
| 저장 위치·수명 | `team/<member>/preferences/<skill>.md`, 저장소 관리, 작업 종료 후 유지 | 승인 계획의 임시 team 설명과 다른 수명 확장으로 증거에 남긴다. |
| 작성 지원 스킬 | 보류 | 파일을 자동 생성하지 않고 직접 편집만 지원한다. |

이 결정은 새로운 checker·hook·상태·등록부를 만들지 않고 현재 prose 스킬의 안전 경계 안에서
개인 방법을 적용한다. 따라서 B 수준의 사전 차단이나 모든 모델에서의 준수를 입증한 것으로 보고하지 않는다.

## 12. 기획 검토와 증거 상태

아래 §12.1–12.7은 구현 전에 수행한 논리 검토 기록이다. 당시 전달·행동·효과가 `unproven`이었다는
판정을 고쳐 쓰지 않는다. 구현 뒤 증거는 §13에서 별도로 구분한다.

### 12.1 소스 책임과 전달 경계 대조

현재 아홉 진입문, 공통 모듈, Skill Rails 소스 관계도와 관련 기존 증거를 대조했다. 검토 기준은
개인화가 기존 담당 경계를 대체하는지, 다음 역할의 의무가 그 역할의 진입문에서도 도달 가능한지,
수명과 게시 순서를 잃는지였다. Work가 계약·판정을 작성하지 않는 것과 종료에서 작업 산출물을
삭제하는 것을 구분하도록 §2의 표현을 고쳤고, 실제 개인 입력을 보고하는 위치를 §9에 명시했다.
기존 Sketch 저장 방식과 과거 시험용 프로젝트의 차이를 그대로 인정했으며 그 관찰을 새 개인화의 증거로 쓰지 않았다.

### 12.2 실패·인계·증거에 대한 반례 검토

무설정, 읽을 수 없는 개인 파일, 손상된 필수 계약, 담당자 교체, 추가 품질 요구, 재개와 종료를 각각
문서의 규칙으로 따라갔다. 추가 관찰에서 새로운 검증 항목을 발명할 수 있던 표현을 §5에서 좁혔다.
실패 순환은 자연 발생을 기다리는 대신 명시적인 경계값 결함으로 설계하되, 시험용 결함 주입을 실제 Work 실패와
혼동하지 않게 했다. 과거 Verify 시험 장면의 다음 역할과 현재 Direct 인계의 차이도 시험용 프로젝트 준비 경계에 명시했다.
이는 사전 논리 검토이며 이전 대화 없는 실행 AI가 수행한 결과가 아니다.

### 12.3 자기완결성·최소 변경·사용 경험 검토

이전 대화 없이 읽는 구현자가 목적, 바꿀 소스, 개봉 조건, 충돌 처리, 다음 담당 AI와 종료 증거를
찾을 수 있는지 다시 검토했다. 유효한 개인 지침을 단순 참고로 무시할 여지를 줄이도록 §4.2에 기본
방법보다 우선 적용한다는 뜻을 명시했다. 보호 경계는 유지하되 개인화의 실제 효과가 사라지지 않게 했다.

시험 입력의 Architecture와 프로젝트 안내 문서까지 다시 읽어 사전 운영 환경 의무와 과거 Sketch 검색 패턴을 확인했다. §10에서
원본을 수정하지 않는 사본 준비와 주장의 한계를 명시했고, 이 기능에 필요 없는 인위적인 장기 지식
후보를 제거했다. 조건부 모듈 하나와 해당 진입문 연결로 충분한 범위를 유지했으며 별도
설정 상태·횟수 기록·파일 작성 주체·실행 환경의 자동 호출 장치를 추가할 이유는 찾지 못했다. 후속 Direct·작성 지원과 보호 수준
결정은 첫 구현의 숨은 의무가 되지 않게 구분했다.

문서 내부의 상대 링크와 절 경로를 점검했으며, 링크·형식 확인은 문서 전달 점검일 뿐 구현
가능성의 실측 증거가 아니다. 위 세 검토는 당시 같은 작성자가 서로 다른 질문으로 재검토한 기록이다.
이번 독립 검토는 아래에 별도로 기록한다. 남은 실질적 불확실성은 §8·11의 제품 결정과 §10의
미실행 행동·효과 관찰이다.


### 12.4 별도 에이전트와의 독립 검토 및 수정본 재검토

이번에는 별도 에이전트 한 명에게 기존 대화의 결론을 전제하지 않고 유지보수 지침, 승인 계획,
Skill Rails 방식, 아홉 진입문과 관련 모듈을 읽도록 요청했다. 역할·정본·작업 수명에 대한 이해를
먼저 대조한 뒤, 처음 구현하는 AI의 관점에서 반례를 찾게 하고 검토 의견을 주고받았다.

첫 검토에서 실행 지침 문안의 추상성, 원래 올바른 시험 함수로는 수리 행동을 관찰할 수 없는 점,
팀원 이름을 말로만 구분해서는 실제 설정 선택을 검증할 수 없는 점, 정상 자율 반복까지 금지할 수
있는 표현이 지적되었다. §1.1·6·9·10에 읽기 순서, 구체 문안, 결함과 관리권, 실제 팀원 전환을 반영했다.

수정본을 다시 읽은 독립 검토자는 첫 Work 구현부터 Verify 순환까지 인계 순서를 재구성했고,
추가 구조 없이 진행할 수 있다고 판단했다. 이어 진입 문안의 팀원 폴더 부재 분기, 개인 도구 부재와
필수 관찰 수단 부재의 차이, 강제 보호가 거부하는 대상의 표현을 지적하여 최종 반영했다.

설명은 한국어로 정리했으며 실제 경로·필드·상태값·스킬 이름만 원문 표기를 유지한다.
이 검토는 소스와 기획의 의미·실현 경로를 대조한 것이다. 실제 빌드나 새 문맥의 실행을 수행한 것은
아니므로 전달·행동·효과의 상태는 여전히 `unproven`이다. §8의 보호 보장 선택도 해결된 것으로 쓰지 않는다.

### 12.5 확인 시점과 중복 읽기 비용 재검토

현재 Work·Verify의 진입문과 §4·9를 다시 대조했다. 진입 자격 확인 전 탐색은 실행 불가 작업의
비용을 늘리고, 첫 실행 뒤 적용은 선호 누락과 재작업을 만들므로 기존 확인 시점을 유지한다.
다만 판단 단계가 별도 도구 호출·내용 예비 읽기로 구현될 여지가 있어 §4.1과 실제 지침 문안에
정보 재사용과 본문 읽기 통합을 명시했다. 구조·수명·보호 경계는 바꾸지 않았으며 비용의 실측 최적성을
입증한 것으로 기록하지 않는다. 확인 시점에 대한 기획 검토는 이 보완으로 마친다.

### 12.6 최근 커밋 대조와 실행 지침 비용 검토

`f29f096`의 소스·생성물·관찰 기록을 대조했다. Direct의 승격과 Sketch 인계 의무는 기존 담당
위치에 남아 있고, Sketch의 조건부 읽기는 개인화의 발견 시점과 충돌하지 않는다. Product 문서가
추적 작업의 검증 후 반영과 대화 안에서 끝나는 직접 반영을 구별하므로 §4.1에도 이를 명시했다.
추가된 기존 흐름의 관찰을 개인화 실행의 증거로 전용하지 않았다.

비용 검토에서는 기획 문안을 직접 계수하고, 항상 읽기·조건부 읽기·파일 탐색을 구분하여 §9.4에
기록했다. 진입문 전체에 규칙을 넣는 방식과 공통 모듈을 더 나누는 방식을 비교한 뒤 현재 구조를
유지하고 중복 연결 문장만 줄였다. 수정본은 다시 현재 진입 규칙과 대조하여 유효 입력 선행,
팀원 정보 재사용, 파일 부재 기본 동작, 보호 규칙 선행 읽기, 정확한 경로, 재진입 갱신이 유지되는지
검토했다. 공통 모듈의 유효 선호 적용·충돌 배제·필수 계약 실패 처리도 유지된다.

마지막으로 문안 문자 수와 기준 소스 합계를 재계산하고, 상대 링크·절 참조·변경 범위를 확인했다.
이 검토 범위에서 추가 수정 사유를 찾지 못했다. 구현 소스는 바꾸지 않았으며, 실제 호출 지연·토큰
비용·누락과 재작업은 여전히 실행 관찰이 필요한 항목이다. 별도 강제 보호 장치를 도입한 것은 아니다.


### 12.7 실행 문안의 의미 보존과 과잉 절차 재검토

문자 수를 목표로 축약하지 않고 §4–6의 의미를 실제 실행 문안과 현재 `project-gate`·`work-state`에
대조했다. 진입에는 목적·유효 입력·정확한 개인 파일·조건부 모듈 연결을 남기고, 식별 세부 규칙과
중복된 탐색 지시는 기존 담당 규칙과 정확한 경로 지정에 맡겼다. 예비 읽기 금지 등 구현 효율의
세부 설명은 §4.1의 저작 지침에 남겨 매 실행에 반복하지 않는다.

앞서 대화에서 제시한 더 짧은 후보를 그대로 채택하지 않았다. 설정 오류와 필수 계약 오류,
의존된 금지 조항, 숨은 완료 기준, 선호 도구와 필수 관찰 수단의 구분, 실행 중 설정 변경은
각각 다른 실패를 막으므로 최종 문안에 보존했다. 공통 지침은 절차 목록 대신 목적·충돌 판단·
검증 경계·적용 수명의 네 문단으로 구성했다.

수정 뒤 무설정·정상 선호·금지 조항 혼합·필수 계약 오류·추가 품질 문턱·재개와 변경을 다시
대조하고 비용 표를 재계산했다. 더 줄이기 위해 기존 의미를 삭제하거나 새 참조로 분할할 근거는
찾지 못했다. 이는 기획 문안의 의미 대조이며 동일한 실제 행동이나 성능 개선을 입증한 결과는 아니다.
실행 검증은 §10을 따르며 구현 소스는 이번 검토에서 수정하지 않았다.

## 13. 구현과 부분 관찰 결과

### 13.1 실제 채택 범위와 source

2026-09-23 적용 요청을 §11의 A 보호, 저장소 관리 경로, Work·Verify 우선 범위를 채택한 것으로
해석했다. `member-preferences.md`가 개인 방법의 권위·충돌·검증·수명을 한 번만 소유하고, Work와
Verify는 유효한 입력과 관리권을 확인한 뒤 자신의 정확한 개인 파일이 있을 때만 이를 연다. 설정은
자동 생성하지 않으며 Direct·Resume·다른 스킬에는 연결하지 않았다.

변경한 source는 다음과 같다.

- `source/modules/member-preferences.md`: 공통 해석 계약
- `source/skill-package.json`: 모듈 등록
- `source/targets/work/entry.md`, `target.json`: Work의 조건부 소비와 읽은 범위 보고
- `source/targets/verify/entry.md`, `target.json`: Verify의 조건부 소비와 읽은 범위 보고

마지막 항목은 기존의 blocker·candidate·pending landing 종료 조건을 바꾸지 않는다.
`.devflow/team/*/<work-id>.md`만 대상으로 하므로 중첩된 `preferences/`와 개인 Sketch를 삭제하지 않는다.

### 13.2 fresh-use 관찰

원래 대화와 기획서를 주지 않은 새 에이전트가 standalone 생성물과 독립된 Git fixture만 사용했다.
작성자 자신의 재연은 행동 증거로 사용하지 않았다.

### 13.3 비용과 남은 범위

기준 `f29f096`과 LF-normalized Unicode 문자 수를 대조하면 Work entry의 항상 읽는 증가는 332자,
Verify는 339자다. 조건부 공통 모듈은 제목을 포함해 941자이며 개인 파일 본문은 별도다. 따라서 설정이
없으면 새 참조 파일을 열지 않고 entry 증가만 부담한다. 설정이 있으면 Work는 1,273자, Verify는
1,280자와 개인 파일 본문을 읽는다. Work closure의 정리 대상을 명확히 한 문장은 기존보다 27자
늘었다. 기획 단계의 287자·859자 추산보다 크므로 실제 수치로 정정하며, 토큰·지연·재작업을 포함한
평균 효과는 주장하지 않는다.

`proven`은 위 두 fixture와 생성물 전달 범위에 한정한다. 설정이 전혀 없는 기본 실행과 그 기준선
대비 방법·비용 효과, team identity가 없는 경우, 읽기 불가·병합 충돌 설정, 실행 중 설정 변경,
추가 품질 문턱, 실제 같은 ID의 team note 삭제, 다른 모델·host, 장기 사용 효과는 `unproven`이다.
Direct와 B 수준의 기계적 사전 차단은 구현하지 않았다. 작성 지원은 후속
[`workflow-customize`](workflow-customize-plan.md)에서 별도로 구현·관찰했다. 자연어 계약이 일반 파일
쓰기를 기술적으로 막는다고 주장하지 않는다.
