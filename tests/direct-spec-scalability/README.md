# Direct의 상세 기획·대형 작업 수용 — 설계 검토

상태: 교차 검토 완료 · 채택 제안. 구현 승인이 아니며 새 동작은 아직 `unproven`이다.
검토일: 2026-09-23. 기준: Devflow `7af7667`과 현재 작업 트리의 관련 source.
`plan/**`는 변경하지 않는다. 이 문서는 기존 설계와 제안의 차이, 적용 위치, 실행 검증 조건을 소유한다.

## 1. 해결할 문제와 유지할 가치

사용자는 버튼 하나부터 정밀한 기술 계약을 가진 큰 결과까지 맡길 수 있어야 한다. AI는 배경과
목표를 이해하면서도 지금 필요한 상세만 읽고, 구현 방법을 판단하며, 중단 뒤 남은 일을 놓치지
않아야 한다. 문서의 양이 아니라 **계약의 명확성, 읽기의 선택 가능성, 재개의 정확성**이 목표다.

SealQL은 이러한 복잡도가 실제로 존재한다는 사례다. 그 파일명·단계·이력 구조를 Devflow의
기본 양식으로 복제하지 않는다. 모든 작업에 상세 설계나 체크리스트를 강제하지도 않는다.

다음 세 가지는 별개다.

| 질문 | 소유 위치 | 혼동하면 생기는 문제 |
|---|---|---|
| 무엇을 왜 만들고 어디까지 허용되는가? | Direct가 작성한 실행 계약, 해당 프로젝트 정본 | 구현자의 편의가 요구사항을 바꿈 |
| 지금 무엇을 이어서 구현해야 하는가? | Work의 실제 Git 결과와 현재 state | 계약에 진행 상태가 섞이거나 대화를 복구해야 함 |
| 요구가 실제로 충족됐는가? | Verify의 criterion별 관찰·증거 | 작업 체크 표시를 검증 통과로 오인 |

## 2. 기존에 있는 것과 없는 것

| 관심사 | 현재 계약·소스 | 판단 |
|---|---|---|
| 간단한 수정 | Direct의 지속성 세 질문, ephemeral 경로 | 이미 있음. 크기로 tracked를 강제하지 않음 |
| 상세 기획과 자율 구현 | spec의 배경·결정·제약·deliverable·acceptance, 선택적 shaping | 이미 있음. 상세함을 금지하지 않음 |
| 원래 기획의 큰 작업 고려 | `plan/01`, `03`, `08`의 긴 작업·분해·중단 계약 | 고려가 누락됐다고 할 수 없음 |
| 독립 결과 여러 개 | 각각의 Work artifact와 필요할 때 통합 artifact | 이미 있음. 페이지나 구현 단계별 분할은 금지 |
| 프로젝트 상세 지식 | Architecture·Design·Domain의 조건부 자식과 `read_first` | 이미 있음. 현재 프로젝트가 채택한 장기 의미의 자리 |
| 한 결과의 방대한 임시 상세 | spec 하나가 기본. plan/08은 큰 evidence/test matrix 보조 자료만 조건부 검토 | 일반 기술 상세를 분리할 운영 계약은 명확하지 않음 |
| 항목별 구현 진척 | 정적 deliverable은 가능. spec 상태 복제와 state 진행 기록은 금지 | 가변 체크리스트 기능은 없음 |
| 중단 재개 | committed safe point, next action, custody, Git 대조 | 이미 있음. 여러 부분이 동시에 미완성인 큰 작업의 효율은 별도 확인 필요 |

현재 `direct/tracked-contract.md`의 “산문만으로”는 긴 문장으로만 쓰라는 고정 형식이 아니다.
필수 의미를 가진 계약을 요구하지만 항목표의 품질이나 번호를 규정하지 않는다. 그래서 **항목으로
읽을 수 있는 spec**과 **항목 상태가 저장되는 작업 장부**를 구분해야 한다.

## 3. 사례·외부 조사에서 가져올 원리

SealQL의 현재 `plan/redesign/README.md`는 명세·API·프로토콜·예시·전달 계획의 역할을 나누고,
`delivery.md`는 각 구현 묶음과 완료 증거를 연결한다. `docs/r2-progress.md`에는 여러 묶음의
동시 부분 구현이 기록되어 있다. 이는 상세 계약의 선택 읽기와 부분 완료 복구를 검토할 실제
입력이다. Devflow에서의 행동 실패 증거는 아니다. 과거 `plan/README.md`와 현재 redesign의
시점 차이도 확인했으므로, 변경 이력을 순서대로 읽어야 현재 계약을 재구성하는 방식은 가져오지 않는다.

공개 원문 조회일: 2026-09-23. 아래는 제공하는 방법의 비교이며 품질 우열이나 효과 측정이 아니다.

이 비교에서 도출한 설계 판단: 상세 기획의 양을 제한하기보다 **공통 계약과 필요한 상세를
구분하고, 구현 위치와 검증 판정을 분리하는 것**이 중요하다. 구체적인 저장 방식은 Devflow의
기존 소유권과 수명을 기준으로 결정한다.

외부 도구가 체크리스트를 사용한다는 사실은 Devflow에도 필요하다는 증명이 아니다. 반대로
Devflow의 작은 snapshot이 언제나 더 저렴하거나 안전하다는 증거도 없다. 조사에서 실행 비용의
비교 실측을 확보하지 못했으므로 토큰·속도·내구성 순위를 매기지 않는다.

## 4. 제안의 중심 — 하나의 결과, 필요한 만큼의 상세

```text
현재 요청
  ├─ 현재 대화에서 안전하게 끝남 → 기존 ephemeral
  └─ 지속할 계약 필요 → spec + state
                         ├─ 함께 이해할 내용 → spec 본문
                         ├─ 현재 프로젝트의 지속 규칙 → 기존 정본을 참조
                         └─ 이번 결과에만 필요한 선택적 상세 → 조건부 상세

독립 수용·취소·검증 가능한 결과가 여럿이면 기존 artifact 분해를 사용한다.
문서가 여러 장이라는 이유로 결과나 관리권을 나누지 않는다.
```

### 4.1 spec의 최소 구성

Direct는 다음 의미를 채우되 작업이 단순하면 문단이나 짧은 목록으로 합친다. 빈 절을 만들거나
문서 길이를 맞추지 않는다. 기술 계약상 필수인 알고리즘·포맷·순서는 그 이유와 함께 제약으로
명시하고, 단순한 구현 제안은 Work가 바꿀 수 있는 방법으로 구분한다.

```markdown
# <만들 결과>
## 배경과 의도
<왜 필요한가, 무엇이 달라져야 하는가>
## 계약
<목표·비범위·공통 제약·결정된 사항>
허용 변경 범위: <정확한 write boundary>
## 구현할 결과와 수용 기준
| 결과 | 관찰 가능한 수용 기준 |
|---|---|
| <빠뜨리면 안 되는 결과> | <실행·관찰로 판단할 것> |
| <필요하면 전체 결합 결과> | <각 부분의 성공만으로는 판단할 수 없는 기준> |
## 읽을 맥락
<공통 read_first; 필요할 때만 질문/조건 → 정확한 상세 경로>
## 미결 사항
<실행을 막는 결정·위험; 없으면 생략>
```

프로젝트 표준 `summary/read_when` header는 기존대로 적용한다. 항목을 반복 참조해야 할 때만
짧은 식별자를 붙인다. 표의 행은 파일·함수별 코딩 명령이 아니며, 구현 순서도 의존관계가 실제로
필수일 때만 명시한다. shaping은 기존 선택 정보로 유지한다.

### 4.2 조건부 상세의 경계

제안 경로는 `.devflow/work/<id>/spec/<concern>.md`이다. `architecture.md`와
`architecture/`처럼 기존의 부모 문서·상세 폴더 관례를 따른다. 이는 별도 Work spec이나
child artifact가 아니라 같은 계약의 상세 문서다. 폴더는 필요한 경우에만 만든다.
별도 spec, state, manifest, index, ID 계층은 만들지 않는다. 다음 조건을 만족하지 않으면
spec에 함께 둔다: 본문을 열기 전에 필요한지 선택할 수 있고, 하나의 응집된 질문에 답하며,
공통 문맥 재구성과 경로 유지 비용보다 불필요한 읽기를 줄이는 이익이 크다.

spec에는 전체 목적·경계·공통 불변식·수용 기준의 목록·상세 선택 지도를 남긴다. 상세에는
해당 concern만의 배경과 구체 계약을 둔다. 같은 규칙을 양쪽에 복제하지 않는다. 상세가
공통 제약을 덮어쓸 수 없으며, 충돌은 Direct의 계약 수정 문제다. 모든 상세를 무조건
`read_first`에 넣지 않는다. 복수 concern에 걸친 작업이면 해당 상세들을 함께 읽는다.
수용 기준의 목록은 spec 한 곳만 소유한다. 상세는 그 기준이 가리키는 정확한 계약 값·전제 조건과
관찰 방법을 설명하며 독립 수용 기준을 추가하지 않는다. 상세를 직접 지정받아도 먼저 spec의
공통 맥락을 읽는다. 이미 현재 계약의 동일한 내용을 읽었다면 불필요하게 다시 열지 않는다.
root의 criterion은 이름표가 아니라 무엇을 관찰하여 맞다고 판단할지 설명하는 문장이어야 한다.
정확한 포맷·값·테스트 행렬은 상세를 참조할 수 있으며 root에 복제하지 않는다. 상세가 달라져
판정 의미가 바뀌면 계약 변경이다. 기존 root 문장이 더 이상 그 의미를 설명하지 못하면 함께
고치고, 문장 표면이 같더라도 과거 verification을 그대로 사용하지 않는다.

상세는 Direct가 소유하는 같은 실행 계약의 일부다. Work와 Verify가 임의로 고치지 않는다.
독립 custody·완료·검증 상태를 갖지 않으며 artifact와 함께 제거된다. 장기 프로젝트 규칙을
임시 상세에 숨기거나 기존 정본을 복사하지 않는다. 아직 구현되지 않았더라도 현재 채택한
지속적인 기술 결정은 정본에 둘 수 있다. 채택한 결정과 실행으로 확인된 사실은 구별한다.
탐구 원문은 Sketch에 두고, 실행에 필요한
채택 결론만 올바른 정본 또는 실행 계약에 남긴다.

### 4.3 진행 기억 — 기존 좌표를 유지한다

기본은 현재의 `last_safe_point`와 `next_action`이다. 정적인 결과 항목과 이 좌표만으로 새 AI가
안전하게 이어갈 수 있다면 상태나 파일을 추가하지 않는다.

정적인 결과 목록은 빠뜨릴 수 없는 전체 의도를 보존하고, 집중된 commit과 실제 코드·test는
구현한 내용을 보여주며, next_action은 다음에 이어갈 범위를 정한다. 필요한 경우 기존
last_safe_point의 한 줄 의미와 commit 설명에 관련 결과를 명확히 표현한다. 모든 행마다
commit하거나 완료 표시를 관리할 의무는 만들지 않는다. commit 메시지는 탐색 단서이며
실제 구현 또는 Verify 통과의 증거를 대신하지 않는다.

`remaining_items` 같은 필드나 `tasks.md`는 이번 도입 범위에서 제외한다. 여러 항목의 부분
구현 후 새 AI가 기존 좌표로 재개할 때, 요구를 놓치거나 완료 구현을 불필요하게 반복하거나
재탐색 비용이 과도해지는지를 관찰한다. 문제가 재현될 때 원인이 spec의 불명확성인지,
안전 지점의 부실인지, 부족한 진행 기억인지 구분한 뒤 해당 위치만 보완한다. 필요성을
미리 부정하지도, 외부 도구가 체크리스트를 쓴다는 이유로 새 상태를 도입하지도 않는다.

## 5. 실행·수정·검증·재개에 미치는 영향

Work는 전체 spec과 현재 실행에 필요한 상세만 읽고 국소 구현 방법을 선택한다. 정해진 결과나
guardrail을 바꾸지 않는 방법 개선은 계속 실행한다. 계약의 전제를 바꿔야 한다면 기존처럼
safe point에서 Direct로 인계한다. 이때 Verify를 경유할 이유가 없으며 이미 권한 안에서
결정할 수 있는 사항을 사용자에게 반복 승인받지 않는다.

Direct는 관리권을 받은 뒤 spec과 영향을 받는 상세를 함께 조정한다. 여러 파일의 교체가
원자적이라고 가정하지 않는다. 수정 중에는 `next_route: direct`와 적용할 변경 의도를 보존하고,
관련 문서의 일관성을 다시 확인한 뒤 state를 마지막으로 Work 또는 Verify에 공개한다.
새 artifact도 기존 Direct checkpoint state를 먼저 만든 뒤 같은 공개 순서를 따른다.
변경할 상세를 먼저 완성하고 spec의 현재 선택 지도를 교체한 뒤 state를 공개한다. spec
교체만으로 Work 실행 권한이 생기지 않는다. 수정 중 state의 next_action은 영향을 받는
범위와 의도한 계약 변경을 복구할 수 있게 유지한다.
중간 중단은 Direct의 미완료 amendment로 복구한다. 수용 기준을 해석하는 상세 계약이 바뀌어도
기존 acceptance 변경과 같이 stale verification을 처리한다.

Verify는 root의 **전체 수용 기준**을 빠짐없이 판단하면서 criterion별 상세를 읽는다. Work가
마지막으로 만진 항목만 검증하지 않는다. 항목 체크·구현 순서·문서 존재는 `proven`을 대신하지
않는다. 요구 간 결합은 root의 통합 criterion으로 드러내며 각 부분이 맞는 것만으로 닫지 않는다.

Resume은 root와 현재 좌표·Git을 보고 방향을 찾는다. 상세의 일반 내용까지 선행 로드하지
않으며, 구체적인 불일치의 복구 owner 판단에 필요한 경우만 읽는다. 명시적 인계는 복구할 수
있어야 하지만 마지막 게시 이후의 대화·dirty 변경까지 무손실 복구한다고 주장하지 않는다.

## 6. 적용 위치와 비용 원칙

| 위치 | 최소 변경 의도 |
|---|---|
| Direct의 조건부 tracked 작성 reference | 적응형 spec 구성, 결과·수용 기준 표, 상세 분리 판단·작성 |
| 기존 공유 `work-state` | 상세도 같은 계약이라는 소유권·읽기·amendment 의미를 한 번 정의 |
| Work·Verify entry | 기존 spec/read_first 읽기 문장을 필요한 상세 선택까지 연결 |
| Resume·closure | 기존 방향 확인·디렉터리 수명 규칙으로 충분한지 확인. 필요 없는 중복 문구 추가 금지 |

새 스킬·runtime engine·검사기·범용 schema·자동 task scheduler는 제안하지 않는다.
템플릿은 Direct 작성 시에만 읽히는 기존 reference에 둔다. Work·Verify가 작성 안내 전체를
다시 읽지 않게 한다. ephemeral 경로는 tracked 작성 reference와 추가 상세를 읽지 않는다.

실제 비교할 비용은 스킬 문구 증가뿐 아니라 읽은 파일·문자량, 반복 읽기, 도구 호출, 구현과
재개의 오류를 포함한다. 문자 수를 토큰 수나 성능 향상으로 환산하지 않는다. 큰 문서를 나눠도
매번 전부 읽는다면 비용 개선은 없으며 다시 합치는 것이 맞다.

### 6.1 런타임 문구의 후보

다음은 기존 문구의 교체·통합을 검토할 초안이다. 기획서 전체를 스킬에 붙이지 않는다.
최종 배포 비용은 실제 편집·빌드 뒤 측정해야 하며, 아래 문구 길이를 순증 비용이라고 부르지 않는다.

Direct의 tracked 작성 reference에서 기존 의미 목록과 통합:

```text
spec은 배경과 의도, 지켜야 할 계약, 구현할 결과와 관찰 가능한 수용 기준을 연결한다.
각 기준은 상세를 열기 전에도 무엇을 관찰해 판정할지 설명한다.
결과가 여럿이면 짧은 목록이나 표로 구분하고, 반복 참조할 때만 식별자를 붙인다.
계약상 필수인 기술 선택은 이유와 함께 제약으로 명시하며 국소 구현 방법은 Work에 맡긴다.
이번 결과에만 필요한 상세는 공통 맥락을 spec에 남긴 채, 읽기 조건이 분명하고 실제로
함께 읽지 않아도 되는 concern만 spec/<concern>.md로 분리한다. 그 외에는 함께 쓴다.
```

기존 공유 상태 계약에서 같은 artifact의 의미를 정의:

```text
spec이 조건부 상세를 가리키면 그 상세도 Direct가 소유하는 같은 실행 계약이다.
전체 의도·공통 제약·수용 기준은 spec에서 판단하고, 현재 행동이나 criterion에 필요한
상세만 읽는다. 수용 기준 목록은 spec에만 두고 상세는 독립 state나 verdict를 갖지 않는다.
Direct는 관리권을 받은 뒤 상세, spec 순으로 조정하고 일관성을 확인한 후 state를 마지막으로
공개한다. 수용 기준의 의미를 바꾸는 상세 수정에도 기존 검증 무효화를 적용한다.
필요한 상세를 읽을 수 없거나 계약과 모순되면 기존 불일치 복구 경계를 따른다.
```

Work·Verify의 기존 입력 읽기 문장에는 각각 “현재 행동에 필요한 조건부 상세”,
“각 criterion에 필요한 조건부 상세”만 연결한다. 동일한 수정·소유권 설명을 복제하지 않는다.
Resume의 기본 경로는 상세를 열지 않는다. 상세가 없는 tracked 작업에 추가 파일 탐색을
요구하지 않으며, 상세 존재와 읽기 조건은 이미 읽는 spec에서 판단한다.

위 후보 본문은 각각 **297자·6줄 / 315자·6줄**이다. 코드 fence 제외, 공백·LF 줄바꿈 포함,
마지막 줄바꿈 제외로 센 값이며 토큰 수가 아니다. Direct 템플릿과 기존 문구 교체량, entry 연결
문장은 이 숫자에 포함되지 않는다. 따라서 최종 증가량이라는 의미도 아니다.

| 실행 경로 | 이 기획 때문에 읽을 내용 |
|---|---|
| ephemeral | tracked 작성·상태 reference와 상세는 추가로 열지 않음. 전체 entry의 연결 문구 비용은 남음 |
| 상세 없는 tracked | 기존 reference 안의 관련 설명은 읽음. 새 파일 탐색·상세 본문 읽기는 없음 |
| 상세 있는 Work | 공통 spec + 현재 행동에 필요한 상세. 현재성·필요성이 유지되는 이미 읽은 내용은 재사용 |
| Verify | 공통 spec의 전체 criterion을 판단하면서 필요한 상세를 선택. 전체 검증에서 모든 상세가 필요할 수도 있음 |
| Resume | 기본은 spec·state·Git. 소유자 판단에 필요한 불일치가 있을 때만 상세를 읽음 |

공유 의미를 별도 매뉴얼로 떼어 매번 추가 호출하기보다 이미 읽는 `work-state`에 짧게 통합하는
안이다. 실제 빌드 뒤에는 이 가정까지 포함해 비교하며, 이 표는 무조건적인 비용 절감 약속이 아니다.

## 7. 구현 전후 확인할 관찰

이 표는 개발 검증용이다. 스킬 프롬프트에 사례 목록으로 복사하지 않는다.

| 관찰 | 통과해야 할 내용 |
|---|---|
| 작은 수정 / 짧은 tracked 작업 | 불필요한 상세·식별자·진행 장부를 만들지 않음 |
| 하나의 큰 결과, 서로 다른 concern | root로 전체 의도를 이해하고 현재 concern만 골라 읽음 |
| concern 교차 작업 / 전체 Verify | 공통 불변식·결합 criterion을 빠뜨리지 않음 |
| 부분 구현 뒤 새 AI로 재개 | 실제 Git과 다음 행동을 대조해 완료 작업을 불필요하게 반복하거나 남은 요구를 유실하지 않음 |
| 국소 개선 / 계약 변경 | 전자는 Work에서 계속, 후자는 Direct가 같은 계약을 조정 |
| 상세 변경 도중 중단 / stale verification | 혼합 계약으로 Work를 시작하지 않으며 과거 판정을 현재로 오인하지 않음 |
| 잘못된 경로·상세 충돌·구버전 checkout | 추정 구현 대신 기존 복구/결정 경계로 보냄 |
| 독립 결과·통합 결과 / 종료 | 기존 분해 의미와 통합 검증, 종료 뒤 spec/를 포함한 artifact와 해당 member note가 남지 않음 |
| 상세의 지속 사실과 종료 | 필요한 사실은 기존 candidate·landing으로 판단되고 임시 계약은 장기 정본에 복제되지 않음 |

비교 대상은 동일한 의미를 가진 현재 단일 spec이다. 큰 예시가 존재한다는 이유만으로 새 구조가
우월하다고 판단하지 않는다. 먼저 단일 spec의 항목 구조와 기존 정본 route를 정돈한 대조군을
둔다. 최소 수정으로 같은 정확성을 얻으면 그 쪽을 선택한다. 직접 실행하지 않은 결과는
`unproven`으로 기록한다.
재개 시에는 실제 연 문서·관련 Git 탐색·잘못된 재구현도 함께 비교한다. 읽기량 감소를 얻기 위해
필수 계약을 생략하지 않는다. 단 한 번의 작은 비용 차이를 일반적인 성능 우위로 해석하지 않는다.

## 8. 합의·구현 경계

계획 baseline은 불변이다. 일반 임시 상세를 실행 계약에 포함하는 제안은 plan/08의 좁은 보조
자료 예외보다 넓으므로, 채택 시 `tests/README.md`의 차이 기록을 통해 명시적으로 관리해야 한다.
기존 state의 책임을 늘리는 변경은 이번 제안에서 제외한다. 현재 문서 작성 권한을 런타임
소유권 변경 승인으로 해석하지 않는다.

구현 착수 시에는 정돈된 단일 spec과 동일 계약의 조건부 상세를 먼저 대조한다. 문서 분리가
의도 유실 없이 필요한 읽기를 줄이는지 확인한 뒤, 현재 Skill Rails 방식으로 Direct 한 target의
작성·배포·새 사용 관찰을 완료하고 Work·Verify 소비 경로를 차례로 검증한다. Resume·closure는
먼저 기존 규칙으로 관찰하며 실제 빈틈이 확인될 때만 수정한다. 최종 연결 검증 전에는 해당
규칙을 완성된 전체 workflow로 보고하지 않는다.

## 9. 교차 검토 결과와 남은 검증

Orca run `run_bc9004b0a7c5`에서 Claude Fable medium과 high를 각각 실행했다. 최초 시작
receipt의 요청·실효 agent/model/effort가 일치함을 확인하고 후속 검토는 같은 세션을 재사용했다.

| 검토 | task | 결과 |
|---|---|---|
| medium 외부 조사 → 초안 비평 → 수정안 재검토 | `task_75437ed61be9` → `task_1b3cb0479cc9` → `task_4a78a2eb594f` | 최종 수용, 차단 잔여 없음. root 판정문과 중단·종료 관찰의 문구 보완 반영 |
| high 원래 설계·소스·증거 독립 감사 → 반론 교환 → 수정안 재검토 | `task_fb5ed5248a7b` → `task_a8ad720870a1` → `task_c4d3fa43ef2c` | 기획 후보 범위 승인, 차단 정정 없음. 초기 작성 checkpoint와 필요한 상세 누락 처리 보완 반영 |

핵심 이견은 그대로 합치지 않고 원문으로 재확인했다.

| 이견 | 수렴한 판단 |
|---|---|
| 큰 계획이면 기존 artifact 분해로 충분한가? | 독립 수용이 가능한 경우만 그렇다. 원자적 결과의 상세 문제는 남음 |
| `read_first`에 조건만 붙이면 변경이 더 작은가? | 기존 필수 읽기 의미를 바꾸므로 파급이 더 큼. 필수 맥락과 조건부 상세 지도를 구분 |
| 남은 항목을 state 또는 next_action에 열거할까? | 진행 장부를 추가하는 효과가 있어 제외. 정적 결과·실제 Git·다음 행동부터 검증 |
| root에 모든 상세 값을 복제해야 검증 가능한가? | 관찰할 판정은 root에, 정확한 상세 값은 한 곳에. 의미 변경이면 기존 검증 무효화 |
| 파일을 나누면 읽기 비용이 반드시 감소하는가? | 단일 문서도 절 단위로 읽을 수 있음. 실제 선택 읽기·재탐색·오류를 비교해야 함 |

코디네이터는 SealQL 현재 명세·전달·진행 문서를 읽었고, medium 검토자는 공개 원문과 Devflow
소스에 집중했다. 서로 다른 검토 범위를 한 명이 모두 검증한 것으로 표현하지 않는다. 외부
도구의 문서 구조에서 실제 비용 순위나 모든 안전장치의 부재를 추론한 표현은 채택하지 않았다.

이번에 완료한 것은 **소스·설계 대조, 외부 원문 조사, 반복 교차 검토와 구현 전 기획**이다.
새 source·배포 skill은 작성하지 않았고 §7의 행동 실험도 실행하지 않았다. 따라서 대형 원자
결과의 읽기 절감, 비선형 부분 구현 재개, 상세 amendment 중단, 종료·지식 착지의 실제 효과는
여전히 `unproven`이다. 이 구분을 유지하는 것이 이 기획의 완료 조건이다.
